## 这是什么

一套**可复现的智能体团队测评方法论 + 80 题题库**。

给同一个技术方案，让「单 agent」和「多 agent 团队」分别评审，
通过对照发现团队协作的真实价值与局限。

**已用它测评过 3 个智能体团队插件**：
- 官方 Agent Teams（DSH 内建）
- NanmiCoder Agent Teams
- 灵枢蜂巢 Hive

## 核心方法论：坑的深度（L1-L4）

| 层级 | 特征 | 谁会发现 | 报告质量 |
|---|---|---|---|
| **L1 语法/字面** | 一眼就错 | **所有人** | 冗余 |
| **L2 语义** | 需理解字段含义 | **所有人** | 冗余 |
| **L3 跨模块** | 需读多处代码 | 1-2 组 | 互补 |
| **L4 系统性** | 需理解整体设计 | **1 组** | **互补** |

> **结论：好的题要埋在 L3-L4。L1-L2 只能当及格线。**

## 四类考点

| 类型 | 定义 | 代表题 |
|---|---|---|
| **① 前提错误** | 方案引用了不存在的对象 | 出题者 bug，必须修 |
| **② 方案缺陷** | 设计本身有错 | N-15、N-24 |
| **③ 无用功** | 问题已经解决了 | N-29/30/32/42/67/68 |
| **④ 倒退** | 已有更好的实现 | **N-52** |

> **区分诀窍：**
> **③ = 方案说「需要做 X」，仓库已有 X**
> **④ = 方案用 A 方式，仓库已有更好的 B 方式**

## 六维度

| 维度 | 测什么 | 数据源 |
|---|---|---|
| **D1 计划结构** | 任务 DAG 是否合法 | 任务依赖 |
| **D2 调度效率** | 并行率 / 重复劳动 | 时间戳 |
| **D3 依赖正确性** | 顺序违规次数 | 任务状态 |
| **D4 通信质量** | 送达率 / 延迟 | 消息记录 |
| **D5 抗干扰** | 误信率 / 纠偏成功率 | **注入实验** |
| **D6 成本效率** | 每步 token / 插件开销 | 事件流 |

## 诚实记录：出题者的失误

**历史上有 8 次前提错误**（方案引用了不存在的表/列/文件）：

| # | 题 | 我写的 | 实际 |
|---|---|---|---|
| 1 | N-3 | `users.bio` | 无此列 |
| 2 | N-12 | `plugins.status` | 无此列 |
| ... | ... | ... | ... |
| 8 | N-61 | 「审核员」角色 | 系统无此角色 |

**根因**：
> **我把「印象中的项目」当成了「实际的项目」。**

**对策**：`scripts/verify-task-prereqs.mjs` —— 每题入库前自动核实表/列/文件/依赖。
