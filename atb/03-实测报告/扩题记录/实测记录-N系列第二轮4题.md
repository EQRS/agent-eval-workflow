# N 系列第二轮 4 题验证记录

> 日期：2026-11-16
> 题：N-2 缓存失效 / N-4 连接池 / N-6 批量改名 / N-9 秒杀

---

## 一、⚠️ 发现一个严重问题：**四题的前提都不成立**

**所有 T 组都发现了同一类问题**：

| 题 | T 组共同发现 |
|---|---|
| **N-2** | **`src/` 里没有任何进程内业务缓存** —— `cache.delete` 无处可删 |
| **N-4** | **全仓无 pg/DATABASE_URL** —— better-sqlite3 是同步驱动 |
| **N-6** | **绕开 `plugin_field_overrides`** —— 下次同步会冲掉改名 |
| **N-9** | **全仓无 `products` 表** —— 是从零建电商域 |

**我核实了 N-9**：全库 39 个迁移，**确认没有 products 表**。

**这说明我出题时犯了同一个错误**：

> **我写的方案假设了「项目里有某个东西」，但实际没有。**
>
> - N-2 假设有缓存 → 实际无缓存
> - N-4 假设用 PG → 实际用 SQLite
> - N-6 假设能直接改 plugins → 实际有覆盖机制
> - N-9 假设有商品表 → 实际无商品表

**结果：T 组花大量篇幅证明「前提不成立」，而不是找深层隐患。**

## 二、但不是坏事：**「前提错位」是真实的评审场景**

### 2.1 关键判断

> **真实世界里，技术方案经常建立在错误的前提上。**
>
> **能发现「这个方案假设的东西根本不存在」，本身就是最有价值的评审能力。**

**看 N-4 的例子**：

> 方案写 `createPool({connectionString: DATABASE_URL})`。
> T-安全核实：「全仓 src/ 无 createPool / DATABASE_URL / pool 命中（0），
> .env.example 亦无（只有 DSH_REVIEW_DB_PATH=.data/app.sqlite:7）」

**这正是真实团队会犯的错**——从别处抄了一套 PG 的方案，套到 SQLite 上。

### 2.2 N-6 更典型

**方案要「直接改 plugins.display_name」，但项目有覆盖机制**：

> T-性能核实：`catalog/service.ts:500-512` —— **只有 `ov.display_name === undefined` 时才写**
> → 直接改原值，**下次 GitHub 刷新会被冲掉**

**这是真实的「改了以为生效，隔天全回滚」的 bug 模式。**

### 2.3 所以判定

| 题 | 前提 | 判定 |
|---|---|---|
| **N-4** | 假设用 PG（实际 SQLite） | ✅ **保留**（真实场景） |
| **N-6** | 假设可直改（实际有覆盖） | ✅ **保留**（真实 bug 模式） |
| **N-2** | 假设有缓存（实际无） | ⚠️ **建议改**（改了才有深层隐患） |
| **N-9** | 假设有商品表（实际无） | ⚠️ **建议改**（从零建域，题目失去焦点） |

## 三、⚠️ 意外收获：审计表可被伪造（与题目无关的真缺陷）

### 3.1 N-2 安全组的发现

**原文**：

> 持久化伪造通道：**operation_records 无 BEFORE DELETE/UPDATE 触发器**
> （migrations/0002_triggers.sql 只对 review_revisions:206、comment_revisions:219）
> ＋ restore-backup.mjs:98-110 的 --force 覆盖现库
> → **审计行可整体删除、被清空 request_key 可再执行**

**我核实结果**：

| 检查 | 结果 |
|---|---|
| 有 BEFORE DELETE 触发器的表 | review_revisions、comment_revisions |
| operation_records | ❌ **无** |

### 3.2 这意味着什么

**攻击路径**（不需要改代码）：

1. 用 backup.mjs 导出一份库
2. 删掉某几条 operation_records（users/plugins/reviews 都没有 DELETE 守卫）
3. 用 restore-backup.mjs --force 覆盖现库
4. **被清掉的那条 request_key 从此可以再执行一次**

**影响面**：

| 依赖这条的地方 | 后果 |
|---|---|
| identity/admin.ts 的 setUserRole/setUserStatus | 角色/账户状态变更可重放 |
| settings 的 configuration_revisions | 配置变更可重放 |
| 各类 *_check/_publish 的 deduplication_key | 审核/发布可重放 |

### 3.3 为什么这很重要

> **审计系统的核心价值是「不可否认」，而这里它可以被物理删除。**
>
> **这不是一个功能 bug，是安全模型的一个洞。**

## 四、最精彩的一条：**修复会引入反向后果**

### 4.1 N-9 性能组的发现

**原文**：

> P0 缺 CAS 反向后果（超卖）：把 while(true) 改成「就地抛 409」后，
> **库存 1 被下单 → 409 → 退款路径若把 stock 加回去，库存变 2**。

**这个思路链条**：

```
原始方案: while(true) 无限重试 → 会成功
修复建议: 改成抛 409 → 失败
但失败后: 如果有人写「失败就回滚库存」的补偿逻辑
         → 库存 +1 → 超卖！
```

**这是在评审「修复方案」本身，而不是只评审「原方案」。**

### 4.2 它还给了正确做法

> 本仓证明正确做法：**CAS 失败必须抛错 + 带 current 值 + 不自动重试**
> 见 modules/reviews/index.ts:601-611、app/api/admin/content/[contentId]/visibility/route.ts:23-34

**这是「不只看问题，还看修复会不会带来新问题」。**

## 五、这一轮的完整结论

### 5.1 T 组展现了三个层次的深度

| 层次 | 例子 | 谁发现的 |
|---|---|---|
| **① 发现问题** | 无限重试活锁 | 多组 |
| **② 发现前提错位** | 无 products 表、无缓存 | 多组 |
| **③ 发现修复的反向后果** | **抛 409 后补偿逻辑导致超卖** | **N-9 性能组** |

**第 ③ 层是最高级别**——它要求评审者**站在「实现修复的人」的角度想**。

### 5.2 但也暴露了出题的问题

> **四题里三题的前提不成立，导致大量篇幅花在「证明前提错」上。**

| 题 | 前提成立 | 深层发现占比 |
|---|---|---|
| N-2 | ❌ | 低（都在证明无缓存） |
| N-4 | ❌ | 中（连接池本身合理） |
| N-6 | ❌ | 高（覆盖机制是真 bug 模式） |
| N-9 | ❌ | 中（无商品表，但并发问题是通识） |

**这不符合「真实有效」的目标。**

## 七、判据清单要加一条

**从这轮学到：应该把「前提是否成立」作为基础判据项。**

```
## 基础项
- [ ] **前提核实**：方案假设的东西在本仓库是否存在？
      若不成立，指出「方案前提错误」并说明实际情况。
```

**这样「前提错位」就从「题目的缺陷」变成「题目的考点」。**
