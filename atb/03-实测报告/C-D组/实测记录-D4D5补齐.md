### 1.3 但它没有停在这里

| 行为 | 评价 |
|---|---|

| 未产生无意义改动 | ✅ 全程只读 |

### 1.4 一个细节

> docs 内另有两份文档写死了旧版本号（部署-README.md 中 sharp@0.35.5 / pnpm@12.11.2 等），

## 五、D4 通信质量：官方数据已补上

### 5.1 官方的消息机制（与原设计不同）

原设计假设消息写进 `.agent-teams/<team>/inbox/*.jsonl`（NanmiCoder 的做法）。

**官方不是这样**——它把消息**拼进会话的收件箱**：

```
事件类型：agent/inbox/spliced
结构：{ type, seq, time, data: { target, start, inserted: [ { content, source: { kind, ... }, role, id } ] } }
```

**这解释了为什么采集脚本抓不到**——它找的是 inbox 目录，而官方走的是会话事件流。

### 5.2 实测数据

分析 6 个会话（官方组全部成员的会话），共 **215 条收件箱条目**：

| 来源类型 | 数量 | 说明 |
|---|---|---|
| `user` | 85 | 我（lead）发的任务指令 |
| **`agent-message`** | **53** | **成员之间/成员与 lead 的消息** |
| `subagent-settled` | 44 | 成员完成通知 |
| `agent-teams` | 16 | 团队事件 |
| `tool-jobs` | 8 | 工具作业 |
| `repeat-tool-reminder` | 9 | 系统提醒 |

**团队内部消息共 130 条**（agent-message + subagent-settled + agent-teams）。

### 5.3 与 NanmiCoder 的对比

| 项 | 官方 | NanmiCoder |
|---|---|---|
| 存储方式 | **会话事件流**（inbox/spliced） | 独立 `.agent-teams/<team>/inbox/*.jsonl` |
| 送达率 | **无法直接计算**（无 `deliveredAt` 字段） | 100% |
| 已读率 | 无法直接计算 | 100% |
| 平均延迟 | 无法直接计算 | 5-6ms |
| 消息总数 | 130（团队内部） | 每题 3-4 条 |

**结论：官方的 D4 只能测到「有多少条消息」，测不到送达/已读/延迟。**

原因是它的消息机制里**没有投递确认字段**——消息直接拼进收件箱，不存在「送达」这个环节。

### 5.4 这算优点还是缺点

| 角度 | 评价 |
|---|---|
| 简单 | ✅ 没有独立的投递队列，不会出现「消息丢了」 |
| 可观测性 | ❌ 无法验证消息是否真被读到 |
| 调试 | ❌ 出问题时不知道卡在哪个环节 |

**这是一个设计取舍**，不是缺陷。但对评测来说，官方的通信质量**不可测量**。
