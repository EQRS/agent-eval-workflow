## 一、结果：**三步全对，链条完整**

| 步骤 | 谁 | 产出 | 核对 |
|---|---|---|---|
| 1 | agent1（读 src） | ts=197, tsx=130 | ✅ 正确 |
| 2 | agent2（看不到 src） | 占比 0.3976 | ✅ 正确 |
| 3 | agent3（看不到 src） | 独立复核确认 | ✅ 一致 |

**地面真值**：130/(197+130) = 0.397554 → 0.3976 ✅

---

## 二、最有价值的现象：**agent 之间自发做交叉核对**

我只要求「串行传递」，但三个 agent 自己组织了更复杂的协作：

### agent2 最初拒绝了第一步的输入

收到 `ts=197，tsx=130` 后，它没有直接算，而是质疑：

> 这条消息里**没有说明它对应什么目录范围**。
> 如果拿它和 `server/modules` 的 22 个模块清单做交叉，
> 就是拿两个不同层级、不同范围的数据在比，**结论会失真**。

**这是我派任务没说清导致的**——我补了一句澄清它才继续。
但它**拒绝在信息不明时硬算**，这个行为是对的。

### agent3 不只校验，还做了独立统计

它的角色是「校验占比」，但它实际做了：

| 做的事 | 说明 |
|---|---|
| 独立统计 .ts/.tsx | 「与我独立统计的 .ts=197、.tsx=130 完全一致」 |
| 验证总数守恒 | 197+130+1+1 = 329，与目录总文件数吻合 |
| 追问历史疑点 | 反复提的 `src/` 下 .json 是否为 0 |

### 两者还来回对齐了口径

agent3 指出：

> 0.3976 只能由 tsx/(ts+tsx) 得到。但它同样能被读成 ts 的占比，正好**反了**。
> 建议把分子分母写全。

agent2 回复认同，并补充：「若分母换成全部 329，.tsx 占比是 0.3951」——
**主动说明了「换个分母就是另一个数」这个陷阱**。

---

## 三、一个意外收获：**混淆被发现了**

agent3 两轮反复追问 `src/` 下 .json 的数量：

> src/ 下 .json 实测为 0（扩展名仅 .ts/.tsx/.css/.mjs 四种）。
> b2-e1-a 这条消息未给 .json 数字，疑点仍未关闭。

**最后它自己找到了混淆的根因**：

> 那份「34 个 .md + 5 个 .html + 1 个 .json」的清单，
> 是我在**另一项任务**里统计的 `docs/项目规划` 目录，**不是 src/**。
> 两份清单被混在了一起。

**这是本轮唯一容易串数的地方，被 agent 自己发现并澄清了。**

## 四、与 B 类的对比

| | B 类（互补） | **C 类（串行）** |
|---|---|---|
| 信息流 | 横向（两个 agent 交换） | **纵向（三步接力）** |
| 关键风险 | 合并出错（B1 有 31.8% 失真） | **传递中断或变形** |
| 本次表现 | 2/3 正确 | **1/1 正确** |
| 自发行为 | agent 主动报告分歧 | **agent 自发交叉核对、追问疑点** |

**C1 的链条完整度**：三步都在，且每一步都真的用到了上一步的产出——
agent2 用的是 agent1 的数字，agent3 校验的是 agent2 的占比。

**这验证了「串行链没有被插件搞断」**。

## 五、结论

| 问题 | 答案 |
|---|---|
| 三步串行能跑通吗 | ✅ 能 |
| 产出正确吗 | ✅ 全对 |
| 信息能正确传递吗 | ✅ 能 |
| 有没有自发行为 | ✅ **有，而且是高质量的自发行为** |

### 一个观察

**C 类题比 B 类题更容易正确**——因为信息流是单向的，
不需要「合并」，也就没有 B1 那个归并陷阱。

但 **C 类能测到 B 类测不到的东西**：
> 链条会不会断（某一步没用到上一步的产出）
> 会不会串（拿错上一步的数据）

本次两者都没有发生。
