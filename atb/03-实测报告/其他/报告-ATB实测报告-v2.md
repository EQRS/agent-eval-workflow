## 摘要：结论已修正

**v1 结论**（问题数倍数）：

> ~~专业身份使 T 组问题数达单干的 2.3-3.0 倍~~

**v2 结论**（盲区覆盖）

> **协作的价值在「覆盖不同的盲区」，而不在「发现更多问题」。**
>
> M-9v3 给出了最直接的证据：**S 组漏的是「安全」，T-安全漏的是「运维」**。
> **问题数几乎一样（7 vs 7），但漏的维度不同。**

## 二、为什么修正结论

### 2.1 M-9v3 的反例

| 组 | 命中 | 漏掉 |
|---|---|---|
| **S 组** | 7/9 | **安全维度**（评分可被刷） |
| **T-安全** | 7/9 | **运维维度**（无灰度） |

**问题数一样，但盲区不同。**

### 2.2 这说明什么

> **单干不是「看得少」，是「看不到某些维度」。**
>
> 一个认真读过项目代码的 agent，能发现 7 个问题；
> **但它不会想到「评分能不能被刷」**——那需要安全领域的思维习惯。

## 三、M-9 的三次迭代（方法论演进）

**这一节记录我是怎么把一道坏题改成好题的。**

| 版本 | 素材 | S 组表现 | 判定 | 原因 |
|---|---|---|---|---|
| **v1** | 裸 Map 缓存（问题浮在表面） | 9/9 全中 | ❌ **作废** | **判据清单和素材同目录，泄题** |
| **v2** | LRU 缓存（成熟方案） | 7/8 | ❌ **作废** | 隐患仍是「读代码就能看到的事实」 |
| **v3** | 贝叶斯排序（**看起来完全符合最佳实践**） | 7/9（漏安全） | ✅ **合格** | 隐患需要专业视角 |

### 3.1 v1 的错误：泄题

**我把判据清单放在 `docs/` 下，和素材同目录。**

S 组报告末尾有：「**附：M9 判据覆盖自查**」，直接引用了清单编号 S-1/S-2/P-1…

**修正**：清单移到 `_work/判据清单/`，agent 读不到。

### 3.2 v2 的错误：隐患太直白

**v2 的素材是「成熟方案」（用 LRU、有失效、有监控），但隐患仍然是**：

| 隐患 | 发现方式 |
|---|---|
| 撤回路径不写 reviews 表 | 打开 `withdraw/route.ts` 就能看到 |
| featured 6 个写点 | grep 一下就找到 |
| worker 双进程 | `db.ts:67` 注释写着 |

**「认真读就能发现」≠「需要专业视角」。**

### 3.3 v3 的正确做法

**素材设计成「看起来完全符合业界最佳实践」**：

| 设计点 | 看起来如何 |
|---|---|
| 贝叶斯平均 | ✅ 确实是标准解法（IMDb Top 250 用的就是它） |
| m=10 可调 | ✅ 有调整计划 |
| 每小时重算 | ✅ 标准做法 |

**但隐患是**：

| 隐患 | 通用 agent 会想到吗 |
|---|---|
| 项目没有 1-5 分 | ⚠️ 要主动查迁移 |
| **评分可被刷** | ❌ **不会**（要安全思维） |
| **全表重算写放大** | ❌ **不会**（要性能思维） |
| **排序变更无灰度** | ❌ **不会**（要运维思维） |

## 四、出题标准（最终版）

### 4.1 五条标准

| # | 标准 | 反面例子 |
|---|---|---|
| 1 | 素材不能自包含，要结合项目代码 | 纯代码片段 |
| 2 | 问题不能浮在表面 | 「Map 无上限」一眼可见 |
| 3 | 要有现成实现可对照 | 无法发现「重复造轮子」 |
| 4 | **隐患必须是「需要专业视角才会想到查」** | v1/v2 的失败 |
| 5 | **判据清单绝不能让 agent 看到** | v1 的泄题 |

### 4.2 第 4 条的判断方法

**自问一句**：

> **一个认真的通用 agent，不切换专业视角，会不会想到去查这个？**
>
> 会 → **不合格**，删掉重做
> 不会 → 合格

**合格/不合格的例子**：

| 隐患 | 通用视角会想到吗 | 判定 |
|---|---|---|
| 「撤回路径不写 reviews 表」 | ✅ 会（grep 就找到） | ❌ |
| 「Map 无上限」 | ✅ 会（一眼可见） | ❌ |
| **「provider 来自 URL → SSRF」** | ❌ **不会** | ✅ |
| **「逐行 UPDATE 拖垮全站」** | ❌ **不会** | ✅ |
| **「评分可被作者自刷」** | ❌ **不会** | ✅ |
| **「排序变更无灰度」** | ❌ **不会** | ✅ |

### 4.3 素材设计的关键技巧

> **让方案的写法本身是「合理的」——问题在专业判断上，不在代码写法上。**

| 题 | 方案写法（看起来合理） | 专业问题 |
|---|---|---|
| M-7 | `GET /api/auth/{provider}/start`（标准 RESTful） | provider 可控 → SSRF |
| M-8 | 「直接返回 BLOB」（最简单的下载实现） | Content-Type 攻击者可控 → XSS |
| **M-9v3** | 贝叶斯平均（业界标准算法） | **输入可被刷、违反项目哲学** |

## 五、失败的三个设计（保留教训）

### 5.1 材料量大 ≠ 需要协作（M-4）

S 组用 **AST 正则机械提取** 做到 327/327 文件 100% 覆盖，依赖图 28 条全对，**成本 1.0×**。

> 可机械化的任务，单 agent 也能全量覆盖。

### 5.2 显式多视角无效（M-5）

S 组**自己想到了额外维度**（主动查了「别名导入」「文档同步」），成本仅 1.1×。

> 「换个角度」单 agent 也能做到——只要告诉它去看什么。

### 5.3 耗时不固定

| 题 | 倍数 |
|---|---|
| M-6 | **3.6×** |
| M-7 | **0.9×**（更快） |
| M-8 | 1.2× |

> 取决于「最慢的专业 agent 需要多深推理」。

## 六、设计自检

### 6.1 站得住的部分

| 项 | 证据 | 可靠度 |
|---|---|---|
| **专业身份覆盖不同盲区** | 四题验证（M-9v3 最直接） | **高** |
| 成本 1.4-1.9 倍 | 三题稳定 | 高 |
| 判据可机械判定 | 清单打分 | 高 |
| boundary/依赖/采集 | 全部验证 | 高 |

### 6.2 必须守住的四条纪律

| # | 纪律 |
|---|---|
| 1 | **S 组绝不能被提示维度** |
| 2 | **判据清单绝不能让 agent 读到** |
| 3 | **隐患必须需要专业视角** |
| 4 | **每题用全新 agent**（subagent 不占名额） |

### 6.3 已知局限

| # | 局限 |
|---|---|
| 1 | 只测了一个模型 |
| 2 | 判据依赖人工核对（可用清单部分自动化） |
| 3 | 耗时不稳定，样本少 |
| 4 | M-9v3 的 S 组成本未采集 |

## 七、扩题库标准模板

```
【素材】一份看起来完全符合最佳实践的技术方案
       —— 问题在专业判断上，不在代码写法上
【S 组】1 个 agent（subagent，全新上下文）
       —— 只给任务，**不提示任何维度**
【T 组】3 个 agent，各带专业身份（安全 / 性能 / 运维）
【判据清单】放在 _work/ 下，**agent 读不到**
【评分】按清单逐项打勾
```

## 八、最终结论

### 8.1 设计有没有大问题

> **没有。核心机制已被四题验证。**

### 8.2 可以扩题库了吗

> **可以。**
>
> 模板已验证、判据可判定、成本可预期。

### 8.3 一句话总结

> **协作的价值不是「看得更多」，是「看到不同的盲区」。**
>
> 单干能发现 7 个问题，但漏掉的那 1-2 个恰恰是它想不到的维度。
> **多专业协作让每个维度的盲区都有人看。**
