## 三、N-15 是最典型的例子

**我核实了它的核心发现**：

| 文件 | `body_markdown` 引用数 |
|---|---|
| `src/worker/content-screen.ts` | 12 |
| `src/server/modules/reviews/index.ts` | 8 |
| `src/app/reviews/[reviewId]/page.tsx` | 6 |
| `src/app/api/reviews/[reviewId]/route.ts` | 4 |
| `src/server/modules/search/index.ts` | 2 |
| **合计** | **32 处** |

**方案的 `readBody()` 只覆盖 1 处**。

> **清理后，其余 31 处直接 SELECT 会读到空正文**
> → **公开详情页静默显示空白，不报错**

**这个发现需要顺着 32 处引用排查——只有真正读代码才能发现。**

## 四、根因分析：**我为什么会犯这个错**

| 环节 | 我的做法 | 应该做的 |
|---|---|---|
| 构思 | 凭印象写「users 有 bio 列」 | **先查 `0001_baseline.sql`** |
| 写代码块 | 凭印象写 `input.status` | **先 grep `status` 在 plugins 里** |
| 设计 SQL | 凭印象写 `DELETE FROM review_revisions` | **先查有没有触发器** |

**核心问题**：

> **我把「印象中的项目」当成了「实际的项目」。**

---

## 五、得出的出题纪律（第 6 条）

> **方案里提到的每个表、列、接口、现有实现，都必须先用脚本核实存在。**

**具体做法**：

```
1. 列出方案要用的所有表名 → grep CREATE TABLE
2. 列出方案要用的所有列名 → grep 对应表定义
3. 列出方案要改的表 → 查有没有触发器/外键
4. 列出方案要用的现有函数 → grep 函数名
5. 全部通过才动笔
```

## 六、附带发现：T 组独立验证了「审计表可伪造」

**N-5 的安全组报告里出现了这一段**：

> 「审计取证链本身有既存缺口：`operation_records` 无 `BEFORE DELETE/UPDATE` 触发器；
> `restore-backup.mjs:110` 用 `copyFileSync` 整库覆盖；
> `backup.mjs:72` 的 counts 不含 `operation_records`」

**这与我在另一张修复单（`安全修复单-审计表可被删除.md`）里的发现完全一致。**

> **两个独立的 agent 在不同题目的评审中，都发现了同一个真实缺陷。**
> **这是「多专业协作」价值的另一种体现——交叉印证。**

## 七、N-15 安全组又挖到一个新维度

**它的核心发现**：

> §3 的 `readBody()` 只按 id 查、**完全不经过鉴权与可见性判定**
> 等于给所有私有正文开了一条**无门禁的读通道**

**对比真实读路径**：

| 真实路径 | 做了什么 |
|---|---|
| `api/reviews/[reviewId]/route.ts:43` | `resolveVisibilityInTx` 判定可见性 |
| `route.ts:59` | `JOIN published_revision_id` |
| `revisions/route.ts:100-106` | `canReadBodies` 才能拿正文 |

**方案的 `readBody()` 一个都没有。**

**这比「会读到空正文」更严重——它是「越权读」。**

## 八、这次重跑的方法论价值
