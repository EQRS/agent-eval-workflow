# B1 重跑记录 · agent 直接通信版

> 日期：2026-11-16
> 环境：官方 `dsh-experimental-agent-team-profile@0.2.2-rc.1`
> 改进：agent1 直接 send_message 给 agent2，不经过 lead 合并

---

## 一、结果：**答案接近正确，但暴露了信息传递损耗**

| 项 | 首次跑（lead 合并） | **重跑（agent 直连）** |
|---|---|---|
| 最终答案 | 7 个 ✅ | **8 个**（多了 imports） |
| 正确值 | 7 个 | 7 个 |
| 逐模块数值 | 全部正确 | **7 个模块偏低** |

**重跑的最终答案错了一个**——把 `imports` 误判成「只被 1 个测试引用」。

---

## 二、逐模块对比：7 个偏低

| 模块 | 正确值 | agent2 算成 | 偏差 |
|---|---|---|---|
| catalog | 13 | 7 | **-6** |
| identity | 11 | 7 | -4 |
| imports | **2** | **1** | **-1** ← 导致最终答案错 |
| media | 3 | 2 | -1 |
| moderation | 3 | 2 | -1 |
| roles | 5 | 4 | -1 |
| tasks | 5 | 4 | -1 |

**规律：全部偏低，没有一个偏高。**

### 根因

agent1 是**按子路径分行报告**的：

```
catalog=7
service=6
types=6
discovery=1
parse-url=1
```

agent2 合并时**取的是某一行的值，而不是并集**——
导致「同一测试文件引用同一模块的多个子路径」被漏算。

**agent2 自己在报告里其实意识到了这个陷阱**：

> 特别注意 imports 和 tasks 这种「一行=1、但有多行」的情况

但它对 `imports` 的判断仍然错了——它以为两行都是同一批测试，
实际是 `author-import.test.ts` 和 `plugin-import.test.ts` 两个不同文件。

---

## 三、这次重跑最大的价值：**暴露了信息传递损耗**

首次跑（lead 合并）结果是**完全正确**的，因为是我自己做的合并。
重跑（agent 直连）反而错了——**这才是真实的多 agent 协作的样子**。

| 对比 | 首次跑 | 重跑 |
|---|---|---|
| 谁做合并 | **lead（我）** | agent2 |
| 结果 | 完全正确 | 错 1 项 |
| 说明 | 测的是「信息是否互补」 | **测的是「协作能否无损传递」** |

**首次跑只验证了一半**——证明了信息互补成立，但没测到协作的真实损耗。

### 这是一个真问题，不是 bug

多 agent 协作的核心风险就是**信息在传递中失真**：

| 环节 | 可能丢失的信息 |
|---|---|
| agent1 组织输出 | 按子路径分行，丢了「这些是同一个模块」的聚合 |
| 消息传递 | 内容完整（send_message 没丢） |
| agent2 解析合并 | 取单行而非并集 |

**这恰恰是评测该抓的**——插件能不能让协作**无损**，比「能不能协作」更重要。

## 四、对 B1 题目的改进建议

**问题**：agent1 的输出格式有歧义，导致合并容易错。

| 现在 | 建议改成 |
|---|---|
| agent1 自由组织输出 | **规定输出格式**：一行一个模块，值为「不同测试文件数」 |
| 不要求说明归并规则 | 要求 agent1 在消息里**写明归并规则** |

**但这会让题变简单**——如果格式死板，agent2 就没法犯错了。

**两难**：

| 选项 | 好处 | 坏处 |
|---|---|---|
| 严格规定格式 | 能测「合并能力强不强」 | 测不到「信息组织能力」 |
| 放开格式 | 能测真实的协作损耗 | 答案不稳定，判分难 |

**建议：保留放开格式，但把它变成一个观测项**——
记录「信息传递损耗率」（错误的数值项 / 总项数），作为 D4 通信质量的指标。

本次损耗率 = **7 / 22 = 31.8%**。

## 五、两个有价值的正面发现

### 5.1 agent1 主动提示了同伴一个口径风险

它在发给 agent2 的消息里加了：

> 我主动提示了 b2-e1-a 一个口径风险：`server/platform/context` 43 个测试文件引用
> （含 15 个从最外层引入的），属测试基础设施复用，不宜直接等同「业务模块被测试覆盖」。

**这是自发的**——没人要求它提醒同伴口径问题。

### 5.2 agent2 也声明了数据可靠性边界

> 我只读了目录列表，没有读任何模块内部代码。所有引用数值来自 agent1，我只做归并和判定。

> 如果 agent1 那边有遗漏的模块，我的 22 个清单仍然完整，因为它是从目录直接枚举的。

**它准确区分了「我验证过的」与「我复述别人的」。**

## 六、结论

| 问题 | 答案 |
|---|---|
| agent 间直接通信可行吗 | ✅ 可行 |
| 信息互补成立吗 | ✅ 成立（首次跑已证） |
| **协作能无损传递吗** | ❌ **不能**——31.8% 的数值失真 |
| 最终答案正确吗 | ❌ **差 1 项**（imports 误判） |

### 这轮最重要的收获

> **首次跑「完全正确」是个假象**——那是我（lead）自己合并的。
> 重跑让 agent 自己协作，立刻暴露了 31.8% 的信息损耗。

**这说明评测设计必须让 agent 自己完成全流程**，
lead 代劳合并会掩盖真实问题。
