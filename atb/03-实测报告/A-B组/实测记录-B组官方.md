# 实测记录 · B 组（官方 Agent Teams）

> 对象：`@deepseek-ai/dsh-experimental-agent-team-profile`（0.2.2-rc.1，4 包组合）
> 团队：`@nanmicoder/dsh-agent-teams` 已从 bundles 移除
> 模型：deepseek-v4.1-flash-fastest
> 日期：2026-11-15

---

## 一、最重要的差异：工具面完全不同

| 能力 | 官方（原语层） | NanmiCoder（产品层） |
|---|---|---|
| 建队 | ❌ **没有这个概念** | `agent_teams_create` |
| 招人 | `spawn_teammate` | `agent_teams_add_member` |
| 建任务 | `team_task_create` | `agent_teams_create_task` |
| 指派 | `team_task_update` (reassign) | 建任务时传 assignee |
| 查状态 | `team_task_list` | `agent_teams_status` |
| 发消息 | `send_message` | `agent_teams_send_message` |

**官方是原语层**：没有「团队」实体，直接招人、建任务、指派。

## 二、机制差异：官方**不自动分配任务**

实测：建了 4 个任务，**25 秒后仍然全部 `pending`、无归属**，需要显式指派。

| | 官方 | NanmiCoder |
|---|---|---|
| 建任务后 | 一直 pending，等人指派 | 调度器自动分给空闲成员 |
| 谁决定分工 | **人 / lead** | **调度器** |

这不是缺陷，是哲学差异：
- NanmiCoder 把「谁做什么」交给调度器
- 官方把「谁做什么」留给人

**对使用者的意义**：官方更可控但更费心；NanmiCoder 更省心但可能不如人意
（比如首跑时 4 个任务全给了 A，B 一直空着）。

### 分成员看

| 成员 | token | 步数 | 缓存 |
|---|---|---|---|
| b-e1-a | 743,688 | 17 | 95.8% |
| b-e1-b | 559,039 | 14 | 92.5% |

### 重跑后的结论：官方仍贵 51%

排除返工污染后（重跑数据干净，两个成员都是 2 轮），官方仍然比 NanmiCoder 贵 51%。

**可能的原因**：

1. **官方没有调度器**——任务要我手动指派，多了一次交互往返
2. **成员各自的验证更重**——b2-e1-b 一个人跑了 95.8% 缓存、15 步，
   做了三路反证（文件名含 json / 扩展名以 .json 开头 / 隐藏文件）
3. **原语层缺少「团队上下文」共享**——每个成员从头开始，不像 NanmiCoder 有团队级状态

**但这个对比不完全公平**：官方的成员做了更重的验证，
如果 C 组也要求三路反证，差距可能缩小。

## 五、产出质量：官方也要人盯着

### 5.1 两个成员都做了超出要求的验证

| 成员 | 做了什么 |
|---|---|
| b-e1-b | glob + python os.walk **双路独立统计**，130 条清单逐条比对 0 差异 |
| b-e1-a | **三条通路**交叉验证（os.walk / PowerShell / ripgrep）确认 .md = 0 |

b-e1-a 的补充很到位：

> 197 + 130 = 327，加 .css 1 + .mjs 1 = 329，账是平的。
> 如果 b-e1-b 报的 .tsx 不是 130，也能立刻发现。

**它自己建立了交叉校验关系**，不只是在报数字。

### 5.2 但也要人纠正

b-e1-a 第一次把「统计 src/」理解成「统计整个工作区」，
扫了 59 万文件、14.37 GB，还顺带发现了一个真实的环境问题（见下）。

**说明官方这套更需要人盯着任务描述**——它不会像 NanmiCoder 那样被调度器约束范围。

## 六、意外的收获：发现工作区非法路径

b-e1-a 在跑偏的那一轮里发现：

```
<本机路径>
```

这是 Windows 保留设备名目录。**我核实它确实存在。**

**后果**：

| 工具 | 表现 |
|---|---|
| `glob` 全仓搜索 | 报「系统找不到指定的路径」直接失败 |
| PowerShell `Get-ChildItem -Recurse` | 同样报错，返回空集 |

**这会让任何全仓检索静默失败**——不是给出错误结果，是直接失败或返回空。

这不是本次评测的目标，但值得单独记一笔。

## 九、E2 依赖链：官方**强制阻断**，比 NanmiCoder 更严

### 9.1 机制对比：直接拒绝指派被阻塞的任务

我试图把三个任务同时指派给三个成员，结果：

```
task-9  → b-e2-a  ✅ in_progress
task-10 → b-e2-b  ❌ 报错：team task "task-10" is blocked
task-11 → b-e2-c  ❌ 同样 blocked
```

**这是官方依赖机制生效的直接证据**——它不允许你提前把活派下去。

对比 NanmiCoder：它允许指派，靠调度器在执行时判断依赖。

### 9.2 解锁时序（实测）

| 时刻 | task-9 | task-10 | task-11 |
|---|---|---|---|
| 建任务后 | pending | pending（blocked） | pending（blocked） |
| task-9 完成后 | **completed** | **ready=true** | pending（仍 blocked） |
| task-10 完成后 | completed | **completed** | **ready=true** |

**每一环都是前驱完成后才解锁**，零违规。

### 9.3 成本：官方贵 51%（与 E1 一致）

| 成员 | 任务 | token | 步数 | 缓存命中 |
|---|---|---|---|---|
| b-e2-a | t1 读依赖 | 393,938 | 8 | 69% |
| b-e2-b | t2 写介绍 | 485,851 | 12 | 94% |
| b-e2-c | t3 核对 | 267,882 | 7 | 44% |
| **合计** | | **1,147,671** | **27** | — |

| | C（NanmiCoder） | B（官方） | 差异 |
|---|---|---|---|
| 总 token | 760,161 | **1,147,671** | **+51.0%** |
| 步数 | 20 | **27** | +35% |

**注意成本分布反过来了**：

| | C 组 | B 组 |
|---|---|---|
| 最贵环节 | **核对**（524,588，69%） | **写介绍**（485,851，42%） |
| 核对环节 | 524,588 | **267,882** |

**C 组的核对环节是 B 组的 2 倍**——因为 C 组的 reviewer 去读了源码验证用法，
而 B 组的 b-e2-c 受限于「只读 package.json」的约束，没去查配置。

### 9.4 一个值得记的细节

b-e2-c 明确说：

> 仅凭 package.json 只能说「jsdom 依赖已安装、版本 27」，不能断言其用途。
> 建议核对 vitest.config 后再定稿（需要你放行我读该配置文件）。

**我核实了：vitest.config.ts 的 environment 是 'node'，不是 jsdom。**

也就是说 b-e2-c 的判断**方向完全正确**——它没有轻易下结论，
而是说「无法确认，需要看配置」，并主动请求放行。

**这比直接断言「jsdom 用于测试」要好。**

### 一个反直觉的总结

**官方在「一个成员做一件小事」时更省（-20%），
但在「多个成员协作」时更贵（+34%~-51%）。**

可能的解释：

1. 官方没有团队级共享状态，每个成员从头开始
2. 官方需要人工指派，多了一次交互往返
3. 官方成员做了更重的验证（但也因此发现了更多问题）
