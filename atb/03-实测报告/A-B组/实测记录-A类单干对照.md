## 二、A2：单干比协作多找出 1 张表

**B2 协作结果**：77 张（不含虚拟表）

**A2 单干结果**：**78 张**（77 普通 + 1 虚拟表 `review_search`）

**A2 的说明**：

> 78 = 77 张普通表 + 1 张虚拟表（review_search，CREATE VIRTUAL TABLE）。
> 若只要普通实表，则是 77。

**我核实：78 是对的**（含虚拟表），83 distinct − 5 个 _new = 78。

**B2 为什么少 1 张**：它的 agent1 只匹配了 `CREATE TABLE`，
漏了 `CREATE VIRTUAL TABLE`——这个漏洞是 B2 的 agent2 事后发现的，
但当时已经给出了 77 这个答案。

**A2 单干时一次性匹配了 `CREATE [TEMP] [VIRTUAL] TABLE`，所以没漏。**

## 四、对照结论：**协作在这三题上没有优势**

| 题 | 单干 | 协作 | 结论 |
|---|---|---|---|
| A1 vs B1 | 7 个，一次通过 | 7 个，一次通过 | **平手** |
| A2 vs B2 | **78 张，正确** | 77 张，少 1 张 | **单干胜** |
| A3 vs C3 | **0 轮自学自纠** | 5 轮被驳 | **单干胜** |

**这个结果与预期相反。**

v2 设计时的假设是「B/C/D 比 A 好」，用来证明协作的价值。
**实测结果是：单干在这三题上不输，甚至更好。**

---

## 五、为什么单干反而更好？三个原因

### 原因 1：B 类题的「信息封锁」反而制造了错误

B1/B2 通过 boundary 让两个 agent 各看一半，**但这引入了合并环节**。

| 题 | 协作的问题 |
|---|---|
| B1 | agent2 合并时取单行而非并集，31.8% 数值失真 |
| B2 | agent1 只匹配 CREATE TABLE，漏了 VIRTUAL |

**单干没有合并环节，所以不会在合并上出错。**

### 原因 2：C3 的「提议」环节本身就是多余的

单干时 agent 想到 3 条 → 自查 → 全部撤回。
协作时是：agent2 提 3 条 → agent3 驳 3 条 → 来回 5 轮。

**单干把「提议」和「评审」合并到同一个 agent 里，省掉了传递环节。**

### 原因 3：这个模型有很强的自查能力

A3 自己想到了「要核查文档是否已存在」，并且真的去 grep 了。

**这说明在「有明确核查标准」的任务上，单干的自我监督够用。**

## 六、这对题库设计意味着什么

### 6.1 v2 的核心假设被推翻了

| 假设 | 实测结果 |
|---|---|
| B/C/D 比单干好，能证明协作价值 | ❌ **不成立**——单干不输甚至更好 |

### 6.2 但不是「协作无用」

**A 类只跑了 3 题，样本太小。** 而且：

| 未测的场景 | 可能协作更好 |
|---|---|
| 任务量超过单 agent 上下文 | 需要分工 |
| 需要并行（时间敏感） | 协作省时间 |
| 需要多视角（如安全审查） | 协作带来盲区互补 |

**当前 12 题都是「小任务」，本来就适合单干。**

### 6.3 真正的问题：**题目规模太小**

| 题 | 规模 |
|---|---|
| B1/B2/B3 | 读 2 个目录，算个数 |
| C1/C2 | 3 步机械流程 |
| D2 | 算平均行数 |

**这些任务一个 agent 十秒到一分钟就能做完，本来就不需要协作。**

**协作的价值要在「一个 agent 做不完」的任务上才能体现。**

---

## 七、结论

| 问题 | 答案 |
|---|---|
| A 类跑通了吗 | ✅ 三题都完成 |
| 单干比协作好吗 | **在现有 12 题上是——A2 更准、A3 更快** |
| 协作没用吗 | **不能这么说**——题目规模太小，没测到协作的真正价值 |
| 题库该怎么改 | **扩大题目规模**，让单 agent 做不完 |

**最重要的发现**：

> **当前题库测的是「小任务上的协作」，而小任务不需要协作。**
> 要测协作价值，题目必须大到「单 agent 装不下」。
