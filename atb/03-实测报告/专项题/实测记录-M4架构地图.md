## 二、S 组的表现：超出预期（**我差点错判它**）

### 2.1 它没有「逐文件读」，而是「机械提取」

> import 关系覆盖 **327/327 个文件（100%）** —— 用 AST 级别的正则机械提取，非人工抽样。
> 共提取 **1637 条 import 边**。

**这是聪明的做法**——58 万 token 逐文件读不完，但机械提取能覆盖全量。

### 2.2 我一度误判：28 条是对的

**我最初认为 S 组的 `comments → tasks` 是误报，实际是我错了。**

我当时的检测只匹配静态 `from '...'`，而这条是**动态 import**：


**实际代码（comments/index.ts:249）**：

```ts
cachedTasksModule = (await import('@/server/modules/tasks/service')) as TasksModule;
```

**我核实后确认：28 条边是对的，S 组没问题。**

| 我的检测 | 结果 |
|---|---|
| 只匹配 `from '...'` | **漏掉动态 import** → 算出 27 |
| 加上 `import(...)` | **正确算出 28** ✅ |

### 2.3 为什么这个错误很典型

S 组用机械提取拿到了 1637 条 import 边，**但在归类到模块时，
把`taskType` 这个字段名误当成了对 tasks 模块的引用**。

**这是我的第 5 次同类误判**（M-3 两次、M-4 两次、D1 一次）：

> **用关键词匹配去判语义，而语义的结构比关键词复杂。**
>
> 这次是：**漏了动态 import 这种语法形式。**

## 三、T 组发现的关键架构事实（S 组没提）

### 3.1 **页面与 API 是两条独立通路**

**agent2 的发现**：

> 50 个页面里 **37 个直接 import `@/server/modules/*` 调服务层**，
> **不走 fetch 自己的 API**。
> **0 个客户端 page**（全是 Server Component）。

**我核实：49 个页面，37 个直连（76%）。属实。**

**这是本项目最重要的架构决策**：

| 通路 | 谁用 | 经过什么 |
|---|---|---|
| **页面通路** | 49 个 Server Component | **直连服务层，跳过 API** |
| **客户端通路** | 77 个组件 | fetch → /api/* → 服务层 |

**为什么重要**：它解释了 M-1 里发现的一个现象——

> `favorites` 那些路由敢在路由层不写 guard，是因为**页面根本不经过 API**，
> 权限必须在服务层兜住。

**S 组完全没提这条**——它画了依赖图，但没注意「页面和 API 是平行关系」。

### 3.2 agent3 发现的 19 处「裸 fetch」

**它逐个核实了上下文**：

> 19 处绕过 `apiFetch` 的裸 fetch，集中在 featured / feedback / import / pack-release；
> 危害：**错误码退化**（把 `rate_limited` / `input_invalid` 统一压成 `request_failed`），
> 导致 `retryAfterSeconds()` 这些路径全部失效。

**它还做了归因**：

> 这是「**后加的代码没跟上早期约定**」，不是架构设计问题。

**S 组完全没提这个**。

### 3.3 三份报告的共同点：都做了「防误判」

| agent | 做了什么 |
|---|---|
| agent1 | 核实「UI 直连 db」是不是违规（结论：146/147 只读，1 处有意例外） |
| agent2 | 核实「10 个路由无鉴权」是不是漏鉴权（结论：都是设计上公开） |
| agent3 | 核实「api-client 算不算组件」（结论：是基础设施，应单列） |

**这些「主动排除误判」的工作，S 组只做了部分**。

## 五、M-4 揭示的新规律：**「装不下」不必然导致「做不好」**

**设计时的假设**：58 万 token，单干装不下，必然做不好。

**实际结果**：S 组用**机械提取**做到了 **100% 覆盖**，依赖图 27/28 正确。

| 假设 | 实际 |
|---|---|
| 装不下 → 必然抽样 → 漏 | ❌ **S 组没抽样，改用机械提取** |

**这是一个重要发现**：

> **当任务可以用「机械方法」完成时，单 agent 也能全量覆盖。**
>
> 真正「装不下」的，是那些**必须逐个理解内容**的任务，
> 而不是**可以机械提取结构**的任务。**

### 对题库设计的启示

| 任务类型 | 单干能做完吗 | 协作有价值吗 |
|---|---|---|
| **可机械提取**（import 关系、文件计数） | ✅ 能 | ❌ 无价值 |
| **需逐个理解**（代码审查、文档一致性） | ❌ 不能 | ✅ 有价值 |

**M-4 属于前者——虽然材料多，但结构可以机械提取。**

**这是设计上的一个失误**：把「材料量大」等同于「需要协作」，其实要看**能否机械化**。
