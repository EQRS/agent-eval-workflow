# M-1 安全审计 · 实测结果

> 日期：2026-11-16
> **这是 v3 的第一道题，用来验证「多视角协作有没有价值」**

---

## 一、结果：**协作发现了单干漏掉的 P1 越权漏洞**

| 组 | 覆盖 | 发现问题 | 高危 |
|---|---|---|---|
| **S 组（单干）** | **100/100** | **0 个** | **0** |
| **T 组（协作）** | **100/100** | **3 个** | **1（P1）** |

**这是本次评测第一个明确的「协作优于单干」的证据。**

> 注：T 组原报 P0，我核实影响面后调整为 P1（理由见 `安全修复单-后台分区管理越权.md` §五）。

## 二、T 组找到的越权漏洞（我核实属实）

### 漏洞：`GET /api/admin/forum/boards/[boardId]` 匿名可读完整任职名单

**代码**（`route.ts:41-56`）：

```
export async function GET(...) {
  assertForumEnabled();
  const ctx = await currentContext();          // ← 只是读了上下文
  // 名单里含 user_id / 授予人，只给本区管理者与站方管理员看   ← 注释写了意图
  const role = await service.boardRoleOf(boardId, ctx.userId ?? '');
  const members = await service.listMembers(ctx, boardId);      // ← 但没有校验！
  return okJson({ boardId, myRole: role, members }, requestId);
}
```

**服务层也没兜底**（`boards.ts`）：

```
async listMembers(_ctx, boardId) {    // ← 参数名前缀下划线，作者有意不用
  // 函数体内无任何权限判断，直接 SELECT
}

async boardRoleOf(boardId, userId) {  // ← 连 ctx 参数都没有
  return withRead((conn) => roleOf(conn, boardId, userId), db);
}
```

**后果**：匿名请求即可拿到该分区完整任职名单，含 `userId`、昵称、头像、角色、**`grantedBy`（授予人 id）**、授予时间。

**这是「注释写了意图、代码没实现」的典型**——
第 49 行明写「只给本区管理者与站方管理员看」，紧接着 50-51 行没有任何身份判断。

## 三、为什么单干漏了？

### S 组的报告质量其实很高

它审了 **100/100**，分类清楚（10 无鉴权 + 63 强鉴权 + 27 弱鉴权），
还主动声明了四项审计盲区。**但它的结论是「未发现越权漏洞」。**

### 根因：**它把「有 currentContext」当成了「有鉴权」**

S 组对 27 个「弱鉴权」路由的处理方式：

> 只调 currentContext()，路由层无 assert。这是**最需要警惕的一类**——
> 因为它看起来「有鉴权」但实际只是「读了上下文」。我逐个下钻 service 层，**全部有兜底**。

**它确实下钻了 27 个，但漏了这个第 28 个。**

| S 组的判断 | 实际情况 |
|---|---|
| 27 个弱鉴权都有 service 层兜底 | ✅ 对 |
| **forum/boards/[boardId] 也有兜底** | ❌ **错——它没有** |

**为什么会漏**：S 组在 admin/ 目录下有 30 个路由，
其中 29 个都调了 assertCanAdmin，**只有这 1 个没调**。
在一堆「都合规」的文件里找「唯一不合规的那个」，需要逐个对比 import 语句。

### T 组为什么能发现

| 因素 | 说明 |
|---|---|
| **范围小** | agent1 只审 30 个 admin 路由，对比更细致 |
| **有对照意识** | 它发现「同目录其他 29 个都 import 了 assertCanAdmin，唯独这个没有」 |
| **追到最底层** | 它不止看路由，还去 service 层确认 listMembers 真的没校验 |

**最关键的是第二点**——**「同类对比」是发现异常的有效方法**。
S 组要审 100 个，没精力两两对比；T 组的 agent1 只审 30 个 admin 路由，容易发现「就它特殊」。

## 四、T 组其他两个 agent 的发现

### agent2（me/ 14 个路由）

## 五、成本对比（用 --split 切分）

| 组 | turn | token | 步数 |
|---|---|---|---|
| **S 组（单干）** | 19 | **2,110,784** | 12 |
| **T 组 agent1（admin）** | 5 | 2,394,795 | 28 |
| **T 组 agent2（me）** | 9 | 2,464,473 | 19 |
| **T 组 agent3（其余）** | 32 | 1,922,330 | 10 |
| **T 组合计** | | **6,781,598** | 57 |

### 关键对比

| 指标 | S 组 | T 组 | 倍数 |
|---|---|---|---|
| **成本** | 2,110,784 | 6,781,598 | **3.2×** |
| **步数** | 12 | 57 | 4.75× |
| **发现** | 0 | 3 | — |
| **有效高危** | 0 | **1** | — |

**协作花了 3.2 倍的成本，换来 1 个真实越权漏洞的发现。**

### 一个有意思的细节

三个 T 组 agent 的成本很接近（192-246 万），但**步数差很大**（10 / 19 / 28 步）。

| agent | 步数 | token | 每步 token |
|---|---|---|---|
| agent1（admin 30 个） | 28 | 2,394,795 | 85,528 |
| agent2（me 14 个） | 19 | 2,464,473 | 129,709 |
| agent3（其余 56 个） | 10 | 1,922,330 | 192,233 |

**agent3 审的路由最多（56 个），但步数最少（10 步）、每步最贵（19 万）。**
说明它用了更少的步数但每步塞了更多内容——**这可能就是它漏掉问题的原因**（读得快、看得浅）。

**而 agent1 步数最多（28 步），恰恰是它发现了 P0 漏洞。**

## 六、M-1 验证了什么

### 6.1 v3 的核心假设成立

> **v3 假设**：多视角协作能发现单干漏掉的问题。
> **实测结果**：✅ **成立**——T 组找到了 S 组漏掉的 P0 漏洞。

### 6.2 与 v2 的对比

| | v2 的题 | **v3 的 M-1** |
|---|---|---|
| 题目规模 | 一个目录，几十个文件 | **100 个路由，约 100 个文件** |
| 单干表现 | 全对 | **审完了但漏了关键问题** |
| 协作表现 | 不如单干 | **发现了单干漏的** |
| 结论 | 小任务不需要协作 | **大任务需要协作** |

**这验证了扩题方向的正确性**：把题做大，协作价值就出现了。

### 6.3 关键判据得到了数据

| 判据 | S 组 | T 组 |
|---|---|---|
| 覆盖率 | 100/100 | 100/100 |
| **发现数** | **0** | **3** |
| **高危发现** | **0** | **1** |
| 有效发现（我核实） | 0 | **1（P0）** |

**协作增量 = 1 个 P0 漏洞。**

## 七、一个反直觉的观察

**S 组的报告写得比 T 组任何一份都长、更结构化。**

| 组 | 报告特点 |
|---|---|
| S 组 | 分类清晰、四项盲区声明、覆盖率 100% |
| T 组 agent1 | 聚焦、发现问题、给了修复建议 |

**但 S 组的结论是「未发现漏洞」，T 组是「发现 1 个 P0」。**

**这说明：报告的完备性不等于发现的深度。**
一份「结构完整但结论错误」的报告，比一份「简洁但结论正确」的报告更危险——
因为它看起来更可信。

## 八、结论

| 问题 | 答案 |
|---|---|
| M-1 能跑通吗 | ✅ 能 |
| 协作比单干好吗 | ✅ **是——发现了单干漏的 P0 漏洞** |
| 扩题方向对吗 | ✅ **对——做大之后协作价值出来了** |
| 判据可算吗 | ✅ --split 切出了精确成本 |

**这是整个评测里第一个「协作确实优于单干」的硬证据。**

## 九、协作净值分析

| 项 | 值 |
|---|---|
| 协作增量价值 | **1 个 P1 越权漏洞** |
| 协作成本增量 | 4,670,814 token（6,781,598 - 2,110,784） |
| 协作净值 | **约 467 万 token / 个漏洞** |

**这个比值怎么解读？**

| 视角 | 判断 |
|---|---|
| 成本角度 | 3.2 倍成本换一个漏洞，**偏贵** |
| **价值角度** | 一个**未授权的数据泄露**如果被利用，代价远超 467 万 token |

**关键在于「单干会不会漏」：** 本次实测**确实漏了**。
不是「多花 3 倍买个保险」，而是「单干会漏，协作能补上」。

## 十、对后续题的启示

**这条数据可以指导出题**：

| 观察 | 启示 |
|---|---|
| agent1 步数最多（28 步）却发现了漏洞 | **深读比快读更可能发现问题** |
| agent3 审 56 个但只 10 步 | 覆盖广但深度不足 |
| 单干审 100 个用 12 步 | **比协作任何一个 agent 都浅** |

**下一题应该设计成**：
> 让单干**必然**因为要审太多而变浅，
> 而不是靠运气漏掉。
