## 三、为什么耗时反了

**M-6 的 T-运维跑了 226 秒**（深度推理），拖慢了整组。

**M-7 的三个 agent 都在 50-71 秒**，没有特别慢的。

| | M-6 | M-7 |
|---|---|---|
| T-安全 | 72s | 71s |
| T-性能 | 62s | 61s |
| **T-运维** | **226s** | **50s** |
| 最慢的 | **226s** | 71s |

**关键**：M-6 的运维 agent 在分析「逐行 UPDATE 拖垮全站」这种需要推演的问题；
M-7 的运维 agent 面对的是「迁移失败」这种更直接的问题，**不需要那么深的推演**。

**这说明耗时取决于「任务要求的推理深度」，不是固定的。**

## 五、T 组各专业的独有价值

### 安全组：发现了 SSRF 面

> `/api/auth/{provider}/start` 里 provider **攻击者可控**，
> 且直接决定「向哪个域名发请求」。若实现用拼接（`https://${provider}.com/oauth/token`）
> **直接构成 SSRF**。

**这是我埋素材时完全没想到的**——我只想到「路由参数化是好设计」。

### 性能组：指出「锁表风险被严重低估」

> 方案只写了建新表 + INSERT SELECT，这两步便宜。
> 但**要放开 provider CHECK，必须重建两张表**——这才是真贵的。

**它把「方案没写的成本」算出来了。**

### 运维组：发现「账号分裂」这个 P0

> 「找不到就创建新用户」—— 一旦回填漏人，该用户再登录会**创建一个全新账号**，
> 他的评测、帖子、收藏全部「消失」。
> **这不是 bug，是用户直接失去账号。**

**它还提出「新建用户数告警」这个具体措施。**

### 6.3 修正后的耗时结论

~~旧：协作耗时是单干的 3.6 倍~~

**新结论**：

> **协作耗时取决于「最慢的那个专业 agent 需要多深的推理」。**
>
> M-6 的运维 agent 要推演「全站影响」→ 226 秒；
> M-7 的运维 agent 面对「迁移失败」这种直接问题 → 50 秒。

**这意味着「协作更慢」不是必然的**——如果各专业的任务难度均衡，并行反而更快。

>

### 最重要的一句话

> **「专业身份」是唯一在两道题里都稳定生效的设计。**
>
> 不是「材料多」（M-4 失败），不是「显式视角」（M-5 失败），
> **而是「换一套知识体系」——这是单 agent 想不到的。**
