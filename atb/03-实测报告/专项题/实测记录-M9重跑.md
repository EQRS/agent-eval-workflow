## 三、但有一个更严重的问题浮出来了：**agent 会累积经验**

### 3.1 现象

**这次的 S 组用的是 `b-e1-b`，它已经跑过 M-1~M-8 的所有 S 组任务。**

| 阶段 | S 组表现 |
|---|---|
| M-6（第一次专业会诊） | 覆盖 1.5/3 维度，漏安全 |
| M-7 | 自己挖出 2 个我没埋的关键问题 |
| M-8 | 自己挖出「重复造轮子」等 |
| **M-9（重跑）** | **7 全中 0 漏，超过所有 T 组** |

**这是一个明显的上升趋势。**

### 3.2 为什么

**同一个 agent 连续跑同类型任务，会形成「检查清单」**：

| 学到什么 | 来源 |
|---|---|
| 「要看权限」 | M-1 |
| 「要看失效覆盖」 | M-6/M-7 |
| 「要看重复造轮子」 | M-7/M-8 |
| 「要看进程模型」 | M-8 |

**到 M-9 时，它已经内化了这些检查项。**

### 3.3 这解释了报告修正第 3 条为什么重要

我在报告里写了：

> 「同一 agent 跑多题会「学乖」→ **每题用新 agent**」

**但这条没能执行**（成员名额已满 8/8）。

**M-9 重跑用的还是老 agent，所以结果被污染了。**

## 五、T 组仍然有价值的发现

### 5.1 T-运维：列出了**全部 9 处写路径**

**这是本轮最扎实的一个发现**：

> 我扫了全仓所有会改变这两类聚合的写操作，实际有 **9 处**：
> reviews:517、reviews:592（UPDATE plugin_id）、publish-review:124/127、submit-review:281、
> featured:464/468、pack-reviews:95…

**S 组只说「撤回/隐藏/删除」没列出全部位置。**

### 5.2 T-性能：发现了真正的 N+1

> `page.tsx:72` 的 `rows.filter(row => resolveVisibilityInTx(db, row.review_id))`
> **N 篇评测 = N 次额外查询**，这是标准 N+1。
> 方案只缓存了 JOIN 结果，**没缓存逐行过滤** → 缓存命中时 N+1 依然存在。

**它还提了一个更优解**：把可见性判定下推到 SQL，**根本不需要缓存**。

### 5.3 T-安全：指出方案「致命含糊」

> `computeAggregates` 到底返回什么——方案没说。
> 这恰恰是整个方案安全性的**分水岭**。
