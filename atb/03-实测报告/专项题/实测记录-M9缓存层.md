## 三、方法修正

### 3.1 问题根源

| 项 | 问题 |
|---|---|
| **判据清单位置** | 和素材同目录，agent 能读到 |
| **素材本身** | 47 行的「最小实现」，问题浮在表面 |

### 3.2 修正方案

| # | 修正 |
|---|---|
| 1 | **判据清单必须放在 agent 读不到的地方**（如 `_work/` 而非 `docs/`） |
| 2 | **素材要更复杂**——问题不能浮在表面，需要读代码才能发现 |
| 3 | 派任务时明确「只读素材文件」 |

### 3.3 修正后的正确做法

```
docs/M9素材-xxx.md          ← agent 读这个
_work/判据清单/M9-checklist.md  ← agent 读不到（不在 docs 下）
```

## 四、这轮暴露的一个更深问题

### 4.1 「判据清单」是双刃剑

**我引入清单是为了让判据机械化**（报告修正第 1 条）。

**但它同时暴露了答案结构**：

| 用途 | 效果 |
|---|---|
| 给**评测者**打分用 | ✅ 好，机械可判 |
| 给 **agent** 看到 | ❌ **灾难**，等于泄题 |

**正确用法**：清单只给评测者，**绝不放进 agent 能读的目录**。

### 4.2 另一个观察：M-9 素材本身太简单

**M-9 的问题全部浮在表面**：

| 问题 | 发现难度 |
|---|---|
| Map 无上限 | 看一眼就知道 |
| 无失效机制 | 看一眼就知道 |
| 无监控 | 看一眼就知道 |

**对比 M-6/M-7/M-8**：那三题的问题需要**读项目代码**才能发现（如「external_identities 已存在」「users 没有 github_id」）。

**M-9 不需要读项目代码**——47 行素材自包含，问题全在里面。

### 4.3 修正后的素材标准

| 要求 | 说明 |
|---|---|
| **素材不能自包含** | 必须结合项目现有代码才能判断对错 |
| **问题不能浮在表面** | 要读几处代码才能确认 |
| **要有「现成实现」对照** | 像 M-7/M-8 那样能发现重复造轮子 |
