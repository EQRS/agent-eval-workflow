## 一、题目的设计意图

`测评设计-AgentTeams.md` 说：

> **E3 是这次对照的关键**：如果 team 在单点深挖上也赢，说明测评设计有问题——
> 三个 agent 查同一个 bug，只会互相干扰、重复劳动、拉高成本。

所以我给的题面**只描述现象、不给位置**：

> 用户反馈「收藏夹详情页顶部的条目总数」偶尔会显示错，没人能稳定复现。
> 请找出根因、给出证据。

---

## 二、⚠️ 最重要的发现：**我给的题面前提是错的**

**e3-investigator 没有接受我的前提，而是去验证了它。**

| 做法 | 说明 |
|---|---|
| 定位代码 | 找到 `:48-49` 的三元表达式，**和另一处 COUNT(*) 子查询** |
| **建真实数据库跑矩阵** | 用项目自带 `createTestDb` + 真实服务，测了 5 种场景 |
| 验证结论 | **「当前代码下算不错」** |
| 说清原因 | 详情页 SQL 全是 INNER JOIN，外键是 ON DELETE RESTRICT，源码内无硬删 |

**它测的 5 种场景**（表行数 / 列表页 count / 详情页 total 三者全等）：

- 包版本被撤回、被隐藏
- 帖子软删
- 插件仓库 unavailable
- 自建空夹、默认夹、folder_id IS NULL 的历史收藏

**结论：我编的那个「偶尔显示错」的场景，在当前 schema 下不可达。**

## 三、但它找到了两个真问题

### 问题 1：同一个数字有两套实现

| 位置 | 实现 |
|---|---|
| 列表页每夹条数 | `interactions/index.ts:770-785` 的 COUNT(*) 子查询 |
| 详情页顶部总数 | `[folderId]/page.tsx:48-49` 的 length |
| getFavoriteFolder 已算好的 count | **算了但没人用——死字段** |

**已核实属实。**

### 问题 2：删除确认的文案是错的（真 bug）

`folder-actions.tsx:51-54` 写着：

```
删除收藏夹「xxx」？夹内 N 个插件会一并取消收藏（不会移到其他收藏夹）。
```

而 `deleteFavoriteFolder` 实际行为是**移回默认夹、不取消收藏**。

**已核实属实。这是我上一轮改行为时忘了同步的文案。**

## 四、产出质量

### t1（investigator）：拒绝错误前提

**这是本次评测最有价值的行为。**

给一个「用户说这里有 bug」的题面，它没有顺着找，而是先验证「这个 bug 到底存不存在」，
然后如实报告「未能复现」，还建议：

> 先向用户取具体收藏夹 id + 页面显示 N + 实际条数，再决定修复点；不建议盲改计数逻辑。

### t2（fixer）：修复方案分三层

| 层 | 内容 |
|---|---|
| A（核心） | 统一计数实现；详情页改用 `folder.count`；补等价性测试 |
| B（真 bug） | 改正文案 + 增加 targetKind prop |
| C（线上核查） | 写只读脚本查数据层残余原因 |

**还明确列了「不做什么」**：不改 INNER JOIN 为 LEFT JOIN（会渲染空标题）、
不加冗余计数列（违反项目既有纪律）。

并识别出技术风险：`folder-actions.tsx` 是 `'use client'`，
从服务端模块引常量可能把 better-sqlite3 拖进客户端 bundle。

## 六、结论

| 结论 | 证据 |
|---|---|
| **team 在单点深挖上没赢** | 成本 65 倍，且题面前提被证伪 |
| **但深度不是白花钱** | 它证伪了我的题面，找到 2 个真问题 |
| **关键行为是「拒绝错误前提」** | investigator 没有顺着题面找 bug |

**对整合包选型的意义**：

- E3 这类「深挖一个不明确的问题」**不该用团队**——成本 65 倍，
  收益是「证伪前提」而不是「更快修好」
- 单 agent 做同样的排查，成本大概是 P3 量级（十几万 token）

**这正是设计文档预期的结果**：team 在单点深挖上没赢。

## 八、t3 审查：needs_revision，砍掉 2/3 的实现

reviewer 给出 `verdict=needs_revision`，核心判断：

> t1 结论可保留，t2 方案方向对但**约 2/3 的实现应砍掉**。

| # | 指控 | 核实结果 |
|---|---|---|
| 1 | t2 用的 `service.setFavorite` 不存在 | ❌ **不成立**。方法存在，签名 `{ pluginId, folderId? }`，接受 folderId |
| 2 | 页面的 `total = folder.count` 没有测试兜住 | ✅ **成立**，确实是漏的 |
| 3 | B-1/B-2 之争是伪问题，仓库已有现成做法 | ✅ **成立**，`favorite-picker.tsx` 就是 `import type` + 就地字面量 |
| 4 | `targetKind` prop 是过度设计 | ✅ **成立**，`FolderActions` 全仓只有一个调用点 |
| 5 | 重写 `listFavoriteFolders` 是过度设计 | ✅ **成立**，原 SQL 子查询本来就是唯一真值 |
| 6 | 新增核查脚本与 `diagnose.mjs` 重叠 | ✅ **成立**，该脚本已存在（294 行，只读/--json/退出码） |
| 7 | 文档自相矛盾（「多一次 COUNT」vs「原来也有只是没人用」） | ✅ **成立**，第 494 行与第 13 行确实互相矛盾 |

**7 条里 6 条成立，1 条（第 1 条：setFavorite 不存在）不成立——我实查该方法存在且接受 folderId。**

### 审查者给出的最小方案

> 最小可行 = 3 处 diff：
> ① `getFavoriteFolder` 三个分支用对应表 COUNT(*) 给 count（`listFavoriteFolders` 一行不改）
> ② `page.tsx:48-49` 改 `total = folder.count`
> ③ `folder-actions.tsx:53` 改文案（写死「插件」）

**还把 t1 的一个归类偏差指了出来**：删夹文案属于独立产品 bug，
不该挂在「计数口径」这个议题下。
