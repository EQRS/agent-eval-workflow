## 一、最直接的对标：MultiAgentBench（MARBLE）

| 项 | 信息 |
|---|---|
| 论文 | ACL 2025 Main，arXiv 2503.01935 |
| 代码 | `github.com/MultiagentBench/MARBLE` |
| 定位 | **多智能体协作与博弈**评测（和我们的目标最接近） |

### 1.1 它的核心方法：**里程碑式 KPI**

这是最值得借鉴的一点。原文：

> 每个任务被切成**一系列灵活的里程碑（milestones）**。
> 一个基于 LLM 的检测器**持续监控**过程，识别哪些里程碑已达成，
> **并记录贡献的 agent**。

**计算方式**：

```
KPI_j = n_j / M        （第 j 个 agent 贡献的里程碑数 / 总里程碑数）
KPI_overall = (1/N) * Σ KPI_j   （所有 agent 的平均）
```

**这解决了我们的什么问题**：

| 我们的问题 | 里程碑法怎么解决 |
|---|---|
| D3 都是 0 分，没区分度 | 里程碑是连续的，不是二值的 |
| D2 只看「有没有并行」 | 能看出**每个成员贡献了什么** |
| 无法评价「多人协作是否比一人强」 | KPI 本身就是按人摊的 |

### 1.2 它的五个场景

| 场景 | 类型 |
|---|---|
| **Research** | 开放式研究任务 |
| **Minecraft** | 沙盒环境操作 |
| **Database** | 数据库错误修复 |
| **Coding** | 编码任务 |
| **Bargaining** | 谈判博弈 |
| **Werewolf** | 狼人杀（对抗性） |

**注意它同时测「协作」与「竞争」**——我们的评测集只测协作。

### 1.3 它的协调协议维度

> 评估各种协调协议（**star / chain / tree / graph** 拓扑）

**这对我们是新维度**：我们测的是「插件能不能协作」，它测的是「什么拓扑结构更好」。

### 1.4 可复用的结论

> gpt-4o-mini 平均任务分最高；
> **graph 结构在 research 场景表现最好**；
> 认知规划让里程碑达成率提升 3%。

**「3%」这个数字值得注意**——说明这些提升幅度不大，需要足够大的题量才能测出来。
**这正好印证了「题量要够」的判断。**

### 1.5 **MARBLE 题库的真实结构**（已读到源码）

> 经过代理配置后成功拉到仓库内容。以下是从 `multiagentbench/` 目录读到的实际结构。

#### 目录组织

```
multiagentbench/
  ├─ coding/      coding_main.jsonl     100 题  (509 KB)
  ├─ research/    research_main.jsonl   100 题  (1745 KB)
  ├─ database/    database_main.jsonl   (未统计)
  └─ bargaining/  (未统计)
```

**每个场景一个 JSONL 文件，coding 与 research 各 100 题。**
如果五个场景都是这个量级，题库总规模约 **400-500 题**。

#### 一道题的完整字段（以 coding 为例）

```
{
  "scenario": "coding",           // 场景类型
  "task_id": 1,                   // 题号
  "coordinate_mode": "",          // 协作拓扑（star/chain/tree/graph）
  "relationships": [              // 成员间关系声明
    ["agent1", "agent2", "collaborates with"],
    ["agent2", "agent1", "collaborates with"]
  ],
  "llm": "",                      // 指定模型
  "environment": {
    "type": "", "name": "",
    "workspace_dir": "workspace",
    "max_iterations": ""
  },
  "task": { "content": "..." },   // 任务全文
  "agents": [ ... ],              // 每个成员的人设与能力约束
  "memory": { "type": "" },       // 记忆类型
  "metrics": {                    // **判分项声明**
    "evaluate_llm": "",
    "code_quality": true,
    "test_coverage": true,
    "collaboration_effectiveness": true
  },
  "output": { "format": "jsonl", "file_path": "" }
}
```

#### 三个可直接抄的设计

**① `relationships`：显式声明成员关系**

> `["agent1", "agent2", "collaborates with"]`

用三元组表达「谁和谁是什么关系」。这比我们的「建个团队」更细——
**能表达「A 和 B 协作、C 和 B 对抗」这种混合关系**。

**② `agents[].profile`：人设里写死能力约束**

读到的原文举例：

> I am a Senior Software Developer specialized in Python development.
> I **have to** call "create_code" in the first iteration.
> I am **very terrible** at modifications so I **have to** let agent 2 or 3 revise.
> I **can't** call "give_advice_and_revise_code".

**这是关键设计**：给每个成员设定**互补的能力边界**，强制协作。
否则多 agent 会各自做一份完整的工作，测不出协作价值。

**③ `metrics`：判分项按任务声明**

> coding 领域用 `code_quality` / `test_coverage` / `collaboration_effectiveness`

**不同场景用不同的判分项**，不是一套指标套所有题。

## 二、其他可借鉴的题库

### 2.1 MASEval（我们设计文档已引用）

| 项 | 信息 |
|---|---|
| 定位 | LLM 多智能体**系统级**评测框架 |
| 提供的 benchmark | MultiAgentBench / ConVerse / GAIA2 / MACS / MMLU / τ² |

**它的价值**：**一个框架集成多个 benchmark**，不用自己造。
我们设计文档引用了它的 Coordination Entropy 与 Message Utility Ratio，思路对。

### 2.2 GAIA（通用 AI 助手基准）

| 项 | 信息 |
|---|---|
| 特点 | **真实世界问题**，需要多步推理与工具使用 |
| 分级 | 按难度分 Level 1/2/3 |

**可借鉴的**：**难度分级**。我们的题目前是平铺的（P1-P8），没有难度梯度。

### 2.3 SWE-bench（软件工程任务）

| 项 | 信息 |
|---|---|
| 形式 | 从真实 GitHub issue 构造，**用测试用例判分** |
| 特点 | **完全客观**——跑测试就知道对不对 |

**可借鉴的**：**用真实 issue + 测试判分**，比我们现在的「让 LLM 判断」更客观。

## 三、对 ATB 的五条具体建议

### 建议 1：改用**里程碑式 KPI** 替代「通过/不通过」

**这是最重要的一条。**

| 现在 | 改成 |
|---|---|
| 「P2 依赖顺序：通过」 | 「P2 达成 5 个里程碑中的 5 个，贡献者：worker-a(3) / worker-b(2)」 |
| 二值判定 | 连续得分 + 贡献归因 |

**好处**：

1. D3 这种「都做对了」的维度也有区分——看**谁贡献了更多里程碑**
2. 能回答「多 agent 比单 agent 强在哪」——里程碑贡献分布
3. 解决题量不足——**一道题能产出多个数据点**

### 建议 2：给题目加**难度分级**

借鉴 GAIA 的 Level 1/2/3：

| 级别 | 定义 | 我们现有的题 |
|---|---|---|
| **L1 单步** | 一个任务、一个成员 | P3 成本基线 |
| **L2 多步** | 多个任务、需要协作 | E1 并行、E2 依赖链 |
| **L3 开放** | 目标模糊、需要判断 | E3 单点深挖、P7 假需求 |

**好处**：不同难度的题能测出不同的能力，而不是全混在一起。

### 建议 3：题库分类按**任务形状**，不按「插件能力」

现在我们是按 D1-D6 维度出题，但**一道题往往同时测多个维度**。

**MultiAgentBench 的做法是反过来的**：先定场景（Research/Coding/Bargaining），
每个场景用统一的里程碑 KPI 打分。

**建议改成**：

```
题库 = 按任务形状分类
  ├─ 并行型（可拆成独立块）
  ├─ 串行型（有依赖链）
  ├─ 汇聚型（多路结果合并）
  ├─ 对抗型（成员目标冲突）
  └─ 开放型（目标模糊）
```

每个形状出 5-10 题，**同形状的题之间可比**。

### 建议 4：判分尽量**客观化**

借鉴 SWE-bench 的「用测试判分」：

| 现在的判分 | 客观程度 |
|---|---|
| 「团队是否指出前提不成立」 | ⚠️ 需要人判断 |
| 「文件数对不对」 | ✅ 完全客观 |
| 「消息送达率」 | ✅ 完全客观 |

**建议**：每道题至少有**一个机械可判的硬断言**。
现在我们已经有（文件数、依赖顺序），但要**扩大这个比例**。

具体做法：把「团队说要 X」变成「团队产出的文件里 X 能通过检查」。

### 建议 5：**不要追求「三次取中位数」，而是「多题取分布」**

你指出的这一点是对的。我重新想了一下：

| 做法 | 问题 |
|---|---|
| 同一题跑 3 次取中位数 | **成本 ×3，但只覆盖一种题型** |
| 同一题型出 10 题各跑 1 次 | 成本 ×10，**但覆盖了该题型的变化** |

**后者更好**——因为：

1. 插件性能的差异**体现在不同类型任务上的表现**，不是同一任务的抖动
2. MultiAgentBench 的「认知规划提升 3%」这种结论，是靠**大量题**得出的，不是靠重复
3. 重复运行只能消除噪声，不能增加信息量

**正确做法**：**同一题型多题、跨题型对比**。

## 四、题库规模的现实建议

| 阶段 | 题量 | 目的 |
|---|---|---|
| **当前（8 题）** | 8 | 验证采集链路可用 ✅ 已完成 |
| **下一阶段** | **每形状 5 题 × 5 形状 = 25 题** | 能出初步的分布结论 |
| **成熟阶段** | 每形状 10-20 题 | 能做统计显著性检验 |

**为什么是「每形状 5 题」而不是更多**：

按我们的成本数据，一题平均 50 万 token（不含 E3），25 题约 **1250 万 token**。
这个量级可接受。如果每形状 20 题（100 题），就是 5000 万，成本太高。

## 五、可以直接借鉴的三个模板

| 来自 | 借鉴什么 | 怎么用 |
|---|---|---|
| **MultiAgentBench** | 里程碑 KPI + 贡献归因 | 改造现有的 8 道题，每题定义 3-5 个里程碑 |
| **GAIA** | 难度分级 L1/L2/L3 | 给现有题目标级别，后续出题按级别配比 |
| **SWE-bench** | 真实任务 + 测试判分 | 把「统计文件数」升级成「按规范写出脚本并通过断言」 |
