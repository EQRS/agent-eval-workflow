> 依据：M-1 到 M-5 的实测数据

## 一、五题数据

| 题 | 材料(万) | 可机械化 | **S 组能否自己想到视角** | 成本 | 稳定性 |
|---|---|---|---|---|---|
| M-1 | 15 | 部分 | 能想到，但**看不过来** 100 个 | 3.2× | 低 |
| M-2 | 6.9 | 半 | 能想到但**没做**（时间分布分析） | 1.7× | 中 |
| M-3 | 4.2 | 半 | **有信息但没追问** | 1.31× | 高 |

## 二、核心发现：**决定因素不是「能否机械化」**

### 2.1 反例对比

| 题 | 可机械化 | T 组优势 | S 组表现 |
|---|---|---|---|
| **M-3** | 半 | **1.31×，稳定性高** | 有信息但没追问 |
| **M-5** | **不可** | **1.1×，稳定性低** | **能想到，还主动扩查** |

**M-5 更「不可机械化」，但 T 组优势反而更小。**

### 2.2 真正的决定因素

> **S 组会不会自己想到那个视角。**

| S 组的状态 | T 组优势 | 例子 |
|---|---|---|
| **想不到** | **高** | — |
| 能想到但没做 | 中 | M-2（想到了但没分析时间分布） |
| 有信息但没追问 | 高 | M-3（看到 9/10 没问那 1 个） |
| **能想到且做了** | **低** | **M-5（主动扩查别名导入、文档）** |

### 2.3 修正后的规律

~~旧规律：T 组优势 = 视角数量 × 不可机械化程度~~

**新规律**：

```
T 组优势 = 视角数量 × (1 - S组自己想到的概率)
```

**而 S 组「想到的概率」取决于**：

| 因素 | 越想得到 | 越想不到 |
|---|---|---|
| 任务熟悉度 | 熟悉的领域 | **陌生的领域** |
| 视角是否显式 | 题目提示了视角 | **需要自己发现视角** |
| 信息是否在手 | 一眼能看到 | **需要主动去挖** |

## 三、新出题原则

### 原则 1：**要让 S 组「想不到视角」**

**不是「告诉它三个视角但限制范围」，而是「让它自己发现有哪些视角」。**

| 旧做法（失效） | **新做法** |
|---|---|
| 派给 S 组 3 个视角，让它做 | **只给任务，不告诉它要看哪些维度** |
| T 组明确分 3 个视角 | T 组在任务里被引导，S 组不被引导 |

**但这样不公平**——于是需要新的对照设计：**信息差**。

### 原则 2：用「信息差」制造 S 组想不到

**核心思路**：让某些信息**只有特定视角才自然会发现**。

| 例子 | 为什么 S 组想不到 |
|---|---|
| 运维视角：这个改动凌晨出事怎么办 | **写代码时不会想运维** |
| 安全视角：这个输入能被构造吗 | **功能实现时不考虑攻击** |
| 用户视角：这个错误提示用户看得懂吗 | **开发者知道内部逻辑** |

**这些都是「专业领域的思维习惯」——不是想不想的问题，是会不会。**

### 原则 3：**优先测「专业纵深」而非「覆盖广度」**

| 维度 | 结论 |
|---|---|
| （覆盖广度） | ❌ M-1/M-4 证明：材料多不等于需要协作 |
| （视角数量） | ❌ M-5 证明：S 组也能想到多个视角 |
| **（专业纵深）** | ✅ **未验证——可能是真正的差异点** |

**专业纵深是什么**：

> 同一个 bug，**安全专家看到的是「可被利用」**，
> **性能专家看到的是「O(n²)」**，
> **运维专家看到的是「没法灰度」**。
>
> **这三种看法需要三套不同的知识体系。**

## 四、按新原则设计的题型

### 题型 A：**多专业会诊**

```
任务：评审一个新功能的实现方案

S 组：1 个 agent，给完整方案，让它评审
T 组：3 个 agent，**各自带专业身份**
  agent1：安全工程师（只看可被攻击面）
  agent2：性能工程师（只看瓶颈）
  agent3：SRE（只看可运维性）
```

**关键**：S 组**不被告知**要分这三个专业看——它得自己想到。

**预期**：S 组可能只从「代码质量」角度评审，T 组能覆盖三个专业维度。

**判据**：

| 表现 | 评级 |
|---|---|
| 指出代码风格问题 | 及格 |
| **指出安全/性能/运维任一维度** | 良好 |
| **三个维度都覆盖** | 优秀 |

### 题型 B：**跨界审查**

```
任务：审查一个数据库迁移脚本

S 组：1 个 agent 审查
T 组：3 个 agent
  agent1：DBA（关注锁表、索引、数据量）
  agent2：应用开发者（关注代码适配）
  agent3：运维（关注回滚、灰度、监控）
```

**为什么 S 组想不到**：它默认会从「代码对不对」看，
**不会主动切换到 DBA / 运维视角**。

### 题型 C：**反向论证**

```
任务：评审一个技术方案

S 组：1 个 agent 评审
T 组：3 个 agent，其中一个的**唯一职责是「证明这个方案不行」**
```

**为什么有效**：S 组倾向于「找问题但不否定整体」，
**专职反驳者会逼出「最坏情况」**。

## 五、需要废弃的题型

| 题型 | 为什么废弃 |
|---|---|
| **纯覆盖型**（M-1/M-4） | 材料多可以机械提取，S 组不输 |
| **显式多视角型**（M-5） | S 组被告知维度后，自己也能想到 |
| **纯机械任务** | 完全可机械化，测不出协作 |

## 六、一个必须承认的局限

**五题下来，T 组优势最大的只有 M-1（3.2×）**，而它有运气成分。

| 题 | T 组优势 | 可信度 |
|---|---|---|
| M-1 | 3.2× | ⚠️ 低（范围优势有运气） |
| M-2 | 1.7× | 中 |
| M-3 | 1.31× | 高 |
| M-4 | 1.0× | — |
| M-5 | 1.1× | 低 |

**去掉有运气成分的 M-1，T 组优势只有 1.0-1.7 倍。**

### 这意味着什么

**可能有三种解释**：

| # | 解释 | 应对 |
|---|---|---|
| 1 | 这个模型单干已经很强，协作增量小 | 换更弱的模型测 |
| 2 | 题目设计还没抓住「真正需要协作」的场景 | **继续试新题型** |
| 3 | 协作的价值本来就不在「质量」而在「时间」 | **改测并行速度** |

**建议**：

> **下一题同时测「质量」和「时间」**——如果质量差异小，但时间差异大，
> 那协作的价值就在「快」而不在「好」。

## 七、下一题的推荐设计

**M-6：多专业会诊 + 时间测量**

### 7.1 设计

| 项 | 内容 |
|---|---|
| 任务 | 评审一个真实的功能实现方案 |
| S 组 | 1 个 agent，**不提示专业维度** |
| T 组 | 3 个 agent，各带专业身份（安全/性能/运维） |
| **双判据** | **① 质量：覆盖几个专业维度 ② 时间：墙钟耗时** |

### 7.2 为什么这样设计

| 设计点 | 目的 |
|---|---|
| **S 组不提示维度** | 测「能不能自己想到」 |
| **T 组给专业身份** | 测「专业视角能否带来覆盖增量」 |
| **同时测时间** | 如果质量差不大，看时间差 |

### 7.3 判据

| 指标 | 怎么取 |
|---|---|
| 质量覆盖 | 三个专业维度覆盖了几个 / 3 |
| **墙钟耗时** | 从派发到完成 |
| 成本 | --split 切分 |
| **性价比** | 质量增量 / 时间增量 |

### 7.4 预期三种结果

| 结果 | 说明 |
|---|---|
| T 组质量高、耗时短 | ✅ **协作全面优于单干** |
| T 组质量高但耗时长 | ⚠️ **协作是「用时间换质量」** |
| T 组质量差不多 | ❌ **协作在评审类任务上无价值** |

**三种都有信息量。**

## 八、已确认的原则

| # | 原则 |
|---|---|
| P1 | **优先测「S 组想不到的视角」**，不是「S 组来不及做的」 |
| P2 | 用「专业身份」制造信息差，而不是「信息封锁」 |
| P3 | 废弃纯覆盖型、显式多视角型、纯机械任务 |
| P4 | **必须同时测质量与时间**——协作的价值可能只在「快」 |
| P5 | 承认五题里 T 组优势只有 1.0-1.7 倍（去掉有运气的 M-1） |

---

## 九、不适用条件

- 不适用于「单 agent 已经能想到所有视角」的任务
- 不适用于「可以用脚本机械完成」的任务
- 不适用于「材料量决定成败」的场景（M-4 已证伪）
