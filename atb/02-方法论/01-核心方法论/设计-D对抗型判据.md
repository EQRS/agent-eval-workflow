# D 对抗型题的判据设计

> 日期：2026-11-16
> 解决的问题：(“)平衡(”是主观的，怎么客观判？

---

## 一、问题的本质

对抗型任务里，两个 agent 目标相反。比如：

- A 想「尽可能多收录插件」
- B 想「尽可能严格筛选」

**「最终方案是否平衡」这个判断，人来做都吵架，机器更难判。**

所以**不能直接判「平衡与否」**，要换成**可机械验证的间接判据**。

---

## 二、三种可客观判定的对抗设计

### 设计 1：对抗双方各自产出可核验的事实

**不判「谁赢了」，判「双方说的都对不对」。**

| 角色 | 任务 | 判据 |
|---|---|---|
| 提议方 | 提出 N 条改进建议 | 每条建议要**指明文件与行号** |
| 质疑方 | 逐条指出建议的问题 | 每条质疑也要**指明依据** |

**硬断言**：

1. 提议方给的每个「文件:行号」真实存在
2. 质疑方的每个反驳都有依据（引用原文或代码）
3. 至少有一条建议被推翻，或所有建议都被确认无误

**这完全可机械判定**——文件在不在、行号对不对，一查就知道。

### 设计 2：对抗结果要收敛到可验证的数字

**不判「方案好不好」，判「数字能不能对上」。**

| 场景 | 判据 |
|---|---|
| A 主张「放宽标准能多收录 30 个」 | 实际差异必须是 30（或接近） |
| B 主张「严格标准会漏掉重要插件」 | 要指出具体是哪几个，且确实符合「重要」定义 |

**硬断言**：双方给出的数字与地面真值比对。

### 设计 3：引入「裁判」角色，但裁判只判形式

**三个 agent**：提议、质疑、裁决。

**裁决者的产出格式固定**：

```
{
  "verdict": "accept | reject | modify",
  "accepted_points": [1, 3],      // 采纳了哪几条质疑
  "rejected_points": [2],         // 驳回了哪几条，并给理由
  "final_artifact": "..."
}
```

**硬断言**：

| 检查项 | 判定 |
|---|---|
| `verdict` 是否为合法值 | 机械 |
| `accepted_points` + `rejected_points` 是否覆盖所有质疑 | 机械（集合相等） |
| 每条 `rejected_points` 是否给了理由 | 机械（非空） |
| `final_artifact` 是否包含被采纳的修改 | 机械（关键词包含） |

**这四条都能脚本判定，不需要人评。**

## 三、三道对抗题的最终设计

### D1 代码审查对抗

| 项 | 内容 |
|---|---|
| 任务 | 给 src/server/modules/roles/ownership.ts 提 3 条改进建议 |
| agent1（提议） | 读该文件，提 3 条建议，每条指明行号 |
| agent2（质疑） | 也读该文件，逐条判断建议是否成立 |
| **硬断言** | ① 3 条建议的行号都真实存在；② 质疑方的每条判断都有引用依据；③ 至少找出 1 条不成立的建议（或确认 3 条都成立） |
| 判分 | 行号正确率 + 质疑依据完整率 |

**为什么这是对抗**：提议方想「显得有见解」，质疑方要「挑刺」——目标天然对立。
但**判据不判谁对**，只判「双方说的站不站得住」。

### D2 数字主张对抗

| 项 | 内容 |
|---|---|
| 任务 | 「如果把 src/components 下所有组件的行数统计出来，平均值是多少」 |
| agent1 | 主张一个具体数字，并给出计算方式 |
| agent2 | 独立算一遍，若与 agent1 不符则指出 |
| **硬断言** | 双方最终数字一致，且等于地面真值 |
| 判分 | 数字正确 = 1，否则 0 |

**这是「背靠背计算」类对抗**：两人各算各的，有分歧必须解决。
判据极硬——就是那个数。

### D3 方案评审对抗

| 项 | 内容 |
|---|---|
| 任务 | 设计一个「给收藏夹加排序功能」的方案 |
| agent1（设计） | 给出方案，包含：改哪些文件、加哪些字段 |
| agent2（评审） | 指出方案的问题 |
| agent3（裁决） | 输出结构化裁决（见设计3的格式） |
| **硬断言** | ① agent1 提到的文件都真实存在；② agent3 的裁决字段齐全且覆盖所有质疑点 |
| 判分 | 文件存在率 + 裁决格式完整率 |

**这是唯一用三 agent 的题**，测「引入裁判后能否收敛」。

## 四、与「主观判分」的区别

| 原想的判据 | 问题 | 改成 |
|---|---|---|
| 「方案是否平衡」 | 主观，人评都不一致 | 「双方主张的数字是否与真值一致」 |
| 「反驳是否有道理」 | 主观 | 「反驳是否引用了原文/代码」 |
| 「最终方案好不 好」 | 主观 | 「裁决格式是否完整、是否覆盖所有质疑」 |

**核心思路：不判「内容对不对」，判「形式完不完整 + 可核验的事实准不准」。**

这样做的代价是：**测不到「谁的见解更高明」**。
但那是 LLM-as-judge 的范畴，不在机械判分能覆盖的范围里。

## 五、已确认的决策

| # | 决策 | 日期 |
|---|---|---|
| D-1 | 对抗型不判「谁赢」，判「双方的事实主张是否可核验」 | 2026-11-16 |
| D-2 | 提议方必须给「文件:行号」，这是可机械判定的抓手 | 2026-11-16 |
| D-3 | 三 agent 题（提议/质疑/裁决）的裁决用固定 JSON 格式 | 2026-11-16 |
| D-4 | 接受「测不到见解高低」这个局限，不引入 LLM 主观评分 | 2026-11-16 |

## 六、不适用条件

- 不判「建议好不好」——只看能否落到具体行号
- 不判「谁有理」——只看主张能否被事实核对
- 不做主观质量评分——那需要人评或 LLM-judge，与「任何人可跑」矛盾
