# M-5 改动影响面 · 题目设计

> 日期：2026-11-16
> **按四题实测规律设计：测「不可机械化 + 对立视角」**

---

## 一、为什么这道题最能测插件能力

四题数据显示的规律：

| T 组赢的方式 | 依赖什么 | 稳定性 |
|---|---|---|
| 范围优势（M-1） | 任务分配 | 低 |
| 视角优势（M-2） | 分工设计 | 中 |
| **追问优势（M-3）** | **思维习惯** | **高** |

**M-5 同时具备「视角」和「追问」两种优势**，且**不可机械化**。

### 1.1 天然的对立视角

```
写的人看：「我要实现什么」
审的人看：「我会打破什么」
```

**这个对立不是设计出来的，是任务本身固有的。**

### 1.2 不可机械化

机械只能找出「谁 import 了这个函数」，但**判断不了**：

| 机械能找到 | 只有读代码才知道 |
|---|---|
| 16 处出现 | 哪 5 处是 import、哪 10 处是真调用 |
| 调用点位置 | **哪些会真的坏、哪些只是假警报** |

## 二、题目

### 2.1 任务描述

```
改动影响面评估：

假设要把 deliverModerationResultNotification 的 contentEntityId 参数
从「可空」改成「必填」，并新增一个必填参数 source（来源标识）。

请评估：会破坏哪些调用点？

对每一处，给出：
- 文件:行号
- **判定：真受影响 / 假警报**
- 理由（读代码说明为什么）
```

## 三、地面真值（我已完整查证）

### 3.1 全部 16 处出现的分类

| 性质 | 数量 |
|---|---|
| **定义** | 1（notifications/index.ts:151） |
| **import** | 5（各模块顶部） |
| **真实调用** | **10** |

**关键**：如果只看「grep 出 16 处」，会误以为要改 16 处。
**实际只有 10 处需要检查，其中 4 处真受影响。**

### 3.2 10 个调用点的详细判定

| # | 位置 | kind 覆盖 | contentEntityId | **判定** |
|---|---|---|---|---|
| 1 | corrections/index.ts:278 | ❌ 默认 | **null** | **真受影响**（contentEntityId 必填会炸） |
| 2 | forum/applications.ts:226 | ✅ 有 | **null** | **真受影响**（同上 + kind 要重审） |
| 3 | forum/applications.ts:259 | ✅ 有 | **null** | **真受影响**（同上） |
| 4 | interactions/index.ts:1606 | ❌ 默认 | 有值 | ⚠️ 仅受新增 source 影响 |
| 5 | moderation/service.ts:525 | ❌ 默认 | 有值 | ⚠️ 同上 |
| 6-10 | packs/index.ts:77/960/1018/1966/1999 | ❌ 默认 | 有值 | ⚠️ 同上（5 处） |

**精确结论**：

| 类别 | 数量 | 说明 |
|---|---|---|
| **硬破坏**（contentEntityId 必填会编译失败） | **3** | corrections:278、forum:226、forum:259 |
| **需补参数**（新增 source 要传） | **10** | 全部调用点 |
| **假警报**（import 语句，不用改） | **5** | 各模块顶部 |
| **定义本身** | 1 | 改这里 |

### 3.3 一个隐藏的坑

**forum/applications.ts 的 2 处都覆盖了 `kind`**（传 `forum_board_application`）。

如果评估者只看到「要加 contentEntityId 必填」，会漏掉：

> **这两处的 kind 语义（分区申请）与 contentEntityId=null 是绑定的**——
> 改成必填会让「分区申请审核」这类**本来就没有内容实体**的通知无法发送。

**这是最需要「追问」的地方**——不是「能不能编译过」，是「**改了这个语义还成立吗**」。

### 3.4 还有一处容易漏的

**`notifications/index.ts:156` 的注释明写**：

> 可以为空：资料纠错没有对应的内容实体（迁移 0016 放开）。

**这意味着「改成必填」是在推翻迁移 0016 的设计决定**——
评估者应该指出这一点，而不是只列调用点。

## 四、两组配置

| 组 | agent | 视角 |
|---|---|---|
| **S 组** | 1 | 全部 |
| **T 组** | 3 | agent1：发起方（改动会传到哪里）；agent2：调用方（我依赖什么）；agent3：**专职找漏网的**（间接依赖、动态调用、测试） |

**T-agent3 的角色是关键**——它的任务是「找别人会漏的」。

## 五、判据（五个）

| # | 判据 | 说明 |
|---|---|---|
| 1 | 覆盖率 | 找到几处 / 16 |
| 2 | 深度分 | 步数 / 文件数 |
| 3 | **真假区分准确度**（核心） | 正确区分「真受影响」和「假警报」的比例 |
| 4 | **语义洞察**（核心） | 有没有指出「改必填会推翻迁移 0016 的设计」 |
| 5 | 漏报数 | 有几个真受影响的没找到 |

### 评分口径

| 表现 | 评级 |
|---|---|
| 列出 10 个调用点 | 及格 |
| **正确区分 5 个 import 是假警报** | 良好 |
| **精确指出 3 处硬破坏** | 优秀 |
| **指出「改必填会破坏分区申请语义」** | 优秀+ |
| **指出「这推翻了迁移 0016」** | 满分 |

## 六、为什么这道题「不可机械化」

| 机械能做的 | 需要理解的 |
|---|---|
| grep 出 16 处 | 哪 5 处是 import |
| 列出调用点 | **哪 3 处会真的编译失败** |
| 提取参数列表 | **改必填会不会破坏业务语义** |
| — | **是不是在推翻历史设计决定** |

**后三条全部需要读代码、理解意图、追溯历史。**

---

## 七、与 M-1~M-4 的对比

| 题 | 材料 | 可机械化 | T 组优势类型 |
|---|---|---|---|
| M-1 | 15 万 | 部分 | 范围 |
| M-2 | 6.9 万 | 半 | 视角 |
| M-3 | 4.2 万 | 半 | 追问 |
| M-4 | 58.4 万 | **完全** | 深度（弱） |
| **M-5** | **约 8 万** | **❌ 不可** | **视角 + 追问** |

**M-5 的设计目标是「材料适中但不可机械化」**——
这样测的就不是「谁能读得多」，而是「**谁想得深**」。

## 八、已确认的设计

| # | 决策 |
|---|---|
| M5-1 | 任务：评估把 contentEntityId 改必填 + 新增 source 的影响面 |
| M5-2 | S 组 1 agent；T 组 3 agent（发起方 / 调用方 / 找漏网） |
| M5-3 | **核心判据：真假区分准确度 + 语义洞察** |
| M5-4 | 地面真值：16 处出现 = 1 定义 + 5 import + 10 调用；其中 3 处硬破坏 |
| M5-5 | **满分点：指出「改必填推翻迁移 0016 的设计」** |
