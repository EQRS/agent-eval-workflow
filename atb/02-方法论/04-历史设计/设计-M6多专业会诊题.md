# M-6 多专业会诊 · 题目设计

> 日期：2026-11-16
> **按出题原则 v2 设计：测「专业纵深」+ 双判据（质量/时间）**

---

## 一、核心设计

| 项 | 设计 |
|---|---|
| **素材** | 一份「收藏夹排序功能」的技术方案（44 行） |
| **S 组** | 1 个 agent 评审，**不提示任何专业维度** |
| **T 组** | 3 个 agent，各带专业身份（安全/性能/运维） |
| **双判据** | **① 质量：覆盖几个维度 ② 时间：墙钟耗时** |

**为什么这样能测出差异**：

> S 组会从「代码对不对」看，**不一定会切换到安全/性能/运维视角**。
> T 组被赋予专业身份，**各自只看自己那一块**。

---

## 二、方案里埋的四个隐患（地面真值）

### 2.1 安全维度

```
PATCH /api/me/favorites/{folderId}/reorder
body: { "orderedIds": ["id1", "id2"] }
服务端直接：UPDATE plugin_favorites SET position = ? WHERE id = ?
```

**问题**：**没有校验 orderedIds 是否属于该用户、该收藏夹**。

后果：用户 A 可以构造请求，修改用户 B 的收藏顺序（**水平越权**）。

### 2.2 性能维度

```sql
ALTER TABLE plugin_favorites ADD COLUMN position INTEGER DEFAULT 0;
ALTER TABLE pack_favorites ADD COLUMN position INTEGER DEFAULT 0;
ALTER TABLE post_favorites ADD COLUMN position INTEGER DEFAULT 0;
CREATE INDEX idx_plugin_favorites_position ON plugin_favorites(folder_id, position);
```

**问题**：

| 隐患 | 说明 |
|---|---|
| **加列默认值** | SQLite 的 ADD COLUMN 带 DEFAULT 是元数据操作，快；但**后续 UPDATE 全部行**才是真慢 |
| **三张表同时改** | 没有分批，一次性锁三张表 |
| **建索引** | 大表建索引会长时间持有写锁 |

### 2.3 运维维度

**方案原文**：

> 4. 发布方式：直接发布到生产环境，用户下次访问即可使用。

**问题**：

| 缺失 | 后果 |
|---|---|
| **无灰度** | 出问题影响全部用户 |
| **无回滚方案** | 加列可以留着，但**初始化脚本改了数据**，回滚要恢复数据 |
| **无监控** | 出了错不知道 |

### 2.4 数据维度（加分项）

```sql
ADD COLUMN position INTEGER DEFAULT 0
```

**问题**：**所有行的 position 都是 0**，排序结果不确定（相同值 SQLite 不保证顺序）。
方案说「用脚本赋 position 值」，但**脚本失败怎么办没说**。

## 三、判据（双判据）

### 3.1 质量判据

| 维度 | 具体问题 | 满分点 |
|---|---|---|
| **安全** | 越权 | 「reorder 没校验 orderedIds 归属」 |
| **性能** | 锁表 | 「初始化 UPDATE 全表会锁很久」或「建索引要分批」 |
| **运维** | 发布 | 「无灰度/无回滚/无监控」 |
| 数据（加分） | 默认值 | 「position 全 0 排序不确定」 |

**评分**：

| 覆盖维度 | 评级 |
|---|---|
| 0 个（只说代码风格） | 不及格 |
| 1 个 | 及格 |
| 2 个 | 良好 |
| **3 个全覆盖** | **优秀** |
| 3 个 + 数据维度 | 满分 |

### 3.2 时间判据

| 指标 | 怎么取 |
|---|---|
| **墙钟耗时** | 从派发到完成的时间戳差 |
| 成本 | --split 切分 |

### 3.3 综合判据：**性价比**

```
质量增量 = T组覆盖维度 - S组覆盖维度
时间比 = T组耗时 / S组耗时
成本比 = T组成本 / S组成本
```

## 四、预期三种结果

| 结果 | 说明 |
|---|---|
| T 组 3 维、S 组 0-1 维 | ✅ **协作带来质量增量** |
| 但 T 组耗时是 S 组的 3 倍 | ⚠️ **用时间换质量** |
| 两组都是 3 维 | ❌ **S 组也能想到专业视角** |

---

## 五、与 M-5 的关键区别

| | M-5 | **M-6** |
|---|---|---|
| S 组是否被告知维度 | ✅ 告知了（发起方/调用方/找漏网） | ❌ **完全不说** |
| T 组是否带专业身份 | ❌ 只是不同视角 | ✅ **明确专业身份** |
| 是否测时间 | ❌ 只测成本 | ✅ **测墙钟耗时** |

**M-6 修正了 M-5 的两个问题**：

> ① 不告诉 S 组有多少维度 → 测「能不能自己想到」
> ② 加了时间判据 → 如果质量差不多，看时间

## 六、已确认的设计

| # | 决策 |

## 七、不适用条件

- 不测「方案写得好不好」——只看有没有发现隐患
- 不要求给出修复方案——只评审
- 时间判据受机器负载影响，需在相近条件下跑
