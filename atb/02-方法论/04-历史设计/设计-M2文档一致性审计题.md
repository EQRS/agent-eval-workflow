# M-2 文档一致性审计 · 题目设计

> 日期：2026-11-16
> **这是按 v3 修正设计出的第一题**

---

## 一、为什么选这个题

M-1 的教训是「材料量要超出单 agent 预算」。M-2 按此设计：

| 要求 | M-1 | **M-2** |
|---|---|---|
| token 量 | 约 15 万 | **约 48 万** |
| 材料类型 | 100 个路由（同质） | **34 份文档 + 43 个服务文件（异质）** |
| 需要的能力 | 逐个读 | **两边交叉比对** |

**「异质材料交叉比对」比「同质材料逐个读」更难** ——
因为需要在两套心智模型之间来回切换。

---

## 二、题目

### 2.1 任务描述（两组相同）

```
文档一致性审计：找出 docs/项目规划 下文档所声称的内容，
与 src/server/modules 下代码实际实现之间的不一致。

审计维度：
① 文档描述的字段/表结构 vs 实际建表语句（migrations/）
② 文档描述的接口行为 vs 实际路由实现（src/app/api/）
③ 文档描述的迁移号 vs 实际存在的迁移文件

对每处不一致，给出：
- 文档：哪份文档、哪段描述
- 代码：哪个文件、哪一行
- 判定：是文档过时，还是代码写错
```

### 2.2 材料规模（满足新要求）

| 材料 | 数量 | 大小 |
|---|---|---|
| `docs/项目规划/` | 34 份 .md | 866 KB |
| `src/server/modules/` | 43 个 .ts | 约 700 KB |
| `migrations/` | 39 个 .sql | 约 200 KB |
| **合计** | **116 个文件** | **约 48 万 token** |

**远超单 agent 的舒适区。**

## 三、两组配置（按修正设计：两种对比都做）

### 3.1 主对比：不同范围（真实场景）

| 组 | agent | 范围 |
|---|---|---|
| **S 组** | 1 | 全部 116 个文件 |
| **T 组** | 3 | 按维度分工（见下） |

**T 组分工**：

| agent | 负责维度 | 要读的材料 |
|---|---|---|
| agent1 | ① 字段/表结构一致性 | 数据库模型.md + migrations/ |
| agent2 | ② 接口行为一致性 | 设计文档 + src/app/api/ |
| agent3 | ③ 迁移号一致性 | 全部文档 + migrations/ |

**注意**：这个分工会导致**部分重复读**（agent3 也要读 migrations），
但真实场景就是这样——**分工不是完美的正交切分**。

### 3.2 副对比：同范围（控变量，验机制）

**如果时间和成本允许**，再跑一组：

| 组 | agent | 范围 |
|---|---|---|
| S' 组 | 1 | 只审维度 ①（字段一致性） |
| T' 组 | 2 | 也是维度 ①，但一个读文档、一个读 migrations |

**这样能验证「分工是否比单干更深」**，排除「谁分到了问题」的干扰。

**建议**：先跑主对比，有预算再跑副对比。

## 四、判据（按修正设计：四个判据）

### 判据 1：覆盖率

审了多少份文档 / 34，审了多少个文件 / 82。

**但按 M-1 的教训，这个指标廉价**——扫一眼也算审了。

### 判据 2：深度分

```
深度分 = min(步数 / 文件数 / 5, 1)
```

**M-1 的验算**：S 组 12 步 / 100 文件 = 0.12 每文件，深度分 0.02。

### 判据 3：对照检查

报告里有没有「与同类对比」的表述？

| 表述 | 计分 |
|---|---|
| 「同目录其他 N 个都 X，唯独这个没有」 | +1 |
| 「文档说 A，代码实现 B」这种明确的**正反对照** | +1 |
| 只罗列「文档说了什么」「代码做了什么」但没对比 | 0 |

**M-1 里 agent1 就是因为做了对照才发现的。**

### 判据 4：有效发现

**我已经预先查证了几个已知的不一致**（做地面真值）：

| # | 不一致 | 状态 |
|---|---|---|
| 1 | `数据库模型.md` 声称「完整数据库模型」，实际停在 0036 前后 | 已知 |
| 2 | `数据库模型.md` 完全没提 `claimed_note` / `review_note` | 已知 |
| 3 | 其余待补 | 需进一步查 |

**审计者找出 1、2 算及格，找出更多算加分。**

### 4.5 地面真值（我已完整查证）

**这是 M-2 最重要的一节**——没有地面真值就无法判分。

#### 已知不一致 1：数据库模型.md 严重过时

| 项 | 事实 |
|---|---|
| 文档声称 | 「完整数据库模型」 |
| 实际表数 | **78 张**（含虚拟表，不含 _new） |
| **文档完全没提的表** | **33 张** |
| 文档提到的迁移号 | **0 个**（连一个迁移号都没提） |

**漏提的 33 张表完整清单**：

| 分类 | 表 |
|---|---|
| 论坛（15） | forum_boards、forum_board_moderators、forum_board_posting_rules、
| | forum_posts、forum_post_replies、forum_post_likes、forum_post_reply_likes、
| | forum_board_applications、forum_post_attachment_links、forum_reply_attachment_links、
| | forum_post_drafts、forum_post_draft_attachment_links、forum_post_screenings … |
| 精选（3） | featured_columns、featured_column_items、featured_subscriptions |
| 反馈（3） | feedback_tickets、feedback_handling_records、feedback_attachment_links |
| 身份（3） | user_roles、role_applications、plugin_ownerships |
| 收藏（2） | favorite_folders、post_favorites |
| 整合包评价（4） | pack_reviews、pack_review_revisions、pack_release_helpful_votes、plugin_pack_appeals |
| 其它（3） | attachment_blobs、runtime_heartbeats、rate_limiter_flexible、plugin_pack_release_files、user_preferences |

**审计者只要拿「migrations 里 CREATE TABLE 的表名」对「文档里出现的表名」做集合差，
就能发现这 33 个。**

#### 已知不一致 2：claimed_note / review_note 缺失

**上一步 D1 题发现的**：

| 事实 | 位置 |
|---|---|
| `role_applications` 有 `note` + `review_note` 两列 | 0040:55/57 |
| `plugin_ownerships` 只有 `claimed_note` 一列 | 0040:89 |
| `数据库模型.md` **完全没提这两张表** | — |

**所以这条其实是「不一致 1」的子集**——表都没提，字段更不会提。

#### 判分口径

| 发现数 | 评级 |
|---|---|
| 找出「数据库模型.md 过时」 | **及格** |
| 具体数出漏了 30-35 张表 | **良好** |
| 精确定位到 33 张 | **优秀** |
| 还发现其它维度（接口行为、字段定义） | **加分** |

**注意**：33 这个数字**不用完全精确**，因为「文档没提」的判定有歧义
（比如某个表名在文档的代码块里出现过但没在正文讲）。
**给区间 30-35 都算对。**

## 五、成本预估与预算设置

**按 v3 修正设计，要给 agent 明确预算**。

| 组 | agent | 预算（步数） | 理由 |
|---|---|---|---|
| **S 组** | 1 | **40 步** | 116 个文件，每文件 0.34 步——**明显不够深读** |
| **T 组** | 3 | **每个 25 步，共 75 步** | 分工后每个 agent 文件少，可以读深 |

**这个预算设置的关键**：

> S 组 40 步审 116 文件 = 每文件 0.34 步，**物理上无法深读**。
> T 组每个 25 步审约 40 文件 = 每文件 0.6 步，**是 S 组的 1.8 倍深度**。

**这样「漏」就是结构性的，不是运气。**

## 六、与 M-1 的对比（验证设计改进）

| 项 | M-1 | **M-2** |
|---|---|---|
| 材料量 | 15 万 token | **48 万 token**（3.2 倍） |
| 材料类型 | 同质（100 个路由） | **异质（文档 + 代码 + 迁移）** |
| 是否有预算 | ❌ 无 | ✅ **S 40 步 / T 每人 25 步** |
| 是否做同范围对比 | ❌ 无 | ✅ 有（副对比） |
| 判据数 | 2 个 | **4 个**（覆盖率/深度分/对照检查/有效发现） |
| 地面真值 | 1 个漏洞 | **33 张漏提的表** |

**M-2 是 M-1 的改进版**——四个设计问题都修了。

## 七、风险与应对

| 风险 | 表现 | 应对 |
|---|---|---|
| **超出上下文** | agent 读不完就报错 | 先小规模试跑，撞上限就减材料 |
| **成本过高** | 48 万 token × 两组 | 预计 200-400 万，可接受 |
| **判据难判** | 「不一致」的定义模糊 | 给了明确的三维度 + 地面真值 |
| **T 组分工重叠** | agent1 和 agent3 都读 migrations | 接受——真实场景就这样 |

## 九、不适用条件

- 不评判「文档该不该这么详细」——只查一致性
- 不要求给出文档修订方案——只审计
- 33 张表的精确数不强求——「把某张表在代码块里出现过」也算「提过」，有歧义
