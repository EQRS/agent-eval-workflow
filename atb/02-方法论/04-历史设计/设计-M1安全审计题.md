# M-1 安全审计 · 题目设计

> 日期：2026-11-16
> 目的：验证「多视角协作」能否发现单干漏掉的问题

---

## 一、为什么这道题能测出协作价值

**核心假设**：

> 100 个 API 路由，一个 agent 会因为「太多了」而抽样；
> 三个 agent 各审一部分，可以全覆盖。

**这是一个可验证的假设**——只要看：

| 指标 | 含义 |
|---|---|
| **覆盖率** | 审了多少个路由 / 100 |
| **发现数** | 找到了多少个真实问题 |
| **漏报率** | 地面真值里有多少没被发现 |

---

## 二、题库的客观现状（我已勘察）

| 项 | 数量 |
|---|---|
| API 路由总数 | **100** |
| 有鉴权调用 | 90 |
| **无鉴权调用** | **10** |

**那 10 个无鉴权的**：

| 路由 | 方法 | 判断 |
|---|---|---|
| `/api/auth/github/callback` | GET | ✅ 合理（登录回调） |
| `/api/auth/github/start` | GET | ✅ 合理（登录起点） |
| `/api/content/[contentId]/comments/[commentId]/replies` | GET | ✅ 合理（公开读） |
| `/api/featured` | GET | ✅ 合理（公开读） |
| `/api/health` | GET | ✅ 合理（健康检查） |
| `/api/plugins/search` | GET | ✅ 合理（公开搜索） |
| `/api/plugins/[pluginId]` | GET | ✅ 合理（公开读） |
| `/api/reviews` | GET | ✅ 合理（公开读） |
| `/api/reviews/[reviewId]` | GET | ✅ 合理（公开读） |
| **`/api/testing/session`** | **POST** | ⚠️ **需要审查** |

### 最后那个有真实的门道

我读了它的实现，**代码里有三道闸门**：

> 1. 路由路径本身带 `testing/`；
> 2. 环境变量 `DSH_REVIEW_ALLOW_TEST_LOGIN` 正好等于 `1`；
> 3. `NODE_ENV !== 'production'`（生产即使设了开关也不生效）。

**审计者需要判断**：这三道闸门够不够？有没有绕过方式？

**这是主观题**——没有标准答案，但能看出审计者的深度。

## 三、题目设计

### 3.1 任务描述（两组相同）

```
安全审计：审查 src/app/api 下全部 100 个 API 路由的权限校验是否完整。

对每个路由，判断：
① 它是否有鉴权（currentContext / assertCanWrite / assertCanAdmin / isAdmin）
② 如果没有鉴权，它在业务上是否应该公开
③ 如果有鉴权，校验是否足够（有没有漏掉 owner 检查、角色检查）

输出：
- 有问题的路由清单（路由路径 + 问题描述 + 依据的行号）
- 无问题但需要说明的路由（如刻意公开的）
```

### 3.2 两组的配置

| 组 | agent 分配 | 边界 |
|---|---|---|
| **S 组（单干）** | 1 个 agent | 可读全部 `src/app/api/` |
| **T 组（协作）** | 3 个 agent | 各读一部分（见下） |

**T 组的分工**（按一级子目录，覆盖面相当）：

| agent | 负责 | 路由数 |
|---|---|---|
| agent1 | `admin/` | 30 |
| agent2 | `me/` | 14 |
| agent3 | 其余（forum/content/reviews/packs/...） | 56 |

**注意 agent3 负担更重**——这不公平，但真实场景就是这样（路由分布不均）。
**要不要平衡一下？** 见 §五的讨论。

### 3.3 判据

| 判据 | 怎么判定 |
|---|---|
| **覆盖率** | 审计者声明审了多少个 / 100 |
| **发现数** | 提出的问题数 |
| **有效发现** | 其中经我核实为真的 |
| **漏报** | 我已知的问题中，它没报的 |

**我已确定的地面真值**：

| 项 | 值 |
|---|---|
| 无鉴权路由 | 10 个（9 个合理 + 1 个需审查） |
| 有鉴权路由 | 90 个 |

**「需审查」那个（testing/session）** 有明确的三道闸门，
**能指出「有三道闸门、且都生效」也算正确答案**。

## 四、预期结果与判读

| 场景 | S 组 | T 组 | 说明 |
|---|---|---|---|
| **A** | 抽审 20-30 个 | 全覆盖 100 个 | **协作有价值**——覆盖增量明显 |
| **B** | 也审完 100 个 | 全覆盖 | **协作无增量**，只是更快 |
| **C** | 审完但漏报 | 审完且发现更多 | **协作有深度增量** |
| **D** | 都审完、发现相同 | 都审完、发现相同 | **协作完全无价值** |

**A 是最可能的**——因为 100 个文件确实多，单 agent 容易抽样。
**但如果结果是 B 或 D，那说明协作在审计类任务上也没用**。

**这四种结果都有信息量**，这正是好题的标准。

---

## 五、一个待定项：T 组的分工是否公平

**问题**：按一级子目录分，agent1 只有 30 个、agent3 有 56 个。

**这公平吗？**

| 观点 | 理由 |
|---|---|
| **公平** | 真实场景就是分布不均，测的是「插件能不能应对不均衡」 |
| **不公平** | 如果 agent3 成了瓶颈，测的是「负载均衡」而不是「协作价值」 |

**我的倾向**：**先用不均的分工跑一次**，因为：

1. 如果 agent3 拖慢了，正好暴露「插件的任务分配能力」
2. 如果要测「纯协作价值」，下次再跑均分版

**这也符合「一次只改一个变量」的原则。**

## 六、成本预估

| 组 | agent 数 | 预估 token |
|---|---|---|
| **S 组** | 1 | 约 80-150 万（读 100 个文件） |
| **T 组** | 3 | 约 150-250 万（各自读 + 汇总） |
| **合计** | | **约 250-400 万** |

**这个量级可接受**——比 v2 最贵的 E3（1275 万）少很多。

## 七、已确认的设计

| # | 决策 |
|---|---|
| M1-1 | 题目：审计 100 个 API 路由的权限校验 |
| M1-2 | 两组：S 组单干（可读全部）、T 组 3 agent 按一级子目录分工 |
| M1-3 | 判据：覆盖率 + 发现数 + 有效发现 + 漏报 |
| M1-4 | 先用**不均的分工**（admin 30 / me 14 / 其余 56） |
| M1-5 | 地面真值：10 个无鉴权（9 合理 + 1 需审查） |

---

## 八、不适用条件

- 不评判「问题严重性排序」——那是主观的，只看发现数
- 不要求给出修复方案——只审计不修
- 不测「运行时验证」——只做静态审查
