# 原型任务规格 · ATB 评测集（8 题）

> 配套文档：`docs/设计-智能体团队评测集.md`
> 目的：验证六维度能否区分团队、采集链路能否自动化
> 日期：2026-11-15

---

## 统一约定

### 执行方式

```
每道题 = 一个新会话（captain）+ 一支新团队
跑完后用 scripts/atb/collect.mjs 采集该会话
```

### 判据类型

| 类型 | 判定方式 | 举例 |
|---|---|---|
| **机械** | 脚本自动判 | 依赖是否违规、状态转换是否合法 |
| **断言** | 跑测试/命令判 | 生成的代码能否通过测试 |
| **结构** | 分析事件流判 | 有没有环、有没有孤立任务 |

**不允许人评**——人评无法复现，也做不到「任何人可跑」。

---

## P1 · 计划拆解（L1 / D1）

| 项 | 内容 |
|---|---|
| **题目** | 把「给这个仓库加一个 /health 接口」拆成可执行的子任务，输出任务清单 |
| **给团队的输入** | 目标 + 仓库路径 |
| **判据** | ① 子任务数 ≥ 3；② 每个子任务有明确动词（读/改/写/测）；③ 无依赖环 |
| **采集维度** | D1 计划结构 |
| **通过线** | 结构合法 = true |

**为什么这样设计**：拆解本身难判定，但**拆出来的结构**是机械可判的。

---

## P2 · 依赖顺序（L1 / D3）

| 项 | 内容 |
|---|---|
| **题目** | 三个任务 A→B→C 串行：A 读文件、B 基于 A 写、C 校验 B |
| **判据** | B 在 A 完成前**不可被认领**；C 同理 |
| **采集维度** | D3 依赖正确性 |
| **通过线** | 顺序违规 = 0 |

**这是唯一能证明依赖机制真的生效的断言**。如果 B 在 A 之前就被 claim，说明依赖是摆设。

---

## P3 · 成本基线（L1 / D6）

| 项 | 内容 |
|---|---|
| **题目** | 单成员完成一件极小的事（读一个文件并总结） |
| **判据** | 记录完整 usage；token 不为 0 |
| **采集维度** | D6 成本 |
| **通过线** | 能采到 usage 且数值合理 |

**这题是成本基线**——后面所有题的 D6 都要跟它比。

---

## P4 · 并行分发（L2 / D1+D2）

| 项 | 内容 |
|---|---|
| **题目** | 4 个互不依赖的任务（分别统计 4 个目录的文件数），2 个成员 |
| **判据** | ① 4 个任务全部完成；② 无成员重复做同一任务；③ 并发峰 ≥ 2 |
| **采集维度** | D1、D2 |
| **通过线** | 全部完成 + 无重复 + 并发峰 ≥ 2 |

**这题测的是「团队到底有没有并行」**——如果并发峰只有 1，那团队等于单干。

---

## P5 · 依赖 + 汇报（L2 / D3+D4）

| 项 | 内容 |
|---|---|
| **题目** | 两步依赖任务，**强制要求**成员完成后用 `send_message` 向 captain 汇报结果 |
| **判据** | ① 依赖顺序正确；② captain 收到消息且内容与产出一致 |
| **采集维度** | D3、D4 |
| **通过线** | 顺序违规 0 + 消息送达 |

**这题专门解决 D4 的代理指标问题**——强制走消息通道，D4 才有真实数据。

---

## P6 · 溢出成员（L2 / D2）

| 项 | 内容 |
|---|---|
| **题目** | 3 个任务，**4 个成员**（成员多于任务） |
| **判据** | ① 3 个任务完成；② 无成员做重复任务；③ 记录空闲成员数 |
| **采集维度** | D2 调度 |
| **通过线** | 全部完成 + 无重复 |

**为什么设计成「成员多于任务」**：这能测出调度器会不会让多余的成员闲着、会不会产生重复劳动。
这是真实使用中常见的情形（派的人比活多）。

---

## P7 · 假需求陷阱（L3 / D5）

| 项 | 内容 |
|---|---|
| **题目** | 「把这个仓库里所有的 Node 依赖升级到最新版」，但仓库**实际没有 Node 项目**，只有 Python 脚本 |
| **期望行为** | **先质疑**「这里没有 Node 项目」，而不是硬找一个升级 |
| **判据** | 团队是否在动手前指出「前提不成立」 |
| **采集维度** | D5 抗干扰 |
| **通过线** | 有明确质疑，且未产生无意义改动 |

**这是 L3 的核心**：好的团队会停下来说「你搞错了」，一般的团队会照着做。

---

## P8 · 沉默失败（L3 / D5）

| 项 | 内容 |
|---|---|
| **题目** | 3 个任务，其中 1 个**注定失败**（如「读取一个不存在的文件」），但不告诉团队 |
| **期望行为** | 团队能**及时发现**失败并报告，而不是静默卡住 |
| **判据** | ① 失败任务进入 failed 状态；② captain 收到失败通知；③ 其余 2 个任务不受影响完成 |
| **采集维度** | D5、D2 |
| **通过线** | 失败被发现 + 其余任务正常完成 |

**为什么重要**：多 agent 最危险的失败是沉默的——某个成员卡住了，其他人都不知道。

| 维度 | 覆盖题目 | 题数 |

## 执行清单

跑每道题时记录：

| 记录项 | 怎么取 |
|---|---|
| 会话 id | 开团队时记下 captain 的 session id |
| 开始/结束时间 | 便于算墙钟 |
| 人工干预 | 中途插话了几次、说了什么 |
| 采集结果 | `node scripts/atb/collect.mjs <会话文件>` 的输出 |

## 判定「这道题有效」的标准

每道题跑完后问三个问题：

1. **它测的维度有没有出数？** 没出数 = 采集链路有问题
2. **不同团队跑它，结果有没有差异？** 全一样 = 区分度为 0，题要改
3. **判据是机械的吗？** 需要人判断 = 不达标

**第 2 条最重要**：原型阶段如果某题在所有团队上都拿满分，那它测不出东西。

---

## 不适用条件

- 不追求题目难度上限——原型目标是验证链路，不是压测
- 不做隐藏题库（正式版才引入）
- 不要求跨模型可比（固定 DS）
- D4 只有 1 题，代理指标问题待 P5 验证后再决定是否加题
