# 测评设计 · Agent Teams 插件（NanmiCoder vs 官方）

> 对象：`@nanmicoder/dsh-agent-teams@0.1.30`
> 对照：官方 `@deepseek-ai/dsh-experimental-agent-team@0.1.5-alpha.2`（4 包组合）
> 基线：单 agent 会话
> 日期：2026-11-14

---

## 一、测什么：三个层次

| 层次 | 回答的问题 | 手段 |
|---|---|---|
| **可用性** | 功能能不能正常工作 | 8 个任务逐个跑，有硬断言 |
| **好用程度** | 相比单 agent 是否真的更好 | 三组对照实验 |
| **实现质量** | 代码本身是否可靠 | 源码静态分析 |

**为什么要有基线组**：只比 NanmiCoder vs 官方，回答不了「组队本身值不值」。
三个组才能看出「各自比单干强多少」。

---

## 二、三组对照

| 组 | 配置 | 说明 |
|---|---|---|
| **A 基线** | 单 agent 会话 | 不用任何 team 插件 |
| **B 官方** | `@deepseek-ai/dsh-experimental-agent-team` 4 包 | 原语层 |
| **C 产品** | `@nanmicoder/dsh-agent-teams` | 产品层 |

### 为什么这两者不能简单比「谁更好」

| | 官方 | NanmiCoder |
|---|---|---|
| 形态 | 4 个包（运行时 / profile / 工具 / UI） | 1 个自包含包 |
| 版本 | `0.1.5-alpha.2` | `0.1.30` |
| 文档 | 无 | 20KB README + 兼容矩阵 |

**两者不在同一层**：官方给原语，NanmiCoder 给产品。
所以对照要问的是「什么场景下多一层封装值得」，而不是「谁赢」。

### 如果 C 全面获胜，要怀疑测评设计

> 若 C 在**所有维度**都优于 B，说明测的多半是「C 有而 B 没有的功能」，
> 而不是两者的真实能力差。好的测评应当能暴露 C 的劣势（比如灵活性、成本）。

## 三、可用性测试：8 个任务

设计原则：**每个任务都有一句可判死的断言**，不接受「看起来能用」。

### T0 最小闭环（冒烟）

| 项 | 内容 |
|---|---|
| 做什么 | 让 1 个成员做一件 1 分钟内能完成的事 |
| 覆盖工具 | `create` `add_member` `create_task` `claim_task` `update_task` `status` |
| **硬断言** | 任务从 pending 到 completed 全程状态可查；成员确实执行了 |
| 失败即停 | 此项不过，后面 7 项都不必跑 |

### T1 依赖链（顺序控制）

| 项 | 内容 |
|---|---|
| 做什么 | 建 A→B→C 三级强依赖任务 |
| 覆盖工具 | `create_task` 的 `dependencies`、调度器依赖判断 |
| **硬断言** | **B 在 A 完成前不可被认领**（这是唯一能证明依赖生效的断言） |
| 怎么验 | A 还在跑时，检查 B 的状态必须是 pending 且不可 claim |

### T2 并行分发（调度与去重）

| 项 | 内容 |
|---|---|
| 做什么 | 建 4 个互相独立的任务，2 个成员 |
| 覆盖工具 | 自动认领、`claim_task` 的互斥 |
| **硬断言** | 4 个任务全部完成，且**没有任何两个成员做同一件事** |
| 为什么重要 | 调度去重失败是多 agent 最典型的问题 |

### T3 消息传递（通信）

| 项 | 内容 |
|---|---|
| 做什么 | 要求成员完成后**必须**通过 `send_message` 向队长汇报 |
| 覆盖工具 | `send_message`、持久邮箱 |
| **硬断言** | 队长确实收到消息，且内容与成员产出一致 |

### T4 中途改派（接管）

| 项 | 内容 |
|---|---|
| 做什么 | 成员 A 正在做任务 X 时，把 X 改派给 B |
| 覆盖工具 | `reassign_task`、attempt 作废 |
| **硬断言** | A 的旧 attempt_id **失效**；B 能接手并完成；A 不会还在偷偷做 |

### T5 计划先行（审批流）

| 项 | 内容 |
|---|---|
| 做什么 | 用 `/agent-teams` 发起多步任务，**先不批准** |
| 覆盖工具 | `create` 的 staged 计划、`approve`、`edit_plan` |
| **硬断言** | 计划出来后：**没有成员被 spawn、没有任务开始执行** |
| 变体 | 计划出来后先 `edit_plan` 改一版，再批准 |
| 注意 | 这项需要人工批准，属于人机协作测试 |

### T6 契约变更（amend）

| 项 | 内容 |
|---|---|
| 做什么 | 建一个**质量任务**（kind=implementation），故意给过宽的 inScope，随后 amend 收紧 |
| 覆盖工具 | `amend_task` |
| **硬断言** | 能改成功，且 revisions 记录里能看到旧值与原因 |
| 边界 | 已通过审核的任务**不能**再 amend（这是它自身的限制） |

### T7 恢复与清理

| 项 | 内容 |
|---|---|
| 做什么 | T0 跑完后 `resume` 一次，再 `delete` |
| 覆盖工具 | `resume`、`delete`、`remove_member` |
| **硬断言** | resume 能从停处继续而非重来；delete 后无残留成员/任务 |

## 五、对照实验设计

### 5.1 三组任务（覆盖不同形状）

| 任务 | 形状 | 为什么选它 | 预期胜者 |
|---|---|---|---|
| **E1 并行独立** | 4 个互不依赖的子任务 | team 的强项场景 | C/B 应明显优于 A |
| **E2 依赖链** | A→B→C 顺序 | 考验任务调度 | B/C 略优，但差距小于 E1 |
| **E3 单点深挖** | 排查一个复杂问题的根因 | **team 的弱项场景** | **A 可能反而更好** |

**E3 是这次对照的关键**：如果 team 在单点深挖上也赢，说明测评设计有问题——
三个 agent 查同一个 bug，只会互相干扰、重复劳动、拉高成本。

### 5.2 记录指标

| 指标 | 怎么取 | 为什么 |
|---|---|---|
| **结果质量** | 人评 3 级（不合格/合格/优秀） | 最重要的指标 |
| **墙钟耗时** | 从下达到完成的实际时间 | 组队应该更快 |
| **token 消耗** | 会话统计 | 组队是 N 倍成本，必须算 |
| **人工干预次数** | 中途插话纠正几次 | 干预多说明自主性差 |
| **返工次数** | 有几个任务做错要重来 | 质量稳定性 |

## 六、A 组（单 agent）操作规范

使用者负责跑 A 组。为保证**控制变量**，必须遵守：

### 6.1 开新会话，不要复用

每组任务都**新开一个会话**。复用会带入上一轮的上下文，导致 A 组「记得」之前做过什么。

### 6.2 用同样的原始提示词

A 组的提示词 = B/C 组任务描述的**原文**，不加任何「你是单 agent，所以……」这类提示。

### 6.3 不中途帮忙

**只在它明确卡住（连续两轮没有进展）时才干预**，且要记录干预了几次、说了什么。

### 6.4 三个任务的 A 组提示词模板

```
【E1 并行独立】
统计这个仓库里 src/ 目录下有多少个 .ts 文件、多少个 .tsx 文件、
多少个 .json 文件、多少个 .md 文件，分别列出清单。
```

```
【E2 依赖链】
（1）读 package.json，总结这个项目用了哪些主要依赖；
（2）基于第 1 步的总结，写一段 200 字以内的项目技术栈介绍；
（3）检查第 2 步写的介绍里有没有事实错误，逐条对照 package.json。
```

```
【E3 单点深挖】
这个项目里有这样一个问题：<在此填入一个真实的、需要深挖的小 bug>。
请找出根因，并给出修复方案。
```

> **E3 的 bug 由使用者挑**，要求是：单点、需要读几处代码才能定位、但不至于无解。

## 七、风险观察清单

除了「能不能用」，还要主动去找它**什么时候会坏**。

| 风险 | 怎么观察 | 记录什么 |
|---|---|---|
| **成员失控** | 给它一个模糊目标，看会不会跑偏 | 偏到什么程度、有没有自查回来 |
| **重复劳动** | T2 里盯有没有两人做同一件事 | 发生了几次 |
| **消息丢失** | T3 里连发 3 条消息 | 收到几条、顺序对不对 |
| **任务卡死** | 全流程盯有没有任务长期 in_progress | 卡在哪个状态、能不能恢复 |
| **成本失控** | 记 token | 组队 vs 单干的倍数 |
| **唤醒风暴** | 观察有没有成员被反复唤醒 | 同一个任务被唤醒几次 |

## 八、源码分析要点（C 阶段）

不做运行时，只看代码，检查这些：

| 项 | 看什么 | 为什么重要 |
|---|---|---|
| 状态持久化 | 团队状态存哪、怎么恢复 | 决定了「重启后能不能接着干」 |
| 并发控制 | claim 时怎么防重复 | 调度正确性的根 |
| attempt 机制 | 改派时旧 attempt 怎么作废 | 防止两个 agent 同时写同一处 |
| 错误处理 | agent 失败时任务回到什么状态 | 决定容错能力 |
| 与宿主耦合 | 依赖哪些 DSH 内部接口 | 决定升级后会不会碎 |
| 代码规模 | 80 个文件 / 1.2MB | 复杂度是否合理 |

## 九、执行顺序

```
1. C 阶段：源码分析（不占运行时，先做）
      ↓
2. T0 冒烟（不过就停，不值得继续）
      ↓
3. T1-T7 可用性（8 项，逐项打勾）
      ↓
4. 对照实验 E1-E3（三组 × 三任务）
      ↓
5. 出结论
```

**为什么先 C 后 A**：源码能提前暴露结构性问题（比如状态没持久化），
这类问题在运行时测试里可能只是「偶尔卡住」，很难复现；读代码能直接看出来。

## 十、结论的三种可能

| 结论 | 判据 | 建议 |
|---|---|---|
| **推荐** | 8 项全过；E1 明显优于 A；E3 不比 A 差太多；风险项都出现过但可接受 | 进整合包，正常推荐 |
| **有条件推荐** | 8 项全过；但 E3 明显劣于 A，或成本高出 3 倍 | 进整合包，但说明「适合并行任务，不适合单点深挖」 |
| **不推荐** | 有硬断言不过（依赖失效、认领重复、消息丢失） | 不进整合包，记录问题反馈给作者 |

## 十二、不适用条件

- 不测 UI 的美观程度（主观，不在可用性范畴）
- 不测与灵枢蜂巢的兼容性（使用者已裁定不启用官方实验版，无对照对象）
- 不对 alpha 版官方包做稳定性评价（版本本身就不保证稳定）
- 不评估商业价值与定价（不在本次范围）
