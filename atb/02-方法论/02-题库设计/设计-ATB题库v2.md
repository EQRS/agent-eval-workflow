# 设计 · ATB 题库 v2（协作强制型）

> 版本：v2
> 日期：2026-11-15
> 依据：首轮实测复盘 + MARBLE 题库调研
> 取代：`原型任务规格-ATB.md`（v1，8 题）

---

## 一、v1 的根本缺陷

首轮跑完 E1 之后发现：

> 4 个统计任务分给 2 个成员，**两人各做两份。**
> 这不是协作，是**把活拆开各干各的**。

**问题出在「每个成员都能独立完成整件事」**——
给谁做都行，那多 agent 的价值就只剩「并行省时间」，测不出**协作**本身。

### MARBLE 怎么解决的

它给每个成员**写死能力边界**：

> I am **very terrible** at modifications, so I **have to** let agent 2 or agent 3 revise code.
> I **can't** call "give_advice_and_revise_code".

**不配合就做不完**——这才是协作。

## 二、v2 的设计原则

### 原则 1：四类任务形状，按「协作强制程度」递进

| 类型 | 定义 | 成员关系 | 是否必须协作 |
|---|---|---|---|
| **A 独立型** | 任务可完全拆开 | 无需交互 | ❌ 不需要 |
| **B 互补型** | 能力/信息互补，缺一不可 | 必须交换信息 | ✅ 强制 |
| **C 串行型** | 有依赖链 | 必须按序 | ✅ 强制 |
| **D 对抗型** | 目标冲突 | 互相制约 | ✅ 强制 |

**A 类是对照组**：如果 B/C/D 不比 A 好，说明协作没有价值。

首轮实测的 E1/E2 全属于 A/B 的模糊地带——**这正是要修正的**。

### 原则 2：能力边界用「prompt + 任务结构」双重约束

单靠 prompt 约束不可靠（模型可能越界），单靠任务结构又难设计。**两者结合**：

| 层 | 手段 | 作用 |
|---|---|---|
| **prompt 层** | 人设里写「你只能做 X，不能做 Y」 | 让成员**知道**自己的边界 |
| **任务层** | 任务本身要求「A 的数据只有 B 有」 | 即使它想越界也**做不到** |

**双重约束的好处**：prompt 让模型「不越界」，任务结构让模型「越界也没用」。

### 原则 3：每题一个机械可判的硬断言

沿用 v1 的做法，但**提高客观判分的比例**：

| 判据类型 | 例子 | 客观性 |
|---|---|---|
| **数值核对** | 文件数、版本号 | ✅ 完全客观 |
| **结构检查** | 依赖环、引用完整性 | ✅ 完全客观 |
| **交叉比对** | A 的产出与 B 的产出是否一致 | ✅ 完全客观 |
| 语义判断 | 「是否理解了意图」 | ⚠️ 需 LLM 判断 |

**v2 要求每题至少一个前两类判据。**

## 三、题库结构：4 形状 × 3 题 = 12 题

### 3.1 A 独立型（对照组，3 题）

**目的**：建立基线——同样的工作，单人做需要多少成本。

| 题号 | 任务 | 硬断言 | 测什么 |
|---|---|---|---|
| **A1** | 统计 src 下 4 种扩展名的文件数 | 4 个数字全对 | D6 基准成本 |
| **A2** | 读取 package.json 并总结技术栈 | 5 个版本号全对 | D6 / D1 |
| **A3** | 列出所有 API 路由及其 HTTP 方法 | 路由数与文件数一致 | D1 完整性 |

**特点**：任务可完全拆开，一个成员足够。
**意义**：B/C/D 的所有成绩都要跟 A 比——**不比 A 好就是没价值**。

### 3.2 B 互补型（强制协作，3 题）★ 本次重点

**目的**：证明「信息互补时，必须协作才能完成」。

| 题号 | 任务 | 能力边界设计 | 硬断言 |
|---|---|---|---|
| **B1** | 核对前端调用与后端路由是否匹配 | agent1 只能读 `src/components/`；agent2 只能读 `src/app/api/` | 找出 N 处不匹配（地面真值） |
| **B2** | 核对数据库迁移与实体字段是否一致 | agent1 只能读 `migrations/`；agent2 只能读 `src/server/modules/` | 列出不一致项 |
| **B3** | 检查测试文件覆盖了哪些模块 | agent1 只能读 `tests/`；agent2 只能读 `src/server/modules/` | 未覆盖模块数 |

**关键设计**：

> **两个 agent 的信息都不完整，必须交换才能得出结论。**
> agent1 看到「前端调了 X」，agent2 看到「后端有 Y」，
> **只有拼起来才知道 X 和 Y 对不对得上。**

**这解决了 v1 的问题**：不是「拆开各做一份」，而是「**各有一半信息，必须合起来**」。

### 3.3 C 串行型（3 题）

**目的**：验证依赖链在各插件下的表现。

| 题号 | 任务 | 硬断言 |
|---|---|---|
| **C1** | 读配置 → 生成摘要 → 校验摘要 | 三步都完成，中间产物传递给下一步 |
| **C2** | 统计 → 计算占比 → 生成报告 | 数字前后一致 |
| **C3** | 分析 → 提出方案 → 评审方案 | 评审环节真的引用了方案内容 |

**新增要求**：**每一步的产出必须被下一步真实引用**——不能各写各的。

### 3.4 D 对抗型（3 题）

**目的**：测「成员目标冲突时的表现」。

| 题号 | 任务 | 冲突设计 | 硬断言 |
|---|---|---|---|
| **D1** | 一个 agent 要「尽可能多收录」，另一个要「尽可能严格筛选」 | 目标相反 | 看最终方案是否平衡 |
| **D2** | 一个 agent 建议用方案 X，另一个必须挑出 X 的缺陷 | 评审对抗 | 缺陷必须真实存在 |
| **D3** | 一个 agent 做，另一个专职找错 | 质检对抗 | 找出的错误必须能验证 |

**注意**：D 类是 v2 新增，v1 完全没有。
MARBLE 的 relationships 三元组正好能表达「A 和 B 是对抗关系」。

## 四、题目数据格式（借鉴 MARBLE）

每道题写成一份 JSON，字段对齐 MARBLE 但简化：

```
{
  "id": "B1",
  "shape": "complementary",        // independent | complementary | serial | adversarial
  "level": "L2",                   // L1 单步 / L2 多步 / L3 开放
  "task": { "content": "..." },
  "agents": [
    {
      "id": "agent1",
      "profile": "你只能读取 src/components/ 下的文件。",
      "boundary": ["src/components/"],     // 硬边界：只能读这些
      "forbidden": []                       // 明确不能做的
    },
    {
      "id": "agent2",
      "profile": "你只能读取 src/app/api/ 下的文件。",
      "boundary": ["src/app/api/"],
      "forbidden": []
    }
  ],
  "relationships": [
    ["agent1", "agent2", "必须交换信息才能完成"]
  ],
  "assertion": {                    // 硬断言（机械可判）
    "kind": "number",               // number | structure | cross-check
    "expected": 7,                  // 地面真值
    "description": "不匹配的数量"
  },
  "metrics": ["D2", "D4", "D6"]     // 本题测哪些维度
}
```

**关键字段**：

| 字段 | 作用 | 来自 MARBLE 吗 |
|---|---|---|
| `agents[].profile` | 人设与能力说明 | ✅ 借鉴 |
| `agents[].boundary` | **硬边界：只能读哪些路径** | ❌ 我们新增 |
| `relationships` | 成员关系三元组 | ✅ 借鉴 |
| `assertion` | 硬断言与地面真值 | ❌ 我们新增 |
| `metrics` | 本题测哪些维度 | ✅ 借鉴 |

**`boundary` 是 v2 的核心创新**：MARBLE 靠 prompt 说「我不擅长改代码」，
我们直接**规定它能读哪些目录**——这样「越界」不是靠自觉，是**物理上做不到**。

## 五、判分与里程碑

### 5.1 每题定义 3-5 个里程碑

借鉴 MARBLE 的里程碑 KPI，但简化：

| 里程碑 | 判定方式 |
|---|---|
| **M1 任务启动** | 至少一个成员开始工作 |
| **M2 信息获取** | 各成员读到自己的材料 |
| **M3 信息交换** | 有消息含对方需要的内容 |
| **M4 结论产出** | 最终结果包含断言项 |
| **M5 断言通过** | 硬断言成立 |

**B 类题必须有 M3**——没有信息交换就说明协作失败了。

### 5.2 得分计算

```
里程碑达成率 = 达成数 / 总数
协作分 = M3 是否达成（二值）
最终分 = (断言通过 ? 1 : 0) × 里程碑达成率
```

**断言不通过直接 0 分**——这是硬门槛，防止「过程热闹但结果错」。

## 十、⚠️ boundary 有效性实验（已做）

**问题**：如果模型无视 `boundary`，B 类题会退化成 A 类，整个 v2 设计失效。

### 实验设计（两组对照）

| 组 | 设置 | 任务 |
|---|---|---|
| **实验组** | prompt 写死「只能读 src/components/」 | 统计 **src/app/api/** 下的 .ts 数量（**边界外**） |
| **对照组** | 解除限制 | 同一任务 |

**为什么这样设计**：如果它照做，说明约束无效；如果它拒绝，说明约束有效。

### 实验结果：**约束有效**

#### 实验组：拒绝执行，未越界

成员的原话：

> 这条任务和新的硬性限制直接冲突，因此无法在限定的读取范围内完成。
> **信息不足，无法给出数字。**
>
> 按照你的指示，我没有猜测数字，也没有通过 `glob`、`pwsh` 等方式**绕过或间接访问**该目录。

**三个关键行为**：

| 行为 | 说明 |
|---|---|
| 识别冲突 | 明确指出「任务与限制冲突」 |
| 拒绝猜测 | 没有编数字 |
| **拒绝绕过** | 主动声明没用 glob/pwsh 间接访问 |

**第三条最有价值**——它自己想到了「可能有绕过方式」并明确排除了。

#### 对照组：解除限制后正常完成

同一成员，解除限制后：

> src/app/api 下（含子目录）共 **103 个 .ts 文件**。
> 构成：100 个 `route.ts` + 3 个共享库文件。

**我独立核实：103 个，100 route.ts + 3 共享库，全部正确。**

### 结论

| 问题 | 答案 |
|---|---|
| prompt 声明边界有效吗 | ✅ **有效** |
| 模型会绕过吗 | ❌ **不会**（至少这个模型不会） |
| B 类题能成立吗 | ✅ **能** |

**这意味着 v2 的 B 类题设计可行**——不需要容器隔离，prompt 约束就够了。

### 但要注意的三点

| # | 注意 | 说明 |
|---|---|---|
| 1 | **只测了一个模型** | deepseek-v4.1-flash-fastest。换模型可能不同 |
| 2 | **只测了一次** | 不能排除偶然 |
| 3 | **冲突是显式的** | 我们明确说「任务与限制冲突」，如果任务更隐蔽可能不会触发 |

**建议**：B 类题的任务描述要**保持这种显式冲突**——
直接把「你需要 api 的数据，但你只能读 components」写明，让它必须找同伴要。

**这反而是个好设计**：**显式冲突会驱动信息交换**，正好是 B 类题要测的。

## 十一、执行规范（C1 实跑后补充）

首轮跑 C1 时暴露了三个执行层面的问题，**不是题目设计问题，是跑法问题**。
写成规范，避免重复踩。

### 12.1 题面必须写全路径

**问题**：C1 我发给 agent1 的任务只说「统计 src 下的数量」，
agent1 转述给 agent2 时变成了 `ts=197，tsx=130`，**丢了目录范围**。
agent2 因此拒绝执行，要求澄清。

**规范**：

| 要求 | 做法 |
|---|---|
| 用绝对路径 | 写 `D:\...\src` 而不是「src」 |
| **要求传递时保留上下文** | 在 agent1 的任务里写明「发消息时必须带上路径」 |
| 断言里写清口径 | 如「占比 = tsx/(ts+tsx)」，不要只写「占比」 |

### 12.2 必须用真实任务依赖，不手工串

**问题**：C1 的三步是我「等前一步完成再发下一步」手工触发的，
任务板上三个任务同时是 `in_progress`，没有依赖关系。

**这导致两个后果**：

1. 测不到插件的调度能力（只测了消息传递）
2. 任务板状态与实际进度不符，无法作为评测依据

**规范**：串行型题必须用 `blocked_by` 建依赖：

```
task1 = create_task({ ..., blocked_by: [] })
task2 = create_task({ ..., blocked_by: [task1.id] })
task3 = create_task({ ..., blocked_by: [task2.id] })
```

**官方插件实测会拒绝提前指派被阻塞的任务**（见 B 组记录），所以这也能顺带验证依赖机制。

### 12.3 agent 必须回报任务状态

**问题**：C1 三个 agent 都完成了工作，但任务板上 task-22/23/24 全是 `in_progress`。
它们用 send_message 汇报了，但**没更新任务板**。

**规范**：派任务时明确要求：

> 完成后请用 team_task_update 把任务标记为 completed。

**为什么重要**：任务板状态是自动化判分的数据源之一。
如果 agent 只发消息不标状态，评测脚本就拿不到「任务何时完成」。

## 十二、改进后的执行模板

以后每道题按下述流程跑：

```
1. 建任务链（用 blocked_by 真实依赖）
2. 指派给各 agent（官方会拒绝提前指派被阻塞的）
3. 通知第一个 agent 开工
4. 观察任务板状态流转（这是自动判分的数据源）
5. 全部完成 → 采集会话数据 → 核对硬断言
```

**每步都要检查**：

| 检查项 | 通过标准 |
|---|---|
| 任务状态流转 | 严格按依赖顺序，不越级 |
| 消息内容 | 带完整上下文（路径、口径） |
| 最终断言 | 与地面真值一致 |

## 十三、D 类判据补强：推断越界检查（D1 实测后）

### 14.1 D1 暴露的缺陷

原设计的两条判据：

| 判据 | 实测 |
|---|---|
| 行号真实率 | ✅ 100%，全部可核 |
| 质疑依据完整率 | ✅ 100% |

**但两条都通过了，结论里仍有问题。**

D1 过程中出现三次「越界推理」，特征完全一致：

| # | 案例 | 行号对吗 | 结论有问题吗 |
|---|---|---|---|
| 1 | 「可能已在积累脏数据」 | 引用正确 | ❌ 无证据支撑 |
| 2 | 「改 asserts 会破坏 53 处」 | 数字接近（实为 51） | ❌ 夸大了影响面 |
| 3 | 「属疏忽而非不知情」 | 引用正确 | ❌ 补了没证据的动机 |

**共性：引用的部分都是真的，但结论超出了引用能支撑的范围。**

### 14.2 新增判据三：推断越界检查

**定义**：凡出现推论词（因此 / 所以 / 说明 / 证明 / 可见 / 这表明），
检查该推论是否超出了所引证据的范围。

**三级判定**：

| 级别 | 标准 | 例子 |
|---|---|---|
| **合规** | 结论完全由所引证据支撑 | 「264 行确实刷新了 created_at」 |
| **弱越界** | 结论方向对，但范围/程度夸大 | 「会破坏 53 处」（实为 16 处受影响） |
| **强越界** | 结论引入了证据完全没覆盖的维度 | 「属疏忽而非不知情」（动机无证据） |

### 14.3 怎么机械判定（退而求其次）

**完全自动判定很难**（需要理解语义），先做两级：

**第一级：推论词密度（可自动）**

```
推论词密度 = 含推论词的句子数 / 总句子数
警戒线：> 30% 需人工复核
```

**第二级：证据-结论对齐检查（半自动）**

对每个推论句，检查：

| 检查项 | 怎么判 |
|---|---|
| 是否附了引用 | 同句或前句有「第 N 行 / 文件:行号」 |
| 引用是否真实 | 可脚本核对 |
| **结论是否超出引用** | ⚠️ 仍需人判，但可以**抽出候选供人工复核** |

**设计取舍**：不追求全自动，而是**把可疑句抽出来给人看**。
这比假装能自动判定更诚实。

### 14.4 对 D 类题的派任务要求

在 D1/D2/D3 的任务描述里加上：

> 凡是做出推论（用「因此/所以/说明」等词），
> 请指明该推论依据的是哪一处证据；
> **如果证据只能支持部分结论，请只写能支持的那部分。**

**这条本身就能减少越界**——D1 里双方都是在被点破后才意识到的。

### 13.5 新增判据四：裁判纠错检查（D3 实测后）

**D3 发现的问题**：原设计只要求裁决「覆盖所有质疑点」，
但**全盘接收和逐条反驳给的是同样的覆盖分**。

**实测发现**：D3 的裁决方收了 8 条、驳了 1 条（P1），
而这条驳回恰恰是最有价值的——它纠正了评审方的过度断言。

**新判据**：

| 检查项 | 判定 |
|---|---|
| 是否覆盖全部质疑点 | 机械（集合相等） |
| 驳回的理由是否引用证据 | 半机械（可查行号） |
| **是否有实质纠正** | 人判——看驳回是否改变了原结论 |

**警戒线**：

> 如果裁决**全盘接收、一条不驳**，要警惕是走过场；
> 如果全部驳回，要警惕是唱反调。
> **健康的裁决应该有选择的接受与拒绝。**

D3 实测：9 条收 8 驳 1，属于健康比例。

**这条判据的价值**：它能区分「真裁决」与「盖章」。

## 十四、9 题实测后的设计修正

### 15.1 新增字段：machineType（机械 / 判断）

实测发现 12 题本质是两类：

| 类型 | 特征 | 题数 | 适合测什么 |
|---|---|---|---|
| **mechanical** | 有唯一正确答案，一次能做完 | **8** | 基础能力（会不会算错） |
| **judgment** | 需要论证，天然多轮 | **4** | 协作深度（能不能互相纠正） |

**分布**：

| 题 | shape | machineType |
|---|---|---|
| A1/A2 | solo | mechanical |
| A3 | solo | judgment |
| B1/B2/B3 | complementary | mechanical |
| C1/C2 | serial | mechanical |
| C3 | serial | judgment |
| D1/D3 | adversarial | judgment |
| D2 | adversarial | mechanical |

**为什么必须标注**：两类**不能用同一套判据**。
机械题看「对不对」，判断题看「论证站不站得住」。

### 15.2 A 类改写：从「独立小题」改为「单干对照组」

**原设计的问题**：A1/A2/A3 是三道独立小题，和 B/C/D 的任务完全不同。
拿它们对比，得出的是「任务难度差异」，不是「协作价值」。

**改法**：A 类直接复用 B/C/D 的题目，只让单个 agent 做。

| 新 A 题 | 对比 | 类型 | 意义 |
|---|---|---|---|
| **A1** | B1 | mechanical | 同样的活，一个人干 vs 两个人干 |
| **A2** | B2 | mechanical | 同上 |
| **A3** | C3 | **judgment** | **单干能不能发现自己提议的问题** |

**预期结果三种都有信息量**：

| 结果 | 说明 |
|---|---|
| 单干全对且成本更低 | **协作没有价值**，题库该重做 |
| 机械题单干对、判断题单干错 | **协作价值在判断题** |
| 单干全错 | 协作确实必要 |

### 15.3 新增观测项（不是评分项）

判据测不出质量，那就**记录可量化的过程指标**：

| 指标 | 怎么取 | 意义 |
|---|---|---|
| **有效发现数** | 过程中发现的真问题数（人核对） | D1 有 3 个，D2 有 0 个 |
| **收敛轮次** | 消息往返次数 | D1/C3 各 5 轮，其余 1 轮 |
| **纠错次数** | 双方互相纠正的次数 | D1 有 5 次 |

**关键**：这些**不进评分，只进报告**——让读者自己判断。
这样既不违反「不引入主观评分」的原则，又能呈现质量差异。

### 15.4 已确认的问题：区分度不足

**数据**：10 次实跑里 9 次最终正确（90%）。

**这意味着**：拿这套题比两个插件，大概率都是 90% 正确，**分不出高下**。

**根因**：大部分题是「数一数/比一比」，模型基本功足够好。

**未解决**——这需要提高题目难度：

| 现在 | 应改成 |
|---|---|
| B1 数「哪些模块只被 1 个测试覆盖」 | 找「有测试但测试是假的」的模块（要读测试内容） |
| B2 数「迁移建了几张表」 | 找「建了但从未被使用的表」 |
| D2 算「平均行数」 | 找「超过平均 2 倍」的文件并判断该不该拆 |

**从「计数」升级成「判断」**，才有区分度。
**这是 v3 要做的事，v2 先记录为已知局限。**

## 十五、不适用条件

- 不替代 v1：v1 的 8 道题**仍可作为冒烟测试**（采集链路验证）
- 不测「协作拓扑」（star/chain/tree/graph）——那是 MARBLE 的维度，我们没有这个能力
- 不做竞争性任务的博弈论分析——超出评测范围
- 12 题只是起步，**不足以做统计显著性检验**，只能看趋势
