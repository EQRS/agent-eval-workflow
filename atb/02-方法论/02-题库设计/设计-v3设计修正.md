# 设计 · v3 修正（M-1 实测后）

> 日期：2026-11-16
> 依据：M-1 安全审计实测（协作胜出，但暴露四个设计问题）

---


M-1 证明了大任务方向对，但暴露**四个设计问题**。逐条修正。

## 一、四个设计问题与修正

### 1.1 问题一：单干漏掉有运气成分

**现象**：S 组审了 100 个，12 步，恰好那 1 个问题路由没细看。

**为什么是问题**：如果它恰好看了那个，结论就反了。
**这不是「必然漏」，是「可能漏」**——用它证明协作价值，说服力不够。

**修正**：让「漏」成为**结构性必然**，而不是概率事件。

| 现在 | 改成 |
|---|---|
| 100 个路由，单干可能看不完 | **任务量超出单 agent 上下文预算**，物理上看不完 |

**具体做法**：

| 手段 | 说明 |
|---|---|
| **扩大材料量** | 从 100 个文件扩到 300-500 个（如全仓审计） |
| **提高单份材料密度** | 每个文件要求逐行核对，不是扫一眼 |
| **明确预算** | 告诉 agent「你只有 N 步」，逼它取舍 |

**判据变成**：

> 不是「有没有漏」，而是「**在给定预算下，能覆盖多少**」。
> 覆盖率的差异是结构性的，不是运气。

### 1.2 问题二：没验证「深读导致发现」这个机制

**现象**：agent1（28 步）发现漏洞，agent3（10 步）没发现。
**但这可能只是「谁分到了问题路由」**，不是「读得深」。

**修正**：**控制变量**——让对照组审**同一批路由**。

| 组 | 范围 | 预算 |
|---|---|---|
| **S 组** | admin 30 个 | N 步 |
| **T 组** | **也是 admin 30 个**，但分给 3 个 agent | **每人也 N/3 步** |

**这样对比的才是「同样的活，一个人干 vs 三个人干」。**

**代价**：失去「覆盖不同范围」的对比，但换来**机制可验证**。

**建议**：**两种都做**——

| 类型 | 测什么 |
|---|---|
| **同范围对比** | 深度差异（控制变量） |
| **不同范围对比** | 覆盖差异（真实场景） |

### 1.3 问题三：判据缺「审计深度」维度

**现象**：两组都自称「100/100 覆盖」，但 agent3 **10 步看 56 个文件**
（平均每步 5.6 个），这不叫深度审计。

**为什么是问题**：「审了多少个」是**廉价指标**——扫一眼文件名也算「审了」。

**修正**：加**深度指标**。

| 指标 | 定义 | 怎么取 |
|---|---|---|
| **覆盖率**（已有） | 审了几个 / 总数 | 声明即可，**但不可信** |
| **每文件步数** | 步数 / 审的文件数 | 从 --split 的步数算 |
| **引用密度** | 报告里引用了多少处「文件:行号」 | 正则统计 |
| **核实深度** | 是否追到 service 层 | 人工抽查 |

**新的判据组合**：

```
审计质量 = 覆盖率 × 深度
深度 = min(每文件步数 / 5, 1)     // 每文件至少 5 步才算深度审计
```

**用 M-1 的数据验算**：

| agent | 文件数 | 步数 | 每文件步数 | 深度分 |
|---|---|---|---|---|
| S 组 | 100 | 12 | 0.12 | **0.02** |
| agent1 | 30 | 28 | 0.93 | **0.19** |
| agent2 | 14 | 19 | 1.36 | **0.27** |
| agent3 | 56 | 10 | 0.18 | **0.04** |

**这个指标把「读得浅」量化出来了**——S 组和 agent3 的深度分都很低。

**但也要注意**：agent1 深度分只有 0.19，却发现了漏洞。
说明**深度不是唯一因素**，还有「对比意识」（它注意到同目录其他 29 个都 import 了）。

**建议再加一条**：

> **对照检查**——报告里有没有「与同类对比」的表述（如「同目录其他 N 个都 X，唯独这个没有」）。
> 有则记 1 分，这是发现异常的关键手段。

### 1.4 问题四：成本对比不完全公平

**现象**：S 组 12 步，T 组三个 agent 共 57 步。
但 T 组每个 agent 都要**重新建立上下文**（读任务、理解规范、定策略）。

**这不完全是浪费**——是协作的**固有成本**。

**修正**：**把成本拆成两部分**。

| 成本类型 | 定义 | 谁有 |
|---|---|---|
| **准备成本** | 每个 agent 建立上下文（前几轮） | T 组 × 3 |
| **执行成本** | 实际审计的轮次 | 两组都有 |

**用 --split 可以区分**：看看每个 agent 的前 1-2 轮是不是「准备」。

**M-1 的数据**：

| agent | 总步数 | 估准备步数 | 执行步数 |
|---|---|---|---|
| agent1 | 28 | ~4 | ~24 |
| agent2 | 19 | ~4 | ~15 |
| agent3 | 10 | ~4 | ~6 |

**扣除准备成本后**，T 组执行步数约 45 步，S 组 12 步，仍是 3.75 倍。
**结论：协作贵是真的贵，不是准备开销造成的错觉。**

**但报告里应该明确**：

> 协作成本 = N × 准备成本 + 执行成本
> 当 N（agent 数）大且任务小时，准备成本占比高；
> 当任务大时，执行成本占主导，准备成本可摊薄。

**这解释了 v2 和 v3 的差异**：

| | v2（小题） | v3（大题） |
|---|---|---|
| 准备成本占比 | 高 | 低（被摊薄） |
| 协作划算吗 | **不划算** | **划算**（若增量价值足够） |

## 二、修正后的 v3 题目模板

```
【题号】M-2 / M-3 / ...
【规模要求】
  - 材料总量：≥ 200 个文件 或 ≥ 100K token
  - 单 agent 上下文：预估装不下
  - 明确预算：告诉 agent「你最多 N 步」

【两组配置】
  S 组：1 agent，可读全部，预算 N 步
  T 组：K agent，范围可以相同（控变量）或不同（真实）

【判据】
  1 覆盖率 = 审了几个 / 总数
  2 深度分 = min(每文件步数 / 5, 1)
  3 对照检查 = 报告里有「同类对比」表述？1/0
  4 有效发现 = 经核实为真的问题数

【成本】
  准备成本 = 前 1-2 轮
  执行成本 = 其余轮次
  用 --split 取数
```

## 三、已确认的决策

| # | 决策 |
|---|---|
| X1 | v3 题目材料量要**超出单 agent 上下文预算**，让「漏」成为结构性必然 |
| X2 | 每道题**两种对比都做**：同范围（控变量）+ 不同范围（真实场景） |
| X3 | 新增三个判据：**深度分、对照检查、有效发现** |
| X4 | 成本拆成**准备成本 + 执行成本**，说明协作贵在哪 |
| X5 | 报告里明确：v2 小题不划算是因为准备成本摊不薄 |
