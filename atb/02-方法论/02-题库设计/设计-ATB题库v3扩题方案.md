# 设计 · ATB v3 扩题方案

> 日期：2026-11-16
> 依据：v2 的 12 题全部跑完 + A 类单干对照
> 核心结论：**当前题目规模太小，测不出协作价值**

---

## 一、为什么必须扩题

### 1.1 实测数据

| 观察 | 数据 |
|---|---|
| 12 题任务描述长度 | **68-297 字**，平均约 140 字 |
| agent 数 | 1-3 个 |
| 单题耗时 | 十秒到一分钟 |
| **单干 vs 协作** | **单干不输甚至更好**（A2 更准、A3 更快） |

### 1.2 根本原因

> **小任务不需要协作。**
> 一个 agent 十秒能做完的活，分给两个人反而多了一次合并环节，而合并会出错。

**证据**：B1 协作组有 31.8% 的信息失真，全部来自「合并」这一步。
单干没有合并环节，所以不会在合并上出错。

### 1.3 那什么任务需要协作？

三个条件，**满足其一即可**：

| 条件 | 含义 |
|---|---|
| **单 agent 装不下** | 任务量超过一个上下文窗口，必须分 |
| **必须并行** | 有明确的时间约束，串行做不完 |
| **需要多视角** | 单一视角必然有盲区，需要对抗性审查 |

**v2 的 12 题三个条件都不满足。**

---

## 二、扩题的四个方向

### 方向 1：**把题做大**（最优先）

**做法**：把任务量从「一个目录」扩到「整个子系统」。

| v2（小） | **v3（大）** |
|---|---|
| 统计 src 下 4 种扩展名 | **给整个 src 写一份架构地图，标出每个模块的职责与依赖** |
| 找出只被 1 个测试覆盖的模块 | **审计全部 91 个测试文件，找出「假测试」（有断言但不验证行为）** |
| 数迁移建了几张表 | **审计 41 个迁移，找出所有 schema 漂移（文档与实际不符）** |

**规模判据**：

| 指标 | v2 | v3 目标 |
|---|---|---|
| 需读文件数 | 2-20 | **50-200** |
| 预估上下文 | <10K token | **>100K token** |
| 预估耗时 | <1 分钟 | **10-30 分钟** |

**这样单 agent 才会真的装不下。**

### 方向 2：**加时间约束**（测并行）

**做法**：明确要求「N 分钟内完成」，只有并行才做得到。

| 题 | 设计 |
|---|---|
| **P-1** | 审计 5 个子系统，**要求 15 分钟内完成**。串行做需要 40 分钟 |
| **P-2** | 对 3 个模块做独立审查，**要求同时开始**（用任务时间戳验证） |

**判据**：看「并发峰数」和「墙钟耗时」，而不是看答案对不对。

### 方向 3：**多视角强制**（测对抗的价值）

**做法**：设计「单一视角必然有盲区」的任务。

| 题 | 设计 | 为什么单干会漏 |
|---|---|---|
| **M-1** | 安全审计：找出 API 路由里所有的权限漏洞 | **写代码的人不会想到自己的漏洞** |
| **M-2** | 文档一致性审计：找出所有「文档说的和代码做的不一致」 | 需要同时持有两套心智模型 |
| **M-3** | 迁移风险评审：每个迁移有什么回滚风险 | 需要从「运维视角」看，与「开发视角」冲突 |

**这类题的关键**：**单干时 agent 的能力是有上限的**，不是时间不够，是**视角不够**。

### 方向 4：**长链路**（测上下文管理）

**做法**：任务需要多轮迭代，中间产出必须被后续环节消费。

| 题 | 设计 | 测什么 |
|---|---|---|
| **L-1** | 分析需求 → 设计方案 → 实现 → 测试 → 审查，五步 | 长链路的信息保持 |
| **L-2** | 重构一个模块，改 5 个文件，每改一个都要跑测试 | 跨文件的依赖管理 |

**判据**：**中间产物是否被后续真实使用**，而不只是「步骤都做了」。

## 三、v3 题库结构建议

### 3.1 保留 v2 的一部分作为「基线题」

**v2 的 12 题不要全扔**——它们是很好的**冒烟测试**：

| 用途 | 保留哪些 |
|---|---|
| 冒烟（验证采集链路） | B1、C1、D2 |
| 基础能力基线 | B2、B3 |
| 机械 vs 判断对照 | D1 |

**剩下的可以作为「已知答案的回归测试」。**

### 3.2 v3 新增题的结构

| 方向 | 题数 | 每题 agent 数 | 预估成本 |
|---|---|---|---|
| **方向1 做大** | 4 | 2-3 | 每题 100-200 万 |
| **方向2 时间约束** | 2 | 3-5 | 每题 200-300 万 |
| **方向3 多视角** | 3 | 3 | 每题 100-150 万 |
| **方向4 长链路** | 2 | 3-5 | 每题 300-500 万 |
| **合计** | **11** | | **约 3000-5000 万 token** |

**这个成本是 v2 的 5-10 倍**，但：

| 对比 | 结论 |
|---|---|
| v2 花 2000 万得出结论「单干更好」 | **这个结论是错的**（题目太小） |
| v3 花 5000 万能得出结论「什么情况下协作更好」 | **这个结论有价值** |

## 四、判据也要跟着改

### 4.1 v2 判据的局限

v2 的判据都是「**最终答案对不对**」：

| 判据 | 问题 |
|---|---|
| 数字一致 | 单干和协作都对时，分不出高下 |
| 行号真实率 | 单干也能做到 100% |
| 覆盖度 | 单干自己覆盖也能达标 |

**结论：v2 的判据测不出「协作的增量价值」。**

### 4.2 v3 需要的判据

| 新判据 | 测什么 | 怎么取 |
|---|---|---|
| **单干可行性** | 这个任务单 agent 能不能做完 | 跑 A 类，看是否超时/超上下文 |
| **并行收益** | 协作比单干快多少 | 墙钟耗时对比 |
| **覆盖增量** | 协作发现了多少单干漏掉的 | 对比两组的发现清单 |
| **盲区消除率** | 对抗组发现了多少非对抗组漏掉的 | 对比两组产出 |

**核心变化**：从「答案对不对」变成「**协作带来了什么额外价值**」。

### 4.3 一个关键的对照设计

**每道 v3 题都要跑两组**：

| 组 | 配置 |
|---|---|
| **S 组（单干）** | 1 个 agent，能读全部材料 |
| **T 组（协作）** | 2-3 个 agent，按题目设计分工 |

**判据**：

```
协作增量 = T组发现数 - S组发现数
成本增量 = T组成本 - S组成本
协作净值 = 增量价值 / 成本增量
```

**这个比值才是「该不该组队」的直接答案。**

## 五、实施顺序建议

### 5.1 三阶段

| 阶段 | 内容 | 目的 | 成本 |
|---|---|---|---|
| **阶段 1** | 先做 **方向 3（多视角）** 的 3 题 | 最容易验证「协作有独特价值」 | 约 400 万 |
| **阶段 2** | 再做 **方向 1（做大）** 的 4 题 | 验证「单 agent 装不下」 | 约 600 万 |
| **阶段 3** | 最后做 **方向 2/4** | 补并行与长链路 | 约 1500 万 |

**为什么先做方向 3**：

| 理由 | 说明 |
|---|---|
| 成本最低 | 每题 100-150 万 |
| **最容易出差异** | 多视角是协作的独特优势，单干理论上做不到 |
| 判据明确 | 看「有没有发现对方漏掉的」 |

**如果方向 3 都测不出差异，说明协作真的没什么用。**

### 5.2 第一道题的建议

**M-1 安全审计**：

| 项 | 内容 |
|---|---|
| 任务 | 审计 src/app/api 下所有 100 个路由，找出权限校验缺失的地方 |
| S 组 | 1 个 agent 全做 |
| T 组 | agent1 审 admin 路由（30 个）、agent2 审 me 路由（14 个）、agent3 审其余 |
| 判据 | 找出的漏洞数 + 每个漏洞能否验证 |
| 关键 | **单干时 agent 会因为「太多了」而抽样**，协作时可以全覆盖 |

## 六、v3 与 v2 的关系

| 项 | v2 | v3 |
|---|---|---|
| 题目规模 | 小（68-297 字） | **大（需要读 50-200 文件）** |
| agent 数 | 1-3 | **2-5** |
| 判据 | 答案对不对 | **协作带来什么增量** |
| 是否跑对照组 | A 类 3 题（后补） | **每题都跑 S/T 两组** |
| 结论 | 单干不输 | **待验证** |

**v2 不是做错了，是规模不够。**

它验证了这些**基础设施**是好的：

| 项 | v2 验证结果 | v3 可复用 |
|---|---|---|
| boundary 约束 | ✅ 有效 | ✅ |
| blocked_by 依赖 | ✅ 有效 | ✅ |
| 采集脚本 | ✅ 可用 | ✅ 需加「按任务切分」 |
| 判据框架 | ✅ 可机械判定 | ⚠️ 需扩展 |

## 七、必须先解决的两个技术问题

### 7.1 成本无法按任务切分（A 类实测发现）

**问题**：`collect.mjs` 只能统计整个会话的累计成本。
而复用同一个 agent 跑多题时，**无法知道每题花了多少**。

**证据**：A1 跑完采集到 1437 万 token，但那是该 agent 会话的全部累计，不是 A1 的。

**影响**：**v3 的「成本增量」判据无法计算**。

**解决方向**：

| 方案 | 做法 |
|---|---|
| A | 每题开一个新 agent（不复用） |
| B | 采集时按时间戳切分（记录任务开始/结束时间） |
| C | 用「消息数」代替「token」做相对比较 |

**建议 A + B 组合**：v3 每题用新 agent，同时记录时间戳以便切分。

### 7.2 大任务的超时风险

**问题**：v3 的题预期 10-30 分钟，而 v2 实测最长的题（C3/D1）约 5 分钟。

**风险**：

| 风险 | 表现 |
|---|---|
| agent 超时 | 任务卡住不返回 |
| 上下文溢出 | agent 报错或开始遗忘 |

**解决方向**：先跑一道 M-1 试水，看会不会撞上限。

---

## 八、一句话总结

> **v2 证明了「小任务不需要协作」，v3 要证明的是「什么任务需要协作」。**
> 扩题的方向不是「加更多题」，而是「加更难的题」——
> **难到单 agent 装不下、看不全、想不周到。**
