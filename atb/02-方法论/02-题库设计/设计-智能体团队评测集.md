> 全称：Agent Team Benchmark
> 对象：DSH 生态下的智能体团队插件
> 模型：固定 DeepSeek（DS）系列
> 版本：v2（补充数据采集与内外调研）

## 一、核心定位：测机制，不测模型

使用者提出的关键疑虑：**「我们设计的维度，真的在测插件而不是模型吗？」**

自查结论：**原设计六维中三个测的是混合体**。现按此重构。

### 定位原则

> 插件依赖模型运行。**对模型能力的利用率，本身就是插件的能力。**
> 所以不追求「纯插件」——那不可能。而是**把两部分拆开呈现**。

### 拆分方法：用 token 结构分离

| token 类别 | 归属 | 说明 |
|---|---|---|
| `system` + `tools` | **插件开销** | 插件注册了多少工具、注入多少系统提示 |
| `inject` | **插件开销** | 记忆、上下文管理注入的内容 |
| `tool` | **插件开销** | 调度往返产生的工具结果 |
| `assistantCallTokens` | **模型开销** | 模型的推理成本 |
| `assistantAnswerTokens` | **模型开销** | 模型的输出成本 |

**每个成本类指标都拆成两行**：插件部分 / 模型部分。
读者能直接看出「这个团队贵，是贵在机制臃肿还是模型啰嗦」。

## 二、外部调研：我们不是从零开始

使用者要求「大范围搜索，避免闭门造车」。已做的调研：

| 来源 | 关键发现 | 对我们的影响 |
|---|---|---|
| **MultiAgentBench**（ACL 2025） | 用**里程碑式 KPI**衡量协作，不只看完成度 | 印证「测协作过程」的方向 |
| **MASEV**（Zenodo 19756291） | 四个正交维度；提出 **Coordination Entropy** 与 **Message Utility Ratio** | **直接借鉴两个新指标** |
| **MASEval** | 把整个 agent 系统作为分析单元 | 印证「测系统而非模型」 |
| **Collab-Overcooked** | 专门评测合作行为 | 印证 D5 抗干扰方向 |

**结论**：业界主流已从「任务完成度」转向「协作过程质量」，与本设计方向一致。

### 借鉴的两个新指标

| 指标 | 定义 | 用在哪个维度 |
|---|---|---|
| **Message Utility Ratio** | 发出的消息中，被下游真正用上的比例 | D4 通信质量 |
| **Coordination Entropy** | 协调的有序程度（越有序越低） | D2 调度效率 |

**为什么值得借鉴**：这两个指标测的是「协作是否有效」，而不是「有没有发消息」——
能抓出「表面热闹、实际无效」的团队。

## 三、数据采集：从哪拿、拿什么

使用者裁定：**用 dsh-context 的缓存**。已实查确认其字段完整。

### 3.1 数据源

```
~/.dsh/storages/dsh-context/overview-cache.v1.json
```

**已实测的结构**（取自一个真实会话）：

```json
{ "session": {
    "id": "session-...", "cwd": "...", "blank": false,
    "timeline": {
      "current": {
        "system": 32210, "tools": 628, "user": 6418,
        "inject": 70726, "skill": 1009,
        "assistant": 442677, "tool": 214699, "total": 768367,
        "assistantReasoning": 0, "assistantAnswerTokens": 68750,
        "assistantCallTokens": 369099
      },
      "total": {...}, "turns": 167, "steps": 1207
    },
    "activity": {
      "2026-11-10": {
        "tokens": 82582983, "requests": 399, "turns": 24,
        "toolCalls": 602, "toolsMs": 6222345, "wallMs": 8886458,
        "tools": { "run_code": {"n":375}, "read": {"n":146} }
      }
    }
} }
```

### 3.2 可采集字段清单

| 字段 | 含义 | 用途 |
|---|---|---|
| `timeline.current.*` | 当前上下文各类 token | 拆插件/模型开销 |
| `timeline.total` | 累计 token | 总量统计 |
| `timeline.turns` | 用户轮次 | 效率基准 |
| `timeline.steps` | agent 步数 | **每轮步数 = 规划效率** |
| `activity.*.toolCalls` | 工具调用次数 | 调度活跃度 |
| `activity.*.toolsMs` | 工具耗时 | **等工具时间** |
| `activity.*.wallMs` | 墙钟时间 | **真实耗时** |
| `activity.*.tools` | 逐工具调用次数 | 工具使用分布 |
| `activity.*.cost` | 分模型计价 | 成本核算 |

### 3.3 关键派生指标

```
思考占比 = (wallMs - toolsMs) / wallMs
  → 越高说明时间花在模型思考，越低说明花在等工具
  → 插件调度慢会让 toolsMs 占比升高

每步 token = total / steps
  → 单步成本，反映上下文管理的经济性

工具调用密度 = toolCalls / turns
  → 每轮用了几次工具，反映机制是否啰嗦
```

### 3.4 采集边界（必须说明）

| 限制 | 说明 |
|---|---|
| **依赖 dsh-context 插件** | 没装就采不到，需在评测环境强制安装 |
| **缓存非实时** | `overview-cache` 是快照，需在任务结束后等待刷新 |
| **只有聚合值** | 拿不到逐条消息的内容，只能拿统计量 |
| **activity 按天聚合** | 跨天任务会被拆分，需按会话 id 汇总 |

> **待验证**：`timeline.current` 是「当前上下文占用」还是「累计消耗」？
> 从 `total: 768367` 且 `turns: 167` 看，更像累计。实施时需用一次短会话实测确认。

## 四、六个维度（v2 重构版）

每个维度标注 **【插件】** 或 **【模型】**，表示该指标主要在测谁。

### D1 计划结构质量 【插件+模型】

**不测**「拆得好不好」（纯模型能力），**测**「拆出来的结构是否可被执行」。

| 指标 | 定义 | 来源 |
|---|---|---|
| **结构合法率** | 无依赖环、无孤立任务、无自依赖的计划占比 | 任务 DAG 结构分析 |
| **粒度可控性** | 子任务能否被独立认领的比例 | 任务创建记录 |
| **步数效率** | `steps / turns`，越低说明规划越紧凑 | `timeline` |

### D2 调度效率 【插件】

| 指标 | 定义 | 来源 |
|---|---|---|
| **有效并行率** | 同时在跑的成员数 > 1 的时间占比 | 时间戳分析 |
| **重复劳动次数** | 两成员做同一件事的次数 | 任务内容比对 |
| **Coordination Entropy** | 协调有序度（借鉴 MASEV），越低越有序 | 状态转换序列 |

### D3 依赖正确性 【插件】

| 指标 | 定义 | 来源 |
|---|---|---|
| **顺序违规次数** | 依赖未完成就开工的次数 | 任务状态时序（**必须为 0**） |
| **依赖链完整率** | 完整走完的链 / 总链数 | 任务状态 |

### D4 通信质量 【插件】

**数据源已实测确认**：消息不走 `tool/call`，而是直接写进：

```
.agent-teams/<team>/inbox/<收件人>.jsonl
```

每条消息的字段：`id / from / to / content / ts / sourceTaskId / sourceAttemptId / deliveredAt / readAt`。

| 指标 | 定义 | 数据字段 |
|---|---|---|
| **送达率** | 消息中 `deliveredAt` 非空的比例 | `deliveredAt` |
| **已读率** | 消息中 `readAt` 非空的比例 | `readAt` |
| **平均送达延迟** | `deliveredAt - ts` 的均值 | `deliveredAt`, `ts` |
| **任务绑定率** | 带 `sourceTaskId` 的消息比例（能核验内容与任务对应） | `sourceTaskId` |

> **实测样例**（P5）：2 条消息，送达率 100%、已读率 100%、平均延迟 8ms。


### D5 抗干扰 【拆开】

原设计混了两件事，现在拆开：

| 指标 | 归属 | 说明 |
|---|---|---|
| **纠偏成功率** | 【插件】 | 干扰后任务是否被重新拉回正轨 |
| **自愈时间** | 【插件】 | 从被干扰到恢复的耗时 |
| **误信率** | 【模型】 | 接受错误前提的次数占比 |

### D6 成本效率 【拆分呈现】

| 指标 | 归属 | 定义 |
|---|---|---|
| **插件开销占比** | 【插件】 | `(system+tools+inject+tool) / total` |
| **模型开销占比** | 【模型】 | `(assistantCall+assistantAnswer) / total` |
| **每步 token** | 综合 | `total / steps` |
| **思考占比** | 【插件】 | `(wallMs - toolsMs) / wallMs`，越高说明调度越不拖后腿 |

## 六、仍需补的数据（设计缺口）

实查发现，只靠 `dsh-context` 缓存**不够**。以下数据缺口需另找来源：

| 缺什么 | 为什么需要 | 可能来源 |
|---|---|---|
| **任务级状态序列** | 算顺序违规、依赖链完整率 | agent-teams 的团队状态 API |
| **消息内容** | 算 Message Utility Ratio | 团队邮箱 / 会话记录 |
| **成员并发时间线** | 算有效并行率 | 成员状态时间戳 |

**结论**：`dsh-context` 缓存解决 **D1（部分）与 D6**；**D2/D3/D4/D5 需要从团队插件自身的状态接口取**。

> 这也是为什么评测集要「适配层」——不同插件的状态接口不同，需要统一抽象。

### 适配层设计（草案）

```
interface TeamAdapter {
  getTasks(): TaskSnapshot[]        // 任务 id、状态、依赖、认领人、时间戳
  getMembers(): MemberSnapshot[]    // 成员 id、状态、活跃区间
  getMessages(): MessageRecord[]    // 发送方、接收方、时间、内容摘要
}
```

**有适配层，换一个团队插件只需实现 3 个方法**——这是「后续各种团队都能测」的关键。

## 十、实测验证结果（2026-11-15）

以下全部来自**实跑**，不是推断。

### 11.1 数据源结论：改为以会话事件流为主

原计划用 `dsh-context` 缓存，实测后**降为辅助**。

| 数据源 | 能给什么 | 实测结论 | 优先级 |
|---|---|---|---|
| **`session.v4.jsonl.zstd`** | 完整事件流（7812 条记录） | ✅ 覆盖全部六维度 | ⭐ 主 |
| **`team.json`** | 任务/成员实时状态 | ✅ 格式已实测确认 | ⭐ 主（实时态） |
| **`inbox/*.jsonl`** | **成员间消息（D4 的精确来源）** | ✅ 已实测确认 | ⭐ 主（通信） |
| `dsh-context` 缓存 | token 聚合 | ⚠️ **懒刷新**，任务刚结束读不到 | 辅助 |

### 11.2 两个必须记住的采集坑

#### 坑 1：多帧 zstd

```
session.v4.jsonl.zstd 实测 = 4288 个独立 zstd 帧
zlib.zstdDecompressSync(整个文件)   → 只解第一帧，拿到 1 条
按魔数 28 B5 2F FD 切帧后逐帧解压  → 拿到全部
```

**不处理的后果**：数据缺失 99.98%。

#### 坑 2：一帧多条记录

```
实测 2897 / 4288 帧含有 2-50 条 JSON（换行分隔）
按「一帧一条」解析    → 失败 2891 次，只剩 1388 条
解压后 split('\n') 逐条 parse → 7812 条，失败 0
```

**不处理的后果**：数据缺失 73%。

> 两个坑的差距：修正前 1388 条 → 修正后 7812 条，**差 5.6 倍**。

### 11.5 真实运行的首批实测数据

用采集脚本跑 2026-11-14 那次**四队友并行协作**（PR 修复 + 身份体系，共 8 成员 10 任务）：

| 指标 | 实测值 | 解读 |
|---|---|---|
| 成员数 | 8 | 两批各 4 个 |
| 任务数 | 10 | 状态全部正常流转 |
| **D3 状态转换合法率** | **100%**（16 次转换，0 非法） | 依赖机制工作正常 |
| **D2 并发峰数** | 4 | 8 个成员同时最多 4 个在跑 |
| **D2 并行率** | **8.4%** | 真正多人并行的时间只占 8.4% |
| 总时长 | 61,419,729 ms（约 17 小时） | 含人工等待 |

**并行率 8.4% 是第一个有价值的能力信号**：
派了 8 个成员，但大部分时间只有 1 个在干活。这正是评测该暴露的问题——
**名义并行 ≠ 实际并行**。

> 注：该数据含跨天人工等待，不能直接当作「调度效率低」的结论。
> 但**指标本身成立**，说明采集链路可用。规范化评测时需排除人工等待时长。

### 11.7 状态机（用于 D3 硬断言）

实测确认的合法转移表：

```js
pending     → claimed | cancelled
claimed     → in_progress | failed | cancelled
in_progress → completed | failed | cancelled
completed / failed / cancelled → （终态）
```

**D3 的判定就是机械的**：任何不在表内的转换 = 违规。没有主观空间。

| **D1 计划结构** | 10 任务，结构合法；**2 个任务无负责人** | `team/task.dependencies` | ✅ 精确 |
| **D2 调度** | 8 成员，并发峰 4，并行率 8.4% | 任务时间戳扫描线 | ✅ 精确 |
| **D3 依赖正确性** | 16 次转换，非法 0，合法率 100% | 状态转换 + 合法表 | ✅ 精确 |
| **D4 通信** | 16 条成员事件，113 条注入消息 | 注入/消息计数 | ⚠️ **代理** |

| **D6 成本** | 5.57 亿 token，**缓存命中率 93.7%** | `assistant/message.usage` | ✅ 精确 |

**6 个里 5 个精确、1 个代理。**

### 11.9 三个高信息量的实测发现

#### 发现 1：D5 的重试原因分布

```
RATE_LIMIT   40  ← 最多，占一半
SERVER       29
TRANSPORT     5
TIMEOUT       5
```

**40 次因限流重试**，直接指出运行时瓶颈在哪。这比一个「重试率 6.71%」的单数字有信息量得多。

#### 发现 2：D6 缓存命中率 93.7%

```
输入 token          34,817,616
缓存读取 token     521,325,440
缓存命中率               93.7%
```

**绝大部分 token 来自缓存**，真实成本远低于「总 token」这个数字给人的印象。
这正是本站拒绝「单一总分」的理由——一个数字会掩盖关键结构。

#### 发现 3：D1 抓出「无负责人任务」

结构上合法（无依赖环、无自依赖），但**有 2 个任务没人认领**。
这正是 D1 该抓的：不是「拆得好不好」，而是「拆出来的东西能不能被执行」。

### 11.10 D4 的已知局限（必须如实标注）

**这批数据里没有 `send_message` 工具调用记录**（那次协作没走消息通道）。

所以 D4 用「注入事件数 + 消息数」作**代理指标**，它只能反映「有多少消息往来」，
**不能反映「成员之间有没有真正通信」**。

**改进方向**：规范评测时强制要求成员用 `send_message` 汇报，D4 才有真实数据。
返回值里已带 `说明` 字段标注这一点，不让读者误以为它和别的维度一样精确。

### 11.11 意外收获：D6 不再依赖缓存

原本担心 `dsh-context` 懒刷新会导致 D6 采不到数，实测发现：

```
assistant/message 事件自带 usage 字段：
  { inputTokens, outputTokens, totalTokens, cacheReadTokens, cacheWriteTokens }
```

**直接从事件流累加即可，完全绕开缓存问题**。这是本次验证最大的意外收益。
