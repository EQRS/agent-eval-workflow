# 智能体团队测评流程 v1

> 基于 2026-11-17 NanmiCoder 16 题抽样实测总结
> **含 8 个已踩过的坑**

---

## 一、总体流程

```
1. 明确测评目标 → 2. 设计对照 → 3. 抽样选题
   ↓
4. 采集环境 → 5. 派发任务 → 6. 收集验证
   ↓
7. 六维度计算 → 8. 出报告（附环境+局限）
```

---

## 二、第 1 步：明确测评目标

**必须先回答：测什么？**

| 目标 | 需要的对照 |
|---|---|
| 「团队能不能用」 | 只需 T 组 |
| **「团队 vs 单干哪个好」** | **必须 S + T 双组** ⚠️ |
| 「团队内部协作质量」 | T 组 + 六维度 |

> **坑 1：没跑 S 组基线**
> 我一开始只跑 T 组，导致无法回答「团队 vs 单干」——**这是本次最严重的失误**

---

## 三、第 2 步：设计对照

### 标准配置

| 组 | 配置 | 数量 |
|---|---|---|
| **S 组** | 1 个 subagent | 每题 1 份 |
| **T 组** | Lead + 3 个专业角色 | 每题 3 份 |

### 3 个专业角色（已验证有效）

| 角色 | 关注点 |
|---|---|
| **安全工程师** | 鉴权/越权/敏感数据/对抗性 |
| **性能工程师** | 查询成本/锁/内存/实测 |
| **SRE（运维）** | 部署/回滚/可观测/容量 |

> **实测数据**：安全工程师产出是性能的 1.6 倍（3307 字 vs 2050 字）

---

## 四、第 3 步：抽样选题

### 四类考点必覆盖

| 类型 | 定义 | 抽样数 |
|---|---|---|
| ② 方案缺陷 | 设计有错 | ≥4 |
| ③ 无用功 | 问题已解决 | ≥3 |
| ④ 倒退 | 比现状差 | ≥3 |
| L4 系统性 | 跨模块关联 | ≥3 |

**16 题是较好的平衡点**（覆盖 + 耗时）。

> **坑 2：用 1 题代替全量**
> 我最初只测 1 题就称「完整测评」，被使用者指出

> **坑 3：抽样不按维度**
> 我第一版抽的 M10-M13 全是「② 方案缺陷」，没覆盖其他三类

---

## 五、第 4 步：采集环境（必做）

**报告必须附以下信息**：

```
| 项 | 值 |
|---|---|
| 操作系统 | |
| CPU / 内存 | |
| Node | |
| DSH 版本 | |
| 插件名+版本 | |
| 被测项目 | |
| 题库版本 | |
```

> **为什么必须**：没有环境信息的测评报告无法复现，也无法对比。

## 六、第 5 步：派发任务

### 6.1 任务绑定模型（关键认知）

> **团队插件的任务是「与 assignee 强绑定」的，不是共享池。**

| 动作 | 效果 |
|---|---|
| `create_task({assignee})` | 绑给指定成员 |
| `add_member` | **只对新任务生效，不分担既有队列** |

> **坑 4：不做负载均衡**
> 我给 3 个成员各派 3 个任务，然后加了 2 个成员——新成员 idle，旧成员积压

### 6.2 正确做法

```js
// 轮询分配，而非按题分组
members.forEach((m, i) => { /* 均分 */ });
```

### 6.3 并发上限

| 插件 | 上限 | 来源 |
|---|---|---|
| NanmiCoder | **maxMembers ?? 8** | 源码实测 |
| 官方 Agent Teams | **8（实测阻塞）** | `Team member limit 8 reached` |

**且一个会话只能有一个团队**（实测：换工作区仍报同一 team）。

---

## 七、第 6 步：收集与验证

### 7.1 绝不轻信「已完成」

> **实测发现**：有成员声称「已落盘 review-perf.md」但实际没写。

**必做**：

```js
// 逐个核对磁盘与任务
for (const topic of topics) {
  const files = await readdir(dir);
  assert(files.length === expected);
}
```

### 7.2 检查产出质量

| 检查项 | 判据 |
|---|---|
| 是否空产出 | 字数 < 500 要标记 |
| 是否真的读代码 | 有无 `文件:行号` |
| 是否瞎编 | 引用的行号是否真实存在 |

### 7.3 目录不能重复

> **坑 5：报告目录有重复副本**
> 我保存了两次，导致磁盘 60 份但任务只有 48 份

## 八、第 7 步：六维度计算

| 维度 | 数据源 | 可测性 |
|---|---|---|
| **D1 计划结构** | 任务 DAG | ✅ 可测 |
| **D2 调度效率** | 时间戳 | ⚠️ 部分 |
| **D3 依赖正确性** | 任务状态时序 | ✅ 可测 |
| **D4 通信质量** | `.agent-teams/inbox/*.jsonl` | ❌ **需验证存在** |
| **D5 抗干扰** | 注入错误前提 | ✅ **可测（需设计）** |
| **D6 成本效率** | token/字数 | ⚠️ 部分 |

### 8.1 D4 的前置验证（必做）

> **坑 6：误信文档**
> 文档说消息存 `.agent-teams/`，我直接采信，没查源码。
> 实测：插件 `lib/index.js` 中 `inbox`/`writeFile` **全 0 命中**

**验证方法**：
```js
const src = await readFile('插件目录/lib/index.js', 'utf8');
if (!/writeFile|appendFile/.test(src)) → D4 不可测
```

### 8.2 D5 的正确做法

> **坑 7：D5 用已测过的题**
> 成员做过该题 → 记得答案 → 误信率不可信

**正确设计**：

| 要点 | 说明 |
|---|---|
| **用未测过的题** | 否则有记忆污染 |
| **前提要「看起来合理」** | 来自真实历史错误最佳 |
| **两组实验** | 静默注入（测误信）+ 中途误导（测纠偏） |

## 九、第 8 步：出报告

### 报告必含章节

| # | 章节 | 为什么不能省 |
|---|---|---|
| 1 | **测评环境** | 没有它无法复现 |
| 2 | 抽样设计 | 说明为什么选这些题 |
| 3 | 六维度数据 | 每个维度给实际数字 |
| 4 | 四类考点表现 | 验证题库有效 |
| 5 | **实测证据** | 区分「推断」与「实测」 |
| 6 | 发现的插件问题 | 对被测对象的评价 |
| 7 | **局限（如实）** | 不可测的维度、污染、样本量 |
| 8 | 结论 | 一句话回答测评目标 |

### 关键：缺失项必须如实标注

> **D4 不可测 → 写「数据源不存在」，不能编造数字**
> **D5 未做 → 写「未做」，不能跳过不写**

## 十、完整踩坑清单

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| **1** | **没跑 S 组基线** | **无法回答「团队 vs 单干」** | 必须 S + T 双组 |
| 2 | 用 1 题代替全量 | 样本不足 | 至少 16 题四类覆盖 |
| 3 | 抽样不按维度 | 考点覆盖不全 | 四类各类 ≥3 题 |
| 4 | 不做负载均衡 | 成员积压/空转 | 派任务时轮询分配 |
| 5 | 报告目录重复 | 统计失真 | 保存后核对数量 |
| 6 | 误信插件文档 | 把「未实现」当「路径错」 | grep 源码验证 |
| 7 | D5 用已测题 | 记忆污染 | 用未测过的题 |
| 8 | 不测 D5 | 六维度缺一维 | 设计 4 个前提注入即可 |
| **9** | **S组与T组争抢subagent池** | **互相阻塞** | **分阶段执行** |
| **10** | **官方团队角色认领失衡** | **SRE 83% 缺口** | **检测并补跑** |
| **11** | **官方报告不进任务板** | **无法程序化收集** | **prompt 强制要求写 output** |

## 【补充】官方 Agent Teams 的 3 个新坑（2026-11-17 重测发现）

### 坑 9：subagent 池上限 18，S 组与 T 组争抢

```
subagent limit reached (active child limit: 18);
wait for an existing child to finish
```

**S 组 16 个 subagent 占满后，teammate 无法工作。**

**对策**：**分阶段执行**
1. 先跑 S 组（16 个 subagent）
2. 等 S 组完成后再跑 T 组
（或减少 S 组并发，分 2 批各 8 个）

---

### 坑 10：官方团队角色认领失衡

**官方是「成员自主认领任务板」模型，没有强制分配。**

实测：

| 角色 | 完成率 |
|---|---|
| 安全工程师 | **100%** |
| 性能工程师 | **100%** |
| **SRE（运维）** | **17%** |

**成员倾向选择自己熟悉的领域，SRE 类任务被系统性跳过。**

**对策**：
- 测评时检测某角色未完成 → 用 subagent 补跑
- 或派发时在 prompt 里明确「这是你的角色，必须认领」

**对比**：NanmiCoder 是 assignee 绑定，强制覆盖，无此问题。

---

### 坑 11：官方团队报告不进任务板

**21 个已完成任务，`team_task_list` 返回的 `output` 全部为空。**

成员把报告**发成了消息**，没有写进任务板。

| 项 | 官方 | NanmiCoder |
|---|---|---|
| 报告存放 | 消息 | `task.output` |
| 可程序化提取 | ❌ | ✅ |

**对策**：派发任务时**明确要求**「把完整报告写入 task output」，否则只能从对话消息人工提取。
