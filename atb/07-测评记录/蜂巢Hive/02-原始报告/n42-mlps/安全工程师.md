# 安全工程师评审意见：等保二级合规改造方案

**总体判断：不建议按现方案实施。** 方案新建的 `audit_log` 与本仓库已有的 `operation_records`（`migrations/0001_baseline.sql:411-433`）构成重复且**更弱**的第二套审计载体；同时方案恰好绕开了仓库里已专门修过的安全缺陷（`migrations/0042_audit_immutable.sql`）。按现方案实施后，平台会**拥有两套审计表，但只有旧的那套不可篡改**——这会让使用方对合规状态产生错误信心，比没有审计更危险。

---

## 1. 新建 `audit_log` 表，与既有 `operation_records` 重复

**问题部分**：proposal.md 第 9-18 行的建表 DDL（`CREATE TABLE audit_log ...`）。

**后果**：仓库已存在审计主表 `operation_records`，`migrations/0001_baseline.sql:411-433` 定义，并且它是**被业务逻辑实际依赖**的表，不是预留：

- `migrations/0042_audit_immutable.sql:5-7` 明确写道：`operation_records` 是“全站审计与幂等去重的唯一载体”，其 `UNIQUE(action_type, operation_key)` 被 `setUserRole`、`setUserStatus`、`configuration_revisions`、`catalog` 落库去重等多条关键路径依赖。
- 已有服务层唯一入口 `src/server/modules/operations/service.ts`（`recordOperationInTx`，同文件第 130-140 行左右），注释强调“审计必须与业务变更同事务（架构 §6.4）”。

方案新增 `audit_log` 后，实际写操作会被拆成两条互不相关的记录：业务写 `operation_records`，合规写 `audit_log`。两边**没有一致性约束**——任意一边写入失败或被绕过都不会被察觉。审计的完整性从“单表 + UNIQUE 约束 + 触发器”退化为“两套各写各的”。对等保“审计记录完整、不可抵赖”是实质性倒退。

**建议**：删除 `audit_log` 建表，复用 `operation_records`。方案应改为“补齐 `operation_records` 的覆盖缺口”，而非另起一表。若确需 IP 字段（现表确实没有），就以 `ALTER TABLE operation_records ADD COLUMN client_ip TEXT` 增量补列，而不是平行建表。

## 2. 方案新建的表**没有不可变守卫**，重蹈 0042 已修复的漏洞

**问题部分**：proposal.md 第 9-18 行的 DDL 只有 `CREATE TABLE`，无任何 `BEFORE DELETE` / `BEFORE UPDATE` 触发器。

**后果**：这是本方案最严重的问题。`migrations/0042_audit_immutable.sql:1-27` 是一次专门的安全修复，起因就是“审计表可被删除”这一漏洞，其注释（第 9-13 行）写明了攻击链：

> 删除审计行即可让已消费的 `operation_key` 重新可用，配合 `restore-backup.mjs --force` 整库覆盖，构成**不需要改代码的伪造通道**。

`0002_triggers.sql` 的 33 个触发器里，当时只有 `review_revisions` / `comment_revisions` 有 `BEFORE DELETE` 守卫。方案现在新建一张**同样无 DELETE/UPDATE 守卫**的 `audit_log`，等于给攻击者提供了一个全新的、干净的删除通道——而且因为它是“合规专用表”，运维排查时反而更不会怀疑。等保二级“审计记录应受到保护、避免未预期的删除、修改或覆盖”因此直接不满足。

**建议**：若坚持新表（不推荐），必须同步提供 `BEFORE DELETE` / `BEFORE UPDATE` 的 `RAISE(ABORT)` 触发器，照抄 0042 的写法，并在测试中用 `sqlite_master` 断言其存在（`0002_triggers.sql:6-8` 已确立这一测试纪律）。

## 3. `clientIp` 的取值未定义，直接决定 IP 字段能否作为证据

**问题部分**：proposal.md 第 24-29 行记录点代码里的 `clientIp` 变量，方案全文未说明其来源。

**后果**：这个字段是审计记录唯一的来源标识，取值方式决定它是否可信。仓库里已有实现 `src/server/platform/client-ip.mjs`，其文件头注释（第 6-9 行）点明了风险：

> 反代后面如果直接取 `x-forwarded-for`，等于让**客户端自己决定**日志里记的是谁（这个头 HTTP 上谁都能写）。

该实现的安全边界是 `DSH_REVIEW_TRUST_PROXY`（`resolveClientIp`，第 58-70 行）：未开启时只信任 TCP 对端地址。但方案对此完全无表述。若实现者图省事直接读 `x-forwarded-for`，攻击者伪造该头即可让审计日志把攻击归因到任意 IP，**“有据可查”变为“有据可伪造”**，这比不做 IP 记录更糟——它会主动误导事后追查。

**建议**：方案中明确写死“`clientIp` 必须经 `resolveClientIp()` 获取，且仅在 `DSH_REVIEW_TRUST_PROXY=1` 时读取代理头”，并注明线上部署是否开启该开关及 nginx 侧必须覆盖写入 `X-Real-IP`。

## 4. “管理员操作需要二次密码确认”无法落地

**问题部分**：proposal.md 第 33 行。

**后果**：`migrations/0001_baseline.sql:33-45` 的 `users` 表**没有密码字段**——身份全部来自 `external_identities`（provider 仅 `'github'`，第 47-62 行）。也就是说平台是纯 OAuth 登录，**本地没有可用来“二次确认”的密码**。这句话在现有数据模型下无法实现，评审无法验证，实现者会被迫临时引入密码存储，而密码存储本身是高风险面（等保二级要求口令加密存储、传输加密），方案对此零设计。

**建议**：改为符合现状的二次确认机制（例如对敏感操作要求重新走 GitHub OAuth 挑战，或要求输入 TOTP）。若确要引入密码，必须单列一节说明哈希算法（建议 Argon2id）、盐、重放与锁定策略。

## 5. “所有写操作都记一条”：颗粒度不可行，且与限流表冲突

**问题部分**：proposal.md 第 21 行“所有写操作都记一条”。

**后果**：其一，`0006_rate_limiter.sql` 说明系统存在高频写路径（`rate_limiter_flexible` 表，`points`/`expire` 每请求更新）。把“所有写操作”纳入审计会让审计表行数与限流、心跳（另有 `runtime_heartbeats`）同量级增长，与等保“审计记录保存不少于 6 个月”冲突——方案第 36 行的 6 个月保留期在无容量估算下是空话。其二，审计表若与业务同事务（这是仓库的既定纪律，`service.ts` 第 130 行左右的注释），高频路径上每条 INSERT 都会拉长持锁时间，构成拒绝服务放大面。

**建议**：明确“写操作”指**业务状态变更**，排除限流、心跳、进度上报等遥测类写入。同时给出容量估算（行/天 × 180 天）与清理机制设计。

## 6. 保留 6 个月的实现路径缺失

**问题部分**：proposal.md 第 36 行。

**后果**：方案只说“保留 6 个月”，未说谁清理、怎么清理。而 0042 已把审计表设为**不可删除**（`trg_operation_records_no_delete`，第 20-25 行 `RAISE(ABORT)`）。一旦给 `audit_log` 也加上同样守卫，常规 `DELETE` 归档将直接被触发器拒绝，6 个月后表会无限增长直至磁盘耗尽——这是一个必然发生的可用性事故。反过来若无守卫，则退回问题 2。

**建议**：显式设计归档路径（如按分区/按表切换 + 归档前落冷存储 + 归档动作本身写审计），并说明归档操作如何在不破坏不可变性的前提下执行。

## 结论与优先级

| 优先级 | 问题 | 依据 |
|---|---|---|
| **阻断** | 新表无不可变守卫，重蹈 0042 已修复漏洞 | `0042_audit_immutable.sql:1-27` |
| **阻断** | 与 `operation_records` 重复建表，破坏审计唯一性 | `0001_baseline.sql:411-433` |
| **高** | `clientIp` 来源未定义，可被伪造 | `client-ip.mjs:6-9, 58-70` |
| **高** | 二次密码确认在纯 OAuth 模型下不可实现 | `0001_baseline.sql:33-62` |
| **中** | 审计颗粒度过粗，容量与保留期矛盾 | `0006_rate_limiter.sql` |
| **中** | 6 个月清理与不可删除触发器冲突 | `0042:20-25` |

方案当前形态更像一份“从零开始的小系统”设计稿，未与本仓库既有的审计基础设施对齐。建议重写为“在 `operation_records` 上补齐 IP 字段 + 扩大覆盖点 + 定义归档策略”的增量改造。补充说明：以上仅从安全角度评审，未评估迁移编号 0043 是否与主分支冲突（目录中 0027、0035 已跳号，编号并非严格连续）。
