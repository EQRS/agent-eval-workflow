# 性能工程师评审意见：插件全文搜索方案（proposal.md）

**总体判断：不可按此方案上线。** 主要不是因为 SQL 不够快，而是因为三处设计会让「<50ms」这个指标在真实数据量下根本无法成立，且其中两处在**写入路径上无界放大**（会拖垮不相关接口）。现有代码里已经有一个成熟的、踩过坑的 FTS 实现（`src/server/modules/search/index.ts` + 迁移 0014），本方案没有复用它的任何一条结论。

---

## P1 — 查询串直接拼接进 SQL：每次请求强制全量编译 + 注入风险（阻断级）

**① 哪部分** proposal.md §3「查询接口」，`const sql = \`... MATCH '${q}'\``。

**② 后果** proposal.md §3（`SELECT plugin_id FROM plugin_search WHERE plugin_search MATCH '${q}'`）：
- **语句缓存归零**：每个不同 `q` 都是全新 SQL 文本，better-sqlite3 的 prepared statement 缓存完全失效，每次请求重走 `sqlite3_prepare_v2`（解析+字节码生成）。这是纯 CPU 开销，且随并发线性增长——恰好吃掉「<50ms」预算。
- **q 未做长度与内容约束**：超长 `q`、含 `"` `*` `(` `"` 的输入会变成非法 FTS5 语法 → 抛错（可用性），或被解析成昂贵查询（性能）。
- 顺带：这也是注入面（虽然是性能评审，但这一处同源）。

**③ 建议** 固定 SQL 文本 + 绑定参数，并对输入先规范化。项目已有正解，直接照抄 `src/server/modules/search/index.ts:65-67` 的 `toFtsPhrase()`（内部双引号转义）+ `index.ts:157` 的 `conn.prepare(...).all(toFtsPhrase(q), LIMIT)` 形态，以及 `index.ts:140` 的 `q.trim().slice(0, 100)` 长度钳制。

## P2 — 未声明 `tokenize`：中文搜索目标与默认分词器直接矛盾（阻断级）

**① 哪部分** proposal.md §1 建表语句，`fts5(plugin_id UNINDEXED, name, description)` 缺 `tokenize`；同时 §预期 写「支持中文与英文搜索」。

**② 后果** proposal.md §1（建表 SQL）与 §预期（「支持中文与英文搜索」）：
- FTS5 默认 `unicode61` 按空白/标点切词，**中文整段是一个 token**。搜「记忆」匹配不到「记忆插件」→ 功能目标本身达不成。
- 若照默认实现，索引体积/倒排项也偏大（整句长 token）。
- 这不是猜测：仓库在迁移里已经明确记录了这个坑并做了选型 —— `migrations/0014_review_search.sql:5-10`：「unicode61 按词切，中文整段算一个词，**子串搜不到**」「用 trigram 做三字滑窗索引」。

**③ 建议** 显式 `tokenize = 'trigram'`（对齐 `migrations/0014_review_search.sql:22`）。**并且必须继承该迁移第 10 行记录的边界**：trigram 对 **<3 字符**查询返回 0 条,中文两字词（"记忆""检索"）极常见，所以查询层要像 `src/server/modules/search/index.ts:157,166-166` 那样对 1–2 字查询走 `LIKE` 回退。方案里完全没提这条，等于把已知缺陷重新引入一遍。**另**：trigram 索引体积约为原文的数倍,插件 description 若较长需评估库体积(见 P5)。

## P3 — 「新增或更新时同步写入」：逐行 DELETE+INSERT，且未要求同事务（高）

**① 哪部分** proposal.md §2「索引维护」，`upsertSearchIndex()`。

**② 后果** proposal.md §2（`DELETE FROM plugin_search WHERE plugin_id = ?` 后紧跟 `INSERT`）：
- **两倍写放大 + 两次 prepare**：每个插件 2 条独立语句、2 次 FTS5 虚拟表写入。FTS5 的 DELETE 要读旧行反解 token、INSERT 要写倒排——比普通表贵得多。批量收录 30 个插件（`src/server/modules/catalog/discovery.ts:38-46` 的 `maxPlugins: 30`）= 60 次 FTS 写。
- **没有事务边界**：方案没说这个函数在哪个事务里调。项目硬约束在 `src/server/platform/tx.ts:4-9`（「跨模块流程创建一次短事务」「不得各自提交独立事务」）与 `src/server/platform/db.ts:8-9`（「业务事务保持短小」）。逐条 autocommit 意味着 **N 次 `synchronous = FULL` 的 fsync**——`src/server/platform/db.ts:53` 明确 `synchronous = FULL`。这是本轮评审里对写入路径影响最大的一条：30 个插件从 1 次 fsync 变成最多 60 次。
- 索引与业务行不同事务 → 可能「搜得到但打不开」或「已收录却搜不到」。现有实现为此专门把索引写入做成 `reindexReviewInTx` 并**导出给发布流程同事务调用**（`src/server/modules/search/index.ts:82-107`，注释在第 84-86 行）。

**③ 建议** 三点：
1. 改成 `reindexPluginInTx(conn, pluginId)` 形态，**接受注入的连接**，由调用方（收录事务，`src/server/modules/catalog/service.ts` 的 `runAccept` 写事务内）同事务调用——照 `src/server/modules/search/index.ts:86-87` 的签名。
2. 用 FTS5 的 `DELETE` 语义可简化为「先 DELETE 再 INSERT」保持不变，但**必须在同一事务内**，把 2 次写合并成 1 次提交。
3. 提供 `rebuildIndex()` 全量回填入口（对齐 `src/server/modules/search/index.ts:119-131`），否则后续改 tokenizer 时没法在线重建。

## P4 — `plugin_id UNINDEXED` + 无 `rowid` 规划：查回业务表的代价被藏在「<50ms」里（中）

**① 哪部分** proposal.md §3 只 `SELECT plugin_id FROM plugin_search`，§4 按 bm25 排序；**没有**写如何回查 `plugins` 展示字段、如何分页。

**② 后果** proposal.md §3-§4：
- `plugin_id` 是 TEXT（`UNINDEXED`），命中后要按 id 回查 plugins 展示字段 = 二次查询。若像现有实现那样逐行判可见性（`src/server/modules/search/index.ts:245` 的 `resolveVisibilityInTx(db, row.review_id)`），就变成 **N+1 次查询**。现有实现靠「先取候选 → 一条 `IN (...)` 批量取展示字段」规避（`index.ts:196-206`，分块 200 以避开 SQLite 999 参数上限）。
- **分页语义缺失**：bm25 排序 + `LIMIT/OFFSET`，方案没给候选上限，也没说明 total 怎么算。深翻页（OFFSET 很大）时 FTS5 仍需顺序扫描全部命中行。
- `UNINDEXED` 列不参与匹配是对的，但**缺少「候选上限」这个关键保护**。现有实现的取舍写在 `index.ts:47-50`：`CANDIDATE_LIMIT = 500`（「500 足够覆盖关键词命中的常见规模」）。

**③ 建议** 明确三件事：(a) 候选上限（如 `CANDIDATE_LIMIT = 500`）；(b) 展示字段一条 `IN (...)` 批量取、分块 ≤200；(c) 只 `SELECT plugin_id, bm25(...) AS score` 出候选，**先判可见性/状态再取详情**，避免为被过滤掉的行走详情查询。

## P5 — bm25 权重未定义；「<50ms」无测量口径（中）

**① 哪部分** proposal.md §4「按 FTS5 的 bm25 分数排序」与 §预期「响应时间 < 50ms」。

**② 后果** proposal.md §4 / §预期：
- bm25 必须写成 `bm25(plugin_search, w_id, w_name, w_desc)`，列序与建表列一致。方案只写"按 bm25 排序"，实现时极易写成 `ORDER BY rank` 而漏权重，导致**名称命中与描述命中同分**——「相关度高的在前」在数据上不成立。现有实现把权重显式常量化在 `src/server/modules/search/index.ts:55`：`bm25(review_search, 0.0, 8.0, 1.0, 4.0)`（标题 8 / 正文 1 / 插件名 4），并在 `index.ts:183` `ORDER BY score ASC, review_id ASC`——注意 **bm25 越小越相关，必须 ASC**，且带 id 兜底保证不重不漏（同 `index.ts:183`）。
- 「<50ms」**没有测量条件**：在什么数据量、什么 q 长度、冷/热缓存、并发几路下测的？没有基线就无法验证，也无法防回归。现项目在 `migrations/0014_review_search.sql:10` 记录「实测边界」的做法就值得照搬。

**③ 建议** 权重写明并给理由（建议 name 高、description 中，例如 `bm25(plugin_search, 0.0, 8.0, 3.0)`）；`ORDER BY score ASC, plugin_id ASC`；把指标改写成可测口径：**「N=10000 插件、q 长度 3/10、WAL 热缓存、单连接串行，p95 < 50ms」**，并补一条基准测试钉住。

---

## P6 — 路由未挂限流与缓存，搜索是典型高成本低命中接口（中）

**① 哪部分** proposal.md §3 `GET /api/plugins/search?q=...`。

**② 后果** proposal.md §3：每个非空 `q` 都触发一次 FTS5 全索引匹配 + 可能两次查询。方案未提限流、未提结果缓存。项目已有现成限流设施（`src/server/platform/rate-limit.ts`，迁移 `0006_rate_limiter.sql`），搜索路由若绕过它，会成为**唯一的无成本放大器**：攻击者用随机串制造永不命中的全索引扫描，既耗 CPU 又破坏语句缓存（叠 P1）。

**③ 建议** 搜索路由挂上 `src/server/platform/rate-limit.ts` 的通用限流；对**规范化后的 q** 做短 TTL 结果缓存（同 q 的高频重复是常见模式，如用户逐字输入）；空 q 与超短 q 直接短路返回，不进 FTS。

## 建议的最小改动清单（按 ROI 排序）

| 优先级 | 改动 | 参照 |
|---|---|---|
| P1 | 参数化 + `toFtsPhrase` + 长度钳制 | `search/index.ts:65-67,140,157` |
| P2 | `tokenize='trigram'` + 1–2 字 `LIKE` 回退 | `migrations/0014_review_search.sql:22`, `search/index.ts:166` |
| P3 | `reindexPluginInTx(conn,...)` 同事务、加 `rebuildIndex` | `search/index.ts:82-107,119-131` |
| P4 | 候选上限 + 批量 `IN` 取详情（分块 200） | `search/index.ts:47-50,196-206` |
| P5 | bm25 权重 + `ORDER BY score ASC, id ASC` + 可测指标 | `search/index.ts:55,183` |
| P6 | 路由限流 + q 结果短 TTL 缓存 | `platform/rate-limit.ts` |

**结论**：方案的方向（FTS5 + bm25）是对的，但**目前这版是把仓库三个月前已经踩完的坑重新踩一遍**，且新增了写入路径无事务、无 fsync 合并的放大问题。建议直接以 `src/server/modules/search/index.ts` 为模板改写成插件索引版，而不是重新设计。
