# 安全评审：插件全文搜索方案

**结论：不可上线。** 方案第 3 节存在**直接字符串拼接的 SQL 注入**，且索引维护代码绕开了本项目已有的检索/可见性纪律。以下按严重度排序。

---

## S1 — 严重：查询接口 SQL 注入（可构造任意 SQL）

**① 问题部分**：`proposal.md:36`

```ts
const sql = `SELECT plugin_id FROM plugin_search WHERE plugin_search MATCH '${q}'`;
const rows = db.prepare(sql).all();
```

`q` 直接来自 `GET /api/plugins/search?q=`，未经任何绑定/转义就拼进 SQL 文本。

**② 后果（proposal.md:36）**

- **语句逃逸**：`q = ' UNION SELECT token_digest FROM user_sessions --` 即可把 `user_sessions.token_digest`（迁移 0001:56 的会话摘要）当作 `plugin_id` 返回；配合 `UNION SELECT ... FROM users` 可读出/探测任意表。搜索接口会成为**整库读取通道**，且它通常是未登录可访问的读接口——无需任何凭据。
- **数据破坏**：`better-sqlite3` 的 `prepare()` 会执行多语句（`db.exec` 语义仅限单语句，但拼接仍可闭合引号改变语义）。更关键的是**审计不可删除这张网在本路径上是无效的**：`q = '; DELETE ...` 类注入若被拒绝，应用层报错信息通常会把 SQL 片段回显给调用方，构成**结构泄漏**（表名、列名、FTS5 虚拟表名）。
- **FTS5 语法注入**：即使不逃逸引号，`q` 里的 `"`、`^`、`*`、`OR`、`NEAR`、`col:` 也会被当作 FTS5 查询语法解释——`q = "a" OR ""` 之类可绕过任何"关键词"语义，把全部索引行拉出（含非公开插件）。

> 注意：`0014_review_search.sql:26` 与 `src/server/modules/search/index.ts:62`（`toFtsPhrase` 双引号转义）已经确立了本项目的正确做法：**参数绑定 + 把用户输入包成 phrase 并内部转义**。方案完全没有引用这套既有实现。

**③ 建议**

```ts
const rows = db.prepare(
  `SELECT plugin_id FROM plugin_search WHERE plugin_search MATCH ?`
).all(toFtsPhrase(q));
```

并复用 `search/index.ts:62` 的 `toFtsPhrase()`（双引号 → `""`，整体包 `"`）。同时：`q` 必须先做长度截断（`search/index.ts:136` 用 `.slice(0, 100)`）、类型校验与非空判断；1–2 字符查询走 `LIKE` 回退，且必须用既有的 `escapeLikePattern()` **并配 `ESCAPE '\'`**（`search/index.ts:171-177`），否则 `%`/`_` 被当通配符。

## S2 — 严重：索引表未声明 `tokenize`，中文搜索承诺不成立（功能面 + 拒绝服务面）

**① 问题部分**：`proposal.md:12-16`

```sql
CREATE VIRTUAL TABLE plugin_search USING fts5(plugin_id UNINDEXED, name, description);
```

缺 `tokenize`。FTS5 默认 `unicode61`，按"词"切分，**中文整段算一个词，子串搜不到**——这一点在 `0014_review_search.sql:5-10` 已经写明并用测试钉住（"搜『记忆』匹配不了『记忆插件』"）。

**② 后果（proposal.md:12、proposal.md:44）**

- 第 44 行"支持中文与英文搜索"的预期直接不成立：中文用户搜两字词返回 0 条，被当成"功能没做"。
- 更危险的是**修复路径**：若后续有人为了"支持中文"把查询改成 `LIKE '%q%'` 兜底而不做索引，`plugins.description` 全表扫描 + 无 LIMIT，`<50ms`（proposal.md:45）不成立，构成**低成本的查询型 DoS**（单次请求可触发全表 LIKE）。这是"用性能换功能"的经典安全退化。

**③ 建议**

- 与 0014 保持一致：`tokenize = 'trigram'`，并在应用层对 1–2 字查询显式走 LIKE 回退 + `CANDIDATE_LIMIT`（参考 `search/index.ts:34` 的 `CANDIDATE_LIMIT = 500`）。
- 把"trigram 只对 ≥3 字符生效"这条边界**写进迁移注释并加测试**，与 0014 同规格。
- 查询路径强制 `LIMIT`，禁止无界返回。

## S3 — 高：索引维护缺少可见性/撤回联动，形成"幽灵条目"信息泄漏

**① 问题部分**：`proposal.md:20-28` 的 `upsertSearchIndex`

只有 `DELETE` + `INSERT`，且注释口径是"插件新增或更新时同步写入"。没有删除/下架/隐藏的联动路径。

**② 后果（proposal.md:20-28；对照 `0014_review_search.sql:17-20`）**

- 0014 明确写了设计取舍：索引在**发布**时写入，撤回/隐藏**不改索引**，但"可见性在查询时统一解析（`resolveVisibilityInTx`）"——即**索引可以脏，但查询必须过滤**。本方案的查询（proposal.md:36）是裸 `SELECT plugin_id FROM plugin_search`，**没有任何可见性 JOIN**。
- 于是：插件被下架 / 仓库 `availability_state='unavailable'`（0001:76-78）/ `is_archived=1`（0001:75）/ 分类 `is_visible=0`（0010）之后，**旧索引行仍然存在且会被返回**。用户能通过搜索发现本应不可见的插件名称与描述——已删除内容（包括可能因违规被下架的插件）的名称/描述泄露。
- `upsertSearchIndex` 的 DELETE-then-INSERT 也**不是原子的**（`proposal.md:22-27` 两条独立 `await`，无事务）：并发下或第二步失败时，插件会**从搜索结果中彻底消失**。这与 `search/index.ts:86-88` 的做法相反——那里在**同一事务**内 `reindexReviewInTx`，注释明说"索引与公开指针必须一起成功或一起回滚"。

**③ 建议**

- 索引写入必须与插件写操作**同事务**（参考 `reindexReviewInTx` 的签名：显式接收 `conn`，由调用方在事务内传入）。
- 查询侧补上与 0014 同构的可见性过滤：`JOIN plugins` → `JOIN repositories`，条件至少 `repo.availability_state != 'unavailable'`、`repo.is_archived = 0`，并复用 `resolveVisibilityInTx` 类的统一判据，**不要在新模块里复制可见性逻辑**（0014 的注释专门警告过这点）。
- 增加 `rebuildIndex()` 等价物（参考 `search/index.ts:113-125`），以便索引漂移后可重建。
- 加触发器或补删除路径：插件被硬删除时同步清理索引行。

## S4 — 中：返回裸 `plugin_id` 违反最小暴露，且无分页/频控

**① 问题部分**：`proposal.md:32-38` + `proposal.md:45`

接口只返回 `plugin_id`，无 `page`/`page_size`，无频控。

**② 后果**

- 无分页 + 无 `LIMIT`：一次查询返回全部命中行，配合上面的注入面（S1）可直接做**批量导出**；即使无注入，大结果集也是 DoS 放大器，与 `<50ms` 预期自相矛盾。
- 频控缺失：本项目已有 `rate_limiter_flexible`（0006）与既定动作键规范（`0006:20-23`，形如 `rlflx:<action>:<userId>`）。搜索是典型的"高成本、匿名可打"接口，**必须**上频控，否则 S2 的 LIKE 回退就是免费的资源耗尽手段。
- `plugin_id` 作为内部标识直接外泄给匿名调用方，便利了后续针对单插件的枚举探测。建议返回展示所需字段（name/description 摘要）而非纯内部 ID，或明确该 ID 本就是公开标识并写进契约。

**③ 建议**

- 强制分页：`page_size` 上限 ≤50（对齐 `search/index.ts:135` 的 `Math.min(Math.max(..., 1), 50)`）。
- 接入既有 limiter，新增动作键如 `rlflx:plugin_search:<ip|userId>`。
- 明确 `plugin_id` 的暴露口径并在接口契约里写明。
