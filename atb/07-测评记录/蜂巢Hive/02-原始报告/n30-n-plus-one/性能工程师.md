## 性能评审：`proposal.md`《插件列表页的分类查询优化》

我读完了方案、`migrations/0010`、`0011`、`0005`、`0001`，以及 `src/server/modules/catalog/service.ts`，结论是：**这个方案描述的问题在这个代码库里根本不存在**。它要“改掉”的那段代码是凭空写的，要“改出”的那段代码如果真去做，会破坏现有实现，而且不会带来任何性能收益。

真正的问题不在“库查了几次”，而在**分类匹配是逐行 JSON 全表扫描，且没有索引**。

---

### 1. 前提错误：`plugin_categories` 表没有 `repository_id` 列

**问题部分**：方案第 1 节“优化前”和第 2 节“优化后”都写了 `WHERE repository_id = ?` / `IN (...)`。

**后果**：
- `migrations/0010_plugin_categories.sql:26-34`：`plugin_categories` 只有 `slug, label, topics, sort_order, is_visible, created_at, updated_at`。**没有 `repository_id`**。
- 方案里那两条 SQL 直接跑会报 `no such column: repository_id`，一跑就崩，不可能出现“21 次查询”的线上现象。
- 真实的映射关系是**按 topic 字符串匹配**的：`plugin_categories.topics` 存的是 JSON 数组，如 `["multi-agent","agent",...]`（`0010:40-50`、`0011:17-35`）；仓库侧 topics 在 `repositories.topics`（`0005_plugin_directory_info.sql:25-27`，JSON 列 + `json_valid` CHECK）。两张表之间**没有外键、没有连接表**。

**建议**：把方案的前提整段换成真实机制——“分类 = 仓库 topics 与分类认领 topics 的集合求交”，再去谈优化。否则后面所有“21 次 → 2 次”的论证都没有对象。

---

### 2. 真正的 N+1 早就不存在了，现有实现已经是批量

**问题部分**：方案说现状是“一页 20 个插件查 21 次库”。

**后果**：
- `service.ts:248-271` 已经有 `categoriesByRepository()`，注释明写“一次查询，避免 N+1”。
- `service.ts:858-862` 在 `listPlugins` 里按仓库 id 去重后一次性批查，再 `categoriesMap.get(...)` 分发。
- `service.ts:759` 的 `getPlugin` 单条路径也是走同一个函数。
- 也就是说 `listPlugins` 现在是 **3 条 SQL**（count、list、categories + overrides），不是 21 条。

**建议**：方案应先说明“这个性能问题在当前 HEAD 上不可复现”。如果目标是从 3 次降到 2 次（把 categories 并进主查询），那是另一个命题，收益上限也仅是少量 syscall 级开销，不是“列表页显著变快”的来源。

---

### 3. 最严重的性能问题被方案漏掉了：分类匹配是 O(仓库数 × 分类数 × topics) 的嵌套 JSON 扫描

**问题部分**：方案完全没提这条路径。

**后果**：
- `service.ts:257-267`：
  ```
  FROM repositories r
  JOIN json_each(r.topics) rt
  JOIN plugin_categories c ON c.is_visible = 1
  JOIN json_each(c.topics) ct ON ct.value = rt.value
  WHERE r.id IN (...)
  ```
  两个 `json_each` 都是**表值函数，无法走索引**。SQLite 只能先把 `repositories.topics` 展开成行，再对每个展开行与 `c.topics` 的展开结果做比较。
- `buildDirectoryWhere` 里更糟：`service.ts:296-303`（`__none__` 分支）和 `service.ts:305-313`（具体分类分支）在 **WHERE 子查询**里对每一行 `r` 都重新展开 `json_each(r.topics)` 与 `json_each(c.topics)`。这个表达式同时出现在 `COUNT(*)`（`service.ts:822`）和取列表（`service.ts:826`）两处，等于**每页扫描两遍**。
- `listCategories`（`service.ts:1019-1035`）更重：对每个分类各跑两个相关子查询（`repository_count`、`plugin_count`），每个子查询又把 `repositories` 全表 `json_each` 展开一遍。分类数 = 10（`0010:40-50`），等于 **20 次全表 JSON 展开**。

**建议**：把它当成真正的优化目标。方向：
- 加一张**物化的 `repository_topics(repository_id, topic)` 表**（写入时由 `service.ts:432-476` 的 upsert 处同步展开），在 `topic` 上建索引，把 `json_each` 全部换成索引等值 join；
- 或者加 `plugin_category_membership(repository_id, slug)` 物化表，把“求交”在写入时算好。这才是能把 `listCategories` 从 20 次全表扫描压下去的唯一办法。
- 单靠“21→2”的查询次数合并，对这两个 `json_each` 的复杂度**没有任何改善**。

---

### 4. 拼接 `IN (${ids.map(() => '?')})` 有参数上限风险，且是负优化

**问题部分**：方案第 2 节 `IN (${ids.map(() => '?').join(',')})`。

**后果**：
- 参数个数随页大小线性增长。`service.ts:254` 当前实现有 `if (repositoryIds.length === 0) return out;` 保护，方案的写法在 `plugins` 为空时会拼出 `IN ()`——**SQLite 语法错误**（`IN ()` 不合法）。方案代码在第 3 行就崩。
- 方案没写页大小上限。一旦有人把 `LIMIT` 放开到几百上千，会撞上 `SQLITE_MAX_VARIABLE_NUMBER`（老版本 999）。
- `r.id` 已经按 `IN` 过滤过，这个 `IN` 本身是对的、也是必要的，但它**不是**性能瓶颈——瓶颈是上面第 3 条的 `json_each`。

**建议**：保留空数组早返回；分页大小设硬上限；真正的提速不在这里。

---

### 5. “查询从 21 次降到 2 次”这个指标本身是错的度量

**问题部分**：方案的“预期”只给了次数。

**后果**：
- 在这个代码库里，查询次数在 3 附近，且每次都是 **in-process 同步 better-sqlite3 调用**（`service.ts:44` 引入 `getDb`，全部走同步 prepare/all）。少一次 prepared statement 的收益是微秒级，不是“显著变快”。
- `withRead`（`service.ts:766`、`822`）说明整个列表在一个读连接里，真正的耗时由扫描量决定，不由语句条数决定。
- 方案没有任何 `EXPLAIN QUERY PLAN`、没有数据量前提（仓库数、插件数、topics 平均长度）。在几百行数据上，第 3 条的问题都测不出来；在几万行上，它才是唯一重要的东西。

**建议**：把验收指标从“查询次数”换成：给定数据量（比如 5k 仓库 / 30k 插件）下 `listPlugins` 与 `listCategories` 的 P95 耗时，以及 `EXPLAIN QUERY PLAN` 里不再出现 `SCAN`。方案缺这两样，就没法判断改完到底有没有变快。

---

### 6. 补充：`listPluginTags` 与 `service.ts:876` 的注释已自相矛盾

**问题部分**：`service.ts:876-880` 的文档注释仍写“本切片没有中文分类字典”，但 `0010`/`0011` 已经把中文分类落表了。

**后果**：注释误导后续维护者以为分类只有 `topics` 一条路径，容易照着过期描述去“优化”，方案的错误前提很可能就来自这类过期文档。

**建议**：顺手修掉该注释，并在方案里引用**当前**的 `categoriesByRepository` 实现作为基线。

---

**总结**：方案解决的是不存在的问题（N+1 已解决、`repository_id` 列不存在），提出的改法（拼 `IN`）在空页时会直接语法报错，且对真正的瓶颈——`json_each` 无法走索引导致的反复全表 JSON 展开——毫无帮助。建议整篇重写，把工艺目标改成“为 topics/分类建立物化索引表 + 用 `EXPLAIN QUERY PLAN` 与 P95 耗时为验收”。
