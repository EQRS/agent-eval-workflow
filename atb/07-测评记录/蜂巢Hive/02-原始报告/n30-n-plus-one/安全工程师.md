## 安全评审：插件列表页分类查询优化方案

### 0. 先说一个关键事实核对（影响后面所有判断）

提案里的 SQL 与仓库实际 schema **不一致**。我用 migration 和代码核对了：

- `plugin_categories` 的表定义在 `migrations/0010_plugin_categories.sql:23-30`，主键是 `slug`，列只有 `slug / label / topics(JSON) / sort_order / is_visible / created_at / updated_at`。**没有 `repository_id` 列**。
- 分类与仓库的关联不是外键列，而是靠 `repositories.topics` 与 `plugin_categories.topics` 的 **JSON 数组交集**算出来的。这一点在 `migrations/0011_plugin_categories_expand.sql:16-35` 的 `UPDATE ... SET topics='[...]'` 和 `src/server/modules/catalog/service.ts:178-190` 里都能确认。
- 因此提案中“优化前”和“优化后”两段 SQL（`WHERE repository_id = ?`）**在当前库上都会直接报 `no such column: repository_id`**。

这一点从安全视角必须先说明，因为它意味着：**这份方案描述的“21 次查询”并不是线上真实的热点路径**。真实路径 `service.ts` 早已是批量 JSON 关联（`json_each(r.topics)` JOIN `json_each(c.topics)`），下面会细说。安全评审要防止的是“为不存在的 bug 做优化，顺手把真实的安全边界改坏”。

---

### 1. 核心安全问题：`IN (${ids.map(() => '?')})` 拼装 + `.all(...ids)` 的动态 SQL

**① 哪部分有问题**
`proposal.md:27-31`：
```ts
`SELECT * FROM plugin_categories WHERE repository_id IN (${ids.map(() => '?').join(',')})`
).all(...ids);
```

**② 后果**
- **空数组会产出 `IN ()` 语法错误**：提案代码对 `plugins` 为空（第 0 页/过滤无结果）没有防护。`proposal.md:28` 的 `ids` 若为 `[]`，展开成 `IN ()`，better-sqlite3 直接抛 `SQLITE_ERROR: near ")": syntax error`。这是**可用性问题**：任何人用一个查不到的关键词就能让列表页返回 500，构成廉价的**拒绝服务触发点**（无需登录、GET 参数即可触发）。
- **无上限的占位符数量**：虽然这条 SQL 本身是参数化的（值不会被注入），但**结构**来自数组长度。如果后续有人“顺手”把 `LIMIT 20` 改成用户可控的 `pageSize`，占位符数量就变成不可控输入。SQLite 默认 `SQLITE_MAX_VARIABLE_NUMBER` 是 999（新版 32766），超了会报错而非注入，但仍是输入直接决定 SQL 结构，属于不良模式。
- **`SELECT *` 把整表列都带出来**：`proposal.md:30` 选择 `*`，会把 `plugin_categories` 全部列（含 `topics` JSON）返回给展示层。分类表未来若加内部列（如 `reviewer_note`/`internal_flag`），会**自动泄漏到接口响应**，无法通过 code review 察觉。真实代码 `service.ts:181-183` 就是显式列出 `c.slug, c.label, c.sort_order`，这才是正确示范。

**③ 建议**
- 空集合短路：`if (ids.length === 0) return new Map();`（对照 `service.ts:177` 已有的 `if (repositoryIds.length === 0) return out;`）。
- 显式列名，禁止 `SELECT *`，与 `service.ts:181-183` 对齐。
- `ids.length` 加硬上限断言（如 ≤ 200），超限走分片或改回子查询。
- 更推荐：**直接复用现有实现**。`service.ts:170-192` 的 `loadCategories...` 已经用 `r.id IN (${placeholders})` + `.all(...repositoryIds)` 且已做空集合短路，是同一需求的现成、已审过的实现——方案应说明为何不复用，而不是新写一份。

### 2. 提案上下文与真实数据口径的偏差：这不是一个 N+1 问题

**① 哪部分有问题**
`proposal.md:5` “一页 20 个插件要查 21 次库”与 `proposal.md:22-31` 的优化前提。

**② 后果（文件:行号）**
- 真实代码 `src/server/modules/catalog/service.ts:181-190` 用的是**单条** `SELECT DISTINCT ... FROM repositories r JOIN json_each(r.topics) rt JOIN plugin_categories c ... JOIN json_each(c.topics) ct ON ct.value = rt.value WHERE r.id IN (...)`。**一次查询出全部分类**，根本不存在 21 次。
- 列表主体与分类是通过 `p.repository_id` / `r.id` 关联，而 `plugins` 表本身在 `migrations/0005_plugin_directory_info.sql:46-53` 只有展示字段，没有 `category_id`。
- 安全后果：若按提案实现，会**新增一条与 `service.ts` 并行的第二条分类查询路径**。两条路径对 `is_visible = 1` 的处理一旦分叉（例如提案的 `SELECT *` 忘了 `WHERE is_visible = 1`），就会出现**隐藏分类被打桩但列表仍显示**的信息泄漏——被下线的分类标签重新出现在公开页面上。这是典型的“同一语义多处实现 → 权限判据漂移”失陷模式。代码库已在 `service.ts:127-138` 明确警告过这类漂移（公开评测计数口径必须与 `resolveVisibilityInTx` 逐条一致）。

**③ 建议**
- 撤回该方案，改为在 `service.ts` 复用现有批量查询；如确有性能问题，应先给出**真实**的慢查询证据（`EXPLAIN QUERY PLAN`），而不是假设的 N+1。
- 若必须新写，强制 `WHERE c.is_visible = 1`，并把可见性口径抽成共享常量，禁止两处手写。

### 3. 参数化 SQL 的正确性值得肯定，但需注意“部分优化”留下的注入面

**① 哪部分有问题**
`proposal.md:26` 的 `ids.map(() => '?')` —— 这部分本身是安全的（值走绑定参数）。

**② 后果**
- 对比“优化前” `proposal.md:16-20`，原写法其实也是参数化的（`?` 占位）。**方案并没有修掉任何注入问题**，只修了次数。所以安全收益为零，风险却是新增动态 SQL 拼装点。
- 需要提醒：`proposal.md:27` 里 `repository_id` 若未来改成拼接字符串（常见“顺手优化”），立刻变成注入。当前代码库在 `service.ts:282` 展示了正确做法（`escapeLikePattern` + `ESCAPE '\\'` 应对 LIKE 通配注入），说明团队有意识，方案不应开倒车。

**③ 建议**
- 在方案里显式写一句“占位符只由代码生成，绝不拼接任何外部值”，作为实现约束留给 reviewer。

### 4. 缺失的安全考量：列表页没有提到限流与越权面

**① 哪部分有问题**
`proposal.md` 全文只讨论 21→2 次查询与“显著变快”，**没有任何关于查询成本上限的说明**。

**② 后果**
- 列表页是**匿名可访问**的公开接口。迁移 `0006_rate_limiter.sql` 存在说明项目有限流设施，但方案未说明批量查询是否会影响限流口径。把 21 次单点查询合并成 1 次大查询后，单请求的**每次成本**上升，在限流按“请求数”计的口径下，同等请求量下 CPU/IO 总消耗反而更高，这可能削弱限流对资源耗尽的保护效果（`migrations/0006_rate_limiter.sql` 需按请求计数的前提下）。
- 若 `ids` 来自 `plugins` 表的 `LIMIT 20`，本次可控；但提案没有把“LIMIT 是唯一的上界”写成不变量，后续改动容易失控。

**③ 建议**
- 方案中补一条：单次列表请求的 DB 查询数与返回行数上界，并说明与 `0006` 限流口径的关系。

---

### 5. `SELECT *` 与审计/日志的耦合风险（补充，审计视角）

**① 哪部分有问题**
`proposal.md:26,30` 使用 `SELECT *`。

**② 后果**
- 若该查询被纳入任何操作审计（项目有 `migrations/0042_audit_immutable.sql` 的 `operation_records` 不可变约束），把整表列写入 `changes` JSON 会**固化未来列**到审计记录中，后续想裁剪字段已经不可能（审计行不可 UPDATE/DELETE，见 `0042_audit_immutable.sql:19-27`）。这是**不可逆**的设计债。

**③ 建议**
- 显式列名，审计只记录业务必需字段。

---

### 结论

从安全角度：**不建议按当前提案实施**。三点理由，按严重度排序：

1. **空数组 `IN ()` 导致的 500/DoS 触发点**（`proposal.md:27-28`，无短路保护）。
2. **与真实 schema 不符，且会与 `service.ts:181-190` 形成第二条分类路径，造成 `is_visible` 可见性判据漂移 → 隐藏分类泄漏**。
3. `SELECT *` 在公开接口 + 不可变审计的组合下会扩大暴露面并留下不可逆债。

建议改为：先复核是否真有必要（现有实现已是单查询批量），若确要改则在 `service.ts` 内复用 `loadCategories...` 的写法（空集合短路 + 显式列 + `is_visible = 1` + 占位符数量上限）。
