我从安全工程师角度评审这份方案。**先说明一处事实基础**：方案第 2 节的代码与现有实现不一致。现有 `enqueue` 的签名是**必填** `schedulingGroup` 与 `availableAt`，而去重键的权威判据是 `UNIQUE(task_type, deduplication_key)`（`src/server/modules/tasks/service.ts:188-196`、`migrations/0007_task_type_plugin_discovery.sql:39`）。方案里的 `tasks.enqueue({...})` 缺这两个字段，且 `deduplicationKey` 复用去重键名，因此第 3 节「UNIQUE 冲突返回已存在任务」的说法也需按下面第 1 条重新审视。以下只列安全问题。

---

## 1. 去重键把 `source` 未经校验直接拼进 key —— 键空间可被污染

**哪部分有问题**：第 2 节 `discoveryDedupKey(source, date)` 与第 3 节手动触发 `body: { source: "github" }`，都没定义 `source` 的取值域与校验。

**后果**：
- `deduplication_key` 的唯一约束是 `UNIQUE(task_type, deduplication_key)`（`migrations/0007_task_type_plugin_discovery.sql:38-39`，校验仅 `trim(...) <> ''`，`0007:33`）。若 `source` 来自请求体且不设白名单，管理员（或拿到管理员 token 的人）可以塞任意长字符串，SQLite 无长度上限 → 无界写入 / 存储膨胀；`source` 含 `:` 时还能与 `manual:`（`src/app/api/admin/discovery/route.ts:107`）等其它键前缀**发生别名冲突**，让一个手动任务顶替掉一个定时任务的去重位。
- 更关键的：`source` 一旦成为**上游预算的作用域**，就出现了「按 source 拆分预算」的放大面。现在预算是**每轮常量**（`src/server/modules/catalog/discovery.ts:41-48` 的 `maxRequests: 400`、`maxCandidates: 12`），且 `GITHUB_TOKEN` 共用同一份配额（`discovery.ts:57-70`）。每天开 5 个 source 就是 5×400 次请求，但 GitHub 的匿名额度只有 60 次/小时（`discovery.ts:53-56` 注释已明确此约束）。

**建议**：在**代码常量**里定义 `DiscoverySources` 白名单（与 `TaskTypes` 同风格，见 `src/packages/common/field-rules.ts:96-102`「注册集合随迁移版本维护，不能由配置注入新类型」），`discoveryDedupKey` 入口处校验、非法值抛 `err.input`；并加一条**全局日预算**（所有 source 合计的上限），而不是只靠每 source 预算相乘。

## 2. 手动触发端点复用「系统调度」语组，混淆了权限边界与审计

**哪部分有问题**：第 3 节把管理员手动触发与定时任务放在同一个 dedup key 形态下，而未说明 `requestedBy`、`schedulingGroup`、审计身份如何区分。

**后果**：
- 现有实现刻意把系统任务与用户任务分开：`DISCOVERY_SCHEDULING_GROUP`（`src/worker/scheduled.ts:36`，注释「与用户任务分开，便于观测系统调度占了多少」），系统入队 `requestedBy: null`（`scheduled.ts:83`）。若手动触发沿用同组同键，**「谁按的按钮」在队列层不可见**；一旦真出事（例如恶意管理员刷发现），无法从 `background_tasks` 区分「运维排的」和「人按的」。
- 审计写入失败会被**吞掉**：`src/worker/handlers.ts:352-357` 对 `recordOperationInTx` 包了 `try/catch` 仅 `log.warn`。也就是说「发现动作记录在 `operation_records`」这条最强追溯链是**best-effort**。手动触发如果只依赖这条审计，就等于**可以被无声抹掉的操作**（例如按了按钮但审计写失败、或磁盘满）。
- 端点权限只到 `assertCanAdmin`（`src/app/api/admin/discovery/route.ts:92`），无频控、无二次确认。管理员账号被劫持的场景下，这是无成本、可重复触发的上游请求发生器。

**建议**：手动触发用**独立** `schedulingGroup`（如 `plugin_discovery_manual`）并在 key 或 payload 里带上操作者；审计写入失败时**不要静默**——至少升级为 `log.error` 并在响应/任务 progress 里标记 `audit_degraded`；端点加频控（项目已有 `rate_limiter_flexible`，见 `migrations/0006_rate_limiter.sql`）。

## 3. 「幂等」被过度承诺：去重键只覆盖「今天」，不覆盖「今天的第几次」

**哪部分有问题**：第 4 节「沿用 RETRY_BACKOFF_MS = [30s, 120s]、MAX_RECOVERABLE_ATTEMPTS = 3」与「预期：每个数据源每天只跑一次 / 管理员手动触发不会产生重复任务」。

**后果**：
- 现有终端语义是：3 次尝试失败即 `failed`（`src/server/modules/tasks/constants.ts:33-47`）。任务失败后**该 key 的行仍是 `failed` 终态**，由于 `enqueue` 先查已存在行就返回 `created: false`（`src/server/modules/tasks/service.ts:204-208`），同一天**再也排不进**该 source。所以「每数据源每天只跑一次」实际是「每天最多成功一次，或永久放弃」——这与方案背景要解决的「重复调用 API」是相反方向的失效（可用性风险，非安全风险，但会导致运维反复手动补跑，从而被诱导去削弱去重）。
- 真正的安全问题是：一旦为了补跑而放宽去重（例如把 `retry_cycle` 或时间戳纳入 key），**上游请求预算的守恒性就没了**。而 GitHub 匿名配额共享（`discovery.ts:53-56`）、且被限流时服务层选择「干净收尾」而非重试（`discovery.ts:139-160`）——这正是因为重试烧配额。任何削弱 key 稳定性的改动都会直接放大**配额耗尽 DoS** 面：一个 source 的失败重跑能把其它 source 当天全部饿死。

**建议**：方案里显式写出「失败后如何重开当日额度」的策略（例如只用 `retry_cycle` 递增、并受全局日上限约束），并加一条**不可绕过的全局日请求上限**（跨 source 共享）；把它写进方案「预期」段，避免后续实现者用「改 key」来解决补跑问题。

## 4. `payload.source` 会流入日志与审计快照，存在日志注入 / 伪造面

**哪部分有问题**：第 2 节代码把 `source` 同时写进 `deduplicationKey` 和 `payload: { source, date }`。

**后果**：
- discovery 的汇总日志直接把键值打进结构化日志（`src/server/modules/catalog/discovery.ts:300-320` 的 `run_key`/`query` 字段），审计快照也把 `runKey` 当 `targetId`、`query` 当 `targetSnapshot`（`src/worker/handlers.ts:330-345`）。未校验的 `source` 若含换行/控制字符或超长内容，可污染日志行与审计快照，**伪造取证记录**（把攻击动作伪装成另一个 source 的一轮）。注意 `requested_by` 允许 NULL（`0007:35`），系统任务本就是「无主体」，这让「谁触发的」更难辨。
- `payload` 有 `json_valid` 约束但**无大小上限**（`0007:36`）。

**建议**：`source` 用白名单枚举 + 长度上限；写 `run_key`/审计前做一次归一化与字符集校验；考虑给 `payload` 加长度 CHECK。

## 需要向方案作者确认的两处（影响上述结论强度）

1. **`source` 到底是什么**：现有 `discoveryBudgetFor` 的语义是「有没有 `GITHUB_TOKEN`」两档（`discovery.ts:57-70`），而适配器固定 `API_BASE = 'https://api.github.com'`（`src/server/adapters/catalog/github-discovery.ts:88`）。若 `source` 实际只是「预算档位/查询词」的同义词，第 2 节的「每个数据源互不干扰」就是**预算被意外乘了 N 倍**，风险从「键污染」升级为「配额放大」。
2. **手动触发是否要复用现有 `manual:<requestKey>` 键**：`src/app/api/admin/discovery/route.ts:106-108` 现在已有一套手动幂等键。方案第 3 节改成 `discovery:${source}:${date}` 后，**同一个按钮在同一天点两次会命中已有任务、直接返回 `created:false`，管理员会以为「点了没反应」**——这是可用性问题，但会被当成 bug 用「换个 requestKey 再点」绕过，从而绕开原来的手动幂等保护。建议保留 `manual:` 前缀并叠加 source，而不是替换它。
