核实完毕。以下是性能工程师视角的评审。

## 结论先说

这份方案**没有引入新的性能瓶颈**（它复用已有索引路径），但它把原来"每天 1 个任务"放大成"每天 N 个数据源 × 1 个任务"，而**上游预算与限流是全局限额的，不是按数据源切分的**。方案的核心缺陷是：去重粒度改了，预算和并发控制没跟着改。另外 `enqueue` 的幂等路径是「先 SELECT 再 INSERT」，在并发下会真的抛异常而非如方案所说的"返回已存在的任务"。

---

### 1. dedup key 粒度改成了 source，但 `maxRequests` 预算仍是单轮全局值，多 source 会成倍消耗同一个配额

**① 问题在**：方案 §2「每个数据源每天一个任务，互不干扰」＋ §4 沿用既有重试参数。

**② 后果**：
- `src/server/modules/catalog/discovery.ts:41-48` 定义 `maxRequests: 400`，注释（第 36-38 行）明说这是**整轮**上游预算，取值依据是「GitHub 搜索 30 次/分、核心 5000 次/时」。
- `src/worker/scheduled.ts` 里 `max_requests: budget.maxRequests` 是**每个任务各自 400**。N 个 source → 同一天最多 `400 × N` 次上游请求。
- 未认证档更严重：`discovery.ts:60-79` 的 `discoveryBudgetFor` 按 token 有无分档，未认证时核心接口只有 **60 次/小时**，单 source 就已经贴线；多 source 必然连环 403。
- 触发路径是 `discovery.ts:216-224` / `discovery.ts:220`：`isUpstreamRateLimit` 命中就 `break` 并记 `truncated`，**任务仍然算成功**（`finish(success)`）。所以后果不是"报错"，而是**静默的每日大批插件漏收**——最难排查的那类性能问题。

**③ 建议**：引入**共享上游配额**，而不是每个 source 各发一份。
- 在 source 维度之外加一个每日总预算（如 `DISCOVERY_DAILY_TOTAL_REQUESTS`），入队时按 `总预算 / source 数` 切分，或按各 source 历史消耗比例分配；
- 更稳的做法是把配额状态落到 DB（`0006_rate_limiter.sql` 已有 rate limiter 基础设施，可直接复用），让所有 discovery 任务共享一个令牌桶；
- 未认证档建议**只允许 1 个 source**，或强制串行 + 小时级错峰，否则 60 次/小时必然被击穿。

### 2. 每个 source 一个任务 → 共同竞争 `MAX_CONCURRENT_TASKS=4`，会挤压用户任务队列

**① 问题在**：方案 §1「复用现有队列」＋ §2 多任务化，但没有评估对调度容量的影响。

**② 后果**：
- `src/server/modules/tasks/constants.ts:14` `MAX_CONCURRENT_TASKS = 4`，这是**全站**并发上限。
- `claimWithin`（`src/server/modules/tasks/service.ts:117-131`）的取值 SQL 为：
  `WHERE processing_state IN ('queued','retry_wait') AND available_at <= ? ORDER BY available_at ASC, created_at ASC, id ASC LIMIT 1`
  —— **完全不看 `scheduling_group`**。`scheduled.ts:30-33` 特意定义了 `DISCOVERY_SCHEDULING_GROUP = 'plugin_discovery_schedule'`，注释说"与用户任务分开，便于观测占了多少"，但**这个分组在领取阶段没有任何隔离效果**。
- 结果：N 个 discovery 任务和 `review_check` / `comment_check` 等用户发起的任务排在同一个池子里。discovery 单轮可跑 `maxPlugins: 30`（`discovery.ts:45`）× 每次收录 3 个上游请求，是**长耗时任务**；且 `TASK_DEADLINE_MS = 300s`（`constants.ts:52`）。4 个槽位里有 2-3 个被 discovery 占住时，用户提交评测的审核延迟会明显上升。
- 更糟的是这些任务 `available_at` 都等于当天零点附近（`scheduled.ts` 中 `availableAt: now`，而每日检查在 worker 启动时补排），`available_at` 相同、`created_at` 几乎相同，按 `created_at ASC` 排序 → **discovery 任务会成批抢占最早的槽位**，正好压在用户早高峰前面。

**③ 建议**：
- 要么在 `claimWithin` 的选取逻辑里加分组配额（如"每组最多占 N/2 槽位"），让 `scheduling_group` 真正起作用；
- 要么把 discovery 的 `scheduling_group` 排到独立的低优先级队列，配合 `ORDER BY` 里的分组优先级；
- 至少应把各 source 的 `available_at` **错峰**（如 source × 15 分钟），避免同一时刻齐发。

### 3. `enqueue` 的幂等实现是「SELECT 后 INSERT」，并发下会抛 UNIQUE 异常，而非方案所述"返回已存在的任务"

**① 问题在**：方案 §3 明确写「若当天已有任务，enqueue 会因 UNIQUE 冲突返回已存在的任务（幂等）」。这个描述与实现不符。

**② 后果**：
- `src/server/modules/tasks/service.ts:204-207`：先 `SELECT id FROM background_tasks WHERE task_type = ? AND deduplication_key = ?`，命中才返回 `created:false`。
- `service.ts:213-221`：未命中才 `INSERT`。
- 这中间是 **check-then-insert**，`UNIQUE (task_type, deduplication_key)`（`migrations/0007_task_type_plugin_discovery.sql:51`）只保证了数据正确，**没有把异常转成幂等返回**。
- 单进程 + better-sqlite3 同步驱动下，`withTransaction`（`service.ts:227-228`）能盖住大部分窗口；但方案 §3 面向的是 `POST /api/admin/discovery/trigger` 这个**HTTP 入口**，管理员连点或与定时排入（`scheduled.ts` 每日补排）撞车时，仍可能命中 UNIQUE 冲突并向上抛出，变成 **500 而非 200 幂等返回**。
- 性能角度：这是**失败即重试**的放大器——客户端收到 500 会重试，重试又撞同一个窗口，形成短时重试风暴，每次重试都白跑一遍完整事务。

**③ 建议**：
- 把 INSERT 改成 `INSERT ... ON CONFLICT(task_type, deduplication_key) DO NOTHING`，然后 `changes === 0` 时回查一次拿 `taskId, created:false`；
- 或者捕获 UNIQUE 冲突错误并转为"查回已存在任务"。让幂等语义由**数据库原子操作**保证，而不是靠应用层 SELECT 的时间窗口。

### 4. `claimWithin` 的排序与现有索引不匹配，队列变长后领取开销线性上升

**① 问题在**：方案让同一 `task_type` 下任务数从「1/天」变成「N/天」，队列基数上升，但没检查领取查询是否走索引。

**② 后果**：
- `migrations/0007_task_type_plugin_discovery.sql` 重建的索引是
  `idx_tasks_claimable ON background_tasks(processing_state, available_at, scheduling_group, id)`。
- 而 `service.ts:125-131` 的查询是 `WHERE processing_state IN (...) AND available_at <= ? ORDER BY available_at ASC, created_at ASC, id ASC`。
- 索引第三列是 `scheduling_group`、第四列是 `id`，但 ORDER BY 用的是 **`created_at`**——`created_at` 不在该索引里。SQLite 需要额外排序步骤（temp B-tree）才能满足 `created_at ASC`，行数一多就走 `USE TEMP B-TREE FOR ORDER BY`。
- 叠加历史堆积：`background_tasks` 只增不减（已结束任务无清理机制），`queued/retry_wait` 只是其中一小部分，索引前两列的选择性会随表增长而下降。
- 每个 worker tick（`IDLE_SLEEP_MS` 空转 10s，`constants.ts:55`）都跑一次这个查询。任务数放大 N 倍后，空转扫描成本同步放大。

**③ 建议**：
- 把 `idx_tasks_claimable` 调整为 `(processing_state, available_at, created_at, id)`，让 ORDER BY 完全走索引顺序，消除 temp B-tree；
- 若确实要保留 `scheduling_group` 用于分组调度（见第 2 条），另建 `(processing_state, scheduling_group, available_at, id)` 索引，供分组配额查询用；
- 补充 `background_tasks` 的已完成任务归档/清理策略——本条方案会显著加快该表增长。

### 5. 手动触发用「当天日期」做 key，管理员的"重跑意图"会被静默吞掉，导致绕过幂等的重复跑

**① 问题在**：方案 §3 把手动触发也绑到 `discoveryDedupKey(source, ymd(now))`。

**② 后果**：
- 管理员手动触发**本来就是因为自动那轮失败了/不完整**（`discovery.ts:216-224` 的限流截断会让任务"成功但 truncated"）。此时当天 key 已存在且状态是 `succeeded`，`enqueue` 返回 `created:false`（`service.ts:206`），**什么都不会发生**，接口还返回 200 看起来"成功"。
- 人的反应是可预期的：再点一次；还是没反应 → 就会绕过接口直接改数据或重启 worker。真正的重复上游调用没有减少，只是转移到了不受控路径。
- 这背离了方案背景里"同一天多次触发导致重复调用 GitHub API"要解决的问题——手动通道被堵死后，问题会以更隐蔽的方式回来。

**③ 建议**：
- 手动触发用**独立 key 空间**，如 `manual:${source}:${requestId}`，与每日自动 key `discovery:${source}:${date}` 分离；
- 但要配一个**时间窗节流**（如"同一 source 手动触发最小间隔 10 分钟"，用 `0006_rate_limiter.sql` 的机制），把"防重复调用"降级为频率限制，而不是完全禁止；
- 若状态是 `succeeded` 且 `progress` 里 `truncated: true`，应允许（甚至鼓励）重跑，这属于"没跑完"而非"重复跑"。
- 顺带：`discovery.ts:216-224` 把限流截断记为任务成功，这个语义本身值得重新讨论——它让"本轮未完成"在队列层不可见，也就无法自动重试。

### 6. `runKey` / dedup key 的组成没有 source 白名单，key 形态能被外部输入直接影响

**① 问题在**：方案 §3 的 `body: { source: "github" }` 直接拼进 dedup key。

**② 后果**：
- `discoveryDedupKey` 是纯字符串拼接 `discovery:${source}:${date}`。`source` 若有前导/尾随空格、或大小写差异（`GitHub` vs `github`），会生成**不同的 key**，`UNIQUE` 约束完全失效 → 同一数据源产生了多个任务，回到"重复调用上游"的原始问题。
- 更隐蔽的是：`runKey` 会写进 `operation_records.task_id` 相关审计（`discovery.ts:86` 注释），以及 `deps.probe` 调用（`discovery.ts` 收录路径），key 形态不收敛会让审计与限流统计都按"多个数据源"计数，**观测数据失真**，进一步掩盖第 1 条的配额超发。

**③ 建议**：
- `source` 必须走**枚举校验**（与 `probe` 支持的 provider 列表对齐），非法值直接 400；
- 在 `discoveryDedupKey` 内部做规范化（`trim` + `toLowerCase`），并把规范化后的值同时写进 `payload.source`，确保 key 与 payload 一致；
- 加一条约束/断言：`source` 匹配 `/^[a-z0-9_-]+$/`，防止日期分隔符 `:` 被注入造成 key 空间碰撞。

## 补充：方案未提及但会直接影响性能的两点

**A. 缺少 dedup key 的清理/归档，key 空间无限增长。** 每日每 source 一个新 key，`UNIQUE(task_type, deduplication_key)` 索引持续膨胀，长期会让第 4 条的问题从"可接受"变"显著"。建议明确 `background_tasks` 的保留窗口（如 90 天），并在迁移里预留 `(task_type, created_at)` 索引供归档扫描用。

**B. 方案未给出 source 数量的上界。** 所有性能风险（第 1、2 条）都与 N 强相关。建议明确「支持的 source 数量上限」，并把上面第 1、2 条的预算切分/并发配额设计成**随 N 自动收敛**，而不是写死常量。

---

**总评**：方案在数据库结构上确实做到了"无新表"，改动小、风险可控，这点是好的。但它把"去重"当成了纯粹的**正确性**问题，忽略了去重粒度变化会直接改变**上游配额消耗速率**和**队列并发占用**——而这两者才是性能工程师关心的。建议至少把第 1、2、3 条在实施前解决，第 4 条随迁移一起做掉；第 5、6 条可以列为实施后的跟进项。
