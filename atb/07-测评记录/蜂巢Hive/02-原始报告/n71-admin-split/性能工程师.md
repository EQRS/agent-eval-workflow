# 性能工程师评审：n71-admin-split（管理后台拆成独立应用）

先说结论：**在“共享同一个 SQLite 文件”这一条上，本方案不可行。** 这不是保守意见，而是在现有代码路径下可以直接推出的一连串后果。其余部分（独立构建、共享 users 表）在性能上有代价，但可控。方案只有 19 行，通篇没有提到吞吐、延迟、连接数、锁、缓存。一个要拆部署边界的方案，恰恰最需要这些信息。

## 一、致命问题：两个应用写同一个 SQLite 文件

**① 问题所在**：proposal.md:10「两个应用连同一个 SQLite 文件」。

**② 后果**（有代码和迁移证据）

- SQLite 的写锁是**文件级全局锁**，不是表级。Web 与 worker 已经是两个进程（`src/server/platform/db.ts:70`「进程级单例连接（Web 与 worker 各自一个进程）」），现在再增加一个 admin 进程，写入方就从 2 个变成 3 个以上。
- 更糟的是 `db.ts:53-55` 同时设置了 `journal_mode = WAL` 和 `synchronous = FULL`。WAL 允许多读单写，但 `synchronous=FULL` 意味着**每次提交都要 fsync**。多个进程同时写入时，每个事务都要排队等待 fsync，写延迟会直接叠加。方案没有提这里是否需要继续用 FULL，但它是当前默认值，拆分会继承。
- `db.ts:56` `busy_timeout` 默认 **5000ms**。better-sqlite3 是**同步驱动**，`db.ts:7-8` 的注释已经明确说明「等待会阻塞所属线程」。一旦 admin 的批量后台查询或报表占住写锁，主站任何一个 `withTransaction`（`src/server/platform/tx.ts:48`）都会**同步阻塞整个 Node 线程最长 5 秒**，期间该进程所有请求（包括静态资源和健康检查）全部卡住。这是拆成两个应用后最典型的故障形态：**主站被 admin 拖垮，正是方案要避免的「不影响主站」的反面**。
- 后台天然是重查询（列表、筛选、导出、聚合）。`migrations/0001_baseline.sql` 里有大量 `operation_records`、`content_entities` 这类会随数据增长的宽表。它们与前台共用同一个 page cache 和同一个 WAL 文件。admin 的全表扫描会把前台热数据挤出 page cache，即使没有写锁也会让主站读延迟抖动。
- 备份、`VACUUM`、迁移现在必须由**两个应用协调**。`migrate.ts:63-88` 的执行器假设自己是唯一执行者：先读 `schema_migrations` 判断，再执行。两个进程同时启动会**都判定「未应用」然后都去建表**，产生 `table already exists` 并使其中一方启动失败。`migrate.ts` 里没有 `BEGIN IMMEDIATE` 或任何跨进程互斥；它只是靠 SQLite 的隐式锁碰运气，而 `NO_TRANSACTION_MARKER` 那条路径（`migrate.ts:100` 附近，`0007` 明确用了它）自带 `PRAGMA foreign_keys=OFF` + `BEGIN`，两个进程撞上这条迁移时后果最严重。

**③ 建议**
1. 不要在应用层共享文件。要么保持**同一个应用进程内**用路由前缀分域（工作量最小，性能上最安全），要么迁移到支持多写的存储（Postgres）。
2. 如果非要用 SQLite 多进程共享，必须把以下内容写进方案并给出量化目标：只允许**一个**写进程（admin 走单一写入队列或写代理），其他进程用 `readonly: true` 连接（`db.ts:21` 已支持）；`journal_mode=WAL` 保持、`synchronous` 降为 `NORMAL` 并说明可接受的丢数窗口；`busy_timeout` 显式调低（例如 500ms）并配合重试，**绝不能用默认 5000 配合同步驱动**——要给出“最坏阻塞时间 = busy_timeout”的预算表。
3. 迁移必须由**唯一的独立进程**执行（`migrate-cli.ts` 已在，正好承担这个角色），应用启动时只做版本校验，不执行 DDL。

## 二、独立登录实现：会话表与鉴权查询的热路径翻倍

**① 问题所在**：proposal.md:16「后台应用自己实现登录，复用 `users` 表」。

**② 后果**

- 现有会话在 `user_sessions`（`0001_baseline.sql`，含 `token_digest`、`expires_at`、`last_seen_at`）。另起登录意味着 admin 有自己的一套 session 存储或复用同一张表。若另建表，**每个用户跨域有两条会话记录**，`last_seen_at` 更新（每次请求一次写）会变成双倍写入——而“每请求一次写”正是 SQLite 上最不该有的模式，见第一点写锁排队。
- 若复用同一张 `user_sessions`，`token_digest` 唯一性和过期清理的竞争不变，但**鉴权查询频次不变、写入点翻倍**，且 0001 中 `idx_session_token_digest` 这类索引的写放大也翻倍。
- 方案没有说明 admin 的登录态是否与主站互通。若互通，需要跨站 cookie（`admin.example.com` 与主站不同 origin），`session-cookie.ts` 的 cookie 域策略要改；若不互通，用户要维护两套身份，`external_identities` 的唯一约束 `UNIQUE (user_id, provider)`（`0001_baseline.sql`，`external_identities` 定义处）会让“同一 GitHub 账号绑两次”直接撞约束。

**③ 建议**：明确二选一并写进方案——(a) 共享同一套会话与 cookie 域策略，admin 只做鉴权读取，`last_seen_at` 更新改为采样（例如每 N 分钟才写一次）；(b) 独立身份但**不允许同一 provider 账号重复绑定**，给出冲突处理路径。任何一种都要给出「每请求 DB 命中次数」的预算，目标 ≤ 现有值。

## 三、方案没有热路径数据，无法验证「不影响主站」

**① 问题所在**：proposal.md:18-19「预期：后台独立迭代、不影响主站」——这是**目标而非证据**。

**② 后果**：全文没有 QPS、p95 目标、数据量级、后台典型查询代价。所以无法判断 admin 的新增负载是前台的 1% 还是 300%。在这种信息下做出的拆分决策没有办法事后验证是否达成，也没有回滚判据。

**③ 建议**：给三个数：① 主站当前 p95 读写延迟与峰值 QPS；② 后台预计峰值 QPS 与最重查询的扫描行数量级；③ 拆分后允许的延迟退化上限（例如主站 p95 不得上升 >10%）。没有这三个数，这条评审无法签字。

## 四、独立构建：构建期与运行时缓存的分裂

**① 问题所在**：proposal.md:8「独立构建」。

**② 后果**：两个构建产物各自打包 `src/packages/common`（当前只有一个包），共享代码会**各复制一份**，`instrumentation*.ts`（`src/instrumentation.ts`、`src/instrumentation-node.ts`）也会各自初始化一次。若两者共享同一台机器部署，各自持有一个 DB 单例连接、各自的 `rate-limit.ts` 内存态——**限流阈值相当于翻倍**（`src/server/platform/rate-limit.ts`，12696 字节的内存限流逻辑），前台原本预期的限流强度会被 admin 侧的独立计数器稀释或放大，取决于是否共享 `0006_rate_limiter.sql` 的持久表。

**③ 建议**：明确限流状态是进程内还是持久化（0006 已给了持久表），共享表就必须接受写竞争；进程内就必须给 admin 单独设定阈值并说明依据。构建上把 `common` 提为真正的 workspace 依赖，避免两份实现漂移。

- `src/server/platform/db.ts:7-8,53-56,70` —— 同步驱动阻塞、WAL+FULL+a busy_timeout 5000ms、进程级单例
- `src/server/platform/tx.ts:48` —— 写事务入口，同步阻塞点
- `src/server/platform/heartbeat.ts`（`WORKER_BEAT_INTERVAL_MS = 5_000`）—— 每 5 秒一次写，已存在的固定写入方
- `src/server/platform/migrate.ts:63-88` 及 `NO_TRANSACTION_MARKER` 段落 —— 迁移无跨进程互斥
- `migrations/0001_baseline.sql` —— `user_sessions`/`external_identities` 唯一约束、大量宽表
- `migrations/0002_triggers.sql` —— 触发器带来的写放大（每条写要多跑若干 SELECT）
- `migrations/0003_auth_media.sql` —— OAuth challenge 与附件引用触发器（同样放大写）
- `migrations/0004_runtime_heartbeats.sql` —— 运行时状态独立表，正好印证“进程级状态共享一个库”的问题会被结构性放大
