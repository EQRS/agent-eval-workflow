# 安全评审结论（n71-admin-split）

**评审对象**：`atb/tasks/n71-admin-split/environment/proposal.md`（共 19 行，全文内容见上）
**评审视角**：仅安全。可行性、性能、可维护性不在本次结论范围内。

先说结论：该方案**无法通过安全评审**。技术方案全文只有 19 行，共有三处实质性改动（独立域名与独立构建、两个应用共享同一个 SQLite 文件、后台应用“自己实现登录”并复用 `users` 表），这三处分别对应一个**高危**问题。其中第 2 条（共享库）与第 3 条（自行登录）在现有代码基础上会**构造出可直接越权的攻击链**，并非“不够好”，而是会让现有安全不变量失效。

---

## 逐条问题

### ① 方案第 3 节「后台应用自己实现登录，复用 users 表」——高危：夺走鉴权，并绕过“角色每次从库读”的不变量

**问题**
现有代码的安全模型是“**一条登录路径 + 每次请求从库读角色**”，密钥式设计如下：

- `src/server/modules/identity/service.ts:1-16` 明确列出不变量 3：「角色与账户状态**每次从库读**，不缓存在会话里 —— 撤销管理员后，其旧会话立刻失去管理权限；账户被禁用后旧会话立刻失效」。
- `src/server/platform/context.ts:3-4`、`context.ts:16-18`（`isAdmin` 要求 `role==='admin' && accountStatus==='active'`）、`context.ts:46-54`（`assertCanAdmin`）是唯一判定点。
- `src/app/api/_lib/context.ts:22-24` 的 `currentContext()` 是唯一入口；`src/app/admin/page.tsx:61-80` 与 `src/app/api/admin/**` 全部依赖它。
- 会话凭证的口径也在同一处收口：`src/server/platform/session-cookie.ts:13-19`（`__Host-` 前缀 + Secure + HttpOnly + Path=/）、`0001_baseline.sql:52-66`（`user_sessions` 只存 `token_digest`，带 `absolute_expires_at` 与 `revoked_at`）。

方案要求“后台应用自己实现登录”，这意味着**再写一套会话实现**。后果不是理论风险，而是上述每一条不变量都会被新写的那份实现重新决定一次：

- 新实现若把 `role` 缓存在自己的 token 中（这是最自然的写法），则撤销管理员后旧会话仍是管理员，直到 token 过期——直接违反 `service.ts:1-16` 不变量 3；
- 新实现若用自己的 Cookie（`session-cookie.ts:13-19` 的 `__Host-` 前缀只对单 host 生效，`admin.example.com` 是另一个 host），则同一用户在两个应用有两条独立会话，**退出登录只撤销其一**，`user_sessions.revoked_at` 的撤销语义被拆成两半；
- 新实现若自行生成 token，`session-cookie.ts:42-58` 那段“环境降级”判断（`DSH_REVIEW_INSECURE_COOKIES`）必须被复制一遍；漏掉就会在无 TLS 时明文传输会话，或反过来配错导致全站登录失效。这段代码的注释本身就在说“这个坑极难排查”。

**后果**
- `src/server/modules/identity/service.ts:1-16`（不变量 3）：不变量被推翻，收回管理员权限不再即时生效。
- `src/server/platform/context.ts:16-18`、`:46-54`：`isAdmin`/`assertCanAdmin` 的可信前提（ctx 来自库内实时读取）被替换为“后台自己说了算”。
- `0001_baseline.sql:52-66`：`user_sessions` 的撤销模型对后台会话不成立。
- `src/server/modules/identity/admin.ts:31-34`（“绝不提权：服务层自己再校验一次 actor 是不是仍在任的管理员”）失去意义——越权面从业务层移到了新写的登录实现里。

**建议**
不要让后台新写登录。保留“单点登录、两侧共用会话解析”：

1. 抽出一个**唯一的** `resolveSession → CallerContext` 实现（即今天 `api/_lib/context.ts:22-24` 的逻辑），后台与主站都以它为唯一鉴权入口，禁止后台自带 `users` 查询或角色判断；
2. 会话凭证沿用 `user_sessions` 表（`0001_baseline.sql:52-66`），两侧共用同一个 `token_digest`；
3. 若两个 host 确实无法共享 Cookie（这是真的，`__Host-` 不允许 Domain），则**必须**在方案中写明这一点，并选择：
   - 统一到单 host（`admin.example.com` 只是路径/反代分流，浏览器视角仍是同站），或
   - 显式设计跨站 SSO 授权流程（一次性、短时效、绑定 browser 的授权码），并在方案里给出 token 签发/校验/撤销的完整生命周期；
   - 无论哪种，都要写清“撤销管理员后多久失效”这个 SLA，并对应到可测的证据。
4. 明确「后台不得新增任何登录 POST 旁路」，与 `src/app/api/session/route.ts:9-16` 的既有口径一致（那里已写明旧测试登录通道等于“任何人都能声明自己是某 GitHub 用户”的旁路）。

### ② 方案第 2 节「两个应用连同一个 SQLite 文件」——高危：既是可用性单点，也是审计与恢复链的伪造通道

**问题**
这一条把原本由**单一维护进程**承担的数据库，变成了两个**互相不知情**的写者。现有代码对这一点有三处硬性依赖，方案一条都没有处理：

1. **迁移唯一性**。`docker/compose.yaml:26-38` 注释写明 migrate 是「**唯一维护进程**，web/worker 不抢」，`compose.yaml:30-31` 用 `service_completed_successfully` 串起依赖。`src/server/platform/migrate.ts:85-100` 的 `migrate()` 是“读 `schema_migrations` → 逐个文件执行”的朴素实现，**没有跨进程迁移锁**。两个应用各自部署、各自跑 migrate（这是独立构建的自然结果）时，会对同一文件并发应用同一批迁移。`migrate.ts:41-51` 还记录了 `dsh:migration-transaction=off` 这一逃生口——用于重建表，期间需要 `PRAGMA foreign_keys = OFF`；**两个进程同时处于该状态时，损失的是数据完整性，不只是可观测性**。

2. **恢复会覆盖整库**。`scripts/restore-backup.mjs:117-124`：恢复会先 `renameSync` 现有库、删掉 `-wal`/`-shm`、再 `copyFileSync` 覆盖。若此时另一个应用仍持有连接，则该应用的写入会落到已被替换的 inode 上，**静默丢失**；反过来，备份本身由 `scripts/backup.mjs:14-20` 用在线热备生成，能保证的只是“那一刻一致”，两个应用各自以为在维护的数据可能互相覆盖。

3. **审计不可删除的唯一防线是库内触发器**。`0042_audit_immutable.sql:1-27` 的来龙去脉写得很清楚：`operation_records` 的 `UNIQUE(action_type, operation_key)` 被 `setUserRole/setUserStatus`、`configuration_revisions`、catalog 落库去重等多条关键路径依赖，**删掉审计行就能让已消费的 operation_key 重新可用**，当时是与 `restore-backup.mjs --force` 组合形成“不需要改代码的伪造通道”。这份迁移只加了 `BEFORE DELETE`/`BEFORE UPDATE` 触发器——**它防的是通过正常 SQL 连接删行**。而“共享同一个文件”把攻击面从“改代码”扩大到“**任何一个能碰到该文件路径的进程**”：第二套应用只要以不同的 `journal_mode`/`synchronous` 打开（`src/server/platform/db.ts:52-56` 是唯一的 PRAGMA 收口，新应用若不 import 它就会各写各的），或者用 `VACUUM INTO`/整库替换实现自己的“初始化”，就能绕过触发器改写 `operation_records`。

另外，`db.ts:1-10` 明确写着「本文件由『基础组』拥有，**其他模块不得自行 `new Database(...)`**」。方案的“共享数据库”必然产生第二个 `new Database` 入口，等于主动破坏这条纪律。

**后果**
- `0042_audit_immutable.sql:1-27`：审计不可变从“库强制的硬约束”退回“应用自律”，幂等去重（`UNIQUE(action_type, operation_key)`，见 `src/server/modules/identity/admin.ts:21-26`）随之可被重放攻击绕过。
- `src/server/platform/db.ts:1-10`、`:52-56`：唯一连接工厂与 PRAGMA 收口被绕过；`foreign_keys=ON`（`db.ts:57-62` 有断言）在第二个进程不一定成立。
- `src/server/platform/migrate.ts:85-100` + `docker/compose.yaml:26-38`：并发迁移无锁，`dsh:migration-transaction=off` 期间的数据完整性无人负责。
- `scripts/restore-backup.mjs:117-124`：恢复与线上写入互踩，静默丢数据。
- `src/app/api/_lib/context.ts:22-24` / `identity/service.ts`：并发写者使“每次从库读角色”的读取结果与撤销动作之间可能被另一进程的旧事务覆盖。

**建议**
1. **不要共享 SQLite 文件**。若必须共享状态，正确做法是让 SQLite 继续只被**一个**拥有者进程持有（维护进程/迁移进程唯一），后台应用通过**受控接口**访问，而不是直连文件。
2. 如果评审方坚持共享文件（我不建议），方案必须至少补齐：
   - 迁移的唯一执行者不动（沿用 `compose.yaml:26-38` 的约定），后台应用**只读打开**（`db.ts:20-22` 已有 `readonly` 选项），所有写操作走主站接口；
   - 明确 `journal_mode`/`synchronous`/`busy_timeout` 由 `db.ts:52-56` 单点决定，第二进程强制 import 该工厂，禁止自带 PRAGMA；
   - 备份/恢复流程加**跨应用排他**（恢复前要求两侧停机或被单点锁串行化），并说明 `0042` 的不可变保证在恢复期间如何不被破坏。
3. 无论哪种，方案里必须写明“审计不可变（`0042_audit_immutable.sql`）在新部署形态下由谁保证、如何验证”——这是既有文档里已经吃过一次亏的地方，不能默认沿用。

### ③ 方案第 1 节「后台路由迁到 `admin.example.com`」——中高危：入口假定的信任边界被拆开，且 `role` 判定的“host 无关性”无人验证

**问题**
现有部署的信任边界全部写在 `docker/compose.yaml` 里：

- `compose.yaml:47-49`（web）与 nginx 段：web **不发布端口**，只由 nginx 反代；`nginx` 是「**唯一对外入口**」（`compose.yaml:3`）。
- `compose.yaml:51-52`：因为前面只有 nginx，所以 `DSH_REVIEW_TRUST_PROXY: '1'`；注释明确「直接把 web 端口发布到公网时必须改成 0（否则客户端可伪造 X-Real-IP）」。
- `src/server/platform/client-ip.mjs:1-13`、`:56-72`：真实 IP 只在 `trustProxy` 时才读 `X-Real-IP`/`X-Forwarded-For`，否则只用 TCP 对端地址。这份逻辑直接喂给频控（`src/server/platform/rate-limit.ts` 的键为 `<动作>:<userId>`，见文件头 `:1-12`）和日志。

新增独立应用 + 独立域名，意味着**多一个对外入口、多一处 `trustProxy` 开关、多一份 `/api/health`**。方案里完全没有提到这些。若新入口没有承接 `compose.yaml:51-52` 的约束，`X-Real-IP` 就被客户端掌控——后果是频控键可被伪造（对后台尤其危险：后台接口的频控若按 IP 计，则攻击者可无限换 IP 规避），审计日志里的 `client_ip` 也不再可信。

同样未被提及的是**管理面暴露面**：`src/app/admin/page.tsx:61-80` 目前把“谁在什么情况下能进后台”写成页面内联判断，非管理员看到的是提示文案；`src/app/api/admin/**` 有 17 个子路由。把后台搬到公网独立域名后，这些路由从“站内深链接”变成“可直接枚举的独立攻击面”，而方案没有任何**网络层收敛**（如仅允许内网/VPN/固定 IP 段访问）的表述。

**后果**
- `docker/compose.yaml:47-52`：`trustProxy` 的成立条件（唯一入口 + 不发布端口）在新部署下不再被保证，`client-ip.mjs:56-72` 的输入变为不可信。
- `src/server/platform/rate-limit.ts:1-12`、`:24-33`：频控键虽以 `userId` 为主，但后台若引入按 IP 的限流（登录尝试最常见），IP 可伪造会让这类限流形同虚设。
- `src/app/admin/page.tsx:61-80` + `src/app/api/admin/**`（17 个路由）：管理面暴露到公网且无网络层收敛，仅靠 `context.ts:46-54` 的代码校验兜底；而第 ① 条正说明这份校验在拆分后并不可靠。

**建议**
1. 方案必须补一节「信任边界」：明确后台应用的对外形态，并逐条对应 `compose.yaml:47-52` 的约束——**不发布端口、唯一入口、`trustProxy` 只在可信反代后开启**；新入口若直连公网，必须写明 `DSH_REVIEW_TRUST_PROXY=0`。
2. 后台管理面**加网络层收敛**（内网/VPN/固定 IP 白名单），不要依赖代码校验作为唯一防线；这一点在方案里应作为验收项，而不是部署细节。
3. 明确后台接口的频控与登录尝试限流口径，以及 `X-Real-IP` 由谁覆盖写入（`client-ip.mjs:59-61` 的约定是“我们自己的 nginx 覆盖写入”，新入口必须遵守同一条约定）。

### ④ 横向缺失：方案没有任何“凭据边界”与“验收证据”的表述

**问题**
独立应用部署必然产生新的凭据面：OAuth 客户端（`0003_auth_media.sql:13-32` 的 `oauth_login_challenges` 以 `state_digest`/`browser_binding_digest` 绑定浏览器、`return_path` 用 `CHECK (return_path LIKE '/%' AND NOT LIKE '//%')` 防开放重定向）、`BOOTSTRAP_ADMIN_GITHUB_ID`（`identity/service.ts:88-110` 的引导管理员语义）、`DSH_REVIEW_INSECURE_COOKIES`（`session-cookie.ts:13-21`）。方案对**哪一侧持有 GitHub OAuth 回调、`state`/PKCE 挑战存哪张表、`return_path` 白名单是否扩到第二个域名**只字未提。

特别是 `return_path` 的约束：`0003_auth_media.sql:28-30` 只允许站内相对路径。若后台登录复用同一挑战表却回跳到 `admin.example.com`，要么把白名单放宽（放开重定向面），要么新开一张表（再断一条不变量）。这两种做法都需要在方案里显式拍板，不能留给实现者临场决定。

**后果**
- `0003_auth_media.sql:13-32`（尤其 `:28-30` 的 `return_path` 约束）：开放重定向防线可能被拆分方案放宽或复制出第二份不一致的实现。
- `identity/service.ts:88-110`：引导管理员语义在“两个应用各自部署”时可能被第二次触发或完全不触发，方案未定义归属。
- `session-cookie.ts:13-21`（`DSH_REVIEW_INSECURE_COOKIES`）：新应用若各自读取该变量，一处降级会导致跨站会话部分明文。

**建议**
1. 方案必须写明「登录与 OAuth 唯一归主站持有，后台不接触 GitHub 凭据」——这是第 ① 条建议的自然推论，也是最小暴露面。
2. 若确实要后台独立登录，则在方案中列清：`oauth_login_challenges` 归属、`return_path` 白名单的确定性变更（不接受通配符/绝对 URL）、`browser_binding_digest` 的跨 host 绑定方式。
3. 补齐验收证据清单：至少覆盖“撤销管理员后另一侧多久失效”“禁用账户后旧会话失效”“审计行删不掉（`0042` 在新形态下仍成立）”“`X-Real-IP` 伪造无效”“后台管理面公网不可达”五项，每项对应可执行的测试，而非文字承诺。现有仓库已有 `scripts/verify-*.mjs` 的先例，应当扩展而不是另起一套。

## 总体意见

**不通过（需要重做方案，而非补文档）。**

方案 19 行里没有任何一句涉及鉴权归属、凭据边界、迁移唯一性、审计不可变、信任边界——而这些恰好是本仓库已经用代码注释、迁移文件和事故复盘逐条钉死的地方：

- 鉴权：`identity/service.ts:1-16`、`platform/context.ts:16-18,46-54`、`api/_lib/context.ts:22-24`、`session-cookie.ts:13-21`
- 会话与撤销：`0001_baseline.sql:52-66`
- 迁移唯一性：`docker/compose.yaml:26-38`、`platform/migrate.ts:41-51,85-100`
- 连接收口：`platform/db.ts:1-10,52-56,57-62`
- 审计不可变（已被真实攻击利用过）：`0042_audit_immutable.sql:1-27`
- 恢复与伪造链：`scripts/restore-backup.mjs:117-124`、`scripts/backup.mjs:14-20`
- 真实 IP 与频控：`client-ip.mjs:1-13,56-72`、`rate-limit.ts:1-12`

拆分后台本身不是安全问题（“后台独立迭代”是合理目标），但本方案选择的三个手段（**共享 DB 文件**、**后台自建登录**、**新增对外入口**）恰好逐一踩在上述不变量上。按当前写法实施，最坏结果是：撤销管理员不生效、审计记录可被绕过、恢复操作静默丢数据——这三件事在这个仓库的历史上都已经发生过或被讨论过。

**建议的整改方向**（供方案作者重写时采纳）：
保持**单 DB 拥有者 + 单鉴权实现**，把“独立”限定在构建与界面层；后台的管理面用网络层（内网/VPN/白名单）收敛暴露面；登录/OAuth/会话/迁移/备份恢复的归属在方案中逐一明示，并为每一条给出可执行的验收证据。若这些边界不能保持，则应放弃拆分，改为在同一应用内做路由与模块的物理隔离——那能达成“独立迭代”的大部分收益，且不触碰本文列出的任何一条安全不变量。
