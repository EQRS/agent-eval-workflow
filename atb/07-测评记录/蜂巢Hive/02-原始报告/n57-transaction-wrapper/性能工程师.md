# 性能评审：`proposal.md`「把事务封装成 async 函数」

**结论：方案在当前技术栈上不可行，且性能上是倒退。** 不是风格问题——建议**拒绝**，或仅接受"改签名不改语义"的极小子集。

核心事实（已核实）：`src/server/platform/tx.ts:47-57` 的 `withTransaction` 建立在 `db.transaction()` 之上，`db.ts:5-7` 明确写"better-sqlite3 是同步驱动，等待会阻塞所属线程，因此业务事务保持短小"。提案把它换成 `db.exec("BEGIN")` + `await fn(tx)`，恰好把这个前提打碎。

---

## 问题 1：`await` 会把整个连接的事务窗口撑开，变成跨事件循环的长期写锁（最严重）

**① 哪部分** — proposal.md:24-34 的封装体。`BEGIN` 与 `COMMIT` 之间夹了一个 `await fn(tx)`。

**② 后果** — `tx.ts:10-12` 的纪律是"跨模块流程创建一次短事务"。一旦 `fn` 是真正的 async，`await` 处会把控制权交还事件循环，`BEGIN` 打开的写锁在**被挂起的整段时间里**一直持有：

- `db.ts:49` `busy_timeout = 5000`，`db.ts:46` `journal_mode = WAL`。WAL 下写锁是库级单写者：事务未提交期间，**所有其他请求的写操作**都会撞 `SQLITE_BUSY` 并同步阻塞至多 5s。better-sqlite3 是同步的，这个阻塞阻塞的是整个 Node 线程——不是"这个请求变慢"，是**所有请求一起变慢**。
- 只要 `fn` 里有一次网络/文件/`await import()`，锁持有时间就从"毫秒级 CPU"变成"毫秒到秒级 I/O"，P99 直接断崖。
- 这一点现有代码已经踩到并刻意规避了：`submit-review.ts:129-131` 写明"任务入队放在事务提交之后……better-sqlite3 的事务回调必须同步，而 tasks 的加载是异步的"，`submit-review.ts:295` 的 `await loadTasks(db)` 被硬挪到事务外。提案等于把这个已修复的坑重新挖开。

**③ 建议** — 不要改 `tx.ts` 的同步契约。若确实需要 async 编排，正确形态是**把 async 部分留在事务外**：

```ts
// 事务仍然是同步的同步，async 只在边界上
export async function transaction<T>(fn: (tx: SyncTx) => T): Promise<T> // fn 必须同步
```
即：允许外层 `await`，但**禁止** `fn` 内 `await`（用类型 `(tx) => T` 而非 `(tx) => Promise<T>` 卡死）。若业务真需要"await 中途写库"，应改成两段式：先收集数据 → 单次短事务落库。

## 问题 2：`db.exec("BEGIN")` 绕过 `db.transaction()`，丢失嵌套与重入保护

**① 哪部分** — proposal.md:25/28/32 直接手写 `db.exec("BEGIN")` / `"COMMIT"` / `"ROLLBACK")`。

**② 后果** — `tx.ts:47` 用的是 `db.transaction(() => ...)`，better-sqlite3 对该 API 提供**嵌套事务降级为 SAVEPOINT** 的能力。手写 `BEGIN` 没有这层：

- 任何"工作流调模块、模块内部也开事务"的组合（本项目有 22 个 `src/server/modules/*` 子模块 + 4 个 workflow，`workflows/` 下 4 个文件均 import `withTransaction`）第二次 `BEGIN` 会抛 `cannot start a transaction within a transaction`。这不是偶发——是**必然**，只要有一处复用就炸。
- 若改成 `BEGIN IMMEDIATE` 会立刻暴露该冲突；用裸 `BEGIN` 则退化成**延迟锁升级**：事务前半段是读锁，写到一半才升级为写锁，升级时若他人已持写锁 → `SQLITE_BUSY` 且 SQLite **不重试**（busy_timeout 对锁升级死锁无效），直接抛错。这在 WAL 下是高并发写入的经典退化路径。

**③ 建议** — 必须走 `db.transaction()`，不要手写 `BEGIN`。若需要 async 外壳，用 `const runner = db.transaction(fn); return runner()`，让驱动管理 SAVEPOINT 与锁语义。至少改用 `BEGIN IMMEDIATE` 并把重入检查显式化——但这是治标。

---

## 问题 3：失败路径的 `ROLLBACK` 本身可能抛错，掩盖原始异常且多一次 fsync

**① 哪部分** — proposal.md:31-33 的 `catch` 分支。

**② 后果** — `db.exec("ROLLBACK")` 在"事务已被 SQLite 自动回滚"（多数 `SQLITE_FULL`/`SQLITE_BUSY`/某些约束错误的默认行为）时会抛 `cannot rollback - no transaction is active`，把 `catch` 里的 `throw e` 顶掉，**真实错误丢失**。同时失败路径上每次多一次 `synchronous = FULL`（`db.ts:47`）的 fsync 往返。

**③ 建议** — 交给 `db.transaction()` 处理，它已内建正确的回滚判定。若坚持手写，`catch` 内需 `try { db.exec('ROLLBACK') } catch {}` 再 `throw e`。

---

## 问题 4：批量迁移 40 个迁移文件/多处调用点时，逐条 `exec` 的 fsync 成本

**① 哪部分** — proposal.md:36-37「把所有 withTransaction 调用点改成 await 风格」。

**② 后果** — `synchronous = FULL` + WAL 下每个 `COMMIT` 是一次 fsync。当前同步事务是"一次事务一批写"，改动本身不增加 fsync 次数；但**如果**改造成"每个 `tx.insert` 各自一个 await 事务"（await 风格很容易被这样误用），写 N 行就是 N 次 fsync。对比 `migrations/0031_plugin_import_batches.sql:24-40` 的 `batch_jobs`/`batch_job_items` 批量导入场景（`batch_type = 'plugin_import'`，清单可能上百条），这会从 1 次 fsync 变成上百次，导入耗时数十倍劣化。`0031:9-11` 还明确"处理是同步的（不排队）"——即在请求线程内逐条写。

**③ 建议** — 在方案里写死约束：**一个业务动作 = 一个事务**，禁止把循环体放进事务边界内。批量导入用单事务包多行 `INSERT`。

---

## 问题 5：异步化会让"事务内只做 CPU"的既有优化失效，且回归测试无覆盖

**① 哪部分** — proposal.md:39-41「预期：支持异步操作」——这是方案唯一的收益主张。

**② 后果** — 现有架构刻意把耗时工作放在事务外（`db.ts:5-7`、`tx.ts:10-11`、`submit-review.ts:3-4`"外部拉取与耗时计算一律在事务之外"）。"支持异步操作"**不是需求**，而是被设计明确排除的行为。引入后无任何性能收益，只有问题 1-4 的成本。此外 `tx.ts:32-38` 的 `makeTx` 用 `finished` 标记防"事务后继续写"，async 化后 `finally` 在 `await` 之后执行，标记时机与真实提交时机脱钩，容易写出"看似检查过、实则已提交"的写。

**③ 建议** — 要求提案方给出**可量化的性能目标**（目标 QPS、P99 写延迟、并发写者数）并附压测数据。没有数据就不该动这条路径。若目标是"代码更直观"（proposal.md:40），用纯重命名/类型别名解决，零成本，不要碰事务语义。

---

## 一句话建议

按 proposal.md:24-34 原样实施会造成**写锁长期持有 + 嵌套事务必炸 + 批量导入 fsync 爆炸**。建议改为：保留 `withTransaction` 的同步语义（`tx.ts:47-57` 不动），只在类型层面提供 `Promise` 外壳供调用点 `await`，并在 `Tx` 类型上禁止回调内 `await`。
