# 安全评审：n57 事务封装为 async

**评审对象**：`atb/tasks/n57-transaction-wrapper/environment/proposal.md`（41 行）
**结论**：**不建议按现方案实施。** 方案在手写的 `db.exec("BEGIN")` 上有两处 **安全级** 缺陷（事务边界失效 + 跨请求串号），且它要解决的问题（"支持异步操作"）在本仓库的架构里是被**明文禁止**的，不是待补的能力。

---

## 一、已核实的事实基线（先摆证据，避免凭空判断）

| 事实 | 出处 |
|---|---|
| 现有实现用的是 **better-sqlite3 的 `db.transaction()`**，不是手写 BEGIN | `src/server/platform/tx.ts:47-55` |
| 回调被**强制同步**，注释明文要求"必须是同步函数" | `tx.ts:41-46` |
| 事务内**禁止**网络/文件/Markdown 等异步副作用 | `tx.ts:7-9`；`db.ts:7-8`；`tx.ts:5` |
| `Tx` 是**受限句柄**，结束后访问 `tx.db` 直接抛错 | `tx.ts:14-38` |
| 单例连接（每进程一个） | `db.ts:70-78` |
| 连接上启用了 `defer_foreign_keys = ON`（commit 时才校验外键） | `db.ts:48-49` |
| 审计表**不可删不可改**，靠触发器强制 | `migrations/0042_audit_immutable.sql:17-27` |
| 审计去重靠 `UNIQUE(action_type, operation_key)`，一旦删行就能重放 | `0042:5-13`；`operations/service.ts:4-8` |
| 迁移器**刻意保留**单事务包裹，并专门解释 `PRAGMA`/事务的交互 | `migrate.ts:95-121`、`35-52` |

关键点：`tx.ts:41-46` 的注释说明"必须是同步"是**设计决策**，并非历史遗留。方案的"预期"栏（`proposal.md:39-41`）恰好把这条决策当成待修的缺陷。

## 二、问题清单（按严重度）

### 1. 【严重】手写 `db.exec("BEGIN")` 会静默丢失事务——失败的业务变更被留在库里
- **哪部分有问题**：`proposal.md:20-31` 的封装体，`db.exec("BEGIN")` / `db.exec("COMMIT")` / `db.exec("ROLLBACK")` 全是手写语句。
- **后果**：SQLite 对**已在事务中**再发 `BEGIN` 是**报错**（`cannot start a transaction within a transaction`）。而本仓库中事务是**可嵌套复用**的：`operations/service.ts:175` 会 `withTransaction(...)`，而 `roles/service.ts` 等模块在**已有事务**里调审计（`recordOperationInTx`，`operations/service.ts:143-149`）。换成新封装后，内层 `BEGIN` 抛错 → 被 `:28` 的 `catch` 吞进 `ROLLBACK` 分支 → 外层事务被**连带回滚**，但 `fn` 里已执行的部分写入**可能已发生**。更危险的是 `ROLLBACK` 在无活动事务时同样报错，异常会**遮蔽原始业务异常**（`:28-29` 的 `throw e` 被 ROLLBACK 抛出的错顶掉）。
  叠加 `db.ts:48-49` 的 `defer_foreign_keys = ON`：外键只在 **commit 时**校验。如果 `COMMIT` 因约束失败抛错而异常路径未被正确捕获，写入停留在一个**未提交也不确定**的边界上，`defer_foreign_keys` 的延迟校验语义直接失效。
  审计场景下这是**安全**问题：`0042:5-13` 明确"审计与业务变更必须同事务"，事务边界破了，就会出现**业务写入成功、审计行丢失**（或反之）——即不产生审计痕迹的变更。
- **建议**：**不要手写 BEGIN/COMMIT/ROLLBACK**。保留 `db.transaction()`（它自带嵌套保存点 `SAVEPOINT` 语义与正确的回滚，`tx.ts:47-55`）。若确需 async 外壳，只能作**外层调度**（先把异步副作用在下单前做完），事务体仍交给 `db.transaction()` 的同步回调。至少要补：无活动事务时 ROLLBACK 不得抛错、不得遮蔽原异常。

### 2. 【严重】async 回调期间让出事件循环 → 单例连接被其他请求写入，事务跨请求串号
- **哪部分有问题**：`proposal.md:24` 的 `await fn(tx)`。
- **后果**：better-sqlite3 是**同步**驱动且全进程**单例**连接（`db.ts:70-78`）。`await` 会让出事件循环，此时 Next.js 的另一个并发请求（`package.json:12` 起的 dev/start、`server.mjs`）可以**在同一条连接上**执行写入并 `commit`——写入直接落进**上一个请求尚未提交的事务**里。
  - 越权后果：A 用户的 `BEGIN` 未结束，B 用户的写入被 A 的 `COMMIT` 一起提交，**A 的回滚会连带撤销 B 的写入**。
  - 审计后果：`operation_records` 的 `UNIQUE(action_type, operation_key)` 去重（`0042:5-8`）在跨请求共享事务下会**串号**，B 的操作被误判为 A 的重放而**静默跳过**（`operations/service.ts:105-140` 的 replayed 路径）——即"操作已执行但无审计记录"的伪造窗口。
  这正是架构明文禁止的形态：`tx.ts:5` "不得各自提交独立事务后假装整体原子成功"、`db.ts:7-8` "不在事务内做网络请求"。
- **建议**：**async 事务在此架构下不可实现**，除非引入每请求独立连接（与 `db.ts:70-78` 单例设计冲突，属架构变更）。建议把方案目标改为**纯类型/人体工学改良**：保留同步回调，另提供 `transactionSync` 别名或把 `fn` 签名改为 `(tx) => T` 的重载，彻底去掉 `await`。

### 3. 【高】`Tx` 的"事务结束后禁止使用"防护被 async 化绕过
- **哪部分有问题**：`proposal.md:22-31` 直接复用了 `Tx`，但没处理 `finished` 标记。
- **后果**：现有 `makeTx`（`tx.ts:20-38`）靠 `markFinished()` 在 `finally` 里置位，并用 **getter** 拦截 `tx.db`。async 回调一旦把 `tx` 捕获进闭包（`setTimeout`、未 await 的 Promise、`p-limit` 排队任务），事务早已 commit/rollback，而**闭包里的 `tx` 仍可发起写入**——`finished` 只在属性访问时校验，无法撤销已逃逸的引用。现有同步设计靠"同步回调无法逃逸引用"这一性质兜底；async 化直接**摧毁了这个不变量**。
  `proposal.md:39-41` 还把"支持异步操作"列为**预期收益**，等于主动打开了逃逸通道。
- **建议**：不要提供 async 回调签名。若必须，`tx` 需改为**一次性令牌**（用后置 `null` 并让所有方法在闭包内校验），且加回归测试：事务结束后从闭包内写库必须抛错。

### 4. 【中】全量改造调用点，会顺带削掉审计与幂等路径的保护
- **哪部分有问题**：`proposal.md:33-34` "把所有 withTransaction 调用改成 await 风格"。
- **后果**：`operations/service.ts:175` 是审计写入的统一入口，`resolveDb()`（`:40-48`）刻意同时接受"`tx` 句柄"与"裸 `SqliteDatabase`"两种形态，以便与业务变更同事务。把它改成 async 后，`record()` 的 `await` 位置稍有偏差就会让审计**跑在另一个事务**（`:171-174` 的 `withTransaction` 分支）。且 `0042` 的触发器（`0042:17-27`）只保证行不被改/删，**不保证行被写**——漏写审计不会被数据库发现。
- **建议**：审计路径**保持同步**（`recordOperationInTx`, `operations/service.ts:143-149` 就是为此存在的）。改造清单里**显式排除** `operations/service.ts`，并加测试断言"业务失败时审计行不增加、业务成功时审计行必增"。

### 5. 【中】方案未提 `PRAGMA` / 迁移器的既有事务交互
- **哪部分有问题**：`proposal.md` 全文无一处提及 `busy_timeout`、`defer_foreign_keys`、或迁移器的 `dsh:migration-transaction=off` 逃生口。
- **后果**：`migrate.ts:35-52` 与 `:98-121` 清楚记录：`PRAGMA foreign_keys` **在事务内是空操作**，而 `0007_task_type_plugin_discovery.sql` 依赖"事务外关外键再重建表"。若新封装被复用到迁移/维护脚本路径（`db.exec` 全局替换的诱惑很大），该迁移会在**外键仍开启**的状态下重建表而失败，或更糟：**半成品 schema**（`migrate.ts:102-104` 明确警告"执行器不替它回滚"）。
- **建议**：方案应写明新封装**仅限业务写路径**，禁止用于 `migrate.ts`、`scripts/*.mjs`；并在 `tx.ts` 头注释补一条"迁移/PRAGMA 场景不得使用"。

### 6. 【中】"支持异步操作"与能力边界不符，易诱导出跨事务外部调用
- **哪部分有问题**：`proposal.md:41` 预期"支持异步操作"。
- **后果**：一旦回调可以 `await fetch(...)`，就会出现"事务已 BEGIN，正等外部网络返回"的窗口——SQLite 是**库级写锁**，长事务期间全体写入被阻塞至 `busy_timeout = 5000`（`db.ts:56`）后失败。这既是可用性问题，也是**安全**问题：攻击者可用慢外部依赖制造写锁耗尽（DoS），且失败后 `ROLLBACK`（`:28`）可能再次报错，形成**写入落库但未审计**的缝隙。
- **建议**：明确否定该预期。外部调用必须在事务**之前**完成（`tx.ts:7-9` 已有此纪律），方案应保留而非推翻。

---

## 三、总体建议

1. **拒绝 async 事务体**：与单例同步驱动（`db.ts:70-78`）、受限句柄（`tx.ts:14-38`）、审计同事务（`0042:5-13`）三条硬约束同时冲突。
2. 若目标只是"更直观"，采用**低风险替代**：
   - 保留 `db.transaction()`，把 `withTransaction` 的 `fn` 类型放宽为同步泛型，提供 `tx.insert/tx.update` 这类**同步语法糖**（`proposal.md:13-15` 想要的写法可同步实现）；
   - 或在调用点用 ESLint 规则禁止 `withTransaction(async …)`。
3. 无论如何**不要手写 `BEGIN/COMMIT/ROLLBACK`**（问题 1），也**不要全局替换**（问题 4、5）。
4. 若坚持推进，最低限度补三组测试：嵌套事务、事务内抛错、并发两请求交错写入（验证不串号）。
