## 性能工程师评审：n27-webhook-delivery

先说结论：**方案在性能上不可接受**。它在当前架构里同时打破了三条已书面化的关键约束（同步事务、单连接、全站并发上限），并且漏掉了唯一能兜住外部调用的现有设施 `background_tasks`。以下引用均基于实际读到的文件。

---

### 1. 把 `await fetch` 放在插件更新路径上，违反同步事务约束

**问题**：`proposal.md:22-27` 直接 `await fetch(...)`。

**后果**：
- `src/server/platform/tx.ts:39` 写明“传入的回调**必须是同步函数**”，`withTransaction` 内部是 `db.transaction()`（`tx.ts:44`），better-sqlite3 的同步事务无法让出事件循环。
- `src/server/platform/db.ts:8` 更是直接禁止：“**不在事务内做网络请求**”。
- 若放进更新事务：`fetch` 的 await 期间事务保持打开 → WAL 写锁被持有 → 同一连接上所有其他写入排队，`busy_timeout` 默认仅 5000ms（`db.ts:63`），超过即报 SQLITE_BUSY。**实现上做不到**：同步回调里无法 await；硬把 await 挪出事务，则事件投递与更新提交脱钩，进程崩溃就永久丢事件。

**建议**：更新事务内**只做一次 INSERT**，写入 `background_tasks` 一行（`task_type` 新增 `webhook_delivery`），事务提交即返回；真正的 HTTP 调用放到 worker 进程里执行。这正是 0008 迁移注释里预告过的做法：“将来要加邮件/推送，**再补事件层与投递任务**”。

---

### 2. 一次性 `fetch` 全部订阅者 = 无界并发 + 无超时

**问题**：方案第 2 节只描述了“POST 到订阅的 URL”，完全没有涉及并发与超时，也没有提及从订阅表出发的查询方式。

**后果**：
- 单个插件更新要遍历该插件的**全部**订阅者。若某作者有 N 个订阅者，就是 N 次串行或并发外部调用，耗时随 N 线性增长。
- `fetch` 默认没有超时。第三方挂一个只建立连接、不响应的服务器，就能让投递页面或 worker 线程**永久挂起**。当前唯一的上限是 `TASK_DEADLINE_MS = 300s`（`tasks/constants.ts:52`），而这是最后保底手段，无法充当超时控制，并且到时会连带把整条任务判为失败。
- 慢消费者会把投递积压转成内部资源占用，这属于典型的**外部依赖反向压力**。

**建议**：为每一次投递设置显式超时（例如 5s，用 `AbortSignal.timeout()`），并将**每个订阅者拆成一条独立任务**，而不是一条任务内循环 N 个 URL。单个订阅者的故障要能独立重试、独立失败，不能因为一个慢 URL 拖垮整批。

---

### 3. 重试语义与现有队列不一致，且“3 次”会叠加成 9 次

**问题**：`proposal.md:31` 只写“失败重试 3 次”，没有定义退避、并发上限和终态。

**后果**：
- 现有队列语义是 `MAX_RECOVERABLE_ATTEMPTS = 3` **每个 retry_cycle 内**（`tasks/constants.ts:34-39`），退避 `[30s, 120s]`（`constants.ts:47`）。若在任务里自行再写一层“重试 3 次”的循环，会与外层 `retry_cycle` 相乘，实际最坏 **3×3=9 次**外部请求，且每次都可能是 5s 超时，一条任务就可能耗尽 `TASK_DEADLINE_MS`。
- 无退避的立即重试，面对已经宕机的第三方就是**重试风暴**：3 次密集请求会把对方的恢复窗口一并打掉。

**建议**：**不要自己实现重试**。由 `nextAvailableAt()`（`constants.ts:64`）统一给出退避与上限，投递失败就 `finish({outcome:'error'})`，让队列调度下一次尝试。语义与站内其他任务保持一致，测试也能复用。

---

### 4. 订阅表缺少必要索引

**问题**：`proposal.md:10-17` 的 `webhook_subscriptions` 只有 `PRIMARY KEY (id)`，没有任何索引。

**后果**：
- 投递时要按插件查订阅者，而表里**没有 plugin 维度字段**，只有 `user_id`，这本身就是模型缺陷；即便退化为按 `user_id` 查询，也没有索引，会全表扫描。
- 对照同类订阅表 `featured_subscriptions`（`0034:20-23`）直接以 `user_id` 作主键，`notifications` 也明确建了 `idx_notifications_inbox`（`0008:37`）。本方案的索引密度明显低于项目既有标准。
- 订阅量增长到万级后，每次插件更新都要全表扫描一次，会与 WAL 写入互相加剧锁竞争。

**建议**：补上索引，并把订阅粒度写清楚，即订阅具体插件还是订阅全部更新。若按插件订阅，则需要 `plugin_id` 并建 `(plugin_id, user_id)`；若是广播式订阅，则至少要有 `UNIQUE(user_id)` 防止同一用户重复投递。

---

### 5. 全站并发上限 4，会被 webhook 投递直接占用

**问题**：方案没有说明投递任务使用哪个 `scheduling_group`。

**后果**：`MAX_CONCURRENT_TASKS = 4`（`constants.ts:19`）是全站共享的。webhook 属于**慢速、外部依赖不可控**的任务，如果与 `review_publish`、`comment_publish` 混用同一调度组，一次 webhook 集中投递就会占满 4 个槽位，导致**用户发布评测和评论的延迟显著上升**，而且这类请求直接面向用户，用户能感知到。

**建议**：为 webhook 单独设置 `scheduling_group`，并明确它是否有独立的并发额度。至少要在队列里做到“外部投递不阻塞站内主流程”，必要时降级为低优先级组。

---

### 6. 每次投递都重新构造订阅列表与 JSON 序列化

**问题**：方案没有提到是否对每个订阅者重复 `JSON.stringify(event)`（`proposal.md:25`）。

**后果**：N 个订阅者 N 次序列化同一份事件。这本身开销不大，但叠加在第 2 条的无界并发上，会放大单次更新路径的 CPU 占用与内存峰值，而 better-sqlite3 是同步驱动（`db.ts:8`），CPU 占用会直接表现为写事务排队时间变长。

**建议**：事件体只序列化一次，复用同一个字符串；若事件体较大，考虑存一份到表里，投递任务只持引用（`payload` 已强制 `json_valid`，见 `0007:33`）。

---

### 补充：与 0008 迁移的既有设计保持一致

`0008_notifications.sql:9-14` 已经明确写下取舍：不做 `business_events`/`event_delivery_tasks` 那一整层，理由正是“**将来要加邮件/推送，再补事件层与投递任务，不必现在建三张空表**”。现在要加 webhook 了，方案理应对照这段说明补上投递任务层，而不是在请求路径上直接发起网络调用。缺失这一层，是上述所有性能问题的共同根因。

**最小修订方向**：更新事务只写任务行 → 每个订阅者一条任务 → 复用现有退避与租约 → 显式超时 → 独立调度组低优先级 → 补索引。
