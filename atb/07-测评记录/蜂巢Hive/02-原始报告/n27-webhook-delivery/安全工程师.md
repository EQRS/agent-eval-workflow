# 安全评审：n27 Webhook 推送方案

评审对象：`atb/tasks/n27-webhook-delivery/environment/proposal.md`（全文 37 行）
核实依据：`migrations/0008_notifications.sql`、`0042_audit_immutable.sql`、`src/server/platform/{db,rate-limit,file-store,session-cookie}.ts`、`src/server/adapters/catalog/github-probe.ts`、`src/server/modules/{notifications,operations,tasks}`、`src/worker/{main,handlers}.ts`

结论：**不接受现状**。方案的核心风险不是“webhook 怎么写”，而是它把一个**可从用户输入直接驱动服务器出网的能力**（SSRF）和**一份明文存储的签名密钥**塞进了现有代码里最需要克制的地方。以下按严重度排列。

---

## P0-1 SSRF：`url` 完全由用户控制，方案没有任何出站校验

**① 哪部分有问题**
proposal.md:11 的建表语句 `url TEXT NOT NULL` —— 只有类型，没有长度、没有协议前缀、没有主机白名单；proposal.md:26-30 的推送代码 `await fetch(sub.url, ...)` 把库里这串字符**原样**交给 fetch。

**② 后果**
用户填 `http://127.0.0.1:3000/api/admin/...`、`http://169.254.169.254/latest/meta-data/`、`http://10.x.x.x:port/`、`http://[::1]/`、`http://<内网主机名>/` 时，推送动作会由 **worker 进程**发起（worker 与 Web 同机同容器，见 `src/worker/main.ts:1-10` 的“独立进程”但共享 `.data` 与网络命名空间）。项目现有的出网纪律是“地址由服务端拼、主机是常量”：

- `src/server/adapters/catalog/github-probe.ts:69`：`const API_BASE = 'https://api.github.com'` 是**硬编码常量**，用户只能影响 `encodeURIComponent` 后的 owner/repo —— 这是本项目唯一被允许出网的地方，且它刻意不接受 URL。
- 对照 `src/server/platform/file-store.ts:5-9` 的写入铁律（“storage_key 由服务端生成，绝不用用户提供的文件名拼路径”）—— 同一个“用户可控串不能直接进系统调用”的原则，本方案在出网方向上完全放弃了。

后果具体化：worker 能访问的**全部**内网与回环服务都变成用户可达的盲探接口。即使 POST 不带认证，`fetch` 的错误/超时/连接成功与否本身就是端口扫描信道；若目标接受 JSON POST 且无 CSRF 防护，则是一次真实的写操作。加上 P0-2 的重试机制同样落在内网，等于给攻击者一个自动重放的打点器。

**③ 建议**
- 库层：`url TEXT NOT NULL CHECK (length(url) BETWEEN 9 AND 2048 AND (url LIKE 'https://%'))` —— 只放行 `https`（生产不应让服务器向明文 HTTP 发事件正文）。
- 服务层**保存前**必须做：URL 解析 → 拒绝非 443 自定义端口（或白名单）→ 解析出 IP 后拒绝私网/回环/链路本地/CGNAT/组播/保留段（`10/8`、`172.16/12`、`192.168/16`、`127/8`、`169.254/16`、`100.64/10`、`::1`、`fc00::/7`、`fe80::/10` 以及 IPv4-mapped 形式）。
- **更关键：在投递那一刻再校验一次**。DNS rebinding 会让“保存时解析到公网、投递时解析到 127.0.0.1”。做法是自己 `dns.lookup` 拿到 IP → 校验 → **用该 IP 建立连接并保留 Host 头/SNI**，不要“校验一个域名再 fetch 同一个域名”。
- 禁用 `redirect`：`fetch(url, { redirect: 'error' })`，否则一个 302 到 `169.254.169.254` 就绕过了前面所有检查。
- 出站只允许 443，禁止跟随协议变更（https→http）。

## P0-2 重试不是“3 次”：没有超时、没有响应体上限、没有总预算

**① 哪部分有问题**
proposal.md:33 全文只有一句“失败重试 3 次”。proposal.md:26-30 的 `fetch` 没有 `signal`、没有 `AbortSignal.timeout`、没有读取响应体。

**② 后果**
三件事叠在一起，会把 worker 拖死：

1. **无超时 = 无限挂起**。对照 `github-probe.ts:70` 的 `DEFAULT_TIMEOUT_MS = 15_000` 和 `github-probe.ts` 中 `get()` 的 `AbortController` + `setTimeout`/`clearTimeout` 结构——本项目对外请求有既定纪律，本方案一条都没写。一个只接受连接不发响应的地址会让 `fetch` 永久 pending。
2. **这会直接击穿现有租约机制**。`src/server/modules/tasks/constants.ts:24` 的 `LEASE_DURATION_MS = 120s`、`:27` 的 `RENEW_INTERVAL_MS = 30s`、`:41` 的 `TASK_DEADLINE_MS = 300s`。若 webhook 在任务的 handler 里同步 await（`src/worker/handlers.ts:1-40` 的注册表模式），一个挂起的 fetch 会让任务超过 300s 被 `recoverExpired` 回收，另一 worker 领走后**再推一遍** —— 而用户的 URL 是同一个挂起地址，于是形成“回收→重推→再挂起”的活锁。`MAX_CONCURRENT_TASKS = 4`（constants.ts:20）意味着 4 个恶意 URL 就能让整个 worker 停摆，连带评论发布、内容筛查全部停掉。
3. **响应体不读不丢弃**。攻击者返回一个 10GB 的 body，连接池与内存都会被吃。

另外 `src/server/platform/db.ts:6-9` 明确写着“better-sqlite3 是同步驱动…**不在事务内做网络请求**”。方案没有说明投递点在事务内还是事务外。若照 `0008_notifications.sql:8-12` 那种“投递与发布同事务”的既有做法照搬，就是**在 WAL 写事务里 await 网络**，直接违反该文件的成文规则，并把写锁持有时间拉到秒级。

**③ 建议**
- 明确写出：`AbortSignal.timeout(10_000)`；`redirect: 'error'`；`response.body?.cancel()` 或只读前 N 字节；单次尝试上限 < 10s。
- 重试必须**异步化**：投递点只做 `INSERT` 一条投递记录（在业务事务内），实际 POST 由 worker 的独立任务类型消费，走现有 `nextAvailableAt`（constants.ts:59）的 `[30s, 120s]` 退避，不要自己再造一套“3 次”。同时给 webhook 任务一个**独立于发布事务**的总预算。
- 明确写出投放点在事务**之后**，并补一条测试：webhook 目标不可达时，评论发布/插件更新本身仍然成功。

## P0-3 `secret` 明文入库，且方案里根本没有“签名”

**① 哪部分有问题**
proposal.md:9 `secret TEXT NOT NULL`；proposal.md:26-30 的请求头只有 `content-type`。

**② 后果**
两件事：

1. **字段存在但未被使用，等于给了错误的信任感**。方案把 `secret` 建进表却不在发送路径上用它，接收方没有任何办法区分“真事件”和“任何人向这个 URL 发的 POST”。这是 webhook 设计的核心安全属性，缺失即等于把接收方暴露在伪造事件下——如果第三方依据 webhook 做发币/发货/权限变更，这是可直接变现的漏洞。
2. **`secret` 是明文列**。本项目对同类凭证的既定口径是**只存摘要**：`migrations/0001_baseline.sql:57` 的 `token_digest TEXT NOT NULL CHECK (length(token_digest) = 64)`，配合 `src/server/platform/digest.ts:27` 的 `digestText()`（SHA-256）。但 webhook secret 有个区别：**签名需要明文（HMAC 的密钥），不能存哈希**。这意味着它比会话 token 更敏感——一次库泄露（备份、`backups/`、`.data/`）就是全部订阅方共享密钥泄露。而 `0042_audit_immutable.sql:3-15` 的教训正是“备份/整库覆盖是真实威胁面”。

**③ 建议**
- 发送路径必须带签名：`X-DSH-Signature: t=<unix秒>,v1=<hex>`，`v1 = HMAC-SHA256(secret, t + "." + rawBody)`，时间戳参与签名并让接收方能拒绝 >5 分钟的旧事件（防重放）。**必须签原始字节**，所以 body 要先 `JSON.stringify` 成字符串再签再发（proposal.md:29 目前是 `JSON.stringify(event)` 内联进 fetch，无法先签，需要把 body 提出来）。
- 用 `crypto.timingSafeEqual` 校验（若做接收侧）；key 用 `randomBytes(32)` 生成。
- 明文存储就如实承认，并配环境变量级密钥（如 `DSH_REVIEW_WEBHOOK_SECRET_KEY`）做应用层加密，或至少在文档中写清“此列等同凭证，导出/备份必须与之同等定级”；同时在表上限制可读面（见 P1-2）。
- 若允许用户自带 secret，`CHECK (length(secret) >= 32)`，避免 `secret='1'`。

## P1-1 缺少投递审计与去重，`0042` 的教训在这一层被重复

**① 哪部分有问题**
方案通篇没有投递记录表，没有 `operation_records`，没有 `deduplication_key`。proposal.md:16-22 只有订阅表，proposal.md:26-30 只有一次裸 fetch。

**② 后果**
- **无法证明发过什么**。`migrations/0042_audit_immutable.sql:3-15` 刚刚把“审计行可删”定为安全缺陷并加了 `trg_operation_records_no_delete`。webhook 是**跨组织**的数据出口：它把插件更新事件送出站。没有任何不可变的投递记录，意味着事后无法回答“某次更新是否被推给了哪个第三方”“推的内容里是否含未公开字段”。审计缺口在出站方向上比入站更严重。
- **重复推送**。“失败重试 3 次”没有幂等键。重试与“任务被 `recoverExpired` 回收后重跑”叠加（见 P0-2），接收方可能收到同一事件的多次投递且**无法识别**——项目在 `0008_notifications.sql:16` 已经用 `UNIQUE (deduplication_key)` 解决过同类问题，并在 `0008:19-22` 写明“并发下两个发布任务同时跑也不会插出两条”，本方案退回了应用层“先查后插”的等级。
- **没有 `UNIQUE (deduplication_key)` 的事件载体**，也就没有办法做“至少一次 + 接收方幂等”的标准契约。

**③ 建议**
- 增加 `webhook_deliveries(id, subscription_id, event_id, deduplication_key UNIQUE, payload_digest, attempt_no, status, response_status, error_code, created_at)`，投递尝试写入即不可改（同 0042 的触发器口径）。
- 事件侧定义 `event_id`（UUIDv7，`src/server/platform/id.ts:26`），请求头带 `X-DSH-Event-Id`，重试**复用同一个 event_id**，让接收方可以去重。
- 事件落库后才投递，用 `payload_digest`（复用 `src/server/platform/digest.ts:21`）证明“发出去的就是库里那条”。

## P1-2 订阅表缺所有权约束与权限边界

**① 哪部分有问题**
proposal.md:6-13。`user_id TEXT NOT NULL REFERENCES users(id)` 之外没有任何东西：没有唯一约束、没有数量上限、没有 `enabled` 列、没有修订/轮换字段，也没有说明谁可以创建（普通用户？开发者？管理员？）以及是否要限制在“已 verified 的插件归属人”（对照 `migrations/0040_user_roles.sql` 的 `uq_plugin_ownerships_verified` 局部唯一索引）。

**② 后果**
- **事件面失控**。“插件更新”事件的内容如果包含未发布/已下架的插件信息，任何注册用户都能订阅到，等于把 `notifications` 那套“公开后才发”的收件人判定（`src/server/modules/notifications/index.ts:1-12`：`resolveRecipient()`、只在 `publishComment` 事务里投递）整体绕过。方案没有定义事件载荷字段，也就没有回答“订阅者凭什么能看见这条更新”。
- **放大 P0-1/P0-2**：没有每用户订阅数量上限，一个账号可以注册 N 个内网 URL，把 worker 的四条并发槽全占满。这正是 `src/server/platform/rate-limit.ts` 要解决的问题，但该文件的 `RateLimitAction` 联合类型（rate-limit.ts:52-61）里没有 webhook 相关动作，方案也没提要加。
- `secret` 无轮换：泄露后只能删行重建，中途事件会丢。

**③ 建议**
- 建表补：`UNIQUE (user_id, url)`（防同一 URL 重复注册放大）、`enabled INTEGER NOT NULL DEFAULT 1 CHECK (enabled IN (0,1))`、`secret_rotated_at`、`disabled_at/disabled_reason`。
- 明确写入“只有持有该插件 `verified` 归属权的用户才能订阅其更新事件”或“事件载荷只含已公开字段”，二选一，写进文档。
- 每用户订阅数上限（如 5），并在 `rate-limit.ts` 的 `RateLimitAction` 增加 `webhook_subscription` 档。
- 补一条校验：`url` 变化视为新订阅（重置失败计数与退避），否则用户可以靠改 URL 把退避状态洗掉。

## P1-3 退避与自动禁用缺失 → 内网探测与放大器的持久化

**① 哪部分有问题**
proposal.md:33 “失败重试 3 次”。没有退避、没有熔断、没有自动禁用、没有失败计数清零条件。

**② 后果**
- 用户把 URL 指向内网某个**会响应但拒绝写**的接口，3 次失败后订阅仍然有效，下一次插件更新再打 3 次。这是一个**长期驻留的内网探测/放大器**，且没有运维可见的关闭开关（没有 `enabled` 列）。
- 与 P0-1 结合：攻击者无需持续操控，只需注册一次，之后每次插件更新（可能是全站高频事件）都会替他打内网。
- 项目既有口径：`github-probe.ts:250-256` 把网络错误与“仓库不存在”严格区分（“绝不用远端文案冒充本地判定”），`rate-limit.ts:33-38` 承认固定窗口的实际偏差并写清。本方案“失败重试 3 次”一句话，没有任何端口可供运维判断“这个订阅是不是在打内网”。

**③ 建议**
- 指数退避（复用 `nextAvailableAt` 语义：30s → 120s → …，上限如 6h）。
- 连续失败 N 次（如 20）**自动 `enabled = 0`** 并写一条站内通知给订阅者（复用 `notifications` 模块的能力，注意 `0008_notifications.sql:31` 的 `CHECK (recipient_id <> actor_id)`——系统触发时 `actor_id` 的取值要设计好，现有表要求 `actor_id NOT NULL`）。
- 每次失败落日志时只记 `subscription_id` + 目标 host + 拒绝原因，**不要把内网 IP 与端口写进用户可见的地方**（信息泄露给攻击者做扫描结果回读）。这一点要在实现里显式确认。

## P2-1 表定义缺与本项目一致的 CHECK 口径

**① 哪部分有问题**
proposal.md:6-13 与项目所有既有迁移的风格不一致。

**② 后果**（逐条对文件）
- `id TEXT PRIMARY KEY` 没有约束形状。`0001_baseline.sql:7-8` 约定“ID = 规范小写 UUIDv7 的 TEXT”，`src/server/platform/id.ts:26` 生成。没有 `CHECK` 就意味着脏 ID 可入库，而审计与去重都靠 ID 串联（`operations/service.ts` 的 `operationDigest` 把 `target_id` 纳入摘要）。
- `created_at INTEGER NOT NULL` 没有 `CHECK (created_at >= 0)`。全库每一张表都有这条（`0001_baseline.sql:29`、`0008_notifications.sql:30`、`0040_user_roles.sql` 的 `granted_at >= 0`），缺失会让“时间戳异常”这条路在对账时静默通过。
- `user_id ... REFERENCES users(id)` 缺少 `ON UPDATE RESTRICT ON DELETE CASCADE`。全库统一写明（`0001_baseline.sql:37`、`0008_notifications.sql:23`、`0040_user_roles.sql` 对 `user_roles` 用 `ON DELETE CASCADE`）。不写就是默认 `NO ACTION`，用户注销路径会与全站其它表行为不一致 —— 而 webhook 订阅里存着别人拿不到的出站能力，**残留行比级联删除危险**。

**③ 建议**
照抄既有风格补 `CHECK`/`ON DELETE CASCADE`，并加 `CHECK (instr(url, '?') = 0 OR ...)` 之类若需要（查询串里塞 token 会进日志）。

## P2-2 未定义载荷与脱敏

**① 哪部分有问题**
proposal.md:29 `body: JSON.stringify(event)` —— `event` 的形状、字段集合、脱敏规则全部未定义。

**② 后果**
webhook 是**出站数据出口**，比页面渲染的风险面更大：没有渲染层可以拦截。如果 `event` 里带了作者邮箱、内网路径、草稿内容、`operation_records` 快照，一次误配就是不可撤回的泄露（对方已收下，重试与审计都无法收回）。项目对同类问题的既定做法是 `markdown.ts:5-9` 的“必须经过 sanitize / 只允许固定媒体地址与安全外链”和 `github-probe.ts:100-110` 的 `asTextOrNull`（类型不符返 null、超长截断、空串当没有）——载荷构造应沿用同一套“白名单字段 + 截断 + 不猜”的纪律。

**③ 建议**
- 在方案中把事件 schema 逐字段列出，采用**白名单构造**（不是从行里 `SELECT *` 再删字段）。
- 明确禁止出现：用户邮箱、`token_digest`、内部 ID 之外的关联信息（如 `operation_records.target_snapshot`）、草稿/未发布内容。
- 加一条总大小上限并截断长字段（对照 `github-probe.ts:107` 的 `maxLength = 2000`）。

## P2-3 推送与日志的旁路泄露

**① 哪部分有问题**
方案没有提日志与错误暴露。

**② 后果**
`src/server/platform/log.ts` 是全站日志入口。若投递失败时把 `response.text()` 或请求体打进日志，第三方返回的内容会进日志；若把 `url`（可能带 `?token=...`）打进用户可见的错误页，等于二次泄露。另外 `PROPOSAL` 没说清 `secret` 是否会在任何 API 响应里回显——这是最常见的 webhook 实现事故。

**③ 建议**
- 日志只记 `subscription_id`、目标 host、状态码、`error_code`，不记 URL 全串、不记 body、不记响应体。
- 列表/详情接口对 `secret` 做**只读掩码**（`****`+末 4 位），轮换只返回一次明文。
- 错误信息遵循 `github-probe.ts:266-270` 那套“不给额外信息”的口径。
