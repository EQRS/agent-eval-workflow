# 安全评审：插件归属争议申诉流程

**结论：不建议按现方案实施。** 方案共 30 行，其中“任何用户都可以对任意插件提出归属争议”和“管理员直接改归属人”两条，直接绕过了现有 schema 中已经设计好的唯一性、审核痕迹和审计约束。下面每条都附实际读到的文件行号。

## 1. 审计缺失：改归属不写 `operation_records`

**问题部分**：方案 §3「管理员查看证据后，直接改 `plugin_ownerships` 的归属人」（proposal.md:26）。

**后果**：

- 现网 `operation_records` 是全站审计的唯一载体，0042 迁移明确它是“全站审计与幂等去重的唯一载体”，并已加 `BEFORE UPDATE`/`BEFORE DELETE` 守卫（0042_audit_immutable.sql:19-27）。
- 但现有变更归属的唯一路径 `reviewClaim` 是**纯 UPDATE，不调用 `recordOperationInTx`**（src/server/modules/roles/ownership.ts:311-385，整个 `reviewClaim` 函数体内没有任何 operations 模块调用；对比 operations/service.ts:150 明确说“审计必须与业务变更同事务（架构 §6.4）”）。
- 方案又在这个无审计的路径上叠加“改归属人”这个最高危操作。归属变更直接决定“开发者身份门槛”（ownership.ts:9-11，`countVerifiedForUser` 数 verified 数）。**改归属 = 改谁有开发者身份 = 改谁能发整合包**，而全过程零留痕。

**建议**：争议处理必须在**同一事务**内调用 `recordOperationInTx`，`actionType` 用 `ownership.dispute.resolve`，`targetSnapshot` 存改前归属行、`changes` 存改后，`reason` 必填。可以参考 operations/service.ts:150-160 的同步入口写法。

## 2. 「任何用户对任意插件提争议」= 无成本 DoS + 信息探测

**问题部分**：proposal.md:22「任何用户都可以对任意插件提出归属争议」。

**后果**：

- 表里**没有任何唯一约束**（proposal.md:10-18）：既没有 `UNIQUE(plugin_id, claimant_id)`，也没有部分唯一索引限制“同一插件只能有一条 pending”。对比同一代码库的成熟做法：0028 用 `CREATE UNIQUE INDEX uq_pack_appeals_pending ON plugin_pack_appeals(release_id) WHERE state = 'pending'`（0028_pack_appeals.sql:50-51），并在注释里写明理由“并发下两次提交也不会出现两条待审，管理员不会重复处理同一次申诉”（:20-22）。方案把这条经验整个丢掉了。
- 后果一：**管理员队列污染**。一个脚本对全站插件各提交一条争议，管理员队列直接不可用（`listQueue` 没有分页，ownership.ts:298-306）。
- 后果二：**per-user 速率无上限**。0028 那套还有 `message` 长度约束 `BETWEEN 5 AND 2000`（0028:37），方案里 `evidence TEXT` 完全裸奔（proposal.md:14）——无长度上限、无 `json_valid`。
- 后果三：`evidence` 是用户可控文本，后续管理员在后台查看时若不转义，即为存储型 XSS 入口。

**建议**：加 `UNIQUE INDEX uq_disputes_pending ON ownership_disputes(plugin_id, claimant_id) WHERE status = 'pending'`；`evidence` 加 `CHECK (length(trim(evidence)) BETWEEN 10 AND 5000)`；接口层加 per-user 每日配额（仓库已有 0006_rate_limiter.sql 可直接复用）；渲染侧统一转义。

## 3. 争议未处理期间的归属竞态：与 `uq_plugin_ownerships_verified` 冲突

**问题部分**：方案未定义“争议 pending 期间原归属人的权限态”，也未定义处理时的并发语义。

**后果**：

- 0040 有一个硬约束：`CREATE UNIQUE INDEX uq_plugin_ownerships_verified ON plugin_ownerships(plugin_id) WHERE status = 'verified'`（0040_user_roles.sql:118-119）。方案 §3 说“直接改归属人”，但没说是 UPDATE 原行还是 INSERT 新行——
  - 若 INSERT 新 verified 行：**撞唯一索引**，抛 SQLite 约束错误。ownership.ts:238-250 的注释已记录过同类踩坑（“直接 UPDATE 成 verified 就撞了部分唯一索引，errors-http 只映射 DomainError → 500”），结果是**管理员看到 500 而不是可理解的失败**。
  - 若把原行改成 rejected 再改新的：中间的 `status` 组合会短暂违反 0040:95-110 的 `CHECK (source = 'github_match' OR status <> 'verified' OR reviewed_at IS NOT NULL)` 与 `CHECK (status <> 'pending' OR reviewed_at IS NULL)` 蕴含式，需要精确的字段时序。
- 更严重的是**争议状态与原归属不同步**：争议表 `status`（proposal.md:15）与 `plugin_ownerships.status`（0040:92-93）是两套独立状态机，**没有任何跨表约束**保证“争议 overturned 时归属一定换了人”。会出现“争议已结案改判，但归属表没动”的分叉，双方各自的视图互相矛盾。

**建议**：在 `ownership_disputes` 上加 `resolved_by`/`resolved_at` 并用 CHECK 绑定（抄 0028:44-47 的 `CHECK ((state = 'pending') = (resolved_at IS NULL))` 写法）；处理时对 `plugin_ownerships` 走既有 `reviewClaim` 的 taken 预检（ownership.ts:243-249）以保证拿到 DomainError 而非 500；处理事务内先 `UPDATE` 原 verified 行为 rejected、再落新行，两步同事务。

## 4. `plugin_id` 外键未指定 `ON DELETE`，与全库口径不一致

**问题部分**：proposal.md:12-13
```sql
plugin_id     TEXT NOT NULL REFERENCES plugins(id),
claimant_id   TEXT NOT NULL REFERENCES users(id),
```

**后果**：

- 基线约定所有外键显式写 `ON UPDATE RESTRICT ON DELETE ...`（0001_baseline.sql:7 的约定段，以及全文件每个 REFERENCES 都带，例如 0001:40-41、0040:31）。
- 漏写 → SQLite 默认 `NO ACTION`，行为与 `RESTRICT` 在延迟语义下有差异，且**与 `plugin_ownerships` 的口径相反**：后者是 `ON DELETE CASCADE`（0040:86-87，`plugin_id ... ON DELETE CASCADE`）。
- 实际后果：插件被删时，`plugin_ownerships` 行级联消失，但 `ownership_disputes` 行**留下指向不存在 plugin 的孤儿**，方案 §1 的“争议有据可查”在插件删除场景下直接失真。

**建议**：`plugin_id ... ON DELETE CASCADE`（与 0040:86 对齐）；`claimant_id ... ON DELETE RESTRICT`（与 0040:87 的用户侧对齐）。

## 5. 缺 `resolved_at`/`resolved_by`/`resolution_note`，争议结论不可追责

**问题部分**：proposal.md:10-18 表定义只有 `id / plugin_id / claimant_id / evidence / status / created_at`。

**后果**：

- 0028 明确写了为什么必须留这些：“已处理的必须有处理人/时间，待处理的不许有（避免‘处理了但没留痕’）”（0028_pack_appeals.sql:44-47）。
- 方案的表**无法回答“谁在什么时候把这个插件判给了谁”**。配合第 1 条的审计缺失，等于归属被改后**没有任何一方能举证**——这正是申诉流程存在的意义，方案把自己的目的架空了。
- `status TEXT NOT NULL DEFAULT 'pending'` 无 CHECK 枚举（proposal.md:15），对比 0028:40-41 与 0040:32-33 都写了 `CHECK (status IN (...))`。裸 TEXT 可被写入任意值，后续按 status 过滤的队列查询会静默漏行。

**建议**：补 `resolution_note TEXT CHECK (length(resolution_note) <= 500)`、`resolved_by TEXT REFERENCES users(id) ON UPDATE RESTRICT ON DELETE RESTRICT`、`resolved_at INTEGER CHECK (resolved_at IS NULL OR resolved_at >= 0)`，并加 `CHECK (status IN ('pending','upheld','overturned'))` 与两条 `CHECK ((status = 'pending') = (resolved_at IS NULL))` 蕴含式。

## 6. 状态机缺口：无「撤回」，且 claimant 不能自己关单

**问题部分**：proposal.md:15 的 `status` 只有隐式 `pending`，方案 §2/§3 未定义撤回或重复提交。

**后果**：认领人误报后无法撤销，只能等管理员处理，进一步放大第 2 条的队列污染。0028 虽也只留 pending/upheld/overturned，但 0040:40-42 的 `role_applications` 有 `withdrawn` 态可参考。

**建议**：加 `withdrawn` 态，允许 `claimant_id` 本人撤回，撤回同样要写审计。

## 补充：一处需要产品澄清而非代码修改的点

方案 §2 允许“任何用户对任意插件提争议”，但 `plugin_ownerships` 的 `source = 'github_match'` 一类归属是**OAuth 证据链直接 verified**（ownership.ts:11-13，0040:79-82 注释）。对 github_match 归属提争议，本质是**质疑 GitHub 账号绑定**，这属于身份安全事件而非归属争议，应有独立处置路径（如账号申诉、`external_identities` 解绑审计）。建议在方案里显式排除 github_match 类归属，或为它单列分支并接入账号安全流程，否则会让管理员在证据薄弱的情况下推翻一条密码学强度的证据链。
