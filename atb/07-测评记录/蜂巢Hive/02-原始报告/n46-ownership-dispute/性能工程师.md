**前置事实（会放大下面所有问题）**：`plugin_ownerships` 表**在 migrations/ 里根本不存在**——0001 的 `plugins`（0001:82-92）只有 `id / repository_id / plugin_path / created_at / updated_at`，全 40 个迁移文件里没有 `plugin_ownerships`。提案 §1、§3 是**建立在一张不存在的表上**。性能后果：所有"归属可纠正"的写入路径没有可依赖的唯一约束，只能靠应用层先查后写，这正是 0028 明确避免的并发写法（0028:22-25）。

## 1. 「任何用户都可以对任意插件提出归属争议」——无基数上限的写放大入口

**① 哪部分有问题**：提案 §2 一句话设计（`proposal.md:24`）。表定义（`proposal.md:11-19`）里**没有任何唯一约束**，只有 `plugin_id` 和 `claimant_id` 两个外键列。

**② 后果**：
- 用户数 U × 插件数 P 是**笛卡尔积**：任一账号可对全站每个插件各提一条争议，且**同一个人对同一个插件可以无限重复提交**（无 `UNIQUE(plugin_id, claimant_id)`、无 `WHERE status='pending'` 部分唯一索引）。写入行数无上界，`ownership_disputes` 会变成全站唯一一张**不设增长上限**的用户写入表。
- 对比既有范式：0028:44-46 用 `CREATE UNIQUE INDEX uq_pack_appeals_pending ON plugin_pack_appeals(release_id) WHERE state = 'pending'` 把"同一目标只能有一条待处理"压到数据库层。本提案**缺失这一条**，等于把去重责任留给应用层先查后插——并发下双写（0028:22-25 已写明这是必须避免的）。
- `rate-limit.ts:64-72` 的 `RateLimitAction` 联合类型里**没有 ownership_dispute 这个动作**；`RATE_LIMIT_RULES`（`rate-limit.ts:66+`）是所有动作逐条登记的表，新动作不登记就**没有额度**。按现有 10 次/小时的口径（`rate-limit.ts` 中 correction/feedback 均为 `points: 10, durationMs: 3_600_000`），最坏情况仍是每小时数千行入表，且**每个插件详情页都可能被顶上游标**。

**③ 建议**：
- 迁移里加 `CREATE UNIQUE INDEX uq_disputes_pending ON ownership_disputes(plugin_id, claimant_id) WHERE status = 'pending';`，再加一条"同一 plugin 待处理争议数上限"的护栏（触发器或服务层计数，取 0028 部分唯一索引之外的第二道闸）。
- 在 `rate-limit.ts:57-72` 加 `'ownership_dispute'` 到 `RateLimitAction`，并在 `RATE_LIMIT_RULES` 登记 `specKey: 'rate_limits.ownership_disputes_per_day'`，建议**按天**而非按小时（这类申诉是低频高价值动作，`points: 5, durationMs: 86_400_000`）。
- 复用 0028 的"提交时快照 + 状态机"结构，而不是裸 `status TEXT DEFAULT 'pending'`。

## 2. 表定义缺索引与 CHECK——管理员队列会全表扫，且脏数据会静默进库

**① 哪部分有问题**：`proposal.md:11-19` 的整个 DDL。

**② 后果（逐条）**：
- **无 `status` 索引**：管理员"待处理队列"必然写 `WHERE status = 'pending' ORDER BY created_at`。SQLite 只能全表扫描 + 排序。对比 `0015:38` `idx_corrections_queue ON plugin_correction_requests(state, created_at ASC, id)`、`0028:49` `idx_pack_appeals_state ON plugin_pack_appeals(state, created_at, id)`、`0036:56` `idx_feedback_queue ON feedback_tickets(status, created_at ASC, id)` —— 仓库里**每一个**同类待办表都有这条索引，本提案是唯一没有的。
- **无 `plugin_id` 索引**：详情页/插件卡片展示"该插件是否有归属争议"时按 `plugin_id` 查，无索引 = 全表扫。`0028:52` 有 `idx_pack_appeals_release ON plugin_pack_appeals(release_id, created_at DESC)` 正是为此。
- **无 `claimant_id` 索引**：用户查"我提的争议"（`0036:57` `idx_feedback_mine` 的对应物）全表扫。
- **`status` 无枚举 CHECK**：只有 `DEFAULT 'pending'`，任何字符串都能写入。0028:30-31、0036:23、0015:36 全部用 `CHECK (state IN (...))`。缺 CHECK 的后果不是行数问题，而是**索引选择性崩塌**——一个拼错的 `'PENDING'` 会永久留在索引里，让"待处理"查询永远扫不干净。
- **`evidence TEXT` 无长度约束**：`0015:31` 对同类自由文本用 `length(description) <= 2000`，`0028:28` 用 `BETWEEN 5 AND 2000`。无上限意味着单行可以是 MB 级——SQLite 行溢出到 overflow page，`SELECT *` 的队列页会被证据正文拖慢。举证材料应由 media/file-store 承接（见 `platform/file-store.ts` 已存在），表里只存引用。
- **`created_at INTEGER NOT NULL` 无 `CHECK (created_at >= 0)`**：全仓约定（0001 里每张表、0028:38、0015:37 都带）。这不是性能问题本身，但缺它会放过 `NULL`/负值时间戳，而 `ORDER BY created_at` 的索引顺序依赖该列单调可用。
- **缺处理结果列**（`resolved_by` / `resolved_at` / `resolution_note`）：提案 §3 直接改 `plugin_ownerships`，争议行永远停留在 `pending`。后果：`status='pending'` 的行**只增不减**，管理员队列的扫描集随时间线性增长，且 0028:37-40 那组 `CHECK ((state='pending') = (resolved_at IS NULL))` 的一致性保证完全没有——"处理了但没留痕"在性能上表现为"索引里 pending 永远是满的"。

**③ 建议**：照抄 0028 的形状，最小补齐：

```sql
status TEXT NOT NULL DEFAULT 'pending'
  CHECK (status IN ('pending','upheld','overturned','withdrawn')),
evidence TEXT CHECK (evidence IS NULL OR length(evidence) BETWEEN 5 AND 2000),
created_at INTEGER NOT NULL CHECK (created_at >= 0),
resolved_by TEXT REFERENCES users(id) ON UPDATE RESTRICT ON DELETE RESTRICT,
resolved_at INTEGER CHECK (resolved_at IS NULL OR resolved_at >= 0),
CHECK ((status='pending') = (resolved_at IS NULL)),
CHECK ((status='pending') = (resolved_by IS NULL))
```
索引三条：`(status, created_at, id)` 给队列、`(plugin_id, created_at DESC)` 给详情、`(claimant_id, created_at DESC)` 给"我的"。

## 3. 「管理员直接改 plugin_ownerships」——热表原地 UPDATE，无并发控制、无快照

**① 哪部分有问题**：提案 §3（`proposal.md:28`）："管理员查看证据后，直接改 `plugin_ownerships` 的归属人"。

**② 后果**：
- 这是**对热表的原地 UPDATE**。`plugin_ownerships` 若被插件详情页/列表页 JOIN（归属人是页面上展示的字段），每次改归属都是对读缓存/页面的失效点；更要紧的是 `plugin_ownerships` 若按 `plugin_id` 有唯一约束，UPDATE 会走唯一索引维护 + 可能的行迁移，而且**没有任何版本列**（对比 `users.management_version`、`content_entities.visibility_control_version`，0001:29、0001:129）。
- 无 `state_version` / 无可延迟约束 → 两个管理员同时处理同一争议时，后写的静默覆盖前写的（lost update），且争议行与归属行**不在同一事务语义内**（提案没说是否同一事务）。
- **无历史快照**：0028:25-27 明确论证了为什么要把"申诉时的判定现场"快照进申诉行——因为主表随后会被改，事后回看不清当时状态。本提案把结论写进主表、把证据留在争议表，**两者之间没有任何链接字段**（`ownership_disputes` 没有 `resolved_at`、没有指向哪次归属变更的引用）。性能上这意味着审计要重建"某次归属变更对应哪条争议"时，只能靠时间戳范围模糊匹配——**范围扫描 + 无索引**。
- 与 `0042_audit_immutable.sql` 的既有约束冲突：全站审计是 `operation_records`（0042:5-8 说明它是"全站审计与幂等去重的唯一载体"）。提案完全没提走 `recordOperationInTx`（`corrections/index.ts:15` 的既有用法），归属变更**不会留下可审计的操作记录**，也**不参与幂等去重**——重放同一个管理动作会重复改一次归属。

**③ 建议**：
- 归属变更必须走 `withTransaction` + `recordOperationInTx`（照 `corrections/index.ts:15` 与 `catalog/service.ts:22` 的既有写法），`action_type: 'ownership.transfer'`，`operation_key` 用争议 id —— 借 `operation_records(action_type, operation_key)` 的 UNIQUE 天然拿到并发原子性（`catalog/service.ts:15-19` 已论证过这一手法）。
- 争议行加 `resolved_at/resolved_by/resolution_note`，并在同一事务内把"改归属"与"结案争议"写死在一起，避免出现"归属改了但争议还 pending"的半状态（否则 pending 集合永不收敛，见上一条）。
- 若 `plugin_ownerships` 将被加入，请**先补它的迁移**（当前不存在），并且照 0015 的做法把"同步来源的归属"与"管理员改判的归属"分开存，而不是原地覆盖——`0015:10-17` 已经把这个模式论证得很清楚：覆盖式写会让"原值"永久丢失，且每次改判都要重新探测 GitHub。

## 4. 通知/回执路径缺失，成本被推迟到事后排查

**① 哪部分有问题**：`proposal.md:12-30` 全文只有 `ownership_disputes` 一张表和一个管理员手工动作，**没有 notification kind、没有反馈给争议双方的出口**。

**② 后果**：`0036:69-79` 显示 `notifications` 的 `CHECK (kind IN (...))` 是**每加一种通知就要重建整表**（`notifications_new` → `INSERT ... SELECT` → `DROP TABLE` → `RENAME`，0036:87-101）。这是仓库里最重的迁移模式（整表拷贝 + 索引重建）。提案如果现在把通知留空，将来补通知时就要再跑一次全表重建 —— 而且是在 `notifications` 已经积累了大量行的生产库上。0028 的申诉配套通知与 0034/0036 一样走这个模式，说明这是既定代价；**现在设计时就该定好 kind**，避免二次重建。

**③ 建议**：在 `proposal.md` 里明确 `notifications.kind` 新增 `ownership_dispute_result`，并与 0043 同批落库（同一次整表重建里加完），而不是留到下一片。这也顺带解决"争议被驳回后 claimant 不知道"的产品闭环。

## 5. 一处需要澄清的读取放大（证据不足，标记待确认）

**① 哪部分有问题**：提案未说明"争议是否存在"是否对外可见。

**② 后果**：`catalog/service.ts` 的列表与详情是目录主读路径（`service.ts:9-13` 提到 `overridesFor` 在读取时合并）。若争议状态被加进 `PluginSummary`/`PluginView`，每页 N 个插件就要多一次按 `plugin_id` 的查询（N+1），或一次 `IN (...)` 扫描 —— 在缺索引（见第 2 条）的情况下退化为全表扫。

**③ 建议**：明确争议**不进入公开目录读路径**（与 `0036` 的 feedback 同理，"纯私有"，`feedback/index.ts:5` 的边界 1）；若确需展示，用 `(plugin_id) WHERE status IN ('pending')` 的部分索引 + 批量 `IN` 查询，禁止页内 N+1。这一点我无法从提案判断，**需要产品确认后才能定性**。
