# 性能评审：N-52「草稿保存的版本控制」

**评审对象**：`tasks/n52-draft-version/environment/proposal.md`（28 行）
**基线事实（已核实）**：better-sqlite3 **同步驱动** · 单进程单例连接（`platform/db.ts:66-73`）· WAL + **`synchronous=FULL`**（`db.ts:50-53`）· Web 与 worker 双进程共享同一个库文件（`db.ts:66`）· 所有写操作都走 `withTransaction`（`tx.ts:43`）。

**总判定**：§1 的版本控制**已经实现，而且比提案写得更正确**；提案真正新增的只有 §2 的 30 秒轮询，而它恰好把原本设计好的防抖（debounce）改成了**定时写入放大**。以下按严重度排序。

---

## 1【致命】§1 的 `UPDATE ... WHERE id = ?` 缺少 `save_version = ?` 条件 —— 提案的 SQL 本质上是无条件覆盖，不能防止互相覆盖

**问题部分**：提案 §1 伪代码
```sql
UPDATE content_drafts SET payload = ?, save_version = save_version + 1 WHERE id = ?
```
**后果**：检查 `expectedVersion !== current.save_version` 与实际写入之间隔了一次读，二者不在同一原子操作内。两个设备同时保存时：A、B 都读到 `save_version=3`，都通过检查，随后两条 UPDATE 各自执行 `save_version+1`，后写者覆盖先写者 —— **提案声称的「不会互相覆盖」并不成立，而且写入次数还是 2**。这不是理论问题：该仓库当前代码已经是正确的 CAS，提案若被当作「方案」回退实现，等于主动退化。

**建议**：直接删除提案 §1 的 SQL，改为对齐现有实现（`src/server/modules/reviews/index.ts:664-673`）：
```sql
UPDATE content_drafts SET payload = ?, save_version = save_version + 1, saved_at = ?
 WHERE id = ? AND save_version = ?
```
并以 `updated.changes === 0` 作为唯一冲突判据（`:675-681`）。**提案没有新增价值，应当写明「复用既有 CAS，不改动」**，避免后续实现者按提案重写。

---

## 2【致命】§2「每 30 秒自动保存一次」：把防抖改成轮询，写入次数放大 6 倍，直撞 `synchronous=FULL`

**问题部分**：提案 §2 与 §3（“编辑器每 30 秒自动保存一次”）

**事实核对**：
- 现有实现是**基于静默期的防抖（debounce），不是定时轮询**，默认 **5 秒**（`packages/common/autosave.ts:12`；`review-editor.tsx:349-354` 注释明确写“是防抖不是轮询”），并且用户可配置为 0/3/5/10/30（`autosave.ts:9`）。
- 现有实现还有两道**免费的写入抑制**：内容摘要未变就不写（`review-editor.tsx:334-336`、`:371-372`）；保存中则跳过本轮（`:363-366`）。
- 提案的“每 30 秒”是**无条件周期写入**，恰好把这两道抑制全部作废。

**后果（按数字）**：一次 draft PUT 在该事务里是**2 次写**（`UPDATE content_drafts` + `INSERT draft_save_receipts`，`reviews/index.ts:664-689`），而 `synchronous=FULL` 意味着**每次 commit 都要 fsync WAL**（`db.ts:53`）。`synchronous=FULL` 的 fsync 成本约为毫秒级（具体值取决于盘，NVMe 约 0.1–1ms，SATA SSD 约 1–10ms，机械盘更高），因此：
- 1 个空闲但标签页开着的编辑器：提案下 **2 fsync / 30s ≈ 5,760 次/天**；现状（内容不变不写）≈ **0**。
- 100 个同时开着的编辑页：提案下约 **6.7 fsync/秒**，只为此就长期占用 WAL 写入。
- 更糟的是**等待是同步的**：better-sqlite3 的 `busy_timeout=5000`（`db.ts:55`）在单例连接上**阻塞整个进程的事件循环**（`db.ts:5-8` 明写“等待会阻塞所属线程”）。定时写入若与任何长事务（如 `deleteDrafts` 批量 50 份，`reviews/index.ts:MAX_BATCH_DELETE`）相撞，**所有 HTTP 请求一起卡住**，而不是只有这一个保存慢。

**建议**：
1. 删除 §2 的“每 30 秒”，改为「**沿用现有静默期防抖**（默认 5s，可配 0–30），不引入周期性写入」。
2. 若目标是提升可靠性（防止崩溃丢字），正确做法不是缩短间隔，而是**保留摘要去重 + 保存中跳过 + 失败退避**，并把“30 秒”只当作**上限兜底**（例如：内容有变化、且距上次成功保存已超过 30 秒才强制写一次），这样空闲时不产生任何写入。
3. 明确禁止“定时无条件 PUT”：它会绕过 `lastSavedDigestRef` 与 `savingRef`（`review-editor.tsx:363-372`），把两个 PUT 推成同一 `expectedVersion` 的**假冲突**。

## 3【严重】`draft_save_receipts` 无保留期，自动保存越频繁，这张表增长越快，而读取路径要全表扫它

**问题部分**：提案未提回执生命周期；每次成功保存插入一行（`reviews/index.ts:685-689`），表上 `PRIMARY KEY (draft_id, request_key)`，无 TTL/清理。

**后果**：`request_key` 每次请求新生成（`review-editor.tsx` 用 `newRequestKey()`，`:375`），所以**每次自动保存 = 一条永久行**。提案的 30s 轮询把这个速率抬高 6 倍。按每天 2,000 次全站保存估：约 73 万行/年。**热路径代价在冲突判定上**：每次保存都要先查这张表（`reviews/index.ts:634-641`），键是 `(draft_id, request_key)` 尚可；但 `deleteDraftInTx` 会 `DELETE FROM draft_save_receipts WHERE draft_id = ?`（`reviews/index.ts:401`），**该列不是索引前缀之外的单列索引**，删除时须扫索引；且 WAL 下这些删除会产生大量页翻转。真正的问题是**存储与 vacuum 压力无界**，而不是某一次查询慢。

**建议**：
1. 明确回执保留策略：**只保留最近 N 次/最近 24h**，由 worker 定期 `DELETE ... WHERE saved_at < ?` 并**加 `(saved_at)` 索引**；或按 `draft_id` 设上限（保留最近 20 条）。
2. 迁移里补 `CREATE INDEX idx_receipts_saved_at ON draft_save_receipts(saved_at)`，否则清理任务会全表扫。
3. 提案必须写清“频控/回执/清理”三者关系，否则 30s 轮询等于给一张只增不减的表加速灌数据。

---

## 4【严重】§3 冲突处理「丢弃本地修改」= 用户输入作废，且放大保存风暴

**问题部分**：§3“提示用户刷新，丢失本地修改”。

**后果**：现有实现的冲突语义是**不覆盖、保留用户输入、由调用方重试**（`reviews/index.ts:675-680`，错误体带 `current_version` 与 `expected_version`）。提案改成“刷新丢稿”，在自动保存场景下后果不对称：自动保存失败被吞成状态条提示（`review-editor.tsx:392-395`），用户**往往没看见**，等发现时已丢了整段。更隐蔽的性能副作用：用户看到冲突后按 F5 重载 → **重新拉草稿详情 + 重新计防抖**，形成“冲突 → 刷新 → 再冲突”的循环，把一次冲突变成多次全量读（`getReview` 里含 4 次 join 查询，`reviews/index.ts:707-760`）。

**建议**：
1. 冲突时**不得丢弃本地内容**：保留编辑器状态，按 `current_version` 让用户选择「用我的覆盖」/「载入服务端版本」，覆盖路径用新的 `expectedVersion=current_version` 重试。
2. 自动保存遇冲突时**停止自动保存直到用户处置**（避免每 5s 重试一次撞同一个版本），这是纯性能收益：消除重试风暴。
3. 若坚持丢稿，至少要在提案里给出量化前提（冲突率），否则这是个用性能换数据丢失的坏交易。

---

## 5【中】提案缺少 `expectedVersion` 的并发正确性前提：单连接 + 双进程下 CAS 是够的，但提案没写，易被实现成“先 SELECT 再 UPDATE”

**问题部分**：§1 用 `current.save_version` 做比较 —— 该值从哪来未定义。

**后果**：若实现者按字面「先读 current 再比较再写」，在**单例同步连接**（`db.ts:66`）下单进程内侥幸安全，但 Web 与 worker 是**两个进程**（`db.ts:66` 注释“Web 与 worker 各自一个进程”），跨进程下「先读后写」失去原子性 → 需要 CAS 才有意义。这正是第 1 条要 CAS 而不能用 `current.save_version` 的原因。

**建议**：提案把不变量写死为「**冲突判定必须由 UPDATE 的 `changes===0` 决定，不得依赖先读到的 current 值**」，并注明跨进程前提。

---

## 6【中】“30 秒”与现有可配置偏好（0/3/5/10/30）语义冲突，可能引发设置项失效

**问题部分**：提案 §2 固定 30 秒 vs `AUTOSAVE_SECONDS_OPTIONS = [0,3,5,10,30]`（`autosave.ts:9`）。

**后果**：若按提案硬编码 30s，用户把设置调到 **0（关闭）** 或 **3 秒** 都会失效 —— `autosaveMs <= 0` 的分支（`review-editor.tsx:357-360`）会被绕过，于是“关闭自动保存”的用户**仍以 30s 被写库**。对性能工程师而言这是最坏的一类回归：**用户显式要求的零写入被悄悄推翻**。

**建议**：提案删除固定间隔，改为“尊重 `editorAutosaveSeconds` 偏好，默认 5s”；若要引入 30s，只能作为**内容变化后的兜底上限**，且必须与 `autosaveMs <= 0` 的关闭语义兼容（关闭即彻底不写）。

---

## 7【低-中】§1 每次保存都 `JSON.stringify(payload)` 全量重写正文，未评估载荷体积

**问题部分**：`payload` 是整篇正文（`body: DraftBodySegment[]`，`reviews/index.ts` DraftPayload）。

**后果**：`UPDATE ... SET payload = ?` 是全量重写，等于每 30 秒把整篇 markdown 连同 WAL 一起重写一遍；长文（数十 KB～百 KB）时，**WAL 增长与 checkpoint 频率**随之上升，且 `synchronous=FULL` 下 fsync 的字节量也上升。现行 5s 防抖 + 摘要去重把“只写真正变化的版本”做到了，提案的 30s 轮询会把这份收益抹掉。

**建议**：保持“内容未变不写”；若要进一步降写放大，可评估**分段存储**（`body` 段落独立行）或对 payload 体量设上限并在提案中给出数字（如“单草稿 ≤ 256KB”）。

---

## 结论与最小修改清单

提案的**核心主张（§1 版本号）已被现有代码实现且更严谨**；**新增部分（§2/§3）在性能上是净负**。建议按以下改写后再评审：

1. **§1 整段替换**为“复用既有 CAS（`AND save_version = ?` + `changes===0` 判冲突），不新增逻辑”，并删掉会诱发无条件覆盖的 SQL。
2. **§2 改为**“沿用静默期防抖（默认 5s，尊重 0=关闭），30s 仅作内容变化后的兜底上限”，明确**空闲不写**。
3. **§3 改为**“冲突保留本地输入 + 停止自动保存待处置 + 明确重试路径”，不得丢稿。
4. **补一节「回执与清理」**：`draft_save_receipts` 保留期 + `(saved_at)` 索引 + worker 清理，否则 30s 轮询会把这张只增不减的表变成增长最快的表。
5. **补一节「写放大预算」**：明确单次保存 = 2 写 2 fsync（`synchronous=FULL`）、单进程同步连接的阻塞前提（`busy_timeout=5000` 会卡事件循环），给出可接受的全站保存速率上限。
