# 安全评审：草稿保存的版本控制方案

**评审结论：不通过（存在一个可直接利用的越权读写漏洞）。**

方案正文（proposal.md:1-28）只有一段伪代码，但它与仓库中**已实现**的 `saveDraft` 存在关键差异，而且方案里明确写了「冲突时丢弃本地修改」，这属于功能问题；按安全要求，我只讲安全面。

---

## 一、[严重] 重放分支绕过了草稿归属校验（IDOR）

**① 问题所在**

方案 proposal.md:11-16 的伪代码只有两条语句：先比较版本，再 UPDATE。`UPDATE ... WHERE id = ?` **没有 `owner_id = ?` 条件**，也没有归属校验步骤。这看起来是「简化」，但对比真实实现可以看到，这种简化会把一个已有的防线拆掉：

- `src/server/modules/reviews/index.ts:637-651`：先查询 `draft_save_receipts`（按 `draft_id + request_key`），命中就直接 `return { ..., replayed: true }`
- `src/server/modules/reviews/index.ts:654`：`if (row.owner_id !== userId) throw err.forbidden('只能保存自己的草稿。')` 在**回执分支之后**才执行

**② 后果**

`reviews/index.ts:637-651` 的 `return` 语句先于 `reviews/index.ts:654` 的归属检查，所以任何已认证用户只要知道（或猜到）他人的 `draftId` 和一个曾经出现过的 `requestKey`，就能：

- 通过 `reviews/index.ts:646` 的 `digest(payload) !== receipt.payload_digest` 比较，做一次 **试探性探测（oracle）**：错误时会得到 `keyReused`，正确时会返回 `replayed: true` 以及**真实的 `saveVersion` 与 `savedAt`**。这等于向攻击者确认「这份草稿存在，且该 requestKey 在某个时刻保存过摘要完全相同的载荷」。由于摘要比对必须存在，攻击者若已知载荷内容（草稿正文常用于预览或分享场景），就可以完全重放。
- `reviews/index.ts:644` 的 `storedDigest !== receipt.payload_digest` 分支会抛 `err.internal`，同样是一个可观测的差异信号。

这不是理论风险：`requestKey` 在客户端是稳定值（同一编辑会话反复使用），而 `draftId` 是 UUIDv7。UUIDv7 **前 48 位是毫秒时间戳**，创建时间相近的草稿前缀高度可枚举；这是 UUIDv7 的公开特性，仓库也在多处依赖它（`packages/common/field-rules` 的 `isUuidV7`）。因此「猜不到 ID」不能作为唯一防线。

**③ 建议**

把归属校验提到回执查询**之前**，且回执查询本身也带上 owner 约束（纵深防御，避免今后有人再调整顺序时重新出现该问题）：

```ts
// 先取行并校验归属，再做回执判定
const row = readDraftRow(db, draftId);   // 内部已过滤 deleted_at IS NULL
if (row.draft_type !== 'review') throw err.unavailable(...);
if (row.owner_id !== userId) throw err.forbidden(...);
```
回执查询改为带归属的联表：
```sql
SELECT rc.* FROM draft_save_receipts rc
  JOIN content_drafts d ON d.id = rc.draft_id
 WHERE rc.draft_id = ? AND rc.request_key = ? AND d.owner_id = ?
```
注意：现有注释（`reviews/index.ts:630-632`）解释了「回执必须先于 CAS」的理由，这个理由**成立**，要先于 CAS，但**不必**先于鉴权。请把注释改成「回执先于 CAS、后于鉴权」，避免后续维护者按照错误顺序「修复」回去。同时给这条路径补测试：跨用户重放必须返回 `forbidden`，而不是 `replayed`。

## 二、[高] 方案伪代码在版本比较与写入之间不是原子操作

**① 问题所在**

proposal.md:11-16 是两段独立的逻辑：先 `if (expectedVersion !== current.save_version)` 读取判断，再单独执行 `UPDATE`。读到判断与写入之间存在时间窗。

**② 后果**

`proposal.md:11-16`：两个并发请求都读到 `save_version = 3` 并通过检查，随后两个 UPDATE 都执行，`save_version` 变成 5，后写者**静默覆盖**前者。方案在 proposal.md:27 自称「不会互相覆盖」，这只在单进程串行时成立，多设备同时编辑（正是 proposal.md:4 描述的背景场景）时恰好失效。这直接否定了方案要解决的唯一问题。

**③ 建议**

不要把校验与写入拆成两条语句。用 CAS 单语句，让数据库来仲裁：

```sql
UPDATE content_drafts
   SET payload = ?, save_version = save_version + 1, saved_at = ?
 WHERE id = ? AND save_version = ?
```
然后检查 `changes === 0` 作为冲突信号。这是 `reviews/index.ts:665-676` 已经在用的正确写法，方案应与之对齐，而不是各写一套。

**补充证据**：`migrations/0001_baseline.sql:195` 的 `save_version INTEGER NOT NULL DEFAULT 0 CHECK (save_version >= 0)` 说明版本列已存在；`migrations/0001_baseline.sql:207-218` 的 `draft_save_receipts` 表连同 `CHECK (result_version = expected_version + 1)` 也已存在。**方案完全没有提到这张回执表。** 没有它，客户端在超时后重试同一个 `requestKey` 会被当成新的保存，从而触发虚假冲突，或者重复递增版本。而 CAS 比较的是 `expectedVersion`，重试时该值已过期，必然返回冲突。这会让用户在弱网下频繁看到「请刷新」，方案 proposal.md:19-20 的「提示用户刷新、丢失本地修改」会变成常态。**请把 `draft_save_receipts` 的幂等语义写进方案。**

## 三、[中] `expectedVersion` 缺少类型与范围校验

**① 问题所在**

proposal.md:10 的 `client sends: { draftId, payload, expectedVersion }` 直接信任了客户端字段，既没有说明类型，也没有说明范围。

**② 后果**

`proposal.md:10-11`：若以字符串 `"3"` 传入，`"3" !== 3` 恒为真，导致所有保存都被判为冲突，功能不可用；若传入 `-1` 或 `NaN`，与 `save_version` 的比较行为取决于实现，可能绕过 CAS 直接写入（`NaN !== 3` 为真，在「不等即冲突」逻辑下反而安全；但在 `WHERE save_version = ?` 下 `NaN` 绑定可能退化为 NULL 比较，`changes` 恒为 0）。行为不确定本身就是风险。

现网实现是对的：`reviews/index.ts:622-624` 有 `Number.isInteger(...) && input.expectedVersion >= 0`，`migrations/0001_baseline.sql:195` 有 `CHECK (save_version >= 0)`。方案必须显式继承这条要求，否则按方案重写时会丢掉。

**③ 建议**

在方案里写死校验契约：`expectedVersion` 必须是非负整数，不合法直接返回 `input_invalid`，不要落入冲突分支。也应对 `payload` 复用 `parseDraftPayload`（`reviews/index.ts:625`）做结构校验，`migrations/0001_baseline.sql:193` 的 `CHECK (json_valid(payload))` 只能保证它是合法 JSON，不保证结构正确。

## 四、[中] 「自动保存每 30 秒」缺少频率控制说明

**① 问题所在**

proposal.md:23「编辑器每 30 秒自动保存一次」只描述了客户端意图，没有提到服务端限流。

**② 后果**

`proposal.md:23`：自动保存把「用户手动点击」变成了「常开的高频写」，每个打开编辑器的用户都会稳定产生 2 次/分钟的写事务。攻击者可以简单地忽略 30 秒约定，构造高频 `saveDraft` 请求。每个请求都会：开启事务、读回执、读草稿行、执行 UPDATE、写回执（`reviews/index.ts:627-695`）。`draft_save_receipts` 是**只增不减**的表（`migrations/0001_baseline.sql:207-218` 无任何过期或清理机制），因此这会同时造成数据库膨胀，形成存储型 DoS 面。仓库已有频控设施：`migrations/0006_rate_limiter.sql` 的 `rate_limiter_flexible` 表，方案应当引用它并给出动作键与配额，例如 `rlflx:draft_save:<userId>`。

**③ 建议**

方案补一节「频控与存储增长」，明确：(a) `saveDraft` 走 `rate_limiter_flexible`，按 userId 限流；(b) 为 `draft_save_receipts` 定义保留策略（例如只保留最近 N 条回执，或按 `saved_at` 过期），否则这张表会无限增长。回执保留窗口还必须**大于**客户端重试窗口，这一点要写清楚，否则清理会破坏幂等语义。

## 五、[低] 冲突响应里的版本信息泄露面

**① 问题所在**

`reviews/index.ts:677-680` 在冲突响应里回了 `current_version: row.save_version` 和 `expected_version`。

**② 后果**

这块本身合理，因为要支持客户端重新合并。但配合第一条的越权问题，`current_version` 就成了判断「他人草稿活跃度」的旁路通道。修复第一条之后，该风险自然消解，暂时不需要额外改动；这里记下来，是为了说明**这两条问题有耦合**，修第一条不能只加 owner 校验却保留跨用户可探测的错误差异。

**③ 建议**

修复条目一后，确认所有跨用户路径统一返回 `unavailable`/`forbidden`，不区分「不存在」与「不是你的」，避免枚举行为。

## 六、[低] 方案缺失的安全要素

方案 proposal.md:1-28 通篇没有出现鉴权、审计、软删除相关表述。经核实，以下约束是**现网已经实现、方案若重写就会丢失**的，建议在方案中显式列出：

| 约束 | 现网证据 | 方案是否覆盖 |
|---|---|---|
| 软删除草稿不可写 | `readDraftRow` 的 `deleted_at IS NULL`（`reviews/index.ts:218`）、`migrations/0018_draft_soft_delete.sql:19` | ❌ 未提 |
| 账户状态每次请求复查 | `assertCanWrite`（`platform/context.ts:33-41`） | ❌ 未提 |
| 一篇评测仅一份活跃草稿 | `uq_drafts_review` 部分唯一索引（`migrations/0018_draft_soft_delete.sql:19-20`） | ❌ 未提 |
| 提交后草稿软删除不可改绑 | `reviews/index.ts:585-590` | ❌ 未提 |

`migrations/0018_draft_soft_delete.sql:8` 的注释已经写明「列表/详情/保存统一过滤 `deleted_at IS NULL`，删除后不可再读写」。方案若不承接这条约束，重写 `saveDraft` 时极可能漏掉过滤，让已删除草稿重新可写。这会产生「已撤回评测的草稿被改写后再次提交」的完整性问题。
