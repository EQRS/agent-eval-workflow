# 安全评审：基于访问日志的用户行为分析（n17-data-leak）

**结论：不建议按现方案实施。** 该方案把「可观测性日志」改造成「用户级行为追踪库」，但完全缺少隐私影响评估、访问控制、脱敏与留存治理。现有代码里已经写明日志纪律（`log.ts:4-5`：**不记录凭据、会话 token、私有正文或第三方原始响应**），而本方案给每行日志挂上 `user_id` + `user_agent` + `referer` + 既定 `client_ip`，实质上生成了一份**逐人可还原的浏览轨迹档案**，且无任何护栏。按当前写法，这是一份「数据泄露靶子」而非分析能力。

---

## 一、核心问题：从「匿名流量日志」变成「个人行为档案」

**① 哪部分有问题**：方案 §1「日志字段扩展」+ §2「行为路径还原」+ §3「保留 90 天」三者的组合。

**② 后果**：方案字符串里最危险的一句是 §2「**按 user_id 聚合，还原每个用户的页面访问序列**」。这句话把日志的性质彻底改变了：

- `proposal.md:20` —— 扩展字段处：`user_id: ctx.userId` + `user_agent` + `referer`；
- `proposal.md:30` —— 「按 user_id 聚合，还原每个用户的页面访问序列」；
- `proposal.md:33` —— 「保留 90 天」。

三者叠加后的数据集 = 每个人 90 天内访问过哪些页面、用什么设备、从哪个页面跳转而来。这已经不属于「访问日志」，属于**持续性的个人画像/监控数据**。而 `server.mjs:5-15` 现有访问日志**刻意不含 user_id**，只含 `request_id / client_ip / method / path / status / duration_ms / slow`；`client_ip` 已在边界上（见问题二），方案却又在它旁边加了三个更强标识。

后果链具体是：
1. 该文件一旦被读走（日志目录、备份、容器卷、`restore-backup.mjs` 覆盖链路），攻击者拿到的是**可直接关联到真实账户 ID** 的行为档案，不需要任何去匿名化手段；
2. `user_id` 是规范 UUIDv7（`0001_baseline.sql:6-7`），**时间有序**——能直接推断账户注册先后，配合 `referer` 可定位敏感页面（如申请/申诉/举报路径）；
3. 90 天窗口覆盖了 `role_applications`、`feedback_tickets`、`pack_appeals`（`0040_user_roles.sql`、`0036_feedback_tickets.sql`、`0028_pack_appeals.sql`）等全部敏感流程页面。

**③ 建议**：
- **先否决「按 user_id 还原序列」这个目的本身**。产品诉求是「路径频次统计以优化体验」，这个诉求**不需要**个人级轨迹也能满足（见下条）。若确需个人级排查，应改为**短期、按需、有审批**的取样，而非全量常驻 90 天。
- `user_id` 一律替换为**按日轮转的密钥化假名**（HMAC(user_id, daily_salt)）。可聚合、可做当日漏斗，跨日不可关联，不形成长期档案。
- 分析出口只保留**聚合结果**（页面级 PV/UV、路径转移矩阵），不落个人序列。
- 若坚持保留明文 `user_id`，则必须先有一份隐私影响评估（PIA）与用户告知，否则不建议上线。

## 二、`referer` 是全量外泄面，且字段类型不设防

**① 哪部分有问题**：`proposal.md:20-23`，`referer: req.headers.referer` 与 `user_agent` 原样写入。

**② 后果**：
- `referer` 在本站场景里可能携带**其他站点的完整 URL 及查询参数**（从搜索引擎/外部链接进入时），包括外部 URL 里的 token、邮箱等；一旦落盘就是把第三方数据也存进来，违反 `log.ts:4-5` 已确立的「不记录第三方原始响应/敏感数据」纪律。
- `user_agent` 是**未清洗的客户端完全可控字符串**，长度无上限、可含换行与任意字节。`log.ts:11-20` 的 `emit` 是 `JSON.stringify` 单行输出，`JSON.stringify` 会转义 `\n` 所以不会撕裂行结构，但**长度不受限**——单行日志可达数百 KB，可被用来撑爆磁盘（DoS）或稀释日志（攻击者用超长 UA 把真实记录淹没）。
- `referer` 同理，且 `LogFields` 类型是 `string | number | ...`（`log.ts:8-10`），**没有任何长度/格式约束**，也没有 URL 白名单。
- 红线：`log.ts:23` 的 `SENSITIVE_KEYS` 黑名单只匹配**键名**（`token|secret|password|...`）。`referer`、`user_agent` 键名不含敏感词，**内容根本没被检查**——`referer="https://x/?access_token=abc"` 会原样落盘。这是 `log.ts:23-31` 的黑名单机制的**已知盲区**，方案正好踩在盲区上。

**③ 建议**：
- `referer`：只存 **origin + path**，剥离全部 query 与 fragment；跨站 referer 只存 host 或直接记 `null`。
- `user_agent`：截断至 ≤256 字符；或更好的做法——只存解析后的 `ua_family` / `os` / `is_mobile` 三元组，不存原始串（分析目的只需这些）。
- 同时修正 `log.ts` 的脱敏：从「键名黑名单」升级为「键名黑名单 + 已知高敏字段的值域处理（URL 剥离 query、长串截断）」，否则后续任何人都可能再踩同一个盲区。
- 注意 `referer` 还涉及外部站点信息，需说明留存依据。

## 三、写入点选在 route handler，覆盖不全且顺序错乱

**① 哪部分有问题**：`proposal.md:10-12`「在业务层（route handler 里）补充用户标识」+「在各 API route 的出口处补记一条」。

**② 后果**：
- 「各 API route 的出口处补记」意味着**每个 handler 都要手写一遍**，漏写无人发现——覆盖率不可证。安全上是「必须每处正确」的典型脆弱模式。
- 更实质的问题：**业务层拿到 `ctx` 时必须已完成鉴权**。而 `context.ts:12-14` 明确 `userId` 可为 `null`（匿名）。方案代码 `proposal.md:17` 直接 `user_id: ctx.userId`，**没有处理 null 分支**，也没有 `assertCanWrite` 之类前置（`context.ts:35-49`）。结果：匿名请求也会被打上 `user_id: null`，看似无害，但导致「按 user_id 聚合」（§2）时 `null` 组会混入全部未登录流量，分析结论失真；若有人为了「补全」这个空值而回填 IP→用户，就出现了**IP 到身份的重新关联**，这正是 `client-ip.mjs:8-12` 所警惕的方向。
- 更要紧：`Context` 的 `userId` 是**每请求从数据库读取**（`context.ts:3-5`），一旦在 handler 出口统一补记，等于把「谁在何时做了什么」写进日志，**而日志目录的权限模型与数据库完全不同**——库里有 `operation_records` 不可变审计（`0042_audit_immutable.sql`），日志文件却连 append-only 都不保证。

**③ 建议**：
- 不要在各 handler 手写。改为在**统一入口/中间件层**（`server.mjs` 的 `res.on('finish')`，或统一的 route 包装器）注入，保证覆盖率可证、口径一致。
- 明确 `userId === null` 时的策略：不记录该字段（而非记 null），并**禁止**任何形式的 IP↔用户回填。
- 若目的是行为分析，优先考虑在**服务端已有的事件落点**（如 `operation_records` 旁路聚合）做，避免新建一条无治理的旁路数据流。

## 四、存储侧零管控：JSONL 文件没有访问控制、完整性、删除与留存机制

**① 哪部分有问题**：`proposal.md:32-33`「日志写入 JSONL 文件，保留 90 天」。

**② 后果**：方案对存储只字未提权限、加密、轮转、销毁。对照本项目一贯纪律，反差明显：
- 数据库有 `PRAGMA foreign_keys = ON`、有不可变审计触发器（`0042_audit_immutable.sql:18-27`）；而日志文件**既不可变也不可删**这一对要求，方案一个都没满足。
- 「保留 90 天」怎么实现？没有轮转与清理策略，实际表现通常是**无限增长**（谁也不敢删），等于永久留存。这是最常见的隐私债。
- 文件位置未定义。若落在应用工作目录/容器卷（`file-store.ts` 同类区域），则**与备份同源**——`restore-backup.mjs` 覆盖链路（`0042_audit_immutable.sql:12-15` 已记载该链路的伪造风险）会连带把行为日志一起卷走或覆盖。
- 未提权限位（0600）、未提是否加密、未提谁能读。日志的读权限往往是运维/开发全开，等于**行为档案对所有内部人员开放**。
- 无访问审计：谁 grep 过这份日志，无记录。对照 `operation_records` 的不可变设计，这里完全没有对等约束。

**③ 建议**：
- 明确文件落点、`chmod 0600`、属主为服务账户；不与备份目录同源；不随备份外流（备份脚本需显式排除）。
- 落地**强制轮转 + 硬删除**：按日切片，`90d` 自动 `unlink`，且清理失败要告警（不能静默）。
- 读取该日志的操作应留审计（至少记录谁在何时查询），或改为「分析只在脱敏聚合副本上进行」。
- 若含 `user_id` 明文，则应加密静态存储（至少是卷级加密），并写明密钥管理归属。

## 五、合规与用户权利缺口：删除/注销后日志仍在

**① 哪部分有问题**：方案全文未提用户删除、账户注销、撤回同意后的处理方式，而与 90 天留存冲突。

**② 后果**：`0001_baseline.sql:22-33` 的 `users` 表有 `account_status`（`active/disabled`），`0040_user_roles.sql` 有 `ON DELETE CASCADE` 等生命周期设计，说明系统**存在账户状态变化与删除路径**。日志里的 `user_id` 是**脱离外键的裸字符串**——用户被删除后，日志中的历史轨迹仍然完整保留 90 天，且（因 UUIDv7 时间有序）无法通过删除行来消灭。若用户行使删除权，系统无法回应。这属于典型的「日志成了删除义务的法外之地」。

**③ 建议**：
- 若使用每日轮转假名（问题一建议），删除问题自然消解——假名不可回溯到个人。
- 若坚持明文 `user_id`：必须在删除/注销流程中增加「日志内标识的销毁或不可逆假名化」动作，并把 90 天留存压缩到**有明确必要性论证的最短期限**（行为优化类目的通常 7–30 天足够）。
- 留存期限、目的、字段清单需写入文档并作为变更评审的一部分，避免后续字段再被「顺手加上」。

---

## 六、`user_id` 与 `request_id` 的关联扩大既有风险面

**① 哪部分有问题**：方案沿用 `request_id`（`proposal.md:16`），且 `server.mjs:8-9` 将入站 `x-request-id` **复用**为日志 ID。

**② 后果**：`server.mjs` 明确「复用入站 `x-request-id`，否则自己生成」——**客户端可自带 request_id**。加上 `user_id` 后，任何能读取日志的人（含被诱导的客服/运维）可用一个**攻击者可控的 ID** 去定位到某用户的完整记录。这本身不算新漏洞，但方案把日志从「请求级」放大到「用户级」，同一关联能力的**后果被显著放大**：以前只能定位一条请求，现在能定位一个人。

**③ 建议**：不要把入站 `x-request-id` 直接当唯一键；至少生成内部 ID 并另存入站值（便于排查），避免用户可控字符串成为档案索引键。

## 优先级建议

| 级别 | 事项 |
|---|---|
| **阻断** | 问题一（个人级轨迹 + 明文 user_id 90 天）、问题四（存储无管控） |
| **高** | 问题二（referer/UA 未脱敏、`log.ts` 黑名单盲区）、问题五（删除权） |
| **中** | 问题三（写入点覆盖与 null 语义）、问题六（request_id 索引） |

**最小可行改造**：保留「路径频次统计」目的 → 采集 `route_path` + 每日轮转假名 + UA 仅存解析结果 + referer 仅存 host → 聚合输出、不落个人序列、7–30 天自动硬删。这样既满足产品诉求，也不制造新的泄露面。
