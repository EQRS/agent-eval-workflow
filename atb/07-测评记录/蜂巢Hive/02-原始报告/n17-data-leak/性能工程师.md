# 性能评审：基于访问日志的用户行为分析

## P1｜提案在 route handler 里各写一条日志，会让每请求日志从 1 条变成 2 条（重复且分叉）
- **哪里有问题**：提案 §1 要求在「各 API route 的出口处补记一条 `http_request`」。但 `server.mjs:66-83` 已经在 `res.on('finish')` 记录了同一份语义的 `http_request`（request_id/method/path/status/duration_ms）。提案没有说明是"替换"还是"追加"，按字面实现就是追加。
- **后果**：① 每条请求产生两行 `message:'http_request'`，字段集不同（一行有 user_id 无 client_ip，一行反之），后续按 `message` grep 会拿到大量半残记录，用户报错时按 request_id 定位会得到两行需要人工合并；② 日志体积/行数直接翻倍，下面 P2/P3 的量级估算也翻倍；③ 两处 `duration_ms` 的口径不同（route 内的看不清中间件与 Next 渲染开销，`server.mjs` 的才是真实端到端），分析时会得到互相矛盾的"慢请求"结论。落点在 `server.mjs:66-83` 与提案 §1 的 log 调用点。
- **建议**：只在 `server.mjs` 的 `res.on('finish')` 一处记，不新增第二处。user_id 不要在 route 里补——`res.on('finish')` 时若 route 已把 userId 挂到 `res`（如 `res.locals.userId`）就带上，拿不到就留空。这样保住了"一行一请求"这个已经是事实的单一口径。

## P2｜`log.ts` 的写日志是同步阻塞 stdout，90 天全量访问日志会直接压到请求尾延迟上
- **哪里有问题**：`src/server/platform/log.ts:12-21`，`emit()` 用 `process.stdout.write(\`${line}\n\`)`，是同步调用；`JSON.stringify` 也在请求线程里同步执行。提案把 user_agent 与 referer 加进来，单行变长（UA 普遍 100-200 字节，referer 可能很长），且 §3 要求 JSONL 保留 90 天。
- **后果**：容器里 stdout 是管道/文件时，`process.stdout.write` 在队列满时会阻塞事件循环。这条调用点在 `res.on('finish')` 里（`server.mjs:66`），意味着**响应已经发出但连接未释放**，阻塞会推迟下一条请求的处理，表现成"吞吐下降、p99 长尾抖动"，且 `duration_ms` 统计不到这段（它只到 finish 为止），监控上看不出来。用户多、日志行变长后这是非线性恶化。
- **建议**：① 明确接受"写日志在请求路径上"，就必须给 `server.mjs` 的 writer 加一个内存缓冲 + 定时/满批 flush（非背压阻塞路径），或至少 `write()` 返回 false 时做有界队列 + 丢弃策略并计数；② 不要在这里引入 user_agent/referer 的原文（见 P4 的字段裁剪），单行控制在 ~300 字节内。

## P3｜字段扩展会把每请求日志从固定的 ~200 字节推到不可控长度，直接决定 90 天磁盘与扫描成本
- **哪里有问题**：提案 §1 新增 `user_agent` 与 `referer` 两个**无长度上限**的外部输入；§3 定 90 天；§4 用脚本按 user_id 分组统计。`server.mjs` 现有字段（`server.mjs:70-82`）长度基本可控，`path` 也已在 `server.mjs:52` 用 `split('?')[0]` 截掉 query。
- **后果**：referer 是攻击者/爬虫可任意放长的字段，一行日志可达数 KB；配合 P1 的重复行，磁盘与后续 `jq`/脚本的解析时间都按行长度线性涨，90 天保留期把这个问题放成常驻成本。§4 的"用脚本按 user_id 分组"在没有索引的 JSONL 上意味着每跑一次分析全量扫 90 天文件，随数据量线性劣化。落点：提案 §1/§3/§4。
- **建议**：① 两个字段都截断（如 UA 256、referer 512 字符，超长截断并标记 `truncated:true`）；② 更省的做法是**不存 UA 原文**，只需解析出 `ua_family`（一个短枚举）用于路径分析；③ §4 的分析不要每次全量扫 90 天——按天分文件（`access-YYYY-MM-DD.jsonl`），分析先按日期范围挑文件；④ 明确日增量估算（日请求数 × 单行字节）再定保留期，90 天这个数字要有依据而不是拍定。

## P4｜按 user_id 聚合把"每请求一次写"从 append 变成需要长期可检索，但没有对应索引/分区设计
- **哪里有问题**：提案 §2「按 user_id 聚合」+ §4「按 user_id 分组统计」要求对 `user_id` 做高基数分组。JSONL 是纯 append，任何按 user_id 的检索都退化成全扫。
- **后果**：`user_id` 是高基数字段（每用户一行/多行），90 天数据下任何"某个用户的完整路径"查询都是 O(总行数) 的全文件扫描，交互式回溯（提案"便于回溯"）在数十 GB 量级上不可用。文件:行号指向提案 §2/§4 与 `migrations/` 中**不存在**任何为访问日志建表的迁移（已核对 0001-0042，只有 `rate_limiter_flexible`、`operation_records` 等，无 access log 表）。
- **建议**：不要走 JSONL 全扫。要么按 `user_id` 哈希分桶写多个文件（`access/ab/<shard>.jsonl`），要么写一张 SQLite 表（可复用 `db.ts` 的 WAL 单例，`db.ts:56-69`）并建 `(user_id, ts)` 索引——后者才让 §2/§4 的聚合成本从 O(全量) 降到 O(该用户行数)。若坚持 JSONL，至少在 §4 的脚本里明确"只扫指定日期范围"。

## P5｜`ctx.userId` 的取值范围要精确核对：`currentContext()` 在代码里不存在，且拿它的代价是每请求一次 DB 读
- **哪里有问题**：提案写「`user_id: ctx.userId`, 来自 `currentContext()`」。实际代码里 `src/server/platform/context.ts` 只有 `CallerContext` 接口与断言函数，没有 `currentContext()`；上下文由 `identity/service.ts:246+` 的 `resolveSession` 每请求从库读（`context.ts:2-6` 注释明确"每次请求从数据库读取，不缓存"），并且可能顺带一条 `UPDATE user_sessions SET last_seen_at`（`identity/service.ts` 中 `activityWriteIntervalSeconds` 节流处）。
- **后果**：如果为了在 access log 里拿到 user_id 而在 route 外层再调一次上下文解析，就是**每请求多一次 SQLite 读（甚至一次写）**。`db.ts:8-9` 明确 better-sqlite3 是同步驱动、等待会阻塞线程；写还会抢 WAL 写锁，与 `synchronous = FULL`（`db.ts:60`）叠加。并发上去后这会变成实打实的 p99 恶化，而它纯粹是为了打日志。
- **建议**：绝不为日志新增一次上下文解析。复用 route 内已经解析好的那个 `ctx`（route 已经有引用），把 userId 传递到 `res.on('finish')` 能读到的位置即可；匿名请求记 `user_id: null` 而不是去查。同时提案里的 `currentContext()` 应改成"route 已有的 ctx 变量"这一事实描述。

## P6｜匿名/爬虫流量会把高基数与体积同时放大，提案未设采样与排除
- **哪里有问题**：`server.mjs:40-42` 的 `isQuiet` 只排除了 `/_next/`、`/api/health`、`/favicon.ico`。提案要"完整浏览路径"（§预期），意味着要放开或新增记录面。
- **后果**：爬虫与匿名访问是量级最大、user_id 为空的部分，它们占据几乎所有磁盘与扫描成本，却对 §2 的"按 user_id 还原路径"零贡献。日志被淹后，真正需要的登录用户行反而难定位。
- **建议**：保持/扩展现有 `isQuiet` 思路，并明确策略：匿名请求要么只记计数（不落 JSONL 明细），要么采样（如 1/10）。行为分析的目标用户在登录态，没必要为匿名流量付全量成本。

---

一句总结：这份方案在性能上是"每请求新增同步 I/O + 无上限字段 + 90 天全量 JSONL + 按高基数字段全扫聚合"四个乘法叠加，而现有 `server.mjs:66-83` + `log.ts:12-21` 已经有一条单点、口径正确的访问日志可以增量扩展。建议改为"单点记录 + 字段截断/采样 + 按天或分桶存储"，并在提案里补上日增量与查询成本的量化估算。
