# 安全工程师评审：n61 「审核员」角色与待审任务分配方案

我已实际读取 `proposal.md`（全 49 行）、`migrations/0001_baseline.sql`、`0002_triggers.sql`、`0040_user_roles.sql`、`0041_role_notifications.sql`、`0042_audit_immutable.sql`，以及 `src/server/platform/context.ts`、`src/server/modules/moderation/service.ts`、`src/server/modules/roles/service.ts`、`src/server/modules/roles/ownership.ts`。

**总体结论：不可实施。** 该方案在权限模型、审计留痕、不可变性约定、状态机前置条件四个方面都违反现有系统的硬性约束；其中第 1、3 条属于越权或伪造通道，必须阻塞（block）。

## 问题 1（严重）：把「审核员」放进 `users.role`，直接击穿 `isAdmin()` 的权限底座

**① 有问题部分** — proposal.md:8-14（`migrations/0043_moderator_role.sql`，`CHECK (role IN ('user','admin','moderator'))`）

数据库里这一列是权限底层，不是身份标签。`0001_baseline.sql:23` 定义 `role TEXT NOT NULL CHECK (role IN ('user','admin'))`；`src/server/platform/context.ts:22-24` 的 `isAdmin()` 只认 `ctx.role === 'admin'`；`context.ts:26-29` 的 `CallerContext.role` 类型就是 `'user' | 'admin' | null`。

更关键的是，仓库已经就这一点做过明确设计并写了理由。`0040_user_roles.sql:6-11` 原文：

> `users.role` 是**权限底座**（user / admin，决定能否进后台、能否审内容），而测评员 / 开发者是**叠加在普通用户之上的能力标记**……混进同一个 CHECK 会让「管理员是不是测评员」这种问题没有答案。

`roles/service.ts:13-15` 也重申：「**身份不是权限底座**：users.role（user/admin）仍然决定能否进后台、能否审内容；user_roles 只是能力标记，`isAdmin()` 的行为一个字都不变。」

**② 后果** — 一旦写入 `moderator`，`CallerContext.role` 的类型收窄（context.ts:10-12）就会被违规赋值，同时所有 `isAdmin()` 分支对 moderator 一律返回 false。但方案第 4 条（proposal.md:44-45）又要求审核员用 `/admin/submissions` 页处理，那么实际放行的只能是通过人为放松权限检查来实现的通道。而任何一处为了「让 moderator 也能进后台」而改成 `role !== 'user'`、`isAdmin() || role==='moderator'`，都会立刻让 moderator 继承后台全部能力（`decideByAdmin` 之外还有设置、用户管理、`operation_records` 相关路径）。**也就是说，审核员实际上就是管理员，只是名字不同**。而且 `moderator` 与 `user_roles.role_type='reviewer'`（0040:30）会形成两套互相矛盾的「审核员」定义。

**③ 建议** — 不要动 `users.role` 的 CHECK。审核权限改用已有的 `user_roles`（`role_type='reviewer'` + `status='active'`）作为唯一事实来源；在 `context.ts` 增加独立的 `isReviewer(ctx, db)` 判定，并且必须每次请求从数据库读取（沿用 context.ts:1-6 的「角色每次请求重读」原则，避免撤销后残留）。后台入口用 `assertCanReview()`（新增）而不是复用 `assertCanAdmin`。若确需第三种底座角色，必须另开一份设计文档明确「moderator 能做什么、不能做什么」，并同步修改 `CallerContext.role` 的联合类型与全部 `isAdmin` 调用点；不能用一条 ALTER 悄悄扩大集合。

## 问题 2（严重）：分配逻辑静默跳过所有 SQLite 限制，`reviewer_id` 可能指向已禁用或非审核员

**① 有问题部分** — proposal.md:24-42

```ts
const reviewers = db.prepare("SELECT id FROM users WHERE role = 'moderator' AND account_status = 'active'").all();
pending.forEach((p, i) => { ... reviewers[i % reviewers.length].id ... });
```

**② 后果** —

- `reviewers` 为空时 `reviewers[i % 0]` = `reviewers[NaN]` = `undefined`，`.id` 会抛 `TypeError`。这是每 5 分钟跑一次的定时任务，会永久失败，队列继续积压（proposal.md:2-4 的痛点一个都没解决）。
- `SELECT *` 加 `LIMIT 50`（proposal.md:27-29）**没有 `ORDER BY`**，也没有 `WHERE NOT EXISTS (SELECT 1 FROM review_assignments ...)`。每轮都取同一批最早的行，同一批 50 条被反复分配；`review_assignments` 表（proposal.md:17-22）**没有任何唯一约束**，于是同一 submission 会生成无限多行，同一审核员重复看到同一条。
- 「active」是在分配那一刻的快照。方案没有撤销、禁用、离职的回收逻辑，分配后审核员被禁用，任务就永久卡在一个无权的人名下。
- 轮询分配（`i % len`）没有考虑审核员当前负载，这是可用性缺陷，但在安全上是「分配不均导致单人可审完全部队列」的隐蔽风险面。

**③ 建议** — 分配查询加 `WHERE processing_state='manual_review' AND NOT EXISTS (SELECT 1 FROM review_assignments a WHERE a.submission_id = content_submissions.id)` 加 `ORDER BY submitted_at, id`；先判 `if (reviewers.length === 0) { 记日志 + 告警, return; }`；`review_assignments` 加 `UNIQUE (submission_id)`（或 `UNIQUE(submission_id, reviewer_id)` 加状态列）；分配与查询放同一事务，并用 `INSERT ... ON CONFLICT DO NOTHING` 实现幂等。审核员权限判定必须在**审核动作发生的那一刻**重新校验 `user_roles.status='active' AND users.account_status='active'`，不能信任分配时快照。

## 问题 3（严重）：新角色绕过 `content_moderation_records` 的 `actor_kind` 审计约束

**① 有问题部分** — proposal.md 通篇未提审核记录表

`0001_baseline.sql` 的 `content_moderation_records` 有 `actor_kind` 与 `actor_user_id` 的成对约束；`src/server/modules/moderation/service.ts:218-226` 的 `appendRecordWithin` 明确：`system` 身份必须有 `task_id`，非 system 身份必须有 `actor_user_id`；`service.ts` 的 `decideByAdmin`（约 469-478 行）把 `actorKind` 硬编码为 `'admin'`，并 `if (!isAdmin(ctx)) throw err.forbidden(...)`。

**② 后果** — 「审核员」既不是 `system`、也不是 `admin`。方案没有给出第三条 `actor_kind` 取值，那么审核员的每一次决定只能：要么借 `actorKind:'admin'` 写入，**导致审计记录把审核员伪造成管理员**（`operation_records` 由 `0042_audit_immutable.sql:19-27` 的触发器永久不可改不可删，这个伪造因此无法事后纠正）；要么根本不写 `content_moderation_records`，那么人工审核环节出现一个**完全无审计的审查路径**，这与 0042 整篇修的就是「审计可被绕过」直接冲突。

**③ 建议** — 在迁移中显式扩展 `actor_kind` 取值（需重建表并改 CHECK，参考 0041 的重建手法 `0041_role_notifications.sql:33,68-73`），新增 `'moderator'`；给 `ModerationService` 增加 `decideByReviewer(ctx, input)`，内部用 `assertCanReview(ctx)` 加 `actorKind:'moderator'`；同时保证 `operationKey` 仍走 `(submission_id, operation_key)` 幂等去重（service.ts:230-234）。审核员权限与 `content_moderation_records` 的写入必须在同一事务内。

## 问题 4（高）：分配表没有不可变性与外键删除语义，破坏 0042 建立的审计不可变约定

**① 有问题部分** — proposal.md:17-22

```sql
CREATE TABLE review_assignments (
  id TEXT PRIMARY KEY, submission_id TEXT NOT NULL REFERENCES content_submissions(id),
  reviewer_id TEXT NOT NULL REFERENCES users(id), assigned_at INTEGER NOT NULL);
```

**② 后果** —

- 外键未声明 `ON UPDATE/ON DELETE`。`0001_baseline.sql` 与 `0040` 的每一处都显式写了 `ON UPDATE RESTRICT ON DELETE RESTRICT`（如 0040:20、0040:45），`0040:28-30` 还专门为撤销态加 CHECK 保证「谁在什么时候撤的」留痕。本表缺失，`DELETE FROM users` 会被默认 NO ACTION 挡住，但错误信息与全库风格不一致，且无 `revoked/unassigned` 状态列，任务被回收、改派后历史完全丢失。
- 没有 `CHECK (assigned_at >= 0)`，违反全库所有时间列的约定（0001 中每一列都有）。虽然不直接是安全漏洞，但它是上面第 2 条「异常行与脏数据」的前置条件。
- 更严重的是：这张表是「谁审了谁」的唯一凭据，却**没有任何 BEFORE UPDATE / BEFORE DELETE 守卫**。`0042_audit_immutable.sql:1-27` 刚为 `operation_records` 补上不可删不可改触发器，理由正是「删除审计行即可让已消费的 operation_key 重新可用……构成不需要改代码的伪造通道」。`review_assignments` 一旦可随意删除，审核员删掉自己「被分配过某条内容」的记录，就同时抹掉了利益冲突证据与工作量证据。

**③ 建议** — 补齐 `ON UPDATE RESTRICT ON DELETE RESTRICT`、`CHECK (assigned_at >= 0)`、`UNIQUE (submission_id)`；增加 `status TEXT NOT NULL CHECK (status IN ('assigned','completed','reassigned','expired'))` 与 `unassigned_at/unassigned_by`（成对 CHECK，学习 `0040:28-30` 的写法）；参照 0042 增加 `trg_review_assignments_no_delete` / `no_update` 触发器，或至少把改派实现为「追加新行 + 旧行标记 superseded」而非 UPDATE/DELETE。

## 问题 5（高）：审核入口放在 `/admin/submissions`，没有数据级授权，属 IDOR 风险

**① 有问题部分** — proposal.md:44-45（「审核员通过 `/admin/submissions` 页面处理被分配的内容」）

**② 后果** — 方案只说「处理被分配的内容」，但没有任何一处规定服务层必须校验 `review_assignments.reviewer_id = ctx.userId` 且 `submission_id` 匹配。现有 `decideByAdmin`（service.ts 约 469 行）只做 `isAdmin(ctx)` **不校验对象归属**，因为对 admin 而言全量可见是合法的；一旦把它开放给审核员，同一条路径就变成「只要拿到 submissionId 就能对任意提交作出裁决」。这是典型的 IDOR：审核员可以审未分配给自己、甚至分配给了别人的内容，绕过第 2 条的负载均衡，还可针对特定作者的稿件定向放行或驳回。

**③ 建议** — 独立 `decideByReviewer`，在事务内先做 `SELECT 1 FROM review_assignments WHERE submission_id=? AND reviewer_id=ctx.userId AND status='assigned'`；无该行一律 `err.forbidden()`，而不是 `not found`（避免探测）；后台列表页按 `reviewer_id` 过滤，不依赖前端隐藏。同时保留「管理员可审全量」的独立分支，两者不共用一个函数。

## 问题 6（中）：`manual_review` 不是普通的待分配池，缺少前置条件校验

**① 有问题部分** — proposal.md:2-4 与 proposal.md:27-29

方案把 `processing_state='manual_review'` 当成「排队等审核员」的状态在用，但该状态的真实语义是「**自动放行失败后的兜底**」。`service.ts:12-14` 是硬规则：

> **外部内容筛查未配置时绝不自动放行、也不认定违规**：停在 `manual_review`（或回 `pending` 并记 `fault`），永不自动 `approved`。

`service.ts` 在 `not_configured` / `fault` / `inconclusive` 三种情况下都转 `manual_review` 并记 `fault`（见 runRuleCheck 的 434-455 行附近注释与 `isFault` 分支）。

**② 后果** — 队列里混着两类完全不同的内容：一类是「人工判断过、确实灰色」的，一类是「**筛查系统根本没配置或故障**、无人看过任何一眼」的。把后者批量分给一个权限更低的角色，等于降低了这批高风险内容的人工门槛——它们是全系统唯一未经任何自动化过滤的通道。方案没有任何字段区分两者，审核员无法知道自己在审的是哪一种。

**③ 建议** — 分配前按 `content_moderation_records` 里最近一条 `stage='content_screen'` 的 `result` 区分（`fault` 与 `manual_review` 分池）；带 `fault` 的条目要么仍由管理员处理，要么在 UI 上强制标注「自动化筛查未生效」。审核员的放行决定建议记录到 `evidence` 里，便于事后追责。

## 问题 7（中）：角色授予通道与提权面未定义

**① 有问题部分** — proposal.md:8-14 只加 CHECK 取值，通篇未说明「谁可以把某人变成 moderator」

**② 后果** — 现有 `setUserRole` 走 `operation_records` 的 `UNIQUE(action_type, operation_key)` 做幂等（`0042_audit_immutable.sql:4-7` 明确指出这一点被 `setUserRole/setUserStatus` 依赖）。如果 0043 只改 CHECK 而不接这条通道，管理员可以直接 `UPDATE users SET role='moderator'` 绕过审计；反之若改了 `setUserRole` 却未同步 `user_roles`，会出现同一人在两套身份表里状态不一致——而「撤销」在 `user_roles` 里有完整的 `revoked_by/revoked_at`（0040:28-30），在 `users.role` 上**没有**任何撤销留痕字段。

**③ 建议** — 明确禁止直接改 `users.role`（可在 0002 风格下加 BEFORE UPDATE OF role 触发器，要求存在对应的 `operation_records` 行）；授予、撤销都必须走 `setUserRole` 并写审计；撤销时同步失效 `review_assignments` 中该审核员的 `assigned` 行。
