# 性能工程师评审：n61 moderation-queue 方案

我读了方案、`0001_baseline.sql`、`0002_triggers.sql`、`0038`、`0040`、`0041`、`0042`、`0006`，以及 `src/worker/main.ts`、`tasks/service.ts`、`tasks/constants.ts`、`platform/db.ts`、`platform/context.ts`、`modules/moderation/service.ts`。下面每条都只关注**性能与运行时开销**，安全问题只在它会直接放大开销时提及。

---

## 1. 分配逻辑：每次循环重新 `prepare`，且逐行单条 INSERT（N+1 写入）

**① 哪部分有问题**
方案 §3 的代码块（proposal.md:31–41）。`db.prepare(...)` 被写在 `pending.forEach` **内部**，每行都要重新编译一次语句；50 条待审就是 50 次 `prepare` + 50 次独立 `INSERT`。

**② 后果**
- 每轮 50 次语句编译 + 50 次独立事务提交。better-sqlite3 是同步驱动（`db.ts:8-12` 明确写了「等待会阻塞所属线程」），每条 INSERT 若不在显式事务里，都是一次独立的隐式事务 → 50 次 WAL 提交、50 次 fsync 级别的刷写。连接已配 `synchronous = FULL`（`db.ts:56`），单次提交的代价被**放大**，不是默认的 NORMAL。
- worker 主循环里 `MAX_CONCURRENT_TASKS = 4`（`constants.ts:18`）的任务要靠同一个连接跑（`getDb()` 是进程级单例，`db.ts:66-73`）。分配循环一占住同步线程，4 个任务的处理与 `renew` 续期（`service.ts:250`，要求 `lease_expires_at > now`）全部被拖延。租期只有 120s（`constants.ts:21`），分配批一旦变慢，续期晚到就可能让在跑任务的租约过期，进而被 `recoverExpired` 回收并产生重复执行。
- 随着 `review_assignments` 增长（每 5 分钟一批，一天 288 批 × 最多 50 条 = 14,400 行/天），INSERT 的索引维护成本单调上升，而这里**没有任何清理/归档策略**（见第 4 条）。

**③ 建议**
- `prepare` 提到循环外，并整体包进一个事务（项目已有 `withTransaction`，`service.ts:19` 在用）。方案代码里 `db.prepare(...).run()` 逐个裸跑，正是 `db.ts:9-11` 那条纪律要防的写法。
- 用多值 `INSERT INTO ... VALUES (...),(...)` 或**单条 `INSERT ... SELECT`** 完成分配，让 SQLite 一次成型，避免 50 次往返。

## 2. 分配查询没有 `ORDER BY`，却有 `LIMIT 50` —— 索引扫到哪算哪，且与游标方式冲突

**① 哪部分有问题**
proposal.md:33–35：`SELECT * FROM content_submissions WHERE processing_state = 'manual_review' LIMIT 50`。

**② 后果**
- 基线里这条查询**有**可用索引：`idx_submissions_state ON content_submissions(processing_state, submitted_at, id)`（`0001_baseline.sql`，提交记录小节末）。但方案没写 `ORDER BY`，SQLite 只会按索引顺序返回，**不保证**是 FIFO。积压场景下（方案开篇说的就是「积压」），最老的那批可能被反复跳过、永远轮不到，而新到的先被分配。从性能角度这是**饥饿**：队尾积压无限增长，队列长度不收敛。
- 用 `LIMIT 50` 且**不加 `OFFSET`/游标**做「每 5 分钟扫一遍」，意味着每次都是**从索引头部重新扫前 50 行**。前 50 行一旦已被分配但状态没变（方案没改 `processing_state`！见第 3 条），下一轮扫到的还是同一批 50 行 → 生成 50 条重复分配，无限重复，直到永远。

**③ 建议**
- 补 `ORDER BY submitted_at, id`（正好沿用 `idx_submissions_state` 的列序，可走索引免排序），保证 FIFO 且稳定。
- 加游标/水位：要么记录已分配的 `(submitted_at, id)` 上界，要么用 `EXCEPT`/`NOT EXISTS` 排除掉已存在于 `review_assignments` 的 submission。否则这个循环的**有效工作量恒为 0，而开销恒定**——纯空转。

## 3. 「每 5 分钟全量扫描」+ 未过滤已分配的提交 → 分配表爆炸与二次方增长

**① 哪部分有问题**
proposal.md:27–41。查询只过滤 `processing_state = 'manual_review'`，**没有排除**已经在 `review_assignments` 里的 `submission_id`；而且分配表没有唯一约束。

**② 后果**
- 设积压 N 条 manual_review、每 5 分钟一轮，则每轮新增 `min(50, N)` 行。一天 288 轮 → 最多 +14,400 行/天，且**同一 submission 被反复分配**（同一审核员会看到同一条内容几十次）。
- 更糟：`review_assignments` 没有 `UNIQUE(submission_id)`，重复行会累积，审核页列表查询（方案 §4 说走 `/admin/submissions`）要 `JOIN` 这张表，表越大越慢，且没有为其列出的任何索引（连 `submission_id` 和 `reviewer_id` 都没建索引）。见第 4 条。
- 每轮都是一个全量 `SELECT ... LIMIT 50` + 最多 50 次写，**空转成本**也照样付。

**③ 建议**
- 分配查询加 `AND NOT EXISTS (SELECT 1 FROM review_assignments ra WHERE ra.submission_id = cs.id)`，或建 `review_assignments(submission_id)` 上的 `UNIQUE`，让重复分配被数据库挡住而不是靠应用逻辑。
- 改成**事件驱动**：内容进入 `manual_review` 的 `transition()`（`moderation/service.ts` 的 `transition`）时入队一次分配任务，而不是定时全表扫描。现有基础设施已支持——`TasksService.enqueue` 带 `deduplicationKey` 幂等（`service.ts:196-206`），天然适合「按 submission 去重，只分配一次」。

## 4. 新表缺索引，而方案没为它建任何索引

**① 哪部分有问题**
proposal.md:18–23 的 `CREATE TABLE review_assignments` —— 只有主键 + 两个外键 + `assigned_at`，**一个索引都没有**。

**② 后果**
- 对照基线惯例，每张被查询的表都配了索引（`0001_baseline.sql` 的 `idx_submissions_state`、`idx_moderation_submission`；`0038` 的 `idx_reports_queue`、`idx_forum_post_drafts_by_author`）。本方案是唯一的例外。
- 两个外键列 `submission_id`、`reviewer_id` 无索引 → 审核员登录查「我的待审」（`WHERE reviewer_id = ?`）是全表扫；`DELETE`/`UPDATE` `content_submissions` 与 `users` 时，SQLite 的外键检查需要反查子表，无索引即**每行一次全表扫描**（`db.ts:52` 显式开了 `defer_foreign_keys = ON`，外键检查一定发生）。用户被删时，`users` 上也没有 `role` 相关索引可借力。
- worker 的定时全表扫描 `WHERE role='moderator' AND account_status='active'`（proposal.md:36-38）：`users` 表**没有 role 或 account_status 的索引**（我核了 `0001_baseline.sql` 的 users 定义与索引段，只有主键和若干唯一键）。审核员本来就没几个，但这个查询每 5 分钟全表扫一遍 `users` 是纯粹浪费。

**③ 建议**
- 建 `CREATE UNIQUE INDEX uq_review_assignments_submission ON review_assignments(submission_id)`（同时解决第 3 条的重复分配）。
- 建 `CREATE INDEX idx_review_assignments_reviewer ON review_assignments(reviewer_id, assigned_at DESC)` 服务「我的待审」列表。
- 审核员查询要么极少执行（改为变更时缓存/物化），要么给 `users(role, account_status)` 建部分索引（`WHERE role = 'moderator'`）。若审核员查询结果在 5 分钟循环里复用，就应把它提出循环，避免每轮重复查。

## 5. `ALTER TABLE ... DROP CONSTRAINT` 在 SQLite 里根本不存在 —— 这条迁移会失败，且其"正确写法"是全表重建（重成本 + 锁）

**① 哪部分有问题**
proposal.md:11–14：`ALTER TABLE users DROP CONSTRAINT users_role_check;`。

**② 后果**
- SQLite **不支持** `DROP CONSTRAINT`，这条语句直接语法错误、迁移中止。`0040_user_roles.sql:15-17` 和 `0041_role_notifications.sql:6-8` 都刻意记录了「SQLite 改不了 CHECK，只能建新表 → 拷 → 删 → 改名」，且需要 `PRAGMA foreign_keys = OFF` + `BEGIN/COMMIT`（`0041` 文件头就是 `-- dsh:migration-transaction=off`）。本方案完全没走这套，属于**对目标数据库的能力误判**。
- 性能视角更要紧的是：一旦照 0041 的正确手法重写，就是**整表重建 `users`**。`users` 被 `0002_triggers.sql` 的 33 个触发器、以及几乎所有业务表外键引用，重建期间 `PRAGMA foreign_keys = OFF` 窗口里**所有外键校验失效**，且重建 `users` 会连带触发各引用表的索引重算。`0042` 文件头专门提到过 `restore-backup.mjs --force` 整库覆盖的风险面，重建 `users` 属于同一级别的高风险操作，必须在维护窗口做。
- `/api/health` 与启动自检（`instrumentation-node.ts:26-38` 的 `selfCheck`）依赖 `schema_version` 与表存在性；迁移中途失败会让自检长期报错（`db.ts` 单例在首次 `getDb` 时已打开连接）。

**③ 建议**
- 照 `0041_role_notifications.sql` 的既有范式重写：`-- dsh:migration-transaction=off` + `PRAGMA foreign_keys = OFF` + `BEGIN`/`COMMIT` + 末尾 `PRAGMA foreign_key_check`。
- 更省事的替代：**不要动 `users.role`**。`0040` 已经论证过「能力标记用 `user_roles` 表存、`users.role` 是权限底座」，且已有 `role_type IN ('reviewer','developer')`（`0040_user_roles.sql:29`）。审核员完全可以是 `role_type = 'reviewer'` 的 `user_roles` 行——**零表重建、零锁窗口**，直接消灭这一整条风险。方案另起 `moderator` 值与既有设计冲突（`0040` 的 `role_type` 闭集里没有 `moderator`），这本身也说明方案没消化 0040。

## 6. 方案 §4 复用 `/admin/submissions`，但该入口是按 `isAdmin` 守的 —— 审核员会被挡在外面，或被迫放宽守卫

**① 哪部分有问题**
proposal.md:45：「审核员通过 `/admin/submissions` 页面处理被分配的内容」。

**② 后果**
- `context.ts:37-44` 的 `assertCanAdmin` 硬性要求 `ctx.role === 'admin'`，且 `isAdmin`（`context.ts:25-27`）只看 `role === 'admin'`。仅把 `users.role` 扩出 `'moderator'` **不会**让审核员通过这道守卫。要放行就得改 `assertCanAdmin` 或另开一条判定——而 `context.ts:3-4` 明说角色是**每次请求从数据库读**、不缓存。新增一条「读 `user_roles` 判 reviewer」的路径，会让**每个受保护请求多一次 DB 往返**（若做成「role 或 user_roles 任一满足」的联合判断，最坏情况每请求 2 次查询）。
- 性能要点：这是**热路径**（后台每个请求都过）。若方案不加索引，就是每请求一次 `user_roles` 全表扫——`0040` 已建 `idx_user_roles_by_user ON user_roles(user_id, role_type)`，能覆盖，但前提是查询写法对上 `(user_id, role_type)` 前缀。

**③ 建议**
- 明确权限判定走 `user_roles`（复用已有的 `idx_user_roles_by_user`），而不是扩 `users.role`。这样同时解决第 5 条的表重建问题。
- 不要在 `assertCanAdmin` 里加「或」逻辑——另开 `assertCanModerate(ctx)` 并在该请求内**复用同一次** `user_roles` 查询结果（一次请求一次查询），别让热路径叠加成两次往返。

## 7. 方案没有说明分配发生的**位置**（Web 进程 vs worker），这决定它是否拖慢用户请求

**① 哪部分有问题**
proposal.md:27 只说「每 5 分钟扫描」，没写这个 5 分钟循环跑在哪。

**② 后果**
- 若跑在 Next 进程（`src/server/...`，`getDb()` 同样是进程级单例，`db.ts:66`），better-sqlite3 是**同步**驱动。50 次独立 INSERT + 每次 `synchronous = FULL` 的提交（`db.ts:56`）会**阻塞用户请求**。`db.ts:9-11` 原文：「等待会阻塞所属线程，因此业务事务保持短小，不在事务内做网络请求、图片处理或 Markdown 解析」——本方案的 50 次裸写正好违反这条。
- 若跑在 worker（`src/worker/main.ts`），则和 4 个并发任务抢同一连接，见第 1 条。

**③ 建议**
- 明确放到 worker 的定时排程里（现有机制齐全：`worker/scheduled.ts` 的 `ensureDailyDiscoveryTask` 就是「按天幂等 + 重启自愈」的范式，`DISCOVERY_SCHEDULE_CHECK_MS = 60_000` 那个常量说明作者知道「不必每 tick 都查」）。5 分钟一次同理，且应做成**幂等的排程任务**而不是循环内联代码。
- 无论放哪，分配批必须包在一个事务里，把 50 次提交压成 1 次。

## 8. 无并发保护：多实例/多副本部署下分配会重复

**① 哪部分有问题**
proposal.md:27–41 是裸的「查 50 条 → 逐条插」，没有 `claim`/`CAS`/租约。

**② 后果**
- 任务的领取是有严格 CAS 的（`service.ts:150-159`，`WHERE ... execution_token IS NULL` + `changes !== 1` 判定），项目对「并发下别做重复事」有明确纪律。而分配逻辑完全没照这个来。
- 部署两个 worker 或两个 Web 副本时，同一 5 分钟窗口内两个实例都会扫到同样 50 条 → 每条被插两次。配合第 4 条「无唯一约束」，重复直接落库；配合第 3 条「不过滤已分配」，重复还会**持续**发生。
- 性能上，这是双倍的写入开销 + 双倍的 WAL 增长，而产出只有一半有效。

**③ 建议**
- 用 `uq_review_assignments_submission` 唯一索引 + `INSERT OR IGNORE`，让并发重复由数据库静默丢弃（零应用层协调成本，且幂等）。
- 若要「每轮只让一个实例干活」，套用 `TasksService` 的 `deduplicationKey` 幂等入队（`service.ts:196-206`），把「分配第 K 批」做成去重键。

## 9. 轮询分配的首个副作用：`reviewers[i % reviewers.length]` 在审核员为 0 时崩溃，且分配比例失衡

**① 哪部分有问题**
proposal.md:39：`reviewers[i % reviewers.length].id`。

**② 后果**
- `reviewers.length === 0`（尚未有任何 moderator，方案 §1 只说扩闭集，没说谁来当）→ `% 0` 得 `NaN` → `reviewers[NaN]` 为 `undefined` → 读 `.id` 抛 `TypeError`。这是**每 5 分钟必炸**的循环。如果循环体在事务外、异常未被捕获，worker 主循环的异常会打断整轮（`main.ts` 的 `run` 结构），牵连在跑的 4 个任务。
- 即便非空，`i % n` 只按「本轮序号」轮转，不看各审核员**已有多少待审**。审核员负载漂移时（比如一个审核员请长假），分配依旧均摊，积压集中到某人身上——「分散压力」的预期（proposal.md:48）在这些情况下不成立。

**③ 建议**
- 空审核员时**提前返回**（`if (reviewers.length === 0) return { skipped: 'no_reviewers' }`，参考 `scheduled.ts` 的 `skippedReason` 模式，把原因写日志），别让 `% 0` 变成定时爆炸。
- 分配按**当前在办量最少**（`LEFT JOIN review_assignments GROUP BY reviewer_id ORDER BY COUNT(*) ASC`，配合第 4 条的 `reviewer_id` 索引）而不是 `i % n`。

## 10. 缺少对「积压不收敛」的可观测性，性能问题会被静默吞掉

**① 哪部分有问题**
proposal.md:47-49「预期」只有两句定性描述，没有任何指标。

**② 后果**
- 前 9 条的失败模式（空转、重复分配、饥饿、表膨胀）**都不会报错**——它们只表现为「CPU 白烧、库变大、没人处理」。没有指标就没有发现路径。
- 现有基础设施有落点：`background_tasks.progress`（`service.ts:14` 提到「后台页据此展示这一轮做了什么」）、`log.info`（`scheduled.ts` 排入成功时打日志）。方案一个都没用。

**③ 建议**
- 每轮结束记录：`pending_count`、`assigned_count`、`skipped_count`、`no_reviewer` 标记、耗时。至少 `log` 一行，最好写 `progress`。
- 加一个收敛判据：若连续 N 轮 `pending_count` 不降，就是第 2 条（饥饿/空转）出问题的信号，应告警而不是继续空跑。

## 汇总（按性价比排序）

| # | 问题 | 类型 | 修复成本 |
|---|---|---|---|
| 5 | `DROP CONSTRAINT` 在 SQLite 不存在；正解是全表重建 `users` | **迁移必失败** + 大锁 | 改用 `user_roles`（零成本） |
| 3+4 | 分配不过滤已分配 + 新表无任何索引 | 表无限膨胀 + 全表扫 | 一个唯一索引 |
| 1 | 循环内 `prepare` + 50 次裸 INSERT | 阻塞同步线程 / 拖垮续期 | 包事务 + 提出 prepare |
| 2 | 无 `ORDER BY` 的 `LIMIT 50` + 无游标 | 饥饿 + 有效工作恒为 0 | 一行 `ORDER BY` + `NOT EXISTS` |
| 7 | 未定执行位置 | 可能阻塞用户请求 | 移到 worker 排程 |
| 8 | 无并发保护 | 多副本重复写 | `INSERT OR IGNORE` |
| 9 | `% 0` 崩溃 / 负载失衡 | 每 5 分钟炸 | 提前返回 |
| 6 | `/admin/submissions` 走 `assertCanAdmin` | 审核员被挡 / 热路径多一次查询 | 复用已有索引 |
| 10 | 无指标 | 问题静默 | 两个计数 |

**一句话结论**：这个方案的分配循环是「每 5 分钟全表扫一遍、重复插入同一批行、还不建索引」的原型代码状态；而它打算改的 `users.role` 恰好是 `0040` 已经论证过**不该**往里塞能力标记的那一列。照 `0040`/`0041` 的既有范式走 `user_roles` + 事件驱动 + 唯一索引，能同时消掉第 3、5、8 条——这是本方案最大的性能杠杆。
