# 性能工程师评审：表单防重复提交方案（n55-dup-submit）

## 结论先行

**这个方案在性能上是错的，而且解决的是一个本仓库已用数据库唯一约束解决过的问题。** 方案的两条措施——前端禁用按钮、进程内 `Set` 加锁——都不提供跨进程幂等性，后者还会引入内存无界增长和“永久卡死”的风险；而本仓库已有现成的 `operation_records UNIQUE(action_type, operation_key)` 与 `content_submissions UNIQUE(submitted_by, request_key)` 幂等机制。方案未引用它们中的任何一条。

---

## 问题 1（严重）：内存 `Set` 是单进程状态，在并发与重启下既不防重也不释放

**哪部分有问题**：提案第 2 节「后端加锁」，`const inFlight = new Set<string>()`（proposal.md:24-30）。

**后果（文件:行号）**：
- `proposal.md:24` —— `inFlight` 是模块级单例，进程边界即作用域边界。本仓库的写操作走 `withTransaction`/better-sqlite3 同步事务（`src/server/platform/tx.ts:46-57`），而 `runtime_heartbeats` 的存在（`migrations/0004_runtime_heartbeats.sql:14-21`，注释明写“worker 每轮循环”）证明部署形态是**多进程（server + worker）**。用户在 A 进程提交，重试落到 B 进程 → `inFlight.has()` 为 false → 重复创建照旧发生。方案宣称的「不会重复提交」（proposal.md:31-32）在目标拓扑下**不成立**。
- `proposal.md:26` —— 用 `userId` 作为 key，粒度是“同一用户的一切提交”。该用户同时开两个表单（例如评测 + 评论）提交，第二个会被误判为重复而返回 409。这是**把并发用户变成串行**，属于可用性回归，不是防重。
- `proposal.md:28-30` —— `finally inFlight.delete(userId)` 只在 `handle()` 正常返回/抛错时执行。若 `handle()` 因进程崩溃、容器 OOM、`SIGKILL` 而中断，`finally` 不执行，但进程也没了（无害）。**真正的风险是方案若被改成“带超时”或“进程常驻、请求超时但 handler 挂住”**：此时 `userId` 永久留在 Set 里，该用户**此后每一次提交都被 409 拒绝**，且没有回收机制、没有 TTL、没有可观测手段。这类故障只能靠重启进程恢复。
- `proposal.md:24` —— `Set` 无界。任何能构造 userId 的攻击面（多账号、脚本）可让 Set 单调增长。对一台常驻进程这是缓慢但确定的内存泄漏；`runtime_heartbeats.detail` 里预留的“正在处理的并发数”（`0004_runtime_heartbeats.sql:20`）说明本仓库**期望**这类指标被观测，而方案完全不暴露。

**建议**：**删除**这条措施。改用已在仓内验证的数据库幂等：
- 有 `operation_key`/`request_key` 的路径，直接复用 `recordOperationInTx`（`src/server/modules/operations/service.ts:120-126`）。它同键同摘要 → 返回原记录 `replayed=true`（`service.ts:143-146`），同键不同摘要 → `request_key_reused`（`service.ts:147-149`）。这是**幂等**，语义强于“拒绝”：重复点击拿到的是同一份结果，用户无感。
- 提交类动作落在 `content_submissions` 时，`UNIQUE (submitted_by, request_key)`（`migrations/0001_baseline.sql:326`）已由引擎保证唯一，无需应用层预检。
- 若确实需要“拦截并发中的重复”，用 `migrations/0006_rate_limiter.sql` 的 `rate_limiter_flexible`（`key` 为 PRIMARY KEY，`expire` 有索引 `idx_rate_limiter_expire`，`0006_rate_limiter.sql:26-30`）——**它天然带 TTL 和过期清理**，且跨进程共享。不要新建内存结构。

## 问题 2（严重）：前端 `setSubmitting(false)` 无 `finally`，失败即永久禁用按钮

**哪部分有问题**：提案第 1 节 `await submit(); setSubmitting(false);`（proposal.md:12-14）。

**后果（文件:行号）**：
- `proposal.md:14` —— `submit()` reject（网络断开、500、校验失败）时，`setSubmitting(false)` 不执行，按钮永久保持 `disabled`。用户唯一出路是刷新页面——**丢掉全部已填写内容**。对一篇长评测正文这是严重的数据损失。方案的「性能」自述是防重复创建，实际交付的是“一次失败就要重填”。
- `proposal.md:13` —— 没有 `AbortController`/超时。慢网络下请求悬挂，按钮永久灰禁，用户既不能重提交也不知道状态。这是**用不可恢复的 UI 状态换幂等**，代价过高。
- 与仓内既有做法不一致：草稿保存已经用 `draft_save_receipts` 做重放回执（`src/server/modules/reviews/index.ts:6-7` 的不变量声明，保存流程见 `index.ts` 中 request_key 查回执分支），前端本可安心重试。

**建议**：`try { await submit() } finally { setSubmitting(false) }`，并配合 `request_key` 让重试安全。禁按钮只做**视觉防抖**（防止同一帧内的双击），不作为正确性保证——正确性由问题 1 的数据库约束兜底。

## 问题 3（中）：把“防重”建在应用层检查上，浪费了一次索引查找且存在竞态

**哪部分有问题**：方案整体思路是“先检查、再执行”（proposal.md:26-28 的 `has` → `add` → `handle`），与仓内“让数据库约束判定”的纪律相悖。

**后果（文件:行号）**：
- 仓内权威范式是**写时依赖 UNIQUE 索引判定**，而非读时预检：`content_submissions` 的 `UNIQUE (submitted_by, request_key)`（`0001_baseline.sql:326`）与 `operation_records` 的 `UNIQUE(action_type, operation_key)`（`0042_audit_immutable.sql:5-8` 明确称其为“全站审计与幂等去重的唯一载体”）。`u`/部分唯一索引也已就位：`uq_submissions_review_revision`、`uq_submissions_comment_revision`（`0001_baseline.sql:334-337`）。
- 应用层 `has→add` 在**单进程内**也不是原子的：`await` 前若发生任何重入（React 18 StrictMode 双调用 effect、并发请求交错），`has` 与 `add` 之间无 await 故本进程内尚安全，但**方案没写清楚 key 的构造方式**，一旦 key 由前端传入或被规范化（trim/大小写），两个不同请求会映射到同一 key 或相反，行为不可预测。
- 性能上：预检多一次 `Set.has` 是 O(1)，看似便宜，但它换来的是**与其它副本状态不一致的缓存**——运维排查时无法解释“为什么 A 机器拒绝、B 机器接受”。

**建议**：不做预检。直接写，捕获 `SQLITE_CONSTRAINT_UNIQUE` 后按 `operation_key` 回查原记录并返回（这正是 `service.ts:106-149` 的既有形态：先 `SELECT` 命中则重放，未命中则 `INSERT`）。若要避免“先 SELECT 后 INSERT”的两次往返，可改为直接 `INSERT ... ON CONFLICT DO NOTHING` + `changes === 0` 判定，把两次语句压成一次。

## 问题 4（中）：`userId` 粒度的锁会劣化热门用户/热点表单的吞吐

**哪部分有问题**：`inFlight.add(userId)`（proposal.md:27）。

**后果（文件:行号）**：
- `proposal.md:26-28` —— 串行化单位是“用户”，不是“用户 + 动作 + 请求”。这意味着同一用户对**不同资源**的提交互相阻塞。对后台批量导入场景（仓内有 `0031_plugin_import_batches.sql`、`0032_author_import_inputs.sql`、`src/server/modules/imports`）这类“一个操作者连续触发多次写入”的负载，这直接**把本可并行的写入压成单线程**，吞吐 ~1/T，T 为一次 `handle()` 的耗时。
- 也会把无冲突的并发转成 409 错误：并发度越高，误判率越高。

**建议**：幂等键必须是 `(actor, action_type, request_key)` 三元组，而不是 `actor`。`operation_records` 的 `UNIQUE(action_type, operation_key)` 正是这个粒度；`content_submissions` 用 `(submitted_by, request_key)`。`request_key` 由客户端生成（UUID），一次用户意图一个键——**重放复用同一键、新意图用新键**，天然不互相阻塞。

## 问题 5（低，但会被压测放大）：方案缺少失败清理语义，`finally` 在异步路径上不可靠

**哪部分有问题**：`try { await handle(); } finally { inFlight.delete(userId); }`（proposal.md:28-30）。

**后果（文件:行号）**：
- `proposal.md:29` —— 仓内事务层明确要求“外部拉取、Markdown 解析、图片处理、文件复制一律在事务之外完成”（`src/server/platform/tx.ts:7`），且事务回调**必须是同步函数**（`tx.ts:42-45`）。若 `handle()` 内含任何 `await`（网络、媒体处理），那么 `inFlight` 在整个 I/O 期间被占用——把一次慢 I/O 的持锁时间放大到数百毫秒至数十秒，任何重试都被 409 挡回。这正是**最需要防重复的时刻被误伤**。
- 相比之下 `operation_records` 的幂等在**同一同步事务内**完成（`service.ts:120-126` 的 `recordOperationInTx` 是同步的），不持有跨 I/O 的逻辑锁。
- 没有记录 `expire`/时间戳，因此无法做“超时自动释放”，也无法像 `0006` 那样靠 `idx_rate_limiter_expire` 清理（`0006_rate_limiter.sql:31-32`）。

**建议**：同样删掉。若坚持要应用层锁，须（a）带时间戳 + TTL，（b）锁范围仅覆盖事务内的同步段，（c）释放放在与业务提交同一事务的边界上，而不是包住整个含 I/O 的 `await`。

---

## 汇总建议（按优先级）

| 优先级 | 动作 |
|---|---|
| P0 | 删掉内存 `Set`；改用 `recordOperationInTx`（`service.ts:120-126`）或 `content_submissions.request_key` 唯一约束（`0001_baseline.sql:326`）实现幂等，返回原回执而非 409 |
| P0 | 前端改 `try/finally`，禁按钮仅作视觉防抖，不作为正确性依赖 |
| P1 | 幂等键改为 `(actor, action_type, request_key)` 三元组，消除跨表单误判与人为串行 |
| P1 | 若需拦截“进行中重复”，用 `rate_limiter_flexible`（`0006_rate_limiter.sql:26-30`），自带 TTL 与跨进程共享 |
| P2 | 补可观测：把“已在处理/被幂等拦截”的计数写进 `runtime_heartbeats.detail`（`0004_runtime_heartbeats.sql:20` 已预留该字段） |
