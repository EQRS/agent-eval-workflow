# 安全评审：表单防重复提交方案（n55-dup-submit）

评审人：安全工程师　｜　评审对象：`proposal.md`（32 行，含两段代码示例）

结论：**方案不安全，不建议按当前形态实施。** 前端禁用按钮只是可用性方面的改进，不构成任何安全控制；后端“内存 Set”既不能防止重复提交，又引入了新的拒绝服务（DoS）与越权维度，而且完全绕过了本项目已有的幂等与频控基础设施。

---

## 1. 后端“内存 Set 防重”在语义上就是错的，无法防止重复提交本身

**问题**：`proposal.md:23-31` 的 `inFlight.has(userId) / add / finally delete` 实现的是“同一用户**同时**只能有一个在途请求”，并不是“同一次提交只生效一次”。请求处理完会立即删除 Set 条目；如果第二次点击落在 `await handle()` 之后，这个 Set 毫无作用。

**后果**：
- 双击的两次点击若被串行处理，或第二次点击在第一次事务提交之后到达，**重复创建照样发生**。方案的目标（`proposal.md:30` 声称“不会重复提交”）不成立，但评审通过会给人“已修复”的错觉。
- 更糟：它会把“两个并发的**不同**业务请求”误判成重复。同一用户在前端并发提交两篇不同评测、或提交+评论，第二个会被 `err.conflict('请勿重复提交')` 拒掉。

**建议**：删掉该 Set。真正的防重要建立在**数据库幂等键**上——本项目已有现成机制，见第 3 条。

---

## 2. 以 `userId` 为粒度的全局锁构成自助式拒绝服务（DoS / 可用性攻击面）

**问题**：`proposal.md:25` 的 key 是 `userId`，与具体业务动作、目标对象无关。

**后果（`src/server/workflows/submit-review.ts` 的提交流程为长事务 + 后续入队）**：一次慢请求（大正文、Markdown 解析、任务入队）期间，该用户的**所有**相关写操作全部被 409。攻击者不需要任何权限——自己开两个标签页、或在提交后立刻脚本并发，就能稳定把自己的后续操作锁死；如果后续把这个 Set 复制到“评论”“举报”等其他入口，就等于全站写操作都受影响。同时它是 **单进程内存态**，多实例/重启即失效，安全属性不可依赖。

**建议**：不要用“用户级互斥”表达业务幂等。若确需限并发，用第 4 条的频控设施（已持久化、按动作分键）。

---

## 3. 绕过了项目已有的两个权威机制：`operation_records` 幂等键 与 `draft_save_receipts` 回执

**问题**：

- `migrations/0001_baseline.sql:422-428` 的 `operation_records` 有 `UNIQUE (action_type, operation_key)`，且表已由 `migrations/0042_audit_immutable.sql:18-26` 加了**不可删、不可改**触发器。`0042` 的注释明确写着它是“全站审计与幂等去重的唯一载体”，`setUserRole`/`setUserStatus`/`configuration_revisions`/`catalog` 落库去重都依赖它。
- 保存草稿路径已有成熟范式：`src/server/modules/reviews/index.ts:611-620` 的注释说明“重放必须在 CAS 之前判定”，用 `draft_save_receipts(draft_id, request_key)` 同键同摘要返原回执、同键不同摘要报 `request_key_reused`。

**后果**：方案另造一套不受审计、不持久、不可回放的重复判定，导致同一“重复提交”问题在仓库里存在三种互不兼容的答案（operation_key / requestKey 回执 / 内存 Set）。audit 链上看不到被 Set 拦掉的请求，安全事件复盘时无法还原“用户到底提交了几次”。

**建议**：提交动作走 `recordOperationInTx`，`actionType` 如 `review.submit`，`operationKey` 取**客户端 `requestKey`（或草稿 id + 载荷摘要）**，依靠 `UNIQUE(action_type, operation_key)` 让第二次插入失败并返回首次结果。这条路径天然跨进程、跨重启、可审计。

---

## 4. 频控设施未被利用，且方案没有为“被拒请求”定口径

**问题**：`src/server/platform/rate-limit.ts` 已提供按“服务端确认的 userId + 动作 + 窗口”的持久化频控（键形如 `<action>:<userId>`，表 `rate_limiter_flexible` 见 `migrations/0006_rate_limiter.sql:26-30`），并有 `refundQuietly` 处理“通过限流但业务失败”的退还语义（`rate-limit.ts` 文件末尾注释）。方案对此零提及。

**后果**：防重复提交的正确兜底（“限速 + 幂等键 + 退款语义”）被替换成一个内存 Set。同时 `RATE_LIMIT_RULES`（`rate-limit.ts`）里**没有** review submit 这一动作，提交动作目前不受频控约束——双击刷提交在频控层面也是敞口。

**建议**：为 `review_submit` 增加 `RateLimitAction` 与规则；先取频控 ticket → 再做幂等写入 → 业务失败 `refundQuietly`。

---

## 5. 前端示例吞掉异常，错误路径上按钮永久禁用（可用性/安全边界）

**问题**：`proposal.md:14-19`：

```tsx
setSubmitting(true);
await submit();
setSubmitting(false);
```

`await submit()` 抛错时没有 `finally`，`setSubmitting(false)` 不执行。

**后果**：任何一次失败（409/422/429/网络错误）后按钮**永久禁用**，用户只能刷新页面重来——而刷新恰好绕过前端保护、直接触发第 1 条所述的重复创建。等于“防御在失败时自我拆除”。另外前端禁用**不能**被当作安全控制：`proposal.md:11` 的标题“前端禁用按钮”与 `proposal.md:30` 的“不会重复提交”把它当成了交付物，这是威胁建模上的错位——攻击者/脚本根本不点按钮。

**建议**改为标准幂等 UI：请求携带稳定 `requestKey`（在用户点击进入提交态时生成，重试复用同一个）；用 `try/finally` 复位；服务端返回 `replayed: true` 时按成功处理并跳过二次跳转。前端注释里明确写“这是 UX 改善，不是防重手段”。

---

## 6. 缺少对“重复提交产生什么”的影响确认（越权/审计面）

**问题**：方案没有说明重复调用的**数据后果**是什么。按已读代码，`submit-review.ts` 会写 `content_submissions` + 不可变 `review_revisions` 快照（`migrations/0002_triggers.sql` 对 `review_revisions` 有 `BEFORE UPDATE/DELETE` 守卫，`review_revisions` 有 `UNIQUE (review_id, revision_number)`）。

**后果**：重复提交若各自拿到新的 `revision_number`，产生的是**两条不可删除的修订快照**——不可变触发器意味着事后**无法清理**，只能靠另外写撤回/隐藏流程掩盖。这使“重复提交”从 UI 瑕疵升级为**不可逆的数据污染 + 审计噪声**，并可能被用来刷高某评测的提交次数或淹没审核队列。

**建议**：方案需显式声明提交是“幂等写入”（同 `requestKey` → 同一条 `content_submissions`/同一修订），并在测试中固定该不变量；同时在威胁清单里登记“重复提交 → 不可变表膨胀”这一条。`submit-review.ts` 里写 `operation_records` 的 `operationKey` 必须包含 `requestKey` 而非随机 UUID。

---

## 7. 缺少输入边界与失败模式说明

**问题**：`proposal.md:25` 把 `userId` 直接拼进 Set，未说明来源。项目规范是“额度只认服务端读出来的 userId，前端传什么都不影响”（`rate-limit.ts` 顶部注释）。方案没有写这条约束，实现者极易从请求体取 `userId`。

**后果**：若实现时取自请求参数，攻击者可指定他人 `userId` 制造**跨用户锁**（把别人锁在 409 里），这是明确的越权拒绝服务。

**建议**：方案中写明“key 的 userId 必须来自 `CallerContext`（`requireActiveUser`），禁止来自 body/query”，并加一条测试断言。

---

## 汇总建议（按优先级）

1. **删除**内存 Set（第 1、2 条）；提交幂等改由 `operation_records` 的 `UNIQUE(action_type, operation_key)` + 客户端 `requestKey` 承担（第 3、6 条）。
2. 复用 `rate-limit.ts`，新增 `review_submit` 动作规则（第 4 条）。
3. 前端改为“稳定 requestKey + try/finally + 识别 replayed”的幂等 UI，并在文档中声明其非安全控制（第 5、7 条）。
4. 方案补一节“数据后果与不变量”，覆盖不可变 `review_revisions` 的膨胀风险（第 6 条）。

**已核实的文件**：`proposal.md`（全文 32 行）、`migrations/0001_baseline.sql`（`operation_records` 定义 :409-437、`review_revisions` :163-180、`content_submissions` 区）、`migrations/0002_triggers.sql`（不可变触发器）、`migrations/0006_rate_limiter.sql`、`migrations/0042_audit_immutable.sql`、`src/server/platform/rate-limit.ts`、`src/server/platform/tx.ts`、`src/server/modules/reviews/index.ts`、`src/server/workflows/submit-review.ts`（部分，工具轮次耗尽未读完中间 8KB）。

**未覆盖的残留风险（因读文件被截断/轮次用尽）**：`src/server/workflows/submit-review.ts` 中间段实际是否已写 `operation_records` 幂等键；`src/app` 下的提交路由是否已有 `requestKey` 透传与频控 ticket。建议实施前由开发确认这两点，否则第 3、4 条可能部分已存在、方案属于重复造轮子。
