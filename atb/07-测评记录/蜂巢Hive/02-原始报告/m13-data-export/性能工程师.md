# 性能评审：m13-data-export 方案

先说结论：接口设计（异步 202 + 轮询 + 下载）方向正确。**但方案的索引与查询形态没有经过任何验证，第 4 节的可见性过滤是主要的 N+1 问题，会导致 worker 出现停顿。** 以下按严重程度排序。

---

## P0-1 第 4 节：逐行调用 `resolveVisibilityInTx` 是典型 N+1，且单次成本为 3~4 条 SQL 查询

**① 问题部分**
`proposal.md:51`
```ts
if (!resolveVisibilityInTx(db, row.id).publiclyVisible) continue;
```

**② 后果**
`resolve` 一次调用实际执行多条 SQL：

- `src/server/modules/content/index.ts:96-104` → `readControlRow`：1 条 `SELECT ... FROM content_entities WHERE id = ?`（走主键，本身开销不大）
- `index.ts:112-121` → `hasPublishedRevision` 的第一段：`reviews JOIN review_revisions`
- `index.ts:125-131` → **`SELECT ... FROM sqlite_master WHERE type='table' AND name='plugin_pack_releases'`**
- `index.ts:133-139` → 整合包版本查询
- `index.ts:142-148` → **又一次 `sqlite_master` 查询**
- `index.ts:149-155` → 整合包测评查询

即：**每条导出行 ≈ 6 条 SQL**，其中 2 条查 `sqlite_master`（系统目录表，**没有任何索引能优化**，SQLite 要遍历 schema，虽然内存级但每行×2 稳定开销）。一个写了 500 条评测的用户 = 3000 条语句。这是纯串行、同步驱动的 SQLite 调用，**每条都会让出控制权给 V8 与语句缓存**，累积起来是秒级。

更棘手的是**写事务外的不一致**：这段代码放在循环里，若外层不是单一事务，导出过程中用户撤回一条评测，快照就会"半新半旧"；有些行是按旧可见性判的、有些是新判的。

**③ 建议**
1. **改为集合查询，一次完成**。字段已经在 `content_entities` 上：`withdrawn_at`、`hidden_at`、`visibility_control_version` 全在表内，配合 `idx_content_entities_author ON content_entities(author_id, created_at, id)`（`0021_content_entities_pack_release.sql:80`）可以一次取全。只有"是否有公开修订"需要 join，用 `LEFT JOIN review_revisions` 一次带出，不要循环。
2. **删掉 `sqlite_master` 探测**。它存在的理由是"旧库还没跑 00xx 时表不存在"（`index.ts:122-124` 注释）。但迁移是一次性、版本化的——在导出任务里按表存在性做运行期降级毫无意义。把探测结果提到循环**外**算一次，或在模块加载时缓存，成本即可降为 O(1)。
3. 明确导出在**单个读事务**内完成（`withRead`），保证快照一致性。

## P0-2 第 5 节目录：导出任务与关键任务共用 4 个并发名额，会阻塞全站任务

**① 问题部分**
`proposal.md:59` 只说"后台任务异步生成，不阻塞请求"。但现有 worker 是**全站共享的 4 并发**池：`src/server/modules/tasks/constants.ts:19` `MAX_CONCURRENT_TASKS = 4`，且单任务上限 300s（`constants.ts:57` `TASK_DEADLINE_MS`）。

**② 后果**
一个用户导出大数据集占满 300s 名额。**4 个用户同时点导出 = 整个任务队列被填满**，插件自动发现、内容审核、通知分发全部排队。发起导出**几乎零成本**（`proposal.md:15-17` 的接口），但执行单位是稀缺资源——这是一个**廉价请求触发昂贵任务**的放大结构。方案第 63-64 行"不影响其他用户"的预期在此不成立。

另外注意 `constants.ts:64` 的语义：`nextAvailableAt` 在第 3 次失败即进入终态 `failed`。大导出若因超时失败，**用户重试 3 次就拿不到了**，而重试又各占一个名额。

**③ 建议**
1. **独立调度组**（参照 `src/worker/scheduled.ts:44` 的 `DISCOVERY_SCHEDULING_GROUP` 写法），并给导出单独设并发上限（如 1）。导出是离线可携带权诉求，优先级应低于线上交互任务。
2. **给导出任务单独设 deadline**，不要套 300s 常规上限；同时必须显式处理超时分片，而不是让它撞死循环。
3. 队列侧加**每用户导出去重**（`deduplication_key = export:<userId>:<windowStart>`），防止用户连点堆积。

## P0-3 第 5 节：`/data/exports/` 落盘方式与会话处理方案未定义，同步导致内存驻留

**① 问题部分**
`proposal.md:56-61`
```
/data/exports/<userId>/<taskId>.json.gz
TTL 7 天，定时清理。
```

**② 后果**
- 方案只定义了**路径**，没定义**写路径**。若实现为"先在内存里拼出整个 JSON 数组再 `JSON.stringify` 后 gzip"，一个重用户（大量 `body_md`，`forum_posts.body_md` 上限 20000 字符见 `0037_forum.sql:76`）会直接打出几百 MB 的 JS 字符串——**超出 V8 单字符串上限即抛错**，而且 gzip 前的那份全是常驻内存，worker 会 OOM。
- `data/exports/<userId>/` 目录在任务前不创建，首次必报 `ENOENT`。
- 下载接口 `proposal.md:13` 未提 `Content-Length` 或流式发送，容易变成整个文件读进内存再回写。

**③ 建议**
1. **流式管道**：`SELECT` 游标逐行 → `JSONStream`/手写分隔符 → `zlib.createGzip()` → `fs.createWriteStream()`。峰值内存应只与单行大小相关，**不随用户数据量增长**。JSON 数组可以手动用 `[`、`,`、`]` 包裹，完全不需要把全集放进内存。
2. 写**临时文件再原子 `rename`**，避免下载到半成品。
3. 下载接口用 `fs.createReadStream().pipe(res)`，带上 `Content-Length` 与 `Content-Encoding`。

## P1-1 第 3 节：`reviews` 的 join 是多余的，但 `forum_posts` 才真正需要索引

**① 问题部分**
`proposal.md:26-30`
```ts
ownerColumn: 'content_entities.author_id',
join: 'JOIN content_entities ce ON ce.id = reviews.id',
```

**② 后果**
`content_entities.id` 与其子类型 `review_id` 是**同值**的（`0021_content_entities_pack_release.sql:47-50` 的 CHECK 强制 `review_id = id`），因此这个 join 在语义上可以用 `ce.id` 直接当 `reviews.id`。它当前的唯一作用是取 `author_id`——**该字段没有出现在导出列里**（`columns` 只有 `id/plugin_id/source_kind/created_at`）。所以这个 JOIN 只为了过滤就额外做了一次主键查找，收益为零。

更要紧的是**方案完全没提 `forum_posts` 和 `plugin_favorites` 的索引**。逐表核对：
- `plugin_favorites`：`idx_plugin_favorites_by_user ON plugin_favorites(user_id, created_at DESC, plugin_id)` —— **有**（`0012_interactions.sql:72`）。✅ 不需要新增。
- `forum_posts`：`idx_forum_posts_by_author ON forum_posts(author_id, created_at DESC, id)` —— **有**（`0037_forum.sql:99`）。✅ 不需要新增。
- `reviews`：裸表，无 `author_id` 列（作者信息在 `content_entities`）。设计方案用 `ce.author_id` 驱动，靠 `idx_content_entities_author`。✅ 可行。

**③ 建议**
去掉无用的 `reviews` join，把 `content_entities` 作为**驱动表**：
```sql
SELECT ce.id, r.plugin_id, r.source_kind, r.created_at
FROM content_entities ce
JOIN reviews r ON r.id = ce.id
WHERE ce.author_id = ? AND ce.content_type = 'review'
  AND ce.withdrawn_at IS NULL AND ce.hidden_at IS NULL
ORDER BY ce.created_at DESC
```
索引已经齐备。**注意 `idx_content_entities_author` 是 `(author_id, created_at, id)`，`ORDER BY` 可以走索引序，不要再写成 `ORDER BY r.created_at DESC`** 那样会丢掉索引序，退化成 filesort。这是一处容易踩的细节。

## P1-2 第 4 节：用「公开可见」当导出判据，会**漏掉**用户自己的私密内容，且掩盖了真正的性能优化点

**① 问题部分**
`proposal.md:47-53`

**② 后果**
判据 `publiclyVisible` 要求"有公开修订 + 未撤回 + 未隐藏"。用户的**草稿**（没有 published revision）与**被管理员隐藏的内容**会被直接 `continue` 掉。从性能角度，这反而意味着导出必然要走"逐行判定"的慢路径——如果按作者直接全量导出（作者看自己的东西本来就该全量），则可以完全**省掉可见性判定**，只走一条带索引的 `SELECT`。

这既是功能问题，也是一个被错过的**数量级优化**：不判可见性 = 从 O(N×6 SQL) 降到 O(1 SQL)。

**③ 建议**
区分两个语义并明确选一个：
- **自视图（推荐）**：作者导出自己的全部数据，判据只需 `author_id = ?`，**无需 `resolveVisibilityInTx`**。性能与正确性同时改善。
- **公视图**：若坚持只导公开内容，则必须改为 P0-1 的集合式过滤。

无论哪种，都请在方案里写明判定口径，现在的写法是歧义的。

## P2-1 第 2 节：限流只挡请求频率，不挡并发长任务

**① 问题部分**
`proposal.md:21-24` 只有 `enforceRateLimit({ action: 'me_export' })`。

**② 后果**
限流通常按时间窗计数，允许"窗口内 N 次"。用户仍可在窗口内提交 N 个导出任务，每个都进队列、都落盘 7 天。磁盘与队列双双累积。方案第 60 行"定时清理"未给清理频率与单批上限——一次 `readdir` + `unlink` 百万个目录项会长时间持有事件循环（若同步 `fs`）或打满 IO。

**③ 建议**
1. 除了限流，加**"同一用户同时只允许一个 running 状态的导出任务"**的硬约束（查 `background_tasks` 状态即可）。
2. 清理任务**分批 + 限量**（每轮最多删 K 个），并记录游标，不要一次性扫全目录。

## P2-2 第 6 节：JSON 格式没有分页/分片，与 gzip 的不良组合

**① 问题部分**
`proposal.md:62-63`

**② 后果**
gzip 对 JSON 的压缩比取决于窗口内重复度。若把三类数据顺序拼接（reviews → forum_posts → favorites），单文件大时压缩收益递减，且**下载端无法先拿到一部分**。用户拿到的文件在完整生成前不可用（这是必然的），但方案没有对外承诺生成耗时——`GET /:taskId` 状态在报表上如果没有 progress，用户只能盲等。

**③ 建议**
1. 每类数据（reviews / posts / favorites）**分文件**或至少在 JSON 里分节，未来可独立扩展。
2. `GET /:taskId` 返回 `progress: { rows_exported, current_section }`，让用户能判断是否卡住。
3. 若单文件可能超数十 MB，考虑提供 `?section=reviews` 的分节下载。

## 汇总：落地前必须补的三件事

| 项 | 现状 | 必须改成 |
|---|---|---|
| 可见性过滤 | 逐行 × 6 SQL（`content/index.ts:96-155`） | 集合式单条 SQL，或按作者免过滤 |
| 任务调度 | 共用 `MAX_CONCURRENT_TASKS=4`（`constants.ts:19`） | 独立调度组，并发 1，独立 deadline |
| 产物落盘 | 只有路径，无流式约定 | `cursor → gzip → file stream`，峰值内存恒定 |

一个正面确认：`reviews`、`forum_posts`、`plugin_favorites` 三条导出查询所需的索引**当前已全部存在**（`0021:80`、`0037:99`、`0012:72`），**不需要新增迁移**——前提是按 P1-1 改写查询形态并保持 `ORDER BY` 与索引列序一致。
