# 安全评审：m13 用户数据导出方案

评审范围：`proposal.md` 全文、`migrations/`（0001/0003/0006/0012/0019/0037/0038/0039/0040/0042）、`src/server/platform/{context,file-store,rate-limit}.ts`、`src/server/modules/{content,operations,tasks}`。以下只从安全角度列问题，按严重度排序。

---

## 1. 【严重】导出范围把「用户自己的内容」等同于「用户自己的可见内容」

**① 问题位置**：`proposal.md §4 可见性过滤`

```ts
if (!resolveVisibilityInTx(db, row.id).publiclyVisible) continue;
```

**② 后果**：这是方案里最危险的一条。数据可携带权要求导出**数据主体自己的数据**，与「这条数据现在是否对公众可见」无关。按当前写法：

- 用户被管理员 `hidden` 的评测（`content_entities.hidden_at` 非空，见 `0001_baseline.sql` 的 hidden 三列约束）→ 导出里**消失**。用户会认为「平台把我的数据删了/藏了不给我」，这恰好是可携带权要防止的行为，也抹掉了申诉所需的证据。
- 用户自己 `withdrawn_at` 撤回的评测 → 同样消失。
- `forum_posts.status = 'deleted'` 的帖子（`0037_forum.sql`，软删保留行）→ 消失；而迁移注释明确说软删的意义就是「让作者看到已被删除而不是凭空消失」。

更糟的是它**反向泄露**：`resolveVisibility` 对「不存在的 id」与「存在但不可见」的行为差异（`content/index.ts` 的 `readControlRow` 抛 `target_unavailable`）会被导出流程吞掉或抛出，攻击者可借导出接口的成败/耗时差异探测「某 id 是否存在、是否被隐藏」，构成一个**可见性预言机**。

**③ 建议**：导出判据改为 **作者归属**（`author_id = ctx.userId` / `ownerColumn`），完全不做可见性过滤；在产物中**显式带上状态字段**（`withdrawn_at`、`hidden_at`、`hidden_reason`、`status`、`deleted_at`），并在文件头部说明「其中 N 条因违规被隐藏」。可见性判断只用于「要不要给**别人**看」，不用于「要不要给本人看」。

## 2. 【严重】下载端点缺对象级归属校验（IDOR）

**① 问题位置**：`proposal.md §1 接口` 的 `GET /api/me/export/:taskId/download`，以及 `§5 产物` 路径 `/data/exports/<userId>/<taskId>.json.gz`

**② 后果**：`§2 鉴权` 只给 `POST /api/me/export` 写了 `assertCanWrite`，两个 GET 端点**没有任何鉴权描述**。`taskId` 是 UUIDv7（`packages/common/field-rules` 的 `isUuidV7`），**UUIDv7 前 48 位是毫秒时间戳**，不是不可猜的随机量——攻击者枚举自己任务的时间邻域即可命中他人 taskId。若下载端点只按 `taskId` 查路径而不校验 `userId`，就是标准 IDOR，一次请求拿到别人全量个人数据（含 `body_md` 草稿、收藏夹名）。文件系统路径以 `<userId>` 分层并不能防住，因为路由是自己拼的。

**③ 建议**：
- 三个端点**全部**走 `assertCanWrite(ctx)`（`platform/context.ts` 已提供统一实现，禁用账户会被挡）。
- 下载/状态查询的 SQL 必须带 owner 条件：`WHERE id = ? AND requested_by = ?`，命中 0 行返回 **404 而非 403**（403 会确认该 taskId 存在）。
- `taskId` 单独用 `newOpaqueToken()`（`platform/id.ts`）生成，不要复用 UUIDv7 作对外凭据。
- 若必须支持「下载链接分享」，用一次性、短 TTL 的签名 token，且同样绑定 userId。

## 3. 【高】产物落在应用可写目录，且无加密、无完整性保护

**① 问题位置**：`proposal.md §5` `/data/exports/<userId>/<taskId>.json.gz`；对照 `platform/file-store.ts` 的存储根（`.data/media`）与 `assertSafeStorageKey`

**② 后果**：
- 导出文件是**全量个人数据明文**（含未发布草稿、被隐藏内容、邮箱类身份信息，见 `0003_auth_media.sql` 的 `external_identities`），却与可被 Web 层访问的持久目录同源。一旦静态服务配错（或 `defaultMediaRoot()` 被指向 exports），即可匿名下载。`file-store.ts` 的路径穿越防护只保护「key → 路径」，**不保护「谁能读这个目录」**。
- `json.gz` 无摘要校验：落盘后被篡改无法发现。方案 `§6` 只写了 `schema_version` 与时间戳，没有任何完整性字段。
- `<userId>` 直接拼进路径：若 userId 来源不是数据库而是上下文，且未过 `assertSafeStorageKey`（其正则要求 `[A-Za-z0-9._-]`，UUID 可通过），Segment 里出现 `..` 就上跳——这条当前大概率安全，但方案没写「必须过 assertSafeStorageKey」，属于把安全依赖于调用方自觉。

**③ 建议**：导出根目录独立于媒体根（新环境变量，如 `DSH_REVIEW_EXPORT_ROOT`，默认在 Web 不可达的位置）；**默认对产物做静态加密**（AES-GCM，密钥来自部署配置，与 `0003` 中 `code_verifier_envelope` 同一套密钥管理口径）；文件名用 `taskId` 而非 userId；产物记录 sha256 并在下载时比对；路径构造强制走 `resolveWithinRoot()`。

## 4. 【高】未设配额与并发上限：单用户可拖垮 worker / 撑爆磁盘

**① 问题位置**：`proposal.md §2 鉴权` 只调用 `enforceRateLimit({ action: 'me_export', ctx })`

**② 后果**：
- `me_export` **不是 `RateLimitAction` 联合类型的成员**（`platform/rate-limit.ts` 的 `RateLimitAction` 只有 comment_change / plugin_submission / report / correction / feedback / forum_post / forum_reply / forum_board_application / role_application）。直接照方案写会**类型不通过**，实际落地时极易被"顺手改成不限流"或塞进别的 action 复用额度。
- `RATE_LIMIT_RULES` 的语义是「每用户每窗口 N 次」，不控制**同时存在**的产物数。攻击者每个窗口提交 1 次、连续多窗口，磁盘上就会堆积 N 份全量导出；任务队列 `MAX_CONCURRENT_TASKS = 4`（`modules/tasks/constants.ts`），导出是长任务，**4 个并发槽可被少数用户完全占满**，导致审核、通知等正常后台任务饿死——这是可用性攻击，最终影响内容安全（举报审核停摆）。
- `TASK_DEADLINE_MS = 300s`：大数据量导出超时后 `recoverExpired` 会重试 3 次（`nextAvailableAt`），实际放大三倍资源消耗，且每次重试都从头跑。

**③ 建议**：新增独立 `RateLimitAction = 'me_export'` 与独立规则（如「每用户每天 1 次，24h 窗口」——数据可携带权不要求高频）；增加**每用户同时只允许 1 个未完成导出任务**（DB 层部分唯一索引，参照 `0038` 的 `uq_reports_open_*` 写法）；导出走**独立调度组**，不占用那 4 个并发槽；超出 `TASK_DEADLINE_MS` 直接终态失败而不是重试（标记为不可重试错误）。

## 5. 【中】收藏导出与实际 schema 不一致，会静默漏数据

**① 问题位置**：`proposal.md §3` 的 `favorites` 只写了 `plugin_favorites`（`plugin_id, folder_id, created_at`）

**② 后果**：`0039_favorite_folders_target_kind.sql` 之后收藏是三套表：`plugin_favorites`、`pack_favorites`、`post_favorites`，且 `favorite_folders` 有 `target_kind` 区分。按方案导出，用户**整合包收藏与帖子收藏全部丢失**——这是"导出不完整"，恰恰是数据可携带权最核心的合规缺陷，且在验收时很难被发现（用户不会逐条比对）。另外 `0039` 注释说明 `plugin_pack_favorites` 旧表**未删除**，若误读旧表则会拿到过期数据。

**③ 建议**：`EXPORT_SPEC` 增加 `pack_favorites` / `post_favorites`；导出时 JOIN `favorite_folders` 带上 `folder.name` 与 `target_kind`；**在 `EXPORT_SPEC` 上加一条自检**：导出完成后统计「所有 `ownerColumn = userId` 的表」的行数与实际导出条数做差，差额写进任务 `progress`，非零即告警——防止未来新增用户数据表时再次静默漏导。

## 6. 【中】`reviews` 的 owner 判定走 JOIN，与 `content_entities.author_id` 单点信任问题

**① 问题位置**：`proposal.md §3` `reviews.ownerColumn: 'content_entities.author_id'` + `join: 'JOIN content_entities ce ON ce.id = reviews.id'`

**② 后果**：`0001_baseline.sql` 中 `reviews.id = content_entities.id` 是**互指 + DEFERRABLE 外键**设计，`content_entities` 还允许 `content_type = 'pack_release'`（当前被 CHECK 闸门限制为 review）。若导出 SQL 用 `JOIN` 而非 `INNER JOIN ... WHERE ce.content_type = 'review'`，或未来放开闸门，导出会把**整合包版本的作者数据**混进 review 导出；更危险的是若写成 `LEFT JOIN` 且 owner 判据落在 `reviews` 上，会出现「行存在但 author 为 NULL」被当成匹配（SQL 三值逻辑里 `NULL = ?` 为 NULL，`WHERE` 会过滤掉，但若代码在 JS 侧做比较则可能放行）。

**③ 建议**：导出查询统一用 `INNER JOIN content_entities ce ON ce.id = reviews.id AND ce.content_type = 'review'`，owner 判据只用 `ce.author_id`，并在 SQL 里显式 `AND ce.author_id = ?`（不要取回后在 JS 里过滤——那会在内存里持有他人数据）。所有导出查询加 `LIMIT` 分页，避免一次把全表读进内存。

## 7. 【中】任务载荷与审计的泄露面

**① 问题位置**：`proposal.md §1` 用 `POST /api/me/export → 202 { taskId }` 走后台任务；对照 `modules/tasks/service.ts` 的 `progress` 字段与 `modules/operations` 的 `targetSnapshot` / `changes`

**② 后果**：
- `finish({ progress })` 的内容会展示在后台页（注释原文：「后台页展示这一轮干了什么」）。若导出任务把**文件名、条数、内容摘要**写进 `progress`，管理员无需 impersonation 即可看到用户导出行为的元数据。
- `recordOperationInTx` 的 `targetSnapshot` / `changes` 会落进 `operation_records`，而 `0042_audit_immutable.sql` 让该表**不可删改**。如果为了审计而在 `changes` 里写了导出内容片段（含被隐藏的草稿正文），等于把敏感数据**永久固化**进一张删不掉的表——这会造成新的、更严重的合规问题（被遗忘权与不可删审计直接冲突）。

**③ 建议**：导出任务的 `progress` 只放**计数与状态**（`rows_exported`、`bytes`、`schema_version`），绝不放内容；审计记录 `actionType: 'me.export'` 只记 `{ taskId, requested_at, row_counts_by_table }`，`targetSnapshot` 不含任何正文字段；在方案里写明「导出任务不得将用户内容写入 operation_records」作为硬约束。

## 8. 【中】TTL 清理与「用户删除账户」的交互未定义

**① 问题位置**：`proposal.md §5` 「TTL 7 天，定时清理」

**② 后果**：导出成功后 7 天内，`/data/exports/<userId>/` 下存在一份**用户已注销账户后仍然有效**的全量数据副本。清理任务若与用户注销流程不联动（本项目 `users` 外键多为 `ON DELETE RESTRICT`，见 `0001`/`0012`，说明注销大概率是软删 + 人工流程），这份副本会成为「已删除用户数据仍可被获取」的活口子。另外若清理是「扫描目录 mtime」，攻击者无从触发，但**磁盘写满时清理失败**会让副本无限期留存。

**③ 建议**：产物记录进一张 `export_artifacts` 表（`task_id, user_id, storage_key, created_at, expires_at, sha256`），清理以表为准而非目录扫描；用户注销/禁用流程必须级联删除该用户全部产物记录与文件（`platform/file-store.ts` 已有 `remove()`）；清理失败必须告警而不是静默（磁盘满时尤其）。

## 9. 【低】格式与元数据层面的两处小口子

**① 问题位置**：`proposal.md §6` 「JSON，带 schema_version 与导出时间戳」

**② 后果**：(a) `body_md` 原样导出，用户下载后若在浏览器里直接打开（`file://` 或错误 MIME），产出的 HTML 可能触发脚本执行——虽然是用户自己的机器，但分享给第三方时是标准 XSS 载体；(b) 未定义 `Content-Disposition` / `Content-Type`，若服务端以 `application/json` 内联返回，某些浏览器会把 `application/json` 当 HTML 嗅探。

**③ 建议**：下载响应固定 `Content-Type: application/octet-stream` + `Content-Disposition: attachment; filename=...` + `X-Content-Type-Options: nosniff` + `Cache-Control: no-store`；产物内保留 `body_md` 原文（这是用户数据），但**不要**预渲染成 HTML。
