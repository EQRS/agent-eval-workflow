# 性能工程师评审：服务优雅停机方案

我按性能工程师视角评审，只关注**停机期间的延迟、停顿、CPU 与 I/O 浪费、容量与超时的数量级是否匹配**。先说结论：**当前仓库里已经有一套比提案更合理的三层设计（server.mjs 10s 兜底、compose 里 web 15s、worker 30s），而提案把这三层收缩成单个固定 `sleep(5000)`，在性能上是明确的退步。**

---

## 1. 固定 `sleep(5000)` 把「等待」变成了「空转等待」——5 秒是纯延迟

**问题部分**：提案 §1 `await sleep(5000)` + §2「给 5 秒让请求完成」。

`sleep` 与「等待请求完成」在性能上毫无关系：它既不知道有没有在途请求，也不知道还剩几个。两个后果都不可接受：

- **空闲停机被白拖 5 秒**：worker / web 在无流量窗口重启（大多数滚动发布都是如此），进程仍然满 5 秒才退出。容器滚动发布时这是每个副本 5s 的**串行化延迟**，部署窗口直接乘副本数。
- **反向也不成立**：有慢请求时 5 秒被硬截断，请求仍被砍掉 —— **它既不省时间也不保请求**，等于花 5s 买了个心理安慰。

**后果（文件:行号）**：
- 提案：`proposal.md:7-9`、`proposal.md:17`（「给 5 秒」）。
- 现有实现已经是「事件驱动关闭 + 兜底超时」，不是 sleep：`server.mjs:97-114`（`server.close(cb)`，回调里才 `process.exitCode = 0`），兜底 `server.mjs:109-112` 的 10s `setTimeout(...).unref()`。
- 对比可见 `proposal.md:7` 的 `server.close(); await sleep(5000)` 甚至**丢弃了 `server.close` 的回调**，因此写的不是「等请求完成」，而只是等满 5s。

**建议**：删掉 `sleep`，用 `server.close()` 的完成回调作为唯一退出信号；兜底超时单独给、且要大于 P99 请求耗时。直接把现有 `server.mjs:97-114` 作为基线，不要回退。若某天要支持 keep-alive 长连接，加 `server.closeIdleConnections()`（Node ≥18），比固定 sleep 精确得多。

## 2. 超时预算倒挂：提案把 web 的退出预算压到 5s，但编排愿意给 15s

**问题部分**：提案 §1 固定 5s vs §3 `stop_grace_period: 15s`。

这是典型的**预算配置彼此不一致**：编排给了 15s，进程自己 5s 就 `process.exit(0)`，导致 **10s 的可用排空预算被浪费**。在 `synchronous = FULL`（见下条）的库上，5s 对「一批写请求」是很紧的 —— 恰恰是慢请求最需要那 10s。

**后果（文件:行号）**：
- 提案 `proposal.md:7-9`（5s 自杀）对比 `proposal.md:21`（15s 编排）。
- 现有 compose 已经是 15s：`docker/compose.yaml:77`（web `stop_grace_period: 15s`）；worker 30s：`docker/compose.yaml:96`。
- 现有 server 内部兜底 10s：`server.mjs:109-112` —— 与 15s 编排**基本对齐**（留 5s 给日志 flush 与 SIGKILL 前收尾）。提案把它改成 5s 是明确倒退。

**建议**：保持「进程内超时 < 编排 grace period」，且差值 ≥ 2-3s。建议 web：进程内 12s、编排 15s；worker：进程内 25s、编排 30s。把这三个数字写进一处文档并互相引用，避免下次再调单边。

## 3. 真正的性能风险不在 web，而在 worker —— 提案完全没提 worker

**问题部分**：提案只写了 HTTP 服务（`server.close`），但本仓库停机时**最贵的在途工作不在 web**，而在 `worker` 进程。

**后果（文件:行号）**：

- 单任务最长可跑到 **300s**：`src/server/modules/tasks/constants.ts:52`（`TASK_DEADLINE_MS = 300 * SECOND`），而租期 120s（`constants.ts:23`）、续期 30s（`constants.ts:26`）。
- worker 收到 SIGTERM 只是置 `running = false`（`src/worker/main.ts:250-254`），然后**等在跑的 handler 自然结束**（`main.ts:203-206`：`shouldContinue` 为 false 就 break，但 `await execute(claim)` 里的 handler 不会被中断）。
- 可是编排只给 30s：`docker/compose.yaml:96`。所以**一个 discovery 任务必然会被 SIGKILL 掐断**。
- discovery 一轮的上游预算是 400 次请求、30 个插件（`src/server/modules/catalog/discovery.ts:38-45`），是**串行网络 I/O** —— 天然是几十秒到分钟级。被 SIGKILL 掐断意味着：这几十秒的 GitHub 请求配额**全部沉没**，且任务靠租约到期回收后**整轮重跑**（`main.ts:169-171` `recoverExpired`），重复烧配额。
- 更糟的是未认证时 GitHub 核心接口只有 60 次/小时（`discovery.ts:51-54` 注释），一次被掐断的重跑就可能吃掉当天配额的一大块 —— **停机一次，当天的自动发现能力实质受损**。

**建议**：
1. worker 内加「排空截止时间」：SIGTERM 后记录 `drainDeadline = now + 25s`，把该值传给 handler（或用 `AbortSignal`），让 discovery 在**请求之间**检查它并主动收尾，把已完成的进度写回 `progress`，而不是等被 SIGKILL。
2. 停止领取新任务要在 **claim 之前**判断（`main.ts:189-194` 的 for 循环里现在就只在 execute 前判断，会**多领一次**：一旦 `running=false`，已 claim 未 execute 的任务会因 break 被丢下，白占一次 attempt 计数）。
3. 编排侧把 worker 的 `stop_grace_period` 与 `TASK_DEADLINE_MS` 的关系显式化：要么提高 worker 预算，要么在 `TASK_DEADLINE_MS` 之上再加一层「可中断」的语义。

## 4. `synchronous = FULL` 让「5s 排空」的实际容量远低于直觉

**问题部分**：提案假设 5s 足以排空在途请求，但没考虑写路径的持久化成本。

**后果（文件:行号）**：
- `src/server/platform/db.ts:57` 显式 `db.pragma('synchronous = FULL')`，配合 WAL（`db.ts:56`）。`FULL` 意味着**每次事务提交都要等 fsync**。在机械盘/云盘上单次提交可能是毫秒到十几毫秒级。
- better-sqlite3 是**同步驱动**（`db.ts:9-11` 注释明确说了「等待会阻塞所属线程」）。所以停机时若有 N 个并发写请求排队，它们是**串行**过 fsync 的，不是并行。
- 结论：5s 突然变得很紧；而且 `busy_timeout = 5000ms`（`db.ts:58`）意味着一个被锁住的写请求**自己就可能耗掉全部 5s 预算**，然后正好被 exit 掐掉 —— 而它可能已经写了一半。

**建议**：进程内超时不要低于 `busy_timeout` + 一次 commit 的量级（`db.ts:58` 的 5000 只是**单次**等待上限，不是总上限）。把 web 的进程内排空定到 12s 是有依据的（≥ 2×busy_timeout + 余量）；并且停机时**不要**在响应未发出前主动 `process.exit` —— 现有 `server.mjs` 用 `process.exitCode` 而非 `process.exit()` 正是对的，提案的 `process.exit(0)`（`proposal.md:9`）会**丢弃尚未 flush 的 stdout 日志**，让「哪些请求没排空」这件事在事后完全查不到。

## 5. `process.exit(0)` 与日志/心跳的观测成本

**问题部分**：`proposal.md:9` 的 `process.exit(0)`。

**后果（文件:行号）**：
- `server.mjs:38-42` 的 `writeLine` 直接 `process.stdout.write`。在容器里 stdout 是**管道**（json-file driver），写是异步的；`process.exit()` 会截断缓冲区。停机时最后几行（`server_shutdown_done` / `server_shutdown_timeout`，`server.mjs:101-110`）恰恰是最需要的那几行，可能刚好丢掉。
- worker 侧同理：`main.ts:257-277` 的退出路径靠 `finally` 里 `heartbeat.stop()` + `closeDb()`（`main.ts:284-287`）收尾。如果按提案的写法在信号回调里直接 exit，**`closeDb()` 不会执行** —— WAL 的 `-wal`/`-shm` 文件留在盘上，且最后一次心跳（`runtime_heartbeats`，迁移 `0004_runtime_heartbeats.sql:13-19`）停在旧值，健康检查（`docker/compose.yaml:105-109`，`interval: 30s`、`retries: 3`）要再过最多 ~90s 才会判定 dead，`start_period: 30s` 也帮不上重启后的判定。这是**可观测性上的延迟成本**。

**建议**：用 `process.exitCode = 0` + 让事件循环自然排空（现有写法），只在兜底超时才 `process.exit`；退出前显式 `closeDb()` 并在心跳表写一条带 `stopping` 状态的 detail，让健康检查能立刻区分「正在优雅停机」与「静默死亡」。

## 6. 静态常量与配置分散：性能参数没有单一来源

**问题部分**：提案把超时硬编码在代码里（`sleep(5000)`），同时在 compose 里另写一份 15s。

**后果（文件:行号）**：现在仓库里「停机相关的时间数字」至少散在四处 —— `proposal.md:9`（5s）、`proposal.md:21`（15s）、`docker/compose.yaml:77`（15s）、`docker/compose.yaml:96`（30s）、`server.mjs:111`（10s）。这类数字一旦不同步，性能表现就是「看起来配了，实际没生效」。对比任务队列常量已经做对了：`constants.ts:1-13` 明确写了「这些值必须是模块内常量而不是散落字面量」。

**建议**：照 `constants.ts` 的做法新增一个 `shutdown` 常量模块（`WEB_DRAIN_MS` / `WORKER_DRAIN_MS` / `HARD_EXIT_MARGIN_MS`），compose 的值在注释里引用它，并加一个测试断言「进程内超时 < 编排 grace period」。

## 总体判断

| 提案条目 | 性能结论 |
|---|---|
| §1 `sleep(5000)` + `server.close()` | **反对**，退化为固定延迟，丢弃 close 回调 |
| §1 `process.exit(0)` | **反对**，截断日志缓冲、跳过 `closeDb()` |
| §2「5 秒够用」 | **数量级不足**：`synchronous=FULL` + 同步驱动 + `busy_timeout=5s` |
| §3 `stop_grace_period: 15s` | 合理，但与进程内 5s 不匹配，浪费 10s 预算 |
| 未提 worker | **最大缺口**：300s 任务 vs 30s 预算，必然 SIGKILL + 配额沉没 |

**最小改动建议**：把提案 §1 直接替换为仓库已有的 `server.mjs:97-114` 实现（事件驱动关闭 + 12s 兜底 + `process.exitCode`），把 5s 改成 12s 以对齐 15s 编排，并**补上 worker 的可中断排空**——后者才是性能上真正会丢东西的地方。
