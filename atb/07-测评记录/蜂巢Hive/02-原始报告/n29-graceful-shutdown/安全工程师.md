# 安全评审：服务优雅停机改造（proposal.md）

## 先说结论

方案本体只有 12 行，我实际读过原文，全部 25 行中技术部分只覆盖「SIGTERM → server.close() → sleep(5000) → exit(0)」。**它的问题不是不够细致，而是其中两处做法恰恰会削弱代码库中已经实现的安全机制**：它把「审计/幂等记录」和「频控计数的有效性」当成停机时可按「可用性」取舍的东西。

---

## 1. 【高】`process.exit(0)` 无条件退出会切断审计与幂等写入通道

**问题部分**：`process.on('SIGTERM', ...)` 里 `await sleep(5000)` 后**无条件** `process.exit(0)`。

**后果**：
- `migrations/0042_audit_immutable.sql:5-11` 明确写明：`operation_records` 是全站审计与**幂等去重**的唯一载体，`UNIQUE(action_type, operation_key)` 被 `setUserRole/setUserStatus`、`configuration_revisions`、catalog 落库去重多路径依赖。该迁移第 7-9 行还指出，审计行被删除就意味着「已消费的 operation_key 重新可用」是一条**不需要改代码的伪造通道**。
- 固定 5 秒睡眠到期时，那些正在 `withTransaction`（`src/server/platform/tx.ts:47-57`）中的写操作会被 `exit(0)` 直接截断。better-sqlite3 事务是同步的，被 SIGKILL/exit 打断的 WAL 事务回滚是安全的，**但「事务没提交」与「提交了但审计没写」在时序上都可能发生**：凡是在事务外先产生副作用、再补审计的路径，停机窗口就是一次「有副作用无审计」的空档。审计一旦可缺，0042 想封的那条通道就重新打开。
- 更关键：`exit(0)` 上报退出码 0，编排器认为**正常退出**，不会告警。安全事件最常见的掩盖方式就是「看起来是计划内重启」。

**建议**：
- 停机路径**不得**用 `process.exit(0)` 作为兜底。用 `server.close()` 的回调 + 一个「在途计数」归零后再 `closeDb()` 退出；只在超出 `stop_grace_period` 的硬超时上才 `exit(1)`（**非 0**，让编排与监控看到异常）。
- 退出前显式 `closeDb()`（`src/server/platform/db.ts:74-80` 已有该入口），确保 WAL 正常 checkpoint、无悬挂事务。
- 停机期间**拒绝接收新写请求**（返回 503 或 Retry-After）但不拒绝新开事务：宁可让请求快速失败，也不要在已停止推进的进程里开始新的审计写入。

---

## 2. 【高】5 秒固定睡眠 = 给攻击者一个可预测的「审计盲区窗口」

**问题部分**：「### 2. 等待 给 5 秒让进行中的请求完成」，而 `stop_grace_period: 15s`。

**后果**：这是一个**确定性、可预测**的窗口——任何能读到这套 compose 配置的人（内部人员、接了仓库读权限的第三方、甚至被泄露的部署文件）都知道「重启开始后最多 15 秒内，审计可能不完整」。安全上这等价于公开一个「维护窗口可用于操作而不留痕」的施压时间点。方案「预期」里写「重启不丢请求」，但**没有任何一条预期是关于「重启不丢审计」**——这是优先级排序上的实质缺陷，不是措辞问题。

**建议**：把「审计完整性」列为停机的一等验收标准：验收项中加一条「重启前后 `operation_records` 无缺号、幂等键无重放成功」。同时，不要在方案里把时长写死并公开；实际取值应由部署侧配置注入，且不要跟审计保留策略一起出现在同一份可读文档里。

---

## 3. 【中】方案完全没提 worker，而 worker 的停机语义与 web 不同

**问题部分**：方案只写了一个 `process.on('SIGTERM')`，上下文看是对 web 进程；但仓库里 worker 是**独立进程**，且已有自己的信号处理。

**后果**：
- `src/worker/main.ts:252-258` 已实现 `running=false` 的优雅退出，`shouldContinue: () => running`（:268）会让循环在**当前任务处理完**后退出，`finally` 里 `heartbeat.stop(); closeDb()`（:298-300）。
- 若按方案给 worker 也套上「sleep 5s 后 exit(0)」，会把一个**正确实现**替换成**按时间猜**的实现：正在跑的任务（`src/worker/main.ts:127-160` 的 `execute`）被中断，任务租约要等 `recoverExpired` 才回收——这段时间里任务处于「谁都不拥有」状态。若该任务属于角色变更、审核结论落库一类操作，中断点的审计与业务状态一致性由谁保证？方案没有回答。
- 另一点需要指出：`startHeartbeat` 的定时器用了 `unref()`（`src/server/platform/heartbeat.ts:139-141`），注释写明是为了不阻塞退出。这意味着**心跳在停机期会静默停止而不阻止进程**，`health.ts:117-140` 的 `worker.heartbeat` 检查在 `?worker=1` 时会变成 503。这是预期行为，但方案完全没提，运维侧会把「优雅停机中的 503」误判为 worker 崩溃。

**建议**：方案需**显式区分 web 与 worker 两条停机路径**，worker 复用现有「信号置位 → 处理完当前任务 → finally 清理」的实现，不要再叠加 sleep+exit。并在停机开始时主动把心跳状态标注为「正在停机」（可利用 `runtime_heartbeats.detail` 这个 JSON 字段，`migrations/0004_runtime_heartbeats.sql:19`），避免健康检查误报为「静默死亡」。

---

## 4. 【中】停机与频控窗口的交互未被考虑，存在「重启洗额度」的解释空间

**问题部分**：方案未涉及限流状态。

**后果**：`src/server/platform/rate-limit.ts:26-30` 与 `migrations/0006_rate_limiter.sql:9-14` 说明计数落在 `rate_limiter_flexible`，`expire` 是**绝对 UTC 毫秒**，且 `src/server/platform/rate-limit.ts:36-38` 的退还是 `refund()`（即 `limiter.reward`）。计数在库里、按绝对时间过期，**本身不会因重启重置**——这点方案是安全的，但需要有据可查。真正的风险在另一头：如果停机时 `exit(0)` 截断了某个已 `take()` 成功、业务又失败、但 `refundQuietly`（`src/server/platform/rate-limit.ts:286-294`）还没跑到的请求，那么额度被白扣；反过来若有人把「停机时清限流表」当运维惯例，`006` 那张表没有任何不可变守卫（对比 0042 给 `operation_records` 加了 `BEFORE DELETE/UPDATE` 守卫），删一行就洗掉一次滥用记录，**且不留审计**。

**建议**：方案里写明「停机流程**不得**触碰 `rate_limiter_flexible`」，并把该表纳入与 `operation_records` 同级的运维保护清单（若要加 DELETE 守卫，注意该表被 `rate-limiter-flexible` 自身更新，守卫只能挡 DELETE 不能挡 UPDATE）。

---

## 5. 【低-中】`server.close()` 的返回值与错误路径被忽略

**问题部分**：`server.close();` 没有 await、没有回调、没有错误处理。

**后果**：`server.close()` 只停止**接受新连接**，不终止 keep-alive 连接；Node 不会在仍有 socket 时让进程退出。方案靠 `sleep(5000)` 掩盖这一点，于是「5 秒到了连接还没断」的情况直接掉进 `exit(0)`。同时 `close()` 若抛错（例如已被关闭），该异常在 `async` 处理器里会变成 **unhandled rejection**，而方案没有 `process.on('unhandledRejection')`，线上表现为「重启时进程无声消失、退出码非预期」。

**建议**：`await new Promise(r => server.close(r))`，并显式 `server.closeIdleConnections?.()` / `closeAllConnections()` 作为超时兜底；信号处理器外层包 try/catch 并 `log.error`（用现成的 `src/server/platform/log.ts`），确保停机失败**留痕**。

---

## 6. 【低】部署配置面：`stop_grace_period` 大于代码内等待，值得肯定但缺护栏

**问题部分**：`stop_grace_period: 15s` vs 代码内 5s。

**后果**：方向是对的（编排给的宽限期长于应用自等待），但两者是**硬编码在两个地方的两个数字**，没有任何一致性校验。若有人调小 `stop_grace_period` 到 3s，代码会先被 SIGKILL，`closeDb()` 与审计 flush 全部跳过，而且**没有任何测试或启动自检会发现这个不一致**。

**建议**：加一条启动自检（`src/instrumentation-node.ts:17-38` 里已有 `selfCheck` 的位置可以挂），把「配置的宽限期 vs 代码内等待」的差值打日志；差值小于安全余量时报 `log.error`。这与仓库既有做法一致（`instrumentation-node.ts:32-36` 明确选择了「不退出但大声报」）。

---

## 不构成问题、但方案该写清楚的

`src/server/platform/heartbeat.ts:41-44` 的 `WORKER_DEAD_MS = 120_000` 远大于本方案的 15 秒宽限期，所以**停机不会触发 worker 判死**——这是好事，说明现有阈值有余量。但方案没有引用这个数字，评审者无法判断 15s 是被论证过的还是拍脑袋的。建议在方案里把「15s < 30s(stale) < 120s(dead)」这个不等式写出来，让停机宽限期变成**有依据的约束**而非配置巧合。

---

**总体**：方案在可用性上方向正确，但把「停机」当作纯运维动作来设计，遗漏了它同时是一个**安全边界事件**——审计通道（0042 刚刚加固的那条）、幂等键、限流计数都在这 5-15 秒内失去保护。最低要求是去掉 `exit(0)` 兜底、不动 worker 现有实现、并把「重启不丢审计」写进验收。
