## 性能工程师评审意见

**核心结论：方案写的表结构在库里不存在。** `plugin_favorites` 是 (0012_interactions.sql:41-48) 定义的四列复合主键表，无 `position`、无 `version`；0039 之后收藏拆成三张表。方案按单表设计，基准就错了——下面第 1 条是所有其他问题的前提。

---

### 1. 表结构假设错误，方案可能根本跑不起来（数据库迁移层面，最严重）

**问题**：方案第 1 节对 `plugin_favorites` 执行 `ADD COLUMN position/version`。实际库中这张表只有 `user_id / plugin_id / created_at`（0012_interactions.sql:41-48），而且 0039 把收藏体系拆成了三张同构表：`plugin_favorites`、`pack_favorites`（0039:68-75）、`post_favorites`（0039:84-91）。前端讨论区的“收藏夹条目排序”按 0039 的默认 `target_kind` 覆盖三类内容，方案只改插件表。

**后果**：
- 用户拖拽一个整合包（pack）或帖子（post）的条目，`newPosition` 无处可写——`pack_favorites`/`post_favorites` 都没有位置列（0039:68-75、0039:84-91）。功能对 2/3 的收藏类型直接失效。
- 更实际的性能隐患：如果按“三张表各加一列”补救，写入逻辑要复制三份，而三份的语义差异（统一写入由 `FAVORITE_TABLES` 映射，interactions/index.ts:156-160）意味着重试循环也要复制三份，复杂度三倍。

**建议**：把方案基准改成三张表统一加 `position INTEGER NOT NULL DEFAULT 0`，并且复用现成的 `FAVORITE_TABLES` 映射（interactions/index.ts:156-160）来生成语句，不写三份代码。另外确认 `position` 的作用域是“夹内”（folder_id 内），不是“用户内”——否则跨夹排序会错。

---

### 2. `while (true)` 重试无上限、无退避，在 SQLite 单写者模型下会变成 CPU 自旋（最要命的性能问题）

**问题**：方案第 2 节的重试是 `while (true)` 直到 `changes === 1`，第 3 节明确“并发冲突时循环重试，直到成功”，**没有最大次数、没有退避、没有 yield**。

**后果**：
- 迁移 db.ts:56-58 是 `synchronous = FULL` + WAL，单次写事务要等 fsync。better-sqlite3 是**同步驱动**，db.ts:8-9 的注释自己写了大写警告：“同步驱动，等待会阻塞所属线程”。这个循环一旦活锁，阻塞的不是一个请求，而是**整个进程的事件循环**——所有其他请求一起卡死。
- 更坏的是活锁必然发生：CAS 的失败条件是 `version` 被别人推进了。多个请求同时对**同一个 (user_id, plugin_id)** 做重试时，每次重试都要先 `SELECT` 再 `UPDATE`，自己没有 CAS 间隙的让步机制，在单进程同步驱动下重试方会连续争抢同一行。方案第 3 节说的“并发高时自动重试”在这里是**放大**而非缓解：重试次数随并发度超线性增长。
- 事务边界也没说清。`interactions` 模块所有写都在 `withTransaction` 里（tx.ts:49-57，createReport 在 index.ts:1281 起就是 `withTransaction`）。如果这个重试循环**在事务内部**，那 `result.changes === 1` 的 CAS 完全无效——同一事务内的 SELECT/UPDATE 看不到其他事务的提交，读到的是同一快照，循环会 100% 空转到天荒地老（真正的死循环，不是理论风险）。如果**在事务外**，那就不满足 tx.ts:4-7 的“外部流程不得拆成多次独立提交”。

**建议**：
- 重试上界写死（如 3-5 次），失败就返回冲突给前端，由前端重拉列表。这比“用户感知不到冲突”诚实，也避免自旋。
- 明确要求：CAS 的 SELECT/UPDATE 必须在**同一个** `withTransaction` 里（满足 tx.ts 纪律），且循环次数上限在事务内无法绕开时，改为**整段事务重试**，不能在事务内部重试 CAS。
- 若确实要吸收并发，用 `busy_timeout`（db.ts:60 已配 5000ms）而不是应用层自旋——但注意 5000ms 会让同步驱动阻塞线程 5 秒，这个值在拖拽场景偏高。

---

### 3. 拖拽整夹重排会放大成 O(n) 次单行 CAS，数据库写入放大 200 倍

**问题**：方案背景说“拖拽调整顺序时**批量更新** position”，但第 2 节的实现是**一条** (userId, pluginId) 的 CAS。n 条条目重排 = n 次“SELECT + UPDATE + version+1”。

**后果**：以 README 里 0039 的收藏量级，一次拖拽 50 个条目：
- 50 次 fsync（synchronous=FULL，db.ts:57），保守按单次 1ms+ 计，一次拖拽就压出几十毫秒到上百毫秒的写锁持有时间；
- 每次 UPDATE 都要改 `version` 列，WAL 里写 50 条独立的脏页，checkpoint 压力跟着涨；
- 如果 n 个用户同时拖拽，写锁串行排队，`busy_timeout=5000` 一旦打满就抛 SQLITE_BUSY，用户侧看到的失败率随并发上升。

**建议**：
- 拖拽是“整个夹的新顺序”语义，应该传**完整的目标顺序数组**，在**一个**事务里用 `CASE WHEN` 批量更新或先删后插紧凑 position（一次 fsync），而不是逐条 CAS。
- 排序键在 DB 层要能支撑顺序读取：现有索引是 `(folder_id, created_at DESC, plugin_id)`（0019:31-32、0039:76、0039:88），**没有 position**。加 `position` 之后必须补 `(folder_id, position)` 索引，否则每次读夹内列表都会 fallback 到临时 B 树排序——这是每日高频路径（`readFavoritePacks` interactions/index.ts:297-300、`listFavoritePlugins` index.ts:1230-1238 都是夹内全量读）。

---

### 4. `position INTEGER NOT NULL DEFAULT 0` 会让所有存量行挤在同一个键值上

**问题**：方案给 position 的默认值是 0，历史收藏行没有回填逻辑。

**后果**：存量收藏全部 `position = 0`，`ORDER BY position` 退化成所有行等值——排序完全由 SQLite 内部顺序决定，**不稳定**（同一查询两次可能不同序）。同时第 3 条新增的 `(folder_id, position)` 索引在这种全是重复值的情况下**选择性为零**，索引等于白建，还可能比全表扫更慢（要按 rowid 二次回表）。

**建议**：迁移里必须回填——用 `ROW_NUMBER() OVER (PARTITION BY folder_id ORDER BY created_at DESC, plugin_id)` 在迁移中给每行分配唯一 position（0039 已经用过 `randomblob`/窗口函数类写法，有先例），并把 `DEFAULT 0` 改掉或加 `UNIQUE(folder_id, position)` 之类的约束兜底，防止后续新增行又全落 0。

---

### 5. `version` 列与现有“不落冗余计数列”的设计纪律冲突，且增加每行写宽

**问题**：方案新增 `version INTEGER NOT NULL DEFAULT 0` 专门服务 CAS。

**后果**：interactions/index.ts:5-8 明写了全模块纪律“计数不落冗余列，一旦漂移就要写修复脚本”。`version` 是每行常驻的额外写字段：每次 position 变更都要写两列而非一列，WAL 脏页和行大小都增加。在拖拽这种高频写路径上，这是纯开销——而 SQLite 本身已能通过 `changes` 判定乐观并发。

**建议**：优先考虑**无 version 方案**：`UPDATE ... WHERE user_id=? AND plugin_id=? AND position = ?`（用旧 position 做 CAS 谓词），省掉一列和一次读取。只有确认 position 可能不唯一、无法作谓词时再退回 version 列，并且要在方案里论证这一列的必要性。

---

### 6. 缺失并发冲突下的读路径退化：三张表各自的夹内读已经是 N+1

**问题（顺带发现，会被本方案加重）**：`listFavoritePacks`/`listFavoritePosts` 是**先查该用户所有 folder_id，再对每个 folder 循环调 `readFavoritePacks`**（index.ts:1185-1197、1213-1223），每个夹一次带 `ROW_NUMBER()` 窗口的查询。

**后果**：一个有 10 个收藏夹的用户，个人中心页 = 11 次查询，其中 10 次各含一次对 `plugin_pack_releases` 全表的 `ROW_NUMBER()` 分区计算（index.ts:266-271，**无 WHERE 下推**，`latest` CTE 会对全表所有版本算窗口）。这是现存瓶颈，本方案加的 position 排序不会改善它。

**建议**：这次改造顺手把 `latest` CTE 收窄到 `WHERE rel.pack_id IN (SELECT pack_id FROM pack_favorites WHERE user_id=?)`，并把跨夹循环改成单条带 `folder_id` 的查询在应用层分组。否则 position 排序只是在一个 O(夹数 × 版本数) 的底座上加东西。

---

**总体判**：方案对“顺序错乱”的现象判断是对的，但落地方案有三处会让性能倒退而非改善——无限重试自旋（第 2 条）、逐条 CAS 的写放大（第 3 条）、全 0 position 导致索引失效（第 4 条）。建议按“单事务批量重排 + 有界重试 + 迁移回填 + 补 (folder_id, position) 索引”重写第 2、3 节，并先把表基准从单表纠正为三表。
