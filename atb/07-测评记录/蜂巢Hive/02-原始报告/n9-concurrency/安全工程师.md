# 安全工程师评审：收藏夹条目排序并发更新

已实际读取：`proposal.md`（全文 34 行）、`migrations/0012_interactions.sql`、`0019_favorite_folders.sql`、`0039_favorite_folders_target_kind.sql`、`0002_triggers.sql`、`0042_audit_immutable.sql`、`0001_baseline.sql`（节选），以及 `src/server/modules/interactions/index.ts`（节选）。

先说结论：**这个方案如果按当前写法落地，会同时引入 4 类安全问题（拒绝服务、越权写入、审计盲区、并发语义错误），我不建议放行。** 按严重度排序如下。

---

## S1【阻断】无上限重试循环 = 单请求即可打满数据库，形成低成本 DoS

**问题部分**：方案 §2「更新逻辑」的 `while (true)` + §3「重试：并发冲突时循环重试，直到成功」。
方案没有重试次数上限、没有退避、没有让出事件循环、没有超时。

**后果**：
- `proposal.md:20-31`：当同一 `(user_id, plugin_id)` 行存在持续竞争（或客户端重放拖拽请求）时，这个 `while(true)` 会无限自旋。每次循环至少执行 1 次 SELECT + 1 次 UPDATE，全部写在同步的 `better-sqlite3` 调用上；该库是**同步阻塞**的（见 `interactions/index.ts:21` 的 `withTransaction` / `withRead` 用法），事件循环被占满，**整个进程的所有用户**连同健康检查一起停摆。
- 更糟的是：方案把 `version` 放在 `plugin_favorites` 上，而 `plugin_favorites` 的主键是 `(user_id, plugin_id)`（`0012_interactions.sql:34-40`）。**同一用户同一插件只有一行**，它的竞争者是「同一用户的另一个浏览器/标签页」——一个用户自己就能触发无限重试，无需任何特权，只需快速拖拽或写个脚本。这是一个「未认证攻击面之外的已认证单用户自伤型 DoS」。
- `RUN` 的 `result.changes === 1` 在 SQLite 里对「值未变化」的 UPDATE 仍可能记为 1（changes 按匹配行数计），如果顺带被用来当「成功」判据，还可能掩盖真正的写入失败。

**建议**：
1. 重试必须有上限（建议 3-5 次）+ 指数退避，超限后向调用方返回明确的冲突错误（例如 409 `排序冲突，请刷新`），**不要**静默吞掉。
2. 每次重试之间必须 `await` 一个 tick（`await new Promise(r => setImmediate(r))`），确保不饿死事件循环。
3. 更好的方向：用 SQLite 的 `BEGIN IMMEDIATE` 把「读-改-写」放进单个 `withTransaction`（项目已有该封装），一次性完成，从根本上不需要应用层重试循环。当前方案在事务外自旋，是自找的复杂度。

## S2【阻断】方案「重建」了一个已存在的表结构，绕过 0039 的既有约束与迁移约定

**问题部分**：方案 §1「表结构」用 `ALTER TABLE plugin_favorites ADD COLUMN position/version`。

**后果**：
- `plugin_favorites` 的真实定义在 `0012_interactions.sql:34-40`，且已被 `0019_favorite_folders.sql:25-27` 加了 `folder_id`（可空）、被 `0039_favorite_folders_target_kind.sql:120` 整库重构后**收藏体系已改为三表**：`pack_favorites`（`0039:68-75`）、`post_favorites`（`0039:80-88`），三者共用 `favorite_folders.target_kind IN ('plugin','pack','post')`（`0039:44`）。方案只给 `plugin_favorites` 加 `position`，意味着**排序语义只在插件收藏上成立**，而 UI 上三类内容共用一个收藏夹体系（`interactions/index.ts:66-72` 的 `FavoriteFolderView.targetKind`、`readFavoritePosts` 按 `f.created_at DESC` 排，见 `interactions/index.ts:296-300`）。结果是同一个夹里插件按 `position`、帖子和整合包按 `created_at`，**同一列表的排序规则由数据来源决定**——这类不一致后续极易演变成「顺序被绕过」的 bug。
- 方案连新增列的可空性/取值范围都没有约束：`position INTEGER NOT NULL DEFAULT 0` 没有 `CHECK (position >= 0)`。`0001_baseline.sql:5-13` 明确约定全局用 `B`/`N` 加 `CHECK`，本文件大量表都写了 `CHECK (created_at >= 0)` 之类。**新列不写 CHECK 直接违反本仓库的建模纪律**，且给 `position` 留了负值/巨值的口子。
- 迁移文件缺头部约定：`0039` 顶部有 `-- dsh:migration-transaction=off`（`0039:1`），`0042` 明确说明「纯增量可安全重放」（`0042:18-19`）。方案没有任何迁移编号、没有 `dsh:` 说明、没有写「是否需要关外键」。按本仓库习惯，这份「SQL 片段」不能被安全地当作迁移评审。

**建议**：不要写「ALTER 片段」，交一份**完整迁移文件**（建议 `0043_favorite_positions.sql`），并明确：
1. `position INTEGER NOT NULL DEFAULT 0 CHECK (position >= 0)`；
2. 是否同时覆盖 `pack_favorites` / `post_favorites`（若只做插件，需在文档里写明「三类不一致」是**已知取舍**，并说明前端对另两类仍按 `created_at`）；
3. 回填策略（存量行 `position` 全为 0 → 排序全部并列，NULLs/ties 的确定性排序键是什么？必须 `ORDER BY position, created_at DESC, plugin_id` 这类兜底全序，否则「顺序不错乱」这个预期根本不成立）。

## S3【高】更新语句的归属校验形同虚设，暴露给越权写入与 IDOR 风险口

**问题部分**：方案 §2 的 SQL 以 `WHERE user_id = ? AND plugin_id = ? AND version = ?` 为唯一归属条件。

**后果**：
- 现状代码是**统一在事务内先校验**的：`assertFavoriteTarget`（`interactions/index.ts:227-232` 起）、`assertFolderOwned`（`interactions/index.ts:199-208`，注释明确写明「不匹配按『不存在』处理，不泄漏别的类型的夹」）、`assertCanWrite(ctx)`（`interactions/index.ts:604`、`interactions/index.ts:637`）。方案把 `userId` 当普通参数拼进 WHERE，**没有说明 userId 的来源**。如果它来自请求体而非 `ctx.userId`，就是标准的 IDOR：任意登录用户可改他人收藏顺序。
- 另外 `version = ?` 这个条件在「行不存在」时的行为是静默失败：`row` 为 `undefined` → `row.version` 抛 `TypeError`，或 `changes === 0` → 进入无限重试（叠加上 S1 就是**永久挂起**）。攻击者可以对一个不存在的 `plugin_id` 反复请求，让服务端在自己的重试循环里空转。这是把「不存在的目标」从 `err.unavailable` 降级成了「服务端资源消耗」。
- 方案完全没有提 `assertCanWrite`（封禁用户 `account_status = 'disabled'` 的写闸门，见 `users.account_status`，`0001_baseline.sql:28`）。收藏排序也必须过这个闸门，否则被封禁用户仍可写库。

**建议**：
1. `userId` 必须只来自 `ctx.userId`，并在入口 `assertCanWrite(ctx)`；
2. 保留 `assertFavoriteTarget` + `assertFolderOwned` 的既有校验链，不要用「WHERE 里带 user_id」替代它们；
3. `row` 为 `undefined` 时立即 `throw err.unavailable(...)`，**绝对不能**进入重试分支；
4. 所有错误对外统一为「不存在」，不区分「别人的 vs 不存在的」（沿用 `assertFolderOwned` 的现有口径，`interactions/index.ts:200-207`）。

## S4【高】排序变更无审计、无幂等键，与 0042 刚修的安全缺陷同类

**问题部分**：方案全文未提审计与幂等。

**后果**：
- `0042_audit_immutable.sql:8-16` 记录了一次真实的安全修复单：《安全修复单-审计表可被删除》——当时正是因为「删审计行即可让已消费的 operation_key 重新可用」，构成伪造通道。该修复刚把 `operation_records` 变为不可删改（`0042:21-27`）。
- 收藏顺序是**用户可见状态**（列表渲染直接依赖），且本方案引入了「批量并发更新」这条新的高频写路径。如果这条路径不写 `operation_records`，则：一次批量重排之后，**无法回答谁在何时把顺序改成了什么**。而 `recordOperationInTx` 已经是本模块的既有纪律（`interactions/index.ts:24` 已 import；举报处理路径在用）。
- 并发 + 无幂等键的叠加风险：前端「每次拖拽都发一个请求」（`proposal.md:4`），重试机制会产生**同一次拖拽的多条等价写入**。没有 `operation_key` 去重，审计里会出现重复记录，也没法在事后区分「用户拖了三次」和「网络重试了三次」——这正是 0042 修复的那类「不可区分即不可审计」的问题。

**建议**：
1. 排序写入必须在同一事务内 `recordOperationInTx`，`action_type` 形如 `favorite_position_reorder`，带上前后 `position` 快照；
2. 请求携带客户端生成的 `operation_key`，落 `operation_records` 的 `UNIQUE(action_type, operation_key)` 做幂等去重（该唯一约束已在 `0001_baseline.sql` 的 `operation_records` 上，且被 `0042` 的注释点名为关键依赖）；
3. 注意 `0002_triggers.sql` 只对 `review_revisions` / `comment_revisions` 有 `BEFORE DELETE/UPDATE` 守卫（`0002` 中段 `trg_review_revisions_no_delete` 等），`plugin_favorites` 这类互动表**没有**不可变守卫——所以「删掉收藏行再重加」可以洗掉顺序痕迹。若顺序具有取证价值，需要考虑把重排历史落到不可变表，而不是只覆盖当前 `position`。

## S5【中】`version` 乐观锁选型与「用户感知不到冲突」的预期自相矛盾

**问题部分**：§2 用 `version` 乐观锁，§3 用无限重试，§「预期」声称「用户感知不到冲突」。

**后果**：
- `proposal.md:33` 的「用户感知不到冲突」+ §3「直到成功」= **静默覆盖**。两个标签页同时拖拽时，后完成的一方会用自己的 `newPosition` 覆盖前者，`version` 递增让「谁最后写」变成纯粹的时间竞态。用户确实「感知不到」，但**实际上是丢了一次操作且不告知**。从安全/可追责角度这比报错更糟：没有失败记录，事后无法归因。
- `position` 是**相对排序**还是**稀疏绝对序号**？方案没定义。如果是连续整数编号，`position` 唯一性完全没有约束（方案里没有 `UNIQUE(folder_id, position)` 或 `UNIQUE(user_id, position)`），两个条目拿到同一 `position` 是允许的，排序结果退化为未定义顺序 —— 「顺序不会错乱」这个预期（`proposal.md:32`）没有任何机制保证。
- 缺少夹内顺序的作用域说明：`0039` 之后列表是按 `folder_id` 分组的（`idx_plugin_favorites_by_folder ON plugin_favorites(folder_id, created_at DESC, plugin_id)`，`0019:28-29`）。`position` 必须是**夹内**有序，跨夹撞号无害但必须写清，否则「拖到另一个夹」这一动作（`setFavoriteInKind` 的移动语义，`interactions/index.ts` 中 `DO UPDATE SET folder_id = excluded.folder_id`）会产生什么 position 需要明确。

**建议**：
1. 明确定义 `position` 的语义（推荐稀疏大间隔序号，如步长 1024，插入取中值，避免每次重排全夹 UPDATE）；
2. 加 `UNIQUE (folder_id, position)` 或至少 `UNIQUE (user_id, plugin_id)` 之外的夹内唯一索引，用数据库兜底「同号并列」；
3. 冲突时**明确告知**（返回 409 + 最新顺序让前端重放），而不是无限静默重试；
4. 「预期」一节删掉「用户感知不到冲突」，改成「冲突被检测并以确定性方式解决」。

## 一句话结论

方案解决的是一个真实的并发问题，但实现方式（**事务外无界自旋 + 不完整的表结构变更 + 弱化的归属校验 + 零审计**）会让当前这套**好不容易把审计不可变、收藏夹归属校验、写闸门都补齐的系统**出现退化。请按 S1→S4 全部整改后再送审；S5 建议一并处理，否则「顺序不会错乱」这条预期无法被验证。

附：本评审**未**覆盖的一次性核对项 —— 方案引用的 `plugin_favorites.position` 与前端「拖拽后立即 GET 刷新」之间是否存在缓存/竞态（属前端行为），以及 `0043` 若需重建表则必须遵循 `0039:1-20` 那套「关 FK → 建新表 → 拷 → 删旧索引 → 删旧表 → 改名 → 建新索引 → 开 FK → `foreign_key_check`」的实测钉死顺序。若迁移走「重建表」路线，请单独让 DBA/迁移负责人复核该顺序。
