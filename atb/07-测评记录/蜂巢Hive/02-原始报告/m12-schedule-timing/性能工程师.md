# 性能工程师评审：定时任务调度时间改造

## 结论先说

方案的**方向没错**（用 `available_at` 推迟执行是对的做法），但实现方式有两处会直接损害性能的问题：**新增 `scheduled_at` 列及其索引会破坏现有的领取索引，造成全表排序**；**`if (now >= target)` 的写法和主循环节拍绑定，会导致每秒对两个任务进行重复 upsert 检查**。另有一个会让「固定时刻」在**多 worker 场景下变成 N 次重复扫表**的设计问题。

---

## 问题 1（严重）：`scheduled_at` 与既有 `available_at` 语义重复，且新索引不会被领取路径使用

**① 哪部分有问题**
方案 §1 提议 `ADD COLUMN scheduled_at` + `CREATE INDEX idx_tasks_scheduled (processing_state, scheduled_at, id)`。

但 0007 重建后的表**已有** `available_at INTEGER NOT NULL`，并且已存在索引：

- `migrations/0007_task_type_plugin_discovery.sql` 重建时保留：`available_at INTEGER NOT NULL CHECK (available_at >= 0)`
- 同文件末尾：`CREATE INDEX idx_tasks_claimable ON background_tasks(processing_state, available_at, scheduling_group, id);`

而领取查询 `src/server/modules/tasks/service.ts:130-137` 用的是 `available_at <= ?`：

```sql
WHERE processing_state IN ('queued','retry_wait')
  AND available_at <= ?
ORDER BY available_at ASC, created_at ASC, id ASC
```

**② 后果**
- `scheduled_at` 加了但**没有任何查询读它**（领取仍按 `available_at`），要让它生效必须同步改领取 SQL；改成 `ORDER BY scheduled_at` 就会立刻**失去 `idx_tasks_claimable` 的排序能力**，SQLite 只能对满足 `processing_state IN (...)` 的行做临时 B 树排序（EXPLAIN 会看到 `USE TEMP B-TREE FOR ORDER BY`）。这一行是 worker 每次 `claim()` 都跑的**最高频查询**，`service.ts:136` 的 `LIMIT 1` 本来能靠索引直接取第一行，退化后要扫描并排序全部 queued/retry_wait 行。
- 更糟的是任务表**永不删除**：`succeeded`/`failed` 是终态，行会长期累积（`0007` 的 `idx_tasks_lease` 只覆盖 `processing_state`）。历史成功任务越多，任何按 `scheduled_at` 的排序/扫描就越慢。
- 两列并存意味着**双写但不一致**：`enqueue` (`service.ts:293-299`) 只写 `available_at`，`scheduled_at` 会大面积为 NULL，索引选择性极差（`idx_tasks_scheduled` 第二列近乎全 NULL，几乎无法用于范围扫描），等于凭空增加一条无用的写放大。

**③ 建议**
- **不要新增 `scheduled_at`**。定时语义直接用现成的 `availableAt`：`tasks.enqueue({ ..., availableAt: targetTs })`。
- `ensureDailyDiscoveryTask` 已经在这么做（`src/worker/scheduled.ts` 末尾 `availableAt: now` 处改成 `target` 即可），零 schema 变更、零新索引。
- 若产品要求「记录计划时刻」以备观测，把它塞进已有的 `payload`（`payload.date` / `payload.scheduled_for`），`payload` 已是 `json_valid` 列，不产生索引成本。
- 顺带：如果迁移真的要重建表（见问题 5），**保留 0007 的两个索引名与列顺序不变**，别让 `idx_tasks_claimable` 变形。

## 问题 2（严重）：`if (now >= target)` + 复用主循环节拍 = 每秒 2 次无效 upsert

**① 哪部分有问题**
方案 §2 的 `tick()` 挂到「复用现有主循环的节拍」，条件是 `if (now >= target)`。

主循环节拍是 `IDLE_SLEEP_MS = RECOVERY_SCAN_INTERVAL_MS = 10 * SECOND`（`src/server/modules/tasks/constants.ts:43`、`:37`），且 `run()` 在 `handled === 0` 时每轮 sleep（`src/worker/main.ts:213-222`）。而现有实现**已经**用节流变量挡住了这件事：

```ts
if (options.scheduledTasks === true && now >= nextScheduleCheckAt) {
  nextScheduleCheckAt = now + DISCOVERY_SCHEDULE_CHECK_MS;  // 60_000
```

见 `src/worker/main.ts:177-179`，`DISCOVERY_SCHEDULE_CHECK_MS = 60_000`（`src/worker/scheduled.ts:33`）。

**② 后果**
- 方案把 `>=` 判断直接放进循环，**丢掉了这个节流**：一天 24 小时内 `now >= target` 永远为真，于是每个 tick（10s 一次）都跑 2 次 `enqueue`。
- 每次 `enqueue` 不是免费的：`service.ts` 的 `enqueue` 走 `withTransaction`（`service.ts:302`），即一次 `BEGIN` + 一次 `INSERT`（触发 `UNIQUE(task_type, deduplication_key)` 冲突，走异常/`ON CONFLICT` 路径）+ `COMMIT`。按 10s 节拍 = **8640 次/天 × 2 个 schedule ≈ 1.7 万次无用写事务**，全部压在 better-sqlite3 的**同步单写者**上（`service.ts:20` 注释明确 better-sqlite3 是同步驱动）。
- 这些写事务与真正的 `claim`（`service.ts:270`）、`renew`（`RENEW_INTERVAL_MS = 30s`）、`finish` 抢同一把写锁。SQLite `busy_timeout` 一旦触发，`claim` 会变慢甚至超时，**直接拉高任务吞吐延迟**，而 `renew` 变慢还会让租约被误判过期 → `recoverExpired` 多做无用的回收（`main.ts:174`）。
- 更隐蔽的一点：每天过了 03:00 后永远为真，即使当天的 `plugin_discovery` 还在 `running`，也在反复打这个事务。

**③ 建议**
- 保留现有节流模型，**不要**用 `now >= target` 直接判真。改成「下次触发时刻」比较：`if (now >= nextFireAt)`，触发后把 `nextFireAt` 推到**明天的 target**（不是 `now + 60s`），这样每天每个 schedule 只做 **1 次** `enqueue`。
- 判断「今天是否已触发」用进程内 O(1) 状态（`lastFiredDay[schedule] = 'YYYY-MM-DD'`），配合 `UNIQUE(task_type, deduplication_key)` 兜底，不要靠反复 hit 数据库去重。
- 检查频率维持 60s 级即可，02:59:59→03:00:00 的偏差对「每日发现」无业务影响；若产品接受秒级精度，也应该用 `setTimeout(next - now)` 定点唤醒，而不是把轮询频率提到 1s。

## 问题 3（中）：多 worker 时排程是 N 份重复扫表

**① 哪部分有问题**
`scheduledTasks: true` 是**每个 worker 进程**都传的（`src/worker/main.ts:263`）。方案 §2 的调度循环同样在每个 worker 里跑。

**② 后果**
- 副本数 3 → 每天每 schedule 打 3 次 `enqueue` 事务；虽然 `UNIQUE` 保证只建一条任务，但**写锁竞争和异常路径的成本是 N 倍**，且 `log.info('已排入当天…')` 只有 1 个副本会打，另外 2 个走冲突分支——排查时看起来像「排程失效」。
- 症状在问题 2 的基础上被放大：10s 节拍 × N 副本 × 2 schedule。

**③ 建议**
- 短期：既然只 1 条任务能成功，就**别让所有副本每天都写**。用「先读后写」短路：`enqueue` 前先 `SELECT 1 FROM background_tasks WHERE task_type=? AND deduplication_key=?`（命中率高、走 UNIQUE 索引覆盖，是纯读不拿写锁），命中就直接跳过，不进事务。这把 N 次写事务降为 N 次索引点查。
- 长期：把「谁负责排程」收敛到一个位置（例如只有拿到某个轻量 lease 的 worker 才执行 tick），或用现成的 `runtime_heartbeats`（migrations/0004）选主。

## 问题 4（中）：`cache_warmup` 走 `enqueue` 会与用户任务抢 `max_concurrent=4`

**① 哪部分有问题**
方案 §2 只给了 `dedup`，**没给 `schedulingGroup`**。而 `enqueue` 对 `schedulingGroup` 是必填且非空校验（`service.ts:200-203` 抛 `err.input`）。现有的 `plugin_discovery` 特意用了独立组 `DISCOVERY_SCHEDULING_GROUP = 'plugin_discovery_schedule'`（`src/worker/scheduled.ts:36`），注释写明「与用户任务分开，便于观测」。

**② 后果**
- 若不传 → **运行时直接抛错**，`tick` 抛出后被 `main.ts:183-185` 的 catch 吞掉，只留一行 error 日志，排程静默失效。
- 若传了共用组 → `cache_warmup` 与 `review_publish`/`comment_publish` 同组争抢。`claim` 的排序是 `ORDER BY available_at ASC, created_at ASC, id ASC`（`service.ts:136`），04:00 排入的 warmup 因 `created_at` 较早，会**插到用户新提交之前**被领取，占掉 4 个并发槽之一。`MAX_CONCURRENT_TASKS = 4` 是全站硬上限（`constants.ts:16`），且 `execute` 是**串行**的（`main.ts:200-203`：`for (const claim of claims) await execute(claim)`）——一个耗时的 warmup 会直接拖慢同批用户任务的开始时间。

**③ 建议**
- 每个 schedule 显式带独立 `schedulingGroup`（如 `'cache_warmup_schedule'`），至少在观测和后续分组限流上留出空间。
- 给 warmup 的 payload 设**明确的请求/时长预算**（对齐 `discoveryBudgetFor` 的做法，`scheduled.ts` 中 `max_requests` 就是这个思路），避免单次占用 `TASK_DEADLINE_MS = 300s` 的整个窗口。
- 若 warmup 属于可延后的工作，考虑把它的 `availableAt` 排到低峰、并显式在 claim 层做组级限流，而不是靠创建时间排序被动抢槽。

## 问题 5（中）：迁移编号 0042 已被占用，且重建 `background_tasks` 的代价被低估

**① 哪部分有问题**
方案 §1 写「迁移 0042」。实际 `migrations/0042_audit_immutable.sql` **已存在**（审计表不可变触发器）。下一个可用编号是 **0043**。

同时方案 §3 说「迁移里放开 CHECK」新增 `cache_warmup`。按 0007 的注释，SQLite 改不了 CHECK，**必须整表重建**：

> 只能"新建 → 拷数据 → 删旧 → 改名"…… 必须先把 `foreign_keys` 关掉…… 文件头声明 `dsh:migration-transaction=off`

**② 后果**
- 编号冲突会导致迁移器把 0042 判为重复而跳过（`0042` 文件注释写着「迁移器按文件名去重」），**新迁移永远不执行**，`cache_warmup` 入队时撞 CHECK 失败。
- 重建表 = 全表 `INSERT ... SELECT` + `DROP` + 重建索引。`background_tasks` 是只增表（终态行永不删），生产上若已积累数十万行，这一步是**秒级到分钟级写锁**，迁移期间所有 `claim`/`renew`/`finish` 全部阻塞；而 `dsh:migration-transaction=off` 意味着**中途失败会留半成品表**（0007 注释明确承认这是「重建表的固有代价」）。
- 更省事的观察：`0007` 重建时重建的索引里**没有** `idx_tasks_scheduled`（不存在），但方案的 `idx_tasks_scheduled` 若在新迁移里加，和问题 1 重叠。

**③ 建议**
- 编号改 **0043**，并在 PR 里显式核对 `migrations/` 目录的最大编号（当前 0042）。
- **优先考虑免重建的路子**：把 `cache_warmup` 复用现有 `task_type` 之一（如 `plugin_discovery` 加 payload 区分），或在应用层用 `payload.kind` 分派——`TaskTypes` 在 `src/packages/common/field-rules.ts` 是代码常量，但**DB CHECK 才是硬约束**，能不动表就别动。
- 若必须重建：在迁移前记录 `SELECT COUNT(*) FROM background_tasks` 并在发布流程中固化「重建耗时 vs 行数」的基线；安排在低峰执行；重建时必须**逐个列出列名**（0007 那样，不用 `SELECT *`），并**同步更新 `field-rules.ts` 的 `TaskTypes`**，否则类型层与 DB 漂移。

## 问题 6（轻）：`atTime`/`ymd` 的时区决定「固定时刻」是否真的固定

**① 哪部分有问题**
方案用了未定义的 `ymd(now)` / `atTime(now, s.at)`，`at: '03:00'` 没有标注时区。

平台约定是**全站 UTC 毫秒**（`src/server/platform/time.ts:5`：`数据库中所有时刻为 Unix 纪元起算的 UTC 毫秒整数`）。

**② 后果**
- 若 `ymd` 用本地时区而 `available_at` 存 UTC，跨时区容器/夏令时下「03:00」会漂移一小时，且 `dedup(today)` 的日期键在 UTC 日界附近可能**生成昨天/明天的 key** → 同一天排两次或整天不排。
- 对性能的间接影响：日界附近重复 key 会让 `UNIQUE` 冲突分支多跑，或让一天出现两条 warmup 任务叠跑，占用并发槽。

**③ 建议**
- 显式钉死「按 UTC 还是按固定偏移（如 `Asia/Shanghai`）计算 `at`」，写进方案，并在 `dedup` key 里带上**同一个时区口径的日期**（现有 `discoveryDailyKey` 已是按天，复用它）。
- 把 `atTime`/`ymd` 放进 `src/server/platform/time.ts`（那里是唯一允许碰时间的地方，`:6` 明确「业务代码不得散落 Date.now()」），而不是 `scheduled.ts` 里就地写。

## 一句话汇总（按修复优先级）

| 优先级 | 问题 | 位置 | 处置 |
|---|---|---|---|
| P0 | 丢掉 60s 节流，`now >= target` 导致每天 1.7 万次写事务 | `main.ts:177-179`、`scheduled.ts:33` | 改「下次触发时刻」，每天 1 次 |
| P0 | `scheduled_at` 冗余，新索引不被领取用；改排序会丢 `idx_tasks_claimable` | `0007` 索引、`service.ts:130-137` | 直接用 `availableAt`，不加列 |
| P1 | 迁移编号 0042 冲突 → 迁移被跳过 | `migrations/0042_audit_immutable.sql` | 改 0043，核对最大编号 |
| P1 | 重建表是只增表的全量拷贝 + 无事务 | `0007` 头注释 | 尽量免重建；必须重建则低峰 + 列名全列 |
| P1 | 多 worker 重复 enqueue | `main.ts:263` | 先 SELECT 短路，再进事务 |
| P2 | `cache_warmup` 缺 `schedulingGroup`（会抛错）或抢并发槽 | `service.ts:200-203`、`constants.ts:16,43` | 独立组 + payload 预算 |
| P2 | `atTime`/`ymd` 时区未钉死 | `time.ts:5` | 明确 UTC/固定偏移，函数归一 |

**“无新表”这个结论我认可**——整个方案确实不需要新表。但“无新列”也该成立：`available_at` + `scheduling_group` + `payload` 已经把这件事表达完整了，加 `scheduled_at` 只会多一个永远为 NULL 的列和一条用不上的索引。
