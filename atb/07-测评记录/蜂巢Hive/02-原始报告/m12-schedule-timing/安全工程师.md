# 安全评审：定时任务调度时间改造（m12-schedule-timing）

## 结论

**不通过，需重做。** 方案存在 1 个致命缺陷（迁移编号冲突导致生产迁移器静默跳过或数据丢失），以及 3 个高危缺陷（调度逻辑导致任务永不入队或每日重复入队、新增任务类型绕过不可变审计链、任务执行路径完全缺失 handler 造成“静默 skipped/永久失败”）。此外方案把“无新表”当作安全优势，但实际引入了队列语义污染与无界执行面的问题。

以下逐条列出，每条含：问题部分 / 后果（文件:行号）/ 建议。

## 一、致命：迁移编号 0042 已被占用，方案会与审计表不可变修复直接冲突

**① 问题部分**：方案 §1 写“给 background_tasks 加一列（迁移 0042）”。

**② 后果（migrations/0042_audit_immutable.sql:1）**

该编号已被 `0042_audit_immutable.sql` 占用，它正是上一次安全修复单《安全修复单-审计表可被删除.md》的产物，内容为 `trg_operation_records_no_delete` / `trg_operation_records_no_update` 两个触发器（同文件 :19-25）。

具体风险有两层：

- **迁移器按文件名去重**（该文件 :14 自述“纯增量，可安全重放（迁移器按文件名去重）”）。若开发者在本地或分支上把新迁移也命名成 `0042_*.sql`，两者文件名不同但编号相同，**去重机制不会拦住**，执行顺序取决于文件名字典序：`0042_audit_immutable.sql` < `0042_scheduled_at.sql`，看起来恰好排在后面没事；但只要命名变成 `0042_schedule_timing.sql`，字典序上 `schedule` < `audit` 不成立而 `audit` < `schedule` 成立 —— 这类顺序依赖**没有任何检查在守**。更糟的是若有人误覆盖同名文件，审计触发器会被**整份静默丢弃**，而 REPLAY 语义会认为“已应用过”直接跳过。
- 丢失该触发器后，`operation_records` 的 `UNIQUE(action_type, operation_key)` 幂等链（见该文件 :6-11 注释所述 setUserRole/setUserStatus/configuration_revisions/catalog 落库多条关键路径）重新变成可被删除重置 —— 即那份安全修复单要堵的“不需要改代码的伪造通道”**原地复活**。

**③ 建议**

- 新迁移改用 **0043**（`0043_task_scheduled_at.sql`），并在文件头注明“本迁移与 0042 的关系（互不依赖）”。
- 补一条**迁移编号唯一性**的测试/CI 检查（现有 0027、0035 已缺失，说明该目录已有编号空洞历史，更需要机器校验）。这条检查本身就是安全项：它防止的正是“审计守卫被同名/近名文件顶掉”。

## 二、高危：`background_tasks` 重建表的迁移模式没有沿用，且方案漏了 CHECK 重建的真正代价

**① 问题部分**：方案 §3 只说“cache_warmup 需要新的 task_type（迁移里放开 CHECK）”，§1 却说“ALTER TABLE ... ADD COLUMN”。

**② 后果（migrations/0007_task_type_plugin_discovery.sql:1-16, :23, :60-73）**

`task_type` 的约束是 `CHECK (task_type IN ('review_check','review_publish','comment_check','comment_publish','plugin_discovery'))`（0007:23）。SQLite **改不了 CHECK**（0007:6-7 明写），要放开就必须重建整张表：`PRAGMA foreign_keys=OFF` + 自管事务（`dsh:migration-transaction=off`）+ 拷数据 + DROP + 重建索引（0007:60-73）。

方案对这个代价**只字未提**，等于把一个高风险 DDL 混进了“加一列”的轻松叙述里。安全上真正的问题在于：

- 0007:12 自己承认“万一中途失败，会留下半成品（执行器的其它迁移有自动回滚，这条没有）”。`background_tasks` 被 `background_task_attempts.task_id` 与 `operation_records.task_id` 外键引用（0007:9）—— 重建期间 `foreign_keys=OFF` 是一个**外键校验真空窗口**，此时若有并发写（web 进程也在 enqueue！见 service.ts:245 的 `withTransaction((tx: Tx) => run(tx.db), db)`），会产生**指向新表不存在的 task_id 的孤儿 attempt / operation_records 行**，而在 `foreign_keys=OFF` 下它们会被静默接受、`PRAGMA foreign_key_check` 事后才会暴露。`operation_records` 现在又**不能删**（0042 的 BEFORE DELETE 触发器），孤儿审计行将永久残留且无法修复。
- 更严重：重建表 + `DROP TABLE background_tasks` 会触发对 `background_tasks` 的 DELETE。若此前有人在 `background_tasks` 上加了不可变/审计类触发器，DROP 时的行为将不可控。当前 0002 里 33 个触发器没有覆盖该表，但**方案应当明确写出这一前置核查**，否则未来任何一次加守卫都会让迁移炸在半途。

**③ 建议**

- 迁移沿用 0007 的完整骨架（PRAGMA 在 BEGIN 前、DDL 在事务内、显式列名不用 `SELECT *`、索引按 0001 重建），并在文件头**显式声明 `dsh:migration-transaction=off`**。
- 迁移执行期间**必须停止 worker 与 web 写入**（维护窗口或先置只读），把外键真空窗口压到零;并在迁移后加 `PRAGMA foreign_key_check` 断言。
- `idx_tasks_claimable`、`idx_tasks_lease`（0007:69-70）以及方案想加的 `idx_tasks_scheduled` 三个索引都要重建，不要漏。
- **更强建议：不要放开 CHECK。** 见第四条 —— `cache_warmup` 根本没有 handler，加这个类型等于扩大攻击面。

## 三、高危：调度逻辑无法做到“每天固定时间跑”，并在失败后造成每日重复入队

**① 问题部分**：方案 §2 的 `tick`：

```
if (now >= target) { await tasks.enqueue({... deduplicationKey: s.dedup(today) ...}) }
```

**② 后果（src/worker/scheduled.ts:8-13, src/server/modules/tasks/service.ts:186-197, 211-213）**

两个独立缺陷：

**(a) `now >= target` 不是“在 03:00 跑”，而是“03:00 之后每次 tick 都试”。** 这本身靠 dedup 兜住，但 dedup 只在**任务行仍存在且同 key** 时生效。而 `deduplicationKey` 是 `discovery:github:${d}`，`d` 是当天日期 —— 一旦当天的任务跑完变成 `succeeded` 终态，**行还在，同 key 再次 enqueue 会被 `service.ts:211-213` 判为 existing 而返回 `created:false`**，这一点是对的。但方案**完全没有处理**以下情形：任务 `failed`（终态）后当天不会再试 —— 这不算安全问题。

**(b) 真正的安全问题是 `d` 的来源。** 方案伪代码用 `ymd(now)`，而现有实现刻意用 `discoveryDailyKey(now)`（discovery.ts:122-124），其内部是 `formatDate(now)`，**时区钉死 Asia/Shanghai**（time.ts:13, 32-34）。time.ts:1-11 的注释说明了这个坑：“线上 VPS 是 UTC，于是页面上所有时间都比北京时间少 8 小时 —— 本地全对、线上全错”。如果方案的 `ymd(now)` 用服务器本地时区或 `toISOString().slice(0,10)`（UTC），那么：
- 在 UTC 服务器上，`03:00` 到底是北京时间 03:00 还是 UTC 03:00（=北京 11:00）？`atTime(now, '03:00')` 的实现方案**没给**，语义不明。
- 更危险的是 `d` 用 UTC 日期而 `atTime` 用本地时间（或反之）时，**跨零点区间会产生两个不同的 key、或同一 key 被跨日复用**，导致：某天的发现任务被跳过（漏跑），或某天的任务用错日期去 `operation_records` 里做 `run_key` 审计前缀（discovery.ts:87-89 表明 runKey 直接进审计）。审计键错日期 = 事后无法用日期定位“那天到底跑没跑”，这直接削弱审计可追溯性。

**(c) `tick` 里 `for ... await enqueue` 无错误隔离。** 第一个 schedule 的 enqueue 抛错（如 deduplicationKey 为空命中 service.ts:189-191，或 CHECK 失败）会让第二个 schedule **当天彻底不排**，且异常向上冒到 worker 主循环；而主循环外层若因此退出，worker 会停止心跳 → 被判定 stale。方案没有 try/catch 也没有 skipReason 机制，**丢失了现有 `discoveryScheduleSkipReason`（scheduled.ts:48-60）那套“硬刹车 + 如实记录为什么没跑”的能力**。

**③ 建议**

- 强制复用 `discoveryDailyKey` / `formatDate` 的时区语义（Asia/Shanghai），方案里必须写明 `ymd()` 的实现来源，禁止用 `toISOString()`；建议在 `packages/common/time.ts` 增加唯一的 `ymdShanghai(ms)` 并让它成为**唯一入口**，用 lint/测试禁止直接 `toISOString().slice(0,10)`。
- `atTime(now, '03:00')` 必须给出实现，并明确“Asia/Shanghai 的 03:00 对应的 UTC 毫秒”换算；补跨 DST/跨零点用例（Asia/Shanghai 无 DST，但代码不能依赖这一点）。
- `tick` 内每个 schedule **独立 try/catch**，失败只 log 不扩散；保留并推广 `ScheduleEnvView`/`skipReason` 的刹车与原因回报机制，方案应说明 `DSH_REVIEW_DISCOVERY_DAILY=0` 这类现有开关在新调度器下**仍然有效**（否则运维的紧急刹车会静默失效 —— 这是运维安全项的回归）。
- 明确 `scheduledTasks: false` 默认值（main.ts:63-70）在新调度器下保持不变，避免测试/调试环境凭空产生任务。

## 四、高危：`cache_warmup` 无 handler，必然产生“静默 skipped 或永久失败”的定时垃圾，且扩大无鉴权执行面

**① 问题部分**：方案 §2 引入 `cache_warmup`，§3 只加迁移，**没说 handler、没说谁触发、没说它做什么**。

**② 后果（src/worker/main.ts:89-102, src/packages/common/field-rules.ts 的 TaskTypes）**

- `TaskTypes` 是**封闭注册集合**，注释明写“注册集合随迁移版本维护，**不能由配置注入新类型**”（field-rules.ts 该段）。加了迁移和类型却**不注册 handler**，worker 执行时会走 `if (!handler)` 分支，直接 `finish({outcome:'skipped', errorCode:'no_handler'})` 并 `log.warn`（main.ts:89-102）。结果是：每天 04:00 产出一条一定会被 skipped 的任务行 + 一条 warn 日志，**永久性噪音**。运维侧若把 warn 当告警，就是每天一次的假告警疲劳（这会实质性降低对真告警的敏感度 —— 属于安全运营质量退化）。
- 更大的问题：`cache_warmup` 的语义是“预热缓存”。缓存预热天然需要**访问内部/上游资源**。方案没有任何鉴权、预算、上游限流说明（对比 `plugin_discovery` 有完整预算分档与 `GITHUB_TOKEN` 说明，discovery.ts:29-79）。一个无预算、无隔离、由定时器自动触发的任务类型，等于给攻击者/误配置一条**周期性自动执行的上游打点通道**；若未来它被接入需要凭证的资源，凭证使用会脱离现有审计（`operation_records` 按 task_id 关联）。
- 另外 `cache_warmup` 与 `plugin_discovery` 共用一个 `tick` 和同一个 UNIQUE 空间，`dedup: (d) => \`warmup:${d}\`` **没带 task_type 前缀区分度问题**：UNIQUE 是 `(task_type, deduplication_key)`（0007:52），所以技术上不冲突；但 `discovery:github:${d}` 与现有 `discoveryDailyKey` 生成的 `daily:YYYY-MM-DD`（discovery.ts:123）+ 现有 enqueue 用的是 `key`（scheduled.ts:81-89 传的是 `key` 变量），**两套 key 命名体系并存**，同一天可能出现两条 `plugin_discovery` 任务（旧 key `daily:...` 与新 key `discovery:github:...`），意味着**每日发现会跑两遍** —— 直接翻倍消耗 GitHub 上游配额，未认证档只有 60 次/小时（discovery.ts:71-77 明说不认证必然撞 403）。这不是理论风险：方案改 `dedup` 格式却不迁移旧 key，是必然发生的双重排入。

**③ 建议**

- **删掉 `cache_warmup`**，或至少在方案里补齐：handler 实现位置、上游预算（对齐 `DISCOVERY_DEFAULTS` 的分档思路）、失败与限流处理、是否需要凭证以及凭证怎么审计。没有这些，它不应进本方案。
- 若保留，必须显式声明它与 `plugin_discovery` 的配额关系，并禁止在同一 tick 内无上限地叠加外部请求。
- **`dedup` key 必须与现有 `discoveryDailyKey` 统一**，不能新增第二套格式；若确实要改，方案必须包含“旧 key 如何一次性收敛”（否则生产上会双跑）。建议直接调用 `discoveryDailyKey(now)` 而不是手写模板串。
- `field-rules.ts` 的 `TaskTypes` 与迁移 CHECK 必须**同一次变更**同步，并补防漂移测试（scheduled.ts:76-80 的注释记录了“payload 键名漂移导致预算被静默忽略、线上真实踩过”的先例 —— 同类漂移必须在注册集合上再防一次）。

## 五、中危：`scheduled_at` 列与索引对 claim 路径无效，且引入未加约束的时间语义

**① 问题部分**：方案 §1 新增 `scheduled_at INTEGER` + `idx_tasks_scheduled(processing_state, scheduled_at, id)`。

**② 后果（src/server/modules/tasks/service.ts:117-133, 211-218；0001_baseline.sql 中 background_tasks 的 `available_at INTEGER NOT NULL CHECK (available_at >= 0)`）**

- 现有 claim 唯一依赖的排序与过滤是 `available_at`：`WHERE processing_state IN ('queued','retry_wait') AND available_at <= ? ORDER BY available_at ASC, created_at ASC, id ASC`（service.ts:120-131）。新增的 `idx_tasks_scheduled` **claim 根本不会用到**（除非同时改 claim 的 WHERE/ORDER，方案没提）。一个不被任何查询使用的索引只会增加写放大 —— 而且它会和 `idx_tasks_claimable`(processing_state, available_at, scheduling_group, id) 高度重叠。
- `scheduled_at INTEGER` **没有 NOT NULL、没有 `CHECK (scheduled_at >= 0)`**。全库时间列一律带 `>= 0` 校验（0001 里每个时间列都是，例如 `available_at INTEGER NOT NULL CHECK (available_at >= 0)`）。裸 INTEGER 列允许写入 `NULL`、负数、非整数，**破坏了“时间戳一律 UTC 毫秒非负整数”的库级不变量**（field-rules.ts:1-8 明确该规范）。一旦有代码把它当日期做比较，负值/空值会产生静默错误分支。
- 语义重叠：`scheduled_at` 与既有 `available_at` 是什么关系？方案没说。若两者不一致（scheduled_at 已到但 available_at 未到，或反之），claim 用哪个？**两套时间字段并存是典型的“状态真值分裂”**，未来必然出现“显示已到点但仍不执行”或“未到点却执行”的错乱。

**③ 建议**

- **本方案不需要 `scheduled_at`**。真正的排程时刻完全可以在 enqueue 时算好并写入既有的 `available_at` —— 这恰好是现有 `ensureDailyDiscoveryTask` 传 `availableAt: now`（scheduled.ts:98）的同一条路径。删掉新列即消除不变量风险。
- 若产品确实需要“计划时刻”与“可执行时刻”分离，必须：`scheduled_at INTEGER NOT NULL CHECK (scheduled_at >= 0)`、明确 `available_at = max(scheduled_at, ...)` 的推导规则、并**同时**修改 claim 的 WHERE/ORDER 让新索引真正被用上，再补两者关系的一致性 CHECK 或触发器。
- 索引若保留，需给出**实际执行计划证据**（EXPLAIN QUERY PLAN）证明被使用，否则不要加。

## 六、中危：`requested_by: null` 的系统排入 + 新增调度组，需要审计可见性兜底

**① 问题部分**：方案 `requestedBy: null`，`payload: { date: today }`，且未提 `schedulingGroup`。

**② 后果（src/server/modules/tasks/service.ts:190-193, 216；src/worker/scheduled.ts:35）**

- `schedulingGroup` 是 **NOT NULL 且 CHECK trim != ''**（0001 的 background_tasks 定义 + service.ts:190-193 的显式校验）。方案伪代码里 **enqueue 没传 schedulingGroup**，会直接抛 `err.input('调度组不能为空。')` —— 定时器每 tick 抛一次，且（见第三条(c)）会连累同批其他 schedule。这是会**当场炸掉功能**的缺陷，同时也是可观测性问题：现有代码用 `DISCOVERY_SCHEDULING_GROUP = 'plugin_discovery_schedule'`（scheduled.ts:35）把系统调度与用户任务分开以便观测。方案若给两个 schedule 共用一个组，或各组命名随意，会破坏“系统调度占了多少”的观测能力。
- `requested_by: null` 意味着审计只能靠 `actor_kind='system'`（scheduled.ts:82-83 注释：“审计走 operation_records 的 system 身份”）。方案没说明这条链是否延续；若新任务类型的 handler 在写审计时漏了 `task_id` 关联（discovery.ts:87-89 的 `runKey` 与 taskId 关联模式），**系统身份发起的操作将无法回溯到是哪个定时任务触发**，审计链断开。

**③ 建议**

- 每个 schedule 显式配置 `schedulingGroup`（建议 `schedule:<name>` 与现有 `plugin_discovery_schedule` 保持可聚合的前缀），并在方案中给出一致的命名表。
- 明确要求新 handler 一律写 `operation_records` 且带 `task_id`，`actor_kind='system'`；把“系统任务必须有 task_id 关联”作为评审检查项。
- `payload` 键名沿用 snake_case（scheduled.ts:76-80 的漂移教训），并写防漂移测试。

## 七、需要方案补充的安全相关前提

| 缺失项 | 为何是安全问题 |
|---|---|
| 迁移的回滚/前滚策略 | 0007 型迁移无自动回滚（0007:12），失败留半成品；`background_tasks` 是队列核心表，半成品 = 全站任务停摆 |
| `PRAGMA foreign_key_check` 迁移后断言 | 重建期间 `foreign_keys=OFF`（0007:8），孤儿行会被静默接受 |
| 新调度器与 `DSH_REVIEW_DISCOVERY_DAILY=0` / `DSH_REVIEW_CATALOG_OFFLINE=1` 的关系 | 运维紧急刹车是安全控制项，必须明确仍生效 |
| 上游配额（GitHub 60/小时未认证） | 双重排入（第四条）会撞 403，等效于把每日任务变成每日失败 |
| 时钟回拨/NTP 跳变的处理 | `now >= target` 在向回拨后可能当日重排或漏排；建议记录 last-run-date 而非仅依赖 key |

## 建议的最小可行改法

1. **删掉 `scheduled_at` 列和 `idx_tasks_scheduled`**，用既有 `available_at` 表达“计划时刻”。
2. **删掉 `cache_warmup`**（无 handler、无预算、无审计，收益不明确）。
3. 迁移改为 **0043**，若必须加 task_type 则严格照抄 0007 的重建骨架并声明 `migration-transaction=off` + 迁移后 `foreign_key_check`。
4. `tick` 内：复用 `discoveryDailyKey`（禁 `toISOString`）、每个 schedule 独立 try/catch、保留 `skipReason` 刹车、每个 schedule 配 `schedulingGroup`。
5. 补三类测试：迁移编号唯一性、dedup key 不产生双跑、`TaskTypes` 与迁移 CHECK 的防漂移。
