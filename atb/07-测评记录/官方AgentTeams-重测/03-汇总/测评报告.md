## 四、发现的问题（官方 Agent Teams）

### 4.1 严重：角色认领失衡

**官方是「成员自主认领任务板」模型，没有强制分配。**

| 角色 | 完成率 | 说明 |
|---|---|---|
| 安全工程师 | **100%** | 有人认领 |
| 性能工程师 | **100%** | 有人认领 |
| **SRE（运维）** | **17%** | **5 个全部无人认领** |

**根因：成员倾向选择自己熟悉的领域，SRE 类任务被系统性跳过。**

**对比 NanmiCoder**：

| 项 | 官方 | NanmiCoder |
|---|---|---|
| 分配模型 | **自主认领** | **assignee 绑定** |
| 角色覆盖 | ❌ 会失衡 | ✅ 强制覆盖 |
| 灵活性 | 高 | 低 |

### 4.2 严重：报告不进任务板

**21 个已完成任务，`team_task_list` 返回的 `output` 全部为空。**

成员把报告**发成了消息**，没有写进任务板 `output`。

| 项 | 官方 | NanmiCoder |
|---|---|---|
| 报告存放 | **消息/对话** | **task.output 字段** |
| 可程序化提取 | ❌ | ✅ |
| 汇总成本 | 高（人工） | 低 |

### 4.3 严重：成员名额已满且无清理

```
spawn_teammate → Team member limit 8 reached
```

**8 个 teammate 全部 inactive，但永久占位。** 这次只能用已有的 3 个（名字与任务完全不符）。

### 4.4 中等：subagent 池与团队争抢

```
subagent limit reached (active child limit: 18)
```

**S 组 16 个 subagent + T 组 teammate 共用同一个池（上限 18）。**

**必须分阶段执行。**

### 补充 5：中文可搜靠「分层检索」，不是 trigram 单打独斗

**已核实的硬判据**（`tests/review-search.test.ts:62-83`）：

```
'检索测'（3字） → 走 FTS5 trigram  → total=1
'检索'（2字）   → 走 LIKE 回退      → total=1
'完全不存在的词' → 断言 0 条
```

> **方案若只抄 trigram 而不抄分层回退，中文两字词仍然搜不到。**
> **这是可验收的硬判据，不是主观判断。**

### 补充 6：备份自检是「9 表白名单」，索引表天然是盲区

**已核实**（`scripts/backup.mjs:78-88`）：

```
行数白名单只有 9 张表：
users / plugins / repositories / reviews / comments /
notifications / operation_records / site_settings / configuration_revisions
```

> **新索引表天然不在这 9 张里。**
> **`backup.mjs:110-135` 的校验只有 `integrity_check` + 这 9 张表的行数比对**
> **→ 索引行的损坏/污染不会被备份自检发现。**


## 【补充】增量评审的独有发现

> 来源：m11 SRE 补跑时对既有评审的**增量复核**
> 下面是既有评审（含 NanmiCoder 组的）**都没抓到**的，已逐条核实。

### 补充 1：登记 REQUIRED_TABLES 反而更糟（反直觉）

**既有评审说**：「新表不登记 REQUIRED_TABLES 会导致自检失效」

**增量评审纠正**：

> **登记了更糟**：老二进制（回滚后）启动自检发现缺表 → health fail
> → web 永不 healthy → **nginx depends_on service_healthy** → **入口 502 全站不可用**
> **这是把「代码回滚」从可行变成不可行。**

**核实**：`docker/compose.yaml` 确有 `condition: service_healthy`

### 补充 2：注入串进备份包的威胁链

**既有评审只说了 SQL 注入**，增量评审补：

> `q` 从 `server.mjs:52` 取 path 丢弃 query，注入串**只进 journal 不进访问日志**
> 但 `q` 最终进备份包的 `manifest.json`
> 而 `restore-backup.mjs` 要「**先验后写**」——**一份良备份被污染成不可用于恢复**

**核实**：`restore-backup.mjs:59-67` 确实校验 manifest 与 sha256，不匹配直接 fail

### 补充 3：synchronous=FULL 与健康门禁耦合

> 每请求写 `runtime_heartbeats` 等于每 10s 一次 fsync
> **每请求都写的表 + 健康门禁 + 磁盘余量相互耦合**
> 磁盘剩 200MB 级便同时触发 health fail 与写失败

### 补充 4：不该用 FTS 替换现有接口

> 别用 FTS 替换现有 `GET /api/plugins/search`（已是 LIKE 子串，中文 OK）
> **应新路径 + 保留旧路径作运行时兜底**

## 【补充】n57 安全组：从性能问题升级为安全漏洞

**性能组说**：「await 期间事务串流，别的请求的写会被卷进来」
**SRE 组说**：「WAL 单写者全域排队」

**安全组指出了可被利用的后果**：

> **`rate-limit.ts:229` 的 `limiter.consume()` 写若落在别人挂起的事务里，
> 对方回滚会抹掉这次频控消耗 → 被限流用户重新拿回额度。**

**核实**：
- `db.ts:66` 注释原文：「**进程级单例连接**（Web 与 worker 各自一个进程）」
- `rate-limit.ts:229` 用同一个连接做 `consume()`

**这意味着**：事务边界失效不只是「数据可能错」，而是**攻击者可主动触发**——
先让一个长事务挂起，再给自己的请求刷频控，然后让长事务回滚 → 额度恢复。

### 另外两条安全后果

| 发现 | 依据 |
|---|---|
| **TOCTOU 越权**：断言在 await 前、写在 await 后 → **禁用/降权账号仍完成写入** | `context.ts:27-43` 明写「每次从库读」 |
| **审计与业务分离**：`publish-review.ts:119-165` 三段同事务拆开 → **已隐藏内容被发布** | `0042` 加固正是防这个 |

### 三方评审的差异

| 组 | 视角 | 同一问题的表述 |
|---|---|---|
| **性能** | 事务窗口无上界 | 「40+ 调用点全量改签」 |
| **SRE** | WAL 单写者排队 | 「`busy_timeout` 5000ms 全域阻塞」 |
| **安全** | **可被利用** | 「**频控额度可被回滚抹掉**」 |

> **同一个技术缺陷，三个视角看到三个层次。**
> **安全组看到的是「能怎么用」，性能组看到的是「有多慢」，SRE 看到的是「会堵住谁」。**
