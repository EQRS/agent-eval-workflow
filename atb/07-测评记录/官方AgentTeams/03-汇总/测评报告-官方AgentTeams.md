## 五、发现的问题（官方 Agent Teams 本身）

### 5.1 严重：无成员清理机制

```
spawn_teammate → ToolCallError: Team member limit 8 reached
```

**现场**：会话已有 8 个 teammate **全部 inactive**（早就完成任务），但永久占名额。

| 项 | 结论 |
|---|---|
| 上限 | 8 个 teammate + 1 lead |
| **清理机制** | **无** —— 没有 remove/delete 工具 |
| 影响 | 长会话或多次测评后**名额耗尽** |
| 严重度 | **高（阻塞型）** |

**规避**：复用 inactive teammate（实测可行，但语义混淆——名字/描述与新任务不符）。

### 5.2 中等：复用 teammate 的语义问题

**实测**：`b-e1-a`（描述「E1 并行：统计文件数量」）被派发「N-46 安全评审」后**正常完成**。

| 优点 | 缺点 |
|---|---|
| 能复用，省名额 | **名字与任务不符**，`list_agents` 显示混乱 |
| 上下文保留（可能有利） | 无法区分「这个 teammate 到底在做什么」 |

## 七、结论

### 7.1 官方 Agent Teams 值不值得用

| 维度 | 评价 |
|---|---|
| **能不能用** | ✅ 能用，核心功能正常 |
| **好不好用** | ⚠️ 有阻塞缺陷（成员上限 + 无清理） |
| **比单 agent 强吗** | **⚠️ 视任务而定** |

**这条要如实说**：

> **S 组（1 个 agent）发现了 44 条问题，T 组 3 个 agent 合计 26 条。**
> **S 组在「全面性」上更强；T 组在「深度」上有独特价值。**
>
> **这不是「团队一定更好」的证据，而是「团队和单干各有优势」的证据。**

### 7.2 T 组的不可替代性

**T 组挖出的 4 条独有发现，都是需要「特定专业视角 + 跨事实连接」的**：

| 发现 | 需要的视角 |
|---|---|
| 提权漏洞 | **安全**：从「管理员」这个词反推到 API 校验 |
| 33 小时数据丢失 | **SRE**：把「无 down 迁移」+「每日备份」连起来 |
| 重试热点 | **性能**：从失败率看成本 |
| 攻击窗口 | **安全**：无通知 = 攻击者有时间 |

### 7.3 对出题的建议

| 建议 | 理由 |
|---|---|
| **多选题要同时跑 S 和 T** | 两者互补，缺一不可 |
| **T 组适合「需要专业视角」的题** | L3-L4 深度题 |
| **S 组适合「需要全面覆盖」的题** | 它能逐条扫完 |
