N9（收藏夹条目排序并发更新）性能工程师评审完成：结论「有阻塞项（3 P0 + 3 P1），不建议按现行方案上线」。报告：_work/评审-N9-收藏夹排序并发-性能.md

核心判断：方案用错误的手段解决一个并不存在的问题——plugin_favorites 主键就是 (user_id, plugin_id)（0012_interactions.sql:32-37），一条收藏一行，同一用户拖同一行是交互层的重复提交，不是数据层竞态；真正的性能问题是"逐条更新 + 先读后写"。

P0-1 while(true)+同步驱动 = 让整个 Node 事件循环陪着自旋。better-sqlite3 全同步（db.ts:1-11、tx.ts:37-52），循环里没有 await；web 与 worker 是两个进程写同一库（main.ts:229-230、compose.yaml:44-108），busy_timeout=5000（db.ts:56）会让 run() 同步阻塞最多 5 秒 → 整站 5 秒不响应。无次数上限 → 两标签页互拖即活锁（CPU 100%、成功率 0、无日志）。row 为 undefined（收藏已取消）时 row.version 抛 TypeError → 500。建议删掉循环，单行 UPDATE ... WHERE user_id/plugin_id 一次语句；要幂等就用"条件更新到期望 position"，重试上限 2 次且每次前 await。
P0-2 逐条更新 = 2N 次同步语句。一次拖拽移动 N 条（批量接口已允许 200，interactions:1074-1076），方案没提事务 → 若逐条事务就是 N 次 WAL 提交，而 db.ts:54 是 synchronous=FULL，每条一次 fsync，200 条即几百 ms 到秒级；前端每拖一次发一个请求 → 语句量按 N² 放大且到达顺序不定。建议 pointerup 一次性提交整张顺序表 + 单事务批量写 + 服务端 maxItems。
P0-3 position 无分组语义与唯一性：DEFAULT 0 把存量行全设 0，排序退化为扫描顺序且每次刷新可能不同，还与现有 ORDER BY created_at DESC（interactions:900）冲突；无 UNIQUE(folder_id, position) 也无匹配索引，WHERE user_id+folder_id ORDER BY position 无法走索引（现有两索引都不以 position 结尾，0012:40、0019:29-30）→ 5000 条收藏首屏每次排序 5000 行；并行写入产生重复 position 且无 tie-breaker；存量回填是全表重写 + fsync，方案一字未提。建议稀疏编号 + UNIQUE(folder_id,position) + 索引 (user_id,folder_id,position) + 分批回填 + 默认夹保持 created_at DESC。

P1-4 version 列是纯开销：没有任何读者，只让表结构与写入 SQL 复杂化；幂等可用整批提交（天然幂等）或条件更新实现。
P1-5 索引：现有两个索引都带 created_at，按 position 排序用不上；须用 EXPLAIN QUERY PLAN 验证不出现 "USE TEMP B-TREE FOR ORDER BY"。
P1-6 「预期」三条不可测，且 while(true) 的失败模式是 CPU 100% 无日志。建议给出口径：拖拽 N=50 P95<100ms、同用户 5 并发无 5xx 且未触发 busy_timeout、5000 条首屏 P95<150ms、重试触发上限计数日志。
