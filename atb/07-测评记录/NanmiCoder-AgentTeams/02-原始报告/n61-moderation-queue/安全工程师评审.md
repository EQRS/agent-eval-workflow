# n61-moderation-queue 安全工程师评审

评审对象：atb/tasks/n61-moderation-queue/environment/proposal.md（49 行）
已逐行核实 migrations/0001_baseline.sql、0040_user_roles.sql、src/server/platform/context.ts、
src/server/modules/moderation/service.ts、src/server/workflows/decide-submission.ts、src/server/modules/roles/service.ts。

**总判：方案 4 个技术点里有 3 个直接不可执行或会制造提权面，第 4 点指向一个不存在的页面。**

## 最重要 5 条

### S1【阻塞】proposal:12-14 的 SQL 在 SQLite 上**根本执行不了**
```sql
ALTER TABLE users DROP CONSTRAINT users_role_check;
ALTER TABLE users ADD CONSTRAINT users_role_check CHECK (...);
```
**代码事实**：SQLite **没有** `ALTER TABLE ... DROP CONSTRAINT` / `ADD CONSTRAINT` 语法。
本仓对此已有明确记录——migrations/0007_task_type_plugin_discovery.sql:7-11：
「为什么必须重建表：SQLite **改不了列上的 CHECK 约束**（没有 ALTER TABLE ... ALTER CHECK），
只能'新建 → 拷数据 → 删旧 → 改名'。而被外键引用……必须先把 foreign_keys 关掉；
偏偏 `PRAGMA foreign_keys` **在事务里是空操作**」。
users 表被 **20+ 张表**外键引用（content_entities.author_id、content_drafts.owner_id、
plugin_ownerships.user_id、notifications 等）。
② 后果：迁移第一次执行就报 syntax error，整个部署阻塞；
若有人“想办法”绕（强行重建 users），会牵动全库外键，属**最高风险操作**。
③ 建议：**不要动 users.role**（见 S2）。若真需要新角色，应另开表，而不是改权限底座。

### S2【阻塞】把 moderator 塞进 users.role，会污染**全站唯一的权限底座**
**代码事实**：src/server/modules/roles/service.ts:12-14 写死了这条架构纪律：
「**身份不是权限底座**：users.role（user/admin）仍然决定能否进后台、能否审内容；
user_roles 只是能力标记，**isAdmin() 的行为一个字都不变**」。
而 isAdmin 的实现是 `ctx.role === 'admin'`（platform/context.ts:23-25），
assertCanAdmin 同源（:46-53）。
② 后果：`users.role` 是全站**所有**后台判权的根。一旦它多出第三个取值：
  (a) 所有 `role === 'admin'` 的比较仍然只认 admin，moderator **拿不到任何权限**——
      方案因此**完全达不到目的**；
  (b) 更危险的是若实现者“顺手”把某处改成 `role !== 'user'` 之类，
      moderator 会**静默获得全部后台权限**（含封禁用户、改配置、看审计）。
这是一处“改一处、影响全站”的判权根，方案没有任何讨论。
③ 建议：沿用既有分层——`users.role` 只放 user/admin；审核能力用 **user_roles 或新表**表达，
与 0040:23-38 的 `user_roles(role_type)` 同一模式（但注意 S3）。

### S3【高】`user_roles.role_type` 已存在 'reviewer'，但它**不是**审核员
**代码事实**：0040:26 `role_type CHECK (role_type IN ('reviewer','developer'))`，
其中 `reviewer` 的含义是**「测评员」**（写过评测的人，见 0040:4 注释「测评员 / 开发者」），
**不是**「内容审核员」。
② 后果：若实现者看到 `reviewer` 就复用，会把「写过一篇评测的用户」直接变成审核员——
而 0040:443-453 的资格判定是 `COUNT(*) published reviews > 0`，门槛极低（任何人发一篇就能拿）。
那等于**任何用户都能审批内容并直接触发发布**。这是一个极易踩的语义陷阱。
③ 建议：明确新增独立 role_type（如 `content_moderator`）或独立表；
方案里必须显式写「不要复用 reviewer」并说明两者区别。

### S4【阻塞】「审核员」的实际权力 = `approve` = **直接发布到全网**，方案零讨论
proposal:44-45「审核员通过 /admin/submissions 页面处理被分配的内容」。
该页面背后的接口是 `POST /api/admin/submissions/{id}/decisions`，
其 `decision` 只接受 `approve` / `needs_changes`（route.ts:38-40），
而 `approve` 会**同时入队 review_publish 任务**（route.ts:51-53 注释：
「通过时**同时**入队发布任务……只改状态不入队的话，人工通过之后没有任何东西会去发布——曾真的这样」）。
② 后果：授权 moderator 做审核，等于授权他**决定什么内容公开上线**。
这是内容平台里权力最大的一类操作，方案却只用一句「审核压力分散」带过，
完全没有讨论：谁能成为 moderator、如何撤销、是否需要双人复核、能否发布自己的内容。
③ 建议：至少要写清 (a) moderator 的授予与撤销路径（需管理员审批 + 审计）；
(b) **禁止审核自己提交的内容**（自查自批是最典型的内部滥用）；
(c) 高风险内容是否需要双人复核。

### S5【阻塞】proposal:37-41 的分配逻辑在 `reviewers.length === 0` 时**直接崩溃**
```ts
reviewers[i % reviewers.length].id
```
② 后果：系统中还没有任何 moderator 时（**刚上线时必然如此**），
`i % 0` = `NaN`，`reviewers[NaN]` = `undefined`，随后 `.id` 抛 TypeError。
而这个扫描是 proposal:28 的「每 5 分钟」定时任务——每 5 分钟抛一次，
若外层没有 try/catch（方案没写），会让整轮调度失败；
更糟的是 `pending.forEach` 里抛错会**中断剩余分配**，且此前已 INSERT 的不回滚（无事务）。
③ 建议：空数组先返回；整段包进事务；用 `reviewers.length === 0` 早退。

## 完整清单（其余）

### S6【阻塞】方案没有说明 moderator 如何**通过鉴权**，而现有鉴权全部硬绑 admin
route.ts:28 `assertCanAdmin(ctx)`；**更关键的是 service 层还有一道**：
moderation/service.ts:466 `if (!isAdmin(ctx)) throw err.forbidden('只有管理员可以做出审核决定。')`。
② 后果：即便把 moderator 写进 users.role，这两处仍会拒绝——方案对此**完全没提**，
实现者会以为改了 CHECK 就够了，上线后发现“审核员点不动按钮”且原因隐蔽。
③ 建议：若真要放行，必须**同时**改这两处，并引入“是否被分配”这一层校验（见 S7），
不能简单放宽 isAdmin。

### S7【高】分配表没有唯一约束，也没有“只有被分配者才能处理”的校验
proposal:19-24 的 `review_assignments` 没有 `UNIQUE(submission_id)`。
② 后果：(a) 每 5 分钟扫一次 `LIMIT 50`，**同一提交会被反复分配给不同人**
（因为查询不排除已分配的），表无限增长且多人同时抢审同一条；
(b) 方案没说“处理时必须校验该 submission 分配给了我”——
若不校验，任何 moderator 都能处理**所有**内容，分配表形同虚设。
③ 建议：`UNIQUE(submission_id)`（一条提交只需要一个审核人）+ 处理时校验 assignment 归属；
扫描 SQL 要 `LEFT JOIN review_assignments ... WHERE a.id IS NULL` 排除已分配。

### S8【高】分配逻辑用 `SELECT *`，会把审核人**无权看**的内容也扫出来
proposal:32 `SELECT * FROM content_submissions WHERE processing_state = 'manual_review' LIMIT 50`。
② 后果：`content_submissions` 含 `request_digest`、`publication_context` 等内部字段；
虽然分配本身不需要这些字段，但 `SELECT *` 会把它们带进内存与潜在日志。
且 `LIMIT 50` 没有 `ORDER BY`，SQLite 返回顺序不保证——轮询分配会**长期偏向**同一批行（队头饥饿）。
③ 建议：显式列名 + `ORDER BY submitted_at ASC`（先进先出）+ 排除已分配。

### S9【中】轮询分配可被“刷单”操纵：提交者能预测自己会被分给谁
proposal:37-41 是确定性的 `i % reviewers.length` 轮询。
② 后果：若攻击者知道 moderator 列表与队列位置，可安排在自己提交时命中最松的审核人。
对内容平台而言，这是**可被利用的审核规避**。
③ 建议：随机分配（加密随机）或按负载分配；并在文档里说明分配不可被提交方预测。

### S10【中】方案与既有 forum 的 moderator 语义撞名
packages/common/forum.ts:29-34 已有 `BOARD_MEMBER_ROLES = ['owner','moderator']`（= 协管），
且 roles/service.ts:17-18 明确「区长/协管**不进 user_roles**，同一个人可能在 A 区是区长、B 区是普通用户」。
② 后果：新角色若也叫 moderator，会与既有「分区协管」完全混淆，
排查权限问题时极易看错表（forum_board_moderators vs users.role）。
③ 建议：改名（如 `content_moderator` / `trusted_reviewer`），并在文档里与协管明确区分。

### S11【低】迁移号与保留审计缺失
proposal:11 用 0043 —— 当前最高是 0042_audit_immutable.sql，**0043 号可用**（无冲突）。
但方案没有任何审计要求：谁把谁设成 moderator、谁处理了哪条内容，都应进 operation_records。
建议：授予/撤销 moderator、每次审核决定都要写审计（后者现有 decideByAdmin 已在写，
见 moderation/service.ts:490-504 的 appendRecordWithin）。

## 一句结论
**这方案会在第一步就崩**：SQLite 不支持 `DROP CONSTRAINT`（S1），且 users.role 是全站判权根，
roles/service.ts:12-14 已明令「isAdmin() 的行为一个字都不变」（S2）。
更关键的是——方案从头到尾没意识到「审核员 = 能决定内容公开上线」这一真实权力（S4），
也没发现现有鉴权在 service 层还有第二道 isAdmin 硬校验（S6）。
另外 proposal:37-41 在无 moderator 时必然 TypeError（S5），`reviewer` 这个 role_type 极易被误复用（S3）。
建议：**不改 users.role**，用独立表 + 独立鉴权 + 分配归属校验重做，并把「审核=发布权」写进设计。
