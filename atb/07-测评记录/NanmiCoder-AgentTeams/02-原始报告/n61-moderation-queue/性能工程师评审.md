结论：§3 的「每 5 分钟全表扫 + 无去重插入」在现有索引下持续产生重复行，重复行会让「待审积压」这个指标本身失真——越积压、扫描越重、重复越多，正反馈。方案没有一条数量级界定。

摘要前 5 条：
1.【严重】扫描查询无 ORDER BY、无排除已分配 → 每 5 分钟重复插同一批。proposal.md:31-41；0001_baseline.sql:338 只有 idx_submissions_state(processing_state, submitted_at, id)，无 ORDER BY 时按该索引即按 submitted_at 升序 = 最老的 50 条，也正是最容易被重复选中的 50 条。12 次/小时 × 24 = 一个 50 条待审的队列一天写 14,400 行。
2.【严重】与现有无 LIMIT 的后台查询叠加：src/app/api/admin/submissions/route.ts:33-43 的 WHERE processing_state=? ORDER BY submitted_at 无 LIMIT（:65 的 total: rows.length 说明返回全量）；better-sqlite3 同步驱动（db.ts:6-8）会挤占 worker 主循环。
3.【严重】无事务、无语句复用：proposal.md:37-41 循环内每次 db.prepare；db.ts:52-56 是 WAL + synchronous=FULL → 50 条待审 = 50 次 fsync + 半分配状态（违背 tx.ts:1-9）。
4.【高】审核员为空/被禁用未处理：proposal.md:40 的 i % reviewers.length 在空集时 NaN → reviewers[NaN] TypeError，整个 tick 崩溃；禁用审核员名下任务永久滞留无回收路径。
5.【高】方案让审核员走 /admin/submissions，但该接口无分页无 LIMIT（route.ts:33-43），且 context.ts:13 的 role 是 'user'|'admin'|null 封闭类型、:24 isAdmin 只认 admin、:48-52 assertCanAdmin 断言 admin —— 为实现者打通入口，很可能加短路分支，把无 LIMIT 查询的成本乘以审核员人数。

完整清单 P-01…P-08，另含：分配表无索引（读取一定按 reviewer_id 过滤，对照 0001:339、0040:64-65 的范式）；无保留期（表只增不减，按 P-01 的倍数增长）；缺积压深度与等待时长指标，收益无法验收。

最小改造 6 条：加 UNIQUE(submission_id) + idx_assignments_reviewer；分配查询改 LEFT JOIN ... IS NULL + ORDER BY；预编译 + 单事务 + ON CONFLICT DO NOTHING；事件驱动为主、5 分钟扫描只做兜底；后台按「分配给我的」过滤并分页；补积压/等待时长指标。

前提核实：content_submissions.processing_state 含 manual_review（0001:315-316）、idx_submissions_state（:338）、后台无 LIMIT 查询都真实存在；但 users.role 在代码侧是封闭类型，方案只给了 SQL 侧改动（ALTER ... DROP CONSTRAINT 在 SQLite 不可行，留意交给迁移视角）。
