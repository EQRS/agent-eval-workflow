结论：这个改造会把「事务」从一个安全边界变成摆设。await fn(tx) 让出事件循环后，同一连接上会插入其它请求的语句，全部落在未提交事务里——原子性、审计一致性、幂等原子性同时失效。现状 tx.ts:37-52 的同步签名是刻意的安全设计。

摘要前 5 条：
1.【严重】await 让出事件循环 → 事务被其它请求复用。tx.ts:37-52（注释明写回调必须同步）、db.ts:5-8（单连接同步驱动）。具体反例：A 在 await tx.insert 挂起，B 的 withTransaction 被 better-sqlite3 当作嵌套转成 SAVEPOINT，B 返回成功时数据只在外层未提交事务里；A 随后回滚 → B 的写静默消失而调用方已拿到成功响应。
2.【严重】手写 BEGIN/COMMIT 与 db.transaction() 的 SAVEPOINT 嵌套冲突。全仓 33 个文件 161 处 withTransaction（withRead 另 23 文件 72 处）；嵌套会抛 cannot start a transaction within a transaction；catch 里的 ROLLBACK 会把外层事务一起回滚 → 静默数据丢失。
3.【高】审计与业务不再强绑定。operations/service.ts:161-174 的存在理由就是「与业务同事务」；0042:1-15 立规防的正是「审计与事实可分离」；migrate.ts:97-118 还专门为自带事务的迁移留了 dsh:migration-transaction=off 标记并注明「中途失败会留下半成品」。
4.【高】幂等键的「先查后插」在异步化后失去原子性（operations/service.ts:97-134 + 0001:426 的 UNIQUE(action_type, operation_key)）→ 并发重放会各写一条审计或撞唯一索引变 500。§2「所有调用点改成 await」是覆盖 33 个文件的安全敏感重构，方案没给回滚与验证手段。
5.【中】丢掉「事务已结束」保护：现状 tx.ts:21-35 的 markFinished + getter 会在事务结束后抛错；改后是普通对象，SQLite 会逐条自动提交——本该被回滚的写变成已生效。

完整清单 S-01…S-07，另含：COMMIT 失败未回滚 + ROLLBACK 失败会覆盖原始错误（与 rate-limit.ts:276-280 的 refundQuietly 同一教训），可能导致事务悬空直到进程回收；方案文档没记录「为什么现在是同步的」，后来人会重复提议。

建议：否决 async 化；若痛点是写法啰嗦，只做类型层的糖（保持同步回调）；真需要跨网络原子性就走两阶段/后台任务（仓库已有 background_tasks 与租约）。保留 finished 标记与 recordOperationInTx 同事务。

前提核实：withTransaction（tx.ts:42）、Tx（:15-19）、markFinished（:21-35）真实存在；方案「所有调用点」这次改造的范围是 33 文件 161 处，方案没交代量级。
