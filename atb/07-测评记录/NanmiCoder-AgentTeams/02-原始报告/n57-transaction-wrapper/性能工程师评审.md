N57（把事务封装成 async 函数）性能工程师评审完成：结论「性能倒退（3 P0 + 2 P1），不建议实施」。报告：_work/评审-N57-事务异步封装-性能.md

核心判断：better-sqlite3 的事务是同步栈内的东西，db.transaction(fn) 只有 fn 一路同步执行到返回才有意义。方案把 fn 改成 async，等于在事务打开的状态下把事件循环还给别人。

P0-1 await fn(tx) 让写锁跨越事件循环：await 让出后，同进程排队的写请求要么 BEGIN 撞写锁、要么读后写变 SQLITE_BUSY_SNAPSHOT；每个都在 busy_timeout=5000（db.ts:56）上同步阻塞——better-sqlite3 的等待会阻塞整个 Node 线程，一个卡 5 秒的写请求让 web 进程对所有用户无响应（db.ts:7-8 注释就在讲这个）。更进一步：web 与 worker 双进程写同一库（compose.yaml:44-108、worker/main.ts:229-230），web 事务被拉长到秒级后，worker 的短事务写回（tasks/service.ts:278-395）会撞 SQLITE_BUSY，任务吞吐塌方，且失败计入 attempt_count（service.ts:328-331）——性能问题被记成任务失败。方案"支持异步操作"正好违反 tx.ts:4-8"外部拉取/解析/文件复制一律在事务之外"的铁律。
P0-2 手写 BEGIN/COMMIT 绕开 db.transaction()：失去嵌套 SAVEPOINT 处理（嵌套直接 cannot start a transaction 抛错→500，errors-http.ts:62-72）；synchronous=FULL（db.ts:54）下每次 COMMIT 都要 fsync，异常路径若 ROLLBACK 本身失败会留下未提交事务，连接带打开事务继续服务——后续每次写都排队，表现为"突然全站变慢，重启恢复"，且无日志无计数。热点行（operation_records 的 UNIQUE(action_type, operation_key) 0001:426、rate-limit 的 <action>:<userId> rate-limit.ts:226）持锁时间随事务时长线性上升。
P0-3 改造面=全站写路径：grep 实测 33 个文件、161 处 withTransaction；其中"对同步函数加 await"的写法已有 13 处（forum/boards.ts:282,311,349,384,400,426、forum/posts.ts:631,665,771,867、forum/applications.ts:244、forum/drafts.ts:235、search/index.ts:142,195）。这 13 处当前无害（多一个微任务），但说明团队已用 async 直觉写同步 API，方案把它正当化后，下一步就会有人在回调里 await fetch，事务被拉长。用一次语法糖改造换 161 处写路径的回归面，性价比为负。

P1-4 无慢事务/长事务观测：tx.ts:42-52 无任何计时，server.mjs:62-82 只到请求级且 /api/health 被静音（server.mjs:35-37）；busy_timeout 触发的等待不进任何指标。建议给 withTransaction 加慢事务日志（>50ms 打 warn 带调用点标签），验收口径 P99<20ms、>50ms 事务数/小时=0——这才是这次改造真正该做的事。
P1-5 丢失 Tx 生命周期护栏：tx.ts:21-35 的 makeTx 用 getter 在事务结束后抛错，是"事务外继续写"的唯一护栏；async 版本把 tx 交给跨 tick 的回调，闭包逃逸后写入会落到自动提交模式，表现为部分成功部分失败且日志几乎没有。建议保留护栏并让 Tx 不可逃逸。

处置建议：不要改 withTransaction；若需可读性，改成 runTransaction(name, fn) 加事务名用于慢事务日志，不动执行模型。
