性能工程师评审（n46-ownership-dispute proposal.md，30 行）：**方案不能按现状实施**。6 条（3×P0 / 2×P1 / 1×P2），按 proposals 的表形状建库实跑。

**总评**：同一张表上踩了三个互相放大的坑 —— 零索引 + 零配额 + 零分页。既有 plugin_ownerships（migrations/0040_user_roles.sql:82-120）为同样的队列场景建了 3 个索引（user/plugin/(status,created_at,id)），说明这道题在仓库里已有既定答案，方案没有沿用。

**P0-1 表上没有任何索引**：实测三种查询全是 SCAN —— status='pending' ORDER BY created_at 为 SCAN + TEMP B-TREE（2000 行 3.89ms）；WHERE plugin_id / claimant_id 均全表扫描。按 plugin_id 查是热路径（认领判定 ownership.ts:247、:330 同形状）。→ 补 (plugin_id,status)、(status,created_at,id)、(claimant_id,created_at DESC) 三条索引，命名与列序抄 0040:113-115。

**P0-2 §2「任何用户可对任意插件提争议」= 零成本刷屏**：实测一个账号写 5000 条只要 **23.6ms**；evidence 是 TEXT 无长度上限；plugin_id 无唯一约束，同一插件可被无限条争议淹没；管理员每条都要判一次归属（实测 133ms）。仓库对同类场景有部分唯一索引（0012_interactions.sql:59-62）与 UNIQUE(plugin_id,user_id)（0040:111），方案两者都没有。→ 加 uq_open(plugin_id,claimant_id) WHERE status='pending'、每用户/每插件未处理上限、evidence ≤ 2000 CHECK、走既有频控。

**P0-3 §3 管理端无分页**：既有 listQueue 也是无 LIMIT 全取（ownership.ts:296-311），但争议量远大于认领量；2000 条列表 3.89ms + 逐条判归属 133ms，5000 条时列表 7.8ms + 133ms，随插件数线性劣化；status 无 CHECK → 脏值永远看不到也清不掉。→ parsePaging + LIMIT/OFFSET + ORDER BY created_at, id；列表一次 JOIN：实测 JOIN **1.69ms** vs 逐行查用户 **58ms**（34 倍）。

**P1-4 缺 CHECK 与审计列**：status 无 CHECK、无 reviewer_id/reviewed_at，运维无法回答「谁判的、为什么」；created_at 无 >= 0 校验，负数会把脏数据顶到队首；外键缺 ON UPDATE/DELETE RESTRICT。→ 照抄 0040:87-110（注意蕴含式而非等号）。

**P1-5 写入未走事务与幂等**：§3「直接改归属人」会撞部分唯一索引 uq_plugin_ownerships_verified（0040:119-120）—— 这正是 ownership.ts:239-250 记录的「撞唯一索引 → 500」事故；管理动作也没有 operation_key 去重。→ withTransaction + 复用 taken 检查 + 写 operation_records。

**P2-6 预期不可验收**：无数据规模/响应时间/上限口径。→ 改为「队列 P95 < 100ms（未处理 ≤ 500 条）；单用户 ≤ 5；单插件 ≤ 3；evidence ≤ 2000」。
