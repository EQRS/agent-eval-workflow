N46（插件归属争议申诉流程）安全工程师评审完成：结论「有阻塞项（4 P0 + 2 P1），不建议按现行方案上线」。报告：_work/评审-N46-归属争议申诉-安全.md（review-perf.md 是性能视角，本报告不重复）。

核心判断：这套流程真正被利用的不是"提交争议"，而是"管理员直接改归属"——方案 §3 给了一条无审计、无证据门槛、可被社工驱动的越权改人路径；而仓库已有完整的认领-审核链路（roles/ownership.ts），方案既没复用也没说明为什么不够用。

P0-1 §3「管理员直接改归属人」绕过既有状态机且无审计：plugin_ownerships.status 是 CHECK 闭集（0040_user_roles.sql:86-88），并有部分唯一索引 uq_plugin_ownerships_verified（0040:119-120）；"直接改"必须先把旧行改掉再置 verified，否则撞索引。仓库里唯一做对的是 reviewClaim（ownership.ts:313-367：先查 taken 再置 verified，并在事务内投递通知）。审计唯一载体是 operation_records（0001:411-431，0042 已加防删改触发器），正确姿势是 recordOperationInTx（operations/service.ts:161-174）。更根本：grep recordOperation src/server/modules/roles 命中 0 —— claimPlugin/reviewClaim/revokeRole 至今都不写审计，方案不补这一点，"争议有据可查"就是空话。建议：禁止裸改，实现为受控状态转移（旧 verified→rejected+reviewer_id/reviewed_at+理由，新行→verified），同事务，并写 actionType='ownership.transfer' 审计；顺带补既有 claim/review 的审计。

P0-2 §2「任何用户可对任意插件提争议」= 零门槛骚扰面 + 社工入口：项目有现成频控（rate-limit.ts:196-251，动作闭集 :46-55，规则表 :68-134），而连现有的 claim 接口都没挂频控（app/api/me/plugins/[pluginId]/claim/route.ts:14-33 只有 assertCanWrite）；pending/rejected 不受唯一索引限制（0040:117-118），若无 UNIQUE(plugin_id, claimant_id)，一人可对全站每个插件各提一条淹没队列；evidence TEXT 自由文本可指向站外钓鱼页。建议：新增 RateLimitAction 'ownership_dispute'（3 次/天，参照 :127-133）、UNIQUE(plugin_id,claimant_id)、证据结构化且仅 https+禁内网/站内、文件走既有 file-store。

P0-3 表缺最小安全约束：status 无 CHECK（项目同类列一律闭集）；plugin_id 外键无 ON DELETE 策略（plugin_ownerships 是 CASCADE，0040:84）；缺 reviewer_id/reviewed_at/resolution_note（0040:90-91,96-110 有精细注释说明为什么要有）；缺"被争议的现归属人/ownership_id"；缺 status/plugin 索引（0040:113-115 可作模板）。

P0-4 证据无可信锚点：仓库有 github_match 与 claimed 两道判据（ownership.ts:109-127），方案没说与它们的关系——任何注册用户写段文字+传个链接就能让管理员推翻已核验归属（授权被社工绕过）。建议争议方须完成 GitHub 侧锚点验证（一次性验证串/协作者校验），并明确不得以争议替代 github_match。

P1-5 知识产权合规只有"申诉"：缺通知—反通知(声明)—处置—公示四环节（《电子商务法》41-43），被指认方无申辩机会、处置不公示。建议加 frozen 态与反通知期限、期间归属不变。
P1-6 改归属等价于开发者身份资格转移（countVerifiedForUser ownership.ts:369-376 是身份门槛判据），但方案当普通数据修改：无原归属人通知、无连带影响考虑、无 revoke 语义（参照 roles/service.ts:738-759 的撤销口径）。
