# m13-data-export 安全工程师评审

评审对象：atb/tasks/m13-data-export/environment/proposal.md（65 行）
已对仓库逐行核实（migrations/、src/server/、src/app/media/、docker/）。数据导出是**数据外泄面**的典型高危功能。

## 最重要 5 条

### S1【阻塞】产物落在磁盘上由谁读？—— proposal:55 的路径同时踩了目录与鉴权两个坑
proposal:55 `GET /api/me/export/:taskId/download → 文件`，产物写 `/data/exports/<userId>/<taskId>.json.gz`。
**代码事实 (a) 路径错**：本仓数据目录是 `/app/.data`（docker/compose.yaml:41/65/92 挂载 `:/app/.data`），
不存在 `/data`。写下 `/data/...` 在容器内要么写不进去（只读/不存在），要么写到容器层 → **容器重启即丢**，
而 proposal:57 承诺 TTL 7 天。
**代码事实 (b) 鉴权缺**：下载只写了路由，没有任何鉴权描述。
对照本仓既有媒体实现 src/app/media/[attachmentId]/[variantKey]/route.ts:30-37：
先 `currentContext()` 取会话，再 `media.resolveReadable(...)` 判权，**未授权一律 404**
（:35 注释写明“不区分不存在与无权限，避免泄露私有内容的存在性”）。
② 后果：`<userId>` 与 `<taskId>` 都在 URL 里，若下载路由不校验 taskId 归属，
**任何人拿到别人的 taskId 即可下载其全量个人数据**（IDOR）。这是本方案最严重的风险。
③ 建议：下载必须 (1) 校验 `task.owner === ctx.userId`（不只是登录）；(2) 不存在的 taskId 与
无权的一律 404，不区分；(3) 产物目录用 `/app/.data/exports/`，且**不外露给 nginx 直读**——
docker/nginx/snippets/site-locations.conf:30-31 已有明确纪律“绝不能改成 alias/root 直接读盘……
nginx 直读磁盘等于把私有图全公开”，导出文件同理，必须走应用反代。

### S2【阻塞】proposal:20 `assertCanWrite` 在导出上是**错误的权限判据**
proposal:20 注释写“先认人，挡匿名与禁用账户”。
**代码事实**：assertCanWrite 的语义是**写入**前置校验（src/server/platform/context.ts:27-43），
导出是**读**操作。用写权限挡读，语义错位。
② 后果：(a) 只读账户/将来可能出现的只读角色会被误挡；
(b) 更关键的是它给人“已经鉴权了”的错觉，实际上**它不校验资源归属**——
真正的导出授权必须是 `target.userId === ctx.userId`，而方案通篇没有这一条。
③ 建议：保留 assertCanWrite 用于“账户可用性”，但必须显式加一行归属判定，并在文档写明
“登录 ≠ 可导出他人数据”。

### S3【阻塞·照抄即崩】proposal:21 的 enforceRateLimit 调用形式与签名不符，且动作名不在枚举内
proposal:21 `await enforceRateLimit({ action: 'me_export', ctx });`
**代码事实**：src/server/platform/rate-limit.ts:196-208 的真实签名是
`enforceRateLimit(db, action, userId, points = 1, override?)` —— 位置参数，不是对象；
且 `RateLimitAction` 枚举（:46-55）里**没有 `me_export`**，只有 9 个动作。
② 后果：照抄会 (a) TS 编译不过；(b) 就算强转，:215 `RATE_LIMIT_RULES[action]` 取到 undefined，
随后 :225-229 用 undefined 构造 limiter → 运行期崩溃。
更麻烦的是若有人“简化”成直接注释掉，导出就**完全没有频控**——而它是昂贵的全表扫描。
③ 建议：在 rate-limit.ts:46-55 增加 `'me_export'`，并在 :68 的 RATE_LIMIT_RULES 里给规格
（参考 :127-133 role_application 的“按天”口径：导出建议每天 1-2 次）；
调用写成 `enforceRateLimit(db, 'me_export', ctx.userId, 1, await rateLimitOverrideFor(db, RATE_LIMIT_RULES.me_export))`，
与 src/app/api/reports/route.ts:51 等既有调用保持一致。

### S4【高】proposal:26-32 的 reviews 导出**取不到正文，且列名不存在**
proposal:29 `columns: ['id', 'plugin_id', 'source_kind', 'created_at']`。
**代码事实**：migrations/0001_baseline.sql:149-158 的 reviews 表只有 5 列 ——
`id / plugin_id / source_kind / published_revision_id / latest_submitted_revision_id`，
**没有 `created_at`**；正文在 review_revisions.body_markdown（:164-178），标题 title（:169）。
② 后果：SQL 直接 `no such column: created_at`；即使去掉该列，导出出来的评测**只有 id 与 plugin_id**，
对“数据可携带权”而言等于交了一份空表——用户拿不到自己写的任何文字。
③ 建议：导出必须 JOIN review_revisions（按 published_revision_id 取公开修订），
导出 title / body_markdown / 各 revision 的时间；时间列用 review_revisions.submitted_at（:174）。

### S5【高】proposal:46-51 在导出里套“公开可见性”过滤，**语义反了**
proposal:50 `if (!resolveVisibilityInTx(db, row.id).publiclyVisible) continue;`
**代码事实**：resolveVisibilityInTx（src/server/modules/content/index.ts:367）判的是
“这篇内容**对公众**是否可见”。它的既有用途全是**对外展示**：
reviews 页面（app/reviews/[reviewId]/page.tsx:68）、插件页（app/plugins/[pluginId]/page.tsx:72）、
搜索（modules/search/index.ts:256）。
② 后果：用户自己**已撤回/被隐藏/未发布**的草稿**全被跳过** ——
而“可携带权”要的是**本人的数据**，恰恰包括他自己的草稿与被撤回内容。
这条过滤让导出既不合规、又对用户无价值；同时它也会把用户自己的待审内容当成“不该给”，是语义倒置。
③ 建议：导出**不应**用公开可见性过滤。正确口径是“只要 author_id = 本人就导出”，
再对**涉及他人的字段**（如他人评论、他人附件）单独判权。可见性函数在这里用错了地方。

## 完整清单（其余）

### S6【高】白名单只覆盖 3 张表，漏掉了绝大多数个人数据
proposal:26-43 只有 reviews / forum_posts / plugin_favorites。
**代码事实**：本人数据实际分散在 content_entities(author_id)、comments、review_helpful_votes、
favorite_folders、pack_favorites / post_favorites（0039）、notifications(recipient_id)、
reports(reporter_id)、pack_reviews、user_preferences（0030）、role_applications（0040）、
plugin_ownerships（0040）、attachments(uploaded_by) + attachment_blobs（**磁盘字节**，0003:89-100）、
user_sessions、external_identities（0001:35-48）等 15+ 张表。
② 后果：proposal:63「用户可下载自己的全部数据」**不成立**；对外宣称合规会有法律风险。
③ 建议：先写一份“用户数据清单”（表 + 字节位置 + 保留期限），导出按清单生成；
注意 **user_sessions.token_digest（0001:53）与 external_identities 绝不能进导出**——
前者是会话凭据派生值，后者含 provider_user_id，属“导出即泄密”的字段。
这正是白名单（而非黑名单）的价值，方案选白名单**方向对**，只是清单不完整。

### S7【中】异步任务的 task_type 未纳入白名单，需要动重建级迁移
proposal:15「走后台任务异步生成」。若新建 task_type（如 `me_export`），
**代码事实**：要改 migrations/0007:26 的 CHECK **和** src/packages/common/field-rules.ts:88-95 的 TaskTypes；
SQLite 改不了列 CHECK，必须整表重建，且 background_tasks 被外键引用，
需 `PRAGMA foreign_keys=OFF` —— 该 PRAGMA 在事务里是空操作，只能 `dsh:migration-transaction=off` 自管事务
（0007:7-14 有完整记录，并注明“中途失败会留半成品，没有自动回滚”）。
② 后果：方案未提及这条代价，容易被低估成“改个字符串”。
③ 建议：明确写成独立迁移并照抄 0007；或复用既有类型 + payload 区分以避开重建。

### S8【中】产物文件名与权限——同目录下其他用户的导出文件
proposal:55 `/data/exports/<userId>/<taskId>.json.gz`。
② 后果：若目录权限放宽（如 0777）或进程以 root 跑，任一次路径穿越/日志泄漏都会放大；
且同机上其它进程可读他人全量数据。另 taskId 若可预测（如自增/时间戳），
配合 S1 的缺失鉴权会直接变成枚举下载。
③ 建议：目录 0700、文件 0600；taskId 用不可预测随机值（本仓 platform/id.ts 已有 newId/newOpaqueToken）；
下载时校验归属（见 S1）。

### S9【中】TTL 7 天的“定时清理”没有任何机制说明，且与备份共用一个数据目录
proposal:57「TTL 7 天，定时清理」。
**代码事实**：本仓定时排程写在 worker 自身（src/worker/scheduled.ts:1-18），靠每日 dedup key 驱动；
数据目录与**备份**共用 `${DSH_REVIEW_DATA_DIR}:/app/.data`（compose.yaml:41）。
② 后果：(a) 没有清理任务则导出文件**永久留存**，是持续的数据暴露面；
(b) 导出文件若被 `scripts/backup.mjs` 一并打包，会进入备份介质，**扩大泄露半径**，
并且与“可携带权”要求的“用后即删”相冲突。
③ 建议：明确把 exports 目录**排除出备份**；清理挂到既有每日调度里（参照 scheduled.ts 的写法），
并记录每次导出/下载到 operation_records（审计，且便于事后追溯泄露）。

### S10【中】生成过程未提“导出期间数据一致性”与“导出本身是否算一次处理”的审计
proposal 全篇没有审计要求。
**代码事实**：本仓对敏感操作有统一审计载体 operation_records，且 0042_audit_immutable.sql 已加固
（不可删、不可改），说明团队把“可追溯”当硬要求。
② 后果：批量导出个人数据属于**最该留痕**的操作之一，没有审计则一旦泄露无法定位“谁导了谁的数据”。
③ 建议：导出任务创建与下载各记一条 operation_records（actorKind='user'，actorUserId=本人，
targetSnapshot 记范围与条数），下载另记 IP；参考 modules/operations/service.ts:21-34 的入参。

### S11【低】schema_version 有，但缺内容边界声明
proposal:60「JSON，带 schema_version 与导出时间戳」—— 方向对。
建议补充：导出里**必须不含** token_digest / 密码派生值 / 他人私有内容 / 内部管理字段
（如 operation_records 内部列、report_handling_records 的管理员理由），并在文档逐项列出。

## 一句结论
方案骨架（异步 + 白名单列 + 版本化 JSON）方向正确，但**下载鉴权缺失**（S1，IDOR）、
**权限判据用错**（S2）、**限流调用写错且动作未定义**（S3）、**reviews 导出取不到正文**（S4）、
**可见性过滤语义倒置**（S5）五处必须改，否则要么不合规、要么直接构成数据泄露。
本仓 src/app/media/ 已经给出“鉴权后再出字节、未授权一律 404”的正确样板，建议照抄。
