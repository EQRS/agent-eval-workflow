结论：不支持按现方案拆。关键是 proposal:12「两个应用连同一个 SQLite 文件」——加上现有 worker 就是三个写者共享一把写锁。

7 条性能面意见（均带 文件:行号）：
1) 第三个写者（proposal:11-12）：db.ts:52-55 是 WAL + synchronous=FULL，每个写事务一次 fsync，写写之间全局串行；现有 web+worker 已是两个写者（compose.yaml:44-77,78-108）。后果是**尾延迟**，且后台的批量操作正是最长写事务（backup.mjs:63-65 的 db.backup() 也是长写）。
2) busy_timeout=5000 是同步阻塞（db.ts:56 + db.ts:6-8 的注释）：锁被别的进程持有时 web 进程整体卡 5s，而 web.Dockerfile:76-77 的 HEALTHCHECK timeout 恰是 5s → 触发重启自激；SQLITE_BUSY 会被 errors-http.ts:120-126 变成 500（先例 ownership.ts:239-250）。建议降到 1-2s + 映射 503，并给 admin 独立的连接参数。
3) CAS 跨应用：admin.ts:423-432/554 的 version CAS 能把覆盖变成显式 409，但 service.ts:107-113 的 blind 自增是跨进程安全写法，而 service.ts:351-357 的 updateProfile 完全不碰版本号——方案须写死「读后写一律禁止」。
4) 「不影响主站」不成立（proposal:17-19）：共享磁盘 + health.ts:88-97 的 200MB disk.free 阈值会把 admin 的额外文件直接变成主站 503；拆分后 /api/health 有两份互不知情的结论。
5) 限流：计数在库表里共享（rate-limit.ts:42-43,226）额度不翻倍，但每次 consume 都是一次写（db.ts 写锁再叠加），且 rate-limit.ts:46-55 的动作枚举没有 admin 类。
6) 部署面：web.Dockerfile:3-8 的注释已算过「多角色共用镜像」的取舍账；页缓存在进程间不共享 → 有效缓存不变、命中率下降；nginx 新增 server 块若漏 include proxy-common.conf 会丢安全头（proxy-common.conf:4-11）。
7) 预期不可测（proposal:17-19）→ 给 5 条判据（主站 p95 抬升 <10%、SQLITE_BUSY=0、批量操作期间主站不 503、并发改 users 一成功一 409、fsync 基线）。
替代方案：db.ts:22-23 已支持 readonly 连接 + 分进程连接参数 + 写事务预算，无需新开进程。
