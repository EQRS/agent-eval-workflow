注：实际文件名是 `atb/tasks/n71-admin-split/environment/proposal.md`（任务书写成 `71-`，无 n 前缀）。

**总评**：三行技术方案每行单独就是一个安全缺陷，且互相叠加 —— §2 把单一写者拆成两个；§3 在 users 表上叠加两套鉴权；§1 拆域名后会话 Cookie / CSRF / 可信 IP 边界全部要重算，方案一字未写。仓库现有的三条硬约束（角色每次请求从库读、可见性/权限只有一个真相、assertCanAdmin 唯一入口）会被全部打散。

**P0-1「后台自己实现登录」= 第二套鉴权**：现有 assertCanAdmin（context.ts:45-53）+ 角色每次从库读（identity/service.ts:262-267，注释原话「撤销管理员即刻失效」）。后台自建登录若把角色写进 token，**撤销管理员在后台不生效直到 token 过期** —— 这是一次权限提升窗口。且要重做会话三重校验（identity/service.ts:256-260）、__Host- Cookie 策略、OAuth 状态绑定；全仓管理员判定点 **135 处**都要重审。→ 不自建登录，复用 currentContext/assertCanAdmin。

**P0-2 跨子域共享会话 = 放弃 __Host- 保护**：现有 __Host-dsh_session（session-cookie.ts:25-26）强制 Secure+Path=/+无 Domain，是防子域投毒的硬机制。要跨 admin.example.com 就必须改成 Domain=.example.com，任何子域（含 XSS 页面/被 CNAME 的第三方）都能种同名 Cookie 覆盖会话；且 readSessionToken 还会同时尝试两个名字（:85-90），会变成跨域 Cookie 混淆入口。→ 会话不跨子域共享。

**P0-3 两应用共写一个 SQLite 文件**：写锁是库级。实测后台持 600ms 长事务时，主站 INSERT **190ms 后抛 SQLITE_BUSY: database is locked**（主站侧就是 500）。更危险的是连接参数漂移：后台若未设 WAL，实测会把库**切回 journal_mode=delete**，主站 -wal/-shm 瞬间失效。→ 不要让两个应用共写；要么保持同一应用内的路由分区，要么后台走内部 API，要么换掉 SQLite。

**P1-4 CSRF/CORS/可信 IP 边界失效**：SameSite=Lax + 跨域后必须自建 CSRF 防线；新增反代入口若漏配覆盖式 X-Real-IP 或误开 TRUST_PROXY，client_ip 即可伪造（proxy-common.conf:14-23、client-ip.mjs:54-67）。

**P1-5「不影响主站」与共库矛盾**：迁移是单维护进程（compose.yaml:27-42），后台再跑迁移就是两个迁移者且 migrate.ts:64-128 无跨进程互斥；库结构回滚不了（HANDOFF「迁移是向前的」）。
**P2-6 审计链路拆断**：管理动作经 operation_records 统一落（catalog/service.ts:13-17、operations/service.ts:117），后台自带写入口容易漏审计或 operation_key 规则不一致。
**P2-7 方案粒度不足**：19 行里没有信任边界、认证方式、会话载体、密钥托管、审计、回滚降级。
