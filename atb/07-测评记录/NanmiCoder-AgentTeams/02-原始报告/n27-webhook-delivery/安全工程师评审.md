# n27-webhook-delivery 安全工程师评审

评审对象：atb/tasks/n27-webhook-delivery/environment/proposal.md（37 行）
已对仓库逐行核实（src/server/platform/、src/server/adapters/、migrations/、docker/）。
本案是整个仓库**第一次**出现「用户可控的出站请求目标」，其风险等级远高于其它功能。

## 最重要 5 条

### S1【阻塞】SSRF：proposal:9-15 允许用户填任意 URL，proposal:25 直接 fetch
方案没有对 `url` 做任何约束（没有协议白名单、没有解析后 IP 判定、没有重定向策略）。
**代码事实**：本仓**目前不存在任何 SSRF 防护惯例**——全仓 grep 无内网/回环/元数据地址判定
（唯一涉及 127.0.0.1 的是 src/server/platform/client-ip.mjs:16 的日志归一化，不是防护）。
而 web 与 worker 都跑在**内网**（docker/compose.yaml:57-58 注释「web 只挂在内部网络」），
，同一网络里就是 migrate / web / worker / nginx 与宿主机可及的一切。
② 后果：攻击者把 webhook 改成 `http://127.0.0.1:<port>/`、`http://169.254.169.254/latest/meta-data/`
（云元数据，可拿实例凭据）、或内网其它服务，就得到一个**服务端代理**：
  (a) 端口扫描内网（响应时间/状态码差异即可探测）；
  (b) 读取云元数据 → 云账号失守；
  (c) 打到同机 web 的未授权端点（如 /api/testing/session 虽被 nginx 挡，但**内网直连绕过 nginx**）。
③ 建议：至少三条同时做：
  1. 协议只允许 `https:`（禁止 http/file/gopher 等）；
  2. **解析后**校验 IP 是否落在公网：拒绝 127/8、10/8、172.16/12、192.168/16、169.254/16、::1、fc00::/7 等；
     ⚠️ 必须防 DNS rebinding：解析与连接要绑定同一 IP（校验后按 IP 发起，带 host 头），不可“先校验再让 fetch 自己解析一遍”；
  3. `redirect: 'manual'`，禁止跟随重定向（否则 302 到内网就绕过了第 2 条）。

### S2【阻塞】推送无超时，worker 会被拖死
proposal:25-29 的 fetch **没有 signal/timeout**。
**代码事实**：本仓既有出网工具都强制超时——src/server/platform/http.ts:15-22
（DEFAULT_TIMEOUT_MS = 8000 + AbortController），login 适配器同样用 fetchWithTimeout
（src/server/adapters/login/index.ts:62）。
② 后果：第三方 URL 只要不响应（挂住），fetch 就永久 pending；
叠加 `TASK_DEADLINE_MS = 300s`（src/server/modules/tasks/constants.ts:45）与
单进程串行执行（worker/main.ts:199-204 注释「本切片按顺序执行」），
**一个卡死的 webhook 就能让整个 worker 停摆 300 秒**，期间全站后台任务全部积压。
这是低成本 DoS：不需要任何权限提升，只要订阅一个不响应的地址。
③ 建议：照抄 http.ts 的 AbortController + 8s 超时；并限制响应体读取上限
（http.ts:4 注释“不让第三方返回体撑爆内存”，方案连读都没读，但一旦读就需设上限）。

### S3【阻塞】secret 明文入库，且方案未定义签名，等于没有鉴权
proposal:16 `secret TEXT NOT NULL`；proposal:25-29 的请求头只有 content-type，
**没有签名头**，`secret` 从头到尾没被用上。
**代码事实**：本仓对凭据的纪律是**只存摘要**——src/server/migrations/0001_baseline.sql:53
`token_digest TEXT NOT NULL CHECK (length(token_digest) = 64)`，:60 `UNIQUE (token_digest)`；
生成用 newOpaqueToken()（src/server/platform/id.ts:48-49，randomBytes(32)）。
② 后果两个方向都坏：
  (a) **接收方无法验证真伪**：任何人知道 URL 就能伪造 POST，第三方无法区分是本站发的还是攻击者发的；
  (b) 明文 secret 一旦随库泄漏（备份、SQL 注入、运维误操作）即可被直接重放。
③ 建议：secret 用 HMAC-SHA256 对 `timestamp + body` 签名，通过
`X-Signature` / `X-Timestamp` 头传递（参照 GitHub/Stripe 的通行做法）；
库里存 `secret_digest` 而非明文；签名必须含时间戳**并在接收端文档里要求校验时间窗**，
防重放。

### S4【阻塞】无重放防护 + 重试语义未与队列对齐
proposal:32-33「失败重试 3 次」一句话。
**代码事实**：本仓队列已有成熟重试语义——MAX_RECOVERABLE_ATTEMPTS = 3、
RETRY_BACKOFF_MS = [30s, 120s]（constants.ts:32,39），失败进入 retry_wait 而非新行。
② 后果：(a) 方案没说重试是**新建行还是复用任务**，若每次重试都新建，`UNIQUE(task_type, deduplication_key)`
（0001:369）会撞、或产生重复投递；
(b) 更关键：**没有幂等键/事件 ID**，网络抖动导致的“对方已收到但响应丢失”会让第三方**重复收到同一事件**；
叠加无时间戳校验（S3），就是可被重放放大。
③ 建议：每条事件带 `event_id` + `occurred_at`，接收方按 event_id 去重；
重试沿用既有队列（finish 走 retry_wait，不新建行），不要自己写循环。

### S5【高】订阅配置接口的鉴权与频控完全未提（对照 proposal:9「用户可配置」）
proposal:9 只说“用户可配置自己的回调 URL”，没有任何接口设计。
**代码事实**：本仓对每个写接口都有统一口径——assertCanWrite（context.ts:34-43）、
频控（rate-limit.ts:46-55 的 9 个动作）、以及“先认人再读 body”
（如 src/app/api/me/plugins/[pluginId]/claim/route.ts:21-23 的注释）。
② 后果：若接口遗漏鉴权/频控，**任何登录用户都能注册任意 URL**，把站点变成按需触发的
SSRF 探针（配合 S1）；且无频控时可批量注册海量订阅，把 worker 打满。
③ 建议：接口必须 assertCanWrite + 新增 RateLimitAction（参照 rate-limit.ts:127-133 的按天口径）；
订阅归属校验 `user_id === ctx.userId`（与出站前的归属判定同样严格，防 IDOR）。

## 完整清单（其余）

### S6【中】未登记 REQUIRED_TABLES，且缺索引
migrations 新表要登记到 src/server/platform/migrate.ts 的必需表清单（对照 :175-176 的 review_search 注释）。
② 后果：迁移后自检/健康检查报缺表。另 `user_id` 无索引，按用户查订阅会全表扫。
③ 建议：加登记 + `CREATE INDEX ... ON webhook_subscriptions(user_id)`。

### S7【中】事件内容未定义 —— 可能把不该外发的数据推给第三方
proposal:28 `body: JSON.stringify(event)`，`event` 是什么完全没定义。
② 后果：若像 notifications 那样直接序列化业务行，可能带出 author 内部字段、
隐藏/撤回内容的状态、甚至他人昵称；而 webhook 是**出站到不可控的第三方**，泄漏不可撤回。
建议：显式白名单事件字段（与 m13 导出同一纪律），并明确“只推公开可见的内容事件”。

### S8【中】方案与既有架构决策冲突，却在文档里没提
migrations/0008_notifications.sql:7-8 明确写道：「**不做 business_events / event_delivery_tasks 那一整层**。
架构里那层是为了可重试的扇出（邮件/外部 webhook）……将来要加邮件/推送，再补事件层与投递任务」。
② 后果：本方案正是那一层的**第一个消费者**，却直接写 `await fetch(...)`、没有事件层。
这不是说不能做，而是**绕开了团队已经写下的取舍**，后续维护者会困惑“说好的事件层呢”。
建议：在方案里显式回应这条注释：要么补事件表，要么说明为何本场景可直接嵌在任务里。

### S9【中】出站请求会暴露 worker 的真实出口 IP 与内部标识
proposal:25-29 的请求没有设置 user-agent。
对照 http.ts:26 显式设 `'user-agent': 'dsh-plugin-reviews/1.0'`。
② 后果：默认 UA 取决于运行时（可能是 undici/node 版本），既便于被指纹识别，
也不利于第三方排查“这是谁打的”。建议显式设 UA，且**不要**带内部版本号/commit。

### S10【低】URL 需要长度与字符约束（与既有 return_path 校验同一精神）
oauth-challenges.ts:60-78 的 normalizeReturnPath 是本站处理“用户给的地址”的标杆：
它拒绝协议相对地址、反斜杠变体、控制字符（:64-69），并注释说明“拒绝而非静默剔除，
避免剔除后恰好拼出别的地址”。webhook url 需要同样的严格度。
建议：长度上限（如 2048）、拒绝控制字符与含 userinfo 的 URL（`https://user:pass@host/` 会把凭据带进日志/下游）。

### S11【低】日志会记下 URL，可能带出第三方凭据
log.ts:24 的脱敏黑名单是 /token|secret|password|credential|authorization|cookie|code_verifier/i，
按**字段名**匹配，`url` 不会命中。
② 后果：若订阅 URL 形如 `https://hooks.example.com/x?token=abc`（很多平台如此），
整条 URL 进日志即泄漏该凭据。
建议：记录时对 URL 做 query 脱敏，或只记 host + path 前缀。

## 一句结论
Webhook 方向合理，但方案是**全仓第一个用户可控出站请求**，而它恰好把四件事都省了：
目标校验（SSRF）、超时（worker DoS）、签名（接收方无法验真伪）、幂等（重复投递）。
这四条任意一条不补都足以构成安全事件；建议按 S1-S4 重写后再评审，
出站工具可直接在 src/server/platform/http.ts 上扩展（它已有超时与内存约束的骨架）。
