性能工程师评审（n30-n-plus-one proposal.md，35 行）：**方案不能按现状实施，而且优化错了目标**。6 条（2×P0 / 2×P1 / 2×P2），全部按真实 schema 形状建库实跑验证。

**P0-1 问题本身是虚构的，SQL 在现有 schema 上编译不过**：plugin_categories 的列只有 slug/label/topics/sort_order/is_visible/created_at/updated_at（migrations/0010_plugin_categories.sql:19-27），**没有 repository_id**；实测该查询直接报 no such column: repository_id。而目录页早在 catalog/service.ts:242-269 就用 categoriesByRepository() 做了**一次**批量查询（注释原文「一次查询，避免 N+1」），真实的**21 次查询并不存在**。分类与仓库是 N:M（各自持 topics，靠 json_each 交集匹配），不是方案假设的 1:N。

**P0-2 靶子选错：81ms 在 4 个相关子查询上，不在分类查询**：实测 6000 插件/24000 评测下单页 20 条耗时 **81–86ms**，且与 OFFSET 无关（0/3000/5900 同值）；EXPLAIN 显示 SCAN p + CORRELATED SCALAR SUBQUERY + USE TEMP B-TREE FOR ORDER BY；真实代码有 **4 个**这样的子查询（service.ts:822-825）。按方案改完，用户感知不到变化 —— 现状本就是「1 次列表 + 1 次分类」，改前改后查询条数是 2 → 2。

**P1-3 批量 IN 无兜底**：空 ids 会生成 `IN ()` → 语法错误 500（末页/无结果很常见）；参数上限 999 无分块（search/index.ts:196-200 的既有做法是分块 200）；「禁止拼接 id」的约束未写进方案。

**P1-4「按 repository_id 分组」丢语义**：现有 DISTINCT + ORDER BY sort_order, slug（service.ts:254-260）保证 chip 顺序稳定无重复；改为 SELECT * 再 JS 分组会拿到未排序结果、N:M 下出重复 chip（monorepo 放大坑见 migrations/0010:8-9），并把 topics JSON 整列带回应用层。

**P2-5 真正该优化的同类热点（方案没提）**：listCategories（service.ts:964-1021）的 JOIN json_each(c.topics) × json_each(r.topics) 在 2000 仓库×10 插件下实测 **4000 行 / 205ms**；改 EXISTS 交集写法后 **2 行 / 4.7ms**（≈43×）。这条每次首页/目录页都跑，比「21→2 次」重要得多。

**P2-6 预期不可验收**：「21 次降到 2 次」前提错误；「显著变快」无基线/无 P95/无数据规模；同步驱动下应按**主线程占用**度量而非查询条数。
