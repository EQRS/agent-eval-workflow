前提核实（方案要改的东西不存在）：
- plugin_categories 根本没有 repository_id 列（0010_plugin_categories.sql:19-27，真实结构是 slug/label/topics(JSON)/sort_order/is_visible/...），分类靠 topics JSON 匹配建立关联（0010:14）；方案 §1 的 WHERE repository_id=? 直接 no such column。
- "一页 20 个插件查 21 次"在本仓库从未存在：categoriesByRepository（service.ts:242-269）已是一次查询，列表 :857-861、详情 :760 都用它。
- 方案 §2 的 SELECT * 违背全仓逐列列名纪律（service.ts:703-714、818-831）。

P0（安全）SELECT * 是数据暴露放大器：列表页是匿名公开接口（plugins/route.ts:29-42 → service.ts:784-861），SELECT * 会把 repositories 的 github_repository_id / last_checked_at / availability_state / topics 原文等内部字段一并带出，将来新增列也会自动泄漏——这正好是 errors-http.ts:49-60 明确反对的"删除式构造"（那里要求白名单式构造）。方案对"分组后"返回值没有任何字段白名单。建议：显式字段白名单并与 PluginSummary 对齐；plugin_categories 只给 slug/label/sort_order/is_visible，绝不把 topics 原样给匿名访问者；CI 加"公开响应字段 ⊆ 白名单"断言。

P1（可用性即攻击面）IN (...) 的正确性依赖调用方非空但方案未写：ids 为空时 IN () 是 SQLite 语法错误 → 被 errors-http.ts:62-72 折成 500；而 /api/plugins 的 page 没有上界（route.ts:29-42），任何匿名用户传 ?page=999999 就能让公开接口 500。既有实现第一行就是空数组早返回（service.ts:250）。建议空数组早返回 + ids.length 上限（对齐 interactions:1074-1076 的 200）+ 契约写明只能被受控分页调用。

P1（未发布信息泄露）方案无 is_visible 过滤：真实实现每条面向公众的分类查询都带 c.is_visible = 1（service.ts:257、299、307）；方案的 SELECT * FROM plugin_categories 会把管理员尚未上线的分类直接暴露到公开列表页。且分类由管理员随时 upsert/delete（service.ts:1064-1150），不是静态常量。建议批量查询同样带 is_visible=1，并与 buildDirectoryWhere 的分类筛选口径同源。

顺带确认（现状安全、别改坏）：listPlugins 逐字段构造 PluginSummary、categories 只有 label 字符串数组（service.ts:864-889）；错误响应未知异常一律 internal+500 且堆栈只进日志。

处置建议：不实施本方案；若列表页性能确有问题是另一题（categoriesByRepository 里 json_each 的索引/执行计划），并把字段白名单与可见性过滤写成验收项。
