# n42-mlps 安全工程师评审

评审对象：atb/tasks/n42-mlps/environment/proposal.md（37 行）
已对仓库逐行核实（migrations/、src/server/modules/operations/、identity/、platform/context.ts）。

**总判：方案的三个技术点里，第 1、2 条是「重造一套更弱的审计」，第 3 条在当前架构下无法实现。**
本仓已有一套通过 0042 加固的审计体系，等保要的东西大多已经在，缺的是**覆盖与保留**，不是**新表**。

## 最重要 5 条

### S1【阻塞】审计表已经存在且更强，方案另起 `audit_log` 等于制造第二套真相
proposal:11-17 建 `audit_log(id, user_id, action, ip, created_at)`。
**代码事实**：migrations/0001_baseline.sql:411-433 已有 `operation_records`，且字段维度多得多：
`action_type / operation_key / actor_kind('user'|'admin'|'system') / actor_user_id / target_type / target_id /
target_snapshot(json) / changes(json) / reason / request_reference / task_id`，
并带 `UNIQUE(action_type, operation_key)`（:426）与三条索引（:432-433）；
migrations/0042_audit_immutable.sql:17-27 已加**不可删/不可改**触发器。
仓库已有 **20+ 个** actionType 在用（content.withdraw / content.hide / pack.release.approve /
feedback.handle / featured.publish / plugin.import.run 等）。
② 后果：新表若并存，等保要求的“审计完整性”反而被破坏——同一件事两处记录、两套口径，
且 `audit_log` **没有**不可变触发器（0042 的守卫不会自动覆盖新表），
「有据可查」变成「有两份可能不一致的据」。
③ 建议：**不要新建 audit_log**。直接在 `operation_records` 上补齐等保要素（见 S3/S4）。

### S2【阻塞】迁移号 0043 与既有 0042 之外还有坑：文件名去重会导致静默跳过
proposal:10 写 `migrations/0043_audit_log.sql`。
**代码事实**：现有最高是 `0042_audit_immutable.sql`，0043 号**当前可用**（这点没问题）。
但迁移器按**文件名**去重（migrate.ts:51-55 的 readdirSync + localeCompare；0042:15 自注「迁移器按文件名去重」）。
② 后果：若实现者为了“复用”去**改写 0042_audit_immutable.sql 本身**，已迁移的线上库会记为已应用 →
新表**永远不会建**，代码却在 INSERT → 全站 500，且 CI 新库测不出来（新库从头跑）。
③ 建议：独立新文件 0043（不要碰 0042）；并在文件头写明这一点。

### S3【阻塞】`ctx.clientIp` 不存在 —— 方案里的 ip 字段拿不到值
proposal:26 写 `clientIp`，proposal:15 建 `ip TEXT`。
**代码事实**：src/server/platform/context.ts:10-15 的 `CallerContext` **只有三个字段**：
`userId / role / accountStatus`，**没有 ip**。`resolveClientIp`（src/server/platform/client-ip.mjs:54）
只在 server.mjs 里被调用（server.mjs:71-75），**业务层拿不到它**。
② 后果：照抄会得到 `undefined`，审计里 ip 恒为空——
而“IP 记录”恰恰是等保二级审计的显式要求，等于这条要求**没有落地却看起来做了**。
③ 建议：二选一：(a) 在 server.mjs 注入 `x-client-ip` 请求头（与 :59 注入 `x-request-id` 的既有手法一致），
业务层用 `requestIdFromHeaders` 同款校验读它；
**(b) 更稳**：由 server.mjs 在 `res.on('finish')` 直接写访问日志（那里已有可信 ip），
审计表只记业务事实，不再重复存 ip。注意 client-ip.mjs:7-10 的纪律：
头是客户端可写的，**只有 TRUST_PROXY=1 时才可信**。

### S4【阻塞】proposal:30「管理员操作二次密码确认」在本架构下**无法实现**
**代码事实**：全站是 **GitHub OAuth 单点登录**——migrations/0001_baseline.sql:38 与 0003:21 的
`provider CHECK (provider IN ('github'))`；全仓 grep `password|password_hash|credential`
在 migrations/ 下**零命中**，users 表没有密码列。
② 后果：要么实现者自造一套密码体系（等于给 OAuth-only 系统新增一个凭据面，
与 0001:38 的 CHECK、identity 模块的设计全部冲突，且密码哈希/重置/防爆破都要从零做），
要么这条要求被静默跳过。两者都不可接受。
③ 建议：改成适配既有认证的二步确认——重新验证 GitHub 身份（`/api/auth/github/start` 带
`return_path` 回到当前页）或**短时 step-up 令牌**（服务端签发的 5 分钟一次性确认记录），
并把该设计写进方案；不要引入密码。

### S5【高】「所有写操作都记一条」会产出大量噪声，且 recordOperationInTx 强制要求 reason
proposal:21-27 的 `INSERT INTO audit_log` 是裸 SQL，绕过了既有校验。
**代码事实**：正确的入口 `recordOperationInTx`（src/server/modules/operations/service.ts:71-90）
强制 `actionType / operationKey / reason` **非空**（:76-84），且校验 `actor_kind` 与 `actor_user_id` 的配对（:86-95），
相同键但内容不同会抛 `request_key_reused`（:130-132）。
② 后果：裸 INSERT 会**绕过这些约束**，写出没有 reason、actor 自相矛盾的审计行；
而“所有写操作”若含高频低价值写（每次收藏、每次草稿自动保存），会把真正要审的高危操作淹没。
③ 建议：按**等保的重要性分级**而非“全部”：审计的是认证、权限变更、内容发布/撤回/隐藏、
删除、导出、配置变更、备份恢复。现有 20+ actionType 已覆盖大半，缺的补上即可。

## 完整清单（其余）

### S6【高】真正的审计缺口在于**管理员备份**这类高危操作没记审计（可直接补）
实测：src/app/api/admin/backups/route.ts 只做了 `assertCanAdmin`（:17 导入），
**全程没有调用 recordOperationInTx**；而 `scripts/backup.mjs:73-74` 反而明确写着
「operation_records 必须在内：它是审计与幂等去重的唯一载体……恢复时若缺它就无法证明」。
② 后果：管理员“立即备份”这一动作无审计痕迹——这不是等保“补新表”能解决的，是**现成缺口**。
③ 建议：先补这一类（备份、恢复、用户禁用、登录失败），比新建表更能满足等保“审计覆盖”。

### S7【中】6 个月保留与仓库既有取向、以及存储成本都要交代
proposal:33「保留 6 个月」。
**代码事实**：本仓对数据是**尽量少留**取向（备份只留 14 份，compose.yaml:62 `BACKUP_KEEP: '14'`），
且 operation_records 属于**不可删**表（0042），若不分表直接堆 6 个月，
它会与业务库同盘增长（compose 日志上限仅 30MB，见 t24 的同类结论）。
② 后果：**不可删 + 6 个月** = 表只增不减；终态是磁盘耗尽（SQLite 写入失败，含 WAL）。
③ 建议：要么给 operation_records 做**归档表**（到期搬走冷数据，审计表本身仍不可删），
要么明确 6 个月只适用于**安全日志**（server.mjs 的访问日志，可独立轮转），
不要混为一谈。方案当前把两者混在一起了。

### S8【中】未定义“哪些事件算审计事件”的最小清单
等保二级对审计内容的典型要求是：谁、什么时候、从哪、做了什么、结果如何。
方案的 `action` 只有一个字符串列（proposal:14），没有 `target`、没有 `result`、没有 `reason`。
② 后果：即便记录了，也无法回答“他改了**哪一个**对象的**什么**”——
这正是 operation_records 的 `target_type/target_id/changes/reason` 已经解决的问题（0001:418-422）。
③ 建议：直接复用这四个字段，方案改为“补齐 operation_records 的覆盖清单”。

### S9【中】审计写入必须在**业务事务内**，方案没说
proposal:24-26 是一次独立的 `db.prepare().run()`。
**代码事实**：既有做法是 `recordOperationInTx(tx.db, ...)` 与业务变更**同事务**
（例如 identity/admin.ts:330 注释「写库 + 审计（同一事务）」）。
② 后果：独立写入会出现“业务改成功但审计没记”（或反之），两种都破坏审计的可信度。
③ 建议：强制要求同事务，与既有 20+ 处实现一致。

### S10【低】`user_id` 可空但无 actor_kind，匿名/系统动作无法区分
proposal:13 `user_id TEXT`（可空），没有区分“系统动作”与“匿名请求”。
operation_records 用 `actor_kind IN ('user','admin','system')` + CHECK（0001:415,427-430）
表达了这层语义，方案缺。建议直接沿用。

### S11【低】方案没有验收口径
proposal:35-36 只有两句定性描述。等保验收需要**可核查**的项（如“上述 N 类操作均有审计记录，
且审计不可删改”）。建议把 0042 的两条触发器作为现成证据写进验收。

## 一句结论
**等保要的东西本仓大部分已经有了**：operation_records（0001:411-433）+ 0042 不可变触发器
+ 20 多个 actionType + 同事务写入 + `actor_kind` 区分系统/人工。
方案的三点里，第 1 条（新建 audit_log）是**倒退**（无不可变守卫、字段更少、制造第二套真相），
第 3 条（二次密码）在当前 OAuth-only 架构下**无法实现**（0001:38 无密码列），
第 2 条（所有写操作都记）会绕过强制约束并淹没关键事件。
建议改为：**不新建表**，先补现成缺口（管理员备份无审计，S6）、补 IP 来源（S3）、
把二次确认改成 GitHub 重新认证/step-up 令牌（S4），并给出审计事件的**最小清单**与保留/归档方案。
