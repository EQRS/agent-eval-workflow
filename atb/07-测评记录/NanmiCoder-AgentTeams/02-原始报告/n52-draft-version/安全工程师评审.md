安全工程师评审（n52-draft-version proposal.md，28 行）：**方案不能按现状实施**。7 条（3×P0 / 3×P1 / 1×P2），按真实表结构建库实跑验证。

**总评**：方案要做的事本仓库**已经实现且做对了** —— src/server/modules/reviews/index.ts:601-691 的 saveDraft() 已是「回执优先 → 原子 CAS → 写回执」三段式。方案却把它换成一个去掉归属校验、去掉软删除过滤、不更新时间戳、不带幂等键的裸 CAS，等于**把加固过的写路径替换成更弱的一条**。

**P0-1 水平越权（IDOR）**：§1 的 UPDATE 只有 WHERE id = ?，没有 owner_id 校验。实测他人用该语句改被害人草稿返回 {changes:1}、内容被完整替换、归属不变、无报错无审计。UUIDv7 不可猜但会出现在前端 state/日志/共享链接里，不能当授权。→ 复用现有 saveDraft；重写也必须带 owner_id 并把「不存在/非本人」统一回 unavailable（不泄露存在性），只有版本不符才 409。

**P0-2 无幂等键 → 重试即丢稿**：自动保存抖动重发同一 expectedVersion，第一次已成功、第二次必然 changes:0 → 方案据此 409，再按 §3「丢失本地修改」。实测 {attempts:3, applied:1, conflicts:2, final_version:4}。仓库正为此建了 draft_save_receipts（0001_baseline.sql:208-218），并在 reviews/index.ts:605-607 写明「重放必须在 CAS 之前判定」。→ 加 requestKey，先查回执再 CAS。

**P0-3 不更新 saved_at**：它是 NOT NULL 且是草稿列表排序键（0001_baseline.sql:197、:206、0018:19）。实测更新后 save_version 3→4 而 saved_at 仍为 1000；从安全角度等于伪造自己的审计时间。→ 补 saved_at = nowMs()（服务端时间）。

**P1-4 不过滤 deleted_at**：0018 规定「删除后不可再读写」。实测置 deleted_at=4242 后仍更新成功，内容被复活。→ 条件加 deleted_at IS NULL。

**P1-5 §3「刷新即丢本地修改」**：现有实现在冲突时明确「不写回执、不改 payload，用户输入由调用方保留」并把 current_version 放进 conflict context。多设备下冲突是常态而非异常。→ 服务端不得覆盖，保存冲突副本或前端合并，并记录冲突事件。

**P1-6 无事务**：裸 UPDATE 与回执写入不在同一事务，会留下「内容已更新、回执缺失」；提交链路依赖 draft_save_version（0001_baseline.sql:311-326）。→ withTransaction 包住整段。

**P2-7 输入校验与错误分级缺失**：expectedVersion 非整数会静默 changes:0 → 一律 409 → 客户端无限重试；payload 未校验 json_valid 抛裸 SqliteError → 500。→ 复用 parseDraftId/parseRequestKey/parseDraftPayload，错误按 input_invalid → unavailable → version_conflict 分级。
