# n55-dup-submit 性能工程师评审

评审对象：atb/tasks/n55-dup-submit/environment/proposal.md（32 行）
已逐行核实 src/server/workflows/submit-review.ts、modules/reviews/index.ts、
migrations/0001_baseline.sql、src/components/review-editor.tsx、src/packages/common/errors.ts。

**总判：两点都已实现，且方案的「内存 Set 锁」在性能和正确性上都比现状差。**
现状：DB 级 `UNIQUE(submitted_by, request_key)`（0001:321）+ 回执比对（submit-review.ts:148-191），
前端 `busy` 状态锁（review-editor.tsx:965,968），客户端 `newRequestKey()`（api-client）。

## 最重要 5 条

### P1【阻塞】内存 Set 锁是「按 user 单飞」，会把**合法的并发请求**也串行化/误拒
proposal:24-28 用 `inFlight.has(userId)` 做锁，键是 **userId** 而非「这次表单提交的意图」。
② 后果：(a) 同一用户**同时开两个页面**（如两个草稿、或编辑评测时后台还在跑一个提交）——
两个不同的合法请求会被判成「请勿重复提交」，**误报冲突**；
(b) 反过来，双击产生的是**两次不同的请求**，若第一次已在 `finally` 里 delete（proposal:28），
第二次仍可能挤进来 —— 锁的粒度既太宽（跨意图）又太窄（不覆盖已完成后的重放）。
一个正确的幂等键应当是**一次用户意图**，本仓的 `requestKey` 正是这个语义
（errors.ts:17 注释：「用户操作去重。由客户端为一次用户意图生成，重试沿用同一键」）。
③ 建议：**不要用内存锁**。既有 `requestKey` + DB 唯一约束已经覆盖了「双击」与「网络重试」两种情形，
且粒度正确（按意图，不按用户）。

### P2【阻塞】内存锁在多进程/多实例下**静默失效**，且给运维埋下扩容地雷
proposal:24 的 `const inFlight = new Set()` 是**进程内**状态。
**代码事实**：部署是 web + worker 两个**独立容器**（docker/compose.yaml:44,78），各自一个进程；
web 由 nginx 反代（:110-116）。当前单实例，因此今天“看起来能用”。
② 后果：一旦扩容到 2 个 web 副本（或做滚动重启、或将来上 cluster），
同一用户的两次请求会落到**不同进程**，各自 `inFlight` 都不含对方 → **锁完全失效**。
而这种失效**没有任何报错**：平时正常、压力大时偶发重复，属于最典型的“性能优化引入的隐性缺陷”。
单实例下它也只是“碰巧有效”，不是设计上正确。
③ 建议：幂等判定必须落在**共享存储**（DB 唯一约束）上，与本仓既有做法一致。
进程内状态只能用于**降低无效查询**的短路优化，不能承担正确性。

### P3【阻塞】原子性缺失：既有实现是 DB 唯一约束兜底，方案没有并发安全网
proposal:26-28 是 check-then-act（`has` → `add`），Node 单线程下 `await handle()` 之前不切换，
**这一段本身**是原子的；但真正的重复写入发生在 `handle()` 内部，方案对此没有任何保证。
**代码事实**：既有实现靠两层：
  - `content_submissions` 的 `UNIQUE(submitted_by, request_key)`（0001:321）；
  - `uq_submissions_review_revision`（0001:334）——**同一修订只能有一条提交**，
    这是比 requestKey 更底层的兜底，防的是“客户端生成了两个不同 requestKey 但内容相同”的情形。
② 后果：方案只在最外层加锁，一旦绕过（如将来加个后台脚本、或并发 A/B 两次不同 requestKey），
**没有任何约束能拦住重复行**；而 DB 约束是“无论谁来写都拦得住”的。
③ 建议：保留并依赖 DB 唯一索引；`requestKey` 只作为幂等回执的键，不作为唯一防线。

### P4【阻塞】方案没有区分「重放应返回原结果」与「真冲突应报错」
proposal:26 一律抛 `err.conflict('请勿重复提交')`。
**代码事实**：既有实现（submit-review.ts:148-191）的做法是：
同一 request_key 命中 → **比对摘要**：相同则**返回原提交结果**（:184-190，`replayed` 语义），
不同才 `err.keyReused`（:178-180）。这是“幂等重放”，不是“报错”。
② 后果：双击的用户会看到一次报错（而不是“提交成功”），
**这会让用户以为没提交成功，再点第三次** —— 反而制造更多重复请求。
从性能角度看，报错还会触发客户端的重试/刷新逻辑，放大无效流量。
③ 建议：重放必须返回**原结果**（含 submissionId / taskId），让前端表现为“成功”；
只有“同键不同内容”才报 `request_key_reused`。

### P5【高】前端方案用 useState 防抖不足，且和既有 `busy` 实现重复
proposal:12-17 的 `submitting` 与既有 `busy`（review-editor.tsx:221,965,968）是同一件事。
② 后果：两套状态并存会漂移（一个按钮禁用、另一个没禁）；
更实质的是 `setSubmitting(true)` 在 React 中是**异步批处理**，
同一帧内的两次点击（双击的典型间隔 <100ms）在极端情况下都可能通过 `disabled` 检查 ——
所以前端锁**只能减少**重复，**不能消除**。方案把它当第一道防线是对的，但当唯一防线就错了。
③ 建议：保留既有 `busy`（别新增 `submitting`）；前端锁只做体验优化，正确性交给 DB。

## 完整清单（其余）

### P6【中】没有提及既有的全站限流设施，方案会绕过它
本仓有 9 个动作的频控（rate-limit.ts:46-55），提交类接口都在用
（如 content/[contentId]/comments/route.ts:72-77 的 comment_change）。
② 后果：防重复提交若只靠内存锁，**没有频控**兜底；而频控是跨进程共享的（DB 存储），
恰好能补上 P2 的多实例漏洞。
③ 建议：与既有接口一致地接 `enforceRateLimit`，作为内存锁的替代品之一。

### P7【中】内存 Set 无清理上限，长跑进程会累积（内存泄漏面）
proposal:24 `const inFlight = new Set<string>()`。
② 后果：`finally` 里 delete 在**正常路径**能清；但若 `handle()` 挂了事件循环以外的异常
（未捕获的 promise rejection、进程被 SIGKILL 前的挂起），条目会残留。
残留条目会让该用户**永久**无法提交（直到重启）——这是最难查的一类故障。
③ 建议：若一定要用内存结构，必须有 TTL 与容量上限；但更好的是不用（见 P1）。

### P8【中】方案未评估重复提交的真实来源，可能优化错了地方
proposal:3「用户双击提交按钮会重复创建」。
**代码事实**：既有 `busy`（review-editor.tsx:965,968）已在提交时禁用按钮，
且提交走 `requestKey`（客户端 `newRequestKey()` 生成）。
那么“重复创建”更可能来自**网络层重试**或**用户刷新后重新提交**，而非双击本身。
② 后果：若根因是重试，内存锁（P2/P4）不但无效，还会把重试直接打成报错，让用户重试更频繁。
③ 建议：先确认重复的现实来源（看 server.mjs 的 request_id 日志能否配对到同 requestKey），再定方案。

### P9【低】没有给出验收口径（性能角度）
proposal:31-32 只有一句「不会重复提交」。
建议改成可测的：同一 `requestKey` 并发 N 次 → `content_submissions` 只增 1 行；
并发两个**不同** requestKey 的合法提交 → 两个都成功（证明锁没有误杀）；
重启/多实例下行为一致。

## 一句结论
「防重复提交」在本仓**已经用正确的方式解决了**：客户端 `requestKey`（一次意图一键）+
DB `UNIQUE(submitted_by, request_key)` + 幂等回执返回原结果 + 前端 `busy` 锁。
方案新增的内存 `Set<userId>` 在**粒度**（按用户而非意图）、**范围**（进程内，扩容即失效）、
**语义**（冲突报错而非返回原结果）三方面都比现状差，属于用更弱的手段替换更强的手段。
建议：**不新增锁**，改为确认现有幂等链路覆盖是否完整（P8），并把重复来源的真实数据先查清。
