# m12-schedule-timing 安全工程师评审

评审对象：atb/tasks/m12-schedule-timing/environment/proposal.md（50 行）
全部结论已对仓库逐行核实（migrations/、src/server/modules/tasks/、src/worker/、src/packages/common/time.ts）。

## 最重要 5 条

### S1【阻塞】迁移号 0042 已被占用 —— 照抄会让整个迁移被**静默跳过**
proposal:12 写「给 background_tasks 加一列（迁移 0042）」。
**代码事实**：migrations/0042_audit_immutable.sql **已经存在**（审计表不可变，加两枚触发器）。
迁移器按**文件名**去重与排序：src/server/platform/migrate.ts:51-55 `listMigrationFiles` 走
readdirSync + localeCompare，且 0042:15 自己注明「迁移器按文件名去重」。
② 后果：若新迁移也叫 0042_*.sql，它与既有 0042 是**两个不同文件名**→ 都会执行（顺序取决于文件名）；
若有人为省事**改写 0042_audit_immutable.sql 本身**，那么所有已迁移的库会把它记为已应用 →
`scheduled_at` 列**永远不会被加上**，而代码已在用 → 运行期 `no such column` 全站 500。
更隐蔽的是：这不会在 CI 新库上暴露（新库从头跑，列存在），只在**线上老库**炸。
③ 建议：用新的空号（0043 起）；绝不复用 0042。
并明确：本条属「会静默跳过」的部署级风险，应在文档里写死编号规则。

### S2【阻塞】scheduled_at 加了但**没人读**——不改变任何执行时刻
proposal:15-16 加列加索引，proposal:28-41 只做 enqueue，**没有任何一处按 scheduled_at 延后执行**。
**代码事实**：领取逻辑只看 `available_at`，完全不看 scheduled_at ——
src/server/modules/tasks/service.ts:127-128 与 :151-152 的 WHERE 都是
`processing_state IN ('queued','retry_wait') AND available_at <= ?`。
② 后果：tick 在 03:00 之后一看到 `now >= target` 就 enqueue，任务**立刻**变 queued，
main.ts:190-195 下一轮就 claim 掉 → 实际执行时刻仍取决于 worker 何时跑到那次 tick，
正是 proposal:5 抱怨的问题**原样保留**。方案的核心目标（稳定时刻）没有达成。
③ 建议：二选一并写清：
  (a) 不加列，直接把 `available_at` 设成目标时刻（enqueue 已支持，见 :197-199 校验）；
  (b) 保留 scheduled_at，但**同时**把 available_at 设为该时刻，并在 claim 的 WHERE 里加条件。
推荐 (a)：现有队列已有 `available_at` 语义与索引（0001:383 idx_tasks_claimable 已含 available_at），
新列是冗余的，且 proposal:16 的新索引与既有索引职责重叠。

### S3【高】proposal:33-38 的 enqueue 调用缺两个必填参数，照抄直接抛 400
proposal:33-39 只传了 taskType / deduplicationKey / requestedBy / payload。
**代码事实**：tasks/service.ts:194-199 强制校验 `schedulingGroup` 与 `availableAt`，缺失即 `err.input` →
，且 DB 层 scheduling_group 是 NOT NULL（migrations/0001_baseline.sql:353）。
② 后果：实现者照抄会让 tick 每次都抛错；而 tick 在 main.ts:180-188 是被 try/catch 包住的，
只会打一条 `log.error('排入自动发现任务失败')` → **任务永远排不进去且无人发现**（静默失效）。
③ 建议：补 `schedulingGroup: DISCOVERY_SCHEDULING_GROUP`（src/worker/scheduled.ts:31）
与 `availableAt: target`；并参照 scheduled.ts:103-123 的既有调用形态。

### S4【高】`ymd` / `atTime` 两个函数在本仓**不存在**，且时区口径未定义
proposal:29 `ymd(now)`、proposal:31 `atTime(now, s.at)` —— 全仓 grep 无这两个函数。
本仓唯一的日期工具是 src/packages/common/time.ts:26-33 的 formatDateTime/formatDate，
它们把时区**钉死为 Asia/Shanghai**（time.ts:12），源码注释 :4-7 明确写了理由：
「线上 VPS 是 UTC，`toLocaleString` 会让时间少 8 小时，本机开发看不出来」。
且既有 discoveryDailyKey 也是按 Asia/Shanghai 算“哪一天”（catalog/discovery.ts:121-124）。
② 后果：若 `atTime` 用服务器本地时区（UTC）实现，'03:00' 实际是北京时间 **11:00**，
与产品预期差 8 小时——**本地全对、线上全错**（正是 time.ts 记录过的坑）。
③ 建议：显式按 Asia/Shanghai 计算 target，复用 formatDate 的口径；不要引入第二套时间函数。

### S5【中】新增 task_type 需要重建整表，方案严重低估了代价
proposal:45「cache_warmup 需要新的 task_type（迁移里放开 CHECK）」一句话带过。
**代码事实**：SQLite 改不了列 CHECK，必须 新建→拷→删→改名，且 background_tasks 被外键引用
（background_task_attempts.task_id、operation_records.task_id），必须 `PRAGMA foreign_keys = OFF`，
而该 PRAGMA **在事务里是空操作** → 只能声明 `dsh:migration-transaction=off` 自管事务
（migrations/0007_task_type_plugin_discovery.sql:7-14 对这一整套坑有逐条记录）。
② 后果：这是一条**不可回滚、中途失败会留半成品**的迁移（0007:14 明确写“执行器的其它迁移有自动回滚，这条没有”）。
若按 proposal:12 把它和 scheduled_at 的 ALTER 混在一起，风险叠加。
③ 建议：把「加列」与「重建表放开 CHECK」拆成两条迁移；重建那条严格照抄 0007 的写法
（逐列枚举、不用 SELECT *、PRAGMA 在 BEGIN 之外）。
更省事的替代：考虑 `cache_warmup` 是否真需要独立 task_type，
复用 plugin_discovery + payload 区分可免掉整次重建。

## 完整清单（其余）

### S6【中】需要同步改两处类型白名单，方案未提
migrations/0007:26 的 CHECK **和** src/packages/common/field-rules.ts:88-95 的 TaskTypes 常量
两处都要加 `cache_warmup`；:87 注释明确写「注册集合随迁移版本维护，不能由配置注入新类型」。
只改一处会让 `taskType: s.name`（proposal:34）在 TS 层报错或运行期插入失败。

### S7【中】按天 dedup + 「now >= target」的组合会在**同日重试后不再触发**
proposal:24-26 的 dedup 是 `discovery:github:${d}` / `warmup:${d}`（按天）。
结合 tasks/service.ts:205-208 的 enqueue（命中即返回既有任务、created=false、不重跑），
② 后果：若当天任务已 failed，tick 后续每轮都只是拿回那个失败任务，**当天不会再试**；
反之若进程在 03:00 前重启，`now >= target` 为假 → 当天不排（除非整个 tick 都错过）。
建议写明：失败后是否需要当天补跑（现有 ensureDailyDiscoveryTask 的语义是“一天一次，失败即止”）。

### S8【中】调度循环把 schedule 表里的 name 直接当 task_type 用，类型无校验
proposal:23-26 的 `schedules` 是普通数组字面量，`name` 是 string；proposal:34 直接 `taskType: s.name`。
若有人手写错（如 'daily-discovery'），到 DB 层才撞 CHECK（0007:26）→ 静默 log.error。
建议：类型上约束为 `TaskType`（field-rules.ts:96），让编译器在写错时直接报错。

### S9【低】新索引与既有索引职责重叠
proposal:16 `CREATE INDEX idx_tasks_scheduled ON background_tasks(processing_state, scheduled_at, id)`
与 0001:383 `idx_tasks_claimable(processing_state, available_at, scheduling_group, id)` 同前缀。
若采纳 S2(a)（只用 available_at），这条索引完全多余；
若保留 scheduled_at，也应说明它服务于哪条查询（当前没有任何查询用它）。

### S10【低】`requestedBy: null` 正确，但应写明审计归属
proposal:36 传 null —— **与既有系统排入一致**（scheduled.ts:107 注释：系统排入无请求人，
审计走 operation_records 的 system 身份）。这一点是对的，建议保留并写明，
避免实现者“顺手”改成某个固定管理员 id（会污染审计）。

### S11【低】方案未提对既有 ensureDailyDiscoveryTask 的去留
proposal:4 承认现有实现解决了幂等。新调度循环上线后，旧的 ensureDailyDiscoveryTask
（scheduled.ts:70-129，main.ts:181 在调）若**不去掉**，会与新循环并存：
两套 dedup 键若不同（旧 `daily:<date>` vs 新 `discovery:github:<date>`），同一天会跑两轮。
建议：明确替换与迁移路径（旧键兼容或一次性切换），并同步更新 tests。

## 一句结论
方案目标（固定时刻）合理、且本仓**已经有**实现它所需的全部机制（`available_at` + claim 的 WHERE）。
但当前写法有四处硬伤：**迁移号撞车（0042 已存在，会静默跳过）**、
**加了 scheduled_at 却无人读取（核心目标未达成）**、
**enqueue 缺必填参数（静默失效）**、**ymd/atTime 不存在且时区未定义（线上差 8 小时）**。
最小改动路线：不加新列，直接把 `availableAt` 设为 Asia/Shanghai 的 03:00，其余照抄 scheduled.ts 的既有写法。
