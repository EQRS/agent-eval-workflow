结论：方案会让定时任务从「每天最多一轮」退化成「重启/跨天就补跑」，且 03:00 与每日备份撞点；它新增的 scheduled_at 列与索引在方案自己的代码里一次都没被使用。

摘要前 5 条：
1.【严重】§2 的 if (now >= target) 是「过期就补跑」不是「到点才跑」。proposal.md:31-32；daily key 只用 today 计算（:29,35）→ 当天只去重一次，但跨天不会；worker 停机后启动 03:00 的任务 12:00 才跑，配额花在价值最低的时刻。量化：单轮约 26 次核心请求（deploy/discovery-drip.sh:21-22），未认证 60/h（discovery.ts:49-51），03:00+04:00 两 schedule 同 tick 触发。建议加容差窗口（now-target<=15min）+ 排入后记内存，错过记日志跳过（与 backup.timer:14 的 Persistent=true 语义相反）。
2.【严重】§1 的 scheduled_at 列 + idx_tasks_scheduled 是死代码：proposal.md:15-16 建列建索引，但 :28-41 的 tick 只遍历内存数组，从不读写该列。background_tasks 是写热点（service.ts:246-379 每次 claim/renew/finish 都写），多一个索引 = 每次写多一棵 B-tree，零收益。建议删掉 §1，或改用既有 available_at（0001:359，已是 claim 排序键 service.ts:122-131）。
3.【高】「复用主循环节拍」= tick 被长任务阻塞：main.ts:199-204 串行 await execute，跑满 TASK_DEADLINE_MS=300s 的任务会把后续 tick 推迟最多 5 分钟；IDLE_SLEEP_MS=10s（constants.ts:25,48）→ 每天 8640 次空转。建议 tick 用独立 setInterval，不进 runOnce 串行路径。
4.【高】03:00 与备份撞点：proposal.md:24 vs deploy/dsh-review-backup.timer:12-13（OnCalendar 03:00 + RandomizedDelaySec 5m）、dsh-review-backup.service:26（整库 backup.mjs）。备份读一个正被高频写的库，SQLite 单写者下写锁竞争。建议错开到 05:00 并加抖动。
5.【中】§3「新增 task_type」一句话带过，实际要全表重建 background_tasks：0007_task_type_plugin_discovery.sql:1-19/62-81（foreign_keys=OFF、dsh:migration-transaction=off、INSERT SELECT + DROP + RENAME + 重建索引），中途失败留半成品；背景表被 background_task_attempts 与 operation_records 外键引用，重建期间写不受外键保护。建议与其它 task_type 变更合并成一次重建。

完整清单 P-01…P-09，另含：时区未定义（time.ts:5-13 UTC 毫秒；common/time.ts:2-12 明写「本地全对线上全错」；compose.yaml:38/53/88 有 TZ:Asia/Shanghai 但 deploy/dsh-review-worker.service 全文件无 TZ）；cache_warmup 在仓库中不存在（field-rules.ts:87-96 只有 5 个 TaskTypes，handlers.ts:369-377 只有 5 个 handler）→ 每天白排一个必然 skipped 的任务；新旧两套排程并存但键不同（新 discovery:github:${d} vs 旧 daily:${d}，discovery.ts:121-124）→ 同一天跑两次发现；缺「今天为什么没排」的可观测。

最低改造（不新增列/索引）：用 available_at 表达到点时间 + 加 15 分钟窗口 + 时区钉死 Asia/Shanghai 并给 worker.service 补 TZ + 错开备份 + 删除或合并旧排程 + cache_warmup 要么删要么补齐三处。

前提核实：proposal.md:4-5 的「ensureDailyDiscoveryTask 启动即试排 + 按天键」与仓库一致（scheduled.ts:64-129），前提成立；但 §3 的 cache_warmup 在仓库中并不存在。
