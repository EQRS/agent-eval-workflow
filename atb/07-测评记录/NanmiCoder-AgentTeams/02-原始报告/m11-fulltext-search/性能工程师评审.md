# m11-fulltext-search 性能工程师评审

> t11 · m-perf · 2026-11-17

性能工程师评审（proposal.md，48 行）：**方案不能按现状实施**，7 条意见（3×P0 / 3×P1 / 1×P2），关键结论均已用本仓库 node_modules 里的 better-sqlite3 + SQLite 3.53.4 实跑验证。

**P0-1 分词器与「中文可搜」直接冲突**：§1 的 DDL 没写 tokenize，落回 unicode61；实测 (`P2`,'普通插件','这个插件带有记忆功能') 搜「记忆」「记忆功能」均 0 命中、只有整句才命中 → 中文功能等于不可用。改分词器必须重建表（CREATE VIRTUAL TABLE 不能 ALTER），方案无迁移路径。建议 tokenize='trigram' + 1–2 字 LIKE 回退（照抄 migrations/0014_review_search.sql:5-9、src/server/modules/search/index.ts:156-186）。

**P0-2 索引行删不掉（含性能）**：§2 的 DELETE ... WHERE plugin_id=? 因 plugin_id 是 UNINDEXED 列而无索引 —— EXPLAIN 实测为 `SCAN plugin_search VIRTUAL TABLE INDEX 0:`，4000 行时 {insertMs:25, deleteMs:2052, reinsertMs:31}，单次 DELETE 0.51ms，写事务（src/server/modules/catalog/service.ts:424）被全表扫描拖死（db.ts:4-10 要求事务短小）；且内容完全相同的旧行删不干净 → 每次刷新多留一份（该表无 UNIQUE(plugin_id)）。

**P0-3 §3 查询拼接**：单引号即 `unterminated string` → 500；FTS5 语法字符（* - OR NEAR ^ :）必抛 syntax error；参照 search/index.ts:56-58 的 toFtsPhrase()、:170 与 catalog/service.ts:220-229。

**P1-4 与 <50ms 冲突**：无 LIMIT/分页/total 方案；实测 FTS 本身 10000 行 bm25 全排序仅 26ms，真正会击穿 50ms 的是 P0-1 修复引入的 `LIKE '%q%'` 全表扫描（catalog/service.ts:278-282、:788 的 COUNT(*)）；建议 page/page_size + 候选上限 500 + 唯一排序键。

**P1-5 写路径无事务**：两条独立 await，未覆盖 service.ts:512 / :516-531 / discovery.ts:270 全部写入口；建议 reindexInTx(conn,id) + rebuildIndex() 对账。

**P1-6 §4 bm25 无权重**：bm25 参数个数写错不报错（实测列多/列少均不报错），plugin_id 占第一列权重位；实测加权确实改变名次；建议 bm25(plugin_search, 0.0, 8.0, 1.0)。

**P2-7 预期不可验收**：无数据规模/P95/冷热口径；trigram 索引实测约为原文 8 倍（2000 条≈16.6MB），落在 docker/compose.yaml:41 数据卷。
