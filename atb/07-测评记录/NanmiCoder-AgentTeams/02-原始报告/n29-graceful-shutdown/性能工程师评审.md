# n29-graceful-shutdown 性能工程师评审

评审对象：atb/tasks/n29-graceful-shutdown/environment/proposal.md（25 行）
核实方式：逐行读 server.mjs / src/worker/main.ts / deploy/*.service / docker/，
并用 Node 起真实 HTTP server 实测 server.close() 与 process.exit() 的行为（探针已删，仓库零改动）。

**前提事实：本仓的优雅停机已经实现了，而且比方案更正确。**
server.mjs:98-115 有 shutdown（含 10s 兜底），src/worker/main.ts:248-255 有 stop（shouldContinue），
docker/web.Dockerfile:17-20,82 装了 tini 转发信号。方案等于重造一个更差的版本。

## 最重要 5 条

### S1【阻塞】process.exit(0) 会**直接切断进行中的请求**，与「不丢请求」的目标相反（已实测）
proposal:10-14 `server.close(); await sleep(5000); process.exit(0);`。
**实测**：起一个 800ms 才响应的 handler，200ms 时调用 close()，
300ms 时 process.exit(0) → 进程在 530ms 退出，**进行中的请求被直接切断**，客户端拿到连接重置。
关键点：`server.close(cb)` 只是停止接受**新**连接，它**不会**等待进行中的请求；
只有它的**回调**（cb）才代表“连接都关了”。方案用固定 sleep 代替回调，
等于赌“5 秒一定够”——超过 5 秒的请求一律被斩。
② 后果：慢查询、大响应、Markdown 渲染、文件上传都会在部署时被腰斩，
而这种失败用户看到的是“网络错误”，不是可理解的 503 —— 比不优雅停机更难排查。
③ 建议：**不要用 process.exit()**。照 server.mjs:104-112 的写法：
`server.close(() => { process.exitCode = 0 })` + 一个**兜底** setTimeout（该仓库用 10s）设 exitCode，
并对其 `.unref?.()`。让事件循环自然退出，而不是人为砍断。

### S2【阻塞】5s 等待 vs compose 15s 宽限期：时间预算自相矛盾，且与既有 10s 叠加会超支
proposal:12 等 5s，proposal:21 设 `stop_grace_period: 15s`。
**代码事实**：docker/compose.yaml:69 的 web 已是 `stop_grace_period: 15s`，:94 的 worker 是 30s；
而 server.mjs:109-112 已有一个 **10s** 兜底定时器。
② 后果：若在 server.mjs 里**再叠**方案的三段式（close + sleep 5s + exit），
最坏路径 = 10s（既有兜底，此时已 exitCode=0 但连接未断）+ 5s = **15s**，
正好顶满 compose 的宽限期 → Docker 在最后一刻发 **SIGKILL**，
连“兜底日志 server_shutdown_timeout”（server.mjs:110）都可能来不及 flush。
这不是理论：`proxy_read_timeout 60s`（docker/nginx/snippets/proxy-common.conf:41）意味着
nginx 允许单个上游请求挂到 60 秒，远超 15s 宽限期 —— **任何超过 15s 的请求必然被 SIGKILL 斩断**。
③ 建议：时间预算必须三级递减且写进文档：
nginx `proxy_read_timeout` ≥ 应用内部 grace ≥ 应用兜底 ≥ 0 < compose `stop_grace_period`。
当前 60s / ? / 10s / 15s 是**不自洽**的。至少把应用兜底调到 < 15s 并留余量（如 8s），
或把 stop_grace_period 提到 ≥ 应用兜底 + 缓冲。

### S3【高】方案只改 web，**worker 才是真正会丢东西的那一侧**
proposal 通篇只谈“请求”，没有提到 worker。
**代码事实**：src/worker/main.ts:211-220 的主循环靠 `shouldContinue`（:248-255 的 running 标志）退出；
:106-123 每个任务都持有**租约**并每 RENEW_INTERVAL_MS 续期（constants.ts:22 为 30s），
租约本身 **LEASE_DURATION_MS = 120s**（constants.ts:19）。
② 后果：若按方案给“所有进程”加 `process.exit(0)`，worker 会在**任务执行到一半时**被杀：
租约要到 120s 后才被 recoverExpired 回收（service.ts:116-180），
这段时间任务处于 running 且无人执行 → **任务实际卡住最多 2 分钟**；
而 worker 单进程串行执行（main.ts:199-204），一次部署会让**队列整体停顿**。
③ 建议：明确声明**不改 worker**（main.ts:248-285 已经是对的：置 running=false → 跑完当前批次 →
finally 里 heartbeat.stop() + closeDb()）。若确实要改，必须等**当前 claim 结束**而不是计时。

### S4【高】异步信号处理器里 `await` 没有任何超时保护，会静默挂死到被 SIGKILL
proposal:10 `process.on('SIGTERM', async () => {...})`。
② 后果：Node 不会等待 an async 事件处理器的 promise；
若 close 之后有未决的句柄（DB 连接、定时器、keep-alive 长连接），
`await sleep(5000)` 之后的 `process.exit(0)` 反而**掩盖**了“为什么关不掉”的原因；
反过来若 sleep 被替换成“等所有 in-flight 完成”的真实实现，一个挂住的请求就会让进程
一直等到 compose 的 15s → SIGKILL，**连日志都来不及写**（这是运维最难查的一类）。
③ 建议：关机路径必须**每条**都有上限，且上限到点要**先打日志再退**
（server.mjs:109-112 的 `writeLine('warn', 'server_shutdown_timeout')` 正是这个模式，值得保留）。

### S5【中】`server.close()` 对空闲 keep-alive 连接的真实行为：实测**不阻塞**（澄清一个常见误解）
我原本预期「nginx upstream `keepalive 16`（docker/nginx/conf.d/default.conf:21）
+ `Connection ""`（snippets/proxy-common.conf:37-38）会让空闲长连接卡住 close」，
**实测证否**：先建立 keep-alive 连接并拿到响应，再调用 `server.close()`，
回调在 **1ms** 内触发，空闲连接不阻塞关闭。
② 结论：这一点**不是**本方案的问题，但它说明“5 秒够不够”的讨论焦点放错了——
真正的长尾来自**进行中的请求**（S1/S2），不是空闲连接。
（诚实说明：这是我在评审中先假设后证否的一条，保留在此以免后来者重复踩。）
③ 建议：无需为此改 nginx；但要监控**进行中请求的 P99 耗时**
（server.mjs:66,80 已有 `slow` 标记与 `DSH_REVIEW_SLOW_REQUEST_MS`，默认 1000ms），
用它来定 grace 值，而不是拍 5 秒。

## 完整清单（其余）

### S6【中】systemd 部署没有显式 TimeoutStopSec，默认 90s 与 compose 15s 相差 6 倍
deploy/dsh-review-web.service 与 dsh-review-worker.service **都没有** `TimeoutStopSec`
（grep 无结果），systemd 默认 90s。
② 后果：同一份代码在两种部署下的停机行为完全不同——
容器里 15s 被 SIGKILL，systemd 里等 90s。排查“为什么容器部署总丢请求、裸机部署没事”会极难。
③ 建议：在 deploy/*.service 里显式写 `TimeoutStopSec=`，与 compose 的值对齐，并在文档写明“两者必须同步改”。

### S7【中】worker 走 tsx 子进程，信号可能传不到真正的 node
deploy/dsh-review-worker.service:17 `ExecStart=node .../tsx/dist/cli.mjs .../worker/main.ts`。
② 后果：tsx CLI 会再拉起子进程；systemd 的 SIGTERM 只发给 **cgroup 主进程**，
若 tsx 没有正确转发，worker 的 `process.on('SIGTERM')`（main.ts:254）**根本不会触发**，
退化成硬杀 —— 方案在这种情况下完全无效，而方案对此没有任何说明。
③ 建议：worker 改为先编译（去掉运行时 tsx），或用 `KillMode=mixed` 并验证信号确实到达；
最小验证方法：worker 日志里应出现 main.ts:252 的「收到退出信号，准备优雅退出」。

### S8【中】WAL + synchronous=FULL 下的关机写入成本未被评估
src/server/platform/db.ts:53-56：`journal_mode = WAL`、`synchronous = FULL`、`busy_timeout = 5000`。
② 后果：`synchronous=FULL` 每次提交都要 fsync，关机前若有未提交事务会等待磁盘；
`busy_timeout 5000ms` 意味着最坏情况下一次 DB 等待就吃掉 5 秒预算——
正好是方案 sleep 的长度。这是“5 秒够不够”的真实变量之一，方案没有考虑。
③ 建议：grace 预算要把 `busy_timeout` 算进去（至少 grace ≥ busy_timeout + 余量）。

### S9【低】方案未提 SIGINT / 二次信号 / 幂等
server.mjs:99-102 有 `closing` 标志做幂等（:114-115 同时监听 SIGTERM 与 SIGINT）。
方案只有 SIGTERM，且重复信号会重入（第二次 Ctrl-C 时又跑一遍 close+sleep+exit）。
建议保留关闭幂等标志，与既有实现一致。

### S10【低】缺少“停机可观测性”的验收口径
proposal:23-25 的预期只有两句定性描述（“不丢请求”“更平滑”），
没有任何可测量的判据。既有 server.mjs 已有 shutdown_start / shutdown_done / shutdown_timeout 三条日志
（:103/:105/:110），可直接作为判据来源。
建议：验收写成“部署演练中 shutdown_timeout **不出现**，且 shutdown_done 距 shutdown_start < 8s”。

## 一句结论
本仓**已经**有正确的优雅停机（server.mjs:98-115 + worker main.ts:248-285 + tini），
方案不但重复实现，而且用 `process.exit(0)` + 固定 sleep 替换了“等回调”的正确写法——
**实测会在请求进行中被直接腰斩**，与“不丢请求”的目标正好相反。
另外时间预算不自洽（nginx 60s / 兜底 10s / compose 15s / systemd 90s）且只考虑了 web，
忽略了 worker 租约（120s）才是真正会卡住任务的一侧。
建议：**不新增代码**，改为把既有实现的时间参数对齐并补上可观测的验收口径。
