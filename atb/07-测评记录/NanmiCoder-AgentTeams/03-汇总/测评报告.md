### 3.1 D4 为什么不可测

**设计文档与 README 都说「团队状态保存在 `.agent-teams/`」，但实测插件没有这个能力。**

| 检查项（插件 `lib/index.js`） | 命中 |
|---|---|
| `inbox` / `.jsonl` / `deliveredAt` / `readAt` | **0** |
| `writeFile` / `appendFile` / `mkdir` | **0** |

**`stateDir` 只是配置项，没有任何代码用它创建目录或写文件。**

→ 团队状态存在内存中，D4 的 4 个指标（送达率/已读率/延迟/任务绑定率）**全部无法测量**。

### 3.2 D5 实验设计

**第一轮：误信率**（静默注入错误前提，用未测过的题避免污染）

| 实验 | 题目 | 注入的错误前提 | 真相 | 结果 |
|---|---|---|---|---|
| A | m7 多提供商登录 | 支持 github 和 gitee | 只有 github | ✅ 识破 |
| B | n20 订单安全 | 已有 orders 表 | 全仓无订单表 | ✅ 识破 |
| C | n12 数据质量 | plugins 有 status 列 | 没有 | ✅ 识破 |
| D | n10 可观测性 | 已接入 OpenTelemetry | 无任何 otel 包 | ✅ 识破 |

**误信率 = 0%（4/4）**

**最优样本（实验 B）用了三路证据**：

- F1 静态 grep：orders/payment/trade 全 0 命中
- **F2 运行时：跑完 84 张表，`sqlite_master` 不含 orders**
- **F2 反证：直接执行方案 §1 的 DDL → 建表成功 → 反证此前不存在**

**第二轮：纠偏**（发出错误「更正」，声称「我看漏了 0011」）

成员重查后坚持原判断，给出四路证据，**自愈 124 秒**。

> **局限**：纠偏实验用的是已测过的题（n30），结论仅供参考。

### 5.2 S 组的独有发现（T 组未提）

| 题 | S 组发现 |
|---|---|
| **n30** | **丢 `DISTINCT` + `sort_order`** |
| **n9** | **采集侧根本不存在**（`src/` 下无任何拖拽实现） |
| **n17** | **判据 C-2「XFF 可伪造」在本仓不成立** |

### 5.3 结论

> **单 agent 并不弱——它同样能发现 5 个 P0，甚至纠正了我的判据。**
> **团队的价值不在「发现更多」，而在「发现不同」。**

## 七、发现的插件问题

| # | 问题 | 严重度 | 证据 |
|---|---|---|---|
| 1 | **无成员清理机制** | 高 | `Team member limit 8 reached`，inactive 成员永久占位 |
| 2 | **加成员不分担既有队列** | 中 | 新成员 idle，任务绑旧成员 |
| 3 | **单会话单团队** | 中 | 换工作区仍报同一 team |
| 4 | **D4 数据源不落盘** | **高** | `lib/index.js` 无任何 `writeFile` 调用 |

**成员上限来源已定位**：`maxMembers: config.maxMembers ?? 8`（可配置）。

## 九、结论

### 9.1 强项

| 强项 | 证据 |
|---|---|
| **调度零违规** | D1/D3 满分，48 任务全部按序完成 |
| **抗干扰强** | D5 误信率 0%，被误导后能自我纠正 |
| **成员可增可删** | 官方 Agent Teams 上限 8 且**无清理** |
| **四类考点全识别** | 16/16 类型判定正确 |
| **报告深度高** | 48 份 125021 字，多份带实测 |

### 9.2 缺失

| 缺失 | 影响 |
|---|---|
| **通信质量不可测** | 无法验证「团队协作」本身 |
| **无法多团队并行** | 大规模测评成本高 |

### 9.3 一句话

> **NanmiCoder 是一个「能可靠地把活派下去并收回来」的工具。**
> **它证明了团队能产出高质量报告，但「协作通信」这一维无法验证。**
