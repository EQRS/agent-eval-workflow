## 三、核心发现

### 3.1 T-安全的独有深度

**它挖出了我判据里没有的第 2 条**：

> **「转让归属 = 转让『开发者』身份门槛」**
> 依据：`roles/service.ts:443-453` 用 `COUNT(*) status='verified'` 判资格
> 后果：**任何人推动一次「归属纠正」就顺带拿到开发者身份；恶意者可用争议把作者挤下去**

**这是 L4 系统性关联**——单看 `plugin_ownerships` 看不出来。

### 3.2 T-性能的独有贡献

**它给出了两个可选方案（A 保留新表 / B 扩 status 字段）**，并明确指出：

> **方案 B「不建表，把 `plugin_ownerships.status` 扩成 disputed」，性能上严格优于 A**
> 复用已有队列索引与 reviewClaim 事务骨架，代价是一次表重建窗口

**这是「④ 倒退」的反向应用——它找出了更优的实现路径。**

### 3.3 T-SRE 的 6 条阻断

| # | 阻断项 |
|---|---|
| S1 | 建表无可维护性（无 CHECK / 无终态 / 无 reviewer） |
| S2 | 无去重键，表按 用户×插件 膨胀 |
| S3 | **`uq_plugin_ownerships_verified` 会落 500**（`ownership.ts:239-249` 记录过同款事故） |
| S4 | 改归属零审计 |
| S5 | **无回滚口径**：migrate 单向且是启动前置，每日 03:00 单恢复点最老 21 小时 |
| S6 | 开放入口无频控 |

## 七、结论

### 7.1 NanmiCoder 强在哪

| 强项 | 证据 |
|---|---|
| **成员可增可删** | 官方上限 8 且无清理，NanmiCoder 可 `remove_member` 释放 |
| **工具面更完整** | 14 vs 9 个工具 |
| **报告更深** | 38 条 vs 26 条；T-安全挖出「开发者身份耦合」 |
| **有防误操作** | 重复建团队会被拒 |
| **状态落盘** | `.agent-teams/` 可持久化 |

### 7.2 两者共同的问题

| 问题 | 说明 |
|---|---|
| **成员名字与任务不符** | 复用成员时无法改名，`list_agents` 显示混乱 |
| **声称落盘但未落盘** | 需 Lead 逐条核实，不能轻信「已完成」 |
| **深度依赖专业身份** | 团队本身不产生专业视角，是 `executionPrompt` 给的 |

### 7.3 选型建议

| 场景 | 推荐 |
|---|---|
| **长会话 / 多轮测评** | **NanmiCoder**（官方名额会耗尽） |
| **单次任务** | 两者皆可 |
| **需要精细编排** | **NanmiCoder**（有 approve/edit_plan/amend_task） |
