# 性能评审 · N-7《E2E 测试覆盖率从 40% 提升到 85%》

**评审身份**：性能工程师（关注 E2E 执行时间、CI 成本、flake 的真实代价）
**评审对象**：`tasks/n7-test-design/environment/proposal.md`
**评审基线**：本仓库实测（Node 24 / 本地 Windows）。未改任何代码。

---

## 0. 一句话结论

**方案在性能维度上不动。** 它既没有定量目标，也没有对现有 CI 预算取数；而它提出的三条措施（按路由补 200 断言、c8 卡 85%、失败重试 3 次）**每一条都会单方面抬高 CI 时间与 flake 处置成本，且全部不设上限**。按仓库现状推算，"补到 85%"若照字面执行，CI 测试环节会从当前的分钟级膨胀到**小时级**，重试再把它乘以最高 4 倍。

## 1. 实测基线（先取数，再谈方案）

我直接在本仓库跑了真实计时，作为所有推论的锚点（第 3 条 · 白箱：不猜测）。

| 指标 | 实测值 | 证据位置 |
|---|---|---|
| 全量测试 wall-clock | **289.3 s**（Test Files 91 / Tests 1060 全绿，vitest 自报 Duration 288.11 s） | `npm test`，本地串行 |
| 最慢单文件 | `tests/tasks.test.ts` 16.9 s（单独跑 18.1 s） | 同上 |
| 单个"建立已迁移测试库"的成本 | **254–284 ms/次**（3 次采样），88 张表 + 33 个触发器 + 120 个索引 | `.tmp` 临时脚本实测 `createTestDb()` |
| `createTestDb()` 调用点 | **164 处**，分布在 64 个测试文件 | `tests/` 全量 grep |
| 其中"每用例新建库"的坏味道 | `tests/plugin-discovery.test.ts` ×17、`notifications-settings.test.ts` ×14、`plugin-categories.test.ts` ×9 | 同上 |
| 现有 E2E 层 | `tests/e2e-slice.test.ts` 单文件 **4.0 s wall**（6 用例，进程内直调 service，不起 HTTP） | 单独计时 |
| 真正"起进程+HTTP"的 E2E | `scripts/acceptance-*.mjs` 7 个 shell 脚本，**不在 `npm test` 里**，依赖 `curl.exe` + 常驻 dev server（3100）+ 真实 GitHub API | `scripts/acceptance-e2e-chain.mjs:12-25` |

| CI 现状 | `npm ci` → typecheck → `npm test` → 用词检查，**无覆盖率、无重试、无并行** | `.github/workflows/ci.yml:25-34` |

## 2. 逐条问题清单

### P-1【致命】§1「每个 API 路由补一个 E2E + 断言 200」= 把测试数量挂到路由数量上，成本线性失控

**问题部分**：`proposal.md:9`「为每个 API 路由补充一个 E2E 用例」。

**量级测算（按仓库真实路由数）**：`src/app/api` 下 **100 个 `route.ts`、137 个 handler**（GET 52 / POST 58 / PATCH 9 / PUT 4 / DELETE 14）。真正的 E2E 必须走 HTTP，即：
- **起进程**：每个用例要一个 dev server 或 `next start`，冷启动 Next 16 在本机是**秒级到十秒级**；
- **跑迁移建库**：每用例一次 `createTestDb()` = **254 ms** 起（实测），100 个路由 = **25 s** 纯建库，还没算业务；
- **写路径用例无法共用状态**：POST/PATCH/DELETE 共 **85 个** handler，每个都要独立准备数据（用户/插件/评测前置行），否则就是互相污染 —— 这正是仓库现在用"每文件独立临时库 + 串行"来规避的（`vitest.config.ts:8-11` 的注释就是为此写的）。

**后果**：在 `maxWorkers: 1` 下这些成本**全部串行相加**，没有任何并行摊销。保守估计按现有 `e2e-slice` 单用例 0.67 s 的进程内价格算，100 个路由 E2E ≈ **67 s 起**；一旦真要过 HTTP（起服务 + 真实鉴权 + cookie jar），单价会跳到**每个用例 1–3 s**，即 **100–300 s 增量**，直接把 CI 推过 5 分钟，且这还只是"断言 200"那么薄的用例。

**建议**：
1. 先给 CI 定预算（如"测试阶段 wall-clock ≤ 5 min"），再倒推能加多少路由 E2E —— **顺序不能反**；
2. 路由层不要一个路由一个用例：用**参数化表驱动**（一张路由表 + 一个循环），把"起服务"摊销到一次；
3. 只对**有业务状态迁移**的路由（约 20 个）写 HTTP E2E，其余用现有 service 级用例覆盖；
4. 提升覆盖率前先把 `maxWorkers` 从 1 放开到 `min(4, cpu)`（`vitest.config.ts:11`）。**这是当前最便宜的收益**：289 s ÷ 4 ≈ 70–90 s，且不新增任何用例。放开的前提是修掉依赖真实时间的用例（见 P-3）。

### P-2【严重】§2「c8 统计 + CI 卡 85%」：工具选错 + 口径不明 + 默认行为会再拖慢一轮

**问题部分**：`proposal.md:12`。

**事实核查**：
- **c8 不在依赖里**（`package.json` 无，`node_modules` 无）。而且本仓库的测试是 **vitest 跑 TS/tsx 源码**，c8 是 V8 原生覆盖 —— 对 Next 的 TS + jsx 转译链路会**丢失源码映射精度**，实际口径与 vitest 自己的 V8/istanbul provider 不一致。要么引入 `@vitest/coverage-v8`，要么引入 c8 并额外处理 sourcemap，**两条路都要动 lockfile + CI 镜像层，是真实的安装与冷启动成本**。
- **"覆盖率"没定义统计面**：是 `src/**` 全部，还是排除 `src/app/**` 的页面/布局？本仓 100 个路由 + 大量 React 组件，若纳入 `src/app`，85% 这个数**在现有测试结构下几乎不可能达到**（现有 91 个测试文件以 server module 为主，`.tsx` 只有 9 个）。也就是说 §1 的"补路由用例"其实是被 §2 的阈值逼出来的 —— **一个拍脑袋的阈值，派生出一笔没有预算的执行成本**。
- **阈值卡在 CI 而不设白名单/排除项**：Next 的 `app/`、生成的 `.next/`、`server.mjs` 都会被算进去，第一次跑一定红，然后团队会去"凑数"而不是"补质量"。
- **性能代价**：V8 coverage 模式本身会让全量跑变慢（`NODE_V8_COVERAGE` 常驻采样 + 结束时一次性 dump + 生成 report，业界普遍 +20%~+50%）。按实测 289 s 底数，**至少再 +60~145 s**，且这是**每次 CI 都要付**的固定税。

**建议**：
1. 用 `@vitest/coverage-v8`（与测试运行器同源，口径一致），**不要引 c8**；
2. 覆盖率**只在 `main` 分支或 `push` 时跑并归档，PR 上只跑一个增量阈值**，否则每个 PR 都付这 145 s；
3. 阈值前先设 `include`/`exclude` 白名单，并把 85% 拆成**分层阈值**（platform/core 模块 90%，`app/` 路由 60%），别用一个数统管所有层；
4. 更重要的是：**覆盖率不能替代性能预算**。建议同时加"测试阶段 wall-clock 不得超过 N 分钟"的 CI 门禁，否则团队会为了覆盖率无限加测试、无人负责时间。

### P-3【严重】§3「失败自动重试 3 次」：这是把 CI 成本 ×4，并把 flake 的真实代价转移给后来的每一个人

**问题部分**：`proposal.md:15`。

**成本模型（性能视角的硬账）**：
- flaky 率 p 的单次运行，重试 3 次的总成本期望 = `C × (1 + p + p² + p³)`。**最坏情形直接 4×**。以当前 289 s 的全量套件为底，**一次全红的 CI 会被拖成近 20 分钟**，而团队看到的日志是"最终绿了"。
- 更糟的是**重试粒度**：vitest 的 `retry` 默认按**单个用例**重试，但本仓库的成本主体是**文件级的建库与迁移**（254 ms/次 × 164 处）。file 级失败重试意味着**整个文件重跑**，一次重试 = 把一个 16.9 s 的 `tasks.test.ts` 整个再跑一遍。如果 CI 用 `--retry=3` 且按文件失败，**重试成本 ≈ 全量成本**，而不是"只补那一条"。
- **重试不改变 flake 的存量，只改变它的可观测性**。这是性能工程师最反对的一点：**被掩盖的 flake 会在最贵的时刻重新出现**——例如发版前夜、高并发验收、或者（本仓尤其相关）生产用的 SQLite `synchronous=FULL` + WAL 与测试环境完全不同的时刻。

**现有 flake 存量（真实存在，且重试会永久掩盖它们）**：
- `tests/forum-posts.test.ts:330,337,348`：用 `setTimeout(r, 5)` 制造"时间先后"，靠 5 ms 的墙钟间隔让 `created_at` 排到顺序。**在 CI 高负载容器里 5 ms 可能被调度吃掉，导致同毫秒、排序断言翻转**——这是教科书级的 flake，且**重试 3 次后它会 99% 变绿，永远不会有人来修**。
- `tests/forum-posts.test.ts` 的断言依赖 `Date.now()` 单调，`notifications-settings.test.ts:153` 用 `Date.now() + 1000` 做未来时刻——同类问题。
- `scripts/acceptance-e2e-chain.mjs` 的收录步骤**打真实 GitHub API 且匿名只有 60 次/小时**（脚本 60-70 行注释已明写），还有真实 dev server 端口冲突风险 —— 这类"E2E"若被纳入 CI 并配重试，就是一个**会自我放大的成本黑洞**：限流 → 失败 → 重试 → 再消耗配额 → 更快限流。

**建议**：
1. **重试只能作为观测手段，不能作为通过手段**：CI 里跑"重试但记录重试次数"，**重试过的用例单独出一份 flaky 清单并在 24 h 内必查**；重试后通过的用例**不计入覆盖率**（否则覆盖率被 flaky 虚高）；
2. 先修存量：把 `setTimeout(5)` 换成注入 clock 或直接断言 id 单调（`newId()` 是 UUIDv7，天然单调，**根本不需要 sleep**）；
3. 重试上限设 1 次而非 3 次，并对"重试率 >2%"的用例做门禁；
4. 任何打外网的验收脚本**不得进 CI 主链路**（现状是对的，要守住）。

### P-4【中】没提并行化 = 放掉了 3–4 倍的时间红利，且方案里的所有措施都建立在"串行"这个最差基线上

**问题部分**：整份方案对 `vitest.config.ts:11` 的 `maxWorkers: 1` 只字未提。

**后果**：当前 91 个文件 1060 用例是**单 worker 排队**跑的（实测 tests 占比 92%、import 4%、transform 2% —— 说明时间几乎全花在用例体内，也就是建库+业务，**并行化的收益是实打实的**）。不去放开并行，却去加 100 个路由 E2E，等于**在一条单车道高速上继续加车**。放开并行后，CI 仍有风险项：`createTestDb()` 用 `mkdtempSync` 是安全的（每处独立目录），但 `scripts` 里对 `.data/app.sqlite` 的单例（`tests/support/db.ts` 之外，`acceptance-e2e-chain.mjs:55` 直接开 `.data/app.sqlite`）必须排除在并行之外。

**建议**：先做"并行 + 修 flake 存量"，再谈加用例。这一项单独就能把 289 s 压到 ~80 s，**是方案里性价比最高、但完全缺失的一步**。

---

### P-5【中】没区分"进程内 E2E"与"真 HTTP E2E"，成本差一到两个数量级

**问题部分**：`proposal.md` 全文用"E2E"一个词。

**证据**：本仓已经有两层互不相同的"E2E"：
- `tests/e2e-slice.test.ts`：进程内直调 service，**4.0 s / 6 用例**，进 `npm test`；
- `scripts/acceptance-*.mjs`：真起 server + `curl.exe` + 真 GitHub，**不进 `npm test`**。

方案说"补 E2E"时**没有说清是哪一层**，而这决定了成本是"每条 0.67 s" 还是 "每条 1–3 s + 稳定性风险"。按 40%→85% 的覆盖率缺口倒推，若缺口主要落在 `src/app/api/**`（100 个路由），**必须走 HTTP 层** —— 那就避不开 dev server 启动和端口管理，成本量级完全不同。

**建议**：方案里必须明确写死"哪一层 E2E"，并把 `scripts/acceptance-*` 这类真外网脚本与 CI 用例**在目录和命令上物理分开**，避免日后被合并进 `npm test`。

## 3. 性能视角的总账（把方案三项措施的钱算给团队看）

| 项 | 当前 | 方案照做后（保守估计） |
|---|---|---|
| 单文件建库成本 | 254 ms × 164 | 若每路由一用例 → 再 +100 次 ≈ **+25 s** |
| HTTP E2E 起服务 | 0 | 100 个用例，每次 1–3 s → **+100~300 s** |
| 覆盖率（V8 模式） | 0 | 全量 ×1.2~1.5 → **+60~145 s** |
| `maxWorkers` | 1（未改） | 仍为 1（方案未提） |
| **单次 CI 测试阶段** | **289 s** | **~475–760 s（8–13 分钟）** |
| 失败重试 3 次的最坏路径 | 289 s | **×4 ≈ 30–50 分钟** |
| flaky 可观测性 | 直接红 | **被重试掩盖，债务累积** |

## 4. 我建议的替换路线（性能工程师版）

1. **先取数**：把实测基线写进 CI（`ci.yml:3` 的"35 秒"改为实测值），并加一条"测试阶段 wall-clock"输出；
2. **先并行**：`maxWorkers` 放开到 4，配合修掉 `setTimeout(5)` 类用例（`forum-posts.test.ts:330/337/348`）；预期 **289 s → 80 s**；
3. **再定预算**：给出"测试阶段 ≤ 3 min"的硬门禁，作为加用例的**前置约束**；
4. **角色化用例**：路由 E2E 只覆盖有状态迁移的 ~20 条，其余用表驱动参数化，起服务只一次；
5. **覆盖率**：`@vitest/coverage-v8` + 分层阈值 + 只在 main 跑；
6. **重试**：上限 1 次，重试过的用例**必须出 flaky 报告并计入技术债**，不允许静默变绿。

## 5. 我的最后一句（与其它角色可能重复的地方我不避讳，但只从我的角度下判断）

**这份方案把"覆盖率"当成了唯一验收物，而把"运行这份覆盖率要花多少时间和多少人的排查成本"当成了免费的。** 在性能工程里，测试套件是**每个 PR 都要付一次**的税：289 s 的底子已经存在（且被误记为 35 s），方案的三条措施没有一条给这笔税设上限。**先并行、先修 flake、先立预算，再谈 85%** —— 顺序反了，85% 买到的不是稳定性，是一个所有人都开始绕过的红灯。
