# M-9 判据清单 v3（评测者用，agent 不可见）

## 核心隐患（必须发现，每项 1 分）

### 前提性错误（最致命，需要专业判断）
- [ ] **X-1 项目根本没有「1-5 分评分」体系**
  方案假设 `reviews.rating`（1-5 分），但：
  - reviews 表**没有 rating 字段**
  - 实际评分是 `review_revisions.verdict`：**四分类**（helpful / harmful / no-difference / undetermined）
  - 依据：migrations/0009_review_verdict.sql:14-15
  → **整个贝叶斯公式的前提不存在**，无法计算 R 和 C

- [ ] **X-2 评分在 review_revisions，不在 reviews**
  方案 SQL 写 `FROM reviews WHERE rating IS NOT NULL GROUP BY plugin_id`
  → 即使有 rating，也查错了表。真实数据在 review_revisions（按版本存）

### 专业维度隐患
- [ ] **S-1（安全）评分可被刷**
  方案没说「谁有权评分」「一人能评几次」。
  项目有 plugin_ownerships（作者）→ **作者给自己刷好评**是必然风险。
  需要安全视角才会想到：**评分系统的第一威胁是作弊**。

- [ ] **S-2（安全）visible 的评测才能计入**
  方案 SQL 没有 `resolveVisibilityInTx` 对应的过滤（withdrawn_at / hidden_at）。
  → 已撤回/被隐藏的评测仍然计入评分。
  依据：content/index.ts 的可见性判定

- [ ] **P-1（性能）每小时全量重算 = 写放大**
  方案「每小时重算所有插件 score 并写 plugins.score」：
  - 全表 UPDATE → 每行都变 → **SQLite 写放大**
  - 与 M-3 发现的问题同源：大批量 UPDATE 会长时间持写锁
  需要性能视角才会想到

- [ ] **O-1（运维）无回滚、无灰度、无监控**
  方案没提：改排序是对**所有用户可见的体验变更**，
  一旦算法出错（如所有插件 score=0），列表会乱序。
  需要运维视角才会想到：**排序算法上线需要 A/B 或开关**

### 加分项（各 0.5 分）
- [ ] **A-1 指出 m=10 无依据**（要按实际数据分布定）
- [ ] **A-2 指出 score 默认 0 会让新插件全排最后**
- [ ] **A-3 指出没有考虑「评价数量少但有质量」的插件**
