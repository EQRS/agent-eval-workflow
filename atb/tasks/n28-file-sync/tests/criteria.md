## 前提核实（基础项，0.5 分）

- [ ] **方案假设的东西在本仓库是否真实存在？**
  核对表/列/接口/依赖是否在 `migrations/`、`src/`、`package.json` 中真实存在。
  **注意区分**：方案声明要新建的表（有 CREATE TABLE / ALTER / 明确说「接入」某依赖）属合理；
  引用了不存在的对象且没声明 → 前提不成立。

## 必须发现（每项 1 分）

### 跨系统
- [ ] **C-1 上传是串行的，任一节点慢会拖住整个发布**
  §1 的 `for (const node of cdnNodes) await upload(...)`——
  串行 await，N 个节点耗时累加。一个节点超时会阻塞整个发布流程。
  且没有超时设置，节点不可达时会长时间挂住。

- [ ] **C-2 部分成功时数据库状态与服务端不一致**
  若 3 个节点成功、1 个失败，§3 仍会更新 download_url。
  **用户可能被重定向到没有文件的节点**，得到 404。

- [ ] **C-3 没有回滚：旧文件是否删除、旧 URL 是否失效**
  版本更新后，旧包应该保留还是删除？已分发的 URL 会不会失效？
  方案完全没提生命周期管理。

### 对抗性
- [ ] **S-1 上传失败后没有校验，文件可能被静默截断**
  §1 的 upload 没有说是否校验上传后的完整性（sha256）。
  断网/超时可能上传半截文件，DB 却标记成功。

### 跨系统（真实约束）
- [ ] **C-4 项目的媒体文件走 FileStore，不在数据库中**
  `src/server/platform/file-store.ts` 有既定的落盘纪律
  （服务端生成 key、临时文件+rename、回读校验）。
  方案的多节点同步需要接这套，而不是自己 upload。

- [ ] **C-5 SQLite 是单文件，多节点数据库不一致**
  若多地域各有一份数据库，**无法用 SQLite 同步**（官方明确不支持网络文件系统）。
  方案只同步了文件，数据库仍是单点。
