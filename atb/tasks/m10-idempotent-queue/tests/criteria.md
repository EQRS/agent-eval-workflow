## 必须发现（每项 1 分）

### 安全维度
- [ ] **S-1 手动触发的 dedup key 冲突**
  §3 说「用 discoveryDedupKey(source, ymd(now))，若当天已有任务，enqueue 会返回已存在」。
  **这意味着：当天自动跑过之后，管理员再也无法手动触发。**
  手动触发的语义应该是「我要现在再跑一次」，而不是「没跑过才跑」。
  → 应改用独立 key（如 `manual:${source}:${timestamp}`）或 allowDuplicate 参数。

- [ ] **S-2 source 未白名单校验**
  §3 的 `body: { source: "github" }` 直接来自请求体，**方案没说校验 source 是否在白名单内**。
  攻击者传 `source: "../../etc"` 或任意字符串，会让 dedup key 被污染。
  → 应有 `const VALID_SOURCES = ['github','gitee'] as const` 并校验。

### 运维维度
- [ ] **O-1 按 source 拆分 = API 配额被瓜分**
  §2「每个数据源每天一个任务」看似合理，但项目现有实现有限制：
  `deploy/discovery-drip.sh:2-3` 原文「unauth 时每小时只有 ~60 次核心配额，一轮就吃满」。
  拆分后 N 个 source = N 倍配额消耗 → **直接击穿 60/h 触发 429**。
  → 应共享同一个配额预算，而非按 source 各跑一次。

- [ ] **O-2 无积压/失败监控**
  方案零监控。发现任务失败（限流、网络）不可见。

### 性能维度
- [ ] **P-1 无任务类型的去重键设计说明**
  现有 `UNIQUE(task_type, deduplication_key)` 是全类型共享的（0001:369）。
  方案改了 key 格式但没说**旧格式的 key 会怎样**——历史任务与新任务不会冲突，
  但会导致同一天既有旧的 `daily:` 又有新的 `discovery:` 两批任务。

- [ ] **P-2 索引未评估**
  改 dedup key 格式不影响索引，但方案没说明。
