## 必须发现（每项 1 分）

### 运维维度
- [ ] **O-1 补跑风暴（最严重）**
  §2 的 `if (now >= target)` 判断：若 worker 在 12:00 启动，
  会**立即补跑 03:00 与 04:00 两个任务**。
  更糟：若 worker 停机一周后启动，会**补跑 7 天的任务**（每次 tick 都尝试）。
  「按天 dedup key」能防重复，但**防不住「补跑过期任务」**。
  → 应加容差窗口（如 target 后 30 分钟内才算有效，过期跳过）。

- [ ] **O-2 时区语义未定义**
  §1 的 `ymd(now)` 与 §2 的 `atTime(now, s.at)` **没说用哪个时区**。
  项目 db.ts 存的是 UTC 毫秒时间戳。若 atTime 用服务器本地时区，
  跨时区部署（web 在 UTC、worker 在 CST）会错位 8 小时。

- [ ] **O-3 新增 task_type 需要重建表**
  §3「cache_warmup 需要新的 task_type（迁移里放开 CHECK）」——
  SQLite 改 CHECK **必须重建表**（0007 就是这样做的），且 background_tasks
  被多表外键引用，重建要 `PRAGMA foreign_keys=OFF`。
  方案用一句话带过，低估了工作量。

### 性能维度
- [ ] **P-1 tick 空转成本**
  §2 的 tick 每轮都跑（复用主循环节拍），即使没有任务到期也查一次。
  方案没说节拍间隔。若沿用 IDLE_SLEEP_MS=10s，每天 8640 次空转。

- [ ] **P-2 scheduled_at 索引的实效**
  §1 建了 `idx_tasks_scheduled(processing_state, scheduled_at, id)`，
  但方案**根本没在查询里用 scheduled_at** —— tick 是遍历 schedules 数组算 target，
  不是查表。**这个索引是多余的**。

### 安全维度
- [ ] **S-1 schedules 是硬编码常量**
  §2 的 schedules 数组是代码常量，看似安全。
  但方案没说「是否允许动态配置」——若将来做成可配置，就是任务注入面。
