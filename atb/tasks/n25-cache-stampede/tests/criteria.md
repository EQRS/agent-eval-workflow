## 前提核实（基础项，0.5 分）

- [ ] **方案假设的东西在本仓库是否真实存在？**
  核对表/列/接口/依赖是否在 `migrations/`、`src/`、`package.json` 中真实存在。
  **注意区分**：方案声明要新建的表（有 CREATE TABLE / ALTER / 明确说「接入」某依赖）属合理；
  引用了不存在的对象且没声明 → 前提不成立。

## 必须发现（每项 1 分）

### 跨系统
- [ ] **P-1 预热数据与用户可见数据口径不一致**
  §1 直接查 `plugins` 表——但插件列表页展示的是
  `getPlugin` 聚合后的 PluginView（含评测数、评分、可见性过滤）。
  **预热的是裸表数据，与页面实际要的不一样**，起不到预热效果。

- [ ] **C-1 没有考虑 visibility：已撤回/隐藏的插件会被预热进内存**
  `plugins` 表没有可见性列（可见性在 content_entities），
  直接 SELECT 会把所有插件（包括不可见的）放进内存，
  若后续代码不加过滤直接用，等于**绕过可见性控制**。

- [ ] **C-2 global 变量在 Next 生产构建下不保证共享**
  方案用 `global.__hotPlugins`——Next 的 server component 与 route handler
  可能运行在不同模块实例中。且项目用自建 server.mjs，
  global 的作用域需要核实，方案假设它全局有效但没有验证。

### 性能
- [ ] **P-2 每小时全量重载会造成周期性卡顿**
  §3「每小时重新加载一次」——重载瞬间要把新数据全部载入，
  期间内存占用翻倍，且**加载是同步的**（better-sqlite3），会阻塞事件循环。

- [ ] **P-3 没有解决真正的首屏慢因**
  项目所有页面都是 `force-dynamic`，首屏慢的真正原因可能是
  `currentContext` 的两次查询 + 各页面自己的查询，
  **预热一个插件列表解决不了**。方案没有先测量就下结论。
