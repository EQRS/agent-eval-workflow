## 前提核实（基础项，0.5 分）

- [ ] **方案假设的东西在本仓库是否真实存在？**
  核对表/列/接口/依赖是否在 `migrations/`、`src/`、`package.json` 中真实存在。
  **注意区分**：方案声明要新建的表（有 CREATE TABLE / ALTER / 明确说「接入」某依赖）属合理；
  引用了不存在的对象且没声明 → 前提不成立。

## 必须发现（每项 1 分）

### 跨系统交互
- [ ] **C-1 迁移期新用户不在 user_profiles**
  §3 说「迁移完成前代码同时写两张表」，但**没说新注册用户怎么处理**。
  若新用户只写 users 不写 user_profiles，迁移后查 profile 会找不到。

- [ ] **C-2 双写的顺序与外键**
  user_profiles.user_id REFERENCES users(id)。
  若先插 profile 再插 user，外键失败；先删 user 再删 profile，也会失败。方案没说顺序。

### 域外知识
- [ ] **S-1 SQLite 不支持 DROP COLUMN（旧版本）**
  项目用的 SQLite 3.53.4 支持 DROP COLUMN，但**必须先确认没有索引/触发器/视图引用该列**。
  方案直接 DROP，没提检查。
  （注：项目里 users 表的 avatar_kind 等字段实际不存在，是方案臆造的）

- [ ] **S-2 无跨表事务保障**
  §4「回滚：把数据拷回 user_profiles」——
  但迁移和回滚都跨两张表，**SQLite 单库可以事务，但 DROP COLUMN 不可逆**。
  DROP 之后无法「拷回」，因为源列已经没了。方案的回滚思路是错的。

### 长链路依赖
- [ ] **O-1 迁移期读路径未定义**
  §3 只说双写。**读**怎么办？读 users 还是 user_profiles？
  若读 users，DROP COLUMN 后会失败；若读 profile，迁移期数据不全。
