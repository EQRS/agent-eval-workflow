## 必须发现（每项 1 分）

### 对抗性
- [ ] **S-1 用户可配置任意 URL，构成完整 SSRF**
  §1 的 `url` 由用户填，§2 直接 fetch——
  攻击者填 `http://127.0.0.1:6379/` 或 `http://169.254.169.254/`，
  **服务器会替攻击者访问内网**。这是教科书级 SSRF。
  必须做：协议白名单（仅 https）、内网地址黑名单、DNS 重绑定防护。

- [ ] **S-2 secret 字段完全没用上，接收方无法验证来源**
  §1 存了 `secret`，但 §2 的 fetch **没有用它签名**。
  接收方无法区分「真的来自本站」和「伪造的」。Webhook 的标准做法是
  HMAC 签名放在 `X-Signature` 头。

- [ ] **S-3 重试无退避、无死信，且同步 await 会阻塞**
  §3「失败重试 3 次」——如果是立刻重试，等于 3 倍流量打对方；
  如果是同步 await，**推送慢会拖住插件更新的请求**。
  且 3 次都失败后事件永久丢失，没有死信队列。

### 跨系统
- [ ] **C-1 项目已有任务队列，应该用它做异步与重试**
  `background_tasks` 已有租约、重试预算（[30s,120s]×3）、
  recoverExpired。方案手写重试绕开了这套。

- [ ] **C-2 没有考虑接收方不可达时的失败处理**
  大量订阅者失效后，每次推送都超时，会拖慢整个更新流程。
  需要一个「自动禁用长期失败订阅」的机制。
