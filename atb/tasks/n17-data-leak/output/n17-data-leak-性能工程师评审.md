# N17「基于访问日志的用户行为分析」方案 · 性能工程师评审

> 评审对象：`atb/tasks/n17-data-leak/environment/proposal.md`（38 行）
> 评审身份：性能工程师（容量 / 热路径 / 采样率 / 查询代价）
> 事实基线：`server.mjs`、`src/server/platform/{log,request-id,rate-limit}.ts`、`src/instrumentation-node.ts`、`src/app/plugins/page.tsx`、`docker/compose.yaml`、`docker/daemon.json`、`deploy/dsh-review-web.service`、`scripts/grant-admin.mjs`、`src/server/modules/search/index.ts`

## 0. 结论

**性能面判定：不可接受，按现方案实施会同时打坏三件事。**

1. **写路径**：在每个 route handler 出口补记日志，等于把「一行日志」放进**每一个已经做了数据库工作的请求热路径**，且与本仓最贵的几个页面（同步 SQLite 查询）叠加。
2. **容量面**：第 37 行「数据量大但都是文本，成本可控」**是错的**——本仓两套部署的日志磁盘配额分别是 **30 MB（compose）** 和「按分区 10% + 限流」（systemd），90 天留存从基础设施层面根本不成立；更糟的是日志写满会连带把 web 判成 503 并触发重启循环，同时把排障窗口挤掉。
3. **分析面**：第 26–33 行「按 user_id 分组」的全量扫描，在 90 天规模下每次都要把当天的 IO/CPU 打满，而 `better-sqlite3` 是同步驱动，IO 竞争会直接传导成接口延迟。

**全部结论都可以用「先测算、后定参数」修好——但方案现在一个数字都没有。**

## 1. 写路径位置错了：handler 出口补记会把 I/O 放进最贵的请求 —— 方案第 10–24 行

**① 问题**：方案说「在各 API route 的出口处补记一条 `log.info('http_request', ...)`」。这意味着：
- 每个 handler 多一次**同步的 `JSON.stringify` + 一次 `process.stdout.write`**（`log.ts:12-21`）；
- 本仓的页面请求本身就串着多条同步 SQLite 查询，例如 `src/app/plugins/page.tsx:175-194` 一次渲染里连着 `listPlugins` → `listCategories` → `featuredCountsForPlugins` → 可能再来一次 `listPlugins`（:194）。此时 Node 事件循环已经被同步查询占满，再插一段序列化+写盘，延迟直接叠加而非并行。

**② 后果**：
- 页面与接口的 **p95 抬升**发生在最忙的时刻（`server.mjs:18,31` 的慢请求阈值默认 1000 ms，一旦日志让一批请求越过阈值，它们全部从 `info` 升为 `warn` 落 stderr，`server.mjs:41` —— 同一个慢事件被记录两次，还会污染"错误/慢请求"这个唯一的排障信号）。
- `server.mjs:62-82` **已经**在 `res.on('finish')` 里按请求各打一条 `message:'http_request'`。方案再来一条同名同 `request_id` 的行 → **同一请求两行**，日志量翻倍、grep 干扰翻倍，而两行的字段来源不同（一个来自 server 层，一个来自 handler），对不上时无从判断谁是对的。
- 方案还漏掉了**不经过 handler 的请求**（`/media`、404、鉴权失败、中间件直接返回）：路径序列必然残缺，而残缺数据做行为分析比没有数据更危险——它会把"没记录"误读成"没访问"。

**③ 建议**：
- **不要在每个 handler 里写访问日志**。保持「一次请求一行」的不变量：在 `server.mjs:62-82` 的 `finish` 事件里统一补齐字段（用户在 handler 里把 `userId` 写到 `res.locals` 或一个 `AsyncLocalStorage` 里，server 层读它），`request_id` 已经是这条链的锚（`server.mjs:53-60` 会把 id 注入入站头，`request-id.ts:55-57` 保证业务层拿到同一个）。
- 如果非要保底，至少在 handler 侧用**异步 batch 写**（攒 N 行/每 100 ms flush），并保证**序列化失败只丢这一行、绝不阻塞请求**（`server.mjs` 的 `writeLine` 是裸 `JSON.stringify`，`BigInt` 或循环引用会直接抛）。
- 写路径必须带**开关**（环境变量），以便"日志导致延迟异常"时能一条命令关掉。

## 2. 容量判断不成立：两套部署的日志配额都不支持 90 天 —— 方案第 29–30、37 行

**① 问题**：第 37 行「数据量大但都是文本，成本可控」。但本仓实际上**两套部署各自的日志容量上限都很小**：

| 部署面 | 现状证据 | 实际可存 |
|---|---|---|
| compose（现网） | `docker/compose.yaml:70-74`：web 的 json-file `max-size: 10m`、`max-file: 3` → **硬上限 30 MB** | 按每请求约 300–500 B 计，**约 6 万–10 万行**。日均几千请求的站点，**6–10 天的全量日志就把 30 MB 吃满，90 天是天文数字**（差 1–2 个数量级） |
| systemd | `deploy/dsh-review-web.service:29-31`：`StandardOutput=journal`，**无 `SystemMaxUse=`** → 受 `/var/log/journal` 默认上限（分区 10%）与 **`RateLimitBurst` 500 条/30 s** 约束 | 上限比 compose 大，但**突发会被整段丢弃**（见 §3） |

**② 后果**：
- 90 天留存**在 compose 上永远做不到**，在 systemd 上只能靠分区容量赌；方案写的是"保留 90 天"，实际是"最多留几十分钟到 10 天"。这属于**用文字承诺了基础设施给不了的 SLA**。
- 更严重的是**连锁**：日志卷写满 → `/app/.data` 同分区 → `health.ts:88-97` 的 `disk.free`（默认阈值 200 MB）判 `fail` → `statusForHealth` 返回 **503**（`health.ts:149-151`）→ `docker/web.Dockerfile:76-77` 的 HEALTHCHECK 失败 → 编排重启 web——**重启并不能腾出磁盘**，于是进入 503↔重启的死循环。同分区还会拖垮 `scripts/backup.mjs`（:99-107 打包媒体、:159/179 以非 0 退出），**恢复点体系跟着一起坏**。
- 「都是文本，成本可控」忽略了本仓的日志是**逐请求全量 + 结构化 JSON**：字段一变（UA/referer 都是长字符串），单行体积从 ~200 B 涨到 400–800 B，容量预算直接翻倍。方案没有任何单行字节数的估算。

**③ 建议**：
- 先把**容量预算算出来并写进方案**：`日请求数 × 单行字节数 × 90`。以 UA(150 B)+referer(120 B)+其余(~250 B) ≈ 500 B/行 计，日均 2 万请求 → **900 MB/90 天**，与当前 30 MB 的 compose 配额相差 **30 倍**，这个数字必须摆在方案第一页。
- 三个旋钮分开写：**采集率（采样）/ 单行体积（字段白名单）/ 保留天数**。要"看路径频次"，采样 10% + 保留 90 天的预聚合计数，就能拿到同样结论而数据量降 2–3 个数量级。
- 若坚持落盘：单独卷 + 显式配额 + 独立于 web 的健康检查项（不要复用 `health.ts` 的 `disk.free`，那会把日志问题误报成 web 故障）。

## 3. 高峰丢行：最需要的数据恰恰存活不下来 —— 方案第 29–30 行 + 第 36 行

**① 问题**：方案要「看到用户完整的浏览路径」，但两套日志通道在**高峰**都会丢：

**② 后果**：
- systemd：journald 默认 `RateLimitIntervalSec=30s` / `RateLimitBurst=500`。**30 秒超过 500 行就整段丢弃**并打一条 "Suppressed N messages"。方案新增的字段让每行更长、采集点更多（handler + server），**更容易触发限流**；而被丢掉的恰好是"用户密集操作"那段序列——正是行为分析最想要的样本。丢弃是**静默偏倚**：统计结果会系统性低估高频用户（正是最有分析价值的那批）。
- compose：json-file 的 `max-size` 是**按文件滚动**，超过 10m 就把最旧的整个文件丢掉（`compose.yaml:70-74`）。高峰期的日志反而最早被覆盖，**"回溯 90 天"在高负载日自动变成"回溯昨天"**。
- 叠加 §1 的重复记录（每请求两行），有效容量再减半。

**③ 建议**：
- 明确写出「高峰丢弃」的取舍与额度：systemd 侧显式调 `RateLimitBurst`（并在方案里给出压测值），compose 侧把 90 天"源数据"与"预聚合计数"分开——**预聚合结果很小，永不丢；原始行按天滚动**。
- 行为分析结论只依赖预聚合（`user_id × route_path × day` 计数 + 会话首尾），原始行降级为"排障用 7 天"。
- 加一条可验证的验收：压测到 X rps 时，预聚合计数与实际请求数**误差 < 1%**。

## 4. 分析期扫描会打满 IO，与站点共用同步 SQLite —— 方案第 26–33 行

**① 问题**：第 26–33 行「用脚本按 user_id 分组，统计路径频次」，而第 30 行要求保留 90 天全量。

**② 后果**：
- 90 天 × 全量 = 上百 MB 到 GB 级，按 `user_id` 分组需要**全量读一遍**（grep/zcat/awk），每次分析都是持续性 IO。仓储在**单机**上（`deploy/*.service` 同机运行 web + worker），而 `src/server/platform/db.ts:6-8` 明确写了 `better-sqlite3` 是同步驱动、等待会阻塞所属线程。**任何一次「跑分析脚本」都会以 IO 竞争的形式抬高线上 p95**，且没有优先级隔离手段（systemd 只有 web 服务本身，没有 cgroup 的 IO 权重）。
- 若把分析放到容器里跑（`docker compose exec web`），就是**直接与分析目标共用同一个进程的磁盘带宽**。
- 数据一多就用 `grep` 全扫：这是**O(全量)** 而不是 O(结果)，重复执行的成本无法摊销。方案没有任何缓存/物化视图。

**③ 建议**：
- 分析走**预聚合表**（SQLite 里一张 `access_daily_counts(user_id, route_path, day, hits)`），脚本只增量更新当天分区；查询是 O(天数 × 去重路径) 而不是 O(全量行)。
- 分析脚本显式 `nice`/`ionice`，且**不在线上跑全量回溯**；回放走备份副本（`scripts/backup.mjs` 已经产出 `app.sqlite` 副本，可以在副本上跑）。
- 给出"一次分析对线上 p95 的影响"的实测数字（跑前/跑中 `server.mjs` 的 `duration_ms` 分布），作为方案验收项。

## 5. 单行体积：没有字段白名单，UA/referer 是无界输入 —— 方案第 21–22 行

**① 问题**：`user_agent: req.headers['user-agent']`、`referer: req.headers.referer` 原样入日志，**没有长度上限、没有白名单**。

**② 后果**：
- HTTP 头本身有服务器端上限（Next/Node 默认 header 总大小 ~16 KB，nginx 侧 `http_referer` 同样可达数 KB），所以**单行可以从 300 B 膨胀到 8–16 KB**（`~50×`）。一条被构造成超长 referer 的请求，就足以在 30 MB 的 compose 配额里占掉 0.05%，**几百个请求就能把整天的容量挤掉**（这是一种不需要登录的"日志容量 DoS"）。
- `log.ts:24` 的敏感键黑名单只匹配**键名**（`token|secret|password|cookie|...`），`referer` 里 `?code=xxx&token=yyy` 这类**值层面的第三方凭据**不会被遮掉 —— 这既是合规面（安全/法务视角）也是容量面（用户把这行复制出去时体积更大）。
- 没有字段白名单 = **没有体积上界**，所有容量测算（§2）都失去意义。

**③ 建议**：
- 采集端就做**降维**：`user_agent` 只留 `family/version/major`（解析结果），`referer` 只留 `origin + path`（丢弃 query，除非在显式白名单里）。这一步能把单行从 ~500 B 压到 ~200 B，**容量降 60%**，且不损失路径分析所需的全部信息（路径只看 path）。
- 对每个字段设**硬上限**（例如 256 B，超出截断并记 `truncated:true`），让"单行字节数"成为可验证常量。
- 单行体积写进方案的容量表，并加一条回归测试：构造超长 UA/referer，断言日志行 < 1 KB。

## 6. 采样率与统计精度：方案把「全量」当成默认，没有误差口径 —— 方案第 26–33 行

**① 问题**：方案隐含"全量采集 90 天 → 全量统计"，但没给采样讨论，也没给统计精度口径。

**② 后果**：
- 全量意味着**成本随流量线性增长**，而行为分析要回答的是「哪些路径最常走」，本质是**频率估计**问题——用 1–10% 采样 + 置信区间就能以 1/50–1/100 的成本得到同样的产品结论（相对误差 ≈ `1/√n`，n=1000 时 ±3%）。
- 反过来，若为了控成本而**事后删数据**，结论会**随时间漂移**（不同周的窗口不同），历史对比失效。
- 方案没有"采样率"这个旋钮，一旦上线觉得太大，唯一的办法是改代码重新发布。

**③ 建议**：
- 在方案里定两个正交参数：`sample_rate`（默认 10%，可按 user_id 哈希固定采样，**保证同一用户的路径序列完整**——按请求随机采样会截断路径，破坏分析目标）与 `retention_days`（原始行 7 天 / 预聚合 90 天）。
- 给出精度口径：「n 条样本下路径频次相对误差 ≈ ±X%」，并把它写进结论的置信度说明。

## 7. 合规前置会回灌到性能方案：字段越少，成本越低 —— 方案全篇

**① 问题**：方案 §1 同时采集 `user_id + client_ip + user_agent + referer` 四项。这是**可识别个人信息**的组合，安全/法务侧的结论会是"需要告知、授权、最短必要期限、删除能力"。

**② 后果（性能视角）**：这些合规要求落地后会**直接改采集面**：
- 「最短必要" → 保留期必须能从 90 天压缩到实际需要的天数（例如 30 天），容量预算随之变化；
- 「用户删除权」 → 需要在日志侧支持按 `user_id` 删除，这要求日志**按人可寻址**（否则只能全量重写 → 每次删除都是 O(全量) 的重写，**成本爆炸**）；
- 「最小必要字段」 → `referer`、`user_agent` 大概率被判为非必要，需降维或去掉（正与 §5 的建议一致）。

如果方案先按四项全量设计、上线后再因合规要求回退，等于**两次改日志契约**，两次都要重算容量与格式，成本翻倍。

**③ 建议**：**先定字段最小集再定容量**。把 `referer`/`user_agent` 降维为派生字段（§5），`client_ip` 做掩码（IPv4 /24、IPv6 /64），`user_id` 与日志行通过**可删除的分区文件**组织（按天分文件 → 删除某人 = 重建当天分区，O(当天) 而非 O(90 天)）。这三条同时满足合规与性能。

## 8. 与既有实现的重复：同一份 UA/referer 已经被记了两次 —— 方案第 9–24 行

**① 问题**：nginx 的 `log_format main`（`docker/nginx/nginx.conf:24-29`）**已经**记录了 `$http_referer`、`$http_user_agent`、`$request_time`、`req_id=$http_x_request_id`；应用侧的 `server.mjs:62-82` 又记了 `path/status/duration_ms`。

**② 后果**：
- 同一请求的 UA/referer 在**入口与应用各存一份**，两份保留策略不同（nginx 无配额限制但也没轮转；应用侧被 json-file 30 MB 截断）。**没有单一事实来源**，分析时对不上就是"到底哪份是对的"。
- 磁盘上 UA/referer 的**存储成本 ×2**，而这两项恰恰是最大的两个字段（§5）。
- 方案要新增的其实是 **`user_id` 这一个字段**——把它补进 `server.mjs` 的那一行，再把 `req_id` 与 nginx 侧对齐（已经对齐：`proxy-common.conf:32` 透传 `X-Request-Id`），就**能直接把 nginx 的行与业务行 join 起来**，不需要重复存 UA/referer。这是**成本降一半**的等价方案。

**③ 建议**：方案 §1 改为「在 `server.mjs` 的 http_request 行补 `user_id`（+ 会话内序号）」，UA/referer/耗时全部从 nginx 日志按 `req_id` join。这样：新增字段 1 个、单行增加约 40 B、容量只涨 ~10%，而路径分析能力完全不变。

| 6 | 关掉开关后重启，行为完全回退、不再产生新日志行 | 开关 + 重启 + diff |

## 11. 一句话给作者

这份方案的**目标是对的、手段是错的**：要"看路径频次"，需要的其实只是 **`user_id` 这一个新字段 + 一张按天预聚合的计数表**（存储约几 MB），而方案设计成「四个原始字段 × 每请求 × 90 天 × 全量分析」。照 §8 的 join 方案 + §5 的字段降维 + §6 的采样率，**成本能降 2–3 个数量级，而产品结论几乎不变**。现在方案里唯一缺的，是**任何一个具体的数字**。
