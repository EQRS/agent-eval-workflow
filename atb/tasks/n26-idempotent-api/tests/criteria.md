## 必须发现（每项 1 分）

### 对抗性
- [ ] **S-1 幂等键未与用户绑定，可跨用户读取他人响应**
  §2 的 `WHERE key = ?` **只按 key 查，没有 user_id 条件**。
  攻击者若猜到一个 key（或从日志/浏览器历史拿到），
  可以拿到**别人的响应内容**（可能含敏感数据）。

- [ ] **S-2 检查与写入不是原子的，并发窗口内会重复执行**
  §2 是「先查 → 执行 → 写表」三步，**没有事务也没有锁定**。
  同一 key 的两个并发请求都会查到「不存在」，然后都执行一遍。
  **幂等完全失效**——而这正是幂等要解决的问题。

- [ ] **S-3 key 由客户端提供，可被滥用撑爆表**
  没有长度限制、没有格式校验、没有速率限制。
  攻击者用随机 key 发大量请求，**每次都写一行**，表无限膨胀。

### 跨系统
- [ ] **C-1 项目已有幂等机制，方案重复造**
  `operation_records` 的 `UNIQUE(action_type, operation_key)` 就是幂等去重载体，
  `src/server/modules/operations/service.ts` 的 `recordWithin` 已实现「先查后插」+ 重放返回。
  `request_key` 机制也存在于提交链路（content_submissions）。

- [ ] **C-2 缓存响应体本身有风险**
  §1 把 `response` 存成 TEXT——写接口的响应可能含
  token、内部 id 等，长期存储且无脱敏。

### 性能
- [ ] **P-1 每个写请求多两次库往返**
  查一次 + 写一次，在 SQLite 单写者下会加剧写锁竞争。
  方案没有评估这部分开销。
