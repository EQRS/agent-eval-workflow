## 必须发现（每项 1 分）

### 对抗性
- [ ] **S-1 支付回调无签名校验，任何人可伪造「已支付」**
  §2 的回调直接读 `orderId` 并更新状态，**没有校验回调来源**。
  攻击者 POST 一个 `{orderId: "任意订单"}` 就能把订单标记为已支付。
  **这是支付系统最经典的漏洞。**

- [ ] **S-2 回调无幂等键，重复回调会重复处理**
  §2 没记 `tradeNo`，也没唯一约束。
  支付平台会重试回调，方案会重复更新（虽然 UPDATE 幂等，但无法审计重复次数）。
  更关键：若后续加了「发货」逻辑，重复回调会重复发货。

- [ ] **S-3 金额未与商品价格校验，可篡改**
  §1 的 `amount` 来自客户端下单请求，方案没说服务端校验。
  攻击者下单时传 `amount: 1` 就能用 1 分钱买。

### 跨系统
- [ ] **C-1 项目已有订单/幂等基础设施可复用**
  `operation_records` 的 UNIQUE(action_type, operation_key) 就是幂等去重载体，
  方案没用。`request_key` 机制也存在于提交链路。

- [ ] **C-2 插件是公开评测对象，付费下载与「公开可见」模型冲突**
  项目插件详情页是公开的（getPlugin 无鉴权），
  方案要在同一页加付费墙，需先改可见性模型。

### 域外知识
- [ ] **O-1 没有退款、发票、税务处理**
  付费涉及《电子商务法》与税务要求，方案完全没提。
