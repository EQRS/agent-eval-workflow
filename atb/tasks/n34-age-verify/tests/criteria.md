## 必须发现（每项 1 分）

### 域外知识（未成年人保护）
- [ ] **O-1 自填生日不构成「验证」**
  §2 让用户自填出生日期——未成年人会直接填「1990-01-01」。
  《未成年人保护法》第 72-74 条要求的是**身份核验**，不是自述。
  方案把「填了」当成「验证了」，是**概念偷换**。

- [ ] **O-2 只写 birth_date 不写 age_verified，逻辑漏了半截**
  §2 的 SQL **只更新了 birth_date，没更新 age_verified**。
  而 §1 建了 `age_verified` 字段——这个字段永远是 0，
  意味着**按方案的字面实现，所有人都通不过年龄验证**。

- [ ] **O-3 只对未成年人写 birth_date，成年人反而没记录**
  §2 的 `if (age < 18)` 分支里才写库。
  成年人填的生日**根本没存**，无法审计；且下次登录又会被要求填一次。

- [ ] **O-4 「不能发布」的判据没有落点**
  §3 说「未满 18 岁不能发布」——但项目里发布走的是
  `submit-review` / `assertCanWrite`，方案没说要改哪一处。
  且**没有考虑已发布内容的追溯**（未成年时期发的内容怎么办）。

### 对抗性
- [ ] **S-1 出生日期是敏感个人信息，无加密无访问控制**
  生日 + 用户名 + IP 足以精确定位到个人。
  PIPL 第 28 条把**不满十四周岁未成年人的个人信息**列为敏感个人信息，
  需要「单独同意」与「专门处理规则」。方案零提及。

- [ ] **S-2 年龄信息可被用于撞库**
  生日是常见的账号找回验证要素。把它明文存进库，
  一旦库泄露，**其他平台的账号也会受牵连**。

### 跨系统
- [ ] **C-1 项目身份来自 GitHub，拿不到真实年龄**
  `external_identities` 只有 `provider_user_id`/`provider_username`/`profile_url`，
  GitHub 不提供生日。方案的「注册时采集」必须**新增一个界面**，
  而项目当前是 OAuth 直接建号（`callback/route.ts`），没有中间步骤。
