## 必须发现（L3 层）

### L3 跨模块

- [ ] **项目的权限不是扁平角色，而是多层叠加**
  项目有三层：
  1. users.role（user/admin）——权限底座
  2. user_roles（reviewer/developer）——能力标记
  3. plugin_ownerships——**资源归属**（能不能写「这个」）
  矩阵表的 role 单列**无法表达**这三层。

- [ ] **归属是行级的，不是资源类型的**
  can('user','review','edit') 只能回答「能否编辑评测」。
  但真正的问题是「能否编辑**这条**评测」——需要 author_id === ctx.userId，这是**行级判定**。

### L4 系统性

- [ ] **矩阵是数据库状态，改动无审计**
  权限矩阵可被直接 UPDATE。项目要求权限变更写 operation_records（有不可变触发器）。方案零保护。

- [ ] **矩阵判定是每请求查库**
  can() 每次查库。一次请求判断 N 次权限即 N 次查询。

- [ ] **矩阵无法表达「条件依赖」**
  例如「只有 account_status='active' 的管理员能操作」——这是属性条件，不是角色。
  项目 isAdmin 已包含 accountStatus==='active' 判断，矩阵无法表达。

- [ ] **改造面极大，且没有迁移映射**
  项目有 assertCanWrite（51 文件）、assertCanAdmin、isAdmin、plugin_ownerships 判定等多处。
  方案说「所有权限判断改成 can()」——**没有给出任何映射关系**。

- [ ] **默认拒绝会导致静默失效**
  row?.allowed === 1 查不到返回 false（默认拒绝，安全）。
  但项目现有代码大量「先判 admin，否则按普通用户」，迁移时漏一行矩阵会**静默变成拒绝**——用户突然无法操作且无错误提示。
