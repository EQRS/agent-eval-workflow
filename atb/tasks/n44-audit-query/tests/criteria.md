## 必须发现（每项 1 分）

### 跨系统（真实约束）
- [ ] **C-1 operation_records 有不可变触发器，但 audit_stats 没有**
  `migrations/0042_audit_immutable.sql` 给 `operation_records` 加了
  `BEFORE UPDATE/DELETE` 触发器。新的 `audit_stats` **没有任何保护**——
  而它直接决定审计页面的展示。**改统计表就能改变「审计看起来是什么样」**。

- [ ] **C-2 统计与审计不同事务，会漂移**
  §2 的 `recordOperationInTx(db, ...)` 与 后面的 `db.prepare(...).run()` 是**两条独立语句**。
  若第二条失败，审计记了但统计没记；若第一条失败，统计记了但审计没有。
  项目纪律要求「审计与业务变更同事务」（`operations/service.ts` 注释）。

- [ ] **C-3 action 字段的真实语义**
  `operation_records` 的字段是 `action_type`（不是 `action`）。
  且它有 `UNIQUE(action_type, operation_key)`——重放时**不会写新行**，
  但方案的累加会**无条件 +1**，导致统计虚高。

### 对抗性
- [ ] **S-1 统计表可被篡改为「掩盖操作痕迹」**
  攻击者若拿到 DB 写权限，改 `audit_stats` 就能让审计页面显示「今天没有敏感操作」，
  而真实的 `operation_records` 行仍在（但被淹没）。

### 性能
- [ ] **P-1 每次审计多一次写，在 synchronous=FULL 下是双倍 fsync**
  `db.ts` 是 WAL + `synchronous=FULL`，每次提交都落盘。
  多一条 `audit_stats` 的 INSERT 就是**多一次 fsync**。
  审计写入本身是低频（人工变更），但方案说的是「每次写审计记录时」——
  若审计包含高频操作，写放大会很显著。
