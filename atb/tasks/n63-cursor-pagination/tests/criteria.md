## 必须发现（L3 层）

### L3 跨模块
- [ ] **只按 updated_at 排序不唯一，同时间戳会漏项/重复**
  项目 `catalog/service.ts` 的排序是
  `ORDER BY p.updated_at DESC, p.id ASC`——**带 id 作为决胜键**。
  `updated_at` 是 INTEGER 毫秒，同一毫秒可能有多行。
  方案只用 `updated_at < ?` 会**漏掉同毫秒的行**，或翻页时重复。

- [ ] **游标应该是复合的**
  正确的游标是 `(updated_at, id)` 元组：
  `WHERE updated_at < ? OR (updated_at = ? AND id > ?)`。
  方案的单一数值游标**无法表达**。

### L4 系统性
- [ ] **列表有多种排序模式，游标要跟着变**
  项目列表支持 `sort=updated|reviews|assessment|security` 等多种排序。
  方案的游标只适用于 `updated_at` 排序——
  **换成按评测数排序时游标失效**，会返回错误结果。

- [ ] **筛选条件变化时游标失效**
  用户在第 3 页改变了筛选条件（如加了个 tag），
  游标仍指向旧结果集的位置 → **返回的是旧筛选的延续**。

- [ ] **项目已用 OFFSET，切换会破坏既有 API 契约**
  `src/packages/common/result.ts` 定义了分页结构，
  现有前端按 `page/pageSize` 工作。
  改成游标是**breaking change**，方案没有兼容策略。

- [ ] **游标没有签名，可被篡改**
  `nextCursor` 是明文时间戳，客户端可**任意修改**跳到任意位置。
  虽然这不泄露数据，但可能触发**异常查询**（如 cursor 传负数）。

- [ ] **没有处理「数据在翻页期间被修改」**
  若第 1 页的某行在第 2 页请求前被更新（updated_at 变大），
  **它会在第 2 页重复出现**（因为游标是旧值）。
  这正是 OFFSET 分页也有、但游标分页**更容易**出现的问题。
