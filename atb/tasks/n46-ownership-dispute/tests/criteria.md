## 必须发现（每项 1 分）

### 跨系统（真实约束）
- [ ] **C-1 直接改归属会绕过既有的唯一约束**
  `migrations/0040_user_roles.sql` 有 `uq_plugin_ownerships_verified`
  （一个插件只能有一个 verified 归属人）。§3 说「直接改归属」——
  **必须先撤销旧的再建新的**，否则撞唯一约束报错。
  且项目 `roles/ownership.ts` 有既定的转移逻辑，方案绕开了它。

- [ ] **C-2 改归属必须写审计，方案没有**
  `operation_records` 是唯一审计载体，且 `0042` 已加固。
  §3 的「管理员直接改」**没有任何审计**——事后无法追溯「谁在什么时候改了归属」。

- [ ] **C-3 status 字段没有 CHECK，是自由文本**
  §1 的 `status TEXT NOT NULL DEFAULT 'pending'` 没有枚举约束。
  任何字符串都能写进去，处理流程无法依赖它做状态机。

### 对抗性
- [ ] **S-1 任何人都能对任意插件提争议 → 恶意骚扰**
  §2「任何用户都可以对任意插件提出归属争议」——
  **没有频控、没有前置校验**。攻击者可以对全站插件批量提争议，
  让管理员疲于应付，同时污染「谁是真的作者」的判断。

- [ ] **S-2 没有防重复提交**
  §1 没有 `UNIQUE(plugin_id, claimant_id)`。
  同一人可以反复提交同一争议，撑爆表且淹没真实争议。

### 域外知识
- [ ] **O-1 归属纠纷可能涉及知识产权，需要留证与申诉期**
  若争议涉及著作权（如代码是他人作品），单纯「管理员改归属」**不足以作为处理依据**。
  《电子商务法》第 41-43 条要求平台建立**知识产权保护规则**，
  包括通知、声明、处置、公示四个环节。方案只做了「申诉」，缺其余三个。
