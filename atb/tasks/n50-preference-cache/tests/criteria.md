## 必须发现（L3 层）

### L3 跨模块
- [ ] **web 与 worker 是两个进程，进程内缓存不共享**
  `docker/compose.yaml` 里 web 与 worker 是**两个容器**，
  各自一个 `getDb()` 单例（`db.ts`）。
  §2 的 `setPreferences` 只清**当前进程**的缓存——
  **worker 改的偏好在 web 进程里看不到**（直到每小时全清）。

- [ ] **缓存无 TTL，全清前的窗口最长 1 小时**
  §3 说每小时清一次。但方案没定义"从什么时候开始算"——
  若定时器启动时刻不确定，**最长可能 2 小时**才清。

### L4 系统性
- [ ] **偏好直接影响功能开关，缓存不一致 = 功能状态不一致**
  `0030_user_preferences.sql` 的偏好可能包含功能开关类设置。
  若 web 缓存的是"开启"、库已是"关闭"，
  **用户在不同请求上看到不同的功能状态**——这是最难排查的 bug。

- [ ] **清缓存失败时没有任何补偿**
  §2 的 `cache.delete` 在 `UPDATE` 之后。
  若 UPDATE 成功但进程在这之后崩溃，**缓存里的旧值会一直用到下次全清**。

- [ ] **Map 无上限，会内存泄漏**
  §1 的 `Map` 只增不减（只在写时删单个、每小时全清）。
  若有大量用户访问，**内存会持续增长**——项目无 mem_limit 配置。
