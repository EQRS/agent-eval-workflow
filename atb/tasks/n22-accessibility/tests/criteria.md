## 必须发现（每项 1 分）

### 域外知识（WCAG 标准）
- [ ] **O-1 给 button 加 aria-label 会覆盖可见文本，导致语音控制失效**
  §1 的 `<button aria-label="提交评测">提交</button>`——
  aria-label **会覆盖元素内的可见文本**，屏幕阅读器只读 label。
  更糟：语音控制用户说「点击提交」时，因可访问名称是「提交评测」而匹配失败。
  **WCAG 2.5.3 Label in Name 明确要求可见文本必须包含在可访问名称中。**
  正确做法是**不加**这个 aria-label（button 的文本本身就是可访问名称）。

- [ ] **O-2 可点击 div 加 tabIndex 不是无障碍，是反模式**
  §2「给可点击的 div 加 tabIndex 和 onKeyDown」——
  正确做法是**用 button 元素**，它天然支持键盘、焦点管理、角色语义。
  手写 tabIndex + onKeyDown 会漏掉 Enter/Space 差异、焦点环、disabled 态等十几种情况。

- [ ] **O-3 role="dialog" 缺焦点管理，键盘焦点会跑到背景**
  §1 的 dialog 只有 aria-modal="true"，**没有 focus trap**。
  键盘用户 Tab 会跑到弹窗背后的元素上，WCAG 2.4.3 Focus Order 不满足。

- [ ] **O-4 未覆盖 WCAG 的可感知/可理解维度**
  §1-§3 只碰了「可操作」的一部分，完全没提：
  图片 alt（1.1.1）、表单标签关联（1.3.1）、错误识别（3.3.1）、
  以及**动态内容的 aria-live**（本项目的表单校验错误是动态出现的，无 live region 屏幕阅读器不会播报）。

### 跨系统
- [ ] **C-1 项目有 40+ 页面与大量组件，方案没有清单与验收方式**
  §1「给所有交互元素加 aria-label」——**「所有」没有定义**。
  没有覆盖清单、没有自动化检测、没有人工测试计划。
  「通过无障碍检测工具」不等于可用——自动化工具只能发现约 30% 的问题。
