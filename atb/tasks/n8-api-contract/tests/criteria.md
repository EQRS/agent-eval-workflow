# 判据清单（agent 不可见）

> **评分结构（v2）**
> - 前提核实：0.5 分（基础项）
> - **预设考点**（下方「必须发现」）：权重 **60%**
> - **超纲发现**（T 组发现的、预设之外但经核实成立的问题）：权重 **40%**
>
> **为什么有「超纲发现」**：三批实测显示，T 组平均会挖出 4-8 条预设之外的成立问题
> （如 N-34 的 UUIDv7 时序泄露、N-36 的 rate_limiter.key 存 userId、N-37/38 与项目文档冲突）。
> 若判据只认预设，这些发现会被系统性低估。

## 前提核实（基础项，0.5 分）

- [ ] **方案假设的东西在本仓库是否真实存在？**
  核对表/列/接口/依赖是否在 `migrations/`、`src/`、`package.json` 中真实存在。
  **注意区分**：方案声明要新建的表（有 CREATE TABLE / ALTER / 明确说「接入」某依赖）属合理；
  引用了不存在的对象且没声明 → 前提不成立。

## 必须发现（每项 1 分）

### 跨系统交互
- [ ] **C-1 v1 与 v2 共享表 = 字段语义无法独立演进**
  §2「共享同一张 plugins 表，v2 只是换个字段名」——
  若将来 v2 需要改字段语义（如 status 从 3 态变 5 态），v1 客户端会收到不认识的枚举值。

- [ ] **C-2 弃用期 6 个月无技术保障**
  §3「6 个月后下线」——没有访问统计、没有通告机制、没有强制迁移手段。
  6 个月后直接下线 = 可能造成线上故障。

### 对抗性思维
- [ ] **S-1 v2 沿用 v1 鉴权 = 安全面不隔离**
  §4「v2 沿用 v1 的鉴权中间件」——若 v1 鉴权有已知问题并修复在 v2，
  攻击者可继续用 v1 绕过。必须：v1 的漏洞修复要同步到 v1。

### 域外知识
- [ ] **O-1 版本化方案的选择未论证**
  §1 用了路径版本化。业界有三种：URL 路径 / Header / Query 参数。
  路径版本化破坏 RESTful 的资源标识（同一资源两个 URL），且缓存会分为两份。

- [ ] A-2 指出「应先在响应里加 deprecation 头，再谈下线」
