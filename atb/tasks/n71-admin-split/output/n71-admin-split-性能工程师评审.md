# N71「管理后台改造成独立应用」方案 · 性能工程师评审

> 评审对象：`atb/tasks/n71-admin-split/environment/proposal.md`（19 行）
> 评审身份：性能工程师（写锁与并发 / CAS 争用 / 缓存与连接 / 容量与压测）
> 事实基线：`src/server/platform/db.ts`、`src/server/platform/tx.ts`、`src/server/modules/identity/{admin,service}.ts`、`src/server/platform/rate-limit.ts`、`src/server/platform/health.ts`、`docker/compose.yaml`、`docker/web.Dockerfile`、`docker/nginx/snippets/proxy-common.conf`、`deploy/*.service`

## 0. 结论

**不支持按现方案拆。** 关键约束在第 12 行：**两个应用连同一个 SQLite 文件**。

从性能上看，这条约束会同时踩中三个已知机制：

1. **写是全局串行的**：SQLite 同一时刻只有一个写者。本仓 `db.ts:52-56` 是 `WAL` + `synchronous = FULL` + `busy_timeout = 5000`，**每个写事务一次 fsync**。现在的 web 与 worker 已经是两个写者，方案再加一个 admin 应用 = **第三个写者**；后果不是平均变慢，而是**尾延迟放大**（§1）。
2. **`busy_timeout` 是唯一的背压手段，而它会把排队变成卡死**：`db.ts:56` 的 5 s 是**阻塞等待**，`better-sqlite3` 是同步驱动（`db.ts:6-8` 注释原文「等待会阻塞所属线程」）。第三个写者进场后，web 进程可能在一次请求里**同步阻塞最多 5 s**，期间整个 Node 事件循环停摆（§2）。
3. **CAS 的并发窗口被拉长**：`users.management_version` / `account_status_version` 的 CAS（`identity/admin.ts:423-432`、`:554`）在单进程内靠「同一连接串行」天然收敛；跨应用后**两个进程各读各写**，冲突率上升，表现为管理员看到「请刷新后重试」的次数变多（§3）。

**另外：「不影响主站」（第 19 行）在当前架构下无法成立**——两个应用共享同一块磁盘与同一套健康检查口径，主站的 `synchronous = FULL` 尾延迟会直接吃到后台操作上，反之亦然（§4）。

## 1. 第三个写者进场：FULL 同步下写事务全局串行 —— proposal 第 11–12 行

**① 问题**：方案第 12 行「两个应用连同一个 SQLite 文件」——加上现有 worker，就是**三个进程同时写一个库**。方案没有对这个组合做过任何估算。

**② 后果（核实依据）**：
- `db.ts:52-55`：`journal_mode = WAL`、`synchronous = FULL`。**FULL 意味着每次提交都要 fsync 后才返回**；WAL 只让**读**不阻塞写，**写与写之间仍然全局串行**。
- 现有拓扑已经有两个写者：`docker/compose.yaml:44-77` 的 `web` 与 `:78-108` 的 `worker`（systemd 侧是 `dsh-review-web.service` 与 `dsh-review-worker.service`）。方案第 12 行是**再加一个**。
- 写代价的可见后果不是平均变慢，而是**尾延迟**：所有写请求排在同一个写锁后面。一次长写事务（批量导入、发布、每天 03:00 的备份——`scripts/backup.mjs:63-65` 的 `db.backup()`）会把排队的写请求一起推高。后台的「批量审核 / 批量导入」恰恰是**最长的写事务**；把它们放进独立进程**不会让它们变短**，只会让主站与它们排队。
- `synchronous = FULL` 在本仓是**刻意选择**（完整性与崩溃一致性优先，见 `db.ts:1-11` 头注释），不能为了拆应用改成 NORMAL——那会牺牲最后一次提交的持久性保证。

**③ 建议**
- 方案必须先给出**写事务预算**：当前 web+worker 的写 QPS、单次 fsync 实测耗时、`busy_timeout` 命中率；再按 Little 定律（排队长度 = 到达率 × 平均服务时间）估算 admin 加进来后的排队长度。
- 如果 admin 主要是**读多写少**（看队列、查记录），那就不该拆成独立应用去写库；正确做法是给它一个 **`readonly: true` 连接**（`db.ts:22-23` 已支持 `readonly?: boolean`），彻底把它排除在写锁竞争之外。
- 如果确实要拆，必须同时给出「写请求如何串行化」的方案（单写者 + 队列），而不是三个进程各自抢锁。

## 2. `busy_timeout = 5000` 是阻塞等待：第三个写者会把「变慢」变成「卡死整个进程」 —— proposal 第 12 行

**① 问题**：方案默认「多加一个连接只是慢一点」。

**② 后果（核实依据）**：
- `db.ts:56`：`busy_timeout = 5000`（默认值，且 `OpenOptions.busyTimeoutMs` 可覆盖）。在 `better-sqlite3` 下这是**同步阻塞**——`db.ts:6-8` 注释原文：「better-sqlite3 是同步驱动，等待会阻塞所属线程，因此业务事务保持短小」。
- 这条纪律在**跨进程**压力下会被打破：锁被别的进程持有 5 s，web 进程就**整整 5 s 不响应任何请求**。而 `docker/web.Dockerfile:76-77` 的 HEALTHCHECK 是 `--timeout=5s --retries=3`——**一次 5 s 阻塞就足以让健康检查超时**，连续三次即 `unhealthy` → 编排器重启 → 重启期间所有连接重建，形成自激。
- `busy_timeout` 超时抛 `SQLITE_BUSY`，而 `errors-http.ts:120-126` 只把 `DomainError` 映射成业务错误——**`SQLITE_BUSY` 会变成 500**。这条在仓库里有先例：`roles/ownership.ts:239-250` 记录的 500 就是「没被映射的 SQLite 错误被当成未处理异常」。

**③ 建议**
- 明确 `busy_timeout` 在新拓扑下要**降到远小于 HEALTHCHECK 超时**（例如 1–2 s），并给 `SQLITE_BUSY` 一个**明确映射**（503 + `Retry-After`，而不是 500）——这是既有缺口，拆分只会放大它。
- 给 admin 应用**独立的连接参数**（更长的 busy_timeout、更小的页缓存）：让它「愿意等」，而主站「快速失败」。**两边用同一组参数是错的**——主站要低延迟，后台要吞吐。
- 所有 admin 批量操作必须**分片提交**（每批 N 行一个小事务 + 间隔），不能在单个事务里跑几千行，否则它会成为别人的 5 s 阻塞源。

## 3. CAS 版本号：跨应用后冲突率上升，表现为「请刷新后重试」变多 —— proposal 第 12–15 行

**① 问题**：方案没说两个应用如何共享 `users.management_version` / `account_status_version` 这两个 CAS 版本号。

**② 后果（核实依据）**：
- `identity/admin.ts:19-21` 的头注释：「**CAS**：角色用 `users.management_version`、状态用 `users.account_status_version`」；实现是 `:423-426` 的 `UPDATE ... WHERE id = ? AND management_version = ?`，`:427-432` 在 `changes !== 1` 时抛 `version_conflict`。
- CAS 的本质是「读到的版本 → 写入时再比一次」，它**能**跨进程工作（数据库共享），所以不会「互相覆盖」——**但会把覆盖变成显式冲突**。拆开之后，管理员在后台点「设为管理员」的同时主站某条流程改了同一用户，后台请求就会 **409**。
- 而 `identity/service.ts:107-113` 的 `bootstrapAdminWithin` 是**盲自增**（`SET role='admin', management_version = management_version + 1`，无 CAS）——它是**跨进程安全的写法**，但方案没有要求在 admin 应用里也遵守「所有 users 写都用 CAS 或盲自增」这条纪律。一旦有人在新应用里写 `SET management_version = 5`（读后写），就会**把别人的并发更新覆盖掉**。
- 附带一条：`identity/service.ts:351-357` 的 `updateProfile` 直接 `UPDATE users SET nickname/avatar_url`，**不碰任何版本号**——它意味着「users 行上并非所有写都受 CAS 保护」。拆分后这类无版本写会更多，方案的 CAS 讨论必须覆盖它们。

**③ 建议**
- 方案里写死：**`users` 的所有写必须二选一**——要么带 `WHERE <version> = ?` 的 CAS（`admin.ts:423-426`），要么用 `x = x + 1` 的盲自增（`service.ts:109`）。**禁止读出来再写回去**。
- 给出跨应用冲突率的预期与度量：`version_conflict` 次数应在拆分前后**可对比**，并把后台「请刷新后重试」的出现频次接进指标。

## 4. 「不影响主站」不成立：共享磁盘 + 共享健康检查口径 —— proposal 第 17–19 行

**① 问题**：方案第 19 行把「不影响主站」写成了预期。

**② 后果（核实依据）**：
- `db.ts:66-74` 的 `getDb()` 是**进程级单例**：拆分不改变「一进程一连接一事件循环」的事实，admin 应用内部的任何长事务仍然会阻塞它自己的全部请求。
- 磁盘共享（宿主 `/root/dsh-plugin-review/data`，`compose.yaml:41`、`:65`），而 `health.ts:88-97` 的 `disk.free` 阈值是 **200 MB**——admin 若产生额外的导出/临时文件，会**直接把主站的健康检查打成 503**（`health.ts:149-151`）。
- 反向也一样：主站每天的备份（`scripts/backup.mjs:63-65`）会落一份完整库副本，admin 应用在那段时间会感到 IO 抖动。方案没有任何「谁在什么时候读盘」的规划。
- 还有一条：`health.ts:56-147` 的检查是**针对本进程**的，拆成两个应用后 `/api/health` 会有**两份互不知情的结论**——「后台可用吗」必须同时看两个端点，于是告警面翻倍而覆盖不变。

**③ 建议**
- 明确 admin 数据目录隔离（独立 `BACKUP_ROOT` / 临时目录），**不要**让它的文件落在主站 `disk.free` 的同一分区；不可避免时按分区重新分配 200 MB 阈值。
- 健康检查：要么让 admin 暴露自己的 health 并把「两个都 ok」作为部署判据，要么**不要**给它独立的存活探针（避免「后台挂了但没人知道」）。

## 5. 限流：计数共享但写入排队，热点叠加 —— proposal 第 14–15 行

**① 问题**：方案第 15 行「后台应用自己实现登录」，但没说限流计数在哪一侧。

**② 后果（核实依据）**：
- 本仓限流存储是**库表**（`rate-limit.ts:42-43` 的 `rate_limiter_flexible`，`storeType: 'better-sqlite3'`），键是 `<动作>:<userId>`（`:226`）。**计数本身共享**——额度不会翻倍，这点方案可以放心。
- 但限流器实例按 db 实例缓存（`rate-limit.ts:157-188` 的 `WeakMap`），两个进程各持一个实例；它们同时 `consume` 时**都要写那张表**，等于把 §1 的写竞争再叠加一层：每个请求多一次计数行写入。
- `rate-limit.ts:181-184` 刻意**关闭**了库自带的过期清理（避免 `setInterval` 影响进程退出），靠同一条语句里的 expire 判定处理过期。表随「用户 × 动作」增长；拆成两个应用后**键空间不变、写入频率上升**，这张表会成为写热点的额外贡献者。

**③ 建议**：admin 的登录与操作**复用主站同一套 `enforceRateLimit`**（别另写一套），并把 admin 的动作加进 `RateLimitAction`（`rate-limit.ts:46-55` 目前全是主站动作）。后台量级小，但**每次写都排队**——这一点要在方案里算进去。

## 6. 部署面的性能代价：镜像翻倍、容器翻倍、页缓存不共享 —— proposal 第 8–9 行

**① 问题**：方案第 9 行「独立构建」。

**② 后果（核实依据）**：
- `docker/web.Dockerfile:3-8` 的注释已经算过这笔账：「拆成 web 用 standalone、worker 用全量依赖两个镜像，会让『两边是同一份代码』这个前提变得难以核对，收益只是小几百 MB」。再拆一个 admin 应用就是**第三次**付这份成本，并让「三个角色共用一份镜像 = 同一份代码」这条不变量**彻底失效**。
- 每个容器是一份独立 Node 进程 + 一份 `better-sqlite3` 连接 + 一份页缓存。**页缓存在进程间不共享**：主站占一块、admin 再占一块，同一台机器上**有效缓存总量不变而命中率下降**（两个进程各自缓存相同的 `users`/权限行）。
- `nginx` 要为 `admin.example.com` 加一个 `server` 块；`proxy-common.conf:9-11` 的 `add_header` 是**替换语义**，新 server 少 include 一次就会**悄悄丢掉安全头**（`proxy-common.conf:4-6` 已有明文警告）。

**③ 建议**：先回答「为什么需要独立**进程**」。若动机是「后台迭代不影响主站发布」，路由分组 + 同一进程即可，成本低一个数量级；若动机是「后台写压力不能拖慢主站」，正确解法是**只读连接 + 独立连接参数**（§1/§2），而不是再开一个抢同一把写锁的进程。

## 7. 验收：方案第 17–19 行的两条预期都不可测 —— proposal 第 17–19 行

**① 问题**：「后台独立迭代」「不影响主站」都是定性描述。**② 后果**：无法证伪；而 §1–§4 说明它们大概率不成立，没有判据就无法在发布后发现。

**③ 建议**（建议直接写进方案）：

| # | 断言 | 怎么测 |
|---|---|---|
| 1 | 加 admin 进程前后，主站写接口 p95 **抬升 < 10%** | 对照 `server.mjs` 的 `duration_ms` 分布 |
| 2 | `SQLITE_BUSY` 次数为 **0**（或给出明确阈值） | 日志计数 + 明确映射为 503 |
| 3 | admin 执行批量操作期间主站 `/api/health` **不出现 503** | 压测 + 并发观察 |
| 4 | 两进程同时改同一 `users` 行 → **一个成功、一个 409**，版本号只 +1 | 并发脚本 |
| 5 | 单次 fsync 耗时与写事务排队长度有基线数字 | 拆前/拆后各测一次 |

## 8. 一句话给作者

**共享一个 SQLite 文件时，「拆成两个应用」不会带来任何算力收益——它只是把同一把写锁分给了两个进程，还多了一份页缓存、一份连接、一份健康检查和两个进程的日常运维面。** 真正能解决「后台拖慢主站」的是 `db.ts:22-23` 已支持的**只读连接**、§2 的**分进程连接参数**、以及 §1 的**写事务预算**——这些都不需要新开一个应用。
