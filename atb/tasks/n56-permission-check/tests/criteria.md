## 必须发现（L3 层）

### L3 跨模块
- [ ] **项目没有 middleware.ts，方案的新抽象无法挂载**
  `src/` 下没有统一的路由中间件。
  项目的做法是**每个 handler 第一步显式调用** `currentContext()` + `assertCanWrite(ctx)`。

### 考点识别（③ 无用功）
- [ ] **项目已有 assertCanWrite，51 个文件在用**
  `src/server/platform/context.ts` 的 `assertCanWrite`
  已经做了「登录 + 账号未禁用」的判断，且**51 个文件**在用。
  方案的 `requireAuth` 只判断了「有会话」，
  **漏了 `account_status === 'active'` 这一条**——比现有实现弱。

- [ ] **currentContext 每请求读库，方案的 getSession 也是**
  两者都要查会话表，没有性能收益。

### L4 系统性
- [ ] **「统一包装」会掩盖鉴权顺序问题**
  项目 `src/app/api/_lib/context.ts` 的注释明确要求：
  **「开关/鉴权必须先于读 body」**。若 `requireAuth` 包装在
  handler 外层，handler 内的 body 解析就**已在鉴权之后**——这点是对的。
  但方案没说明它比现有「每处显式调用」强在哪。

- [ ] **没有覆盖「资源归属」这一层**
  `assertCanWrite` 只判断「能不能写」，不判「能不能写**这个**」。
  项目另有归属校验（如 `owner_id !== userId → forbidden`）。
  方案把这两件事混成一件。
