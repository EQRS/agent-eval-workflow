## 必须发现（每项 1 分）

### 域外知识（数据安全法）
- [ ] **O-1 只靠 SQL 注释标注，机器读不到也管不住**
  §2 用 `-- sensitivity: public` 这样的注释——
  **这是给读代码的人看的，不是给程序看的**。
  「日志里不出现」「导出时脱敏」都需要**运行时能查到分级**，
  而注释在 SQLite 里不可查询（`sqlite_master` 存的是建表语句原文，但没有解析能力）。

- [ ] **O-2 分级没有落到字段粒度，而「表级」分级对混合表无效**
  §2 的示例是**表级**标注。但真实的表是混合的：
  `users` 表里 `id`/`role` 是内部，`nickname`/`avatar_url` 是公开，
  `last_login_at` 是敏感。**整表一刀切必然要么过严要么过松。**

- [ ] **O-3 「敏感个人信息」的法律定义没有对齐**
  《个人信息保护法》第 28 条把敏感个人信息定义为：
  生物识别、宗教信仰、特定身份、医疗健康、金融账户、行踪轨迹，
  以及**不满十四周岁未成年人的个人信息**。
  方案的 `sensitive` 只是个自定义等级，**没有与法定分类映射**。

### 跨系统
- [ ] **C-1 项目已有 SENSITIVE_KEYS 黑名单，方案并存两套**
  `src/server/platform/log.ts` 已有 `SENSITIVE_KEYS` 正则黑名单
  （token|secret|password|credential|authorization|cookie|code_verifier）。
  方案再来一套 `SENSITIVITY` 常量，**两套规则会漂移**。

- [ ] **C-2 注释分级无法被 CI 校验**
  项目有 `scripts/verify-task-prereqs.mjs` 这类脚本化检查的习惯。
  注释形式的分级**没有任何自动化手段能验证「新增字段有没有标注」**。

### 对抗性
- [ ] **S-1 没有定义「越级访问」的拦截点**
  §3 只说「日志不出现 / 导出脱敏 / 备份加密」，
  这是**三个输出面**，但**没有输入的管控**——
  谁能读 sensitive 字段？查的接口有没有鉴权？
