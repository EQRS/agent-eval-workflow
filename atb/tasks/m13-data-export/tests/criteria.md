## 前提核实（基础项，0.5 分）

- [ ] **方案假设的东西在本仓库是否真实存在？**
  核对表/列/接口/依赖是否在 `migrations/`、`src/`、`package.json` 中真实存在。
  **注意区分**：方案声明要新建的表（有 CREATE TABLE / ALTER / 明确说「接入」某依赖）属合理；
  引用了不存在的对象且没声明 → 前提不成立。

## 必须发现（每项 1 分）

### 安全维度
- [ ] **S-1 可见性过滤与「数据可携带权」直接矛盾（最严重）**
  §4「导出前套用 resolveVisibilityInTx，只导 publiclyVisible」。
  但 §背景 说的是「符合 GDPR 数据可携带权」。
  **数据可携带权要求导出「用户自己提交的全部数据」，包括已删除的。**
  过滤掉被隐藏/撤回的内容 = **不符合法规**。
  正确做法：导出全部，但**标注每条的可见性状态**（deleted/withdrawn/hidden）。

- [ ] **S-2 forum_posts 的 status='deleted' 被过滤**
  同 S-1：用户有权知道「我发过什么、什么时候被删了」。
  方案把 deleted 也过滤掉，等于**隐藏了用户自己的历史**。

- [ ] **S-3 导出范围仍不完整**
  §3 的 EXPORT_SPEC 只列了 reviews/forum_posts/favorites 三张表。
  项目还有：`forum_post_replies`、`comments`、`notifications`、
  `user_preferences`、`external_identities`、`user_sessions`（会话不该导）等。
  声称「全部数据」但只导 3 张表 = **合规承诺与实际不符**。

### 运维维度
- [ ] **O-1 无导出审计**
  §1 有异步任务、§5 有产物与 TTL，但**零审计**。
  导出是批量搬走个人数据的高价值动作，必须留痕（谁、何时、多少行、多大）。
  项目里**没有审计表**（0001 里只有 operation_records，是业务审计）。

- [ ] **O-2 无产物清理的实际实现**
  §5 说「TTL 7 天，定时清理」，但没说谁清理、怎么清理。
  项目 `rate-limit.ts:182` 明确写着「不开数据库的定时清理：它会 setInterval，
  而我们要进程能被干净关掉」。

### 性能维度
- [ ] **P-1 单次导出的内存上限未定义**
  §1 异步生成是对的，但没说分页/流式。
  用户若有 5000 帖 + 2000 评测，一次性 `.all()` 会 OOM。

- [ ] **P-2 无导出大小上限**
  方案没给「单次导出最多多少 MB / 多少行」。
