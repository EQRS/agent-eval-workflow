## 前提核实（基础项，0.5 分）

- [ ] **方案假设的东西在本仓库是否真实存在？**
  核对表/列/接口/依赖是否在 `migrations/`、`src/`、`package.json` 中真实存在。
  **注意区分**：方案声明要新建的表（有 CREATE TABLE / ALTER / 明确说「接入」某依赖）属合理；
  引用了不存在的对象且没声明 → 前提不成立。

## 必须发现（每项 1 分）

### 对抗性思维
- [ ] **S-1 批量接口的鉴权粒度变粗**
  §3「路由层统一 assertCanAdmin(ctx)，一次校验覆盖整批」。
  这本身对管理员操作是对的，但方案没说 items 里的 pluginId 是否需要逐个存在性校验。
  若某条 pluginId 不存在，SQL 静默返回 0 行，方案照样计入 updated。
  更关键：若将来开放给非管理员（作者批量改自己的插件），一次校验覆盖整批 = 漏一条就全放行。

- [ ] **S-2 错误处理导致静默失败**
  §4「某条失败时跳过，返回成功数」——调用方无法知道哪些失败了。
  100 条里 3 条失败返回 97，但哪 3 条？需要重试哪些？方案没给。

### 跨系统交互
- [ ] **C-1 无事务包裹**
  §2 的 for 循环没有事务。100 条 UPDATE 是 100 个独立事务，中途失败留下部分更新。
  §预期说「单次事务，保持一致」——与代码矛盾。

### 域外知识
- [ ] **C-2 幂等性未定义**
  §1 的 PATCH 语义：重试同一请求会怎样？
  若中间失败后重试，已成功的会被重复执行。方案没定义幂等键。
