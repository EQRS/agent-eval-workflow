## 必须发现（L3 层）

### L3 跨模块

- [ ] **项目已有错误处理，方案改变了语义**
  src/server/platform/rate-limit.ts 现在的行为是：只有 RateLimiterRes（超额）被转换，真异常**原样抛出**。项目依赖这个语义——异常时用户看到 500 而不是被放行。

- [ ] **catch 会吞掉「超额」本身**
  limiter.consume 在**超额时会 reject**（rate-limiter-flexible 的 API）。方案的 catch 会把「超额」也当成「不可用」从而**放行**——限流彻底失效。

### L4 系统性

- [ ] **fail-open 对写路径是致命的**
  项目 13 个路由用 enforceRateLimit 保护写操作（评论 5/分、举报 20/时、角色申请 3/天）。数据库故障时全部放行 = **攻击者可无限刷**。

- [ ] **数据库故障时「放行」也没用**
  限流器用同一个 SQLite。限流失败说明数据库已不可用——后面的业务写也会失败。放行只是让请求继续走到失败。

- [ ] **没有区分「存储故障」与「逻辑错误」**
  若 action 拼写错误（RateLimitAction 没有这个动作），也会抛错并被 catch 放行——**配置错误被静默吞掉**。

- [ ] **告警日志在故障时会被刷爆**
  每个请求打一条 log.warn。数据库故障时全站请求都失败 → 日志洪水，而容器日志是 10m×3 轮转，真实信息被淹。

- [ ] **没有熔断，会持续打挂掉的库**
  每次都尝试 limiter.consume。若 DB 挂起（不是拒绝），每次都要等 busy_timeout=5000——**5 秒后失败再放行**，用户等了 5 秒才得到响应。应有熔断器：连续 N 次失败后直接跳过限流。
