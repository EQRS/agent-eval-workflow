## 必须发现（每项 1 分）

### 跨系统交互
- [ ] **C-1 不同入口的校验强度本就不同**
  §2「所有写插件的地方统一调用」——
  **用户提交和管理员后台的校验要求本来就不同**。
  例如：管理员可能需要设置 status=archived，但用户提交不应该能设。
  统一校验等于**要么放宽了用户入口，要么限制了管理员**。

- [ ] **C-2 数据修复脚本不该走业务校验**
  §2 包含「数据修复脚本」——
  修复脚本的输入是**已有的脏数据**，用业务校验会直接拒掉，
  导致修复无法进行。这类脚本需要的是**绕过校验 + 事后校验**。

### 对抗性思维
- [ ] **S-1 错误提示可泄露内部结构**
  §1 的错误信息「名称非法」「描述非法」「状态非法」——
  攻击者可以通过**逐字段试探**，推断出数据模型和约束。
  应统一为「输入无效」并记录详细原因到日志。

### 域外知识
- [ ] **O-1 应保留数据库 CHECK 作为第二道防线**
  §3「删除各处的重复校验代码」——
  **应用层校验和数据库约束是两层防线，不能因为有了应用层就删掉数据库层**。
  本项目 migrations 里有大量 CHECK 约束（如 background_tasks 的 processing_state IN (...)），
  删除后若有路径绕过应用层，数据会直接写脏。

- [ ] **O-2 类型断言不是运行时校验**
  §1 最后 `return input as Plugin` ——
  **`as` 只是 TypeScript 类型断言，运行时不做任何检查**。
  校验函数返回后，调用方拿到的是「被断言成 Plugin 的任意对象」。
