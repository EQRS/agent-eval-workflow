## 必须发现（每项 1 分）

### 域外知识（算法推荐管理规定）
- [ ] **O-1 有舆论属性/社会动员能力的算法需要备案**
  《互联网信息服务算法推荐管理规定》第 24 条：
  具有舆论属性或者社会动员能力的算法推荐服务提供者，
  应当在**提供服务之日起十个工作日内**通过互联网信息服务算法备案系统填报备案。
  方案零提及备案。且**「十个工作日」是从上线起算**，不是「以后补」。

- [ ] **O-2 必须提供「关闭算法推荐」的选项**
  第 17 条：应当向用户提供**选择或者删除**针对其个人特征的标签的功能，
  以及**便捷的关闭算法推荐服务**的选项。方案只做了「展示」，没有开关。

- [ ] **O-3 用户行为采集的告知同意缺失**
  §1 采集 user_id + plugin_id + action 组合，属于**用户行为轨迹**，
  是个人信息。第 16 条要求告知用途，方案没有。

- [ ] **O-4 「相似用户」涉及向他人画像的间接推断**
  协同过滤本质是「找和你像的人」——这个「像」本身是对用户的分组。
  《个人信息保护法》第 24 条把**自动化决策**纳入规制，
  要求「保证决策的透明度和结果公平、公正，不得对个人在交易价格等交易条件上实行不合理的差别待遇」。

### 对抗性
- [ ] **S-1 行为表没有唯一约束，可被刷量污染**
  §1 没有 `UNIQUE(user_id, plugin_id, action)`。
  同一用户重复点击会插入多行，**直接污染协同过滤的权重**。
  恶意用户可以通过刷某个插件把它推上推荐位。

- [ ] **S-2 「相似用户」暴露他人隐私**
  §2 说「推荐相似用户喜欢的插件」——若前端展示「喜欢这个插件的人还喜欢 X」，
  等于**间接暴露了他人行为**。且没有最小人数阈值（k-匿名）。

### 跨系统
- [ ] **C-1 computeRecommendations 是幻影函数**
  `src/` 全仓没有 `computeRecommendations`。方案的核心算法没有实现载体。

- [ ] **C-2 「每日凌晨跑一次」与既有定时任务体系冲突**
  项目已有 `background_tasks` 队列与 `worker/scheduled.ts` 的排程。
  方案另起一套「凌晨跑」，没说明用哪个。
  且凌晨 3:00 已有备份任务（`dsh-review-backup.timer`），撞车会争抢写锁。

- [ ] **C-3 推荐结果表的写入没有分批**
  §2 用一条 `INSERT` 写全部用户的推荐。
  `synchronous=FULL` + `busy_timeout=5000`（`db.ts`）下，
  一次写几万行会**长时间持有写锁**，worker 与 web 都会撞 `SQLITE_BUSY`。
