## 前提核实（基础项，0.5 分）

- [ ] **方案假设的东西在本仓库是否真实存在？**
  核对表/列/接口/依赖是否在 `migrations/`、`src/`、`package.json` 中真实存在。
  **注意区分**：方案声明要新建的表（有 CREATE TABLE / ALTER / 明确说「接入」某依赖）属合理；
  引用了不存在的对象且没声明 → 前提不成立。

## 必须发现（每项 1 分）

### 跨系统交互
- [ ] **C-1 flag 组合爆炸**
  §1 定义了 5 个 flag，各自独立灰度。
  **5 个 flag = 32 种组合状态**，测试无法覆盖所有组合。
  且 flag 之间的交互（如 new_editor + new_upload 同时开）可能出现未预期的问题。
  方案没定义 flag 之间的依赖或互斥关系。

- [ ] **O-1 flag 生命周期管理缺失**
  §4「功能全量后删除 flag」——**没有强制机制**。
  业界称这个问题为 flag rot（开关腐化）：
  flag 上线后没人删，代码里越来越多死分支。
  需要在 flag 定义时就写「预期删除时间」，并定期扫描未删除的 flag。

### 对抗性思维
- [ ] **S-1 flag 状态可被试探**
  §2 的取模算法是**确定性的**：同一用户永远命中同一结果。
  攻击者可注册多个测试账号，**探测出每个 flag 的灰度比例**，
  从而推断未发布功能的存在。

- [ ] **S-2 环境变量可被篡改**
  §3「从环境变量读取灰度比例，支持热更新」——
  没有鉴权、没有审计。谁能改环境变量 = 谁能控制全站功能开关。

### 域外知识
- [ ] **O-2 灰度比例变更不是原子的**
  §3 热更新时，多实例可能在**不同时刻读到不同比例**，
  导致同一用户一会儿看到新功能一会儿看不到。
