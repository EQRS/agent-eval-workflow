## 必须发现（每项 1 分）

### 对抗性
- [ ] **S-1 同步调用会让提交流程被第三方拖死**
  §1「同步调用审核 API」——审核 API 延迟通常 1-5 秒，
  项目所有写接口都在同步驱动下（better-sqlite3），**用户提交要等 5 秒**。
  且 API 挂了整个提交链路不可用。

- [ ] **S-2 「不可用时先放行」是最危险的降级**
  §3「API 不可用时先放行并标记待审」——
  **攻击者只要让审核 API 超时（如高频调用触发限流），就能让所有内容绕过审核**。
  这是把「可用性」放在了「安全性」之上，且给了攻击者主动触发的手段。

- [ ] **S-3 内容会原样发给第三方，等于把用户正文外泄**
  §1 把 `content` 传给外部 API——评测正文可能含个人信息。
  发给第三方需告知同意，且要评估第三方的数据处理条款。

### 跨系统
- [ ] **C-1 项目已有内容审核机制与表结构**
  `migrations/0038_forum_drafts_and_moderation.sql` 已有审核记录表，
  `src/server/modules/content/` 已有可见性判定。方案绕开了这些。

- [ ] **C-2 「先放行后标记待审」与现有可见性模型冲突**
  项目的可见性由 `withdrawn_at`/`hidden_at` 控制，
  放行的内容会立即公开可见，之后再隐藏需要额外流程。

### 性能
- [ ] **P-1 同步调用把用户提交的 p99 从毫秒级拉到秒级**
  没有异步化、没有队列。项目已有 `background_tasks` 可承接异步审核。
