## 前提核实（基础项，0.5 分）

- [ ] **方案假设的东西在本仓库是否真实存在？**
  核对表/列/接口/依赖是否在 `migrations/`、`src/`、`package.json` 中真实存在。
  **注意区分**：方案声明要新建的表（有 CREATE TABLE / ALTER / 明确说「接入」某依赖）属合理；
  引用了不存在的对象且没声明 → 前提不成立。

## 必须发现（每项 1 分）

### 对抗性思维
- [ ] **S-1「断言 200」是假测试**
  §1「调用接口并断言 200」——200 只说明没崩，不说明业务正确。
  返回空数组的接口也是 200，但业务上完全错了。这种测试能刷覆盖率，但抓不到任何 bug。

- [ ] **S-2 自动重试掩盖真实失败**
  §3「失败时自动重试 3 次，避免 flaky」——这是把问题藏起来，不是解决。
  真实 bug 会被重试掩盖。

### 域外知识
- [ ] **O-1 覆盖率不是质量指标**
  §2「覆盖率 >= 85%」——业界共识：覆盖率衡量「执行过」，不衡量「验证过」。
  85% 覆盖率可能全是「断言 200」这种，依然零 bug 发现能力。

### 跨系统交互
- [ ] **C-1 测试与生产的数据库不同**
  方案没说测试用什么数据库。若测试用 SQLite、生产用其他，测试通过不代表生产正常。

## 加分项（各 0.5）
- [ ] A-1 指出「应断言业务结果，不只断言 HTTP 状态」
- [ ] A-2 指出「应先修 flaky 根因，不是加重试」

## 深度加分（各 1 分，需要读项目具体文件）

- [ ] **D-1 违反项目成文的验证标准**
  项目有 `scripts/verify-tests-bite.mjs`（变异验证脚本），
  且 `docs/项目规划/验收纪律.md` 把「**恒真测试**」列为头号假象，
  并明确要求 §3 的「变异验证」。
  **「断言 200」的用例无法通过任一变异实验**（删掉鉴权中间件它多半仍返回 200）。
  → 方案产出的用例在项目既有纪律下**根本无法被判定为「测试」**。

- [ ] **D-2 测试与应用的 WAL 可见性问题**
  生产库是 SQLite + WAL（.data/app.sqlite + -wal）。
  测试用「独立进程 + 独立临时库」，**跨进程写 WAL 后应用可能读不到**。
  表现为「测试绿了但应用根本看不到数据」——比红了更危险。

- [ ] **D-3 夹具数据直接落站点真实库**
  `scripts/acceptance-e2e-chain.mjs:44` 直接写 `.data/app.sqlite`（**开发时也是站点真实库**）。
  方案没规定「夹具不得落生产库」，且夹具数据**无 is_test 标记**，与真实用户数据无法区分。

- [ ] **D-4 测试身份通道无测试守护**
  `/api/testing/session` 是「不需要凭据就能创建任意站内用户并下发会话 Cookie」的入口。
  其文件头声称「生产即使设了开关也不生效」，但实现只有 4 行 NODE_ENV 判断。
  **tests/ 里没有任何用例覆盖它** —— 这是「测试体系自己成为攻击面」。
