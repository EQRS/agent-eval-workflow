## 必须发现（每项 1 分）

### 跨系统
- [ ] **C-1 server.close() 只停止接受新连接，不会等已有请求完成**
  Node 的 `http.Server.close()` 停止 listen，但**不等待进行中的请求**。
  方案用 `await sleep(5000)` 硬等，只是碰运气——
  若有请求超过 5 秒（项目有 5s busy_timeout + 慢查询），
  到点 `process.exit(0)` 会**硬切断**，请求半途失败。

- [ ] **C-2 没有处理 worker 进程**
  停 web 时会话断了，但 **worker 还在跑任务**（租约 120s、单任务上限 300s）。
  worker 被 SIGKILL 后任务处于 running 状态，要等 recoverExpired 才能回收。
  方案只管 web，生产实际有两个进程。

- [ ] **C-3 5 秒与 compose 的 stop_grace_period 15s 不匹配**
  §2 等 5 秒后 exit，§3 给 15 秒——浪费了 10 秒。
  更关键的是**没有考虑 nginx 侧的连接排空**：
  nginx 到 web 的 keepalive 连接会继续转发，需要先让 nginx 摘流。

- [ ] **C-4 没有 drain 状态的健康检查**
  停机时应让 /api/health 立即返回不健康，让负载均衡摘流。
  方案直接 sleep，期间健康检查仍返回 200，流量继续进来。

### 性能
- [ ] **P-1 固定 sleep 是反模式**
  应该等待「活跃连接数归零」而不是固定时间：
  `server.close()` 的回调在最后一个连接关闭时触发，用它比 sleep 可靠。

- [ ] **P-2 长任务没有中断信号**
  项目有批量导入（串行打 GitHub，可能跑几分钟）。
  这些请求无法在 5 秒内完成，需要可中断机制或断点续跑。
