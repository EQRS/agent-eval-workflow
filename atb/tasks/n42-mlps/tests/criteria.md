## 必须发现（每项 1 分）

### 域外知识（等级保护 2.0）
- [ ] **O-1 项目已有不可变审计表，方案重复建设**
  `operation_records`（`migrations/0001_baseline.sql`）是全站唯一审计载体，
  且 `migrations/0042_audit_immutable.sql` 已加 `BEFORE UPDATE/DELETE` 触发器。
  §1 新建 `audit_log` 是**第二套审计**，两套必然漂移。

- [ ] **O-2 新表没有防篡改，反而不满足等保要求**
  等保 2.0 的「安全审计」要求明确写着：**审计记录应受到保护，避免受到未预期的删除、修改或覆盖**。
  §1 的 `audit_log` 可以被任意 DELETE/UPDATE——**新建的表比现有的还不合规**。

- [ ] **O-3 保留 6 个月与现有备份策略冲突**
  §4 说保留 6 个月，但项目备份是 `--keep 14`（14 份，约 14 天）。
  审计日志如果只在数据库里，**14 天后的备份轮转不会删它**——
  但一旦库损坏，恢复后 6 个月的日志就只剩 14 天的备份内容。方案没考虑这个矛盾。

- [ ] **O-4 没有审计日志的访问控制**
  等保要求「审计记录只能被授权用户访问」。方案的表**没有任何访问控制字段**，
  也没有说明哪些接口能读它。

### 对抗性
- [ ] **S-1 ip 字段存明文，且来自客户端可控头**
  §2 的 `clientIp` 由应用从请求头取。项目 `client-ip.mjs` 有
  `DSH_REVIEW_TRUST_PROXY` 开关，未开启时取到的是反代地址。
  且 IP 是个人信息，明文存储无保留期。

- [ ] **S-2 「所有写操作都记一条」会造成写放大**
  全站写路径都会多一次 INSERT。`synchronous=FULL` 下每次提交都 fsync，
  等于**把所有写请求的延迟翻倍**。

### 跨系统
- [ ] **C-1 二次密码确认与 GitHub OAuth 架构冲突**
  §3 说「管理员操作需要二次密码确认」——但项目**没有密码**，
  全站是 GitHub OAuth 登录（`external_identities` 只有 provider_user_id）。
  没有密码可「二次」确认。
