## 必须发现（每项 1 分）

### 对抗性思维
- [ ] **S-1 JWT 无法吊销 → 登出后 token 仍有效**
  §2 把 token 存 localStorage，§1 有效期 7 天。
  **用户点「登出」只是前端删了 token，服务端仍认。**
  若 token 被窃取（XSS、共享设备），7 天内一直有效，无法强制下线。
  需要主动想到「会话撤销」这个安全需求。

- [ ] **S-2 角色变更不生效**
  §4「用户角色改了之后，新 token 会包含新角色」——
  **旧 token 里的 role 仍是旧的**，7 天内继续用旧权限。
  管理员降权后，被降权者仍能操作 7 天。

### 域外知识
- [ ] **S-3 localStorage 存 token 违反 OWASP 建议**
  OWASP 明确建议：JWT 不应存 localStorage（XSS 可读），应存 httpOnly Cookie。
  方案 §2 直接违反了这条行业标准。

### 跨系统交互
- [ ] **O-1 密钥轮换会导致全站登出（不只是部分 401）**
  §5「新旧密钥并存一段时间」——但方案 §3 的代码是
  `jwt.verify(token, process.env.JWT_SECRET)`，**单值、无 kid、无密钥环**。
  「新旧并存」在方案里**没有任何对应机制**。
  后果不是「部分实例 401」，而是**一旦换 secret，所有在途 token 立即验签失败 = 全站登出**。

- [ ] **O-2 三个进程都要拿到密钥**
  项目部署有 migrate / web / worker / nginx 四个服务（docker/compose.yaml）。
  migrate 是一次性进程。**漏配任一处的 JWT_SECRET = 该进程 401。**

- [ ] **O-3 不要与 SESSION_SECRET 混用**
  .env.example:45 已有 SESSION_SECRET（仅用于 OAuth PKCE 信封加密）。
  若与 JWT_SECRET 共用同一变量，轮换时会互相牵连。
