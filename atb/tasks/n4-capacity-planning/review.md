# 评审报告 · n4-capacity-planning「引入数据库连接池提升并发」

**评审结论：不通过（REJECT）。** 方案的五处核心主张逐条与仓库实测事实冲突，其中三处属于「代码写了就会崩」级别的硬伤；即使全部修好，也解决不了方案声称要解决的问题。

---

## 一、先说结论：这个方案要治的病，这个仓库没得

方案的前提是「better-sqlite3 是单连接，所有请求排队」。这句话在本仓是**两个独立的错误**：

1. **没有「排队」这个现象。** better-sqlite3 是**同步驱动**，查询在 Node 事件循环上直接执行完毕再返回，不产生 Promise、不进入任何等待队列。仓库自己的注释就是这么写的：`src/server/platform/db.ts:7-8` ——「better-sqlite3 是同步驱动，等待会阻塞所属线程，因此业务事务保持短小」。想缓解它，要么缩短事务（仓库已经在做），要么把阻塞挪出主线程。**加连接池一条都不沾**。
2. **「单连接」指的是进程内单例，不是全站一个连接。** `db.ts:66-74` 的 `getDb()` 是**进程级单例** ——「Web 与 worker 各自一个进程」。生产部署是 web + worker + 一次性 migrate 三个进程（`docker/compose.yaml:27-108`、`deploy/dsh-review-worker.service:6-8`），它们各自开着连接到**同一个库文件**。systemd 那条注释写得最清楚：「与 Web 用同一个库文件，SQLite 在 WAL 下支持多进程」。

所以真正稀缺的资源从来不是「连接数」，而是 **SQLite 的写锁（同一时刻只有一个写事务）**。把连接从 1 个变成 20 个，抢的是同一把锁。**并发上限一点没变，锁等待反而变多。**

## 二、问题清单

### P0-1 ｜ 技术方案：`createPool` 在本仓根本不存在（引错了技术栈）

**问题所在：** 方案第 1 节（`proposal.md:9-16`）写的是一段 PostgreSQL 风格的连接池配方：`createPool({ connectionString, max: 20, min: 5, idleTimeoutMillis })`。

**后果（实测取证）：**
- `package.json` 依赖里**没有 `pg`、没有 `pg-pool`、也没有任何池化库**；数据库驱动是 `better-sqlite3: 13.0.3`（同步）。
- 全仓 `src/` 搜索 `createPool|pg-pool|DATABASE_URL` —— **0 命中**。
- 本仓唯一的连接入口是 `src/server/platform/db.ts:44` 的 `openDatabase()`，内部是 `new Database(file)`，而 `db.ts:10` 白纸黑字写着：「⚠ 并行纪律：本文件由「基础组」拥有，其他模块不得自行 `new Database(...)`」。
- `connectionString / DATABASE_URL` 这个配置项在本项目中**不存在**，运行时读进来永远是 `undefined`。

→ 这段代码照抄进去，第一次调用就抛 `TypeError: createPool is not a function`。

**建议：** 整节删除重写。容量问题应围绕**真实瓶颈**展开：写事务的时长与频率、WAL checkpoint、`busy_timeout` 下的锁竞争、慢查询。如果确实需要并发能力，选项只有三条：① 把长任务移出请求线程（已有 worker 通道，应加宽而不是加连接）；② 只读查询分流到 `readonly: true` 的独立连接（`db.ts:22-23` 已经支持）；③ 换库——那是另一个量级的方案，必须单独立项并给出迁移与回滚路径。

---

### P0-2 ｜ 使用方式：三个 API 全部用错，且错误方式不一致

**问题所在：** 方案第 2 节（`proposal.md:19-23`）：
```ts
const conn = await pool.acquire();
const rows = conn.prepare('SELECT * FROM plugins').all();
await pool.release(conn);
```

**后果：**
- `pool.acquire()` —— 不存在（见 P0-1）。
- `conn.prepare(...).all()` —— better-sqlite3 的 `.all()` 是**同步**返回数组，不是 Promise；`await` 一个数组不报错但**误导读者以为这是异步链路**。真正的异步边界在 `pool.acquire()` 那一行 —— 而那一行根本不存在。
- `pool.release(conn)` —— 对 better-sqlite3 连接毫无意义：连接是进程级单例，关闭它会让整个进程的 `getDb()` 失效（`db.ts:70` 的 `singleton.close()` 分支）。
- 更严重的是**事务语义丢失**：本仓所有写操作都必须走 `src/server/platform/tx.ts:42` 的 `withTransaction()`，它靠「同一连接」才能把跨模块操作包进一个事务；而仓库明确禁止「各自提交独立事务后假装整体原子成功」（`tx.ts:6`）。池化后每次 acquire 可能是不同连接，**跨模块的原子性会静默消失** —— 这是最难查的一类 bug。

**建议：** 删除该节。若引入任何连接抽象，必须在骨架里保留 `withTransaction` 的语义并写一条不变量：「一个事务内的所有语句必须落在同一连接上」。

---

### P0-3 ｜ 池大小计算：公式的适用前提在本仓不成立

**问题所在：** 方案第 3 节（`proposal.md:26-27`）：`连接数 = CPU 核心数 × 2 + 磁盘数`，4 核 1 盘 = 9，取 20 留余量。

**后果：**
- 这个公式是 **PostgreSQL「查询主要受 I/O 与 CPU 并行度限制」** 的经验值。而 SQLite 的并发度**与核数无关** —— 由文件写锁 + `synchronous = FULL`（`db.ts:54`，每次 commit 都 fsync）决定。4 核和 64 核的 SQLite，写入并发都是 1。
- 「取 20 留余量」在 SQLite 上是**反向优化**：20 个写者争一把锁，每个都持有连接 5 秒（`busy_timeout = 5000`，`db.ts:56`）等锁，把延迟从「排队」放大成「雪崩」。仓库里有实测记录佐证这条路径（`docs/实测记录-M6多专业会诊.md:79`）：「`busy_timeout` 只有 5000ms（db.ts:56）→ 高并发下必然 SQLITE_BUSY」。
- 若真要调，能调的是 **`busy_timeout` 与 `synchronous`**，且必须给出故障模式分析（`synchronous = NORMAL` 掉电丢最后几条事务，对评测站是否可接受），而不是核数乘二。

**建议：** 删掉公式。改成「先测后定」，并把测量口径写清楚（见 P1-2）。

---

### P1-1 ｜ 背景：把「资源稀缺」判断错了对象

**问题所在：** `proposal.md:4`「现在 better-sqlite3 是单连接，所有请求排队」。

**后果：** 这个误判会导致后续所有决策跑偏 —— 方案后续三节（池配置、使用方式、池大小）全部是在解决一个不存在的问题。真实的容量风险另有其人：
- **`synchronous = FULL`**（`db.ts:54`）—— 每次事务提交都 fsync，写入吞吐的硬上限在这里；
- **同步驱动阻塞事件循环** —— 一个慢查询会卡住同进程内**所有**其他请求（包括 `/api/health`，见 P1-3）；
- **web 与 worker 共享一个库文件** —— worker 的重任务写库会直接抬高 web 的锁等待。

**建议：** 背景一节改为陈述可测量的现状（附实测数据），并把「为什么现在必须扩容」写成触发条件（如 P95 延迟、任务积压时长、锁等待次数），而不是笼统的「提升并发」。

---

### P1-2 ｜ 预期：3-5 倍与「不再排队」都是未测承诺

**问题所在：** `proposal.md:32-34`「并发请求不再排队 / 吞吐提升 3-5 倍」。

**后果：** 直接违反项目自己的验收纪律 —— `docs/项目规划/实施顺序与验收.md:62`：「具体容量与响应目标依据预期流量另定，**不把未测的吞吐数写成承诺**」。而且这个承诺**在原理上不可能成立**（见第一节：写并发上限由写锁决定，与连接数无关）。一旦写进方案并被引用，后续验收会拿一个物理上达不到的数字做标准。

**建议：** 删掉数字。改为「验收方式」：在目标 Linux 环境 + 固定镜像下，记录并发读写、P50/P95 延迟、锁等待次数、任务积压时长，与改动前基线对比。指标口径要写明分母（哪些端点、哪类流量、多少并发）。

---

### P1-3 ｜ 监控：往 `/api/health` 塞池状态，与既有设计冲突且指标本身无意义

**问题所在：** `proposal.md:29-30`「暴露池状态到 /api/health」。

**后果：**
- `/api/health` 已经是一套完整且有明确设计意图的契约：`src/server/platform/health.ts:56-147` 输出 `db.readable / db.foreign_keys / db.journal_mode / db.required_tables / disk.free / worker.heartbeat`，并且 `health.ts:5-7` 明确「它**不做业务统计**」「这个端点可能是公网可达的，业务数字不该顺手泄露」。
- 池状态（空闲数/等待数）在 SQLite 下**没有对应的物理量**，暴露一个恒为常数的指标，会让运维误以为并发是健康的。
- 更危险的是：健康检查本身走的是同一个同步连接，慢查询阻塞事件循环时 **`/api/health` 会一起挂**，编排器会把「只是慢」误判成「进程死了」而执行重启 —— 这是比不监控更坏的结局。

**建议：** 不动 `health.ts` 的既有检查项。若要观测容量，正确位置是 `scripts/diagnose.mjs`（直连库、仅运维可跑，见 `health.ts:8`），并新增真正有信号的指标：**写事务持有时长分布、锁等待次数与累计等待毫秒、WAL 文件大小与 checkpoint 间隔、后台任务积压时长**。

---

### P1-4 ｜ 缺失：没有回滚路径、没有阶段划分、没有与双副本/部署的联动

**问题所在：** 整个方案只有「改什么」，没有「怎么退」。

**后果：** 本仓是双副本部署 —— systemd（`deploy/`）与 docker compose（`docker/compose.yaml`）两套并行，且 `compose.yaml:26` 注明 migrate 是「唯一维护进程」。任何触及连接层的改动，若不同步两套部署的进程模型，会出现「一个副本改了、另一个没改」的半状态。评审要求（工作纪律第 6 条）在这里是硬约束。

**建议：** 方案必须补三件事：① 改动涉及的部署面（`deploy/*.service` + `docker/compose.yaml` 逐项列出）；② 回滚判据（什么指标变坏就以什么方式回退，退到什么配置）；③ 灰度与验证节点（先在只读查询上引入独立连接，观察一周再谈其他）。

## 三、修改建议（按优先级）

| 优先级 | 动作 |
|---|---|
| **必修** | 删除第 1、2 节全部代码（引错技术栈 + API 全错） |
| **必修** | 重写「背景」，用实测数据说明到底缺什么；若结论是「缺写入并发」，则本方案整体方向作废 |
| **必修** | 删除第 3 节公式与第 4 节「3-5 倍」，改为可验收的测量口径 |
| **应当** | 监控需求改挂 `scripts/diagnose.mjs`，指标换成写锁/积压/checkpoint 三类 |
| **应当** | 补回滚路径与两套部署副本的联动清单 |
| **可选** | 若目标真的是「读多写少的并发」，单独提案：只读连接分流（`db.ts:22-23` 已支持），与连接池是两个完全不同的问题 |

## 四、如果一定要从这条路走，唯一站得住的最小版本

必须承认：本仓确实**可以**开多个连接，`openDatabase` 已经支持 `readonly` 与自定义 `busyTimeoutMs`（`db.ts:19-26`）。站得住的用法只有一种 —— **把只读查询分流到独立的只读连接，绝不池化写连接**：

- 写：仍然只有 `getDb()` 这个进程级写单例，所有写经过 `withTransaction`（`tx.ts:42`），保证跨模块原子性；
- 读：`openDatabase({ file, readonly: true })` 的少量连接，仅用于 `withRead`（`tx.ts:55`）路径；
- 规模：2-3 个只读连接足够，不需要 20；
- 验证：对比改动前后的 P95 读延迟与写锁等待次数，写侧指标**不得变差**。

即使这个最小版本，也需要先证明「读查询确实在阻塞事件循环」——而在拿到实测基线之前，连这一点都还没有证据。
