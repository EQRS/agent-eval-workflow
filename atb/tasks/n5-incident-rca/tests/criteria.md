## 前提核实（基础项，0.5 分）

- [ ] **方案假设的东西在本仓库是否真实存在？**
  核对表/列/接口/依赖是否在 `migrations/`、`src/`、`package.json` 中真实存在。
  **注意区分**：方案声明要新建的表（有 CREATE TABLE / ALTER / 明确说「接入」某依赖）属合理；
  引用了不存在的对象且没声明 → 前提不成立。

## 必须发现（每项 1 分）

### 对抗性思维
- [ ] **S-1 不记录原因 → 无法定位根因**
  §1「**不记录错误堆栈和具体原因**，避免泄露内部实现」——
  **这是安全过度的典型案例**。500 错误没有堆栈，就无法知道错在哪。
  正确做法：堆栈写内部日志（不返回给客户端），而不是不记录。
  项目的 errors-http.ts 已有「白名单构造响应」机制，正是这个思路。

### 跨系统交互
- [ ] **C-1 只记路径不足以定位**
  §2 的排查步骤「按路径找到对应代码」——
  但 500 可能来自**下游服务**（数据库、外部 API），路径是同一个。
  需要 request_id 串联全链路，方案没提。

- [ ] **C-2 三方对照缺失**
  排查需要**日志 + 指标 + 代码**三方对照。
  方案只有日志，指标只有「500 总数」，**没有 latency、没有下游调用**。

### 域外知识
- [ ] **S-2 告警阈值无依据**
  §3「500 错误数超过 100/分钟时告警」——
  没有基于 SLO（如可用性 99.9% → 允许 ~43 次/天）。
  100/分钟 = 14 万/天，早就远超 99.9% 可用性了。
