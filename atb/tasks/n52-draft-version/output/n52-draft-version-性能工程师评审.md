# N52「草稿保存的版本控制」方案 · 性能工程师评审

> 评审对象：`atb/tasks/n52-draft-version/environment/proposal.md`（28 行）
> 评审身份：性能工程师（写路径成本 / 自动保存节拍 / 索引与写放大 / 并发压测）
> 事实基线：`src/server/modules/reviews/index.ts`、`src/components/review-editor.tsx`、`src/packages/common/autosave.ts`、`src/server/platform/{db,tx}.ts`、`migrations/0001_baseline.sql`、`migrations/0018_draft_soft_delete.sql`

## 0. 结论

**方案描述的核心机制本仓已经实现且更强（原子 CAS + 幂等回执），照方案改是性能与正确性上的双重退步。**

性能面三个关键判断：

1. **"每 30 秒自动保存"这个前提与现实不符**：本仓自动保存是**停笔 5 秒**触发（`autosave.ts:11-12`），用户可配 `0/3/5/10/30`（:9）。按方案改成"每 30 秒"实际上是把节拍**拉到最慢档**，属于**降低写频率**——用"每 30 秒一次 UPDATE"作为性能风险论据，对着的是一个本仓更激进的现状。
2. **本仓写路径比方案多两次读、一次 INSERT，但这是必要成本**：`saveDraft`（`reviews/index.ts:612-691`）在一个事务里做「读回执 → 读草稿行 → 原子 UPDATE → 写回执」，共 **2 读 + 1 写 + 1 写（回执）= 4 次语句、1 次 fsync**。方案那段只有 1 次 UPDATE，**省掉的是幂等与归属校验，不是性能**。
3. **真正的性能风险不在"每 30 秒一次"，而在两处方案完全没提的写放大**：`draft_save_receipts` 会**永久**累积（没有任何清理路径，§4），以及 30 秒自动保存会在**不判断内容是否变化**的情况下反复推进版本（§5 的 CAS 空转）。

## 1. 自动保存节拍：30 秒不是本仓的现状，也不是本仓的最坏情况 —— proposal 第 20–21 行

**① 问题**：方案第 20–21 行「编辑器每 30 秒自动保存一次」，把它当成既有事实来讨论性能风险。

**② 后果（核实依据）**：
- 本仓实际是**防抖式**自动保存：`review-editor.tsx:353-412` 的 `setTimeout(..., autosaveMs)`，且 `review-editor.tsx:372` 在**内容摘要未变时直接返回**（`if (digest === lastSavedDigestRef.current) return;`）——**不产生请求**。
- `autosaveMs` 来自用户偏好，白名单是 `[0,3,5,10,30]`（`packages/common/autosave.ts:9`），**默认 5 秒**（:11-12）。
- 所以按本仓现状，一个持续输入的用户产生的写频率**远高于**"每 30 秒一次"：停笔 5 秒即保存，长文写作中可达**每分钟 3–10 次**；方案改成固定 30 秒反而是**降低**服务端压力（但会显著牺牲"停笔即存"的体验与未保存窗口）。
- 这意味着：**方案若以"30 秒"为由担心写压力，方向反了**；若以"减少写"为目的去改，真正该做的是**合并/节流**（见 §5），而不是改成固定 30 秒。

**③ 建议**：
- 方案里把节拍写成「防抖：停笔 N 秒，N ∈ {0,3,5,10,30}，默认 5」——这是现状，不是提案。
- 如果目标是降写压力，给一套**节流 + 合并**设计：同一草稿在途保存未返回时，**不再发第二次**（已经有 `busy` 保护，`review-editor.tsx:965` 的按钮与 :308 的状态机），并给一个"最少间隔"（例如 2 s）作为服务端侧兜底。

## 2. 写路径成本账：本仓是 1 个事务 4 条语句 1 次 fsync；方案只有 1 条 UPDATE —— proposal 第 8–18 行

**① 问题**：方案 §1 只展示了一条 `UPDATE`，隐含"一次保存 = 一条语句"的成本模型。

**② 后果（核实依据，给出可核算的数字）**：
- 本仓 `saveDraft`（`reviews/index.ts:627-690`）在一个 `withTransaction` 里：
  1. `SELECT ... FROM draft_save_receipts`（主键 `(draft_id, request_key)`，`0001_baseline.sql:215`）——索引定位；
  2. `SELECT payload FROM content_drafts WHERE id = ?`（**仅回执命中时**，:643-647）；
  3. `UPDATE content_drafts ... WHERE id = ? AND save_version = ?`（:664-670）；
  4. `INSERT INTO draft_save_receipts`（:683-687）。
- `db.ts:52-55`：`journal_mode = WAL` + `synchronous = FULL`。**一个写事务 = 一次 WAL 提交 + 一次 fsync**，与语句条数关系不大；**决定成本的是事务数，不是语句数**。
- 因此方案"1 条 UPDATE"并没有省下 IO 次数（仍然是 1 个事务 1 次 fsync），**省下的是幂等回执与归属校验**——而按方案第 3 行（多设备同时编辑）恰恰最需要这两样。
- 反过来算真实规模：按默认 5 秒防抖、活跃写作用户 U，写入 QPS ≈ `U × 0.2`（每 5 秒一次）。100 个持续写作的用户 ≈ **20 writes/s**，而 `synchronous = FULL` 下单次 fsync 在 SSD 上约 0.3–1 ms（HDD 上 5–10 ms）。**是否成为瓶颈取决于磁盘类型，方案没有给出任何磁盘假设**。

**③ 建议**：
- 方案里把「每次保存 = 1 个事务 = 1 次 fsync」写清楚，并给出**目标磁盘类型下的 fsync 实测**（一次 `INSERT` 的耗时可从 `server.mjs` 的 `duration_ms` 里取 `PUT /api/drafts` 的分布）。
- 若要降 fsync 成本，正确做法是**合并写**（把回执 INSERT 与草稿 UPDATE 放在同一事务——本仓已经这样做了），而不是砍掉回执。

## 3. 检查与更新非原子：不仅是正确性问题，也是**重试成本**问题 —— proposal 第 12–17 行

**① 问题**：方案第 12-14 行 `if (expectedVersion !== current.save_version)` 是一次读，第 15-17 行的 `UPDATE` 是另一次语句，**没有放进同一个事务，也没有把版本条件写进 WHERE**。

**② 后果（性能视角）**：
- 两个客户端同时读到 version=5 都通过检查，都执行 UPDATE → **两次都是全表写放大**，其中一次**白写**（数据被覆盖但事务已经付出完整的 fsync 代价）。在 `synchronous = FULL` 下，**白写的成本与有效写相同**。
- 更糟的是它会**制造重试**：客户端检测不到冲突 → 无重试 → 用户看到"保存成功"但内容丢失；下次发现时已经要重放整段编辑。**延迟的重试比立即的冲突贵得多。**
- 本仓的做法是**把版本条件写进 WHERE**（`reviews/index.ts:668` 的 `WHERE id = ? AND save_version = ?`），受影响行数 0 就是冲突（:672-678）——**一次写、零白写、零重试**。这是"并发下最便宜"的写法。
- 补充一个方案没提的成本：**重放判定必须先于 CAS**（`reviews/index.ts:605-607` 的注释原文说明了原因）——否则带着旧 `expectedVersion` 的重放会被判成"真冲突"，客户端重试一次就多一次**必然失败**的事务。

**③ 建议**：照 `reviews/index.ts:664-678` 的三步走：**回执优先 → 原子条件更新（版本进 WHERE）→ 成功才写回执**。这是"零白写 + 零假冲突"的唯一组合。

## 4. `draft_save_receipts` 的写放大与无清理：方案没有提到它，但它是本需求真正的容量风险 —— proposal 全篇

**① 问题**：方案要让"每次保存"带版本号，但完全没提**保存记录本身的存储**。

**② 后果（核实依据）**：
- `draft_save_receipts`（`0001_baseline.sql:208-218`）每条保存**新增一行**，行里含 `payload_digest`（64 字符）与 `request_key`、时间戳。**没有 TTL、没有归档策略**。
- 按 §1 的真实节拍（默认 5 秒防抖）估算：一个持续写作的用户 1 小时 ≈ 200–600 次保存；**一次编辑会话（比如写一篇评测 2 小时）就是上千行**。10 个作者 × 每次会话 → 数万行；再乘上"回执永远不删"。
- 目前的唯一清理路径是**草稿被删除时整批清掉**（`reviews/index.ts:401`：`DELETE FROM draft_save_receipts WHERE draft_id = ?`），也就是说：**只要用户不删草稿，回执就无限增长**；草稿是长期的（`0018` 的软删除设计本就假设草稿会存活很久），所以**这是单调增长的表**。
- 体积影响是实打实的：每行 ≈ 200 B（含索引），10 万行 ≈ 20 MB。它会与业务表挤同一个库文件，而 `health.ts:88-97` 的 `disk.free` 阈值是 200 MB——**回执表的增长是这条阈值的主要消耗者之一**（与日志、媒体并列）。
- 更关键的是**写放大**：每条回执都是一个 `INSERT`，在有主键索引的情况下要维护 B-tree；表无限增长会让 **写事务的复杂度从 O(1) 逐步劣化**，而这正是"保存"这条最高频的路径。

**③ 建议**：
- 给回执表一条**保留策略**（例如"保留最近 N 条 / 最近 7 天"），并放在**删除草稿时**与**保存时**两个入口统一执行（保存侧用一个便宜的 `DELETE ... WHERE draft_id = ? AND saved_at < ?`）。
- 在方案里给出**增长率估算**：`回执行数 ≈ 日活跃作者 × 人均保存次数/日 × 保留天数` 与对应的 MB 数。

## 5. 自动保存的空转：CAS 换来的冲突，可能在**同一个人**身上反复发生 —— proposal 第 12–17 行 + 第 20–21 行

**① 问题**：方案第 12-14 行把 `expectedVersion` 当作"一定对得上"的输入，但我们的现实是**同一个编辑器也会并发**。

**② 后果（核实依据）**：
- `review-editor.tsx:321-322` 的注释承认了这个问题："手动保存优先：清掉待执行的自动保存，避免**两次 PUT 抢同一个 expectedVersion**"。也就是说，**同一标签页内的手动保存与自动保存本就可能撞版本**。
- 一旦撞车落到方案 §3 的路径（"提示用户刷新，丢失本地修改"），结果就是**用户自己把自己的修改丢了**——这不是"多设备"场景，是**单设备**场景。对性能的影响是：冲突 → 刷新 → 重新加载整份 payload（正文可能是几十 KB 的 Markdown 块）→ 再存一次，**一次冲突的成本 ≈ 一次全量读取 + 一次 UI 重建**。
- 本仓在这条路径上做了两件事来避免它：保存成功后**回填 `saveVersion`**（`review-editor.tsx:308、402`）与 **`lastSavedDigestRef` 短路**（:372）——即"内容没变就不发请求、发了就一定能拿到新版本"。方案两者都不提。

**③ 建议**：
- 方案里必须写：**保存响应返回新版本并立即回填**（否则下一次自动保存必然用旧版本 → 必然冲突）。
- 用**内容摘要短路**：本地摘要与上次成功保存一致则不发送（本仓 :372 的做法），这能把"挂着不动的编辑器"的写频率降到 **0**。

## 6. 索引与查询形态：方案没有给出任何索引依据 —— proposal 第 12–17 行

**① 问题**：方案的两条语句都只按主键/草稿 id 走，但**冲突检查读的是 `save_version`**，方案没有说明读路径怎么建。

**② 后果（核实依据）**：
- 本仓的读路径是 `WHERE id = ? AND deleted_at IS NULL`（`reviews/index.ts:214-224`），走主键 → **O(log n)**，没有问题。
- 但如果按方案拿 `current.save_version` 单独做一次 `SELECT` 再比较，就**多一次往返**；而如果实现者为了"更准"把它写成 `SELECT ... WHERE save_version = ?`，就需要为 `save_version` 建索引——而 `save_version` 的**区分度极低**（每份草稿 0..N，多数是 0/1），**建了也不会被用**，只会增加写入成本。这属于典型的"为了校验而增加索引，反而拖慢写"。
- `content_drafts` 现有的索引只有 `uq_drafts_review`（`0018:16-17`，部分唯一索引）与 `idx_drafts_owner_active`（`0018:19`）。**没有任何索引支持"按版本号查"**——这是对的，方案不应该引入。

**③ 建议**：明确写"版本校验走主键读 + WHERE 条件"，**不新增索引**；如果确实要优化保存读路径，考虑的是 `(id, save_version)` 的覆盖索引（让 CAS 的读不回到表），而不是给 `save_version` 单列建索引。

## 7. 压测与验收：方案第 26–28 行的"预期"不可测 —— proposal 第 26–28 行

**① 问题**：「不会互相覆盖」「用户知道发生了什么」都是定性描述。

**② 后果**：无法证伪，也无法在变更后判断是否退化。性能侧尤其需要一条**冲突率**指标——它是"节拍是否合适"的唯一客观依据。

**③ 建议**（建议直接写进方案）：

| # | 判据 | 怎么测 |
|---|---|---|
| 1 | 单次 `PUT /api/drafts` 的 p50/p95 | 从 `server.mjs` 的 `duration_ms` 取，改动前后对照 |
| 2 | 冲突率（409 占比）在**单设备连续写作**下应 **= 0** | 模拟 60 秒连续输入 + 中途手动保存 |
| 3 | 冲突率在**双设备**下应等于"真并发"的比例，且每次冲突只产生 1 次失败事务 | 两个客户端各持旧版本同时保存 |
| 4 | `draft_save_receipts` 行数增长率与保留策略生效 | 压测后统计行数 |
| 5 | 空转写为 0：编辑器挂起 10 分钟不发请求 | 网络面板计数 |

## 8. 一句话给作者

方案要解决的问题（并发保存互相覆盖）在本仓**已经解决，而且用的是并发下最便宜的写法**：版本条件进 `WHERE` 的原子 CAS（`reviews/index.ts:664-678`）+ 幂等回执（`0001_baseline.sql:208-218`）+ 客户端回填版本与内容摘要短路（`review-editor.tsx:308,372,402`）。**方案真正该补的不是这些，而是它没写的那一条：回执表的无限增长（§4）——这才是这次改动里唯一确定会随时间恶化的性能风险。**
