## 前提核实（基础项，0.5 分）

- [ ] **方案假设的东西在本仓库是否真实存在？**
  核对表/列/接口/依赖是否在 `migrations/`、`src/`、`package.json` 中真实存在。
  **注意区分**：方案声明要新建的表（有 CREATE TABLE / ALTER / 明确说「接入」某依赖）属合理；
  引用了不存在的对象且没声明 → 前提不成立。

## 必须发现（每项 1 分）

### 对抗性
- [ ] **S-1 按 IP 限流对分布式攻击无效，且表里根本没有 IP 列**
  §1 的查询是 `SELECT COUNT(*) FROM users WHERE created_at > ?`——
  **这是按全站注册总数限制，不是按 IP**，正常用户也会被误伤（全站 1 小时超 10 个就没人能注册）。
  且 users 表没有 ip 列（只有 10 列），方案想按 IP 但没有任何存储。

- [ ] **S-2 攻击者可换 IP 绕过，且 IPv6 空间无限**
  即便加了 ip 列，攻击者用代理池换 IP 即可绕过。IPv6 下单个用户可拥有海量地址。

- [ ] **S-3 手机验证引入新的合规与成本问题**
  §3「新用户需绑定手机号」——手机号是敏感个人信息，
  需单独告知同意；且短信成本与供应商依赖未评估。

### 跨系统
- [ ] **C-1 项目已有 rate-limiter 基础设施，方案重复造轮子**
  `src/server/platform/rate-limit.ts` 已有完整的限流实现（rate-limiter-flexible + 数据库表）。
  方案另写一套 COUNT 查询，既慢（全表扫）又不复用现有配置。

- [ ] **C-2 注册走 GitHub OAuth，没有传统注册表单**
  项目的注册是 GitHub 登录自动建号（identity/service.ts），
  **不存在「注册表单」这个入口**，图形验证码与手机验证无处挂载。
