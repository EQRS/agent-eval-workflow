## 前提核实（基础项，0.5 分）

- [ ] **方案假设的东西在本仓库是否真实存在？**
  核对表/列/接口/依赖是否在 `migrations/`、`src/`、`package.json` 中真实存在。
  **注意区分**：方案声明要新建的表（有 CREATE TABLE / ALTER / 明确说「接入」某依赖）属合理；
  引用了不存在的对象且没声明 → 前提不成立。

## 必须发现（每项 1 分）

### 跨系统交互
- [ ] **C-1 缓存击穿（stampede）**
  §1 的 getSettings 没有 single-flight。
  缓存过期瞬间，N 个并发请求同时 miss → 同时全表扫 site_settings。
  项目页面全 force-dynamic，没有 CDN 兜底，压力全落 SQLite。

- [ ] **C-2 缓存在模块级变量，多进程下不一致**
  §1 用模块级 `let cached`。项目有 web + worker 两个进程（docker/compose.yaml）。
  若 worker 改了设置，web 的缓存不会失效。

### 域外知识
- [ ] **O-1 60 秒 TTL 与「管理员改设置立即生效」矛盾**
  §2 说改设置后清缓存，但**只在同一进程内清**。
  §3 说「单进程部署所以没问题」——但项目实际有 worker 进程。

- [ ] **O-2 内存泄漏：cached 永不释放**
  §1 的 `cached` 是模块级变量，**只会在下次刷新时被替换**，不会累积。
  但若 site_settings 表很大（比如存了很多配置），一次全表加载可能吃掉内存。

### 对抗性思维
- [ ] **S-1 缓存的可能是敏感配置**
  site_settings 里可能有 `forum.enabled` 等开关，也可能有敏感项。
  进程内缓存等于把配置明文放在内存里。若进程被 dump，配置会泄露。
