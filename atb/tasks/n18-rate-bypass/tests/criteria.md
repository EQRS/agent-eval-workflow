## 必须发现（每项 1 分）

### 对抗性
- [ ] **S-1 表设计没有唯一约束，同一毫秒重复命中会主键冲突**
  §2 的 `PRIMARY KEY (key, hit_at)`——同一 key 在同一毫秒多次请求会主键冲突，
  直接抛错变成 500。攻击者可以利用这点制造错误。

- [ ] **S-2 每次请求写一次库，本身成为 DoS 放大器**
  §2「每次请求插入一条」——限流器本是为了防 DoS，
  结果**自己成了写放大器**。SQLite 单写者下，高频请求会把写锁占满。

### 跨系统（真实约束）
- [ ] **C-1 项目已有数据库限流实现，方案重复造**
  `migrations/0006_rate_limiter.sql` 已有 `rate_limiter_flexible` 表，
  `src/server/platform/rate-limit.ts` 已在用。方案新建表是重复。

- [ ] **C-2 rate-limiter-flexible 已支持数据库存储，不需要自写**
  该库有 RateLimiterSQLite / RateLimiterPrisma 等 adapters，
  方案手写 SQL 等于放弃库已有的原子性与清理逻辑。

### 性能
- [ ] **P-1 统计窗口条数需要范围查询，没有合适索引**
  §2 表的主键是 (key, hit_at)，查询 `WHERE key = ? AND hit_at > ?` 可用主键前缀，
  但**清理时的 `WHERE hit_at < ?` 无法用主键**（第一列是 key），会全表扫。
