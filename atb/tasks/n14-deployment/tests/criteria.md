## 前提核实（基础项，0.5 分）

- [ ] **方案假设的东西在本仓库是否真实存在？**
  核对表/列/接口/依赖是否在 `migrations/`、`src/`、`package.json` 中真实存在。
  **注意区分**：方案声明要新建的表（有 CREATE TABLE / ALTER / 明确说「接入」某依赖）属合理；
  引用了不存在的对象且没声明 → 前提不成立。

## 必须发现（每项 1 分）

### 跨系统交互
- [ ] **C-1 切换点不原子**
  §3「代码改成读 plugins_v2，部署上线」——
  **滚动部署期间，新旧实例同时存在**：
  旧实例写 plugins，新实例写 plugins_v2。
  双写代码是否在两个版本里都有？方案没说。
  若有实例只写一边，切换后数据会丢。

- [ ] **C-2 迁移历史数据与双写有竞态**
  §2 的 INSERT SELECT 是**一次性快照**。
  若此时有写入（双写只写了两边，但 INSERT SELECT 可能读到中间态），
  会导致 plugins_v2 里既有迁移数据又有双写数据 → **主键冲突或重复**。

### 对抗性思维
- [ ] **S-1 回滚窗口内数据不一致**
  §4「确认无误后删除 plugins 表」——**删了就无法回滚**。
  且删除前如果需要回滚代码，旧代码读 plugins 但新写入只在 v2，
  **回滚会丢数据**。

### 域外知识
- [ ] **O-1 时序：代码先上还是库先改**
  §1 双写、§2 迁移、§3 切换、§4 清理——
  这是**四阶段迁移（expand-contract）的正确顺序**，
  但方案**没说明每个阶段之间要间隔多久**、如何验证进入下一阶段。
  正确做法：每阶段间观察期，用指标验证（如 v2 的写入量是否等于 v1）。

- [ ] **O-2 主键结构变更的特殊风险**
  §背景「要改主键结构」——
  **改主键意味着外键引用全部失效**。
  本项目 background_tasks、operation_records 等表都有外键指向 plugins。
  方案完全没提外键处理。
