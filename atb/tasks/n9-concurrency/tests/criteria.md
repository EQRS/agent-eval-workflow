## 前提核实（基础项，0.5 分）

- [ ] **方案假设的东西在本仓库是否真实存在？**
  核对表/列/接口/依赖是否在 `migrations/`、`src/`、`package.json` 中真实存在。
  **注意区分**：方案声明要新建的表（有 CREATE TABLE / ALTER / 明确说「接入」某依赖）属合理；
  引用了不存在的对象且没声明 → 前提不成立。

## 必须发现（每项 1 分）

### 跨系统交互
- [ ] **C-1 无限重试 + 无退避 = 活锁**
  §2 的 `while (true)` 没有次数上限、没有退避。
  并发拖拽时大量请求同时冲突，全部立刻重试 → 活锁。
  SQLite 单写者下更糟：每轮都是同步查询，阻塞整个事件循环。

- [ ] **C-2 单条更新用 while 循环是过度设计**
  §2 只更新一行的 position。**单行更新用乐观锁过于复杂。**
  正确做法：`UPDATE ... WHERE user_id = ? AND plugin_id = ?`（无 version 比较），
  因为同一用户同一插件只有一行，不存在并发冲突。

### 对抗性思维
- [ ] **S-1 恶意制造冲突**
  攻击者持续更新某个收藏的 position，可让其他请求一直冲突。
  方案没有按用户限流。

- [ ] **S-2 拖拽场景的幂等缺失**
  用户拖两次，两次请求都会执行。若第二次基于旧 position，
  会导致顺序错乱。方案没有 request_key 幂等。

### 域外知识
- [ ] **O-1 version 初值 0 的语义未定义**
  新收藏插入时 version=0。若两个请求同时首次更新，都读到 version=0。
  方案没说明这种情况。

- [ ] **O-2 position 唯一性没有保证**
  §1 加 position 列但**没有 UNIQUE(folder_id, position)**。
  两个收藏可能有相同 position，排序结果不确定。
