# N55「表单防重复提交」方案 · 安全工程师评审

> 评审对象：`atb/tasks/n55-dup-submit/environment/proposal.md`（32 行）
> 评审身份：安全工程师（边界：重复提交是否可被利用 / 幂等是否真的成立 / 越权面 / 审计完整性）
> 事实基线：`src/server/workflows/submit-review.ts`、`src/server/modules/reviews/index.ts`、`src/server/modules/operations/service.ts`、`src/server/platform/{request-id,rate-limit,tx}.ts`、`src/components/review-editor.tsx`、`migrations/0001_baseline.sql`、`migrations/0042_audit_immutable.sql`、`docker/compose.yaml`、`deploy/*.service`

## 0. 结论

**这是「倒退」而不是「补强」——而且倒退的正是安全边界。**

方案的两处措施在仓库里**都有更强、已经上线、且有数据库约束兜底的对应实现**：

| 方案给的措施 | 真实强度 | 仓库里已有的实现 |
|---|---|---|
| §1 前端 `disabled` | **0**（不是安全边界，攻击者直接打 API） | 前端这块已经做了（`review-editor.tsx:965` 的 `busy`） |
| §2 进程内 `Set<userId>` | **0**（多进程失效、重启丢失、跨实例无效，且故障时 fail-open） | `content_submissions` 的 `UNIQUE(submitted_by, request_key)`（`0001_baseline.sql:321`）+ 摘要比对（`submit-review.ts:177-191`）+ `draft_save_receipts` 主键（`0001_baseline.sql:215`）+ `operation_records` 的 `UNIQUE(action_type, operation_key)`（`operations/service.ts:97-158`，由 `0042` 两个触发器锁死不可删改） |

**最关键的一句**：方案 §2 的 `inFlight: Set<string>` 用 **`userId` 做键**，这是把幂等退化成了「每个用户同一时刻只能有一个请求」——它防不住真正的重复提交（多进程、重启、并发），却会**误伤正常的多标签页操作**，并引入一条**永久拒绝服务**的路径（§6）。

## 1. §1 前端禁用按钮：不是防护，只是 UX —— proposal 第 8–18 行

**① 问题**：方案把 `disabled={submitting}` 列在「技术方案」里，与 §2 的「后端加锁」并列，暗示两者构成一道防线。

**② 后果**：
- `disabled` 只在**当前渲染的 DOM** 上生效。直接 `curl`、浏览器重放、网络层重试（代理/客户端 SDK 的自动重试）、以及任何绕过 React 状态的调用都能重复打到服务端。**它拦不住任何人。**
- 现状本身也是「前端有、后端也有」：`review-editor.tsx:965` 的提交按钮已被 `busy` 状态禁用，同文件 `:321-322` 还特意处理了「手动保存与自动保存抢同一版本」。**前端这块已经做了**，方案等于把已知事实写进「技术方案」，制造「已经在防」的错觉。
- `disabled` 的真实价值是**减少无意义的请求**（省带宽、省服务端负载），这个价值成立；但把它当**安全措施**写进方案，会让评审者以为「重复提交已被拦住」，从而**放过真正的服务端幂等审查**。

**③ 建议**：方案里把 §1 明确降级为「用户体验优化（减少无谓请求），**不构成安全边界**」，并写明「安全性由服务端的 `request_key` 幂等保证（见 §4）」。

---

## 2. §2 进程内 Set：在**多进程 + 重启 + 多实例**下全部失效，且失效方向是「放行」 —— proposal 第 20–29 行

**① 问题**：`const inFlight = new Set<string>()` 是**进程内**内存状态。

**② 后果（核实依据）**：
- **多进程**：本仓 web 与 worker 是两个独立进程（`docker/compose.yaml:44-109` 的 `web`/`worker` 两个 service；systemd 侧是 `deploy/dsh-review-web.service` 与 `deploy/dsh-review-worker.service`）。worker 里触发的发布/评论流程**完全看不到** web 进程的 Set。
- **重启**：`web` 是 `restart: unless-stopped`（`compose.yaml:68`）、systemd 侧 `Restart=always`（`dsh-review-web.service:20-21`）。**任何一次 OOM/部署/崩溃都会清空 Set**，而这正是「用户会重试」的时刻。
- **多实例**：只要将来起第二个 web 实例（或蓝绿部署时新旧并存），两个进程各自维护一份 Set，**互不可见**。
- **失败方向是放行（fail-open）**：Set 里没有记录 → 不拦截 → 请求继续 → 重复创建。**这与安全机制应有的 fail-closed 完全相反。** 一个只在「恰好单进程、恰好没重启」时生效的机制，不能被称作「锁」。
- 时序上，`finally` 确实能覆盖抛错路径（这点方案写对了）；但它覆盖不了「`add` 之后被 SIGKILL」这一类——而那种场景下进程内的 Set 本身也随之消失，**既没有留下审计痕迹，也没有产生任何拦截**。

**③ 建议**：删除 §2。若确实需要「请求进行中」的节流层，正确落点是**共享状态**：`rate-limiter-flexible` 已经接好（`rate-limit.ts:172-188`，`storeType: 'better-sqlite3'`，计数在库里、跨进程共享、重启不丢），把它当短窗口并发限制即可，**不需要新造内存 Set**。

## 3. 用 `userId` 作锁键：把「防重复」变成「跨请求互斥」，误伤与侧信道同时出现 —— proposal 第 24–28 行

**① 问题**：`inFlight.has(userId)`——锁的粒度是**整个用户**，不是「这一次提交」。

**② 后果**：
- **误伤正常操作**：同一用户开两个标签页、或前端在提交评测的同时后台还在自动保存草稿（`review-editor.tsx:321-322` 正是为这个并发写的），会撞上 `err.conflict('请勿重复提交')`——**用户什么都没做错，却被告知「请勿重复提交」**。这会把一次正常编辑变成失败请求，并**诱发重试**（正是方案想消除的行为）。
- **语义污染**：真正的重复提交是「同一份内容提交了两次」；锁键是「同一用户同一时刻只能有一个请求」。两者**不是一回事**。用后者实现前者，等于用一个更粗的锁代替更精确的判定。
- **侧信道**：锁的粒度到 `userId` 时，任何能触发「该用户已有在途请求」的路径都会让该用户的下一次写操作被拒——**可用性被绑在攻击者可控的时序上**。仓库对「按身份聚合的共享状态」有过明确取舍：`rate-limit.ts:5-12` 的头注释写明「键 = `<动作>:<userId>`，额度只认服务端读出来的 userId，前端传什么都不影响」——但那是**有明确额度上限**的限流，不是「一次请求就能锁住后面所有请求」的互斥。

**③ 建议**：锁键必须是 **`(userId, draftId)`** 或更好——**直接用 `request_key` 做去重键**（§4）。若要限并发，用 `rate-limit` 的「每用户每动作」额度，并给它明确的等待/退还语义（`rate-limit.ts:136-149` 的 `RateLimitTicket` 已设计 `refund`）。

## 4. 仓库已经有**数据库强约束**的幂等：方案在重造一个更弱的版本 —— proposal 全篇（本次评审最重要的一条）

**① 问题**：方案没有提到本仓的 `request_key` 幂等体系，而是另起一套内存锁。

**② 后果（核实依据：四处约束、一条链路）**：
1. **评测提交**：`content_submissions` 有 `UNIQUE (submitted_by, request_key)`（`migrations/0001_baseline.sql:321`）——**同键第二次插入在数据库层就不可能成功**。上层 `submit-review.ts:148-191` 先查后写：同键同摘要 → 原样返回既有结果（不重复建快照）；同键**不同**摘要 → `err.keyReused`（:177-180）。**「防重复」与「防篡改」一次做完**，而方案的内存 Set 两样都不做。
2. **草稿保存**：`draft_save_receipts` 主键 `(draft_id, request_key)`（`0001_baseline.sql:215`），并由 `CHECK (result_version = expected_version + 1)`（:217）在**数据库层**钉死「一次保存只推进一个版本」；`reviews/index.ts:630-651` 的「回执优先」保证重试拿到原结果而**不递增版本**。
3. **审计去重**：`operation_records` 的 `UNIQUE(action_type, operation_key)`，`operations/service.ts:97-158` 先查后比摘要（:115-134：同摘要 → replayed；不同摘要 → `keyReused`），`0042_audit_immutable.sql:17-27` 用 `BEFORE DELETE`/`BEFORE UPDATE` 两个触发器**把已消费的 `operation_key` 锁死**——它的头注释（:5-12）写明了原因：**「删除审计行即可让已消费的 operation_key 重新可用」是一条真实的伪造通道**。
4. **快照唯一**：`uq_submissions_review_revision`（`0001_baseline.sql:334-337`，「一份快照只有一条提交」）是幂等的第二道闸。

**对比结论**：「防重复提交」在本仓不是没有，而是**已经有四层**（前端状态 → 服务端幂等键 → 数据库唯一约束 → 审计不可变触发器）。方案第 4 行「用户双击提交按钮会重复创建」——**在当前代码下这个断言不成立**；若确实观察到重复创建，**必然是某个入口没有接 `request_key`**（例如 `reviews/index.ts:528-530` 对「初建草稿没有回执」的 `void requestKey` 说明）。真正该做的是把那个入口接上，而不是再加一个内存 Set。

**③ 建议**：
- 方案改为「**排查并接通未使用 `request_key` 的写入口**」，列出入口清单与每个入口的幂等键来源。
- 加回归断言：同一 `request_key` 连续提交 5 次（含并发），断言数据库里**只有一行**，且 5 次响应的 `submissionId` 完全一致。

## 5. 幂等的「最后一厘米」：并发下「先查后插」仍可能撞唯一约束，方案没定义这一路 —— proposal 全篇

**① 问题**：方案把「检查 → 处理」当成原子，但仓库真正的幂等实现是**先查、后插、由 UNIQUE 兜底**；并发时第二个人会撞约束。

**② 后果（安全面：撞约束的那一次绝不能变成 500）**：
- `submit-review.ts:148-191` 的 `existing` 查询在 `withTransaction` 之前（:149-153），插入在事务内。**两个同键请求并发时**：都查到 `existing === undefined`，都进入事务；第一个插入成功，第二个撞 `UNIQUE(submitted_by, request_key)`（`0001_baseline.sql:321`）。
- 若这个 `SQLITE_CONSTRAINT` 没有被**特异性地**翻译成「重放，返回原结果」，用户会看到 500——**而正确语义是「这次重复提交被幂等地吸收」**。这不是理论问题：`errors-http.ts:120-126` 会把未映射异常记成 `unhandled_error` 并以 500 返回，**它在日志里看起来像一次真实故障**，从而**污染错误率基线**，让真异常被淹没。
- 同理 `uq_submissions_review_revision`（:334-337）撞上时也需要明确翻译。

**③ 建议**：方案必须写清**撞唯一约束 → 回查既有行 → 返回原结果**这条路径，并把它作为幂等的**权威判据**（内存锁只是加速，不是判据）。验收：并发 20 个同键请求，断言 **0 个 500**、数据库 **1 行**、响应 `submissionId` 全一致。

## 6. 内存 Set 无 TTL：漏删的后果是对单个用户的**永久拒绝服务** —— proposal 第 24–28 行

**① 问题**：`inFlight.delete(userId)` 只在 `finally` 里执行；没有 TTL、没有大小上限、没有兜底清理。

**② 后果**：
- 若 `handle()` 返回一个**永不 settle 的 Promise**（下游网络调用没有超时、某个 `await` 悬住），`finally` 永远不执行，**该 `userId` 就永久留在 Set 里** → 该用户之后**所有**写操作都返回 `conflict('请勿重复提交')`，只能等进程重启。这是**一行的可用性故障**，且只对单个用户生效（「只有我提交不了」），排查成本极高。
- Set 没有上限 → 异常路径下的泄漏没有上界。
- 本仓同类组件已经明确处理过这个取舍：`rate-limit.ts:181-184`——「不开启库的定时清理：它会 setInterval，而我们要进程能被干净关掉」，过期的正确做法是**在同一行 SQL 里带 `expire` 判定**（:17-21）。方案把这个问题重新引入了一次，而且更糟（无过期）。

**③ 建议**：若要节流，用 `enforceRateLimit`（有窗口、有过期、跨进程、可退还），**不要**维护进程内状态。

## 7. 前端 `disabled` 的异常路径：失败后必须恢复，否则用户被锁在按钮外 —— proposal 第 11–17 行

**① 问题**：方案的骨架 `setSubmitting(true); await submit(); setSubmitting(false);` **没有 `try/finally`**。

**② 后果**：`submit()` 抛错（网络错误、409 冲突、500）时 `setSubmitting(false)` **不会执行**，按钮**永久禁用**，用户只能刷新页面——而刷新会丢掉未保存的编辑。**这是方案引入的一个新可用性缺陷**，且触发条件恰恰是「提交失败」，也就是最需要重试的时候。仓库里同一位置的真实实现是有保护的：`review-editor.tsx:317-333` 的 `onSave` 用 `finally` 收尾并重置状态（:332-333）。

**③ 建议**：`try { await submit(); } finally { setSubmitting(false); }`——最小修正；但更重要的是**不要把它当作防重手段**（§1）。

---

## 8. 与限流的交互：拦截点位置决定「是否白扣额度」—— proposal 全篇

**① 问题**：方案没有提到频控层，而「重复提交」在这套体系里**本来就有专门的处理路径**。

**② 后果**：`rate-limit.ts:136-149` 定义了 `RateLimitTicket.refund()`，`:284-293` 的 `refundQuietly` 是「业务失败后善后」，`:29-34` 明确写了「被拒的请求也会把原始计数加上去」。这说明本仓在「重复/失败请求如何计费」上已做过取舍：**重复不应消耗额度，失败应退还**。方案的内存 Set 若放在频控**之前**会让这次请求不消耗额度（好事）；若放在频控**之后**就会**白扣一次额度**（`refund` 不会被调用）。方案没写拦截点位置，也就没写清这个取舍。

**③ 建议**：写明「拦截点必须在频控之前，且不消耗额度」；或者干脆**不拦截**，交给幂等键吸收（本仓的既有语义）。

## 9. 验收：方案第 31–32 行的「不会重复提交」无法证伪 —— proposal 第 31–32 行

**① 问题**：「不会重复提交」没有对象、没有条件、没有度量。**② 后果**：无法判断是否做到；更危险的是**内存 Set 在单进程测试里一定「通过」**，从而给出一个假的安全信号。

**③ 建议**（建议直接写进方案）：

| # | 断言 | 场景 |
|---|---|---|
| 1 | 同键 20 并发提交 → 数据库 1 行、**0 个 500**、响应 `submissionId` 全一致 | 绕过前端直接打 API |
| 2 | 同键但内容不同 → `request_key_reused`（**不是**重复创建） | 篡改检测 |
| 3 | **杀掉一个 web 进程后重试** → 仍然幂等 | 证明「重启不丢幂等」（内存 Set 在此必挂） |
| 4 | 同一用户两个标签页并发编辑不同草稿 → **两次都成功** | 证明锁粒度没有误伤 |
| 5 | 提交失败后按钮可再次点击 | 证明 `finally` 生效 |

## 10. 一句话给作者

**「防重复提交」在本仓不是没做，而是已经做了四层**：前端状态（`review-editor.tsx:965`）、幂等键（`submit-review.ts:148-191`）、数据库唯一约束（`0001_baseline.sql:215/321/334`）、审计不可删改触发器（`0042_audit_immutable.sql:17-27`）。**方案第 2 节真正提出的是一个「在单进程、不重启时才成立、以 userId 为粒度、故障时 fail-open」的替身——它比现有机制弱，而它带来的新问题（误锁、永久拒绝服务、绕过频控时的额度误扣）是确定的。** 要做的是找出那个**没有接 `request_key` 的入口**并接上它。
