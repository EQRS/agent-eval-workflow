## 必须发现（L3 层）

### L3 跨模块
- [ ] **user_version 是 schema 版本，被迁移器使用**
  `src/server/platform/migrate.ts` 用 schema_migrations 表记录版本，
  但 `PRAGMA user_version` 是 SQLite 内建的 schema 版本号。
  用它做缓存信号会**与 schema 管理冲突**。

- [ ] **写 user_version 是一个写操作**
  §3 的 `db.pragma("user_version = ...")` 会**触发一次 fsync**。
  失效通知本身就比被缓存的操作贵。

### L4 系统性
- [ ] **缓存的是裸 plugins 表，不含展示字段**
  项目列表页走 `catalog/service.ts` 的 `listPlugins`，
  要 JOIN repositories、计算 4 个相关子查询（公开评测数等）。
  §1 的 `SELECT * FROM plugins` **拿不到页面要的字段**。
  （项目 `plugins` 只有 10 列，展示名/简介在 0005 后才加。）

- [ ] **缓存无上限、无过期清理**
  §1 的 `cache` 是单变量，只会被整体替换。
  但若将来改成按查询参数缓存（分页、筛选），**需要 key 空间管理**。

- [ ] **多进程下 user_version 的读取时机**
  §3 每次请求都读一次 `user_version`（一次 pragma 查询）。
  **这本身是一次库访问**——缓存省下的查询被信号读取抵消一部分。

- [ ] **没有考虑读到的数据被并发修改**
  60 秒窗口内其他用户改了插件，
  **本进程会返回过期数据**。方案说「数据变更时失效」，
  但**只有走 invalidate() 的路径才生效**——
  直接 SQL 改库（运维、迁移脚本）不会触发。
