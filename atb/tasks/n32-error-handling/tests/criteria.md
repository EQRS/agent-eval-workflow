## 前提核实（基础项，0.5 分）

- [ ] **方案假设的东西在本仓库是否真实存在？**
  核对表/列/接口/依赖是否在 `migrations/`、`src/`、`package.json` 中真实存在。
  **注意区分**：方案声明要新建的表（有 CREATE TABLE / ALTER / 明确说「接入」某依赖）属合理；
  引用了不存在的对象且没声明 → 前提不成立。

## 必须发现（每项 1 分）

### 跨系统（真实约束）
- [ ] **C-1 项目已有完整的错误体系，方案是破坏性替换**
  `src/packages/common/errors.ts` 已有 `DomainError` + 稳定错误码，
  `src/server/platform/errors-http.ts` 已有 `STATUS_BY_CODE` 映射与
  `toPublicError` 白名单（只回 code/message，不回堆栈）。

- [ ] **C-2 HttpError 的 message 直接返回客户端，泄露内部信息**
  §3 的 `NextResponse.json({ error: e.message })`——
  **e.message 可能含 SQL 错误、堆栈、内部路径**。
  项目现有 toPublicError 是白名单构造，方案退化成全量透传。
  这是安全倒退。

- [ ] **C-3 丢掉了 code 与 fields，前端契约破坏**
  §3 只返回 `error: message`，丢掉了：
  - 稳定错误码（前端按 code 分支，errors-http.ts:5-6 明确「code 不可随手改」）
  - fields 数组（表单按 path 定位字段，errors.ts:35-40）
  现有前端依赖这两个，方案会让表单错误提示全部失效。

### 性能
- [ ] **P-1 每个 handler 包 try/catch 会掩盖真实异常**
  §3 的兜底 `return 500` 会吞掉所有未知异常的类型信息，
  日志里只剩「服务器错误」，无法定位。

### 跨系统
- [ ] **C-4 项目已有三个错误记录入口，方案要加第四个**
  `errors-http.ts` 的 logUnknownError、`instrumentation-node.ts` 的 onRequestError、
  `server.mjs` 的访问日志。方案新增全局 catch 会造成重复记录或漏记。
