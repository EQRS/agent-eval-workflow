## 必须发现（L3 层）

### L3 跨模块
- [ ] **项目已有启动自检，方案的预热与之冲突**
  `src/instrumentation-node.ts` 已有启动逻辑（selfCheck）。
  方案另起一套预热，**两次启动检查**。

- [ ] **预热调用 listPlugins 会触发大量查询**
  `catalog/service.ts` 的 `listPlugins` 有
  **4 个相关子查询**（`PUBLIC_*_SQL`）。
  启动时跑一次等于**冷启动时的全表扫描**。

### L4 系统性
- [ ] **预热失败退出的策略与部署编排冲突**
  `process.exit(1)` 会让容器**反复重启**：
  - Docker：`restart: unless-stopped` → 无限重启
  - systemd：`Restart=always` → `RestartSec=3` → 每 3 秒一次

  而 `health.ts` 的判据会给容器判 unhealthy，
  **nginx 的 depends_on service_healthy 会让整个入口起不来**。
  项目 `instrumentation-node.ts` 明确**刻意不退出**（可带病启动）。

- [ ] **多进程下预热会跑多次**
  web 与 worker **两个进程**都执行 instrumentation。
  预热在两边各跑一遍 = **双倍开销**。

- [ ] **预热有时间窗口，但方案没有超时**
  §1 的三个 await 若某个挂起（如数据库锁等待），
  启动会**永远卡住**——容器既不 healthy 也不退出。

- [ ] **预热的数据会立即过期**
  §1 预热了 `listPlugins` 的结果，但**没有缓存它**——
  预热完就等于白跑（除非有缓存层，方案没说）。
  真正的收益只能来自「缓冲池变热」，
  而 SQLite 的页缓存**本来就会被首次查询填充**。

- [ ] **预热会掩盖真实的启动问题**
  若数据库损坏，预热会失败并退出——
  但项目设计是**带病启动让 /api/health 报错**，
  而不是拒绝启动。方案改变了这个语义。
