## 前提核实（基础项，0.5 分）

- [ ] **方案假设的东西在本仓库是否真实存在？**
  核对表/列/接口/依赖是否在 `migrations/`、`src/`、`package.json` 中真实存在。
  **注意区分**：方案声明要新建的表（有 CREATE TABLE / ALTER / 明确说「接入」某依赖）属合理；
  引用了不存在的对象且没声明 → 前提不成立。

## 必须发现（每项 1 分）

### 域外知识（法律）
- [ ] **O-1 只扫直接依赖，传递依赖才是主要风险**
  §1 用 license-checker 扫 package.json——该工具默认扫描 node_modules 全部包，
  但**方案措辞是「扫描 package.json」**，若只扫直接依赖会漏掉数百个传递依赖。

- [ ] **O-2 MIT/Apache/BSD 白名单过严，会把正常依赖判违规**
  §2 只允许三种——实际项目常见的合规许可证还有 ISC、0BSD、CC0、Unlicense、
  Python-2.0、BlueOak-1.0.0 等。**过严会导致 CI 长期红灯，最终被无视**。

- [ ] **O-3 许可证合规不等于「不在白名单就禁止」**
  Apache-2.0 有专利条款与 NOTICE 文件要求；BSD 有署名要求。
  **即使许可证在白名单内，仍有具体义务**（保留版权声明、附上 LICENSE 文件）。
  方案把合规简化成「白名单检查」，没有分发时的义务清单。

- [ ] **S-1 没有区分「自用」与「分发」**
  内部使用的 GPL 依赖不触发传染性，**但项目若分发给用户则触发**。
  方案没说清本项目的分发形态，无法判断 GPL 是否真的不能用。

### 对抗性
- [ ] **C-1 许可证可能被上游偷偷改掉**
  供应链攻击的一种形态是维护者改许可证（或包所有权转移后改）。
  方案只扫描当前状态，**没有变更检测**。

### 跨系统
- [ ] **C-2 项目已有 CI，但没有依赖审查机制**
  `.github/workflows/ci.yml` 只跑 typecheck/test/wording，
  方案要加 CI 步骤，但没说失败时怎么办（阻断合并？还是 warn？）。
