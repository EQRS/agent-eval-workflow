## 前提核实（基础项，0.5 分）

- [ ] **方案假设的东西在本仓库是否真实存在？**
  核对表/列/接口/依赖是否在 `migrations/`、`src/`、`package.json` 中真实存在。
  **注意区分**：方案声明要新建的表（有 CREATE TABLE / ALTER / 明确说「接入」某依赖）属合理；
  引用了不存在的对象且没声明 → 前提不成立。

## 必须发现（每项 1 分）

### 域外知识（PIPL 出境规则）
- [ ] **O-1 备份含个人信息，出境需走法定路径**
  备份是**整个数据库**，含 users（nickname/avatar_url）、reviews 正文、comments。
  这些是个人信息。**PIPL 第 38-40 条要求**：
  通过安全评估、认证、或订立标准合同之一，才能向境外提供个人信息。
  方案完全没有这层设计。

- [ ] **O-2 未做个人信息数量评估，无法判断适用哪条路径**
  PIPL 的分档规则与「处理个人信息达到规定数量」相关。
  方案没统计备份里的个人信息量级，无法判断该走哪条合规路径。

- [ ] **O-3 未告知用户，也没有单独同意**
  PIPL 第 39 条要求向个人告知境外接收方名称、联系方式、处理目的、方式、种类、
  以及「向个人行使权利的方式和程序」，并取得**单独同意**。
  方案把这当成纯技术决策。

- [ ] **S-1 境外存储的凭据可能比数据本身更危险**
  §2 用 aws 命令上传，凭据从哪来？若用长期 AK/SK 硬编码或环境变量，
  一旦泄漏，**境外桶可被任意读写**。没有说明凭据管理。

### 跨系统
- [ ] **C-1 项目已有备份机制与文档，方案绕开了既有纪律**
  `scripts/backup.mjs` + `docs/备份与恢复.md` 已定义了备份口径
  （在线热备、integrity_check、manifest、BACKUP_KEEP）。
  方案只说「上传到境外」，没接这套。

- [ ] **C-2 上传失败时备份算成功吗？没有失败处理**
  §2 的 bash 串行执行，aws cp 失败不会让 backup 失败。
  **备份「看起来成功」但境外副本没上去**，这正是备份系统最危险的静默失败。
